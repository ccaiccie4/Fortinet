<h3>Essence</h3><p>EAP-TLS authenticates the endpoint inside RADIUS; RadSec protects the RADIUS transport itself. Those are separate TLS layers with separate certificate roles. A method type 13 error identifies EAP-TLS failure but not whether the root cause is certificate chain, EKU, revocation, time, or fragmentation.</p>
<h3>How it actually works</h3><p>The endpoint exchanges EAP with the NAS, which carries EAP inside RADIUS to FortiAuthenticator. FortiAuthenticator presents the configured EAP Server Certificate and validates the client certificate chain. If RadSec is enabled, the RADIUS messages also travel inside an outer TLS connection using a separate RadSec Server Certificate and client certificate trust.</p>

<h3>Production troubleshooting scenario</h3><p>After a CA rollover, EAP-TLS fails but password-based RADIUS methods still work. The leaf certificate is valid, yet the intermediate CA is missing from the trust chain. In another site, only clients with a larger certificate chain fail across a constrained path; the failure appears during certificate exchange, so EAP fragmentation and MTU become more credible than identity policy.</p>
<h3>Design guidance</h3><p>Operate EAP PKI and RadSec PKI as related but distinct services. Track server certificate expiration, intermediate/root CA changes, revocation dependencies, and client certificate requirements separately for outer and inner TLS.</p>

<div class="tag">FortiPAM · focused stand-alone chapter</div><h2>FortiPAM — Over-the-shoulder monitoring, live-recording pipeline, resource sizing, and finalization</h2>
<div class="src"><b>Primary feature source:</b> Over-the-shoulder monitoring (Live recording)<br><b>Release:</b> FortiPAM 1.9.0<br><a href="https://docs.fortinet.com/document/fortipam/1.9.0/administration-guide/170626/over-the-shoulder-monitoring-live-recording">https://docs.fortinet.com/document/fortipam/1.9.0/administration-guide/170626/over-the-shoulder-monitoring-live-recording</a></div>

<h3>Essence</h3><p>FortiPAM live monitoring has expected pipeline delay because the session must be captured, transmitted, processed, and rendered. The useful distinction is fixed normal delay versus delay that grows over time. Finalized replay is a later stage and can fail even when live monitoring worked.</p>
<h3>How it actually works</h3><p>The privileged session is launched with recording enabled. Activity is captured by the supported agent/session path, sent to FortiPAM, processed for the Active Sessions monitor, and later finalized for replay. Global Live Recording and per-session recording eligibility are both required.</p>

<h3>Production troubleshooting scenario</h3><p>A nine-second stable delay is not a failure if it stays within the documented range. A delay that grows from ten to forty-five seconds as sessions increase is different; it suggests resource or pipeline backlog. If live monitoring works but a replay is missing after abrupt termination, troubleshoot finalization rather than the live stream.</p>
<h3>Design guidance</h3><p>Size the platform for concurrent recorded sessions, not total secrets. Track both live latency and post-session replay success because they validate different stages of the recording pipeline.</p>
