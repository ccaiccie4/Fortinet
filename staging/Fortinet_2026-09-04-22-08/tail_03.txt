<div class="tag">FortiSASE · focused stand-alone chapter</div><h2>FortiSASE — Security posture tags and dynamic Secure Private Access policy enforcement</h2>
<div class="src"><b>Primary feature source:</b> Configuring dynamic private access policies using security posture tags<br><b>Release:</b> FortiSASE 26.1.x<br><a href="https://docs.fortinet.com/document/fortisase/26.1.107/feature-administration-guide/825799">https://docs.fortinet.com/document/fortisase/26.1.107/feature-administration-guide/825799</a></div>
<div class="src support"><b>Scenario support source:</b> FortiSASE ZTNA agent based / agent-less issue<br><a href="https://community.fortinet.com/support-forum-92/fortisase-ztna-agnet-based-agent-less-issue-222561">https://community.fortinet.com/support-forum-92/fortisase-ztna-agnet-based-agent-less-issue-222561</a></div>
<h3>Essence</h3><p>Security posture tags convert endpoint telemetry into dynamic policy input. Authentication and tunnel connectivity do not imply compliance. The tag must be created, the intended private-access policy must match in the correct order, and traffic must still traverse the SPA hub/FortiGate/application path.</p>
<h3>How it actually works</h3><p>FortiClient evaluates endpoint posture and FortiSASE assigns tags such as compliant/non-compliant. Private-access policy uses those tags with user/source, destination, service, and policy order. If allowed, traffic continues through the SPA hub and FortiGate toward the private application. Agentless access uses a different proxy/bookmark workflow and does not automatically provide the same endpoint telemetry.</p>
<div class="figure"><b>Mermaid teaching diagram — synthesized from the feature model</b><pre class="mermaid">flowchart LR
E[Endpoint telemetry] --&gt; T[Posture tag]
T --&gt; P[Private-access policy]
P --&gt; S[SPA path]
S --&gt; H[FortiGate hub]
H --&gt; A[Private app]</pre><p><b>What to notice:</b> the diagram shows the exact product-specific handoffs discussed in this chapter.</p></div>
<h3>Important implementation details</h3><ul><li>Fortinet documents broad Allow-All private access in relevant baseline SPA use cases before posture restriction is added.</li><li>Posture-specific Allow and Deny policies can use dynamic tags as match criteria.</li><li>Policy order matters because a broad allow can match before a posture-specific rule.</li><li>Agent-based and agentless private access should be treated as distinct paths with different prerequisites.</li><li>A correct FortiSASE Allow decision is the handoff point to downstream routing, FortiGate policy, DNS, and application health.</li></ul>
<h3>Configuration / diagnostics</h3><pre class="code"><code>Security posture / ZTNA tagging &gt; define posture checks/tags
Security &gt; Traffic &gt; Policies &gt; Secure private access
Create compliant Allow and non-compliant Deny policies
Place posture rules above broad Allow-All; disable unnecessary broad default</code></pre>
<h3>Evidence interpretation</h3><table class='ev'><tr><th>Observation</th><th>What it proves</th><th>What it does not prove</th></tr><tr><td>Agent is connected</td><td>On-ramp/authentication is working.</td><td>The endpoint has the expected posture tag.</td></tr><tr><td>Compliant tag is present</td><td>Posture evaluation produced the expected tag.</td><td>The intended private-access policy matched.</td></tr><tr><td>Intended Allow policy is logged</td><td>FortiSASE policy allowed the request.</td><td>SPA hub, FortiGate route/policy, DNS, and application are healthy.</td></tr><tr><td>Agent-based works but agentless bookmark fails</td><td>The application can be reached through the agent-based path.</td><td>The agentless proxy path has identical prerequisites.</td></tr></table>
<h3>Production troubleshooting scenario</h3><p>A laptop remains connected after a posture-rule change but loses its compliant tag. Because an Allow-All private policy still exists, access continues. The actual problem is posture tagging plus policy order. In another case the tag and intended Allow policy are both proven, but the private application still fails; the next checks are the SPA hub route, FortiGate policy, DNS, and server. Agentless bookmark failures should be investigated separately from agent-based posture.</p>
<h3>Design guidance</h3><p>Keep posture states simple and auditable. Remove broad fallback rules once the posture design is proven, and test one device in each expected tag state. Separate policy-decision monitoring from downstream private-application availability.</p>
<div class="take"><b>Key takeaway:</b> Security posture tags convert endpoint telemetry into dynamic policy input. Authentication and tunnel connectivity do not imply compliance. The tag must be created, the intended private-access policy must match in the correct order, and traffic must still traverse the SPA hub/FortiGate/application path.</div>
