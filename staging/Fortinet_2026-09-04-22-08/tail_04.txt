<h3>Essence</h3><p>BGP route tags create dynamic SD-WAN destination membership from routing state. The useful sequence is community/route-map policy, installed best path with a FortiOS route tag, dynamic route-tag address membership, and then SD-WAN service matching.</p>
<h3>How it actually works</h3><p>BGP receives candidate routes and attributes. Route-map logic can match a community and set a FortiOS route tag. Best-path selection decides which tagged route is installed. A firewall address object of type `route-tag` represents the installed prefixes with that tag, and an SD-WAN service references the object as its destination.</p>
<div class="figure"><b>Mermaid teaching diagram — synthesized from the feature model</b><pre class="mermaid">flowchart LR
B[BGP route] --&gt; C[Community match]
C --&gt; R[Set route tag]
R --&gt; P[Best path installed]
P --&gt; D[Route-tag address]
D --&gt; S[SD-WAN service]</pre><p><b>What to notice:</b> the diagram shows the exact product-specific handoffs discussed in this chapter.</p></div>
<h3>Important implementation details</h3><ul><li>Fortinet&#x27;s example matches community `30:5` and sets route tag 15.</li><li>`set type route-tag` with `set route-tag 15` creates dynamic address membership from installed routing state.</li><li>BGP Established does not imply the desired prefix was received, selected, tagged, or installed.</li><li>A tagged non-best path may not populate the intended dynamic destination.</li><li>SLA-aware designs can deliberately change BGP community/tag behavior so service eligibility follows path quality.</li></ul>
<h3>Configuration / diagnostics</h3><pre class="code"><code>config router route-map
    edit &quot;comm1&quot;
        config rule
            edit 1
                set match-community &quot;30:5&quot;
                set set-route-tag 15
            next
        end
    next
end
config firewall address
    edit &quot;DataCenter_route_tag_15&quot;
        set type route-tag
        set route-tag 15
    next
end</code></pre>
<h3>Evidence interpretation</h3><table class='ev'><tr><th>Observation</th><th>What it proves</th><th>What it does not prove</th></tr><tr><td>BGP neighbor is Established</td><td>The BGP session is up.</td><td>The desired prefix is installed with the expected tag.</td></tr><tr><td>Received path has community 30:5</td><td>The route arrived with that attribute.</td><td>That path is best or has populated the route-tag object.</td></tr><tr><td>Installed best path has RouteTag 15</td><td>Routing policy and best-path selection produced the expected tag.</td><td>The SD-WAN service matched the current user flow.</td></tr><tr><td>Dynamic route-tag destination is empty</td><td>No currently installed route satisfies that route-tag object.</td><td>SLA thresholds are the cause.</td></tr></table>
<h3>Production troubleshooting scenario</h3><p>A desired BGP path arrives with the correct community, but an untagged path wins best-path. The route-tag dynamic destination stays empty, so lowering SD-WAN SLA thresholds is irrelevant. Fix the route-policy/best-path outcome first. In an SLA-coupled design, a spoke may intentionally change community preference when an overlay fails, causing hub route-tag membership and SD-WAN service eligibility to change.</p>
<h3>Design guidance</h3><p>Document the semantic mapping from BGP community to FortiOS route tag to SD-WAN service. Operations should be able to explain why a prefix entered or left a service without reading the route-map line by line.</p>
<div class="take"><b>Key takeaway:</b> BGP route tags create dynamic SD-WAN destination membership from routing state. The useful sequence is community/route-map policy, installed best path with a FortiOS route tag, dynamic route-tag address membership, and then SD-WAN service matching.</div>
