<div class="tag">FortiGate · focused stand-alone chapter</div><h2>FortiGate — FGSP session synchronization and selective session pickup</h2>
<div class="src"><b>Primary feature source:</b> FGSP<br><b>Release:</b> FortiOS 7.6.6<br><a href="https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/668583/fgsp">https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/668583/fgsp</a></div>
<div class="src support"><b>Scenario support source:</b> Technical Tip: How to verify Sessions are SYNC in HA cluster through CLI<br><a href="https://community.fortinet.com/fortigate-3/technical-tip-how-to-verify-sessions-are-sync-in-ha-cluster-through-cli-177197">https://community.fortinet.com/fortigate-3/technical-tip-how-to-verify-sessions-are-sync-in-ha-cluster-through-cli-177197</a></div>
<h3>Essence</h3><p>FGSP is designed for horizontally scaled FortiGates that forward independently but need to preserve selected stateful sessions when traffic is redirected to another peer. The critical distinction is that FGSP synchronizes session state; it does not perform cluster election or upstream traffic steering.</p>
<h3>How it actually works</h3><p>A session is created on the FortiGate that receives the first packet. That peer performs route lookup, policy matching, NAT, and inspection, then exports eligible session state to the FGSP peer. If the original peer fails, an external load balancer or routing design must redirect the flow. The surviving FortiGate can continue the flow only if it has compatible synchronized state and matching policy/routing/NAT context.</p>
<div class="figure"><b>Mermaid teaching diagram — synthesized from the feature model</b><pre class="mermaid">flowchart LR
C[Client] --&gt; LB[Load balancer]
LB --&gt; F1[FGSP peer 1]
LB --&gt; F2[FGSP peer 2]
F1 &lt;--&gt;|session sync| F2
F1 --&gt; A[Application]
F2 --&gt; A
F1 -. fail .-&gt; X[Down]
LB --&gt;|redirect| F2</pre><p><b>What to notice:</b> the diagram shows the exact product-specific handoffs discussed in this chapter.</p></div>
<h3>Important implementation details</h3><ul><li>`session-pickup` controls the core state synchronization behavior.</li><li>Connectionless traffic, helper-created expectation sessions, NAT state, and delayed TCP pickup are separate controls because they have different continuity and scale implications.</li><li>Delayed pickup is useful when long-lived sessions matter more than short-lived connections; it reduces synchronization churn but intentionally leaves some early/short TCP flows unsynchronized.</li><li>FTP/SIP helper behavior can require expectation-session state in addition to the parent control session.</li><li>Peer configuration must remain compatible enough that a synchronized session can still map to valid policy, interfaces, routes, and translations on the survivor.</li></ul>
<h3>Configuration / diagnostics</h3><pre class="code"><code>config system ha
    set session-pickup enable
    set session-pickup-connectionless enable
    set session-pickup-expectation enable
    set session-pickup-nat enable
end</code></pre>
<h3>Evidence interpretation</h3><table class='ev'><tr><th>Observation</th><th>What it proves</th><th>What it does not prove</th></tr><tr><td>Same flow appears on both peers with synchronized-session indication</td><td>The session state was replicated for that flow.</td><td>The load balancer will redirect correctly, or that NAT/routing is compatible after failover.</td></tr><tr><td>Post-failure packets arrive at the survivor</td><td>The external steering mechanism redirected traffic.</td><td>The survivor has usable state for the flow.</td></tr><tr><td>TCP survives but UDP or helper-created media does not</td><td>Core FGSP and redirection work for at least one session class.</td><td>Connectionless/expectation/NAT pickup is configured correctly.</td></tr><tr><td>Translated tuple changes after failover</td><td>The survivor received traffic but did not preserve the expected translation behavior.</td><td>The root cause is necessarily the load balancer.</td></tr></table>
<h3>Production troubleshooting scenario</h3><p>A payments application keeps long-lived TLS sessions through two FGSP peers. After a peer failure, TLS survives, but SIP media and UDP telemetry reset. Because steering and ordinary TCP state are already working, the investigation should focus on the unsynchronized state classes rather than the load balancer. If a NATed session reaches the survivor but its translated tuple changes, NAT-state synchronization and peer translation symmetry are the next areas to verify.</p>
<h3>Design guidance</h3><p>Use FGSP selectively. Synchronizing every short-lived connection increases CPU, memory, and sync-link load without necessarily improving user experience. Protect flows whose restart cost matters—long database sessions, selected voice/control flows, or stateful application sessions—and validate failover with real traffic classes. Keep peer configuration consistent with FortiManager or another controlled process.</p>
<div class="take"><b>Key takeaway:</b> FGSP is designed for horizontally scaled FortiGates that forward independently but need to preserve selected stateful sessions when traffic is redirected to another peer. The critical distinction is that FGSP synchronizes session state; it does not perform cluster election or upstream traffic steering.</div>

<div class="tag">FortiManager · focused stand-alone chapter</div><h2>FortiManager — Provisioning-template metadata variables, validation, and scope precedence</h2>
<div class="src"><b>Primary feature source:</b> Validate metadata variables in provisioning templates<br><b>Release:</b> FortiManager 7.6.6<br><a href="https://docs.fortinet.com/document/fortimanager/7.6.6/administration-guide/255972">https://docs.fortinet.com/document/fortimanager/7.6.6/administration-guide/255972</a></div>
<div class="src support"><b>Scenario support source:</b> Install Preview Shows No Changes When Global and VDOM Provisioning Templates Are Both Assigned<br><a href="https://community.fortinet.com/fortimanager-27/technical-tip-install-preview-shows-no-changes-when-global-and-vdom-provisioning-templates-are-both-assigned-vdom-enabled-fortigate-229494">https://community.fortinet.com/fortimanager-27/technical-tip-install-preview-shows-no-changes-when-global-and-vdom-provisioning-templates-are-both-assigned-vdom-enabled-fortigate-229494</a></div>
<h3>Essence</h3><p>FortiManager metadata variables let one template produce different values for different devices. The important behavior is target-specific resolution: default values, group mappings, and device overrides are resolved before FortiManager renders candidate CLI and presents validation or Install Preview.</p>
<h3>How it actually works</h3><p>A provisioning template references metadata variables inside supported fields. FortiManager resolves those variables in the target ADOM, applies the most specific mapping, considers the scope that owns the setting, renders target-specific CLI, validates that result, and only then includes it in an installation transaction. Global and VDOM templates can compete for ownership of the same setting.</p>
<div class="figure"><b>Mermaid teaching diagram — synthesized from the feature model</b><pre class="mermaid">flowchart TD
T[Template] --&gt; V[Resolve metadata]
V --&gt; M[Default / group / device mapping]
M --&gt; S{Scope owner}
S --&gt; C[Candidate CLI]
C --&gt; P[Validate / Preview Script]
P --&gt; I[Install]</pre><p><b>What to notice:</b> the diagram shows the exact product-specific handoffs discussed in this chapter.</p></div>
<h3>Important implementation details</h3><ul><li>Device-specific mappings are used for true exceptions; broader group/default mappings reduce per-device configuration sprawl.</li><li>Preview Script is the most useful checkpoint when a variable appears wrong because it shows the rendered candidate, not just the template source.</li><li>A template can be valid globally while one target fails because its metadata resolution differs.</li><li>Global-versus-VDOM scope can explain a missing Install Preview delta even when connectivity and the template are otherwise healthy.</li><li>FortiManager meta fields and metadata variables are different features; a field being called &#x27;meta&#x27; does not mean it can be substituted in a provisioning template.</li></ul>
<h3>Configuration / diagnostics</h3><pre class="code"><code>Policy &amp; Objects &gt; Advanced &gt; Metadata Variables
Device Manager &gt; Provisioning Templates &gt; More &gt; Validate
Inspect resolved values and Preview Script
Re-validate
Install Preview / Install</code></pre>
<h3>Evidence interpretation</h3><table class='ev'><tr><th>Observation</th><th>What it proves</th><th>What it does not prove</th></tr><tr><td>99 devices validate, one fails variable resolution</td><td>The shared template is broadly valid and the failing target differs in metadata resolution.</td><td>The failing FortiGate is unreachable.</td></tr><tr><td>Preview Script shows the intended target-specific CLI</td><td>Variable resolution and rendering are correct for that target.</td><td>The device has successfully installed or is running that configuration.</td></tr><tr><td>VDOM edit does not appear while Global template owns the same setting</td><td>The effective candidate is controlled by scope precedence.</td><td>FGFM must be down.</td></tr><tr><td>Install completes successfully</td><td>FortiManager delivered the configuration transaction.</td><td>The resulting FortiGate feature is operational end-to-end.</td></tr></table>
<h3>Production troubleshooting scenario</h3><p>A branch template uses a loopback metadata variable. One device fails validation while 99 peers pass. The correct first check is that device&#x27;s mapping and Preview Script, not the shared template. In another case, a VDOM template change never appears in Install Preview because a Global template defines the same setting; removing the scope conflict in a lab demonstrates why the lower-scope change was never candidate configuration.</p>
<h3>Design guidance</h3><p>Use metadata where values genuinely vary—site addresses, loopbacks, tunnel endpoints, branch IDs, or credentials—not for every possible field. Prefer defaults and group mappings; track device-level overrides as exceptions. Make validation and Preview Script review a pre-install gate, especially across mixed FortiOS versions.</p>
<div class="take"><b>Key takeaway:</b> FortiManager metadata variables let one template produce different values for different devices. The important behavior is target-specific resolution: default values, group mappings, and device overrides are resolved before FortiManager renders candidate CLI and presents validation or Install Preview.</div>

<div class="tag">FortiAnalyzer · focused stand-alone chapter</div><h2>FortiAnalyzer — Report Guidance, Analytics-log dependencies, retention, and No Data isolation</h2>
<div class="src"><b>Primary feature source:</b> Report Guidance<br><b>Release:</b> FortiAnalyzer 7.6.7<br><a href="https://docs.fortinet.com/document/fortianalyzer/7.6.7/administration-guide/385104/report-guidance">https://docs.fortinet.com/document/fortianalyzer/7.6.7/administration-guide/385104/report-guidance</a></div>
<div class="src support"><b>Scenario support source:</b> FortiAnalyzer reports do not contain data of required time period<br><a href="https://community.fortinet.com/fortianalyzer-6/troubleshooting-tip-fortianalyzer-reports-do-not-contain-data-of-required-time-period-190624">https://community.fortinet.com/fortianalyzer-6/troubleshooting-tip-fortianalyzer-reports-do-not-contain-data-of-required-time-period-190624</a></div>
<h3>Essence</h3><p>Report Guidance explains which log types and fields a report element expects and whether the required Analytics data is available. This is important because a report queries Analytics data, while older raw logs may still exist in Archive storage.</p>
<h3>How it actually works</h3><p>Logs are generated on source devices, ingested by FortiAnalyzer, and retained as Analytics and/or Archive data according to storage policy. Report charts and macros query Analytics tables using specific fields and filters. Report Guidance exposes that dependency so `No Data` can be traced to source logging, Analytics retention, field availability, scope, or rendering.</p>
<div class="figure"><b>Mermaid teaching diagram — synthesized from the feature model</b><pre class="mermaid">flowchart LR
S[Source logs] --&gt; I[Ingestion]
I --&gt; A[Analytics]
I --&gt; R[Archive]
A --&gt; G[Report Guidance]
A --&gt; D[Dataset/chart]
D --&gt; F[Time/device filters]
F --&gt; O[Report]</pre><p><b>What to notice:</b> the diagram shows the exact product-specific handoffs discussed in this chapter.</p></div>
<h3>Important implementation details</h3><ul><li>A report can be empty for a historical period even though older raw logs are retained.</li><li>ADOM storage allocation and ingestion volume determine how many Analytics days remain queryable.</li><li>One empty chart does not imply the whole reporting engine is broken; its required log type or fields may differ from the rest of the report.</li><li>Report time range and device/ADOM scope are independent of whether the logs exist.</li><li>Database rebuild is appropriate only after the storage/data condition has been diagnosed.</li></ul>
<h3>Configuration / diagnostics</h3><pre class="code"><code>Reports &gt; Report Definitions &gt; All Reports &gt; Config Recommendation
Inspect Item Title, Device Type, Log Type, Log Fields, Analytics availability
# Later remediation only when justified:
execute sql-local rebuild-db
diagnose sql status rebuild-db</code></pre>
<h3>Evidence interpretation</h3><table class='ev'><tr><th>Observation</th><th>What it proves</th><th>What it does not prove</th></tr><tr><td>Report Guidance says required Analytics data unavailable</td><td>The report element lacks its required Analytics input.</td><td>The source device produced no logs at all.</td></tr><tr><td>Older raw logs exist but Analytics retention is only three days</td><td>Data was retained, but the reportable Analytics window is shorter than requested.</td><td>The report schedule itself is wrong.</td></tr><tr><td>Dataset returns rows but chart is blank</td><td>Input data and query are working at least partially.</td><td>The rendering/output stage is healthy.</td></tr><tr><td>Only one report section is empty</td><td>The failure may be specific to that section&#x27;s log type/fields or filter.</td><td>FortiAnalyzer reporting as a whole is unavailable.</td></tr></table>
<h3>Production troubleshooting scenario</h3><p>A 30-day executive report contains only three days of data. Older raw events are still present, but the ADOM retains only about three Analytics days because of storage pressure. Increasing report time range cannot recover Analytics data that has aged out. In another report, only an application-control chart is empty; Report Guidance shows that the required app-control logs/fields are missing while traffic logs are present.</p>
<h3>Design guidance</h3><p>Plan FortiAnalyzer capacity around required Analytics days, not only raw disk size or events per second. For important reports, document each chart&#x27;s log type, fields, and retention requirement so changes in FortiGate logging or ingestion volume can be evaluated before they shorten reportable history.</p>
