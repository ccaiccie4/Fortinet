LESSON 01 · FortiGate

VPNv4/VPNv6 route-reflector next-hop-self

Mechanics diagram: Standalone SVG · Editable draw.io

Mechanics

A route reflector reduces the iBGP full-mesh requirement by reflecting routes between clients. Reflection does not guarantee that a reflected route's NEXT_HOP is reachable. In an MPLS L3VPN, a VPNv4 or VPNv6 route can retain the originating PE's next-hop address. The receiving PE may learn the VPN NLRI but lack a transport route to that PE, leaving a control-plane route that cannot forward. This is distinct from a route-target import problem: route targets decide which VPN routes enter a VRF; NEXT_HOP determines where the packet is sent.

FortiOS 8.0 adds next-hop-self-rr-vpnv4 and next-hop-self-rr-vpnv6. Enabled on a neighbor or neighbor group, the RR rewrites the NEXT_HOP to its local interface address when advertising the corresponding VPN address family. The older next-hop-self-rr behavior applied to IPv4/IPv6 unicast, not VPNv4/VPNv6. The new controls are independent so the RR can rewrite one VPN family without changing another.

Configuration

config router bgp
 config neighbor-group
  edit "VPN-PE-CLIENTS"
   set remote-as 65000
   set route-reflector-client enable
   set next-hop-self-rr-vpnv4 enable
   set next-hop-self-rr-vpnv6 enable
  next
 end
end

Use neighbor-group scope for a consistent PE population and neighbor scope for exceptions. The RR's local interface address must be reachable through the transport network. The command does not create an underlay route, distribute a label, import a route target, or repair a missing VPN address-family activation.

Verification and troubleshooting

Start with get router info bgp summary. Inspect the VPN route's received/advertised NEXT_HOP at the RR and client, then use get router info routing-table all to confirm the installed gateway and recursive resolution. An Established session proves peer transport and OPEN negotiation; a route in the VPN BGP table proves NLRI reception; neither proves a usable FIB next hop. If the route is absent, investigate RT import/export, address-family activation and route policy. If present but recursion fails toward the originating PE, apply the AF-specific RR rewrite and confirm the RR address is reachable. A historical Community case documents the old command not changing VPNv4 NEXT_HOP; the 8.0 feature is the direct correction, not a generic route-map workaround.

Scale, HA and change control

On a large RR, neighbor-group scope prevents per-peer drift, but confirm the group is inherited by the intended VPN clients and not by route-server or non-VPN peers. The rewrite is an advertised attribute, so inspect both the RR's outbound UPDATE and the client's received route; a local configuration line alone does not prove the peer received it. In HA designs, validate the active RR's selected interface address and transport reachability after failover. If the local address changes across members, clients must still have a route to the address the active node advertises. Preserve route-target and label checks as independent gates: a correct next hop cannot compensate for an absent label or a route that was never imported into the VRF.

Primary Fortinet documentation: https://docs.fortinet.com/document/fortigate/8.0.0/new-features/47101/next-hop-self-support-for-vpnv4-and-vpnv6-route-reflectors

LESSON 02 · FortiManager

FortiSASE multi-instance central management across FortiCloud organizations

Mechanics diagram: Standalone SVG · Editable draw.io

Object model and trust boundary

FortiManager 8.0 can add multiple FortiSASE instances as managed devices in Device Manager. Each FortiSASE instance remains an isolated service environment; FortiManager provides a common configuration-management plane. This is a managed-device workflow, not merely the older Fabric View connector. Each instance is assigned to an ADOM, allowing tenant configuration to be separated by administrative domain.

Eligibility follows FortiCloud organization ownership. If FortiManager and FortiSASE share a FortiCare account, the key field can be blank. If they use different accounts but the FortiSASE account is within an allowed child OU/sub-OU hierarchy, enable Central Management on the SASE tenant and generate a FortiManager Key from Central Management Settings. The key is non-expiring until revoked; it does not bypass the OU relationship. A FortiManager in a parent OU can manage eligible child tenants, but unrelated sibling OUs are not automatically trusted.

Registration and synchronization

  1. Select a supported ADOM.
  2. Open Device Manager > Devices & Groups and choose Add FortiSASE Device.
  3. Use a unique name for every SASE instance.
  4. Supply connector settings and, when required, the FortiManager Key generated on FortiSASE.
  5. Review the objects to synchronize and complete registration.

FortiSASE cannot be added to a 7.0 ADOM, Global Database ADOM, or Backup-mode ADOM; once added, the device cannot simply be moved to another ADOM. Central-management synchronization is one-way from FortiManager to FortiSASE. Treat FortiManager as the source of truth for synchronized objects and do not delete objects there as a casual cleanup step. ZTNA telemetry is a separate relationship used to exchange endpoint tag/client mapping; a working central-management channel does not prove that telemetry is flowing.

Operational diagnosis

For add failures, verify FortiCare account equality or OU ancestry before regenerating keys. Then check whether the key was revoked, whether the ADOM mode/version is supported, and whether the device name is unique. After onboarding, confirm the instance appears in the intended ADOM and inspect the synchronization task. Verify the resulting object on FortiSASE; registration alone does not prove every object was accepted. For ZTNA, separately validate telemetry and tag mapping. The Community sweep found recent FortiManager FDS/FGFM/ADOM issues, but none directly matching this multi-instance OU/key workflow, so no unrelated scenario is presented as direct evidence.

Tenant lifecycle and operational guardrails

Plan the ADOM assignment before onboarding because the documented workflow does not support casually moving an already registered SASE instance to another ADOM. Use one ADOM per instance when the tenant separation model requires independent object namespaces, and avoid reusing names across tenants even when the ADOMs differ. A FortiManager Key is a connector credential: store it as a secret, revoke it on tenant offboarding, and do not assume key rotation changes the FortiCloud OU relationship. After a bulk object push, compare the task result with the SASE tenant's resulting objects and test a policy that consumes them. If the management sync succeeds but ZTNA tags are stale, troubleshoot the telemetry path and FortiGate tag-consumer authorization separately rather than repeating the configuration push.

Primary Fortinet documentation: https://docs.fortinet.com/document/fortimanager/8.0.0/administration-guide/907875/adding-fortisase

LESSON 03 · FortiAnalyzer

SAML administrator SSO: SHA-256/SHA-512 signing and digest migration

Mechanics diagram: Standalone SVG · Editable draw.io

Authentication flow

FortiAnalyzer can be a SAML Identity Provider (IdP) or Service Provider (SP). In an SP-initiated flow, the browser sends an AuthnRequest to the IdP, the administrator authenticates, and the IdP returns a signed Response/Assertion to the SP. FortiAnalyzer validates the signature and digest, maps the asserted identity, and applies the local administrator profile and ADOM scope. In a Security Fabric, FortiGate can act as IdP and FortiAnalyzer as a Fabric SP, simplifying access after the administrator has authenticated to the root FortiGate.

FortiAnalyzer 8.0 removes SHA-1 support for SAML signatures and digests. IdP and SP settings support RSA-SHA256 or RSA-SHA512 as the Signature Algorithm and SHA256 or SHA512 as the Digest Method. The two ends may use different supported choices because the SAML trust model is asymmetric. Do not confuse the signature algorithm with the digest method: one describes the signing operation, the other the hash used over the signed content.

Configuration and authorization

Under System Settings > SAML SSO, select IdP or SP, choose the corresponding certificate, and set signature and digest options. For an SP, verify browser-reachable address, entity ID, ACS/login URL, SLS/logout URL, IdP certificate, and signing requirements for AuthnRequest, assertion, and logout messages. The admin must exist on both sides unless a supported wildcard SSO admin is configured. SAML attributes such as username, profilename, and adoms map identity to local authorization. A valid assertion can still produce an access problem if the local profile or ADOM is absent or mismatched.

Evidence boundaries

Use a browser SAML tracer to inspect issuer, audience, destination, ACS, RelayState, certificate, signature and digest. get system saml shows configuration; diagnose system admin-session list confirms the resulting SSO user, profile and ADOM. A signature-validation error points toward certificate/algorithm mismatch. A missing RelayState or incorrect ACS points toward IdP application URLs, not a need to weaken cryptography. The Community article found during discovery is older and focuses on RelayState/Reply URL; it is included as an adjacent diagnostic boundary, not as a SHA algorithm incident. Keep a tested local fallback admin while migrating from SHA-1 and test both IdP- and SP-initiated login before removing it.

Certificate rollover and break-glass planning

During algorithm migration, update the IdP and SP deliberately and keep the old certificate available until a successful round-trip test completes. Certificate validity, issuer trust, key usage, entity ID, audience, and ACS URL are independent checks; passing one does not imply the others. If the SP validates the assertion but the user is denied, inspect local administrator creation, wildcard-admin policy, profile mapping, and ADOM assignment. If the browser loops back to the IdP, inspect RelayState and destination URLs before changing signature settings. In HA or multi-node deployments, confirm every node presents the expected metadata/certificate so a failover does not reintroduce the old algorithm or certificate. Preserve a tested local emergency administrator with a limited profile until SAML is stable.

Primary Fortinet documentation: https://docs.fortinet.com/document/fortianalyzer/8.0.0/new-features/462409/saml-sso-supports-sha-256-and-sha-512-for-both-idp-and-sp

LESSON 04 · FortiSwitch

BGP per-neighbor local-AS identity for multi-AS transitions

Mechanics diagram: Standalone SVG · Editable draw.io

Why neighbor-specific AS identity matters

During a merger, private-AS cleanup, or staged migration, a switch may need to present a temporary AS to one peer while retaining its real global BGP AS for other peers. FortiSwitchOS 8.0 allows a BGP speaker to belong to multiple autonomous systems through per-neighbor local-AS behavior. This is not a second BGP process. The global set as and router ID still define the process; local-as changes the identity presented to a particular neighbor.

The local-AS and its no-prepend/replace controls influence the AS_PATH advertised to that peer. This is security- and loop-prevention-sensitive: the wrong combination can expose an unexpected global AS, hide an AS that downstream policy expects, or cause a peer to reject a route as a loop. The global AS remains mandatory; local-AS is a neighbor-scoped compatibility mechanism.

Configuration pattern

config router bgp
 set as 65001
 set router-id 1.1.1.1
 config neighbor
  edit "10.0.0.2"
   set remote-as 65002
   set local-as 1500
   set local-as-no-prepend enable
   set local-as-replace enable
  next
 end
end

Use the FortiSwitchOS 8.0 CLI Reference for exact syntax on the target build; do not copy FortiGate-only local-as-replace-as syntax without checking. The FortiSwitch guide uses local-as-replace. The feature is model-limited, so confirm the supported hardware list before designing around it.

Verification

Use get router info bgp summary for session state and get router info bgp neighbors for peer detail. Inspect advertised routes and the remote peer's received AS_PATH. An Established session proves OPEN negotiation succeeded, not that the peer accepts routes. If the table is empty, inspect AS_PATH loop detection, local-AS prepend/replace behavior, route maps, and eBGP policy. FortiSwitchOS 7.2.2+ enables ebgp-requires-policy by default, so explicit policy may be needed before eBGP routes are learned or advertised. Test one peer at a time during migration and preserve the global ASN for all unaffected sessions. No directly matching FortiSwitch Community case was verified in the 30-day sweep.

Migration and policy boundaries

Do not change the global ASN merely to satisfy one partner; that alters every BGP adjacency and can trigger route withdrawal or loop detection elsewhere. A local-AS transition should be documented per neighbor with the peer's expected OPEN ASN and exact outbound AS_PATH. No-prepend and replace controls are not interchangeable: one suppresses an extra local-AS prepend while the other changes which AS is exposed. Validate the resulting path at the remote peer rather than inferring it from configuration. If the peer comes up but routes are absent, inspect route maps and the eBGP policy requirement before changing local-AS. During migration, keep a rollback path that restores the previous neighbor identity without touching unrelated peers.

Primary Fortinet documentation: https://docs.fortinet.com/document/fortiswitch/8.0.0/fortiswitchos-administration-guide/939734/parts-and-terminology-of-bgp

LESSON 05 · FortiAP/Wireless

Wi-Fi 7 Multi-Link Operation on FortiAP K-series

Mechanics diagram: Standalone SVG · Editable draw.io

MLO mechanics and model limits

802.11be Multi-Link Operation creates one logical multi-link association between a capable station and AP. Instead of treating 2.4, 5 and 6 GHz as unrelated SSIDs, the client and AP coordinate link identities under a Multi-Link Device (MLD). Multiple links can improve throughput, latency and reliability, but a client does not necessarily transmit on every band at every moment; negotiated capabilities and scheduling determine actual link use.

FortiAP-K models running FAP 7.6.3 or later support MLO. FortiOS 8.0 adds GUI configuration. Local standalone MLO requires FAP 7.6.5 or later. FAP-221K/222KL support 2.4/5 GHz but not 6 GHz; FAP-231K, 23JK, 241K, 243K and 244K support all three; FAP-441K/443K support 5/6 GHz but their 2.4-GHz radio is not Wi-Fi 7 and cannot join the MLO set.

Security and radio configuration

MLO is enabled on the VAP/SSID and then applied to the desired radios in a WTP profile. Supported security modes include WPA3-SAE, WPA3 Enterprise Only and OWE. For WPA3-SAE, use H2E-only; FortiOS automatically enables the H2E-only behavior when SAE is selected. Each radio must advertise a compatible 802.11be band. A non-MLO client may still connect using ordinary single-link behavior, so association success alone is not proof of MLO.

config wireless-controller vap
 edit "VAP1"
  set ssid "VAP1"
  set security wpa3-sae
  set sae-h2e-only enable
  set mlo enable
 next
end

For local standalone Bridge-mode SSIDs, also enable local-standalone, local-bridging and local-authentication. Authentication is then handled locally on the AP, allowing MLO service to continue if the controller is unreachable; the MLO flag alone does not provide standalone survivability.

Evidence and troubleshooting

diagnose wpa wpad mld displays the MLD, num_links and link IDs. On the AP, vcfg | grep mlo confirms the VAP setting. These prove configured/associated link state, not maximum throughput. Check model/radio support, firmware, client capability, WPA3/H2E, and WTP profile assignment before changing RF settings. No directly matching recent Community MLO failure scenario was found, so the lesson is grounded in the official FortiAP configuration guide and FortiOS 8.0 feature guide.

RF planning and client interoperability

MLO is an association capability, not a promise that all bands have identical channel width, power, or airtime. The AP model determines which radios can participate; the client determines which links it can negotiate. A tri-band model does not guarantee a tri-link session if the client supports only two links or the channel plan excludes a supported band. Keep SSID security consistent with MLO prerequisites and do not troubleshoot client fallback as an RF fault until WPA3/H2E and firmware requirements are confirmed. In controller-managed designs, validate the WTP profile actually applied to the AP, not only the global VAP object. In standalone mode, local authentication and bridge configuration must be present before testing controller-loss behavior.

Primary Fortinet documentation: https://docs.fortinet.com/document/fortiap/8.0.0/fortiwifi-and-fortiap-configuration-guide/677212/configuring-wi-fi-7-multi-link-operation

LESSON 06 · FortiNAC

Certificate-backed server trust and allowed-serial admission control

Mechanics diagram: Standalone SVG · Editable draw.io

Two independent trust gates

FortiNAC 9.4.3+ strengthened communication between Manager and managed servers and between primary/secondary HA appliances. A peer must present an acceptable certificate and its appliance serial must be authorized. IP reachability alone is insufficient. License keys generated with certificates have been available since 2020; older appliances may still have keys without the needed certificate material. VM appliances can download a current application VM license key after confirming the product record has the correct UUID and eth0 MAC. Older hardware or split Control/Application appliances may require exchanging self-signed certificates.

The keystore relationship is directional: the Manager must trust each managed appliance, and each managed appliance must trust its Manager. In an HA Manager deployment, managed servers need certificates for both Manager members. The Manager's allowlist contains all managed server serials. Each managed server lists the Manager serials. A primary HA server lists the Manager serials plus the primary and secondary server serials; the secondary receives configuration from the primary.

Configuration and evidence

execute enter-shell
globaloptiontool -name security.allowedserialnumbers -setRaw "FNVX-CAxxxxxxx1,FNVX-CAxxxxxxx2"

Use real appliance serials; these are placeholders. The command may print a warning that the option is unknown. Do not treat that warning alone as failure: read the value back using globaloptiontool -name security.allowedserialnumbers. Confirm System Summary reports Certificates=Yes and use licensetool to list certificate serials. On older appliance types, keytool -list -v can inspect /bsc/campusMgr/.keystore; the Manager should contain managed-appliance certificates and managed servers should contain Manager certificates.

Troubleshooting

A recent Community case describes FortiNAC-OS servers that could not be added to a CentOS-based Manager because the allowed serial list was incomplete. When a server disappears or synchronization stops after an upgrade, compare software versions, certificate presence, and role-correct lists on every appliance before changing routes or restarting services. Make HA changes on the primary and verify replication to the secondary. A successful certificate import proves trust material exists; it does not prove the peer serial is authorized. Both certificate trust and serial admission must pass.

Upgrade and HA sequencing

Before upgrading a multi-server deployment, inventory every appliance serial, role, software version, certificate-bearing license key, and keystore relationship. The Manager's list is not symmetric with a managed server's list; copying one list to every appliance can omit peers or authorize more peers than intended. In an HA pair, the primary's configuration is replicated, but each appliance still has its own certificate identity. After upgrade, test a managed-server add/sync operation and inspect unauthorized-connection events from the remote IP and serial. If the serial list reads correctly but the peer still fails, inspect certificate chain/keystore and version compatibility; if the certificate is present but the serial is absent, correct admission control rather than re-importing the certificate.

LESSON 07 · FortiNAC-F

FortiNAC-F multi-tenant VDOM integration with shared FortiLink infrastructure

Mechanics diagram: Standalone SVG · Editable draw.io

Architecture and ownership

The FortiNAC-F 7.6.5 integration guide describes shared physical access infrastructure with tenant-specific logical networks. FortiGate root/MGMT VDOM owns FortiLink and manages shared FortiSwitch/FortiAP devices. Tenant VDOMs own their VLANs and policy boundaries. FortiSwitch ports can be exported from root into tenant VDOMs; tenant SSIDs can be created in tenant VDOMs while APs remain managed from root. A VDOM link connects the contexts. Tenant traffic toward external services, including FortiNAC, traverses that link and is subject to root-side policy.

FortiNAC-F discovers root and tenant VDOMs as virtualized devices. When a host connects, FortiNAC identifies the VDOM associated with the port and selects the logical-network VLAN for that tenant. Therefore, VDOM context is part of the NAC placement decision; a correct VLAN ID in the wrong VDOM is still the wrong network.

Build sequence

  1. Confirm the FortiSwitch is managed by FortiLink.
  2. Create tenant VDOM and VDOM link.
  3. Create tenant VLAN interfaces on FortiLink; configure DHCP relay toward FortiNAC if it provides DHCP.
  4. Set the tenant default virtual-switch VLAN.
  5. Export the access port from root to the tenant with set export-to "tenantA".
  6. Configure policies and static routes on both sides of the VDOM link.
  7. In FortiNAC, open Network > Inventory > Virtualized Devices, select the tenant VDOM, and map Registration/Remediation/Production logical networks to tenant VLAN IDs.
config ports
 edit "port12"
  set export-to "tenantA"
 next
end
config system interface
 edit "tenantA-registration"
  set vdom "tenantA"
  set interface "fortilink"
  set vlanid 21
  set dhcp-relay-service enable
  set dhcp-relay-ip 192.168.2.2
 next
end

Failure isolation

An exported port is grayed in root and visible in the tenant. If it remains only in root, inspect the export assignment. If the host lands in the wrong VLAN, inspect the tenant virtual-device mapping. If DHCP fails, trace VLAN interface, relay target, VDOM link, routes and policies on both VDOMs. FortiNAC-F 7.6.5+, FortiGate 7.2.9+ (port-name update from 7.4.9+) and FortiSwitch 7.2+ are documented baselines. No direct recent Community tenant-placement case was verified; the lesson follows the official integration guide.

Routing and DHCP dependencies

The VDOM link is both a routing and policy boundary. A tenant default route commonly points toward root, while root needs routes back to tenant VLAN subnets through the VDOM link. Policies must permit DHCP relay, DNS, FortiNAC, and upstream services in the correct direction on both VDOMs. Exporting a port changes logical ownership; it does not automatically create the tenant VLAN, DHCP scope, firewall policy, or return route. Keep VLAN IDs/names consistent with FortiNAC Model Configuration and validate registration, remediation, and production VLANs independently. If a host receives an address but cannot reach NAC, trace relay, VDOM link, route, and policy path.

LESSON 08 · FortiAuthenticator

RADIUS client groups and authentication-profile policy selection

Mechanics diagram: Standalone SVG · Editable draw.io

Object roles

FortiAuthenticator 8.0.2 adds RADIUS client groups and a separate Authentication Profiles tab. A RADIUS client is a NAS device that sends Access-Requests; it is not an end user or user group. Each client definition includes an IP/subnet/range and shared secret, with optional attributes for user IP and device MAC. A client group packages several NAS definitions so policies can reference a set of APs or switches instead of selecting hundreds individually. The authentication profile defines the credential type and authentication behavior; the policy binds that profile to the client population and request criteria.

Policy selection order

When an Access-Request arrives, FortiAuthenticator identifies the client by source IP. If client definitions overlap, the narrowest matching address range wins. It then evaluates policies: the source client must be included directly or through a client group; optional RADIUS attribute criteria must match; and the request credential type must match the policy (Password/OTP, EAP-TLS, EAP-TEAP or MAB). If no policy matches, FortiAuthenticator returns an authentication failure. If multiple policies match, the one closest to the top of the list wins. A correct group membership therefore does not guarantee that the intended policy wins.

Configuration and verification

  1. Create precise RADIUS client objects with correct source ranges and unique secrets.
  2. Create client groups under Authentication > RADIUS Service > Clients > Group.
  3. Create reusable profiles under Authentication > RADIUS Service > Auth Profiles.
  4. Create ordered policies that reference clients/groups, optional attributes and the right profile.
  5. Test a request from each representative NAS and verify Accept/Reject and returned attributes.

When enabled, the Message-Authenticator requirement causes requests without that attribute to be discarded. FortiAuthenticator logs client/policy changes and restarts the RADIUS server to apply them; schedule bulk edits and watch the service log. A packet arriving at the RADIUS interface proves reachability only. An Access-Reject may occur before the user password or certificate is evaluated if no policy matches. Inspect source IP, NAS attributes, policy order, client-group membership and profile binding before troubleshooting the identity source. No direct recent Community case for this specific group/profile workflow was verified.

Policy design and packet-level checks

Keep client groups narrowly defined by NAS role or site; a group is an administrative selector for RADIUS clients, not an identity group returned by LDAP or Active Directory. Use attributes such as NAS-Identifier or Called-Station-Id only when the NAS reliably populates them, and avoid broad policies with overlapping client groups and attribute conditions. If Message-Authenticator is required, validate every NAS includes it; a missing attribute can cause a request to be discarded before password/certificate validation. After policy edits, account for the RADIUS daemon restart and test one request per client type. Compare source IP, NAS attributes, credential type, matched policy, profile, and returned attributes to distinguish a client-selection error from an identity-store failure.

Primary Fortinet documentation: https://docs.fortinet.com/document/fortiauthenticator/8.0.2/administration-guide/622363/clients

LESSON 09 · FortiPAM

Launcher process matching for Java and multi-process applications

Mechanics diagram: Standalone SVG · Editable draw.io

Why executable matching fails

Traditional application launchers identify the target by the initial executable. That is unreliable for Java applications and IDEs that spawn children, rename windows, or use a generic process such as java.exe. FortiPAM 1.9 supports Default, Window Title and Command Line matchers. Default uses the initial launch process. Window Title applies a regular expression to the GUI title. Command Line applies a regular expression to the process execution string, which is useful when Java arguments distinguish the application.

Security controls coupled to custom matching

When matcher type is not Default, FortiPAM forces Multi-process Mode and Full-screen Recording to Enabled. The client must watch the whole process tree to locate a child process, and full-screen capture preserves the audit trail when the target window changes or is only part of a larger desktop. These are mandatory security behaviors, not optional performance preferences.

config os_app
 edit 1
  set multipleprocess enable
  set fullscreen-record enable
  set proc-matcher-type window-title
  set proc-matcher-pattern "^Vision Client.*"
 next
end

The CLI hides proc-matcher-pattern when matcher type is Default. Use a narrow anchored expression against a stable title or command-line token. A broad expression such as .* can bind the launcher to unrelated windows. For a Java process with stable arguments, command-line matching may be more reliable than a title that changes by document or workspace.

Verification

Test the actual launcher path, not a manually started executable. Confirm the parent and child process appear, the matcher selects the intended app, and the resulting recording captures the entire desktop and relevant child window. A successful launch does not prove the matcher selected the intended process; a recording file does not prove it captured the correct context. If the app is missed, compare the actual title/command line to the regex and confirm multi-process mode. If dialogs or child windows are absent from the audit trail, verify full-screen recording before changing the matcher. No direct recent Community scenario was found; this lesson uses the FortiPAM 1.9 Administration Guide.

Audit completeness and regex safety

Choose Window Title when the GUI title is stable across launches; choose Command Line when a process argument uniquely identifies the application. Titles can change with active document, server name, or version, while command lines can contain variable paths and tokens. Anchor the pattern to stable substrings and test positive and negative examples so another application is not captured. Because custom matching forces multi-process mode and full-screen recording, validate the resulting session record, not merely the launcher's success message. The matcher identifies which process/window represents the protected app; it does not replace checkout approval, credential controls, or recording retention policy.

LESSON 10 · FortiSIEM

Python custom threat-feed integration and update semantics

Mechanics diagram: Standalone SVG · Editable draw.io

Ingestion pipeline

FortiSIEM can ingest external indicators through a Python integration. The scheduled threat-feed task invokes a plugin, the plugin retrieves and normalizes source content, and the AppServer parses CSV records into an IOC group. The documented integration directory is /opt/phoenix/data-definition/threatfeedIntegrations/. The feed configuration identifies URL, optional credentials, plugin type, SSL verification, plugin name and update mode. Create the destination group under the matching category: Malware IPs, URLs, Domains or Hashes.

A successful HTTP download is not a successful import. The Python plugin must normalize the feed to the expected CSV format and indicator type. It should handle HTTP errors, authentication failures, empty responses, duplicate indicators and malformed rows explicitly. Do not silently emit an empty CSV when a fetch fails; a Full update could interpret that as a valid empty snapshot.

Full versus Incremental

Full treats the feed as a replacement snapshot. Incremental adds new records to the existing group. If the publisher returns only a daily delta, Full can remove previously valid indicators. If the publisher returns a complete snapshot, Incremental can leave stale indicators unless a separate lifecycle process removes them. Choose the mode based on the publisher's contract, not response size.

Build and troubleshoot

  1. Create the correct IOC group.
  2. Place the Python plugin in the documented directory and ensure the FortiSIEM runtime can execute it.
  3. Configure URL and credentials, select Python, and keep SSL Verify enabled unless repairing a trust problem.
  4. Select Full or Incremental according to source semantics and set the schedule.
  5. Run a controlled refresh and compare source records with imported rows.

When a task runs but the group is empty, separate retrieval, transformation and AppServer parsing. Check URL/credentials/TLS, script path/permissions, CSV columns and escaping, and destination indicator type. If old records disappear, inspect Full versus Incremental first. Community search found older FortiGuard IOC validation guidance but no direct recent Python-plugin failure scenario; no unrelated article is represented as a direct case.

Feed quality, freshness and safety

Normalize indicators before import: trim whitespace, canonicalize domains, validate IP syntax, remove comments, and reject rows that do not belong to the destination IOC type. Preserve stable identifiers when the publisher provides them so incremental updates do not create duplicates. Use TLS verification and rotate feed credentials through the approved secret process. Set a schedule that matches the publisher's update cadence, then monitor last successful execution and age of the newest imported indicator. A green task status with unchanged group count can mean the source returned no new data; it is not necessarily an ingestion failure. A successful fetch with malformed CSV is not a successful intelligence update.

LESSON 11 · FortiSASE

Event-triggered vulnerability scanning after software changes

Mechanics diagram: Standalone SVG · Editable draw.io

Trigger model

FortiSASE endpoint Protection profiles support scheduled scans and event-driven scans. Event-based scanning can run when an endpoint connects to FortiSASE, its operating system is updated, or vulnerability signatures are updated. The separate Trigger vulnerability scan on software change control runs when new software is installed and detected, existing software is updated, or a potentially unwanted application (PUA) is detected. This closes the timing gap between weekly/monthly scans and application changes that occur shortly after the scheduled assessment.

Configuration boundaries

In the assigned endpoint profile, open Protection > Scan for Vulnerabilities. Enable Event-based scanning for connection/OS/signature events and enable Trigger vulnerability scan on software change for application inventory changes. Scheduled scanning remains complementary and can be Weekly, Daily or Monthly. Vulnerability popups and automatic patching are separate controls: a scan discovers findings; a popup notifies the user; patching changes software only when the patch workflow is configured and supported. Do not infer that enabling a scan trigger automatically installs a fix.

Some related controls have release constraints. The documented Show vulnerabilities popup is limited to new instances on the specified 25.4.c v7.4-or-later track supporting FortiClient 7.4. Confirm tenant and agent versions before assuming a control exists.

Verification

Use a lab endpoint and a controlled software install/update or PUA detection. Confirm inventory reports the change, a scan timestamp follows it, and the vulnerability result is visible. If no scan occurs, verify endpoint profile assignment, trigger enablement, agent inventory reporting and endpoint connectivity. If findings exist but the endpoint remains vulnerable, inspect patching separately. A software inventory event proves detection, not scan completion; a scan result proves assessment, not remediation. No directly matched recent FortiSASE Community case was verified for this trigger.

Endpoint coverage and remediation boundary

Event-driven scanning complements rather than replaces a scheduled baseline. Scheduled scans cover devices that remain online without inventory events; event triggers shorten the detection gap after connection, OS/signature update, software install/update, or PUA detection. Ensure the endpoint profile is assigned to the device group and the agent reports inventory changes. If the endpoint is offline or inventory reporting is delayed, the trigger cannot fire immediately. Keep scan result, user notification, and patch deployment as separate operational states. When a vulnerability is found, verify whether a patch exists, whether automatic patching is enabled for that endpoint/profile, and whether installation completed; do not report assessment as remediation.

LESSON 12 · Secure SD-WAN

ToS-mask matching for selective SD-WAN packet duplication

Mechanics diagram: Standalone SVG · Editable draw.io

Packet path and matching

SD-WAN packet duplication sends copies of selected traffic over multiple zone members to improve delivery probability. The destination FortiGate can de-duplicate copies before forwarding. FortiOS 8.0 adds Type of Service matching to duplication rules. The tos field is an 8-bit pattern and tos-mask identifies the bits evaluated. With tos 0x77 and tos-mask 0xff, the full byte must match 0x77. Rules can also constrain source/destination addresses, interfaces and services. This is different from FEC: duplication sends copies of the original packet, while FEC adds recovery information.

Sender configuration

config system sdwan
 set status enable
 set duplication-max-num 4
 config duplication
  edit 1
   set srcaddr "172.16.205.0"
   set dstaddr "172.16.202.0"
   set srcintf "port5"
   set service "PING"
   set tos 0x77
   set tos-mask 0xff
   set packet-duplication force
  next
 end
end

The zone must contain intended members with valid routes. duplication-max-num limits the number of zone members used for copies; member order matters if more eligible members exist than the configured maximum. Use narrow matching and a deliberate maximum because duplication consumes bandwidth and processing capacity.

Receiver and proof

The receiving FortiGate needs a corresponding rule with the same ToS pattern and packet-de-duplication enable. The default discrepancy window is 250 ms (documented range 250–1000 ms); paths with larger delay differences can affect duplicate suppression. Sender and receiver rules describe traffic in their own directions, so do not copy interface names blindly.

The Fortinet example tests a non-match (ping ToS 0x00) and a match (0x77). Use packet captures on multiple members and at the receiver. A successful ping alone proves connectivity, not duplication. Check zone membership, routes, source/destination/service, ToS/mask, duplication maximum and receiver de-duplication. No direct recent Community case for ToS-mask duplication was verified; the lesson is grounded in the FortiOS 8.0 New Features and Administration Guides.

Capacity, timing and test discipline

Duplication multiplies traffic on selected zone members. The maximum member count is 2–4 (default 2); with a value of 3, the original plus two copies are created. Member order matters when more paths are eligible than the limit. The receiver's discrepancy window controls how far apart copies can arrive and still be treated as duplicates; the documented default is 250 ms, with a 250–1000 ms range. Test matching and non-matching ToS values for IPv4 and IPv6 where used. Capture on each sender member and at the receiver. If a ping succeeds but no copy appears on a second path, the test proves reachability only. If the receiver emits duplicates, inspect its rule and timing window before increasing sender copies.

Primary Fortinet documentation: https://docs.fortinet.com/document/fortigate/8.0.0/new-features/293842/tos-based-sd-wan-duplication-matching
