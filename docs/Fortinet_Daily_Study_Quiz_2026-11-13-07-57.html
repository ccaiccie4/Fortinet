FortiGate · FortiOS 8.0.0

Central SNAT map selection with dynamic external IP-feed sources

Use a changing external IP list as a central SNAT source selector while keeping security-policy authorization and translation-rule selection separate.

Purpose and control boundary Central SNAT moves source-address translation out of the per-firewall-policy NAT checkbox and into an ordered translation table. It is useful when many security policies should authorize traffic independently of which public address or IP pool is used for egress. FortiOS reads central SNAT maps from top to bottom and applies the first matching entry. The security policy is still evaluated first; central SNAT then selects translation behavior for an admitted session. A policy hit therefore proves that traffic was authorized, not that the intended central SNAT row matched.

Dynamic source membership FortiOS 8.0 allows an IP address external-feed connector to be used as the source address in a central SNAT map. The feed is represented by an address external-resource object. The map references that object in orig-addr or orig-addr6, so membership can change when the feed is refreshed without editing a static address group. The external-resource must be an address feed, not a URL/domain feed, and the IPv4 or IPv6 field must match the traffic family. A dual-stack design may need separate IPv4 and IPv6 objects or map entries.

Enable and configure deliberately Central NAT is not enabled by default in ordinary profile-based NGFW mode. Enabling it changes the source of truth: the NAT option in IPv4 firewall policies is skipped and SNAT is performed through central-snat-map. Policy-based NGFW mode implicitly uses central NAT. Before changing an established firewall, inventory policy-level NAT and IP pools, enable central NAT in a maintenance window, then build explicit maps in the required order.

config system settings
    set central-nat enable
end
config system external-resource
    edit "Partner-Egress-Feed"
        set type address
        set resource "https://feeds.example.invalid/partner-egress.txt"
    next
end
config firewall central-snat-map
    edit 10
        set srcintf "lan"
        set dstintf "wan1"
        set orig-addr "Partner-Egress-Feed"
        set dst-addr "all"
        set nat enable
        set nat-ippool "Partner-Public-Pool"
    next
end

Matching and evidence A central SNAT entry can constrain incoming/outgoing interfaces, original source and destination addresses, protocol, original source port and destination port, then select an IP pool and translated port behavior. The first matching row wins. A broad row placed above a narrow feed-backed row can shadow it even when the feed is healthy. Translation is not a substitute for routing: the selected egress interface and next hop still need to be reachable, and the security policy must permit the original flow.

Inspect the external-resource object and confirm its last refresh and parsed address family. Use diagnose firewall iprope list 10000d to inspect compiled central SNAT entries and confirm the expected feed object appears in the active map. Then generate a new session and inspect the session/NAT table for the translated source and selected pool. The iprope output proves the map is compiled; it does not prove a particular live session matched it. A session entry proves the translation selected for that flow; it does not prove the feed will remain current.

Operational failure pattern If a partner reports that only some egress sources are translated, compare the original source address with the feed contents, then inspect row order and interface constraints. If the map is present but never matches, check address family and whether the feed contains prefixes or host entries in the format FortiOS accepts. If the policy accepts but the session keeps its original source, verify central NAT is enabled and that the intended map is above any broader matching row. Keep the feed URL reachable, monitor refresh age, and treat a stale feed as security-control drift rather than assuming a successful policy hit is sufficient.

FortiManager · FortiManager 7.6.5

Script object types and execution-target boundaries

A FortiManager script is not just text: its language and Run Script on target determine which database or live device context can execute it.

Why target semantics matter FortiManager stores scripts inside an ADOM context (or the Global Database ADOM) and uses the script type and target to determine where the content is interpreted. The three script types are CLI, Tcl and Jinja. They are not interchangeable wrappers around the same execution engine. A script can be syntactically valid yet be unusable for the selected target because the interpreter and execution context do not match.

CLI scripts have three distinct targets A CLI script can run against the Device Database, a Policy Package or ADOM Database, or a remote FortiGate directly through its CLI. These targets have different operational meanings. Device Database execution changes the configuration model held by FortiManager; it is not the same as sending commands immediately to the appliance. Policy Package/ADOM Database execution changes the centrally managed object context. Direct remote execution sends CLI commands to the live FortiGate and can therefore create a device-side change outside the normal package installation transaction. Know which source of truth is being changed before clicking Run Script.

Tcl and Jinja are constrained FortiManager documents Tcl scripts as remote-FortiGate-direct-only. Jinja scripts run only on the ADOM Database. Only CLI scripts are supported in the Global Database ADOM, and Global Database scripts can target only the Policy Package or ADOM Database. These constraints are enforced by the Run Script on selection; they are not merely recommendations. A common design error is to create a Jinja template and then expect it to execute directly on a FortiGate, or to use Tcl against the ADOM database.

Validation has a boundary The script editor can validate CLI syntax. Validate on change is available for CLI scripts and rechecks the script when it is edited. Validate device platform lets the administrator select the platform used for syntax validation. Advanced Device Filters can narrow device selection by platform, build, device, hostname or serial number. These checks reduce obvious mismatches, but a successful syntax check does not prove that a command is supported by every target build, that a variable resolves as intended, or that a live device will accept the operation in its current state.

config system interface
    edit "port3"
        set alias "Branch-Uplink"
    next
end

Operational workflow Create the script under Device Manager > Scripts (or Policy & Objects > Scripts in the Global Database ADOM). Select its type, then select Run Script on. Validate using the intended platform/build, choose a narrow device group or policy package, run it, and inspect execution history. For direct execution, compare live FortiGate configuration before and after. For database execution, compare the FortiManager database or package and then perform the normal install workflow if the change is intended for production.

Troubleshooting and safety If the target selector does not offer the desired context, check script type and ADOM rather than assuming a GUI defect. If the script reports success but the live device is unchanged, it may have modified the Device Database or ADOM Database instead of the remote FortiGate. If validation passes but execution fails, inspect platform/build, device filters, permissions and the execution result. Keep scripts idempotent, avoid broad filters for destructive commands, and treat direct remote execution as a separate change path that requires its own audit and rollback plan.

FortiAnalyzer · FortiAnalyzer 8.0.0

Real-time log forwarding: filters, masking and reliable TCP buffering

Forwarding mode exports incoming logs as they arrive; it differs from scheduled FAZ-to-FAZ aggregation and has its own filtering, buffering and receiver-authorization behavior.

Two modes, two transaction models FortiAnalyzer supports forwarding and aggregation. Forwarding is the default and sends logs in real time or near real time as the source receives them. Aggregation is a scheduled transfer between FortiAnalyzer units: the client stores logs and later sends records not already present on the server. Aggregation is CLI-only, requires the receiving FortiAnalyzer to accept aggregation, and does not support syslog or CEF destinations. Do not troubleshoot forwarding as though it were aggregation; the server prerequisites and delay model are different.

Forwarding is configured on the source The client creates a Log Forwarding entry under System Settings > Advanced > Log Forwarding. Destination type can be FortiAnalyzer, Syslog, Syslog Pack, Common Event Format (CEF), or an output plugin. For plugin forwarding, an output profile must exist first. Syslog/CEF types expose a server port; FortiAnalyzer destinations use the FortiAnalyzer protocol and do not expose the same port setting. Sending frequency is available for FortiAnalyzer destinations and can be real time, every minute or every five minutes (the documented default).

Reliable transport and buffering Reliable Connection uses TCP instead of UDP. When the connection drops, logs are buffered and automatically forwarded when connectivity returns; Fortinet documents a 12 GB buffer limit. RELP is not supported. UDP avoids the TCP connection but does not provide the same retransmission and backlog behavior. TCP is therefore safer for a syslog/CEF receiver that supports it, but it is not infinite storage: a prolonged outage can fill the buffer, after which the sender cannot preserve all backlog.

Filtering is part of the data pipeline Device Filters select which managed devices are forwarded. Log Filters can use All or Any conditions. Exclusions can remove device types, log types or selected fields. Masking replaces selected field values before the remote system receives them and uses a data-mask key. This is a privacy and data-minimization control, not a transport-encryption feature. When IP address fields are filtered with Equal to or Not equal to, wildcard and subnet values are not supported. For a subnet such as 172.10.0.0/16, use a regex with Contain/Not contain semantics rather than assuming CIDR matching works in an equality field.

Receiver-side state When forwarding to another FortiAnalyzer, devices whose logs are forwarded are added on the receiver as unauthorized devices. The receiver must authorize them before its normal device-management workflows treat them as trusted. A sender showing a configured destination does not prove the receiver has accepted or indexed the data. Check the forwarding entry, connection state, source backlog, receiver device authorization and timestamps of arriving logs.

config system log-forward
    edit 1
        set mode forwarding
        set fwd-server-type syslog
        set server-addr "192.0.2.50"
        set fwd-reliable enable
    next
end

Operational diagnosis If the remote SIEM is missing only certain events, inspect device filters, All/Any logic, exclusions and masking before changing network rules. If logs arrive in bursts after an outage, inspect TCP buffering and receiver indexing delay. If logs never arrive, verify destination type, port, route, TLS trust (where enabled) and receiver status. Use get system log-forward to inspect configured forwarding IDs, then compare sender state with receiver timestamps. A successful TCP connection proves transport establishment, not that the filter admits every desired event or that the remote parser recognizes each field.

FortiSwitch · FortiSwitchOS 7.6.3

LACP aggregator selection, fallback and per-flow member hashing

A trunk can be up while traffic is uneven or a peer is silently operating in fallback; understand aggregator choice separately from per-flow member selection.

What a FortiSwitch trunk represents A link aggregation group combines physical ports into one logical interface. FortiSwitch supports standard LACP in active and passive modes, plus static aggregation and Fortinet trunk mode. Active LACP sends control PDUs; passive LACP responds when the peer initiates. Static mode ignores and does not send LACP control messages. Fortinet trunk mode uses heartbeat packets to determine member availability. These modes are not interchangeable: static aggregation can appear configured while the far end has a different bundle definition, and passive/passive peers may never initiate negotiation.

Aggregator selection is not member hashing If LACP trunk members negotiate different speeds, FortiSwitch groups ports with the same negotiated speed into separate aggregators. Only one aggregator is used by the trunk. The aggregator-mode setting decides which group wins: bandwidth selects the aggregator with the greatest total bandwidth (the documented default), while count selects the aggregator with the most ports. This is a control-plane decision about which speed group is active. After an aggregator is selected, port-selection-criteria chooses a member for each flow using source/destination IP or MAC fields. A four-member bundle does not guarantee every single TCP flow uses all four links.

Hash entropy matters If many clients connect to one server, a source-only or destination-only hash can concentrate traffic on a small subset of members. A source-and-destination IP or MAC tuple generally provides more variation when the workload has diverse endpoints. Hash selection is per flow to preserve packet ordering; a single large flow remains constrained by one physical member. Aggregate throughput can be high across many flows while one transfer is limited to one member's capacity.

LACP fallback is a bootstrapping feature Starting in FortiSwitchOS 7.4.0, a selected fallback port can remain up when no LACP PDUs arrive, allowing a non-LACP peer (for example, a PXE environment) to reach the network. In fallback, the selected port is up and other members are blocked. When LACP PDUs return, the trunk transitions back to LACP. The delay is 90 seconds with slow LACP and 30 seconds with fast LACP. Do not mistake fallback for a healthy negotiated bundle.

Important constraints Fallback cannot be combined with min_bundle or max_bundle, cannot be used in an MCLAG split-brain state, and should not be configured on both switches of an MCLAG pair. The LACP peer-consistency check reports a mismatch if both MCLAG switches use fallback. Member withdrawal behavior also matters: when control packets are lost, the trunk can block or forward on a withdrawn member depending on configuration. That choice changes the risk between blackholing and forwarding on a link whose control-plane status is uncertain.

config switch trunk
    edit "uplink-lag"
        set mode lacp-active
        set lacp-speed fast
        set aggregator-mode bandwidth
        set port-selection-criteria src-dst-ip
        set members "port1" "port2" "port3" "port4"
    next
end

Verification Check trunk membership, negotiated speed, actor/partner LACP state and per-port counters. A logical trunk up state proves some aggregation is active; it does not prove all intended members joined the selected aggregator or that traffic is balanced. Compare member counters during multiple independent flows. If one member carries everything, check hash inputs and traffic diversity before changing LACP timers. If the peer appears online only during fallback, investigate why LACP PDUs are absent rather than accepting fallback as normal operation.

FortiAP/Wireless · FortiAP/FortiWiFi 7.6.1

SSID VLAN pools: AP-group mapping versus client load balancing

A single tunneled SSID can distribute associated clients across multiple VLANs, or map VLANs by FortiAP group, without multiplying SSIDs.

Why pool VLANs A VLAN pool lets one SSID represent multiple client subnets. This can reduce the need to create many nearly identical SSIDs and can distribute a large wireless population across smaller broadcast domains. FortiGate automatically creates a zone associated with the SSID interface when load-balancing VLANs are configured; the zone name is based on the SSID interface followed by .zone. Each VLAN still needs its own network interface, addressing, DHCP options and firewall-policy treatment. A pool is a selection mechanism, not an automatic replacement for the L3 and security design of each subnet.

Two different purposes share the pool object FortiAP group assignment maps an AP group to a specific VLAN. It is useful when floors, buildings or sections should use the same SSID but separate subnets by AP location. Each AP belongs to one FortiAP group. Load-balancing pools instead distribute new clients among multiple VLANs. Fortinet documents round-robin selection as choosing the least-busy VLAN (the one with the smallest client count). Hash selection chooses a VLAN based on a hash of the current SSID client count and number of VLAN entries; the GUI describes the result as a consistent VLAN choice for a specific device. Do not confuse location-based segmentation with client-population balancing.

Mode and method constraints VLAN-pool load balancing is available only for tunnel-mode SSIDs. FortiAP dynamic user VLAN documentation states that RADIUS-based VLAN assignment and VLAN pooling cannot be used simultaneously for the same SSID. If a deployment requires RADIUS attributes to assign a user's VLAN at authentication, use that mechanism rather than assuming the pool will be layered on top. If the pool contains no valid VLAN ID, FortiGate falls back to the SSID's static VLAN ID setting. This fallback can make a broken pool look like a working SSID while all clients land in one subnet.

config wireless-controller vap
    edit "Staff-WiFi"
        set vlan-pooling round-robin
        config vlan-pool
            edit 101
            next
            edit 102
            next
            edit 103
            next
        end
    next
end

Build the downstream network first Create the VLAN interfaces and DHCP scopes for every pool member, verify that the AP-to-FortiGate tunnel can carry the VLANs, and apply the intended policy controls to each subnet. If the SSID uses FortiAP group mapping, ensure group names match the pool entries and AP membership is correct. If the SSID uses load balancing, confirm the selected method is supported in the traffic mode and that the pool has valid VLAN IDs.

Verification and troubleshooting Inspect the VAP's VLAN-pooling mode and entries, then check the automatically generated SSID zone and member VLAN interfaces. Associate a test client and inspect which VLAN it receives, its DHCP lease, gateway and firewall policy. Repeat with multiple clients to observe distribution. A client receiving an address proves DHCP worked on the selected VLAN; it does not prove every pool member is valid or that the intended balancing method is active. If all clients land in the static VLAN, inspect invalid pool entries and AP-group references. If a RADIUS-assigned VLAN is expected, verify VLAN pooling is not also enabled for that SSID.

FortiNAC · FortiNAC 9.4.7

LDAP Organizational Unit mapping into User/Host Profiles and FSSO

FortiNAC 9.4 adds OU mapping to User/Host Profiles and includes OU context in FSSO updates sent to FortiGate alongside user groups and device tags.

What changed in 9.4 FortiNAC 9.4 adds User Organizational Unit (OU) LDAP mapping in User/Host Profiles. Fortinet states that FortiNAC sends the OU to FortiGate through FSSO communication alongside the FortiGate Device Tag and User Group. The value is that directory placement can become part of identity context, rather than relying only on a user name or broad security group. Two users may belong to the same AD group but reside in different administrative OUs that represent different trust boundaries or support organizations.

Keep the identity pipeline separate from enforcement The conceptual flow is directory lookup/synchronization, FortiNAC user record and User/Host Profile mapping, then FSSO identity publication to FortiGate. The OU is directory metadata. It is not itself a VLAN, RADIUS tunnel attribute or firewall policy. FortiNAC network access policies and FSSO publication are separate decision points: a profile can classify identity context, while FortiGate consumes FSSO information to apply firewall policy. Do not assume that adding an OU criterion automatically changes a switch port's VLAN.

Why OU mapping is operationally useful Group membership is often coarse and stable, while OU structure may reflect organizational ownership, delegated administration or a more precise placement hierarchy. OU mapping can preserve that context as users move between organizational containers. It also introduces a dependency on directory synchronization and consistent OU data. If an OU is renamed or a user is moved, the old context may remain visible until directory information is refreshed and the FSSO update is sent.

Design the match carefully Identify the exact LDAP OU value FortiNAC receives and how the User/Host Profile expresses the mapping. Avoid using a display name or broad substring that can match multiple directory branches. If nested OUs are present, decide whether the intended policy should match the leaf OU, a parent OU or a normalized attribute. Keep profile rules understandable so a user does not unexpectedly match a broad profile before the intended OU-specific profile.

Verification chain Inspect the remote LDAP user record and confirm the expected OU is populated. Next inspect the FortiNAC User/Host Profile mapping and resulting user context. Then verify the FSSO connection and confirm FortiGate receives the expected user, group and device-tag/OU information. Finally check which FortiGate identity-based policy matches. Each stage proves something different: LDAP data proves directory visibility; FortiNAC profile data proves mapping; FSSO state proves publication; FortiGate policy logs prove enforcement. A successful LDAP bind alone does not prove the OU is mapped or sent.

Troubleshooting pattern If a user authenticates but FortiGate applies the broad group policy, compare the OU at the directory, FortiNAC and FortiGate stages. If the LDAP record is correct but FortiNAC is stale, investigate the synchronization rule and refresh cycle. If FortiNAC has the OU but FortiGate does not, inspect FSSO connectivity and user update events rather than editing firewall policies blindly. If FortiGate sees the attribute but the wrong rule wins, check the identity source and policy order. The release note identifies the enhancement but does not specify every LDAP polling interval or nested-OU normalization behavior.

FortiNAC-F · FortiNAC-F 7.6.0

IP-phone voice VLAN provisioning with Local RADIUS attributes

FortiNAC-F returns separate data and tagged voice VLAN attributes for profiled IP phones through Local RADIUS, with optional MAC-notification-driven revalidation.

Use case and prerequisite Many access ports carry a workstation and an IP phone. The phone needs a tagged voice VLAN while the workstation behind it remains in the data VLAN. FortiNAC-F can dynamically provision the voice VLAN through RADIUS, but the documented integration requires the Local RADIUS option for the standard workflow. Build the network access policy first: the User/Host Profile must identify the IP phone (Device Type = IP Phone is the simplest documented match), the Logical Network must represent the voice VLAN, and the Network Access Configuration must assign the data VLAN's logical network.

RADIUS response construction In Network > Inventory, select the switch model and open Model Configuration. Enable RADIUS authentication for the device and select Local. Configure logical-network access values for host states. For the tagged voice VLAN, create a custom RADIUS Attribute Group and return the standard tunnel attributes: Tunnel-Medium-Type = IEEE-802, Tunnel-Type = VLAN, and Tunnel-Private-Group-Id = %ACCESS_VALUE%. Fortinet's IP-phone integration example also adds Cisco-AVPair = device-traffic-class=voice so a Cisco phone/switch can distinguish the voice service. The data VLAN remains represented by its own logical network and RFC VLAN attribute group.

Transaction flow The phone connects to the switch; the switch sends a RADIUS Access-Request; FortiNAC evaluates the host profile and network access policy; Local RADIUS returns Access-Accept with VLAN attributes; and the switch interprets the tunnel attributes to place the phone in the tagged voice VLAN. The workstation behind the phone can continue using the data VLAN. A policy match without the correct attribute group is not enough: the RADIUS response must contain the expected VLAN ID and voice-class value, and the switch must support the returned attributes.

Real-time refresh FortiNAC can process IP-phone MAC notification traps to update connectivity information and revalidate phones when they connect or disconnect. The integration guide cautions that some phones generate frequent notification traps; each trap requires processing and can create unnecessary work. Enable MAC Notification Trap Processing only when real-time voice provisioning/revalidation is needed. It is not a generic performance enhancement to turn on for every switch.

Configuration and verification Create the phone profile, voice logical network and policy; map the correct RADIUS attribute group to the logical network; verify the switch model uses Local RADIUS and that the shared secret matches on the switch and FortiNAC. Capture a RADIUS exchange during a test phone connection. Inspect the Access-Accept for Tunnel-Type VLAN, Tunnel-Private-Group-Id and Cisco-AVPair. Then inspect the switch port's voice VLAN and the phone's DHCP lease. A phone obtaining an address proves some VLAN and DHCP path worked; it does not prove the tagged voice VLAN was assigned if the phone fell back to the native/data VLAN.

Failure isolation If the phone receives the data VLAN but not voice, verify the host profile and policy match first, then the Access Value and custom attribute group, then the RADIUS response, and finally switch interpretation. If the Access-Accept has no VLAN attributes, confirm Local RADIUS is selected and the logical network has the expected attribute group. If attributes are present but the phone stays untagged, validate switch vendor/model behavior and the voice-class attribute. If updates lag after a phone move, inspect MAC notification trap reception and avoid enabling trap processing indiscriminately on noisy phone models.

FortiAuthenticator · FortiAuthenticator 6.6.10

Self-service password recovery with SMS or FortiToken verification

Password recovery is a separate pre-login transaction: portal policy exposes methods, user records or LDAP sync rules enroll recovery channels, and rate limiting protects the workflow.

Separate recovery from normal login MFA FortiAuthenticator 6.6.3 adds SMS and FortiToken verification as password-recovery methods in the user portal, with rate limiting in the enhanced reset workflow. This does not mean that every user who can log in with MFA automatically has a recovery channel. The administrator controls which methods are offered at the portal level, while the user record or remote LDAP synchronization rule determines which recovery methods are available to that user.

Portal-level control When Password Reset is enabled under the portal's Pre-Login Services, a Verification methods option determines which recovery methods can be used before authentication. The portal policy is the outer gate. If password reset is disabled or a method is not allowed by the portal, the end user will not be offered that method even if the user has a phone number or FortiToken. This prevents a user-specific enrollment from silently expanding the public pre-login surface.

User enrollment and LDAP sync The user record includes Password Recovery Options for SMS and FortiToken. The remote LDAP sync rule also has corresponding Password recovery by SMS and Password recovery by FortiToken options, while email recovery is renamed Password recovery by email. The end user sees the available methods in the Account Info tab of the user portal. For remote LDAP accounts, the sync rule can populate recovery options, but the password update itself has directory dependencies. FortiAuthenticator documents remote LDAP password reset without the old password as an LDAPS-only operation and requires the LDAP bind account to have permission to reset the user's password. A domain join or secure LDAP setup is also required for the documented AD password-change workflows, depending on the path used.

Recovery transaction The user selects Password Reset, chooses one of the permitted factors, receives an SMS or FortiToken challenge, completes verification, and proceeds to the password update. The verification factor establishes control of the enrolled channel; it does not prove that the downstream directory will accept the new password. For an AD-backed account, the directory's password policy and bind account rights still govern the final update. Rate limiting constrains repeated recovery attempts, so repeated resend requests may be throttled even when the phone or token is valid.

Operational configuration Enable Password Reset and the desired verification methods in Authentication > Portals > Portals. Configure SMS recovery or FortiToken recovery on each relevant user, or in the remote LDAP sync rule for synchronized users. Verify that the SMS provider is operational and that the user has a current mobile number; verify FortiToken assignment and activation before relying on token recovery. For remote LDAP password changes, test LDAPS trust and bind-account password-reset permissions in a controlled account before exposing the method broadly.

Troubleshooting evidence If the user sees only email recovery, compare the portal's allowed methods with the user record and LDAP sync rule. If SMS is offered but not delivered, inspect the SMS gateway/provider path and phone number rather than changing LDAP permissions. If FortiToken verification succeeds but the password update fails, inspect LDAP/AD write permission, LDAPS connection and password policy. If attempts are temporarily blocked, respect the rate-limit window instead of repeatedly resending challenges. A successful SMS or token check proves the recovery factor; it does not prove the password update committed to the authoritative directory.

FortiPAM · FortiPAM 1.9.0

Native RDP TCP forwarding: compatibility path and security-control trade-offs

FortiPAM 1.9.0 can route native RDP launcher traffic through TCP forwarding for compatibility, but this changes the launcher path and removes several native RDP controls.

Why the option exists FortiPAM 1.9.0 adds a TCP Forwarding option when a secret has RDP Service enabled. Enabling it routes RDP traffic through TCP forwarding in a manner consistent with an Other clientType launcher. Fortinet documents three use cases: bypassing the certificate-revocation-check failure warning during native launch, connecting to a legacy or third-party RDP server that only supports plain-text RDP, and working around a native launch failure caused by a recent RDP protocol change. It is a compatibility path, not a general recommendation to weaken every RDP session.

Native and forwarded paths differ The native RDP launcher exposes RDP-specific security settings. Best Effort uses NLA when the server supports it and otherwise uses standard RDP authentication over TLS. NLA forces CredSSP. TLS uses an encrypted RDP-over-TLS connection. The RDP option is standard RDP encryption without TLS and is documented for Web-RDP only. The native path can also expose Restricted Admin Mode, Auto TOTP and Block Clipboard controls. TCP forwarding changes the data path, so FortiPAM does not support RDP Security Level, RDP Restricted Admin Mode, RDP Auto TOTP or Block Clipboard for native RDP launchers when this option is enabled.

Security decision The key question is whether the immediate compatibility requirement outweighs the loss of native launcher controls. If a certificate revocation check fails, first determine whether the target certificate chain, CRL/OCSP reachability and trust configuration are correct. TCP forwarding may allow a session to proceed, but it does not repair certificate trust or prove the remote endpoint is trustworthy. If Restricted Admin Mode or clipboard blocking is mandatory, keep TCP forwarding disabled and resolve the native RDP prerequisite instead. For a legacy endpoint that cannot negotiate the required native path, document the exception and limit who can use the secret.

Configuration workflow Edit the secret under Secrets > Secrets, enable RDP Service, then review TCP Forwarding. Confirm the target address, port and intended launcher type. Test with a dedicated low-privilege account and confirm the session reaches only the approved target. Record the reason for enabling forwarding, the controls no longer available, the target owner and the planned retirement date for the compatibility exception.

Verification and diagnosis Verify the secret's RDP Service and TCP Forwarding settings, then inspect the resulting session/launcher path. If native launch fails with a certificate revocation warning, verify certificate-chain trust and revocation-service reachability before using forwarding as a temporary workaround. If a third-party server accepts only legacy RDP, confirm the limitation is on the target side and that the TCP-forwarded path is approved. If a user expects Auto TOTP or clipboard blocking but cannot select them, check whether TCP Forwarding is enabled; the missing control is an intentional feature boundary, not necessarily a UI defect.

Operational guardrail Treat native RDP and TCP-forwarded RDP as separate security profiles. Use secret policy and folder permissions to restrict access to compatibility secrets. Review session recordings and logs, but do not assume a recording restores controls that the launcher no longer enforces. After the target is upgraded or its certificate issue is corrected, disable TCP Forwarding and re-test native security settings.

FortiSIEM · FortiSIEM 7.5.1

Discovery orchestration: scan types, credential mapping and worker placement

Discovery creates and enriches CMDB objects, while ongoing performance-monitoring jobs may run on a Collector or be distributed across Workers.

Discovery is a workflow, not just a ping sweep FortiSIEM discovers devices, applications and users by using credentials to query infrastructure components. A discovery entry defines scan type, root IP (for Smart Scan), include/exclude ranges, device types, name-resolution priority and optional behaviors. A successful ping is not a prerequisite for every discovery method, and a ping-only scan is a different task from collecting operating-system, hardware, software and configuration details.

Select the scan type based on topology Range Scan walks specified IP ranges and CIDR subnets sequentially. Smart Scan starts with a root device, learns the devices that root knows about, discovers those devices, and continues recursively until the learned-device list is exhausted. L2 Scan discovers only Layer 2 connectivity. AWS Scan and Azure Scan use the corresponding cloud SDK and require a cloud credential mapped to the relevant domain. Nozomi Scan uses the Nozomi REST API and requires the matching credential mapping. Choosing Smart Scan without a useful root IP produces incomplete topology discovery; choosing Range Scan for a cloud inventory does not replace the SDK-based scan.

Credentials are mapped to targets FortiSIEM uses IP-to-credential mapping to select credentials for discovered addresses and device types. A credential existing in the store is not enough: it must be applicable to the target address/domain and access method. Discovery can retrieve host name, OS, hardware details such as CPU and memory, software, processes, services and configuration. Name resolution can prioritize DNS, device configuration or SNMP/WMI when these disagree. Use include/exclude ranges and device-type filters to constrain scope, especially before a large Smart Scan.

Collector and Worker roles are different If a discovery or Test Connectivity task is assigned to a Collector, that Collector performs the task, and the Supervisor assigns the performance-monitoring task to the same Collector. In an environment without a Collector, the Supervisor performs discovery and connectivity testing, then assigns ongoing performance monitoring to active Workers using weighted round robin. Some jobs, such as vCenter monitoring, carry more weight than simple SNMP CPU monitoring. Removing a Worker redistributes its jobs; adding a Worker assigns new jobs to it. Disabling and re-enabling performance monitoring from the GUI triggers a new global job distribution.

Useful options and cost controls Do not ping before discovery is useful for devices that ignore ICMP but still answer the configured management protocol. Ping-only discovery is for reachability status when detailed inventory is not required. Discover Routes can help Smart Scan learn neighbors, but the guide warns route collection can be expensive on BGP routers. Schedule broad scans off-peak, use include/exclude ranges and device-type filters, and avoid scanning every subnet with every credential.

Evidence and troubleshooting Run discovery on demand and inspect Results and Errors. Discovery History exposes Results, Errors and Changes, and reports can be exported to PDF or CSV. A completed scan proves the discovery job finished; it does not prove every device was successfully inventoried or that ongoing monitoring jobs are assigned to the Supervisor. Check credential tests, scan errors, CMDB records and Collector/Worker job placement separately. If a host is missing, check include/exclude logic, scan type, root IP, name-resolution source, credential mapping and whether a ping precheck prevented the protocol attempt.

FortiSASE · FortiSASE 26.1.107

External log forwarding: public/private paths, reliable TCP and TLS trust

FortiSASE exports Security PoP and endpoint events to two independent collectors; private reachability and TLS certificate trust are separate gates.

What is forwarded FortiSASE can forward logs to up to two independent external servers, including FortiAnalyzer, Syslog and Common Event Format (CEF) destinations. The log families are broader than traffic: traffic records describe Security PoP flows and HTTP/HTTPS request/response information; event logs include system and administrative events; user logs capture authentication; endpoint logs include tunnel, scan, malware, sandbox, removable-media and FortiClient events; UTM logs include antivirus, web filter/Inline-CASB, IPS, DLP, application control, DNS filter, SSL and file-filter events. The receiving SIEM should be designed around selected log families rather than assuming one generic event stream.

Public and private access are routing choices Public means the collector is reachable over the internet. Private means it is behind a secure private access FortiGate hub. A private destination therefore depends on the SPA path and hub routing; entering a private IP does not make it reachable by itself. Fortinet documents an additional constraint: if the primary external server is Private, the secondary must be Public. This matters when designing redundancy. Two private collectors are not a valid primary/secondary combination under that documented rule.

Reliable connection and secure connection are distinct Reliable Connection enables TCP instead of UDP for log forwarding. Secure Connection enables TLS and requires Reliable Connection. For TLS, FortiSASE must trust the remote syslog server's CA certificate; import the remote CA under Certificates/System Certificates. A TCP connection can succeed while TLS certificate validation fails, and a TLS connection can succeed while the receiver is parsing the wrong log format. Check these stages independently.

Configuration sequence Under Analytics (or Operations, depending on release UI) > Settings, enable Log Forwarding to Self-Managed Service and create the external server. Select server type, Public or Private access type, address and port for Syslog/CEF, reliable connection and forwarding frequency. For secure syslog, enable Reliable Connection and Secure Connection, then import the correct remote CA certificate and verify supported cipher suites. The connection status changes from Connecting to Connected after configuration is submitted and the connection is established.

Evidence and limits Connected proves the forwarding endpoint is reachable at the configured transport/security layer; it does not prove all log types are selected, the remote receiver is parsing them, or timestamps are aligned. Validate with a controlled event from each required family and check arrival at the receiver. Confirm the remote listener is bound to the expected port, the certificate chain matches the configured FQDN and the private route uses the SPA hub. If logs are missing only for endpoints, verify the endpoint log category rather than assuming traffic-log selection includes it.

Operational design Use separate destinations when the security operations platform and long-term archive have different retention or availability requirements. Keep the secondary path public if the primary is private, as required by the documented design. Protect TLS CA changes through certificate-expiry monitoring and change control. A collector replacement or CA rollover should be tested with a small controlled event stream before broad log forwarding is re-enabled.

Secure SD-WAN · FortiOS 8.0.0

Passive per-application SLA measurement from inspected live sessions

Measure latency, jitter and loss of actual application sessions per WAN member, rather than relying only on generic probe-server health.

Why passive application measurement exists Active SLA probes measure reachability and performance to a detection server using ping, TCP echo, HTTP or DNS. That is useful for infrastructure health but can differ from the path quality experienced by a specific application. FortiOS 8.0 adds passive measurement that differentiates SLA information by Internet Service Database (ISDB) service or Application Control signature. Two applications can perform differently over the same WAN link, so a generic link metric can hide an application-specific problem.

Two layers of enablement First, the firewall policy must enable passive-wan-health-measurement, use an Application Control profile to identify applications, and disable hardware offload with auto-asic-offload disable. Second, the SD-WAN performance SLA must use passive or prefer-passive mode, and the SD-WAN service rule must identify the relevant ISDB service or application signature/group and enable passive-measurement. If any one of these pieces is missing, the rule may not collect the intended per-application statistics.

Session-to-metric flow As TCP sessions pass through the firewall policy, FortiGate collects session information and derives latency, jitter and packet-loss measurements for participating SD-WAN members. When an SD-WAN rule references specific Internet Services or applications, SLA information is differentiated for those services/applications. The SLA metric for a rule can therefore reflect the average latency of the services in that rule, rather than the average of unrelated traffic. Subsequent SD-WAN decisions can use measured application quality to choose a preferred member.

Passive versus prefer-passive In passive mode, live traffic is the measurement source and no active health-check probes are sent. This reduces probe traffic but leaves an idle link without a fresh measurement. Prefer-passive uses live traffic when available; if no live traffic flows through a member for three continuous minutes, FortiGate sends active probes to the configured health-check server. Prefer-passive therefore needs a configured server and link health monitor. Do not configure passive-only mode and then expect a probe result on an idle member.

config firewall policy
    edit 1
        set passive-wan-health-measurement enable
        set auto-asic-offload disable
        set application-list "default"
    next
end
config system sdwan
    config health-check
        edit "Passive-App-SLA"
            set detect-mode prefer-passive
            set server "198.51.100.10"
            set members 1 2
        next
    end
    config service
        edit 1
            set internet-service enable
            set internet-service-name "Example-App"
            set health-check "Passive-App-SLA"
            set passive-measurement enable
        next
    end
end

Verification Use diagnose sys link-monitor-passive admin list by-interface to inspect passive session information by interface. Confirm the firewall policy has passive measurement enabled and hardware offload disabled, the Application Control profile is identifying traffic, the health check is passive/prefer-passive, and the SD-WAN rule has the right ISDB/application signature and passive-measurement. Generate representative application traffic on both WAN members and compare per-rule SLA values. The diagnostic list proves passive session data is collected; it does not by itself prove the SD-WAN rule selected the desired path.

Failure isolation If a ping SLA is green but users report poor performance in one SaaS application, compare per-application passive metrics with the generic probe. If there are no passive entries, check policy inspection and hardware offload first. If one application is not separated, verify the Application Control signature or ISDB identifier used by the rule. If an idle link has no measurement in passive mode, use prefer-passive or generate representative traffic. Enabling passive WAN measurement disables ASIC offload on the participating policy, so assess CPU and throughput impact before applying it broadly.
