1. FortiManager — Policy-package installation is an object-closure transaction

Primary source: FortiManager Administration Guide — Install a policy package.

A FortiManager policy-package install is not merely a transfer of the firewall-policy rows visible in the package. Fortinet documents that objects referenced by policies are installed to the target device and that a default or per-device mapping must exist when required; otherwise installation fails. More subtly, some objects that are not directly referenced by an individual policy can also be installed, including FSSO polling objects, address/profile groups, and CA certificates. Conversely, objects not represented by the managed policy/object database can be removed from the FortiGate, which is particularly important during the first install after importing a device.

Mechanics. Think of the transaction as: policy package → resolve installation targets → walk policy references → resolve per-device/default mappings → calculate supporting object closure → calculate device delta → preview/install → FortiGate candidate/running configuration. The operational implication is that a syntactically valid policy can still fail before device commit if a mapped object cannot resolve for a target. A successful install also proves more than “the policy row exists”: it proves FortiManager could construct a target-specific object graph acceptable to that device.

Why engineers get surprised. A device imported with only selected objects can later lose an object that exists locally but is absent from Policy & Objects when FortiManager calculates authoritative state. Fortinet specifically recommends considering Add ALL Objects during import when those objects may be needed later. Installation targets also matter: a policy can be scoped so only specified devices receive it, which means identical packages can produce different target deltas.

Evidence boundary. The install preview is the first high-value artifact: inspect additions, changes, deletions, and mapping resolution before treating the operation as a transport problem. A failed mapping proves FortiManager could not render a target-specific object; it does not prove FortiGate rejected a valid rendered configuration. A successful preview followed by device-side rejection moves the diagnostic boundary downstream toward device validation/commit.

Troubleshooting application. When one FortiGate in a shared package fails while peers succeed, compare the failing device's per-device mappings and installation target state before cloning policies or editing unrelated rules. When an unexpected object disappears, compare the imported object set and generated install delta rather than assuming an administrator manually deleted it.

30-day uniqueness: this lesson is about reference closure, install-delta construction, and per-device mapping dependency—not the recently taught workspace locking, ordered workflows, metadata variables, device identification, or HA management-address subjects.

2. FortiSIEM — Event forwarding happens where the event is received and parsed

Primary source: FortiSIEM User Guide — Event Forwarding.

FortiSIEM can act as a controlled fan-out point for logs, traps, and NetFlow so a source device does not need to send the same telemetry independently to many consumers. Fortinet states that a Super, Worker, or Collector can forward an event and that the node that receives and parses the event performs the forwarding. That placement detail is the key mechanism: forwarding behavior follows ingestion/parsing locality, not simply the existence of a global-looking rule.

Mechanics. Source telemetry arrives at a FortiSIEM node → the receiving node parses it → forwarding-rule selectors evaluate organization/reporting device/event type/traffic-specific conditions → matching events are emitted to configured destinations. For syslog, the rule can include source IP, destination IP, severity and regex filtering. Transport selection matters: Fortinet explicitly distinguishes UDP, where events can be lost, from TCP, which provides reliable transport semantics.

Evidence boundary. A normalized event visible in FortiSIEM proves ingestion and parsing succeeded; it does not prove the forwarding rule matched or that the downstream receiver accepted the relayed event. A raw packet observed leaving the receiving/parsing node proves the forwarding stage executed, but still does not prove application-level ingestion at the destination. Conversely, debugging the wrong Worker when the Collector received and parsed the event can produce a misleading 'nothing happened' diagnosis.

Operational design. Centralizing fan-out reduces load and destination-count limitations on network devices. It also creates an explicit relay dependency: forwarding rules, parser locality, egress reachability, protocol choice, and destination health all become parts of the transaction. If forwarding should occur only from Workers/Super, Fortinet documents a separate worker-forwarding behavior that must be considered rather than assuming every Collector will relay identically.

Troubleshooting application. Start with one known source event. Identify the FortiSIEM node that actually received and parsed it. Confirm normalized attributes used by the forwarding selector. Then verify rule match, egress packet generation, transport establishment when TCP is used, and downstream receipt. This ordered proof avoids conflating parser failure, selector mismatch, relay transport failure, and destination rejection.

30-day uniqueness: this mechanism is event relay/fan-out tied to receiver/parser locality, distinct from the recently taught Collector/Worker processing architecture, Windows native-XML parsing, CMDB context, maintenance suppression, UEBA, and remediation-rule execution.
