1. FortiGate — IPv6 Neighbor Discovery proxy across an upstream/downstream boundary

Primary Fortinet documentation · No sufficiently recent, feature-specific Community case verified; primary documentation governs this lesson.

IPv6 Neighbor Discovery is not a single address-resolution exchange. Router Solicitation (RS) discovers routers; Router Advertisement (RA) carries router and prefix information; Neighbor Solicitation (NS) resolves or tests neighbors; Neighbor Advertisement (NA) answers those requests; and redirects indicate a better next hop. These are ICMPv6 control messages. A client can have an IPv6 address and still be unable to resolve its next hop, so a simple address check cannot establish that IPv6 forwarding works.

FortiOS 8.0 supports an ND proxy between interfaces, typically with one upstream interface receiving RAs and a downstream interface connected to clients. This differs from DHCPv6 prefix delegation: ND proxy allows the discovery/control exchanges to operate across an interface boundary, while DHCPv6 PD negotiates an address block for routing. The upstream interface is normally identified by receiving RA traffic. The documented example enables upstream IPv6 autoconfiguration on port1 and makes port1 and port5 members of the ND proxy. An engineer should verify that these are the actual intended L2/L3 boundaries; adding an arbitrary interface can create unexpected advertisement or neighbor behavior.

Configuration, adapted from the Fortinet Administration Guide: 

config system interface
    edit "port1"
        config ipv6
            set autoconf enable
        end
    next
end
config system nd-proxy
    set status enable
    set member "port1" "port5"
end
The exact interface names must match the deployment. The proxy does not remove the need for appropriate IPv6 security policy, a working upstream router, or correct address/prefix information. Capture ICMPv6 on both sides. If port1 receives RAs but port5 clients never receive router information, the boundary is proxy membership or advertisement propagation. If a client has a global address but NS/NA exchange fails, inspect neighbor-cache state, multicast delivery and filtering. If both neighbor resolution and routing succeed but an application fails, investigate firewall policy and higher-layer protocols rather than repeatedly changing ND proxy.

Verification should follow a single client: observe RS, upstream RA, client autoconfiguration, duplicate-address detection, NS/NA resolution, then a routed test. An RA proves a router advertised a prefix; it does not prove that the client accepted the prefix. A neighbor-cache entry proves a recent neighbor resolution, not that the end-to-end firewall policy allows traffic. During HA or interface changes, repeat the capture because neighbor caches and advertisements may take time to converge. Treat NDP proxy as a specific control-plane relay, not a universal substitute for routed IPv6 design.

2. FortiManager — Device revision retrieval, revert, and policy-package reconciliation

Primary Fortinet documentation · Secondary Community scenario

FortiManager keeps distinct representations of configuration: the live FortiGate configuration, its Device Database, and policy packages containing firewall policies and objects. A rollback is unsafe when these are treated as one interchangeable store. The revision-history repository tracks device configuration versions, lets administrators view or compare revisions, and supports retrieval, reversion, import, export and installation-log inspection. The Device Manager dashboard exposes Configuration Revision History; the relevant actions include View Config, Revision Diff, Retrieve Config and Revert.

Retrieve Config reads the current running configuration from FortiGate. If it differs from the repository, FortiManager creates a new revision. It does not mean “restore the old configuration to the FortiGate.” Revert selects an earlier repository revision and makes that state available for a subsequent install. The crucial boundary is the install action and the policy-package database. Fortinet's technical guide documents a recovery path where administrators revert the device revision, then choose Install Device Settings Only to restore the intended device revision. Choosing Install Policy Package & Device Settings may mix the old device settings with the current, newer policy package and unintentionally reapply policies that caused the incident.

A practical change-control workflow begins before the outage: capture a known-good revision ID, inspect its configuration and installation log, and save the associated policy-package revision. During rollback, compare the candidate revision with the current state and check install preview. Revert the correct device revision, install the intended device settings, then reconcile or import the FortiGate policies into FortiManager if the policy-package status becomes unknown. Import is a synchronization step, not evidence that the previously selected policy package already matches the device.

The Community procedure also describes a FortiGate-side emergency restoration method: 

execute restore config management-station normal 0
execute restore config management-station normal <revision-id>
The first command lists available management-station revisions; the second can overwrite the device configuration and reboot it. Treat this as a disruptive fallback, not a routine read-only verification. Confirm reachability, HA roles and maintenance authorization before invoking it.

Evidence must include four independent states: revision contents, Device Database status, policy-package status, and installed FortiGate policy/configuration. A successful FortiManager API or GUI revert only proves the repository action succeeded. An installation task marked complete does not prove that the right historical policy objects were restored. Compare actual firewall rules and test the original failed traffic. During firmware upgrades, historical syntax may no longer install cleanly; use preview and targeted corrections instead of blindly pushing an obsolete full configuration.

3. FortiAnalyzer — IOC historical rescan, TIDB package lifecycle, and alert provenance

Primary Fortinet documentation · Secondary Community scenario

FortiAnalyzer's Indicator of Compromise engine compares observed destinations against FortiGuard threat-intelligence data. The TIDB package contains blocklisted IP addresses, domains and URLs, plus a separate suspicious-URL list. A blocklist match and a suspicious score are different detection mechanisms: a blocklisted URL is not scored as a suspicious-list URL. Real-time IOC evaluates incoming logs; historical rescan reevaluates previously collected logs when intelligence changes. Rescan checks the blocklist, not the historical suspicious list. This distinction is central to understanding why an older session can trigger a new alert without new endpoint activity.

The Administration Guide provides global rescan settings and ADOM-specific log-type selection under FortiView > Threats > Indicator of Compromise. Global rescan can run at a specified hour or after a TIDB package update. Administrators need a valid IOC service license and Read-Write System Settings privilege; without the license, rescan options are unavailable. Choose relevant DNS, Web Filter, Traffic and Email Filter logs for the ADOM. A completed rescan marks rescanned detections with the Ioc_Rescan tag. Default compromised-host alert handlers can include that tag, so a rescan can legitimately produce alerts long after the original log timestamp.

The evidence chain starts with license state and intelligence version. Fortinet documents: 

diagnose fmupdate dbcontract
diagnose fmupdate fds-getobject
diagnose test application sqllogd 204 stats
get system log ioc
The first commands establish contract/package visibility; the sqllogd test reports the IOC license and loaded TIDB version. Compare package-download time with the TIDB version actually loaded by the IOC service; these are not necessarily simultaneous. Then inspect the rescan task's time, log count, threat count, package-update time and matched pattern. Correlate an alert's Ioc_Rescan tag with the original log timestamp before claiming the endpoint contacted a malicious destination today.

An unlicensed appliance may load a demo TIDB rather than a current FortiGuard package. Fortinet's Community scenario shows how stale demo intelligence can create misleading IOC alerts. A valid license is therefore part of detection quality, not simply a GUI entitlement. The IOC module also has a notification throttle; its default interval of 1440 minutes prevents repetitive endpoint notifications. A lack of repeated alerts is not proof that detections stopped. For an incident response decision, compare the exact log, current threat-intelligence context, rescan provenance and endpoint activity. Do not equate a newly generated alert with a newly executed attack.

Engineering depth: 382 words; primary source linked above. Configuration is release-dependent; validate syntax against the cited guide.

4. FortiSwitch — FortiSwitchOS 8.0 inter-switch STP cost selection

Primary Fortinet documentation · Secondary Community scenario

Managed FortiSwitch deployments use Spanning Tree Protocol to prevent Layer-2 loops. Multiple Spanning Tree Protocol (MSTP) groups VLANs into instances, allowing different VLAN sets to take different loop-free paths. FortiSwitchOS 8.0 introduces an important operational choice for automatically formed inter-switch links (ISLs): with auto-stp-priority enabled, the automatic ISL STP cost is 1; with it disabled, the ISL cost is derived from trunk-member link speed. This is not the same as changing an MSTP root bridge priority or mapping VLANs into an instance.

The default low ISL cost tends to prefer FortiLink topology paths according to the controller's automatic design. Disabling the behavior allows speed-derived costs to influence the root path, which may be preferable when ISLs have very different capacities. The decision must be made against the actual topology and intended root location. A faster link can have a more favorable cost, but other port and bridge priorities still affect the final root-port choice. Fortinet explicitly warns that changing this setting temporarily takes FortiLink down; a live change can interrupt management and downstream switching.

Fortinet documents the relevant switch-side configuration: 

config switch global
    set auto-stp-priority disable
    set auto-stp-cost disable
end
The Administration Guide also documents controller-side MSTP controls: 
config switch-controller stp-settings
    set name <region-name>
    set revision <revision>
end
config switch-controller stp-instance
    edit 1
        config vlan-range <vlan-list>
        end
    next
end
Use the exact syntax and release appropriate to the managed-switch model; do not change both automatic cost behavior and MSTP region configuration simultaneously when isolating a fault.

The verification sequence is physical link state, trunk membership and speed, STP region/instance, root bridge identity, root port and effective port cost, then forwarding/blocking state per VLAN. A trunk being up does not prove it forwards user traffic. An STP instance showing a root bridge does not prove every VLAN is mapped to the intended instance. A switch that briefly disappears from FortiLink after the command may be experiencing the documented reconvergence rather than a permanent management failure.

A useful failure scenario is a new high-speed ISL added during a maintenance window: after changing automatic STP cost behavior, traffic unexpectedly traverses a slower backup link. Compare effective costs and root-port election, not just interface counters. Capture topology before and after the change, preserve an out-of-band recovery path, and avoid making a simultaneous change to root priority or VLAN mapping until the effect of the ISL cost setting is understood.

5. FortiAP/Wireless — Automatic 802.11ax BSS coloring and spatial reuse

Primary Fortinet documentation · No sufficiently recent, feature-specific Community case verified; primary documentation governs this lesson.

802.11ax introduces Basic Service Set (BSS) coloring to help a station distinguish frames from its own BSS from frames belonging to an overlapping BSS on the same channel. This is a spatial-reuse mechanism, not a replacement for channel planning. The color is signaled in HE operation information and can help a station make more informed channel-access decisions when neighboring transmissions are present. If neighboring BSSs use the same color, the differentiation benefit is reduced and collision handling becomes important.

Fortinet documents automatic BSS coloring in the wireless controller. A FortiAP radio profile can use automatic or static color selection. With automatic mode, the AP can change color when it detects a conflicting BSS color. The documented CLI shape is: 

config wireless-controller wtp-profile
    edit <profile-name>
        config <radio>
            set bss-color-mode auto
        end
    next
end
A static mode can be useful for a controlled design, but it creates an operational obligation to prevent neighboring BSS color collisions. The feature applies to appropriate 802.11ax/HE-capable radio operation; older clients or AP modes do not magically gain HE spatial-reuse behavior.

Separate three wireless layers during troubleshooting. First, RF channel reuse: two APs can share a channel and contend even if their BSS colors differ. Second, color differentiation: the APs can advertise distinct colors, allowing HE stations to classify overlapping transmissions. Third, station behavior and airtime: throughput depends on signal strength, channel width, interference, client capability and contention rules. Changing color does not increase available spectrum or eliminate all co-channel interference.

An engineer should capture the affected radio's profile and effective mode, neighboring beacon HE operation information, current channel and bandwidth, BSS color collision events where supported, and client airtime/retry observations. A profile configured for auto is intent; a beacon advertising the expected color proves the AP applied a value. A reduction in retries or better airtime efficiency under controlled traffic is stronger evidence of benefit. If clients still suffer low throughput, compare RSSI, noise, channel utilization, hidden nodes and band steering rather than repeatedly forcing a new color.

During controller or AP upgrades, validate that the radio model supports the expected HE behavior and that profile inheritance did not change. If a static color design was imported from an older template, compare adjacent AP assignments after channel reoptimization. BSS coloring is a narrowly defined MAC-layer coexistence tool; it should complement, not replace, a sound RF plan.

6. FortiNAC — Chained endpoint compliance scans and graduated access

Primary Fortinet documentation · No sufficiently recent, feature-specific Community case verified; primary documentation governs this lesson.

Endpoint compliance is more expressive than a single pass/fail gate. FortiNAC can chain compliance configurations: a host first runs a baseline scan, then a security action can launch an additional compliance configuration when a higher trust level is required. Fortinet's Administration Guide describes the Run Endpoint Compliance Configuration activity as a way to start further scans, with access determined by the highest-level scan the host passes. This supports graduated access: ordinary production access may require baseline hygiene while a sensitive network segment requires additional controls.

The mechanism requires the Persistent Agent. It is not a general capability of the Dissolvable Agent, which runs during registration and does not remain to support the same ongoing workflow. In Policy & Objects > Endpoint Compliance > Configuration, enable Advanced Scan Controls, associate the initial scan and map scan results to a security action containing the chained activity. The policy's user/host profile determines which hosts are subject to the initial configuration. A chained scan is a separate execution with its own result; it is not a hidden condition automatically inferred from the first scan.

Execution ordering is important. When a host authenticates and matches the policy, the first scan runs. After its result, the configured action can start the next compliance configuration. If that subsequent scan starts successfully, the action sequence can continue while the scan runs. If it fails to start, later activities run only when On Activity Failure is set to Continue Running Activities. Fortinet documents no fixed limit on the number of result-based actions, but that is not a recommendation to build an unbounded scan chain. Excessive scans can delay user access and consume agent/server resources.

The diagnostic evidence is the matched user/host profile, initial scan result, security action mapping, attempt to start the next configuration, second scan result, and resulting VLAN or access assignment. A passed first scan proves baseline compliance; it does not prove that the higher-level scan was invoked. A started second scan proves orchestration, not successful compliance. A final network-access change proves enforcement only after the switch/port or network role reflects the intended access.

Consider a user who can reach ordinary resources but not a secure engineering VLAN. If the first scan passes and the second never appears, inspect the mapped security action and activity-failure behavior before changing VLAN policies. If the second scan passes but the VLAN remains unchanged, move downstream to enforcement and port-control evidence. During agent upgrades, verify Persistent Agent version/communication and rescan scheduling because an apparently successful registration does not guarantee the agent can execute advanced chained scans.

7. FortiNAC-F — EAP-TLS endpoint trust certificate target and unknown-CA failures

Primary Fortinet documentation · Secondary Community scenario

FortiNAC-F separates server identity from trust in endpoint certificates. The Local RADIUS Server certificate lets a supplicant validate the authentication server. The Trusted Certificates target named RADIUS Endpoint Trust [radius] holds CA certificates used by FortiNAC to validate the supplicant's EAP-TLS client certificate. Installing a server certificate does not automatically populate the endpoint-trust target. Fortinet explicitly warns that the two certificate stores are different, and that client authentication fails if the appropriate issuing root CA is missing.

In an 802.1X EAP-TLS exchange, the switch/AP relays EAP to the RADIUS service. The client validates the server's certificate, the server validates the client's certificate chain and proof of private-key possession, and successful EAP produces keying/authentication state used by the network access device. The endpoint's certificate and private key are distinct from the root CA certificate that FortiNAC trusts. Both sides must have correct time, certificate validity and expected trust chains. A user certificate with a matching username does not override an untrusted issuer.

Configure the trust anchor under System > Certificate Management > Trusted Certificates, selecting RADIUS Endpoint Trust [radius]. The documentation permits multiple root CA certificates when endpoints have been issued by more than one enterprise CA. Do not confuse this target with RADIUS Endpoint Trust [RadSec], which validates the certificate of a RadSec transport peer, or with General Trusted CA, which secures other modeled-device connections. The certificate targets correspond to different TLS conversations.

The Fortinet Community troubleshooting case provides a precise evidence signature: RADIUS debug reports OpenSSL error 20, unable to get local issuer certificate, and a fatal unknown-CA alert. The right first check is whether the client's issuing root is installed in the local-RADIUS endpoint trust store, not whether the FortiNAC web GUI certificate is valid. Capture the EAP identity, client certificate issuer, configured trust roots, EAP handshake result and final RADIUS response. An Access-Reject following TLS failure is different from a policy denial after successful certificate validation.

After installing the correct CA, retest a single endpoint and verify the switch receives an Access-Accept and applies the intended VLAN/role. If TLS succeeds but access is still denied, inspect identity mapping and authorization policy. During CA rollover, install both old and new trusted roots before distributing new client certificates, and remove obsolete trust only after all endpoints migrate. The practical lesson is that TLS server identity, endpoint certificate trust and network authorization are three separate verification boundaries.

8. FortiAuthenticator — Per-profile OCSP certificate validation: hard fail versus soft fail

Primary Fortinet documentation · No sufficiently recent, feature-specific Community case verified; primary documentation governs this lesson.

Certificate trust alone does not establish that a certificate remains authorized for use. An endpoint can present a validly signed, unexpired EAP-TLS certificate that has been revoked. FortiAuthenticator 8.0.2 introduces per-authentication-profile Online Certificate Status Protocol (OCSP) verification modes for certificate-based authentication. The policy can disable OCSP, require a successful status check, or use a soft-fail mode that accepts a certificate when the OCSP responder is unavailable or times out, unless the responder explicitly returns a reject/revoked result.

The three modes have different security and availability implications. Disable performs no OCSP check. Enable is fail-closed: certificates must pass the OCSP check, so responder unavailability can interrupt otherwise valid users. Enable-softfail is availability-oriented: a timeout or non-response is not treated as an explicit revocation, but a definite reject still blocks authentication. Fortinet documents a fixed three-second OCSP timeout in this release. An administrator must decide whether the network segment values strict revocation enforcement over continued access during a responder outage.

The feature is configured in Authentication > RADIUS Service > Auth Profiles for a profile whose client credential type is Certificates. Verify that the relevant RADIUS policy selects the intended authentication profile; changing an unused profile does not affect live authentication. The EAP-TLS exchange includes normal certificate-chain validation and identity checks before or alongside revocation evaluation. OCSP is an additional decision, not a replacement for correct CA trust or client identity mapping.

When a wave of endpoints begins failing after a WAN change, capture RADIUS authentication debug, the profile's OCSP mode, responder DNS/reachability, timeout behavior and the certificate serial/status. If failures consistently occur after roughly the configured timeout window and the responder is unreachable, hard-fail OCSP is a plausible cause. If the same users succeed under softfail, that demonstrates a reachability/availability dependency; it does not prove their certificates were definitely good. Conversely, a responder's explicit revoked result should cause rejection even under softfail.

In a controlled test, compare three certificates or conditions: known good with reachable responder, known revoked with reachable responder, and valid certificate with responder intentionally unreachable. Record the observed RADIUS outcome for each. During HA, confirm that both FortiAuthenticator nodes have equivalent DNS, routes, trust chains and OCSP profile settings. Treat fail-open versus fail-closed as an explicit risk decision documented per access tier, not an incidental troubleshooting toggle.

9. FortiPAM — One-time external secret invitation with time-bound access

Primary Fortinet documentation · No sufficiently recent, feature-specific Community case verified; primary documentation governs this lesson.

FortiPAM 1.9.0 supports a one-time invitation that lets a secret owner grant a temporary external user access to a particular secret without creating a standing internal FortiPAM account. The invitation is intentionally constrained by available license seats, secret ownership, email-notification configuration, service selection, start time and link expiration. This is not the same as permanently sharing a secret or granting a user broad vault visibility. The external invitee can use only the permitted launch services, such as SSH or RDP, and cannot choose a default launcher.

For a secret without an approval requirement, the owner opens Secrets > Secrets, selects the secret and uses Invite. The invitation includes recipient email, case-sensitive security question/answer, allowed services, access start and link expiration. Fortinet documents a 30-minute token TTL after the link becomes active in this path. The invitee clicks the unique link, answers the challenge and starts a session. The link is single-use: logging out means the same link cannot be used to log in again, even if the broader start/end window has not passed.

For a secret requiring approval, the request includes an access duration and optional comments; an approver can adjust duration before approval. The approved invitation has a shorter documented token TTL of 10 minutes after activation. The approved session remains subject to its duration and the GUI session timeout. A request being approved does not mean the link was activated; an activated link does not mean a target session succeeded. FortiPAM tracks states such as Pending, Approved, Activated and Deleted in the secret's Permission tab and exposes invitation activity in the Logs tab.

Operational prerequisites are easy to overlook. The inviter must own the secret, a license seat must be available, and Enable Email Notification must be selected under Log & Report > Email Alert Settings. If a user never receives an invitation, verify these prerequisites and the approval state before troubleshooting the target SSH/RDP server. If a link is rejected, check start time, expiration, one-time use and security-answer case. If the link works but the launch fails, move to the allowed-service list, secret launcher, proxy connectivity and target credentials.

The security design benefit is reduced standing privilege and auditable, time-bounded external collaboration. It also creates operational risk when support teams email links too early or rely on them for unattended work. Create invitations near the planned access window, minimize allowed services and require approval for sensitive secrets. Do not reuse a consumed link as a diagnostic test; issue a fresh invite and compare the state transitions. During incident response, distinguish invitation expiry from revocation of an already-running target session, which may have separate proxy enforcement behavior.

10. FortiSIEM — Windows Agent file-integrity monitoring and SVN evidence preservation

Primary Fortinet documentation · No sufficiently recent, feature-specific Community case verified; primary documentation governs this lesson.

FortiSIEM's Windows Agent can monitor file changes as a source of security evidence. File Integrity Monitoring (FIM) is distinct from Windows Event Log collection: it can detect modifications to selected files and directories, including content, permissions and ownership changes, depending on agent version and policy. Fortinet's Windows Agent release notes describe SHA256 hashing in newer agents, replacing MD5 for FIM hashes, and support for pushing changed files to the Supervisor for an SVN-based audit trail. A FIM alert that reports a changed file is not the same as retaining the actual modified file.

The workflow begins with a Windows Agent registered to the FortiSIEM Supervisor and a FIM monitoring policy applied to the correct CMDB device. The agent observes a change, generates FIM telemetry with relevant file attributes/hash, and, when Push Files On Modify is enabled, sends the changed file to the Supervisor. FortiSIEM stores the file in SVN, where an analyst can inspect historical changes. This provides more investigative context than a hash-only event, but it also means file contents may leave the monitored host and be retained centrally; scope monitoring to approved directories and sensitive-data policies.

The Administration Guide documents viewing captured files through CMDB > Devices: ensure AGENT is one of the monitoring Methods, select the device by the hostname used in InstallSettings.xml, and choose File beneath the device table. Search by From/To dates and select the file version. A missing File entry can mean the agent did not monitor the path, the FIM policy was not active, Push Files On Modify was disabled, the agent disconnected, or the Supervisor failed to receive/store the file. It does not automatically mean the file never changed.

For a controlled verification, create or modify a harmless test file in an explicitly monitored directory, then compare agent service status, FIM event timestamp, SHA256 value, supervisor ingestion and the SVN-backed file history. A hash change proves different file bytes; it does not identify the actor or explain why the change occurred. An ACL/owner change may be important even when content hash remains unchanged. Correlate FIM with Windows security events, user sessions and change-management records to attribute activity.

Fortinet's Windows Agent release history notes fixes for agent crashes and stoppages when FIM was enabled on certain platforms. Version compatibility therefore matters: after upgrading the agent or FortiSIEM, repeat a controlled file-change test rather than assuming existing FIM policies still work. Keep monitored scope and file-push retention proportional to investigative value. In large estates, overbroad monitoring can create event volume and storage pressure; monitor high-value files with clear expected-change baselines.

11. FortiSASE — Split DNS private access and per-PoP resolver override

Primary Fortinet documentation · Secondary Community scenario

FortiSASE split DNS is a routing and policy decision for DNS requests, not merely a list of internal domain suffixes. A client needs to resolve internal names using enterprise DNS while continuing to resolve public names through the normal FortiSASE DNS path. The feature matches specified domains to selected primary/secondary DNS servers and leaves other names to the implicit DNS rule. Sending every DNS request to a distant internal resolver increases latency and creates unnecessary dependency on the enterprise network.

The current FortiSASE Administration Guide documents Configuration > DNS > Create, where an administrator defines one or more domains and DNS server addresses. When SPA uses a BGP-on-loopback design, the Access Type distinguishes a DNS server reachable through Private Access from one reachable publicly. A private IP resolver behind an SPA hub needs the corresponding private route and Private Access policy permitting DNS traffic to that server. A healthy SPA tunnel by itself does not establish that DNS requests are allowed to cross it.

For geographically distributed enterprises, PoP DNS override can select a closer internal DNS server for particular PoP regions. The documented behavior permits up to two internal DNS servers per region per domain; if a region is not configured, FortiSASE uses the rule's main DNS servers. The guide notes that PoP DNS override applies to SWG, Thin Edge and IPsec VPN traffic. Engineers should not assume every access mode uses the same override. Verify the user's connected PoP and traffic type before diagnosing regional differences.

There is a second, easy-to-miss policy boundary: Web Filter or DNS Filter can block internal names categorized as Newly Observed Domains. Fortinet explicitly instructs administrators to create appropriate URL or domain-filter exceptions when split DNS is used for internal domains behind SPA. A resolver may return a valid private address while the security policy still denies the request. Conversely, a DNS timeout can result from a missing Private Access DNS rule, wrong Access Type, incorrect PoP override, unreachable SPA route or the DNS server itself.

Troubleshoot one FQDN end to end: confirm the client query suffix, split-rule match, chosen resolver, public/private access selection, SPA route and DNS permit policy, query/response capture and final application connection. A successful lookup does not prove application authorization; an application TCP connection does not prove the client used the intended regional resolver. During PoP migration or changes to the SPA routing design, repeat both internal and public lookups from representative regions and access methods. Keep split DNS and DNS filtering policy changes separate to preserve a clear causal trail.

12. Secure SD-WAN — VRF-aware Performance SLA across a single segmented overlay

Primary Fortinet documentation · No sufficiently recent, feature-specific Community case verified; primary documentation governs this lesson.

FortiOS supports SD-WAN segmentation in which multiple departments or tenants use separate VRFs over a shared overlay. Each VRF has an independent routing table; a subnet in one VRF must not be treated as interchangeable with a subnet in another. This is different from using multiple VPN tunnels merely for bandwidth. A single overlay can transport multiple logical routing contexts when the hub and spokes are designed for it. The challenge for SD-WAN health measurement is ensuring a probe follows the same VRF context as the traffic it is intended to represent.

The FortiOS 8.0 Administration Guide documents VRF-aware SD-WAN health checks. On the originating spoke, the health check can be tagged with a VRF ID and a source address so that probes traverse the multi-VRF tunnel and reach a health-check server in the matching VRF at the hub. The address mode may be IPv4 or IPv6. The documented configuration pattern is: 

config system sdwan
    config health-check
        edit <health-check-name>
            set vrf <vrf-id>
            set source <source-address>
        next
    end
end
The probe source must be meaningful and routable in the chosen VRF; simply setting the VRF number without validating source and hub return path is insufficient.

A useful topology is two branch departments, each with an overlapping or separate address space and a dedicated hub VRF. The shared overlay carries both, but an SLA probe for Department A must be classified into VRF A to reach its own target. If the probe enters the wrong VRF, it can time out even while the tunnel and Department B are healthy. An engineer might mistakenly fail over the shared WAN because the measurement was taken in the wrong routing context. This is a measurement-design error, not necessarily a physical path outage.

Verify the spoke's VRF and source settings, tunnel/member selection, hub VRF route to the target, target reply route, probe packets and per-member SLA state. A tunnel being up proves only the overlay transport. A probe reaching the hub does not prove the correct VRF route exists beyond the hub. A successful ping sourced from the global routing table is not equivalent to a probe in a tenant VRF. Use a VRF-specific capture or test where supported and inspect the health-check state with diagnose sys sdwan health-check.

When adding new tenant VRFs, treat each as a new routing and measurement domain. Validate that probes do not leak across VRFs and that return routes are symmetric. During HA, link failover or overlay reconfiguration, confirm that each VRF's probe state converges independently. The design goal is to make SLA decisions reflect the tenant path actually used by production traffic, not a default-VRF shortcut that happens to be reachable.
