FortiGate

1. Encrypted DNS Inspection: DoT/DoH, Deep Inspection, and DNS Filter Enforcement

Primary feature lesson source: FortiOS 7.6.3 — DNS inspection with DoT and DoH
Scenario support: Incorrect policy hit for FQDN traffic

Mechanics

DoT and DoH hide the DNS message inside TLS or HTTPS. FortiGate therefore cannot make a domain/category decision until the TLS layer is decrypted. Fortinet documents full SSL inspection for this path and, beginning with FortiOS 7.6.0, support in both proxy and flow inspection. In proxy mode the SSL/SSH profile can map DNS-over-TLS explicitly; flow inspection handles ports differently. A DNS filter attached to a policy without successful decryption is only configured intent—it is not evidence that the query was parsed.

The runtime sequence is client TLS connection → FortiGate deep inspection → DNS parser → DNS Filter category/action → log/block. Wildcard FQDN objects add another observation path: the FortiGate must see a qualifying DNS response to populate the address cache. If the endpoint resolves through encrypted DNS that the firewall does not decrypt, the later FQDN policy can miss even though the browser itself resolved the name successfully.

Evidence interpretation

ObservationProvesDoes not prove
Full SSL inspection on the policy carrying DoT/DoHThe policy is configured to decrypt eligible sessions.That a particular client accepted the inspection CA or that DNS was parsed.
DNS-filter log contains queried domain/category and blockTLS decryption, DNS decoding and DNS-filter evaluation occurred for that query.That every DoH provider or alternate port is covered.
Wildcard FQDN cache contains the addressFortiGate observed the answer and updated that object.That subsequent traffic hits the intended policy if ordering/other objects differ.

Scenario: If a wildcard-FQDN rule is bypassed while clients use Secure DNS, first prove whether FortiGate sees the DNS transaction. A successful HTTPS session proves only TLS reachability. The first decisive evidence is a decrypted DNS-filter log or FQDN-cache update. If neither exists, troubleshoot the decryption/resolver path before changing firewall-policy order.

Mechanism → implication: because encrypted DNS must be decrypted before DNS filtering or FQDN learning, certificate trust and inspection coverage become direct engineering dependencies. The observable downstream event—not the existence of the profile—is the validation target.

FortiManager

2. Policy Blocks: Reusable Policy Composition, Global Assignment, and Install Semantics

Primary feature lesson source: Using Policy Blocks
Scenario support: Using policy blocks with a global policy package

Policy Blocks package multiple firewall, proxy or virtual-wire-pair policies as a reusable unit. Appending a block is composition, not copying: the local policy package inherits the block as a unit. Blocks can also participate in Global Database ADOM header/footer designs. That creates distinct states: Policy Block content, global package assignment, local package synchronization, install preview and device installation.

Fortinet’s community example is especially useful because an assignment can remain Pending change even when the global package was previously assigned. Only after the assignment/synchronization operation changes to Up to date should the engineer expect the local package to contain the new policies. Even then, the managed FortiGate is unchanged until Install Policy Package runs successfully for that target.

Scenario: a newly appended global Policy Block does not appear on a spoke package. If assignment still says Pending change, the failure is before local composition; do not debug the FortiGate. If local package is correct but device is not, move to install preview/result and per-target scope.

FortiAnalyzer

3. Log Integrity: MD5/MD5-Auth Checksums, Roll Boundaries, and Verification

Primary feature lesson source: Log Integrity and Secure Log Transfer
Scenario support: Backup/restore checksum example

FortiAnalyzer can record a digest when a log file rolls or is transmitted. `config system global` → `set log-checksum {md5|md5-auth|none}` controls the behavior. `md5` stores a hash; `md5-auth` stores the hash and authentication code; `none` is the documented default. The integrity boundary is a specific file’s bytes at the time the digest is recorded.

A matching digest proves byte consistency for that file. It does not prove the FortiGate sent every expected event, that SQL insertion succeeded, that the analyst queried the correct ADOM/time range, or that older files created before the setting change carry hashes. Those are different transaction boundaries.

ObservationProvesDoes not prove
`log-checksum md5-auth` configuredNew qualifying log files are configured for hash+auth-code recording.Historical files already contain those values.
Recorded digest matches recomputed digestThe checked file bytes match the recorded integrity value.The file is semantically complete.
Log View returns expected eventsThose events were inserted/queryable.Archive-file checksum verification is enabled.

Scenario: after a restore, analysts can query logs but compliance asks whether an archived file changed. Do not use SQL health as integrity evidence; compare the FortiAnalyzer-recorded digest to a recomputation over the same file.

FortiSwitch

4. Private VLANs: Primary, Isolated, Community, and Promiscuous Forwarding

Primary feature lesson source: Private VLANs
Scenario support: FortiSwitch PVLAN model support discussion

A PVLAN retains one IP subnet and Layer-3 gateway while partitioning Layer-2 reachability. The primary VLAN is paired with secondary VLANs. An isolated secondary VLAN can reach the primary/promiscuous side but its hosts cannot talk to each other or other secondaries. A community secondary VLAN allows members of the same community to communicate with one another and the primary side, but not other communities.

Port role is as important as VLAN mapping. A correct primary/secondary association with the wrong host/promiscuous assignment gives surprising forwarding. Platform capability is another concrete boundary: ordinary VLAN support does not imply PVLAN support, and Fortinet’s feature matrix must be checked for the exact model.

ObservationProvesDoes not prove
Primary/secondary associations are correctThe PVLAN domain relationship is configured.Each access port has the correct PVLAN role.
Two isolated hosts cannot communicate but both reach gatewayIsolated forwarding is enforced for those ports.Community behavior elsewhere is correct.
Feature matrix lists PVLAN for exact modelPlatform supports the mechanism.Current deployment is configured correctly.

Scenario: IoT hosts can ping the gateway but also each other. If the VLAN mapping is correct, the failed boundary is host-port role/enforcement—not Layer 3.

FortiAP

5. Bonjour Micro-Location: Confining mDNS Service Discovery by FortiAP Group

Primary feature lesson source: FortiAP Connectivity Profiles / Bonjour Micro-Location
Scenario support: Bonjour profile compatibility with tunnel-mode SSIDs

Micro-Location adds a physical-location boundary to Bonjour service forwarding. A Bonjour profile already defines from-VLAN, to-VLAN and allowed service classes (AirPlay, printers, Chromecast and others). With `micro-location` enabled, FortiAP group membership supplies a location name so mDNS from one FortiAP group stays isolated from another group even when the SSID/VLAN design is shared.

The profile is applied through the FortiAP profile. Runtime proof exists on both controller and AP. `diagnose wireless-controller wlac -c bjprof` displays controller profile state. On the AP, `cw_diag -c bonjour` shows Micro location status/name, and `bjallow` shows from/to interfaces and allowed Bonjour service names. These are much stronger than merely seeing a profile in FortiGate configuration.

Forwarding architecture matters. Fortinet notes the AP Bonjour Gateway applies to bridge-mode VAPs. Tunnel-mode VAPs are Layer-3 interfaces on FortiGate, so cross-subnet multicast discovery requires multicast routing/forwarding rather than assuming AP-local Bonjour gateway behavior.

FortiNAC

6. Persistent Agent State: Registration, Hello Traffic, Scanning, and At-Risk Outcomes

Primary feature lesson source: Using the Persistent Agent
Scenario support: Error Scanning from Hosts view

The Persistent Agent is a long-lived endpoint process that communicates with FortiNAC at configured intervals. Registration, network presence, agent process availability, agent communication, compliance-policy selection and scan execution are separate states. An endpoint can be registered and online while its Persistent Agent is stale, stopped or blocked.

Fortinet support identifies periodic agent Hello traffic and TCP 4568 as useful evidence. If Hosts view says no live online+communicating adapter, first confirm the host is online, then test the agent channel. A failed on-demand scan without an agent can mark the host at risk without normal scan-result history because no compliance scan completed.

FortiNAC-F

7. Scan on Connect: Endpoint Compliance Policy Selection and Re-Scan State

Primary feature lesson source: Scan on connect
Scenario support: Persistent Agent certificate scan troubleshooting

Scan on Connect is enabled on an individual Scan and applies to registered hosts with the Persistent Agent; Fortinet explicitly says it is ignored when the Dissolvable Agent is used. On an online transition, FortiNAC-F matches the host/user against ranked endpoint compliance policies, selects the policy’s compliance configuration, then uses that configuration’s agent and scan settings.

Disconnect changes the host’s Scan on Connect status so the next connection triggers a new scan. A link-down/link-up event plus agent communication can therefore cause a rescan. On multi-interface hosts the trigger is host online/agent communication state, not a requirement that the same NIC return.

Custom scan debugging must inspect the exact datum. Fortinet’s certificate-check support article shows the certificate payload expected in agent logs and notes that missing data can mean the certificate is not in Local Computer → Personal → Certificates or uses a format/provider the agent cannot read.

FortiAuthenticator

8. SAML Identity Provider: Portal, SP Metadata, Assertions, and Interface Exposure

Primary feature lesson source: SAML IdP General settings
Scenario support: SAML IdP 403 after 6.6.5 upgrade

FortiAuthenticator can expose an IdP portal and IdP-initiated login URL for service providers that allow IdP-initiated assertion responses. The transaction has distinct boundaries: browser reaches IdP service, IdP identifies the SP, user authentication completes, an assertion is created/signed, the SP ACS endpoint validates it, and the application session is established.

SP metadata therefore matters independently of user credentials. A wrong entity/ACS/SLS definition can produce a 403 even when the IdP login page and user authentication are healthy. Fortinet also documented a 6.6.5 multi-interface issue where disabling SAML on one interface could disable it more broadly; the workaround was enabling SAML on all interfaces, fixed in 6.6.6.

FortiPAM

9. Privileged Session Recording and Live Monitoring

Primary feature lesson source: Over-the-shoulder monitoring
Scenario support: Active Session Video Monitoring delay

Live monitoring depends on a secret session launched with Session Recording enabled, Live Recording enabled in system settings, and a supported Privileged Access Agent where required. Monitoring is reached through Monitoring → Active Sessions. A recording icon identifies sessions eligible to stream, and the monitor can disconnect the current secret session.

Fortinet’s July 2026 support article is important because “live” is not zero-latency. It documents expected processing/streaming delays—approximately 8–13 seconds in FortiClient mode and 6–10 seconds in agentless mode—and recommends collecting WAD debug evidence when delay consistently exceeds 30 seconds. The feature therefore has a recording/processing/streaming pipeline, not an instantaneous screen mirror.

FortiSIEM

10. Incident Clear Conditions: Original-Rule Silence, Subpatterns, and Status Semantics

Primary feature lesson source: Creating Rules / Clear Conditions
Scenario support: Incident Status discussion

Clear conditions turn Active incidents into Cleared incidents after explicit rule logic is satisfied. FortiSIEM supports a time window followed by either Original Rule Does Not Trigger or a subpattern based on incident attributes. Fortinet notes the original-rule-silence option is not available for Scheduled Rules.

Clearing status and analyst resolution are different. Auto Cleared means rule clear logic fired; Manually Cleared, System Cleared and Externally Cleared identify other mechanisms. None of those states alone says the original detection was a false positive. That determination belongs to resolution/analyst workflow.

Scenario: an incident “mysteriously” clears. First identify the clearing mechanism in status/audit. If it is Auto Cleared, inspect rule clear condition; if System Cleared or an AI/ML mechanism is involved, debugging the rule’s clear timer alone is the wrong boundary.

FortiSASE

11. Digital Experience Monitoring: Endpoint-to-PoP-to-SaaS Decomposition

Primary feature lesson source: Digital Experience Monitoring
Scenario support: Zoom/Teams missing from DEM

FortiSASE DEM uses an endpoint agent to trace user experience from endpoint to FortiSASE PoP and onward to SaaS applications. It also reports endpoint CPU, memory, disk and bandwidth. That lets an engineer separate endpoint resource pressure, endpoint-to-PoP access/ISP degradation, and PoP-to-SaaS path behavior.

Endpoint Details exposes management connection and tunnel state separately from DEM metrics. A tunnel being up proves connectivity to FortiSASE; it does not prove acceptable latency to a SaaS application. Subscription and release track also affect capability. Fortinet documents DEM entitlement for Advanced/Comprehensive remote-user subscriptions and a limited trial path for Standard/NFR.

Fortinet support documented Teams/Zoom missing in the Mature branch while appearing after moving to the Feature branch. Therefore “application absent from DEM” can be a feature/release-visibility issue, not evidence that the endpoint never used the application.

Secure SD-WAN

12. Passive Application SLA Measurement: Live TCP Evidence, Per-App Metrics, and Offload Tradeoffs

Primary feature lesson source: Passive health-check measurement by internet service and application
Scenario support: Passive performance SLA

Passive measurement derives latency, jitter and loss from real TCP sessions crossing firewall policies with passive WAN health measurement enabled. Per-application/per-ISDB differentiation requires the SD-WAN rule to identify the application/service and enable passive measurement, allowing two applications on the same WAN link to accumulate different SLA evidence.

The measurement requirement has a direct forwarding tradeoff: Fortinet documents that enabling `passive-wan-health-measurement` disables `auto-asic-offload` because FortiOS must observe the session information. `diagnose sys link-monitor-passive admin list by-interface` and by-application views show collected data. Session state can also expose TCP three-way RTT tracking.

Pure passive measurement cannot create quality samples without live traffic and is not a substitute for all liveness detection. Prefer-passive can fall back to active probing after the documented idle interval. Therefore an idle link with no passive samples is not equivalent to a link that has been measured healthy.
