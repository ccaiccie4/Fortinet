LESSON 01 · FortiOS 8.0.0

FortiGate — FortiOS 8.0 TLS 1.3 IPsec transport over TCP

680 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose and boundary

IPsec normally begins with IKE over UDP/500 and moves NAT-traversed data to UDP/4500. That works on most Internet paths, but some hotels, guest networks, cellular providers, and enterprise egress controls block UDP or permit only TCP/443-like traffic. FortiOS 8.0 adds a TLS 1.3 based VPN-over-TCP transport so two FortiGate peers can establish the IKE/IPsec relationship through a TCP/TLS path when the ordinary UDP path is unavailable. This is a transport adaptation, not a replacement for IKE authentication, Phase 2 selectors, routes, or firewall policy.

Keep the support boundary explicit: the new TLS-based VPN-over-TCP mode is documented for FortiGate-to-FortiGate tunnels. Separate RFC 8229 TCP encapsulation support in general IPsec documentation does not prove that a FortiClient endpoint supports this particular TLS mode. Do not turn on a design assumption based only on seeing “TCP encapsulation” in a different client compatibility table.

Mechanics and transaction flow

The feature is gated by per-VDOM service settings. ike-tcp-service enables the TCP listener and ike-tls-service enables the TLS listener. The Phase 1 interface transport selection determines how a tunnel uses them. In an Auto design, the peers try the normal UDP path first; when the path cannot establish the tunnel and the TCP/TLS services are available, the negotiation can fall back to the supported TCP transport. IKE remains responsible for peer authentication and key exchange. The negotiated security associations then protect the data plane; ESP traffic is carried within the selected transport.

That layering matters during troubleshooting. A successful TCP three-way handshake proves only that the path reaches the listener. A successful TLS handshake proves that the TLS peer-certificate checks completed. A completed IKE exchange proves that the IKE peer and proposal negotiation succeeded. A Phase 2 SA proves that selectors and keys were negotiated. None of those alone proves that a remote subnet is reachable: route selection, policy, NAT, and the remote host still matter.

Configuration pattern

config system settings
    set ike-tcp-service enable
    set ike-tls-service enable
end

config vpn ipsec phase1-interface
    edit "branch-to-hub"
        set ike-version 2
        set transport auto
    next
end

Apply the service gates in the relevant VDOM on both peers, and use the exact CLI spelling and supported options from the target FortiOS build. Import the issuing CA and ensure peer identity matches the certificate. For a certificate-authenticated deployment, treat the certificate subject/SAN and the configured peer identity as part of the tunnel design, not as a cosmetic TLS setting.

Evidence and troubleshooting

Start with diagnose vpn ike gateway list and confirm the negotiated transport and peer identity. Enable IKE application debug only for a controlled reproduction; correlate the first UDP attempt with any TCP/TLS fallback and the certificate verification result. A packet capture should show whether UDP/500 or UDP/4500 is leaving, whether the TCP listener is reached, and whether the TLS handshake completes. If TLS succeeds but IKE fails, inspect IKE version, authentication, proposal and peer-ID settings. If IKE and Phase 2 succeed but application traffic fails, stop changing transport and inspect route lookup, policy hit counts, selectors, NAT and return routing.

Upgrade and operational caveats

FortiOS 8.0 release behavior changes how some existing tunnels are represented after upgrade: dynamic dial-up Auto configurations can use the new fallback behavior when the services are enabled, while static tunnel transport settings may be normalized differently. Review the upgrade notes and explicitly inspect static Phase 1 entries rather than assuming every pre-upgrade Auto value remains identical. Test one branch through a UDP-blocked path before broad rollout. Keep a known-good UDP path available during migration and document which peers are expected to support the FortiGate TLS transport.

Operational exercise

A branch reports that the tunnel is down only on a guest ISP. First prove whether UDP/500 and UDP/4500 are blocked. Then verify both VDOM service gates, the selected Phase 1 transport, certificate chain and peer identity. If the TLS handshake succeeds but the SA does not, inspect IKE debug. If the SA is up, use a route lookup and policy counters before concluding the new transport is faulty.

LESSON 02 · FortiManager 8.0.0

FortiManager — FortiManager 8.0 ADOM upgrade readiness and schema conversion

632 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose: firmware version is not ADOM version

An ADOM is a management and database boundary for a class of devices. Its version determines the FortiOS syntax and object model that FortiManager uses when it stores policies, objects, device settings and package state. FortiManager appliance firmware and ADOM schema version are separate dimensions. Upgrading FortiManager does not mean every ADOM is automatically ready to use the newest syntax, and an ADOM can manage devices whose firmware versions are constrained by the ADOM compatibility matrix.

The ADOM upgrade-readiness tool is a preflight check. It examines the managed device and VDOM configurations against the target ADOM syntax and reports unsupported, invalid or missing configuration elements. It does not repair the devices or make the conversion safe by itself. Treat the report as a migration work list and as evidence of the exact object that must be corrected before the schema conversion.

Upgrade transaction

The safe sequence is: establish a recoverable backup, verify the target ADOM version supports the lowest managed FortiOS version, lock the workspace ADOM if workflow mode is enabled, run the readiness check, remediate every reported object, and then perform the ADOM upgrade. FortiManager converts its ADOM database objects and exposes the target feature set. After conversion, resynchronize managed devices and use install preview to validate the proposed device configuration before an install. A clean readiness report is not the same as a successful device install; it proves the preflight did not find the checked incompatibilities, not that every target accepts every command.

Do not batch unrelated ADOM versions into a single assumption. Use the supported ADOM-version matrix for the exact FortiManager build. Upgrade ADOMs with the same source version together where the documented workflow requires it. Device firmware upgrades are a separate operation and should be planned separately from ADOM schema conversion.

Remote certificate failure as a real blocker

A recent Community case demonstrates why readiness is not merely a firmware compatibility check. An ADOM upgrade from 7.4 to 7.6 failed with This remote certificate is invalid. The affected remote certificate object lacked its PEM wrapper lines. The certificate content could still be referenced by an existing SAML or PKI user, but the upgrade parser rejected the non-standard stored representation. The failure was in shared ADOM object data, not in the FortiGate tunnel or the certificate's cryptographic strength.

Inspect Policy & Objects > Advanced > Remote Certificate in the root ADOM. Use Where Used to identify SAML/PKI consumers and export the readiness report to find the affected object. After taking a backup, restore only the required -----BEGIN CERTIFICATE----- and -----END CERTIFICATE----- wrapper around the unchanged certificate bytes. A script can update the shared remote certificate object, but it should be reviewed and tested before execution because a global-scope certificate can affect multiple packages.

config vpn certificate remote
    edit "certificate"
        set remote "-----BEGIN CERTIFICATE-----
<unchanged certificate bytes>
-----END CERTIFICATE-----"
        set range global
    next
end

Evidence and recovery

Save the readiness report and identify each object by ADOM, device/VDOM and syntax path. For a repeat failure, capture timestamped CDB, DVMDB, DVM command, system and main service debug around one controlled retry. Do not repeatedly run a failing conversion without logs; it obscures the first failing object. After the upgrade, compare package status, device database state and install preview. For devices using the corrected certificate, inspect the rendered install diff for unintended SAML or PKI changes.

Operational exercise

Several FortiGates are in a 7.4 ADOM and the upgrade readiness report names one remote certificate. A FortiManager firmware upgrade alone will not fix the object. Find its consumers, repair the PEM representation, rerun readiness, convert the ADOM, resync the devices and preview the install. If preview is clean but installation fails, move to device-specific syntax and firmware compatibility rather than repeating the ADOM conversion.

LESSON 03 · FortiAnalyzer 8.0.0 / FortiOS 8.0

FortiAnalyzer — FortiAnalyzer 8.0 FortiMQ connector and Cloud Fabric Feed enforcement

651 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose and control-plane boundary

FortiAnalyzer 8.0 adds a FortiMQ connector for distributing indicators that an analyst has blocked. The connector moves an indicator from an investigation context into a cloud-delivered feed that a FortiGate can consume. Supported indicator types include IP addresses, URLs, domains and MAC addresses. The connector is not itself a firewall policy, and an indicator being marked Blocked in FortiAnalyzer does not prove that a FortiGate is already dropping traffic. The enforcement step occurs only after the target FortiGate retrieves the feed and a policy or security profile references the resulting external resource.

The connector is disabled by default and is scoped to the source ADOM. That scope is operationally important in multi-ADOM environments: an analyst can block an indicator in one ADOM while a FortiGate managed in another ADOM never receives it. The documented design also requires the FortiGate and FortiAnalyzer to be associated with the same FortiCare account. Confirm that account relationship before investigating playbook syntax.

Indicator transaction

FortiGate logs are sent to FortiAnalyzer. The analyst creates or selects an indicator in the Indicators, Incidents or Log View workflow and changes its status to Blocked. The block_indicator playbook submits the indicator to FortiMQ. The FortiGate then synchronizes the Cloud-based Fabric Feed. A feed object is populated with the indicator, but the administrator still has to reference that object in the appropriate firewall policy or security profile for the traffic type. Unblocking an indicator changes the source state and should flow through the same distribution path.

This is different from a direct automation stitch that sends an action to a FortiGate. FortiMQ is an indicator-distribution path; the FortiGate consumes the feed as a policy data source. The FortiAnalyzer 8.0 feature notes also describe the existing FortiManager connector as a separate option. If an environment intentionally uses the FortiManager connector, FortiMQ may need to be disabled rather than assuming both paths will arbitrate identically.

Configuration and verification

In the relevant FortiAnalyzer Fabric/FortiGate ADOM, enable the existing FortiMQ connector and verify its status. Confirm the target FortiGate is registered to the same FortiCare account and that cloud-based Fabric Feed synchronization is enabled on the firewall. Trigger a test indicator with a known value and record its type, ADOM, creation time and status. Inspect the playbook execution result. Then inspect the FortiGate feed contents and last-update time. Finally, verify that the correct feed object is referenced by the intended policy/profile and test traffic using a controlled source/destination.

Use evidence in layers. An Active connector proves the API session is available. A successful playbook proves FortiAnalyzer submitted the indicator. A populated FortiGate feed proves the firewall retrieved it. A policy reference proves the object is in the enforcement path. A controlled traffic test or policy counter proves the rule actually matched. These are separate checkpoints; skipping one leads to false conclusions about where the block failed.

Operational scenario

A FortiAnalyzer investigation detects a suspicious Node2Shell-related indicator. The incident workflow can provide the forensic context and the indicator to block, but the new connector lesson is about delivery and enforcement. If the indicator appears in FortiAnalyzer but not the firewall, check connector status, FortiCare association, ADOM scope and cloud-feed synchronization. If it appears in the firewall feed but traffic is still allowed, inspect the policy/profile reference, rule order, address family and traffic type. Do not keep rerunning the playbook when the missing step is the FortiGate policy reference.

Scale and change control

Use a controlled test indicator and a documented owner for each ADOM. Avoid broad blocks without validating indicator type and scope; a MAC indicator is meaningful only on a path that sees that layer-2 identity, while an IP/domain/URL indicator has different enforcement points. Keep the feed source, policy reference and unblock process in the same change record so that incident closure removes the enforcement state as deliberately as incident response added it.

LESSON 04 · FortiSwitchOS 7.6.5

FortiSwitch — FortiSwitch egress QoS: trust maps, queues and schedulers

623 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose: classification is not scheduling

FortiSwitch QoS controls which egress queue receives a frame and how the egress scheduler services that queue. Marking, classification, queue selection and scheduling are separate stages. A packet can carry DSCP EF or an 802.1p priority value and still receive best-effort treatment if the ingress trust map is wrong. Conversely, a packet can be placed in a high queue but receive no useful end-to-end guarantee if the next hop ignores the marking or the queue is oversubscribed.

FortiSwitch exposes eight egress queues, numbered 0 through 7. CoS maps translate 802.1p priority values to queues; IP/DSCP maps translate DSCP values to queues. Port trust settings decide which marking is authoritative. When both CoS and DSCP trust are enabled on a port, DSCP takes precedence, so enabling both without an explicit design can make the CoS map appear ineffective. Queue 7 is reserved for switch control and critical management traffic; do not map ordinary user data into it just because the application uses a high DSCP value.

Packet path

At ingress, the switch reads the trusted CoS or DSCP value and maps it to an egress queue. The port's QoS policy defines the scheduler and queue parameters. Strict priority always services higher-priority queues before lower queues when they are non-empty; that protects delay-sensitive traffic but can starve lower queues if high-priority load is unbounded. Round Robin rotates service. Weighted Round Robin allocates service according to configured weights and is often a safer choice when several classes need bounded fairness. The selected drop policy controls what happens when a queue fills: tail drop discards at the end of the queue; RED/WRED can discard probabilistically before full congestion and, where supported, ECN can mark instead of dropping.

Minimum and maximum rates, weights, drop policy and ECN support vary by switch model and ASIC. A command accepted by a generic CLI parser is not proof that the hardware implements every parameter. Check the FortiSwitch feature matrix for the exact model and FortiSwitchOS release before copying a policy across mixed hardware.

Configuration pattern

config switch qos dot1p-map
    edit "voice-cos"
        set priority-5 5
        set priority-6 6
    next
end

config switch qos ip-dscp-map
    edit "voice-dscp"
        config map
            edit "ef"
                set diffserv EF
                set cos-queue 5
            next
        end
    next
end

config switch qos qos-policy
    edit "edge-egress"
        set schedule weighted
        config cos-queue
            edit queue-5
                set weight 5
                set drop-policy taildrop
            next
        end
    next
end

Bind the intended maps and policy to the relevant port using the exact CLI syntax supported by the model. On a managed FortiSwitch, also verify whether the policy is configured locally or pushed through FortiLink from FortiGate.

Evidence and troubleshooting

Read the port's trust settings, map contents and attached QoS policy before looking at application latency. Generate a controlled flow with known DSCP/CoS, observe the ingress marking, then inspect per-port queue counters and drops during congestion. Do not confuse port queue 7 with the switch CPU's internal traffic queues. Control-plane frames such as LLDP, MCLAG, BFD, ARP and FortiLink are handled through CPU paths and may be accounted separately. A rising queue counter proves classification/queue activity; it does not prove the upstream device honors the same DSCP or that the egress scheduler is the only bottleneck.

Operational exercise

A Dante or voice flow is marked EF but suffers jitter. Confirm the port trusts DSCP, EF maps to the intended data queue (not queue 7), and the egress policy uses a scheduler appropriate for the other classes. Check whether strict priority starves lower traffic or whether a model limitation ignores the configured minimum rate. Then validate the next hop's QoS map. Do not solve a voice problem by consuming the reserved control queue and risking FortiLink or spanning-tree stability.

LESSON 05 · FortiAP/FortiOS 8.0.0

FortiAP/Wireless — FortiAP wireless packet sniffer and browser-streamed PCAP

628 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose: capture the air interface, not just the tunnel

When a wireless client fails to associate, roams unexpectedly, retries heavily or never sees a beacon, a capture on the FortiGate's wired interface cannot show the over-the-air 802.11 exchange. FortiAP's wireless traffic packet sniffer places a selected AP radio into a capture mode so the radio can observe frames on a chosen channel and width. This is a radio-local diagnostic, distinct from capturing CAPWAP packets between AP and controller. The distinction determines where to capture and what a missing frame means.

Capture mechanics

The capture is configured through a managed AP/WTP profile. Select the radio to be used for sniffing, choose the channel and channel width, and set the buffer and filters. Filters can narrow by station MAC address and frame types such as management, control or data. The AP listens on that radio/channel and streams captured frames to the FortiGate GUI, which forwards them to the administrator's browser. The capture is not stored as a persistent PCAP on FortiGate; stop the capture and save the PCAP locally before changing the radio mode or navigating away.

Only one radio per AP profile can be used in sniffer mode at a time, and an AP capture is a scarce radio resource. A radio that is sniffing is not simultaneously providing its normal service on that band. Do not expect one AP to capture two different channels or bands at once. For simultaneous 2.4, 5 and 6 GHz analysis, use separate APs or a dedicated multi-radio capture design. The Fortinet guide also describes a one-capture-at-a-time limitation for the AP, so coordinate with other operators before starting a session.

How to configure and preserve evidence

In the FortiGate wireless controller interface, edit the target WTP profile, select the radio, enable packet-sniffer mode and set channel, width, capture buffer and frame filters. Apply the profile to a test AP rather than a production AP carrying a critical SSID. Start the capture, reproduce one client event, stop the capture and save the resulting PCAP to the workstation. Record AP serial, radio index, channel, width, station MAC, filter and time range with the file. A PCAP without those conditions is difficult to interpret because 802.11 frames are channel-specific.

What the capture proves

Beacon and probe frames show what the AP or client advertised on that channel. Authentication and association frames show the management exchange. Control frames such as acknowledgments and block acknowledgments help explain retransmissions and airtime behavior. Data frames show over-air payload exchange, subject to encryption and capture visibility. Radiotap/802.11 metadata can expose signal, data rate and retry indicators. A capture with no client frames does not prove the client transmitted nothing: the AP may be listening on the wrong channel, using the wrong width, filtering the wrong MAC, or operating on a different band.

When the problem is AP/controller connectivity rather than client-to-AP radio behavior, capture CAPWAP control/data traffic separately. CAPWAP control uses UDP/5246 and data uses UDP/5247 in the standard path. An over-air sniffer cannot prove that the CAPWAP DTLS control channel is healthy; a wired capture cannot show the client probe/association exchange. Use the capture point that matches the layer of failure.

Operational troubleshooting

For a client that cannot join a 6 GHz SSID, first confirm that the client supports the advertised band and security requirements. Set the AP radio to the actual 6 GHz channel and width, capture management frames without an overly narrow filter, and reproduce the attempt. If the probe is visible but authentication fails, inspect RSN/AKM negotiation. If the client never appears, validate channel, radio state and capture filters before blaming the WLAN controller. Always save the PCAP before returning the radio to service.

LESSON 06 · FortiNAC 9.4.0

FortiNAC — FortiNAC 9.4 MDM service connectors: host registration, health state and polling fan-out

991 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose and trust boundary

FortiNAC MDM Services is an inventory and posture integration, not a replacement for the NAC policy engine. FortiNAC queries a mobile-device-management platform through its API, uses the returned device record to recognize/register a host, and can retrieve health or application information. The MDM system remains authoritative for enrollment and its own compliance verdict; FortiNAC uses that data as an input to host identity, registration, and network-access decisions. Supported connectors include AirWatch, Fortinet EMS, Google GSuite, JAMF, MaaS360, Microsoft Intune, MobileIron, Nozomi, and Citrix Endpoint Management. The FortiNAC 9.4 guide explicitly states that proxy communication is not supported, so a successful browser test through a corporate proxy does not prove that the appliance can reach the MDM API.

Connector objects and authentication

Create the connector under Network > Service Connectors. The record binds a vendor to a unique connection name, API Request URL, and the vendor-specific identifier or key. For Microsoft Intune, FortiNAC 9.4.6 and later exposes an Authentication Type choice: Application Secret, Certificate, or Delegated Permissions. Application access uses an application password or X.509 certificate registered for the Intune application. Delegated access requires a user to sign in to the Azure portal and grant FortiNAC permission to call Intune on that user's behalf. Fortinet's configuration note recommends application permissions configured and granted in the MDM application registration portal; the legacy Enable Delegated Permissions setting remains enabled on older connectors created before the documented version boundaries. When migrating a connector, do not assume that an old delegated setting is equivalent to a new application-permission registration.

Other connector fields are vendor-specific. Application ID identifies the registered client, while Request URL selects the API endpoint. User ID and Password appear only for connectors that use those credentials. The Credential JSON field is used for the Google service-account integration. Test Connection checks the configured connection and authentication path; it does not prove that a host will be returned, registered, or assigned the intended NAC policy.

Host-data transaction flow

There are two distinct ways for a host to enter the MDM-derived data path. With On Demand Registration enabled, an unknown endpoint that reaches the captive portal causes FortiNAC to query the MDM server for that endpoint. If the device exists in the MDM database, FortiNAC creates/registers its host record from the returned data. This is a lookup triggered by a host-registration event, not a full inventory import. With automatic registration polling enabled, the MDM server returns its device inventory at the configured interval; FortiNAC registers the returned devices and marks them as MDM-managed. The guide warns that this bulk polling path does not provide a filter to restrict which returned devices are processed.

After a host record exists, the connector can refresh posture. Revalidate Health Status On Connect asks the MDM server for compliance each time the host connects. It is disabled by default because the MDM service may not sustain the resulting request rate. A less aggressive design is automatic registration polling once per day, which also retrieves health status with lower query frequency. Update Applications retrieves application inventory for hosts already present in the FortiNAC database; it is also disabled by default because it adds API load. It is not a host-creation switch. Remove Hosts is a destructive reconciliation option: when enabled, a poll deletes FortiNAC host records for devices removed or disabled in MDM.

Manager placement and data fan-out

In a FortiNAC Manager deployment, connector placement changes the number of upstream API transactions. If every managed FortiNAC server needs the MDM host records, configure the MDM Service Connector on the Manager. The Manager polls the MDM service once and copies the host records to its managed servers after each poll, reducing duplicate requests to the MDM platform. If only selected FortiNAC servers need the data, configure the connector on those individual servers instead; each configured server polls the MDM system independently. A Manager-side connector is therefore a data-distribution choice, not simply a UI preference.

Verification and fault isolation

Compare Last Poll with Last Successful Poll. Last Poll tells you when the connector attempted a poll; Last Successful Poll records the last poll that retrieved data successfully. If the first advances while the second remains old, inspect the Request URL, application ID, secret/certificate validity, delegated-versus-application permission model, and MDM API authorization. Use Poll Now to reproduce the transaction and review the service-connector audit log. Then verify a known enrolled device in Host View, including the MDM-managed state and health fields. A successful Test Connection with no new host records usually points to the vendor inventory response, identifier mapping, polling option, or host-matching data rather than a switch VLAN problem.

Scale and operational caveats

Do not enable Revalidate Health Status On Connect and Update Applications across a large estate without measuring the API request rate and vendor throttling behavior. Use a deliberate polling interval and stagger connectors where the Manager is not distributing data. Before enabling Remove Hosts, test what the MDM platform considers removed or disabled; an MDM cleanup can otherwise delete a host record that still matters to a NAC workflow. Keep the MDM registration path separate from the later enforcement path: MDM data can identify and classify a host, but the FortiNAC Network Access Policy, host state, and switch/RADIUS integration still determine the resulting network access.

Operational exercise

A laptop is compliant in Intune but appears as an unknown host at the FortiNAC captive portal. First confirm that the Intune connector's Last Successful Poll is current and that the endpoint exists in the MDM inventory. If the design relies on on-demand registration, verify that the option is enabled and that the device identifiers returned by Intune match the endpoint being presented. If the record exists but posture is stale, inspect the health-revalidation/poll schedule rather than changing the switch VLAN. If the Manager owns the connector, confirm that the host record was propagated to the FortiNAC server controlling that access network.

LESSON 07 · FortiNAC-F 7.6.3

FortiNAC-F — FortiNAC-F 7.6.3 vulnerability-scanner integration: scan thresholds to network enforcement

914 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose and architecture

FortiNAC-F's vulnerability-scanner integration imports results from Tenable Vulnerability Management or Qualys and associates those results with FortiNAC host records. FortiNAC-F is not the scanner and does not prove that a scan ran merely because the service connector is healthy. The scanner performs the assessment; FortiNAC-F polls the vendor API, processes completed scan results, evaluates configured failure thresholds, emits events, and can translate those events into host-security actions. The integration therefore has four separate boundaries: API connectivity, scan execution, result ingestion, and NAC enforcement.

Connector configuration

Create the connector under Network > Service Connectors > Vulnerability Scanners. For Tenable, supply a display name, Request URL, and an authentication type. The guide supports a Tenable username/password or an API Access Key/Secret Key. For Qualys, supply the Qualys Request URL, account username/password, and the appliance that will execute the scan. Enable Poll Scan Result and set the Repetition Rate if FortiNAC-F should retrieve results automatically. Test Connection validates the API path and credentials; use Poll separately to request results now. A connector can be reachable while no completed scan exists to ingest.

The Global SNMP Credential is separate from scanner authentication. FortiNAC-F can use it to retrieve device ID, device location, and firmware version for scanned target hosts. If a host uses a different SNMP security string, configure that host-specific credential. The guide notes that Device Location is displayed only when it can be retrieved for a public IP. Do not troubleshoot a missing SNMP enrichment field by changing the Tenable or Qualys API password.

Scan objects, targets, and thresholds

After the account test succeeds, move to Scan Configuration. Existing scans can be selected from the vendor web application, or a scan can be created through the vendor API. Tenable's API-created scan includes a scan template, optional Agent Group ID, activation status, target hosts, and failure thresholds. Qualys uses an Option Profile Title that must match an existing Qualys option profile, a scan frequency, target hosts, and failure thresholds. Targets can be an IP address/range or a dynamic FortiNAC filter based on host, access, policy-agent, MDM, or additional host attributes. For Qualys, the target IP must also exist in Qualys Asset Address Management; otherwise the scanner can refuse a rescan even though the FortiNAC connector authenticates.

Thresholds are the policy boundary. The configured threshold specifies the number of vulnerabilities at a severity level that causes the host to fail. Multiple scans can target one host. During a poll, FortiNAC-F processes the results for configured scans that completed since the previous poll. If any host's result meets or exceeds the failure threshold for a scan, the host is identified as failing. A host can therefore fail because of one scan while another scan for the same host passed.

Events and enforcement workflow

FortiNAC-F emits Vulnerability Scan Started/Finished events and a Vulnerability Scan Passed or Vulnerability Scan Failed event when it processes the result. For enforcement, configure an administrative scan with a Host Security action, then map Vulnerability Scan Failed to the At Risk action and Vulnerability Scan Passed to the Safe action. The Remediation Portal can display the scanner's vulnerability details and remediation guidance. After remediation, the user or operator can request a rescan; a passing result can then move the host back to the Safe state.

The Vulnerability Exceptions Group is a deliberate bypass. Hosts in that group are allowed onto the network regardless of scan results. Their failed scan may be logged as Vulnerability Scan Ignored, may not appear in the remediation portal, and the Host View Vulnerability Scan Status can display Passed for an exception-group host. That is not proof that the scanner found no vulnerabilities; it is proof that the exception policy overrides the normal posture display/enforcement path.

Evidence patterns that isolate the failure

  • Vulnerability Scanner Connection Failure: the FortiNAC-F-to-vendor API connection failed. Check Request URL, credentials, TLS reachability, and vendor service state.
  • Vulnerability Scan Incomplete: FortiNAC-F polled for a configured scan but the vendor had no result because the scan was not run. Check activation, schedule, target, and vendor-side scan history.
  • Vulnerability Scan Skipped: the scanner has not run that scan since the previous poll, so there is no new result to process.
  • Vulnerability Scan Request Refused (Qualys): the target IP is not in Qualys Asset Address Management. Add the IP to the vendor asset list before requesting a rescan.
  • Vulnerability Scanner Concurrent/Periodic API Limit Exceeded (Qualys): the vendor rejected a request because its API concurrency or rate limit was exceeded. Reduce poll frequency or concurrency and honor the retry interval in the event message.
  • Vulnerability Scan Ignored: the host is in the exception group; do not treat the Passed display as a clean scan.

In Host View, add Vulnerability Scan Status, Last Vulnerability Scan, Vulnerability Details, and Vulnerability Source. The timestamp represents when the scan result was processed for that host. It does not prove that a new scan ran after the most recent remediation unless the vendor scan timestamp and FortiNAC event sequence confirm it.

Operational exercise

A host is not being quarantined although its connector shows green. First check whether the vendor scan actually ran. If FortiNAC-F records Vulnerability Scan Incomplete, run the scan at the scanner and poll again. If Qualys refuses the rescan, verify the IP is registered in Asset Address Management. Once a failed result is ingested, inspect the threshold, event, alarm mapping, and Host Security action. Finally, check the Vulnerability Exceptions Group before assuming the enforcement action failed.

LESSON 08 · FortiAuthenticator 8.0.1 REST API Guide

FortiAuthenticator — FortiAuthenticator 8.0 REST API bulk local-user operations and request correlation

804 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose and API surface

FortiAuthenticator 8.0 expands the Local Users REST resource so automation can manage user cohorts without issuing a separate request for every account. The 8.0.0 API enhancements add a users field for listing users and allow collection-level POST and DELETE on /api/v1/localusers/ to create or delete multiple local users. The same release adds custom1, custom2, and custom3 filters to the Local Users endpoint and expands the CSV import/export filters. This is a user-lifecycle API feature; it does not change RADIUS policy selection or make a local account automatically authorized for a network service.

Use the REST API Solution Guide's initialization, API-admin, authorization, data-format, and resource sections for the deployed version. A dedicated API administrator and API key should be used for automation rather than a human administrator's interactive password. Use HTTPS and validate the FortiAuthenticator server certificate in production. The guide's sample uses curl -k to simplify a lab request; disabling certificate validation should not become the production trust model.

Bulk transaction and correlation

The new collection methods are distinct from the older per-record methods: POST /api/v1/localusers/ creates multiple local users, while DELETE /api/v1/localusers/ deletes multiple local users. The public 8.0 feature note identifies the methods and resource but does not define a universal all-or-nothing transaction guarantee. Do not assume that a batch is atomic or safely repeatable after a timeout. Capture the response, use a read-after-write query to verify the resulting user set, and reconcile any partial or ambiguous outcome before retrying a create or delete operation. Use the detailed request-body schema in the version-matched API guide; do not infer a batch payload from the older single-user POST example.

FortiAuthenticator also supports the optional HTTP X-Request-ID header for distributed request tracking. It accepts ASCII letters, digits, hyphen, and underscore, with a maximum length of 64 characters. The header is supported for GET, POST, PUT, PATCH, and DELETE operations on Local Users, LDAP Users, IAM Accounts, IAM Users, FortiTokens, User Groups, and Local Group Memberships. The example below shows a read request; the response includes the supplied identifier in meta.request_id:

curl -X GET \
  https://[FAC_IP]/api/v1/localusers/ \
  -H 'Content-Type: application/json' \
  -H 'X-Request-ID: batch_20261109_01' \
  -u 'api-admin:[api_key]'

Use a new request ID for each logical batch and retain it in the automation log. When an API job reports a timeout, the request ID lets an operator correlate the client attempt with FortiAuthenticator's server-side log/response metadata. It is a correlation token, not an authentication credential, idempotency key, or encryption mechanism.

Filtering and cohort management

The new custom1, custom2, and custom3 filters allow an automation system to query local users by custom metadata. A practical pattern is to place a stable cohort identifier such as contractor-2026q4 in one custom field, then use the filter to read the exact cohort before changing it. The CSV Local Users endpoint also supports filtering by username, abridged output, and custom1/custom2/custom3. This can simplify inventory export and reconciliation, but CSV import/export and REST batch operations are separate interfaces with different semantics.

Evidence and verification

For a GET request, check the HTTP result, meta.request_id, and returned objects. The echoed request ID proves that the server processed the correlation header for that request; it does not prove that a different POST/DELETE batch succeeded. After a batch operation, query the Local Users resource using the cohort filter and compare the returned usernames, active state, and group memberships with the intended change set. For accounts used by RADIUS, also verify the required RADIUS attributes, certificate binding, user-group membership, and the actual Access-Accept. A local-user record existing in the database does not prove the RADIUS policy selected the intended identity source or returned the required authorization attributes.

Operational caution from the Community

A FortiAuthenticator Community report dated October 27, 2026 describes a separate CSV import issue: with “Keep existing user accounts” enabled, some existing accounts lost RADIUS attributes such as certificate binding after import. The report concerns the CSV path, not the new REST collection POST/DELETE implementation, so it must not be treated as proof that REST batches have the same defect. It is nevertheless a useful control: after any bulk user-data operation, compare the affected users' RADIUS attributes and certificate bindings and perform a controlled authentication test before closing the change.

Operational exercise

An identity automation job provisions a batch of contractor accounts, then times out before recording success. Do not blindly resend the POST. Query the Local Users collection using the cohort's custom field, compare actual accounts with the requested list, and use the original request ID to search the server-side evidence. Reconcile only the missing accounts. Before a bulk DELETE, export the target cohort, verify the filter result, and keep the request ID and returned response with the change record.

LESSON 09 · FortiPAM 1.9.0

FortiPAM — FortiPAM 1.9 JIT privilege through secret checkout/check-in

661 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose and security model

Just-in-Time privilege elevation lets a user work with a normal account and receive temporary membership in a privileged Windows group only while a secret is checked out. FortiPAM 1.9 implements this through optional PowerShell checkout and check-in scripts attached to a secret. At checkout, FortiPAM connects to the target over WinRM and adds the user to an elevated local or domain group. At check-in, it executes a second script to remove that membership. The intent is to shorten the lifetime of privileged group membership rather than to leave users permanently in Administrators or Domain Admins.

Transaction and credential resolution

The user checks out a secret. FortiPAM resolves the administrative credential used to run the script: it first uses a privileged account defined on the target in the secret, and if none exists it tries the associated secret account. FortiPAM then opens a WinRM session to the Windows target and executes the configured checkout script. A common local elevation is Add-LocalGroupMember -Group Administrators -Member $USER. For a domain group, a script can use Add-ADGroupMember with the appropriate group and member identity.

When the user checks in the secret, FortiPAM repeats credential resolution and WinRM execution with the check-in script, for example Remove-LocalGroupMember or Remove-ADGroupMember. The removal operation returns the account to its prior group membership state only if the script succeeds and targets the same identity/group that checkout modified. A check-in click is not proof that the target was de-elevated.

WinRM and token behavior

WinRM must be enabled and reachable on the Windows target. Validate it with winrm quickconfig and Get-Service winrm; the service should be running and firewall policy should allow the configured WinRM transport. The account used to execute the script needs only the rights required to modify the relevant group. Avoid using a broad domain administrator credential for every target when a narrower delegated account can perform the group operation.

Windows access tokens are created at logon. Adding a user to a local or domain group does not necessarily change the token of an already-running RDP or console session. After checkout, the user may need to sign out and sign in again before the new group membership appears. After check-in, a new logon token is likewise required to remove the elevated rights from the user's session. This is a Windows token lifecycle issue, not a FortiPAM launcher bug.

Failure behavior and evidence

FortiPAM documents that script failure does not block checkout/check-in; the user receives a warning and the secret workflow continues. That is deliberate separation between credential availability and the external target-side privilege operation, but it creates an operational control obligation. Check the secret activity/log for script execution result, then query the target's group membership. If checkout succeeded but the user is not elevated, verify WinRM, the privileged account, script variable expansion and the group membership. Then sign out/in to refresh the token. If check-in was skipped or failed, the user may remain in the privileged group even after the secret is returned.

Safe design and recovery

Test checkout and check-in scripts on a non-production Windows host first. Use symmetric add/remove scripts, record the target group and member identity, and create monitoring for secrets that remain checked out longer than expected. A recovery job should compare actual group membership with FortiPAM checkout state and remove orphaned temporary membership through an approved administrative process. Never assume the script's failure warning is harmless. The secret can be available while the target's privilege state is wrong.

Operational exercise

A technician checks out an RDP secret and sees no elevated rights. The secret status says Checked Out. Check the WinRM service and FortiPAM activity log; then query local Administrators membership. If the user was added, sign out/in to refresh the token. If the script failed, fix the target credential or PowerShell command. After work, check in, verify the membership was removed, and force a new logon so the elevated token is discarded.

LESSON 10 · FortiSIEM 7.3.5 EventDB HA architecture / current 7.5.x scenario

FortiSIEM — FortiSIEM Supervisor HA PostgreSQL CMDB replication and Patroni timeline divergence

612 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose: separate the replicated state stores

FortiSIEM Supervisor HA replicates more than one kind of state. The CMDB resides in PostgreSQL and is protected by Patroni-based database HA. Device configuration files and profile data use separate replication mechanisms, and EventDB data on local disk is replicated using rsync in the EventDB architecture. Do not diagnose all stale data as “the database.” A Supervisor can have a healthy process state while its PostgreSQL CMDB replica is no longer streaming, and the EventDB path can be healthy independently.

Fortinet's HA architecture uses etcd for automated leader election and Patroni for PostgreSQL high availability. In an on-premises cluster, internal modules use a virtual IP owned by the DB leader; in AWS, a DNS name points to the current DB leader. The leader accepts PostgreSQL writes and streams WAL to followers. A minimum of three nodes is required for automated leader election. The architecture also elects a replication leader for file/profile state, which is not the same role as the PostgreSQL DB leader.

Timeline divergence

PostgreSQL WAL streaming is tied to a timeline. When a primary fails and a new leader is elected, the database history advances. A replica that cannot follow the new timeline may remain powered on and its PostgreSQL process may still run, but it no longer applies the current leader's WAL. The local CMDB then becomes stale. This can appear as missing or outdated devices, collectors or other inventory records on one Supervisor even when a high-level health widget says replication is Normal.

The critical distinction is between process state and replication state. A running PostgreSQL service proves the process exists. A replica role proves it is not the leader. Neither proves that it is streaming current WAL from the elected leader. The authoritative evidence is Patroni state, timeline, lag and PostgreSQL replication views.

Evidence sequence

patronictl list
patronictl history
psql -c "select * from pg_stat_replication;"
psql -c "select pg_is_in_recovery();"

patronictl list shows role, state, timeline (TL) and lag. patronictl history shows leader changes and timeline history. pg_stat_replication on the leader shows whether a replica is connected and streaming. pg_is_in_recovery() returns true on a standby. Compare CMDB device counts such as ph_device across nodes and use the documented FortiSIEM version script to verify software version consistency. If the GUI says replication is Normal but the replica has no streaming row or a stale timeline, trust the database evidence over the generic widget.

Safe recovery

First identify a healthy current leader and at least one replica that is streaming with zero lag. Only then reinitialize the affected replica from the healthy leader using the documented Patroni procedure. Never reinitialize the leader. Reinitialization discards the divergent replica's local database copy and rebuilds it from the authoritative leader, so choosing the wrong node can destroy the only good copy. Monitor until the replica rejoins on the current timeline, shows streaming state and lag returns to zero. Then restart the relevant FortiSIEM services if the version-specific procedure requires it and confirm CMDB parity.

If reinitialization fails, stop repeating it and collect Patroni, PostgreSQL and FortiSIEM service logs. Confirm the node identity, cluster membership and current leader before taking further action. Do not copy database files manually between nodes or confuse the PostgreSQL CMDB procedure with EventDB rsync recovery.

Operational exercise

After a Supervisor failover, one node displays devices that were deleted elsewhere. The health widget says Normal. Compare patronictl list and pg_stat_replication; a running but non-streaming replica on an old timeline explains the stale CMDB. Confirm the leader and a healthy streaming peer, reinitialize only the divergent node, and verify the device count converges. This is a replication-state problem, not an event ingestion or rule-processing problem.

LESSON 11 · FortiSASE 25.3.148 / 26.1.x

FortiSASE — FortiSASE regional compliance, DNS geolocation and ordered tunnel failover

674 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose: enforce where a remote user may connect

Regional compliance rules override the default behavior in which FortiClient connects to the closest FortiSASE security PoP. They let an organization constrain users from selected source countries/regions to a defined list of on-premise gateways or FortiSASE PoPs, in a chosen priority order. This is a routing and connection-selection control, not merely a firewall rule that filters traffic after the tunnel is up.

Location decision and rule selection

FortiSASE first determines the remote user's country or region from the public-IP and DNS location context used for the connection. It then applies the Regional access to FortiSASE allow/deny gate. Only if that gate permits the source does it select a Regional compliance rule whose source countries/regions match. The rule contains a Permitted connections & priority list. FortiClient attempts the listed on-premise device or security PoP connections from top to bottom, moving to the next entry when a connection fails.

This makes the recursive DNS resolver operationally important. The endpoint's local interface address is not the same as the public egress IP of the recursive resolver. A remote user in the Philippines may use a DNS resolver in Indonesia; the turbo FQDN can then resolve to a Jakarta PoP even though the user is physically elsewhere. The Community troubleshooting example demonstrates this exact failure. Use nslookup on the FortiSASE turbo FQDN, then nslookup whoami.akamai.com to identify the resolver's egress location. A TXT lookup such as nslookup -type=txt o-o.myaddr.l.google.com can reveal whether EDNS Client Subnet is being supplied.

Configuration sequence

Create Geography hosts under the host/resource area first. Configure Regional access to FortiSASE with Allow all, Allow specified or Deny specified. Then create Regional compliance rules, select source countries/regions, add on-premise devices or security PoPs, and order the permitted connections. An on-premise device is not managed by FortiSASE; its gateway must be reachable and configured for the supported remote-user tunnel type. For IPsec regional compliance, the required pre-shared key must match the FortiSASE Cloud Security tunnel and the on-prem FortiGate gateway. The feature requires an Advanced or Comprehensive remote-user subscription.

Health checks and failover timing

FortiSASE continuously checks on-prem gateway availability with ICMP/ping probes approximately every one to two minutes. If the gateway stops responding, FortiSASE updates the DNS record used by endpoints to direct subsequent connection attempts to the next available connection. The turbo A record has a 300-second TTL. Failure detection can take one to three minutes and DNS cache expiry adds up to five minutes, so the documented end-to-end failover is typically about three to eight minutes. Allow ICMP from the FortiSASE health-check source; otherwise a healthy gateway can be marked unavailable.

A matched Regional compliance rule does not automatically fall back to the geographically closest PoP. The endpoint tries only the connections explicitly listed in that rule. If a backup PoP is required, add it to the priority list. If no regional rule matches, the default closest-PoP behavior applies.

Evidence and troubleshooting

Check the configuration state of the rule, but do not stop there. Resolve the turbo FQDN from the affected endpoint and record the answer. Identify the recursive resolver with the whoami lookup and inspect EDNS Client Subnet. Compare that resolver location with the expected user country. Then check the Regional access gate, rule source list and priority order. For on-prem failover, verify ICMP reachability and account for the 300-second DNS TTL. A portal state of Success proves the configuration was applied; it does not prove the user's resolver provides the expected location signal.

Operational exercise

A user in Manila connects to Jakarta even though the rule lists Singapore first and Tokyo second. The tunnel rule is not necessarily wrong. The DNS resolver may be in Indonesia, causing the location decision to use the resolver's egress. Move the user to an in-country resolver with EDNS support, retest the turbo FQDN, and verify the resulting PoP. Only after the location signal is correct should you troubleshoot the ordered connection list or gateway health checks.

LESSON 12 · FortiOS 8.0.0

Secure SD-WAN — FortiOS 8.0 scheduled SD-WAN speed tests and interface bandwidth bounds

595 focused words

Open standalone SVG · Edit diagram in draw.io

Purpose and distinction from Performance SLA

A Performance SLA is a recurring health measurement used by SD-WAN to decide whether a member meets latency, jitter, loss or other service-level criteria. A speed test is a bandwidth measurement coordinated between FortiGate and backend infrastructure. The two can influence WAN operations, but they are not the same transaction. A speed test measures available throughput at a point in time; an SLA probe continuously tests service quality and can influence steering decisions. Do not treat a completed speed test as proof that the member is healthy for a latency-sensitive application.

FortiOS 8.0 scheduling changes

FortiOS 8.0 changes how scheduled speed tests are coordinated. The explicit retry and retry-pause controls used by earlier configurations are removed; retry timing is coordinated by the FortiGate/backend interaction. The speed-test schedule is configured per interface, and the measured result can be constrained by minimum and maximum inbandwidth/outbandwidth values. The result-related configuration has moved to the interface configuration rather than remaining in the older location. After upgrade, inspect the generated configuration and the current CLI reference instead of copying an old retry stanza.

Another important boundary is traffic shaping. Speed-test traffic is not governed by the interface traffic shaper in the same way as ordinary application traffic. The test is intended to measure the path, not to be throttled by the policy it is measuring. The update-inbandwidth and update-outbandwidth minimum/maximum values shape the result that is applied to interface bandwidth settings; they are bounds on the reported value, not proof of raw capacity.

Measurement transaction

The interface schedule tells FortiGate when to run the test. FortiGate and backend coordinate the test timing and retry behavior. The measurement produces a bandwidth result, then the configured minimum/maximum bounds constrain the value used by the interface. The interface configuration consumes the updated bandwidth result for traffic-management behavior. A result that is clamped at the minimum may make a slow link appear to have the configured floor; a result clamped at the maximum may hide a higher measured rate. Preserve both the raw test evidence and the applied interface value when diagnosing a mismatch.

Configuration review

On a FortiOS 8.0 upgrade, inspect show system speed-test-schedule and the interface's bandwidth/shaping configuration. Compare the current syntax with the FortiOS 8.0 SD-WAN New Features Guide and CLI reference. Remove assumptions about explicit retry counts or retry pauses; configure the per-interface schedule and the update-inbandwidth/outbandwidth bounds deliberately. The exact field names and available options depend on the build, so use the target build's CLI reference rather than pasting a generic snippet from an older version.

Evidence and troubleshooting

Confirm the schedule is attached to the intended interface, the backend is reachable, and the test completed. Compare the raw measurement with the bounded result and the interface's current bandwidth settings. If a test succeeds but application traffic still performs poorly, inspect ordinary traffic shaping, SD-WAN rule selection, Performance SLA state, route selection and upstream congestion separately. If the speed-test packets themselves appear rate-limited, verify that you are not confusing the test's measurement path with the normal interface shaper.

Operational exercise

After upgrading to FortiOS 8.0, a WAN interface reports the minimum configured bandwidth every morning. The old configuration still contains retry/retry-pause assumptions and the interface result settings were not migrated to the new location. Inspect the schedule and interface fields, verify backend coordination, and compare raw versus bounded results. Then validate application traffic with a separate test so that the speed-test result is not mistaken for a guarantee of user throughput.
