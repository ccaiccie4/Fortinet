FortiGate · LESSON 01

Preferred outbound BGP route maps: advertise differently when an SD-WAN peer is preferred

Standalone SVG · Editable draw.io

Purpose. A FortiGate can use BGP advertisements to influence traffic arriving from upstream networks, while SD-WAN rules decide how locally originated traffic leaves. Those are different control points. The preferred outbound route-map feature lets the FortiGate advertise one policy when a BGP peer is in its preferred state and a second policy when it is not. This is useful when two provider links remain Established but only one currently satisfies the desired SD-WAN health criteria.

Mechanics. A BGP neighbor can have a normal IPv4 outbound filter (route-map-out) and a preferred-peer filter (route-map-out-preferable). IPv6 has corresponding route-map-out6 and route-map-out6-preferable controls. FortiOS uses the preferred form when the peer is preferred; otherwise it uses the normal outbound form. The route map is evaluated against the route being advertised, not against an individual user packet. Route-map rules are evaluated in ascending rule-ID order; each rule has permit/deny action and match/set conditions. A rule can match a prefix or BGP community and set a community or AS-path attribute. A permit decision allows the route through the map; a deny decision suppresses it.

Configuration pattern. Build two route maps with deliberately different outcomes, then attach both to the same neighbor. The following is a pattern, not a complete production policy; prefix lists, community lists, and route-map rules must match the prefixes and attributes in the actual routing design.

config router route-map
    edit "OUT-NORMAL"
        config rule
            edit 10
                set action permit
                set match-ip-address "BRANCH-PREFIXES"
                set set-community "65000:200"
            next
        end
    next
    edit "OUT-PREFERRED"
        config rule
            edit 10
                set action permit
                set match-ip-address "BRANCH-PREFIXES"
                set set-community "65000:100"
            next
        end
    next
end
config router bgp
    config neighbor
        edit "198.51.100.1"
            set remote-as 65001
            set route-map-out "OUT-NORMAL"
            set route-map-out-preferable "OUT-PREFERRED"
        next
    end
end

The 8.0 New Features Guide adds GUI support for the preferred IPv4 and IPv6 route-map fields that were previously CLI-only. The GUI path is Network > BGP, then create or edit a neighbor/neighbor group, enable the relevant address family, and select the preferred outbound route map. The preferred state itself depends on the SD-WAN neighbor/role/health-check association; simply attaching a route map does not create SLA awareness.

Evidence and interpretation. Compare the SD-WAN health-check state and neighbor role with the BGP advertised routes. The neighbor can remain Established while the selected route map changes. Inspect the advertised prefix and its community/AS-path on the peer, not just the local RIB. A successful ping to the peer proves reachability, not that the intended route map was selected. Likewise, an Established BGP session proves TCP/BGP adjacency, not that the peer is considered preferred by SD-WAN.

Failure isolation. If the failover community is still advertised while the primary SLA is healthy, verify that the BGP neighbor is also represented in the SD-WAN neighbor configuration, that the correct member and primary/secondary role are assigned, and that the configured health-check and SLA ID are the ones actually changing state. Then check rule IDs and match conditions in both route maps. Keep IPv4 and IPv6 policy separate: an IPv4 preferred map does not automatically control IPv6 advertisements. Use a controlled route refresh or soft clear after policy changes, and verify the result at the receiving peer.

Operational boundary. This feature changes outbound BGP advertisement policy. It does not itself move local user traffic to another WAN member. SD-WAN service rules perform local forwarding selection. Fortinet Community's recent BGP connection steering tip describes the separate use-sdwan control for locally generated BGP TCP sessions; do not confuse that control-plane path choice with route-map selection for advertised NLRI.

Evidence checklist

  • SD-WAN health-check and neighbor role state
  • BGP neighbor route-map attachments for IPv4 and IPv6
  • Advertised prefixes and communities on the receiving peer
  • Rule IDs and match/set results in both route maps

Boundary/caveat: A route map controls BGP advertisements, not local packet forwarding. Preferred-state selection depends on the SD-WAN neighbor/health-check relationship. The GUI addition in FortiOS 8.0 exposes existing CLI behavior; it is not a new routing protocol.

FortiManager · LESSON 02

Global policy packages: header/footer insertion, ADOM assignment, and database consistency

Standalone SVG · Editable draw.io

Purpose and object model. Global policy packages let a provider or large enterprise enforce common firewall policy around customer- or business-unit-specific rules. A global header policy is evaluated before the local ADOM policy block; a global footer policy follows it. This creates a shared guardrail layer without copying the same rules into every ADOM. Global policies and objects live in the Global Database ADOM, but they are not active on managed FortiGates merely because they exist there: they must be assigned to the target ADOM and then installed to devices.

Assignment semantics. The Global Database package can be assigned to all policy packages in an ADOM, all except an exclusion list, or only an inclusion list. Each local policy package can have one global policy package assigned, while an ADOM can use multiple global packages. During assignment, FortiManager can include only used global objects or all global objects, and can automatically install policies to ADOM devices. Metadata variables can either be resolved at assignment time or left as-is so that matching local metadata variables resolve them inside the destination ADOM. Only ADOMs with the same version as the Global Database or the next higher major release are offered for assignment.

Workflow. Create the global package in the Global Database ADOM, populate Firewall Header Policy and Firewall Footer Policy, define which ADOMs and local packages receive it, then perform the Assign action. Review the resulting local package before installation. Assignment synchronizes the policy model; installation pushes the compiled policy to managed FortiGates. Treat those as separate transactions. A package that is assigned but not installed may show in FortiManager while the device still runs the prior policy.

Verification. In the destination ADOM, inspect the package's header/local/footer ordering and the assignment status. Check whether global objects were imported or resolved and whether metadata variables remain unresolved intentionally. Use the install preview to confirm that the device-facing policy contains the expected order and objects. A successful assignment status does not prove that the target FortiGate has received the change; device installation status and the device's installed policy are separate evidence.

Failure scenario. Fortinet Community documents a case where assignment appeared successful but header/footer policies were absent in the ADOM, sometimes with a pre-commit database error. The cause was stale configuration-database metadata after a Global Database package had been cloned and renamed, after an upgrade, or when the target ADOM had never received those policies. The targeted diagnostic is diagnose cdb upgrade check invalid-global-assignment. The output identifies invalid assignment entries; the documented example reports affected package object IDs and the number of errors fixed.

diagnose cdb upgrade check invalid-global-assignment
diagnose cdb upgrade check +all

Back up FortiManager before running database repair checks. After the targeted check, reassign the package and verify the header/footer sections in the ADOM. Use the broader +all check only when the targeted repair does not resolve the inconsistency and under an approved maintenance procedure. If the package remains inconsistent, create a fresh global package rather than repeatedly cloning the suspect object. Do not delete database rows manually.

Operational caveats. Re-importing a managed FortiGate configuration does not reconstruct global header/footer policy objects from the device; FortiManager explicitly reports that global policies cannot be retrieved from a managed device. Unassigning a global package removes its global configuration from the local ADOM, but a device install is still needed to remove the policy from the FortiGate. Keep the source of truth in the Global Database and validate the assignment/install boundary after upgrades.

Evidence checklist

  • Global package assignment scope and status
  • Header/local/footer ordering in the destination ADOM
  • `diagnose cdb upgrade check invalid-global-assignment` output
  • Install preview and device installation status

Boundary/caveat: Global policies are not imported back from managed FortiGate configs. Assignment and device installation are separate. ADOM version compatibility constrains assignment; preserve backups before CDB repair.

FortiAnalyzer · LESSON 03

Alert Explorer: filter semantics, alert provenance, and the triggering-log evidence chain

Standalone SVG · Editable draw.io

Purpose. Alert Explorer is an investigation surface, not a replacement for the underlying logs or alert handler. It helps an analyst reduce a large alert set to a time/device/entity slice, inspect related alerts, and pivot to the logs and rule that produced an alert. FortiAnalyzer 8.0 changes the layout to give more room to quick filters and related alerts; the timeline is disabled by default, and a Details action exposes the alert, handler, logs, and rules.

Filter mechanics. Start with device and time period. Quick filters expose alert type/name, host, source, target, and user. Available values depend on the current device, time range, and filters already applied. Selecting multiple values applies an AND relationship. That means choosing two source values does not broaden the result into an OR set; it narrows the result to records satisfying both selections. The record count shown above a filter is therefore an important diagnostic observable. If the count collapses to zero, remove one filter at a time rather than assuming ingestion stopped.

Related-alert and detail flow. The related-alert table includes severity, last occurrence, alert subject, endpoint, source, target, user, alert type/status, device name, triggering rule, and alert handler. The source and target fields are derived from the group-by fields in the alert handler. They are not necessarily a packet's literal source and destination addresses. For example, a handler grouped by source user and target host may display an identity-to-asset relationship rather than an IP five-tuple. Inspect the handler definition before using those fields as network direction evidence.

Open Details from the Actions menu or double-click the alert. The details pane includes formatted alert details (with a raw JSON view), triggering logs, and a timeline for related alerts/entities. The new 8.0 Details action is useful because it connects the alert row to its originating handler and rule. The Search in Log View action opens Log View filtered to the logs associated with that alert. You can create a new incident, attach the alert to an existing incident, or suppress identical/similar alerts from the related-alert table.

Investigation sequence. Select a device and a time range broad enough to include the first and last occurrence. Use one or two high-value filters first; confirm the count changes as expected. Open Details, inspect the raw JSON when formatted fields look incomplete, and compare the triggering logs with the handler's group-by and match criteria. Use the Timeline tab to establish ordering and entity involvement. Only after the evidence chain is coherent should you create or attach an incident or suppress repeated noise.

What evidence proves. A related-alert row proves that an alert object exists in the selected scope. Triggering Logs show a sample of the records that caused it; they do not necessarily show every contributing log. The rule and handler fields identify the logic that fired, but do not prove that the underlying event represents malicious intent. A blank timeline may simply mean the timeline view is disabled; in FortiAnalyzer 8.0 it is disabled by default and can be enabled from View Options.

Troubleshooting. If an alert is known but absent from Explorer, widen the time period, verify the selected device, clear AND-composed filters, and refresh. If the row exists but the analyst cannot explain Source/Target, inspect the handler's group-by fields. If Details shows an alert but no expected logs, pivot to Log View and confirm the time/device scope and log ingestion path. Keep alert suppression narrowly scoped: suppressing an alert family can hide future events that share the same criteria.

Evidence checklist

  • Device and time-period scope
  • Quick-filter value counts and AND behavior
  • Alert Details raw JSON, Triggering Logs, Timeline
  • Rule and Alert Handler fields plus handler group-by settings

Boundary/caveat: Timeline is disabled by default in 8.0. Source/Target semantics are defined by alert-handler group-by fields. Triggering Logs are samples, not proof that all relevant logs were retained.

FortiSwitch · LESSON 04

VXLAN interfaces: VNI-to-VLAN mapping, VTEP reachability, and underlay constraints

Standalone SVG · Editable draw.io

Purpose. VXLAN carries Layer-2 frames between FortiSwitch virtual tunnel endpoints (VTEPs) across a Layer-3 IP network. It allows a VLAN segment to span routed infrastructure without extending the original Ethernet broadcast domain across every physical link. The 24-bit VXLAN Network Identifier (VNI) identifies the overlay segment; the local VLAN ID maps that VNI to the access-side VLAN on the switch.

Object model and packet path. A FortiSwitch VXLAN interface is configured under config system vxlan. It binds a VNI (1–16,777,215), a VLAN ID (1–4094), an outgoing underlay interface, an IP mode (IPv4 unicast or multicast), and one or more remote IP addresses. When a frame arrives on the mapped VLAN, the local VTEP encapsulates it in VXLAN over UDP and sends it toward the remote VTEP. The remote switch decapsulates the packet and presents the inner frame on the VLAN mapped to the same VNI. FortiSwitch learns remote MAC addresses by flooding broadcast, unicast, and multicast traffic to configured remote IPs; this learning behavior is separate from whether the local VXLAN interface object exists.

Configuration pattern. The tunnel destination UDP port defaults to 4789 and can be changed globally. The following illustrates a unicast pair; use matching VNI/VLAN mapping and reciprocal remote addresses on the peer.

config switch global
    set vxlan-dport 4789
end
config system vxlan
    edit "vni-50"
        set vni 50
        set vlanid 50
        set interface "vlan40"
        set ip-version ipv4-unicast
        set remote-ip 192.0.2.2
    next
end

The documented syntax also supports an RVI as the outgoing interface on supported FortiSwitchOS releases. The remote destination must match the peer's configured remote-ip. The underlay IP used by the tunnel must be a configured static primary address; a DHCP-mode underlay is unreliable, and a static interface with no actual primary IP does not create a tunnel.

Underlay and feature boundaries. The VXLAN access VLAN's SVI routing functions are not supported. PIM and IGMP snooping are not supported in the VXLAN underlay network. IGMP snooping can be used on supported VXLAN access VLANs beginning with FortiSwitchOS 7.6.0, but multicast-source placement matters: to deliver multicast to all remote VTEPs, the source and IGMP querier must be on the same VTEP for that access VLAN. Feature availability is model-dependent. Do not assume that a capability supported on an access VLAN is also supported in the routed underlay.

Verification. Use get system interface vxlan to confirm the configured interface, and diagnose switch vxlan mac-address list <name> to inspect learned remote MAC entries. A configured VNI with no learned remote MACs points toward remote reachability, flooding, or peer-address mismatch; it does not prove the VLAN mapping is correct. Capture UDP on the underlay and confirm the destination port, VTEP IP, and VNI. Verify the underlay route and source address on both switches.

Troubleshooting. If the tunnel does not form, check the static primary IP, interface mode, remote-ip symmetry, and routing first. If the tunnel exists but traffic does not cross, compare the VNI and VLAN mapping on both peers and verify the local access VLAN membership. If an existing FortiLink-managed VLAN cannot be attached to another interface, inspect its dependencies before deleting or recreating it; the older Community case shows that pre-existing VLAN references can constrain reassignment. Do not treat that historical behavior as a current defect without reproducing it on the deployed FortiSwitchOS version.

Evidence checklist

  • `get system interface vxlan` configuration
  • `diagnose switch vxlan mac-address list <name>` remote MAC learning
  • Underlay route, primary static IP and UDP VXLAN capture
  • Peer VNI/VLAN mapping and access VLAN membership

Boundary/caveat: VNI and VLAN IDs are different namespaces. Underlay DHCP is unreliable; PIM/IGMP snooping are not supported in the VXLAN underlay. Access-VLAN IGMP support is model/release dependent.

FortiAP/Wireless · LESSON 05

UNII-4 5GHz channels on FortiAP G-series: platform mode and radio-resource trade-offs

Standalone SVG · Editable draw.io

Purpose. UNII-4 extends the 5 GHz channel choices on supported FortiAP G-series hardware with channels 169, 173, and 177 in the 5.85–5.925 GHz band. This is not a universal channel toggle. Availability depends on the AP model, country/regulatory domain, platform mode, and Dedicated Scan behavior. The channel plan also has a radio-resource cost: enabling UNII-4 disables UNII-5 and UNII-6 channels on Radio 3.

Platform behavior. UNII-4 is unavailable in Dual 5G platform mode. On G-series APs operating in Single 5G mode with Dedicated Scan enabled, UNII-4 channels are available by default; Radio 3 does not operate in AP mode and Radio 2 can use the UNII-4 channels. When Dedicated Scan is disabled, the profile exposes an explicit enable/disable control for UNII-4. The administrator must choose whether the added channel set is worth the corresponding Radio 3 channel loss.

GUI workflow. In the FortiGate GUI, go to WiFi & Switch Controller > FortiAP Profiles. Create or edit the supported FAP-43xG profile, set Platform mode to Single 5G, and—when Dedicated Scan is disabled—enable UNII-4 5GHz band channels. Then open Radio 2, select Set Channels, and choose 169, 173, or 177. The channel list is regulatory-domain dependent; a channel not displayed may be prohibited for the configured country rather than missing because of a software defect.

config wireless-controller wtp-profile
    edit "FAP_G"
        config platform
            set 431G
        end
        set unii-4-5ghz-band enable
        config radio-2
            set channel 169 173 177
        end
    next
end

The CLI example is for the supported G-series profile context described in the guide. Confirm the exact model/profile syntax for the deployed FortiOS/FortiAP combination before applying it. When enabling the feature with Dedicated Scan disabled, FortiOS warns that Radio 3's UNII-5 and UNII-6 channel lists will be unavailable and asks for confirmation.

Verification and interpretation. Inspect the FortiAP profile's platform mode, Dedicated Scan setting, UNII-4 toggle, and Radio 2 channel list. Then verify the AP has received the intended profile and that the operational radio is using the selected channel. A profile showing UNII-4 enabled proves the controller configuration; it does not prove the AP is in the intended country code, has accepted the profile, or is actually transmitting on that channel. Check the AP's operational radio state and client association behavior after the change.

Failure isolation. If 169/173/177 are absent, first verify model and country. Next check that the AP is in Single 5G mode; Dual 5G mode suppresses UNII-4. If Dedicated Scan is enabled, the channels should be available by default; if disabled, explicitly enable the UNII-4 option. If Radio 3 loses expected channels after the change, that is the documented trade-off, not necessarily a regression. Plan channel reuse and coverage around the radio allocation before pushing a profile to a large AP group.

Operational design. Treat the UNII-4 decision as a radio-profile design change, not merely a per-channel adjustment. Validate regulatory requirements, RF planning, channel width, neighboring AP use, and the Radio 3 capability loss in a pilot area before expanding the profile.

Evidence checklist

  • FortiAP model and country/regulatory domain
  • Profile platform mode and Dedicated Scan state
  • UNII-4 toggle and Radio 2 channel list
  • Operational radio channel and client association after profile sync

Boundary/caveat: UNII-4 is not available in Dual 5G mode and is country restricted. Enabling it removes UNII-5/6 channels from Radio 3.

FortiNAC · LESSON 06

Admin GUI HSTS default: browser HTTPS enforcement and certificate dependencies

Standalone SVG · Editable draw.io

Purpose. FortiNAC enables HTTP Strict Transport Security (HSTS) for the Admin GUI by default in releases 9.4.5 and later, 7.2.4 and later, and 7.4.0 and later. HSTS is a browser-enforced policy delivered in the HTTPS response header Strict-Transport-Security. It tells a compliant browser to use HTTPS for the host for the advertised max-age. The control reduces downgrade opportunities in which an administrator follows an HTTP link or bookmark and is exposed to an insecure connection before reaching the management interface.

Transaction flow. The browser first reaches the canonical Admin GUI hostname over TLS. After the HTTPS response contains the HSTS header, the browser caches the policy for that host. On later navigation, a request entered as HTTP is internally upgraded to HTTPS or refused if a secure connection cannot be established. HSTS is learned from a secure response; it is not a substitute for a valid TLS certificate. A certificate with a hostname mismatch, expired validity, untrusted issuer, or broken reverse-proxy termination can therefore make the GUI appear unreachable after the browser has cached HSTS.

Operational implications. Use a stable management FQDN and a certificate whose subject alternative names cover that name. Ensure the HTTPS listener and any reverse proxy or load balancer preserve the intended certificate and security headers. Update bookmarks and operational runbooks to use the canonical HTTPS URL. If an administrator reaches the GUI through a raw IP address while the certificate is issued to a DNS name, the browser may reject the certificate even though the service is listening. The HSTS policy makes that certificate hygiene more visible because the browser will not quietly fall back to HTTP.

Verification. Inspect the HTTPS response headers and certificate chain from an administrative workstation:

curl -vkI https://nac.example.net/
curl -I  https://nac.example.net/

The verbose request is useful for diagnosis, but the normal trust-verifying request is the meaningful success test. Confirm the Strict-Transport-Security header, certificate SAN, issuer, validity dates, and TLS termination point. A response header proves that the server or proxy sent the policy; it does not prove that every browser has cached it or that every administrator is using the same hostname.

Failure isolation. If an HTTP bookmark stops working after an upgrade, try the canonical HTTPS hostname and inspect the certificate before assuming the FortiNAC authentication service failed. If HTTPS works only after bypassing a certificate warning, fix the certificate chain or name; do not train administrators to click through warnings. If a reverse proxy is in front of the GUI, verify that it does not strip or rewrite the HSTS header and that it redirects to the same canonical hostname. Avoid clearing browser HSTS state as the first response: that can hide a certificate defect without correcting it.

Version boundary. The default behavior is version-specific. Confirm the exact FortiNAC software train and patch level before comparing two appliances. HSTS behavior on the Admin GUI does not imply that every portal, agent, API, or other service endpoint has identical headers or certificate configuration.

Evidence checklist

  • FortiNAC version and patch level
  • HTTPS response header and certificate SAN/chain
  • Browser network trace and canonical hostname
  • Reverse-proxy TLS termination and header preservation

Boundary/caveat: HSTS is a browser policy learned over HTTPS; it does not repair certificates or prove that all FortiNAC services use the same TLS endpoint.

FortiNAC-F · LESSON 07

EAP-TLS ECDSA P-384 compatibility: identify the CertificateVerify failure boundary

Standalone SVG · Editable draw.io

Purpose. EAP-TLS authentication depends on more than whether the issuing CA is trusted. The RADIUS server must also support the cryptographic algorithms and elliptic-curve parameters used by the client's certificate and signature. A migration from CentOS-based FortiNAC to NacOS can expose a server-side supported-curve boundary: RSA clients may authenticate while ECDSA P-384 clients fail at a specific TLS handshake phase.

Transaction flow. The supplicant and access switch exchange EAPOL; the switch relays the EAP conversation in RADIUS Access-Request messages to FortiNAC-F. The local RADIUS service acts as the EAP-TLS endpoint. The TLS handshake negotiates protocol and cipher parameters, the server receives and validates the client certificate chain, and the client proves possession of the private key in the CertificateVerify message. Only after the EAP method completes and the policy evaluation succeeds does the RADIUS server return Access-Accept with the authorization result, such as a VLAN or other network-access attributes.

Failure boundary. In the documented Community case, the same appliance, client, and switch port accepted an RSA-2048 client certificate but rejected an ECDSA P-384 certificate. The trace reached CertificateVerify, then the server sent a fatal illegal_parameter alert and logged an OpenSSL wrong curve error. Both issuing CAs were already present in the RADIUS Endpoint Trust. Reaching CertificateVerify demonstrates that the handshake progressed through earlier negotiation and certificate-chain processing; the failure was the server's supported-curve restriction when validating the client's signature. It was not evidence of a bad shared secret, VLAN assignment, switch port, or untrusted CA.

eap_tls: (TLS) recv TLS 1.2 Handshake, CertificateVerify
eap_tls: (TLS) send TLS 1.2 Alert, fatal illegal_parameter
eap_tls: ERROR: SSL routines::wrong curve
eap_tls: ERROR: EAP Receive handshake failed during operation.

Configuration prerequisites. FortiNAC-F local RADIUS requires a server certificate for EAP authentication. Confirm the intended local RADIUS virtual server is enabled, the EAP method is selected, and the correct trust anchors are present. The local RADIUS service view exposes service status, service logs, server logs, system journal, and Network Access records. These views are useful for separating service-start failures, TLS handshake failures, and post-authentication authorization problems.

Remediation. Fortinet's Community troubleshooting article states that FortiNAC firmware 7.6.5 GA and later supports ECDSA P-384 client certificates. If the deployed NacOS build predates that support, plan an upgrade to a fixed release. Take system and database backups and a VM snapshot where applicable, review release notes and agent compatibility, and perform the change in a maintenance window. Do not re-import a CA that is already trusted or change the switch configuration when the evidence isolates the failure to CertificateVerify curve support.

Verification. Retest with the same client and port using both RSA and P-384 certificates. Confirm the handshake proceeds beyond CertificateVerify, the RADIUS result is Access-Accept, and the expected VLAN/authorization attributes are returned. If the error changes to unknown CA or revoked certificate, that is a different failure class and should be investigated separately. This lesson is specifically about supported-curve compatibility; it is not the OCSP-only certificate-revocation behavior covered in the earlier FortiNAC-F lesson.

Evidence checklist

  • Local RADIUS service status and EAP certificate/trust configuration
  • RADIUS log phase: CertificateVerify and `wrong curve`
  • Same endpoint/port comparison using RSA-2048 and ECDSA P-384
  • Access-Accept and assigned VLAN after fixed-version upgrade

Boundary/caveat: The cited Community case is older than 30 days. 7.6.5 GA+ support is documented there and referenced to official release notes; verify the target build's release notes before upgrading.

FortiAuthenticator · LESSON 08

RADSec accounting: client-certificate trust and protected RADIUS session records

Standalone SVG · Editable draw.io

Purpose. RADSec transports RADIUS messages over TLS instead of relying on unprotected UDP transport. FortiAuthenticator 8.0 adds support for processing RADIUS accounting requests sent over RADSec and verifies that a RADSec client presents a certificate issued by a configured Local CA or Trusted CA during the TLS handshake. This matters when a deployment expects accounting Start, Interim-Update, and Stop records to traverse the same protected client/server relationship as authentication.

Two certificate roles. The RADSec Server Certificate is the certificate FortiAuthenticator presents to encrypt the TLS connection. The RADSec client must also present a valid client certificate signed by a CA configured under Certificate Management > Certificate Authorities. These roles are not interchangeable. A valid server certificate does not prove that the client is trusted, and a trusted client certificate does not prove that the client trusts the FAC server certificate. The TLS peers must also agree on a protocol and cipher suite.

Message flow. The client opens a TLS connection to the RADSec listener (default port 2083, configurable under Authentication > RADIUS Service > Services). The TLS handshake authenticates the server and validates the client certificate against the configured Local/Trusted CA stores. After TLS is established, the RADIUS daemon handles the decrypted authentication or accounting messages in the same way it handles standard RADIUS requests. FortiAuthenticator documents a maximum of 500 simultaneous RADSec clients. That is a connection-scale limit, not a per-second accounting throughput guarantee.

Configuration checklist. Select the RADSec Server Certificate, configure trusted issuing CAs, set the RADSec listener port, and align the allowed TLS protocols/ciphers with the client. On the client, install a client certificate whose chain reaches one of the configured CAs and configure the FAC hostname/port. For an accounting deployment, enable the client to send Start/Interim-Update/Stop records over the RADSec transport. Keep the accounting identity and NAS identifier stable so that session records can be correlated.

  RADSec Server Certificate: <server certificate>
  Local CAs / Trusted CAs: <client issuing CA>

Authentication > RADIUS Service > Services
  RADSec port: 2083 (default)

Evidence and interpretation. First verify the TLS connection and mutual certificate validation. Then verify that accounting records arrive and update the expected session state. A successful Access-Accept proves that an authentication request was processed; it does not prove that the client is sending accounting packets or that the RADSec accounting path is functioning. Conversely, a TLS handshake proves a secure channel but does not prove that the client is sending the expected accounting record types or that the NAS/session identifiers are consistent.

Troubleshooting. If authentication works but sessions are missing from accounting, isolate the accounting client configuration and message path before changing EAP or user policy. If TLS fails, check server certificate selection, client certificate issuer, expiration, trust-store placement, hostname validation, cipher/protocol overlap, listener port, and network ACLs. If only some clients fail, compare their issuing CA and TLS capabilities rather than changing the global RADIUS policy. Monitor concurrent connections against the documented 500-client ceiling and design reconnect behavior for client restarts or certificate rollover.

Evidence checklist

  • RADSec TLS handshake and peer certificate validation
  • RADSec Server Certificate selection and trusted CA stores
  • Received Accounting-Start/Interim-Update/Stop records
  • Concurrent RADSec client count and listener port

Boundary/caveat: Default port is 2083; documented maximum is 500 simultaneous RADSec clients. Authentication success alone does not prove accounting ingestion.

FortiPAM · LESSON 09

SCIM lifecycle management: Auto Provision Rules, SAML binding, and immediate access revocation

Standalone SVG · Editable draw.io

Purpose. SCIM gives FortiPAM a lifecycle feed for remote users and groups. Instead of waiting for a user to log in before updating their account, FortiPAM can receive provisioning, attribute, and group-membership changes from a SCIM client and apply authorization changes immediately. The feature integrates SCIM, SAML, and Auto Provision Rules (APL): SCIM maintains identity data, APL maps remote groups/attributes to FortiPAM roles and access profiles, and SAML authenticates the user.

Object relationships. Create a SCIM client under User Management > SCIM Service. The client represents the external provisioning source. Create APL rules for the remote user groups and the role/access profile each group should receive. When configuring the SAML SSO server, select the SCIM profile so SAML-authenticated identities are linked to the SCIM-synchronized user/group data. This link is important: a successful SAML assertion proves authentication, but does not by itself prove that the intended SCIM group mapping and FortiPAM access profile were applied.

Lifecycle flow. When a SCIM update creates a user that matches an APL, FortiPAM provisions the account. Group or attribute changes cause the rule match to be reevaluated; if the user matches a different rule, the role, policies, and permissions are updated. If the user no longer matches any APL, FortiPAM de-authenticates and purges the account and terminates active login sessions. If a change removes authorization to particular secrets, ongoing launch sessions associated with those secrets are terminated. SCIM remote groups can also be configured as approvers in secret approval workflows.

Operational design. Treat APL rules as authorization logic, not just a convenience for account creation. Define explicit group-to-role mappings and test the order/coverage of rules. A broad catch-all rule can keep a user provisioned when a privileged group is removed; an overly narrow rule can purge a user after a harmless attribute change. Map stable identity attributes and normalize group names before connecting the SCIM feed to production. FortiPAM can also synchronize supported attributes such as email address and display name.

Verification. Confirm that the SCIM client receives updates, the expected user and group records are present, the intended APL matches, and the resulting access profile is correct. For an authorization change, inspect active login sessions and secret launch sessions; the documented behavior is immediate reevaluation and termination when access is revoked. Do not infer that a SCIM update was fully enforced merely because the user object appears in the user list.

Failure isolation. If a user is authenticated by SAML but receives the wrong secret access, compare the SAML identity and selected SCIM profile, then inspect the synchronized group/attributes and APL result. If an account disappears after a group update, determine whether it no longer matches any APL before recreating it manually. If a user remains able to launch a secret after a group removal, inspect the SCIM update, remote group mapping, APL reevaluation, and launch-session state. Test join, group-change, and leave events with a pilot group before broad rollout.

Security implication. SCIM deprovisioning is an active enforcement event, not merely a directory cleanup. It can terminate sessions while an operator is connected to a target. Coordinate identity lifecycle changes with maintenance and incident procedures, and ensure emergency access accounts are intentionally modeled rather than accidentally excluded from provisioning rules.

Evidence checklist

  • SCIM client update status and synchronized group/attribute values
  • SAML SSO server's selected SCIM profile
  • Matched Auto Provision Rule and resulting access profile
  • Login-session and secret-launch-session termination after revocation

Boundary/caveat: No APL match can de-authenticate and purge the user. SCIM updates can terminate active sessions and secret launches; validate rule coverage before production.

FortiSIEM · LESSON 10

Device and User Risk Scoring: factor lineage, entity quality, and investigation prioritization

Standalone SVG · Editable draw.io

Purpose. FortiSIEM Device and User Risk Scoring helps an analyst prioritize entities by combining multiple evidence dimensions. The documented factors include asset criticality, user role and importance, incident severity, frequency of occurrence, and vulnerabilities found. The score is displayed in a dashboard with drill-down capabilities so the analyst can identify the underlying factors. It is a prioritization signal; it is not a deterministic verdict that an endpoint is compromised.

Mechanics and data lineage. Events and incidents must be associated with the correct user or device entity. Vulnerability findings and asset context contribute additional dimensions. Business criticality and user importance change the operational impact of an otherwise similar incident: repeated medium-severity events on a critical server may warrant more attention than an isolated event on a low-impact lab workstation. Frequency also matters because repeated activity can raise concern even when no single event is severe. FortiSIEM exposes the score and contributing factors, but the public guide does not publish a universal arithmetic formula or a single threshold that should be treated as a compromise boundary.

Investigation workflow. Start with the dashboard score, then drill into the contributing factors. Confirm the endpoint or user identity, inspect the incident list and severity, review recurrence over time, and examine vulnerability findings. Check that the CMDB/asset identity is correct and that the assigned asset criticality and user role reflect the actual business context. Use the underlying incidents and logs to understand the behavior before running mitigation scripts or isolating a device.

Evidence and interpretation. The score proves that FortiSIEM has calculated a composite prioritization value from the available factors. The drill-down explains which factors contributed. It does not prove that every source system reported complete data, that the asset identity is correct, or that the highest-scoring entity is necessarily the most urgent threat. Missing CMDB enrichment can understate the importance of an asset; incorrect user/device mapping can attach incidents to the wrong entity. A score can also change when vulnerability or incident context changes, even if no new endpoint activity occurs.

Operational troubleshooting. If a critical server receives a surprisingly low score, verify that the server is represented as the expected asset, its criticality is set correctly, vulnerability findings are associated with it, and incidents are mapped to the same identity. If a user score appears unexpectedly high, inspect user role/importance and repeated incident history. If two entities have similar scores, compare factor lineage rather than assuming the scoring engine is inconsistent. Validate the underlying time windows and source ingestion before tuning thresholds or suppressing alerts.

Using the score safely. Use risk scoring to order the investigation queue, select entities for deeper threat hunting, and communicate why one asset is being examined first. Keep the raw incident and vulnerability evidence attached to the decision. For containment, use the actual detection, response policy, and change-approval process. A high score without corroborating evidence should trigger investigation; a low score should never be used to dismiss a credible high-severity event.

Evidence checklist

  • Risk score displayed for the device/user
  • Drill-down of asset criticality, user importance, incident severity/frequency and vulnerabilities
  • CMDB entity association and source ingestion freshness
  • Underlying incident and vulnerability records

Boundary/caveat: The guide describes contributing factors and drill-down, not a universal formula or compromise threshold. A composite score is a prioritization aid, not proof of compromise.

FortiSASE · LESSON 11

FIDO2 passkeys for FortiClient agent tunnels: SAML prerequisites and OS-specific enforcement

Standalone SVG · Editable draw.io

Purpose. FortiSASE supports FIDO2 authentication for FortiClient agent tunnels. This adds passkey-based authentication to the SAML sign-in step used by the tunnel profile. It does not replace IPsec or SSL tunnel negotiation; it strengthens the user authentication step that occurs before the agent tunnel is established. The feature requires Entra ID to be configured for FIDO2 and the FortiClient profile to use SSO with the embedded browser.

Authentication flow. The endpoint receives an Endpoint Profile from FortiSASE. The profile enables Authenticate with SSO and Use FortiClient built-in browser for SAML authentication. When the user starts the agent tunnel, FortiClient opens the embedded browser and redirects to the configured SAML identity provider. Entra ID performs the FIDO2/passkey challenge and returns the SAML authentication result. FortiClient then continues with the configured IPsec or SSL tunnel parameters. The FIDO2 ceremony authenticates the user to the IdP; the tunnel's cryptographic negotiation and gateway configuration remain separate.

Profile prerequisites. In Advanced Settings, enable Allow FIDO authentication. This option is available only when Authenticate with SSO and Use FortiClient built-in browser for SAML are enabled. The Entra ID tenant must already have FIDO2 authentication configured. For custom IPsec tunnels, the SAML port defaults to 443 unless changed; for SSL tunnels, verify the remote gateway and port. Custom tunnel settings on FortiSASE must match the settings applied to FortiClient and the remote gateway or the authentication may succeed while the tunnel itself fails.

OS-specific behavior. The guide calls out an important asymmetry. The Allow FIDO authentication setting currently restricts this method for macOS endpoints. For Windows endpoints, enabling the FortiSASE setting is not sufficient by itself: FIDO2 must also be configured in the Entra ID Enterprise Application used for SAML SSO. Therefore, a profile that behaves differently on Windows and macOS may reflect the documented enforcement boundary rather than a FortiSASE policy-sync defect.

Verification. Inspect the endpoint profile flags, OS, FortiClient version, Entra enterprise application authentication methods, SAML sign-in logs, and tunnel negotiation logs. If the user never sees a FIDO prompt, check that SSO and the embedded browser are enabled and that Entra ID offers FIDO2 for the application. If SAML succeeds but the tunnel fails, stop troubleshooting FIDO and compare gateway FQDN/IP, port, certificate, IKE/SSL settings, and the FortiSASE/endpoint profile consistency.

Failure isolation. A missing FIDO option usually points to a profile prerequisite. A password prompt on Windows while macOS uses passkeys points to the additional Entra enterprise-application configuration. A successful FIDO sign-in followed by tunnel failure points to tunnel parameters or gateway reachability, not the FIDO ceremony. Test each supported OS separately and capture both the identity-provider result and FortiClient tunnel logs.

Change caution. The same Advanced Settings area also controls dead-peer detection for IPsec tunnels. Changing DPD settings can disconnect currently connected endpoints for a few minutes; schedule a maintenance window before changing those values. Do not bundle an authentication rollout and an unrelated DPD change into one uncontrolled production change.

Evidence checklist

  • Endpoint profile: Authenticate with SSO, embedded browser, Allow FIDO
  • Entra ID FIDO2 method and Enterprise Application settings
  • SAML sign-in result and FortiClient OS/version
  • IPsec/SSL tunnel negotiation after successful SAML authentication

Boundary/caveat: Windows requires FIDO2 in the Entra enterprise application as well as the FortiSASE setting. macOS and Windows enforcement behavior differs. DPD changes can briefly disconnect endpoints.

Secure SD-WAN · LESSON 12

ADVPN 2.0 Dynamic BGP on loopback: direct spoke route exchange and shortcut lifecycle

Standalone SVG · Editable draw.io

Purpose. Traditional BGP-per-overlay creates a BGP session for each tunnel endpoint. In a hub-and-spoke design, this can produce many iBGP sessions and routing-table updates on the hub. BGP on loopback gives each spoke a stable identity and a single iBGP session toward each hub, independent of the number of overlay tunnels. Dynamic BGP adds a direct BGP session between a pair of spokes over an ADVPN shortcut, allowing them to exchange routes without requiring the hub to re-advertise every spoke route through route reflection.

Architecture. The loopback address uniquely identifies each SD-WAN node. A spoke advertises its LAN prefixes to the hub over the loopback-based iBGP session. The hub learns the spoke routes, but with Dynamic BGP it does not need to reflect those routes to every other spoke. When traffic between two spokes triggers an ADVPN shortcut, the spokes can establish a BGP session directly over that shortcut. ADVPN 2.0 adds intelligence to shortcut selection: the shortcut is established over underlays available at both spokes and selected using link-health criteria. FortiManager's SD-WAN Overlay Template enables BGP on Loopback, Dynamic BGP, and ADVPN 2.0 by default in the documented wizard, but the generated templates must still be reviewed and installed.

Control and data flow. First, the spoke must be able to reach the hub and advertise its loopback/LAN routes. Traffic to a remote spoke then triggers shortcut discovery. Once the shortcut is negotiated, the direct dynamic BGP session exchanges route information between the spoke loopbacks. User traffic can move to the shortcut when the service and health criteria select it. These are separate state machines: the shortcut tunnel may be recreated or traffic may move to a healthier path before the BGP session migrates from the old shortcut.

Configuration principles. Use a stable loopback as the BGP update source and advertise it through the routing design. Ensure each spoke has the required route to reach the hub; the Fortinet Community VRF example shows that a default route in the PE VRF may not automatically provide reachability for another VRF that must trigger shortcut creation. The hub may need a VRF-specific summary/blackhole route or, in FortiOS 8.0, static routes with VRF specified directly. Assign each SD-WAN health check to the VRF that matches the intended routing path.

Operational trap. Do not use the remote BGP peer loopback as the health-check server. The documented Community scenario explains that a kernel route to the health-check server can persist even when the health check fails, causing BGP traffic to continue using the same tunnel. Use a separate health-check target. Another documented behavior is that user traffic can move to a new shortcut when the original shortcut is out of SLA while the dynamic BGP session remains on the initial shortcut until the old shortcut's idle-expire timer flushes it. That difference is not proof that user traffic is still pinned to the old path.

Verification. Inspect BGP neighbor state and uptime, the routing table's recursive next-hop path, the ADVPN shortcut list, and health-check state in each VRF. Compare the route used by the user flow with the tunnel carrying the BGP TCP session. A new shortcut proves that the data-plane shortcut was negotiated; it does not prove the dynamic BGP session moved. A BGP Established state proves a session exists, not that the expected LAN prefix is installed through the preferred shortcut.

Failure isolation. If a spoke never creates a shortcut, verify hub reachability, loopback advertisement, default route and VRF. If the shortcut exists but remote prefixes are missing, inspect dynamic BGP neighbor formation and route exchange. If traffic moves but the BGP session stays on the old shortcut, check the idle-expire behavior before clearing the session. If the session remains pinned despite SLA failure, verify the health-check target is not the BGP peer address and that the correct VRF and members are configured.

Evidence checklist

  • Loopback reachability and BGP neighbor state
  • RIB route detail with recursive tunnel next hop
  • ADVPN shortcut state and underlay SLA health
  • Per-VRF default/static route and health-check assignment

Boundary/caveat: BGP session lifecycle and shortcut/data-plane lifecycle are not identical. Use a separate health-check target from the BGP peer loopback; validate VRF reachability.
