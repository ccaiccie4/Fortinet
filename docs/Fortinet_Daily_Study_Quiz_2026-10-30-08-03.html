Lesson 01 · FortiGate

SNAT source-port preservation under collision: eligibility, allocation, and explicit mapping

522 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiOS New Features — Fine-tuning source port behavior for SNAT (7.4.4)
  • FortiOS 7.6.5 Administration Guide — Central SNAT

Scenario research

  • Community Technical Tip — SNAT source-port changes for IKE traffic (published about three weeks ago) (recent scenario context)

Purpose and packet mechanics

Source NAT changes the source address and may change the source port as a session crosses the FortiGate. The translated address/port pair must be unique enough for the device to reverse-map reply traffic to the originating session. Port preservation is therefore conditional, not an unconditional promise that the external tuple will equal the client tuple.

FortiOS 7.4.4 documents port-preserve for both firewall-policy NAT and central SNAT. When enabled, FortiGate tries to keep the original source port if that port is eligible and not already in use for the translated tuple. The preservation range is 5117–65533. A source port below that floor is translated by the SNAT allocator unless an explicit mapping is configured. If a preserved port collides with an existing session, FortiGate must choose another available port so two flows do not share an ambiguous reverse mapping.

Where the decision is made

With central NAT enabled, policy SNAT settings are not the active source-NAT rule base; the ordered central-snat-map is. Rules are evaluated top-down, and the first matching entry controls the source address/IP pool and port behavior. A protocol-specific rule can narrow matching, but do not assume a destination-port field or explicit source-port mapping is visible in every GUI/version. Confirm the release and the actual saved CLI configuration.

config firewall central-snat-map
    edit 10
        set srcintf "lan"
        set dstintf "wan1"
        set orig-addr "lan_subnet"
        set dst-addr "all"
        set port-preserve enable
    next
end

This illustrates the setting; use the existing rule's real addresses, interfaces, and IP-pool settings. Do not create a broad earlier rule that shadows a more specific mapping. Explicit port mapping is appropriate only for supported port-based protocols and suitable overload pools; it is not a general way to force ICMP or all clients onto one source port.

Evidence and diagnosis

Use diagnose sys session list on a newly created flow. In the session entry, compare the original tuple with the SNAT tuple shown in the origin/reply hooks. A preserved source port proves the allocator found it usable for that session; it does not prove every future session can reuse it. A translated port above 5117 can be normal for an original port below the supported preservation floor or for a collision.

Test after clearing only the relevant test session: existing sessions retain their existing translation after a configuration change. For UDP/500 or UDP/4500 IKE traffic, capture the actual source port on both sides and correlate it with the session entry before concluding that a peer or VPN configuration is wrong. A recent Community tip specifically highlights version and source-port-range effects for IKE SNAT.

Operational workflow

  1. Confirm FortiOS version, NAT mode, VDOM, and the matching central-SNAT rule.
  2. Check whether port-preserve is enabled and whether the source port is in range.
  3. Check the translated tuple for an existing collision and verify the IP-pool type.
  4. Clear and recreate a controlled test session, then compare packet captures with session-table evidence.
  5. Use explicit mapping only when the application requires deterministic ports and the protocol/pool supports it; document the capacity and collision risk.

Do not treat successful traffic as proof that the original port was preserved. The translated tuple is the authoritative evidence.

Lesson 02 · FortiManager

ADOM revision diff and restore: snapshot scope, retention locks, and re-install sequencing

465 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiManager 7.6.7 Administration Guide — ADOM revisions
  • FortiManager Administration Guide — Revert device configuration revision

Scenario research

  • Community Technical Tip — Use an ADOM revision during migration (older scenario context)

Two revision systems protect different state

An ADOM revision is a named snapshot of the FortiManager ADOM database state, including policy packages, objects, and VPN Console settings. It is useful before migrations or large refactors because it preserves a point-in-time configuration that can be compared with the current ADOM database. A managed FortiGate configuration revision is a different object: it represents a device configuration snapshot. Do not use “revision” as if both operations restore the same database.

The ADOM Revisions view shows an ID, name, creator, creation time, comment, and whether the revision is locked against automatic deletion. Retention settings may remove old revisions, so lock the known-good baseline when it must survive a migration window. Locking protects against auto-deletion; it is not a substitute for a separate FortiManager configuration backup.

Diff before restore

Use View Revision Diff to compare the selected ADOM revision with the current database. The summary helps determine whether the snapshot predates the intended change and what policy/object/VPN state would be rolled back. A restore reverts the ADOM database state. It does not itself install that state on the managed FortiGate, and it does not guarantee that a device's running configuration is now aligned with the restored package.

This distinction matters after a failed migration. The restored ADOM may contain an older package while the device still runs a newer or partially installed configuration. A “restore succeeded” message proves the database operation completed, not that the data plane is back at the desired state.

Safe restore sequence

  1. Create and label a pre-change ADOM revision; lock it if retention could remove it during the change window.
  2. Inspect the diff and identify the desired baseline. Record the target ADOM, package, devices, and time.
  3. Restore the chosen ADOM revision and wait for the database operation to finish.
  4. Import the managed FortiGate configuration when needed to synchronize the package stored in the ADOM database with device state.
  5. Run the install wizard and re-install the intended policy package to the correct target devices.
  6. Review install preview/errors and validate a representative data-plane flow.

Verification and failure isolation

Check the revision list for the expected ID/name/comment and use the revision diff to confirm the database baseline. Then inspect the package's installation status and install results. If the ADOM looks correct but the FortiGate is not, determine whether device import and package installation were performed; do not repeatedly restore the same revision to solve a missing install step.

For automation, keep the revision name and comment meaningful (change ticket, migration stage, or rollback point), and explicitly decide which revisions must be locked. Revisions consume backup space, so retention should be deliberate. A rollback plan is complete only when it names both the FortiManager database restore and the device synchronization/install steps that return the managed network to the target state.

Lesson 03 · FortiAnalyzer

Log Fetching between analyzers: approval, ADOM synchronization, transfer, and database rebuild

485 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiAnalyzer 7.6.6 Administration Guide — Log Fetching
  • FortiAnalyzer 7.6.6 Administration Guide — Fetch monitoring

Scenario research

No directly matched Community/KB scenario was independently verified for this lesson in the current search. The primary lesson remains documentation-led.

Why log fetching is not ordinary forwarding

Log fetching retrieves archived logs from one FortiAnalyzer to another so the client analyzer can query and report on historical data that resides on a server analyzer. The fetching client selects a device and time period through a fetch profile/request; the server reviews the request and can approve or reject it. After transfer, the client indexes the retrieved data into its own database. This is different from live log forwarding and from moving archive files by hand.

FortiAnalyzer requires the two appliances to run the same firmware for log fetching. An appliance can act as a fetch server for one peer and a client for another, but only one fetch session can be established at a time between a given pair. Capacity and maintenance planning matter because transferring and rebuilding a large historic interval can consume time and database resources.

Workflow and object dependencies

  1. On the client, create a fetching profile defining the server, devices, time range, and filters.
  2. Send a fetch request to the server.
  3. Synchronize devices and ADOMs when this is the first fetch with the profile or when device/ADOM assignments have changed.
  4. On the server, review the request and approve or reject it.
  5. Monitor transfer progress on either appliance under System Settings > Advanced > Log Fetch > Sessions.
  6. After transfer, allow the client to index the fetched logs and rebuild the affected ADOM/database as configured.

The synchronization step is easy to miss after a device moves ADOMs or the fetch profile changes. A successful connection to the peer does not prove that the client and server agree on device identity, ADOM membership, or the requested time interval.

Transfer complete is not analysis ready

The session may reach Done before the fetched data is queryable. FortiAnalyzer must index the logs and may need to rebuild the ADOM. If “Index Fetched Logs” is enabled, the ADOM rebuild is automatic; otherwise, the operator must rebuild it manually. During this phase, log and report features are not fully available. Do not diagnose a missing report as a transport failure until you have checked the indexing/rebuild stage.

Evidence and troubleshooting

Inspect the fetch session on both client and server. Confirm the request is approved, the selected device and time range are correct, and transfer progress actually advances. Then inspect the GUI rebuild progress/banner and verify a known device/time interval in Log View after indexing completes. If the expected logs still do not appear, check ADOM and device synchronization, the server-side archive retention, and the client-side index state separately.

For a collector-analyzer deployment, the Collector is the fetch server and the Analyzer is the fetch client when historic collector logs are retrieved. This direction is easy to reverse accidentally. Build a run record that states which appliance is client, which is server, the ADOM/device mapping, requested interval, approval, transfer completion, and rebuild completion. Those are distinct checkpoints, not one status.

Lesson 04 · FortiSwitch

LLDP-MED network policy for voice endpoints: VLAN advertisement, QoS TLVs, and port prerequisites

478 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiSwitchOS 7.6.5 Administration Guide — LLDP-MED
  • FortiSwitchOS 7.6.5 — LLDP-MED deployment example

Scenario research

  • Community Technical Tip — Configure voice VLAN on FortiSwitch (older scenario context)

What LLDP-MED actually negotiates

LLDP advertises device identity and capabilities over Layer 2. LLDP-MED extends it for media endpoints such as IP phones. Its network-policy TLV can advertise the voice VLAN, Layer-2 priority, and DSCP values; other TLVs provide location identification and inventory details, and LLDP can also expose PoE capabilities. The switch is not simply “putting the phone in a VLAN” by itself: it is advertising a policy that a capable phone may use to tag its voice traffic.

For a phone and PC sharing a switch port, the common design keeps the PC on the native/data VLAN while the phone tags voice traffic into a separate voice VLAN. The LLDP profile must advertise the correct voice VLAN policy, and the port must actually carry that VLAN. A profile that references a nonexistent VLAN interface, is not assigned to the port, or is not transmitted because LLDP is disabled cannot produce the intended result.

Configuration relationships

On a FortiGate-managed FortiSwitch, the LLDP profile is configured under the switch-controller LLDP profile hierarchy; standalone FortiSwitch uses its own switch LLDP profile hierarchy. The exact object path depends on management mode, so do not paste a controller-managed example into a standalone switch without adapting it.

config switch-controller lldp-profile
    edit "Phone"
        set med-tlvs inventory-management network-policy location-identification
        config med-network-policy
            edit "voice"
                set status enable
                set vlan-intf "VOICE-VLAN"
                set assign-vlan enable
                set priority 5
                set dscp 46
            next
        end
    next
end

Assign the profile to the correct port, keep the data VLAN as native, allow the voice VLAN on the trunk, and enable LLDP transmit/receive. The phone must also support and accept LLDP-MED. The advertised DSCP/priority informs endpoint behavior; it does not replace switch queueing, upstream QoS policy, or end-to-end DSCP trust decisions.

Evidence chain

Inspect the LLDP profile and port assignment first. Confirm the voice VLAN interface exists and the allowed VLAN list includes it. Then capture LLDP frames and verify that the network-policy TLV advertises the expected VLAN and priority. Finally, inspect the phone's tagged traffic and DHCP exchange. An LLDP advertisement proves the switch sent the policy; it does not prove the phone accepted it, that the VLAN is permitted across every trunk, or that DHCP can reach the voice scope.

Failure isolation

If the phone receives an address from the data subnet, check whether it received the voice TLV, whether the profile is attached to the actual port, whether the phone is sending/receiving LLDP, and whether the voice VLAN is allowed. If the phone tags correctly but has no lease, move to VLAN forwarding, DHCP relay/server, and gateway evidence rather than repeatedly editing the LLDP profile.

Use the LLDP-MED design as one part of a voice service chain: endpoint capability, advertised policy, port/VLAN carriage, DHCP, and QoS treatment. A failure at any later layer can look like a VLAN-assignment failure to the user, so collect evidence at each boundary.

Lesson 05 · FortiAP/Wireless

Wireless client load balancing: AP handoff versus frequency handoff and RSSI-driven retries

479 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiAP 7.6.6 Configuration Guide — Wireless client load balancing

Scenario research

  • Community Technical Tip — Load balancing between FortiAPs (older scenario context)
  • Community Technical Tip — Factors causing high channel utilization (older scenario context)

Two different steering mechanisms

FortiGate wireless controllers support access-point handoff and frequency handoff. AP handoff addresses an overloaded AP: if the station count crosses a configured threshold, the controller can signal a weak client to move to a nearby AP that can hear it adequately. When a new client joins while several APs are busy, the controller can select a less-loaded nearby AP to respond. Frequency handoff encourages dual-band clients to use 5 GHz when their measured signal is strong enough, leaving more 2.4 GHz airtime for devices that need it.

These are controller-driven association behaviors, not an instruction that forcibly moves every client at any time. Wi-Fi clients make the final association decisions and can ignore or retry a steer. The controller may withhold a response on 2.4 GHz to encourage a capable client to retry on 5 GHz. If 5 GHz signal quality is actually inadequate, the client may retry or fall back. Roaming clients are excluded from the documented load-balancing behavior, so do not use this feature as a universal roaming fix.

Profile settings and thresholds

Configure the custom WTP profile rather than treating a radio's threshold as an isolated setting. Common controls include frequency-handoff, ap-handoff, handoff-rssi, and handoff-sta-thresh. The documented RSSI threshold range is 20–30; the AP station threshold controls when an AP is considered busy. Actual usable values depend on cell overlap, device capabilities, airtime, application latency, and the RSSI that neighboring APs hear from the client.

config wireless-controller wtp-profile
    edit "FAP-profile"
        set frequency-handoff enable
        set ap-handoff enable
        set handoff-rssi 25
        set handoff-sta-thresh 30
    next
end

Use values supported by the target FortiOS/FortiAP release and validate against a pilot AP profile. The example is not a universal optimum.

What to measure

Before changing thresholds, capture current station counts, client RSSI on each band, channel utilization, retry/discard counters, and association events. High client count alone does not prove that load balancing will help: a weak client may not be audible to a neighbor, and a busy channel may be caused by co-channel interference or low-rate legacy clients rather than station count.

After changing the profile, observe whether new associations distribute to the expected APs/bands and whether retry/discard rates improve. If clients repeatedly reconnect to the original AP, verify neighbor RSSI and overlapping coverage before raising the station threshold. A high RSSI at the controller is not proof of sufficient uplink quality at the AP; wireless links are bidirectional.

Operational caveats

Frequency handoff can produce extra association attempts by design, so a small increase in retries during steering is not automatically a fault. Persistent failures, high discard ratios, or clients that cannot join are different signals. Use a separate, conservative profile/SSID for sensitive IoT and embedded devices when their wireless drivers behave poorly with aggressive band or rate tuning. Optimize the cell design first, then use handoff as a controlled load-balancing tool.

Lesson 06 · FortiNAC

Registered-host Network Access Policy first-match evaluation and catch-all ordering

452 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiNAC 8.3 Administration Guide — Network Access Policies
  • FortiNAC Administration Guide — Network access

Scenario research

  • Community Technical Tip — Configuring a Network Access Policy (older scenario context)
  • Community Technical Tip — Troubleshooting policies (older scenario context)

Policy object model

A legacy FortiNAC Network Access Policy joins two objects: a User/Host Profile, which describes who/what and where may match, and a Network Access Configuration, which defines the treatment to apply. Treatment can include a VLAN, a switch CLI configuration, or a VPN group policy. A host's identity, associated user, connection location, and other attributes are evaluated against the profile; the policy then maps a match to the treatment object.

The important behavior is ordered first-match evaluation. FortiNAC checks policies from the top of the ranked list and uses the first match. A later, more specific policy is irrelevant if a broad earlier profile already matches. A catch-all profile (location Any, group Any, no attribute restrictions, always active) effectively matches everything and should normally be last. This is a rule-ordering problem, not necessarily a VLAN delivery problem.

Eligibility is a separate boundary

Network Access Policies apply to registered hosts. A host must appear online in Host View, its port must be in the Role-Based Access port group, and the host must be registered; rogue hosts are not evaluated by the same policy path. For access points, confirm the relevant wireless access-point policy setting is enabled. A “no policy matched” result can therefore mean the endpoint never entered the expected evaluation path, not that the profile expression is wrong.

Evaluation changes over time

Assignments are not permanent. FortiNAC can re-evaluate a host when a switch is polled or the Persistent Agent reports back. A host may match a different policy after registration, user association, location, or host attributes change. Troubleshoot the evidence used at evaluation time, not only the current intended profile.

Verification workflow

  1. Find the endpoint in Host View and confirm online/registered state and its current connection location.
  2. Confirm the switch port belongs to the Role-Based Access port group.
  3. Use Policy Simulator to test the profile criteria and identify the first policy that matches.
  4. Inspect Policy Details on the host to see the assigned policy and treatment.
  5. Move broad/catch-all policies below specific ones, then trigger or wait for re-evaluation.
  6. Verify the actual VLAN or CLI treatment at the network device; a matching policy does not prove that the switch accepted the command.

When a host gets the wrong VLAN, check policy rank and profile criteria before changing the switch. If the correct policy is assigned but the VLAN does not change, then inspect switch integration, the configured network access treatment, and enforcement logs. Keep the diagnosis split between classification (which policy won) and actuation (whether the device applied it).

For maintainability, document the intended order, keep exceptions above general policies, and test with representative registered hosts. One broad profile inserted near the top can silently shadow many otherwise correct policies.

Lesson 07 · FortiNAC-F

Upgrade migration from Legacy RADIUS Proxy to Virtual Proxy Server in FortiNAC-F 7.4+

480 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiNAC-F 7.6 Administration Guide — Upgrade existing proxy configurations
  • FortiNAC-F 7.6 Administration Guide — Convert legacy proxy to Virtual Proxy Server
  • FortiNAC-F 7.6 Administration Guide — Virtual Servers

Scenario research

No directly matched Community/KB scenario was independently verified for this lesson in the current search. The primary lesson remains documentation-led.

Why the RADIUS model changed

FortiNAC-F 7.4 introduced an enhanced Proxy RADIUS Service configured through Network > RADIUS > Virtual Servers. Configurations created in earlier releases under Network > RADIUS > Proxy are called Legacy Proxy after upgrade. Legacy configurations can continue to work, but they are a migration state, not the preferred place to create new proxy services.

The new model makes the request-processing mode explicit. A Local virtual server can process RADIUS MAC and 802.1X EAP authentication without an external RADIUS server; supported EAP methods include EAP-TLS, TTLS, PEAP, TEAP, and others listed in the release guide. A Proxy virtual server processes MAC authentication locally unless Proxy MAB Requests is enabled, and forwards 802.1X EAP to customer-owned RADIUS. Proxy servers can be configured for failover or load balancing. Accounting is supported by proxy servers; the Local server does not provide accounting by itself.

Upgrade and migration sequence

After upgrade, clear the browser cache and inspect Network > RADIUS. Virtual Servers and Legacy Proxy should appear when the appliance had a pre-7.4 proxy configuration. New Virtual Proxy Server objects may be created automatically, but an automatically created object still needs validation. If the Legacy Proxy tab is absent, check whether Legacy Proxy Configuration is enabled; older port settings may affect whether the view is exposed.

  1. Review each generated virtual proxy's server address, shared secret, authentication/accounting mode, and failover/load-balance order.
  2. For each device, VDOM, or SSID, update its model/SSID configuration to reference the intended new RADIUS mode/server.
  3. Review the attribute group selected during conversion; the default RFC_Vlan group may not match the deployment's actual vendor attributes.
  4. Confirm the correct RADIUS access options on FortiNAC-OS interfaces. Proxy and Local listeners use different allowaccess tokens; HA deployments require checking both appliances.
  5. Test authentication and accounting behavior before disabling Legacy Proxy Configuration.

Evidence and failure boundaries

Check the Virtual Servers table, per-device/SSID RADIUS mode, Network > RADIUS activity and authentication-failure events, and the port1 allowaccess line. A successful Test Connection proves connectivity to the configured service, not that every device/SSID points to the right virtual server or that EAP is being processed at the intended local/proxy boundary.

If MAC authentication works but 802.1X fails, inspect whether the virtual server is Local or Proxy and whether EAP is meant to terminate locally or be forwarded. If authentication succeeds but accounting is missing, remember that Local RADIUS does not provide accounting and proxy accounting must be configured. If only some SSIDs fail after migration, inspect their individual model configuration rather than changing the global server object blindly.

Rollback and release hygiene

Keep the previous working configuration and test one representative switch/controller/SSID before broad migration. Move all devices off Legacy Proxy before disabling its configuration. The goal is not merely to make the new tab visible; it is to prove that each RADIUS transaction reaches the expected server and returns the expected authentication and accounting result.

Lesson 08 · FortiAuthenticator

RADIUS policy selection: request attributes, top-down precedence, and local EAP versus proxy

467 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiAuthenticator 6.6.5 Administration Guide — RADIUS policies
  • FortiAuthenticator 6.4.5 Administration Guide — Policies

Scenario research

  • Community Technical Tip — Use specific RADIUS policies for different IPsec VPN tunnels (older scenario context)

Policy matching starts with the request, not just the user

FortiAuthenticator RADIUS clients must be assigned one or more policies. A policy binds the client scope and request-attribute criteria to an authentication type, identity source, and response behavior. Policies are evaluated top-down. The first policy whose configured request attributes match is selected; a valid username/password does not compensate for a mismatched NAS-IP-Address, NAS-Identifier, or other required request attribute.

Policies can support Password/OTP, MAC Authentication Bypass, and EAP-TLS. Password/OTP policies can accept EAP methods such as PEAP, EAP-TTLS, EAP-GTC, and EAP-MSCHAPv2 when Accept EAP is enabled. Be careful with the trust boundary: the guide notes that EAP settings apply to EAP sessions terminated by FortiAuthenticator, not EAP sessions proxied to a remote RADIUS server.

Build specificity into the order

A practical design separates authentication contexts by client and attributes. For example, two IPsec tunnels may send different NAS-IP-Address values; separate policies can map each request to a different identity source or group. Put the specific criteria first and the broad/default policy later. If a broad policy has no request attributes, it may match before the more specific policy beneath it and send the request to the wrong identity source.

Each policy supports up to two RADIUS attributes as criteria in the documented version. Confirm the exact attributes available in the RADIUS dictionary and ensure the NAS actually sends them. Do not assume an attribute is present because it is configured on the NAS; verify the received Access-Request.

Configuration and observables

In Authentication > RADIUS Service > Policies, create a policy, select the RADIUS clients, enable request-attribute matching, select the authentication type, then configure identity sources and reply behavior. The settings shown in the GUI vary by authentication type. A policy with attribute criteria requires every configured criterion to match; otherwise, evaluation continues down the list.

For a failed login, inspect the received Access-Request fields and compare them with the criteria of each policy in rank order. Then inspect the selected identity source and whether the transaction was handled locally or proxied. A RADIUS Reject alone does not identify whether the failure was credential validation, a missing attribute, a policy-order problem, or an upstream proxy response.

Operational troubleshooting

  1. Confirm the request arrived from the intended RADIUS client.
  2. Record NAS-IP-Address, NAS-Identifier, and any other configured matching attributes from the request.
  3. Walk the policy list top-down and identify the first full match.
  4. Confirm the selected auth method, identity source, and whether EAP is terminated locally or proxied.
  5. Inspect the response attributes and the consuming FortiGate/VPN group mapping.

When different tunnels need different user groups, keep the NAS identity values stable and unique. A policy selection problem is best fixed at the request/policy boundary; changing user credentials or broadening identity sources can hide the actual mismatch and weaken separation between authentication contexts.

Lesson 09 · FortiPAM

Approval revocation as a live session-control action

458 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiPAM 1.9 Administration Guide — Approving a request
  • FortiPAM Administration Guide — Reviewing multiple requests

Scenario research

  • Community Technical Tip — FortiPAM revoke button is greyed out (older scenario context)

Approval is an authorization state, not merely a launch-time check

FortiPAM can require a user to request access to a secret, then have one or more approvers approve or deny it for a bounded period. The approval list records the request state and approver comments; the requester can see comments, and the request appears in the My Requests view. Approval tiers can require multiple approvals, which changes when a tier is considered complete and whether an approver can revoke their own approval before the request moves forward.

FortiPAM 1.9 adds a more powerful Revoke Approval action for an already approved secret request. The approver can revoke regardless of tier, even after the requester has launched the secret. If a session is active, revocation immediately terminates that secret session and resets the request so it must be approved or denied again. That makes approval revocation a live session-control operation, not just a way to prevent the next launch.

Version and tier behavior matter

Older versions may show the revoke action as unavailable once a single-approver tier is complete. In that model, one approver's approval completes the tier, so there is no pending approval to revoke at that stage. With multiple approvers in a tier, an approval may remain revocable until the required tier count is satisfied. On FortiPAM 1.9+, use the documented Revoke Approval workflow for already approved requests rather than relying on the older pre-completion behavior.

Operational procedure

  1. Open Secrets > Approval List and identify the exact secret request and requestor.
  2. Confirm the FortiPAM version and current approval status/tier.
  3. Use Revoke Approval where supported and provide the required audit/comment context.
  4. Check the request resets to a pending state and inspect Monitoring > Active Sessions for the user's launched secret session.
  5. Verify the active session is terminated and that a new launch requires a fresh approval decision.

For bulk operations, the guide supports selecting multiple requests and approving/denying them together. Review the selected rows carefully: a bulk action can change several authorization states. Job requests differ in that script output can be checked in logs, while secret requests govern access to target credentials.

Evidence and failure isolation

A revoked status alone is not enough when the goal is to cut off current access. Verify session termination in the active-session view and correlate the audit event. If the button is greyed out, inspect version, approval tier, approver count, and whether the request has already completed the older tier process. Do not assume that denying a future request terminates a currently running session.

For emergency response, test the revocation path before relying on it operationally. Record the request ID, approver, time, session ID, and result. Least-privilege access requires both time-bounded approval and a proven way to withdraw it when authorization changes.

Lesson 10 · FortiSIEM

Rule execution modes: streaming, scheduled, and scheduled-via-SQL evidence boundaries

479 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiSIEM 7.4.2 User Guide — Creating Rules
  • FortiSIEM 7.4.0 User Guide — Creating Rules

Scenario research

No directly matched Community/KB scenario was independently verified for this lesson in the current search. The primary lesson remains documentation-led.

A rule is a query plus grouping, threshold, and incident semantics

FortiSIEM rule conditions are built from event filters and one or more subpatterns. Group-by attributes define which events belong to the same logical group; aggregate conditions define the threshold that triggers an incident. For example, COUNT(Matched Events) >= 10 with no group-by aggregates matching events together, while grouping by Source IP creates separate threshold calculations per source. With multiple subpatterns, relationship operators such as FOLLOWED_BY or NOT_FOLLOWED_BY connect event sequences and can compare attributes across patterns.

Execution mode changes what the rule can do and what evidence appears on the incident. Streaming rules evaluate incoming events with low latency and can be tested in the rule builder. Scheduled rules can analyze larger intervals and use more complex analytic functions, but they run on a configured schedule/time window. Scheduled-via-SQL is only available with ClickHouse in Super/Global mode and has additional constraints.

Important mode-specific limits

The FortiSIEM 7.4.2 guide documents that scheduled-via-SQL incidents do not show trigger events, can generate at most 100 incidents per execution, support only time as a clear condition, support only key attributes for exceptions, and cannot be tested like streaming rules. Scheduled rules also have limits that vary by backend: in non-ClickHouse environments only one subpattern is allowed for scheduled rules; ClickHouse permits certain multi-subpattern functions such as FOLLOWED_BY and NOT_FOLLOWED_BY. Confirm the deployed backend and rule type before interpreting an empty trigger-event panel as proof that the rule did not match.

Configuration choices

Define the event filters first, then choose group-by fields that represent the incident identity you actually want. Set the aggregation threshold and time window to the intended scope. For scheduled mode, configure timezone and frequency. Set clear conditions deliberately; time-based clearing can be appropriate for scheduled analysis, but it does not mean the underlying event condition has disappeared.

Do not use an excessively broad group-by set: adding destination port or user to a grouping key may split one burst into many small groups, preventing the threshold from being reached. Too few keys can merge unrelated systems into a single incident. Group-by design is a detection-model decision, not just a display preference.

Verification and troubleshooting

  1. Record the rule mode, backend, timezone, query window, and schedule.
  2. Check each subpattern filter against known raw/normalized events.
  3. Verify group-by fields and aggregate expressions independently with a search query.
  4. Confirm the incident count and whether trigger events are expected to be retained in that mode.
  5. Review clear conditions, exceptions, and the 100-incident execution cap where applicable.

If a scheduled rule produces no incident, determine whether the window actually contained events and whether they were grouped under the same key. If an incident exists but lacks trigger-event detail, compare the rule mode and backend limitations before changing parsing. The correct evidence boundary prevents an analyst from “fixing” a rule that is behaving as designed for its execution mode.

Lesson 11 · FortiSASE

Security PoP migration lifecycle: staged target, 30-day cutover, and endpoint/PAC dependencies

491 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiSASE 7.4 Administration Guide — Infrastructure and Security PoPs

Scenario research

  • Community Technical Tip — FortiSASE automated PoP migration (older scenario context)

Migration is a staged control-plane change

FortiSASE Security PoPs can be created, enabled/disabled, decommissioned, and migrated from one location to another. During migration, the target PoP is added to the instance in a disabled state. It will not accept connections until enabled. If the migration is left unattended, the target is automatically enabled and the source is decommissioned after 30 days. This delayed transition is operationally important: the target being visible in the console does not mean it is serving endpoint traffic.

PoP migration can change the address endpoints or edge devices use to reach the service. Devices using the provided global FQDN generally do not need changes. Edge deployments that directly reference a PoP IP do. Proxy deployments also differ by how they fetch PAC files: global-address PAC access usually avoids endpoint changes, while regional PAC fetch addresses or self-hosted PAC files referencing a migrated regional proxy may need updates.

Plan the dependency graph

Before starting, inventory edge devices, endpoint profiles, PAC files, proxy fetch URLs, custom regional references, and any direct PoP IPs. Confirm the target PoP is available for the license type and choose the activation window. The migration procedure allows the operator to choose when the new site activates and the old site deactivates; treat that as a controlled cutover, not an instantaneous DNS change.

  1. Open Operations > Infrastructure and inspect the Security PoP source/target and migration availability.
  2. Start the migration and confirm the target is provisioned but disabled.
  3. Enable the target at the planned time and validate user/edge connectivity through it.
  4. Update edge configurations that use a direct PoP address.
  5. Review PAC files: global address, regional FortiSASE proxy, custom hosted PAC, and self-hosted PAC references have different update requirements.
  6. Confirm the source remains available during the transition, then verify decommission state before the automatic 30-day deadline.

Evidence and troubleshooting

Check PoP state in the Infrastructure view, then test the actual endpoint or edge path. A green target PoP is not proof that a specific client profile points to it. Inspect endpoint profile configuration, PAC fetch URL, and the route/proxy address used by the affected client. If some users fail while others work, compare global-FQDN versus direct-IP/regional-PAC paths before treating it as a global PoP outage.

For PAC files hosted by FortiSASE, the migrated PoP may need to be removed from the file while the fetch address remains unchanged. For self-hosted PAC files referencing a regional proxy, update the regional address. These cases are easy to conflate because both are “PAC problems,” but one concerns the PAC file's content and the other concerns where the client retrieves it.

Operational caveats

PoP disable removes the site from load balancing; decommission deletes it from the instance. If multiple IP addresses are assigned to a PoP, they can be enabled or disabled individually. Use a written cutover checklist and validate before the 30-day automatic transition. A migration is complete only when both service state and all client-facing references are correct.

Lesson 12 · Secure SD-WAN

Dynamic SDN connector addresses in SD-WAN rules: cloud inventory refresh to path match

498 focused words · source-led lesson · mechanism/evidence/remediation

Primary documentation

  • FortiOS 7.6.6 Administration Guide — SD-WAN rules
  • FortiOS Administration Guide — SDN dynamic connector addresses in SD-WAN rules

Scenario research

No directly matched Community/KB scenario was independently verified for this lesson in the current search. The primary lesson remains documentation-led.

Dynamic cloud identity becomes a routing match

An SDN connector retrieves workload/resource information from a cloud or virtualization platform. A dynamic Fabric Connector Address object can select a subset of that inventory using a connector-specific filter, such as a security-group tag. The address object can then be referenced as a destination in an SD-WAN service rule. This joins two control planes: cloud inventory refresh determines which IPs belong to the object, and SD-WAN rule evaluation determines the path for traffic matching those IPs.

FortiOS documents public connectors for platforms such as AWS, Azure, GCP, OCI, and Alibaba Cloud, and private connectors for platforms including Kubernetes, VMware/NSX, OpenStack, ACI, and Nuage. The exact fields vary by connector, but the workflow is consistent: connector connectivity, dynamic address object, filter, SD-WAN rule reference, then path strategy.

Configuration dependency chain

  1. Ensure the FortiGate can reach the connector API endpoints and has working credentials/permissions.
  2. Create and enable the public/private SDN connector and select its update interval.
  3. Create a firewall address of Dynamic type with Fabric Connector Address subtype; bind it to the connector and set the resource filter.
  4. Reference that address object in the destination field of an SD-WAN rule.
  5. Configure the rule's strategy and member preferences independently of the address object.

For an Azure-style connector, the address object might filter a security-group/resource attribute. The filter controls membership; it does not directly choose a WAN link. The SD-WAN rule matches the resolved IP set, then its strategy selects among members based on priority, health, or other configured criteria.

Verification: connector health is not rule membership

Start with diagnose sys sdn status to check whether the connector is connected and updating. If the IP list is stale, use the connector application debug (for Azure examples, diagnose debug application azd -1) to observe polling and address changes. Then inspect the resolved dynamic address object and diagnose sys sdwan service to confirm the destination set appears in the expected service rule.

A healthy connector does not prove that the filter matched any workloads, that the address object is used by the intended SD-WAN rule, or that the rule wins over a higher-priority rule. Conversely, a correct rule cannot match a cloud workload that has not yet been imported into the dynamic object. Check each layer separately.

Failure modes and remediation

If newly created workloads use the wrong path, confirm connector API credentials and last-update status, validate the filter/tag value, and inspect the resolved IP list. If the address list is correct but the wrong member is selected, inspect rule order, strategy, and health state instead of changing connector filters. Protect connector secrets, use least-privilege API permissions, and avoid overly broad filters that can unexpectedly route newly discovered workloads through a different WAN path.

This design is useful for cloud workloads whose addresses change dynamically, but it creates a dependency on connector polling and inventory correctness. Treat the cloud address set as a changing policy input and monitor both refresh health and the final SD-WAN match.
