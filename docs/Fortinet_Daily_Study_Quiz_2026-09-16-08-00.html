1. FortiGate — BFD, BGP graceful restart, and HA failover

Mechanism. BFD and BGP graceful restart solve different failure problems. BFD is a forwarding-path liveness detector; BGP GR attempts to preserve forwarding state while a routing control plane restarts. FortiOS 7.6.6 documents a special HA consideration: BGP has an auto-start delay after failover, so a static BFD neighbor under config router bfd can cause the new primary to create BFD requests immediately rather than waiting for BGP to establish and register BFD. The observable get router info bfd requests therefore proves which protocols have requested BFD; it does not by itself prove that BGP has exchanged routes.

Fortinet's September 16 Community scenario exposes the competing timer boundary: during HA transition, missing BFD packets can expire the BFD inactivity timer before GR can preserve the adjacency. That means an engineer must distinguish “BFD session survived/reformed” from “BGP retained stale forwarding state.” Inspect BFD neighbor/request state, BGP neighbor capability/state, routing-table retention, and actual forwarding separately. A static BFD session initializes as INIT and derives detection time from required-min-rx × detect-mult, so timer tuning directly changes how much HA interruption can be tolerated.

config router bfd
 config neighbor
  edit 172.20.121.23
   set interface "port4"
  next
 end
end
get router info bfd requests
get router info bfd neighbor detail
get router info bgp summary

Operational implication. Do not treat “fastest failure detection” as universally better. If BFD is faster than the control-plane recovery window, it can intentionally defeat graceful behavior. Validate the design objective: immediate withdrawal versus transient-state preservation.

Primary: FortiOS 7.6.6 BFD. Scenario: BGP GR/BFD during HA failover — Sep 16, 2026.

2. FortiManager — workflow sessions are an ordered transaction queue

Workflow mode is not simply an approval checkbox. It changes the ADOM transaction model. Device Manager and Policy & Objects become read-only until the ADOM is locked and a workflow session is created. Changes live in that session, can be diffed, saved, submitted, rejected, repaired, discarded, approved, and eventually installed. Fortinet explicitly requires sessions to be approved in creation order. A rejected session blocks later approval until it is repaired or discarded; discarding a session also discards later sessions. This creates a dependency chain that matters during emergency changes.

Approval matrices can contain up to eight approval groups; one user from each group must approve. Email is notification/approval transport, not the source of truth—the session state in the ADOM remains authoritative. set workspace-mode workflow enables all-ADOM workflow; per-adom allows the GUI to select workflow per ADOM. Changing workspace mode ends the current login session.

Evidence boundary. “Policy package modified” does not prove “approved,” and “approved” does not prove “installed on FortiGate.” Verify session status, View Diff, approval-group completion, package/device config status, install preview, and installation history as separate stages. This prevents a common operational mistake: troubleshooting a FortiGate for a change that exists only inside an unapproved FortiManager session.

Primary: Workflow mode and Enable workflow mode. Scenario: workflow operational example.

3. FortiAnalyzer — event handler → notification → FortiGate automation stitch

FortiAnalyzer event handlers operate on Analytics logs, not Archive logs. A basic handler fires when one of its rules matches; multiple basic rules have OR semantics. Correlation handlers can express AND, AND_NOT, OR, FOLLOWED_BY, and NOT_FOLLOWED_BY sequences. Data selectors scope devices/subnets/log filters, while notification profiles and automation-stitch enablement are separate reusable objects.

When Automation Stitch is enabled on a handler and the handler generates an event, FortiAnalyzer sends a notification to the FortiGate automation framework. The FortiGate must already log to and authorize the FortiAnalyzer, and it needs a FortiAnalyzer Event Handler trigger corresponding to the handler. The FortiGate can additionally match severity and tag before executing actions. Thus, an incremented FortiAnalyzer event counter proves handler evaluation; it does not prove the FortiGate received the OFTP notification or that the FortiGate trigger conditions matched.

For troubleshooting, walk the transaction: Analytics log exists → data selector includes it → rule/correlation condition fires → event appears in Event Monitor → FortiAnalyzer-to-FortiGate connection/certificate is valid → FortiGate trigger count increments → action executes. This prevents skipping directly to the action when the failure is actually upstream in log retention or selector scope.

Primary: Automation Stitch for event handlers. Scenario: FortiAnalyzer → FortiGate trigger flow.

4. FortiSwitch — MCLAG split-brain containment

MCLAG makes two FortiSwitches appear as one logical LAG endpoint, providing node redundancy without waiting for STP reconvergence. The inter-chassis link (ICL) carries peer coordination. Split brain occurs when ICL communication is lost while both peers remain capable of forwarding. FortiSwitch can detect this and place one peer dormant. The lower mclag-split-brain-priority wins the dormant decision; equal priorities fall back to the lower numerical MAC. Optional all-ports-down shuts all ports on the dormant peer except ICL ports.

Important caveats are topology-specific. Detection must be enabled on both peers. FortiSwitchOS 7.4.1 improved distinction between an ICL failure and a peer reboot, but that behavior requires at least one dual-homed FortiSwitch. In 7.6.2, third-party dual-homed switches are supported when at least one FortiSwitch is also dual-homed; split-brain priority is not supported in that third-party topology. Enabling containment can still cause transient loss while LACP renegotiates.

config switch global
 set mclag-split-brain-detect enable
 set mclag-split-brain-all-ports-down enable
 set mclag-split-brain-priority 40
end
diagnose switch mclag icl
diagnose switch mclag list

Primary: FortiSwitchOS MCLAG. Scenario material includes recent FortiSwitch operational articles; the lesson remains documentation-driven.

5. FortiAP/Wireless — roaming is client-driven; 802.11k/v/r change the cost, not ownership

A Wi-Fi station decides when to roam. The controller and FortiAP can influence the decision, but they do not command every client to move merely because another AP has stronger RSSI. Clients discover candidates through passive Beacon reception and/or active Probe Request/Response exchanges. 802.11k can provide neighbor information, 802.11v can provide BSS transition assistance, and 802.11r reduces authentication latency through Fast BSS Transition. These mechanisms reduce scan/authentication cost; they do not repair a bad RF design.

When a client remains “sticky,” first separate RF eligibility from authentication and L2/L3 continuity. Verify RSSI/SNR and channel utilization, candidate AP visibility, whether the client supports/uses k/v/r, reassociation/FT exchange, VLAN consistency, DHCP/IP continuity, and RADIUS/PMK behavior. FortiOS 7.6.7 release notes illustrate why this separation matters: fixes include 802.11r reassociation failures, duplicate reassociation responses, class-attribute restoration during roam, and inter-controller L3 roaming IP preservation.

Primary: Fortinet wireless controller/FortiAP documentation and release-specific behavior. Scenario: Fortinet Wireless Roaming technical tip. The memory rule is: the STA owns the roam decision; infrastructure changes candidate discovery and transition cost.

6. FortiNAC — Persistent Agent heartbeat and compliance are separate signals

The Persistent Agent is permanently installed on Windows, macOS, or Linux endpoints. It identifies the host, runs compliance scans/monitors, and checks in periodically to the FortiNAC agent server. A missing heartbeat produces a Lost Contact event; later communication produces Regained Contact. Lost contact therefore means “FortiNAC expected an online host with PA but is not receiving agent communication,” not automatically “the endpoint failed compliance.”

Architecture matters: the Persistent Agent works with the Control Server/Application Server pair or FortiNAC Server; without the required pairing, Fortinet directs use of the Dissolvable Agent. Registration can be interactive through DNS redirection/login/download or passive. VM guest detection has its own options, so agent presence alone does not guarantee that a new guest attached to a virtual host is represented as intended.

Evidence-driven troubleshooting separates: host online → DNS/registration path → PA installed/running → heartbeat reaches server → host identity mapping → compliance scan result → policy/enforcement action. A “Lost Contact” event proves the heartbeat boundary failed; it does not prove switch VLAN enforcement is wrong.

Primary: Using the Persistent Agent and Persistent Agent communication.

7. FortiNAC-F — logical networks decouple policy intent from device VLAN numbers

A logical network is an intent label whose access value is translated into a device-specific physical value. The same “Corporate” logical network can therefore map to different VLAN IDs on different switches. Policy can reference the logical network once, while Model Configuration supplies each device's actual access value. This reduces policy duplication and makes device replacement/migration less coupled to policy.

The transaction is: define logical network → assign access value on each managed device/model → create network access configuration → policy selects that configuration → FortiNAC provisions the local access value. The recent RADIUS-only integration scenario is useful because it demonstrates that dynamic VLAN assignment can still work without SNMP/CLI management: the network device is added with IP/RADIUS secret, logical networks and VLAN mapping are defined, and RADIUS Access-Accept returns the enforcement value.

A REST API read can return multiple entries with the same logicalNetworkName because each has a different elementID representing the device context. Therefore, changing the first matching name is unsafe; identify elementID/DBID and object id before POSTing a new access value.

Primary: Logical networks. Scenarios: RADIUS-only integration and REST access-value update.

8. FortiAuthenticator — FIDO2 user-verification policy

FortiAuthenticator 6.6.3 added a global FIDO2 user-verification setting under Authentication → User Account Policies → Tokens. This controls what verification behavior FAC instructs the end user's browser/authenticator to use during FIDO registration/authentication. The key engineering distinction is between possession of a registered authenticator and local user verification at that authenticator. Changing FAC policy affects the WebAuthn ceremony request; actual capability still depends on browser/authenticator support.

Troubleshooting should isolate registration from authentication. Confirm RP/origin context, credential registration, authenticator capability, FAC user-verification setting, browser response, and FAC decision. A browser prompt proves a ceremony was initiated, not that FAC accepted the signed assertion. Conversely, an enrolled FIDO credential does not prove the current authenticator can satisfy a stricter verification requirement.

This mechanism is intentionally distinct from the OAuth/OIDC transaction lesson taught earlier in the exclusion window.

Primary: FortiAuthenticator 6.6.3 feature changes.

9. FortiPAM — exclusive checkout, renewal, force-checkout, and password rotation

When Requires Checkout is enabled, only one approved user can hold a secret at a time. Checkout is therefore a concurrency-control mechanism, not merely an audit event. Checkout Duration defaults to 30 minutes and is configurable from 3–120 minutes. Renew Checkout can permit extension with Max Renew Count (default 1, range 1–5). Force Checkout can become available after the current holder has no active launch session for the configured idle time; that option depends on Proxy Mode and Session Recording.

Checkin Password Change can automatically rotate the password on check-in. That creates a crucial transaction boundary: “session closed” and “credential rotated” are not synonymous unless the feature is enabled and succeeds. Verify checkout owner/expiry, active launch session, check-in state, rotation result, and downstream target credential independently.

Primary: Creating a secret and Check out/check in.

10. FortiSIEM — UEBA tags, weights, sticky worker routing, and model persistence

FortiSIEM UEBA tags classify event characteristics using fields such as Machine ID, User, Application, Activity, Resource, and Resource Filename. Each tag has a weight from Never Alert (-5) through Always Alert (+5), allowing contextual influence on alerting rather than a simple binary match. The AI module runs on Super and Worker nodes; agent activity is routed to one node in a sticky manner. If a Worker fails, events move to another Worker; newly added Workers receive new Agents. AI models persist across module restarts.

FortiSIEM 7.4.2 also extends UEBA to regular Windows Security/Sysmon logs for selected behaviors. Regular logs cover only a subset of activities compared with the proprietary UEBA Agent, so “UEBA is receiving Windows logs” does not prove equivalent behavioral coverage. In troubleshooting, verify ingestion/parser identity, tag rule match, entity mapping, worker assignment, model state, alert generation, and UEBA View separately.

Primary: UEBA Tags and UEBA based on log.

11. FortiSASE — Secure Private Access flow through PoP and SPA connector

FortiSASE SPA sends remote-user traffic to a FortiSASE Security PoP, where policy is enforced, then reaches private applications through an SPA Connector. Connector options include an existing FortiGate SD-WAN hub or FortiGate NGFW/DC firewall. SPA can combine user identity and device context for ZTNA-style application access with continuous posture reassessment.

The operational flow is therefore not “client directly tunnels to application.” Separate client-to-PoP reachability/authentication, PoP policy decision, connector availability/routing, connector-to-application reachability, application identity, and posture state. A successful FortiClient/FortiSASE login proves identity/session establishment to the service; it does not prove that a specific private app is reachable behind the connector.

Primary: FortiSASE SPA architecture.

12. Secure SD-WAN — BGP communities become route-tags on destinations

Route-tags integrate dynamic routing with SD-WAN steering. A route-map can translate a received BGP community into a FortiOS route-tag, and an SD-WAN rule can match that tag as a dynamic destination. The non-obvious FortiOS 7.4+ behavior is that once applied, the route-tag is a property of the destination prefix, not of the particular path/session that supplied it. Therefore an SD-WAN rule may match a tagged destination and select a member from which the tag was never learned. This differs from older 7.2 behavior.

That means engineers must not infer path provenance from a matched route-tag. Verify BGP community reception, route-map-in translation, route-tag database, SD-WAN rule match, SLA/member eligibility, and selected egress independently. Fortinet notes route-tag is not a BGP attribute; setting it in a route-map-out does not transmit it to a BGP neighbor. The portable signaling object is the BGP community; the route-tag is local steering metadata.

Useful evidence includes diagnose sys route_tag list, BGP route/community inspection, and diagnose sys sdwan service4/service6. The memory rule is: community travels; route-tag is local; in 7.4+ the tag belongs to the destination.

Primary: Route-tag deep dive. Scenario: BGP + SD-WAN operational example.
