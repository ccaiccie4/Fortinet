LESSON 01 · FortiGate

Static virtual IPs: DNAT mapping, port forwarding and ARP ownership

Editable draw.ioStandalone SVG

A static virtual IP (VIP) is a destination-NAT object. It tells FortiOS that traffic addressed to an external address (or address/port tuple) should be translated to an internal server address. A one-to-one VIP maps the full port range; a port-forwarding VIP narrows the translation to selected external and mapped ports. The VIP is not itself an allow rule: the forwarded flow still needs a firewall policy whose destination references the VIP.

Objects and packet transaction

Keep four values separate: extip is the public address clients target; extintf constrains the interface on which the VIP is valid; mappedip is the real server address; and, for port forwarding, extport/mappedport describe the service translation. The ingress packet first matches the VIP translation. FortiGate then evaluates the forwarding policy using the VIP object as the destination, checks the service/source/schedule and route, and forwards toward the mapped server. The server's return traffic must route back through the FortiGate so reverse translation can be applied to the session.

Central NAT changes where DNAT objects are managed in the GUI: use Policy & Objects > DNAT & Virtual IPs instead of the ordinary Virtual IPs page. It does not make the VIP object a substitute for a firewall policy.

Configuration sketch

config firewall vip
    edit "Web_HTTPS"
        set extip 203.0.113.10
        set extintf "wan1"
        set mappedip "10.20.30.15"
        set portforward enable
        set extport 443
        set mappedport 8443
    next
end

config firewall policy
    edit 0
        set name "Internet_to_Web"
        set srcintf "wan1"
        set dstintf "server_vlan"
        set srcaddr "all"
        set dstaddr "Web_HTTPS"
        set action accept
        set schedule "always"
        set service "HTTPS"
    next
end

The official sample uses the same extip, extintf, mappedip object model and references the VIP by name in dstaddr. Treat the sample as a pattern: use the actual external interface, server VLAN, source scope and service required by the deployment.

ARP ownership is a separate boundary

By default, VIP/IP-pool ARP reply is enabled. When enabled, FortiGate answers ARP for the external VIP address and treats it as a local address. The documented side effect matters: a configured VIP can change how FortiGate handles traffic for that address even if the VIP is not referenced by a policy; FortiGate may not forward that traffic according to the routing table. An unused VIP is therefore not harmless configuration residue. Delete unused VIPs, or deliberately disable ARP reply when the design requires another device to own the address. Do not disable it reflexively: first establish who should answer ARP on that segment.

Verification: prove each stage

  • Object: inspect the VIP and confirm external address/interface, mapped address and port mapping. This proves intended translation, not policy admission.
  • Policy: verify the intended policy references the VIP and the expected service; check hit counters during a controlled connection. A zero counter points toward interface/VIP/policy matching, not the server application.
  • Packet path: capture on WAN and server VLAN. The WAN-side packet should target the external address/port; the server-side packet should target the mapped address/port. This proves DNAT occurred, not that the server accepted the application request.
  • Return: confirm the server's gateway/route returns through this FortiGate and observe the reverse-translated response.

Operational scenario

An administrator reports that ping to the FortiGate WAN address stopped working after publishing a VIP for that same address. The VIP has no explicit port-forward restriction, so ICMP is also eligible for translation. FortiGate may forward the ping toward the mapped server rather than answer locally; the server then needs a permitted return path. Check the VIP's ARP reply and mapping before changing local-in policy or upstream routing. This is a destination-ownership problem, not automatically a WAN reachability outage.

Dependencies and caveats

Use a distinct external VIP address where possible. If the public WAN address itself is mapped, explicitly consider ICMP and other non-port traffic. Under HA, verify the VIP and policy configuration on the synchronized peer and test after failover; an object visible in the configuration is not proof of correct ARP ownership on the active node. Remove stale VIPs because their local-address behavior can affect unrelated routing.

Primary source: FortiOS 8.0 Static virtual IPs. No directly matching Community scenario was verified in the rolling 30-day window.

LESSON 02 · FortiManager

Normalized interfaces with per-device and per-platform mapping

Editable draw.ioStandalone SVG

Normalized interfaces let one ADOM policy refer to a logical interface name even when managed FortiGates use different physical ports or device zones. The object is a translation layer in FortiManager's policy database; it is not a new interface created on the FortiGate. At installation time, FortiManager resolves the logical name into the target device's real interface.

Two mapping scopes, one policy reference

A per-platform mapping associates a normalized interface with an interface name for a model family. It is useful when a set of same-model devices share a port layout. A per-device mapping binds the logical name to the interface or zone on one specific managed device/VDOM. When both mappings exist, the per-device value is the more specific override; devices without a matching device entry use the applicable platform/default mapping. If neither mapping resolves, install compilation can fail with a missing or undefined dynamic interface.

For example, the shared policy can use VOICE as its incoming interface. A 40F might resolve VOICE to port3, while a larger appliance or a device with a zone resolves it to a different local interface/zone. The shared policy stays readable and the target-specific interface remains explicit in the mapping object.

Configuration workflow

  1. Enter the correct ADOM and open Policy & Objects > Normalized Interface.
  2. Create the logical interface and description.
  3. Add a per-platform mapping by choosing the FortiGate model and entering the device interface name.
  4. Add a per-device mapping when one device/VDOM needs an exception; select the managed device and its actual interface or zone.
  5. Reference the normalized interface in the policy package, then run Install Preview and inspect the generated target configuration before installation.

The FortiManager 7.6.6 guide documents an important default-mapping trap: if a physical interface name must be used in a per-platform mapping, the default per-platform rule on the default normalized interface may need to be deleted first. Otherwise FortiManager can report dynamic-interface default mapping has been used and refuse creation. Do not delete defaults blindly; first confirm the object and model design actually require a custom physical-port mapping.

CLI representation and boundaries

config dynamic interface
    edit "VOICE"
        set default-mapping enable
        set defmap-intf "VOICE"
        config dynamic_mapping
            edit "FGT_SERIAL"-"root"
                set local-intf "port3"
            next
        end
        config platform_mapping
            edit "FortiGate-40F"
                set intf-zone "VOICE"
            next
        end
    next
end

This is FortiManager ADOM-database syntax, not a FortiGate CLI block to paste directly onto the firewall. The general dynamic-mapping guide also notes that CLI scripts modifying policy objects must be run against a policy package rather than the Device Database. Keep the management-plane representation separate from the installed device configuration.

Verification and troubleshooting

  • Inspect the normalized-interface mapping table and confirm the target device/VDOM and model are correct.
  • Use View Where Used or policy search to find every package that references the logical interface.
  • Read Install Preview. It must show the expected real interface/zone in the generated firewall policy. Preview is the strongest pre-commit proof that mapping resolved.
  • After installation, inspect the FortiGate policy's actual srcintf/dstintf. A green install task alone does not prove the correct physical port was selected.

When a device is imported or replaced, compare the new device's mapping against the old device before installing. Imports can create per-device mappings from learned values; a hidden override can continue to win even after the default object is corrected. Check the per-device entry before assuming a platform map is being used.

Operational application and caveats

Use normalized interfaces for repeatable policy packages across models, but keep mapping ownership in change control. A zone can be the mapped object when the policy should apply to a group of physical ports. A wildcard normalized interface is a different feature: its pattern can resolve to multiple interfaces at install time, so verify every match rather than treating it as a single port. In HA-managed FortiGates, ensure both peers share the intended physical interface naming and validate the installed result after a topology change.

Primary sources: FortiManager 7.6.6 Creating normalized interfaces; Per-device and per-platform dynamic mapping. No directly matching Community scenario was verified in the rolling 30-day window.

LESSON 03 · FortiAnalyzer

FortiGate onboarding through Security Fabric authorization

Editable draw.ioStandalone SVG

Security Fabric authorization is the trust-enrollment step that lets a FortiGate become an authorized FortiAnalyzer member for centralized logging and Fabric visibility. It is distinct from simply typing a FortiAnalyzer IP into the FortiGate. The authorization endpoint and port are configured on FortiAnalyzer; the FortiGate then initiates the Logging & Analytics connector and an administrator approves the device.

Control-plane transaction

  1. On FortiAnalyzer, open System Settings > Settings and configure the Fabric Authorization address and port. This is the address used to reach the FortiAnalyzer login/authorization service.
  2. On FortiGate, open Security Fabric > Fabric Connectors, edit the Logging & Analytics card, enable the FortiAnalyzer connector and enter the FortiAnalyzer server address.
  3. FortiGate contacts the configured authorization endpoint. The FortiAnalyzer administrator reviews the pending device and supplies the required administrative approval/credentials.
  4. After approval, the FortiGate appears as an authorized device in FortiAnalyzer Device Manager. Log upload settings then govern the separate log-delivery path.

Think of this as two transactions. The first establishes trust and device authorization. The second transports logs and makes them available for Analytics. They can fail independently. A FortiGate can be authorized but not delivering logs because its logging configuration, OFTP reachability, device/ADOM mapping or log-storage state is wrong. Conversely, a device that is reachable over the network is not automatically an authorized Fabric member.

What the connector does not prove

The FortiGate connector card proves the configured endpoint and enabled state. It does not prove that FortiAnalyzer has approved the device. The authorized-device record proves the trust relationship, not that every log type is being uploaded. A log visible in a raw receive view proves arrival, not necessarily successful insertion or query visibility. Keep the evidence chain separate: connector configured → authorization approved → log transport established → log received → log indexed/queryable.

Verification and failure isolation

  • On FortiAnalyzer, confirm the Fabric Authorization address and port are the intended reachable interface/service, not an unrelated management address.
  • On FortiGate, verify the Logging & Analytics connector is enabled and points to that address. If FortiAnalyzer certificate verification is enabled, confirm the certificate chain/name is valid rather than disabling verification as a first response.
  • On FortiAnalyzer, inspect the pending/authorized device state in Device Manager. If the request never appears, troubleshoot endpoint reachability and connector configuration before changing the admin account.
  • After authorization, test log upload separately. Check the FortiGate log settings and the FortiAnalyzer device/ADOM assignment, then verify a known test event in the expected log type and time range.

A useful operational scenario is a FortiGate that appears in the Fabric topology but has no recent logs in FortiAnalyzer. Do not re-authorize repeatedly. First confirm whether the device is already authorized; then follow a known event through the log-delivery path. Re-authorization will not repair an OFTP transport or log-type setting.

Dependencies and scale considerations

Use a stable authorization address reachable from all intended Fabric members. If management and logging networks are separated, ensure the FortiGate reaches the correct service interface and that return traffic is permitted. In a FortiAnalyzer HA or failover design, verify the configured authorization endpoint remains reachable after role change. After adding many devices, validate ADOM/device mappings and log ingestion separately; an authorized-device count is not a data-quality metric.

Primary sources: FortiAnalyzer Adding a FortiGate using Security Fabric authorization; FortiOS Configuring FortiAnalyzer. No directly matching Community scenario was verified in the rolling 30-day window.

LESSON 04 · FortiSwitch

IGMP snooping, proxy, querier and multicast membership

Editable draw.ioStandalone SVG

IGMP snooping prevents a Layer-2 VLAN from treating every multicast stream like broadcast. The FortiSwitch observes IGMP membership reports exchanged by hosts and routers, learns which switch ports have listeners for each multicast group, and forwards a stream only to interested ports plus the required multicast-router (mRouter) ports. It does not route multicast between VLANs; it constrains L2 replication within the VLAN.

Membership, querier and mRouter roles

When a receiver joins a group, its IGMP report is visible to the switch. Snooping records the VLAN, group and port. Membership is time-bounded: queries refresh listener state and the aging timer removes stale entries when reports stop. A querier is therefore important when no upstream multicast router is sending queries. The switch can run a per-VLAN querier; the configured querier address participates in querier selection and the IGMP version determines which reports it processes. mRouter ports identify the direction toward multicast routing infrastructure and are eligible to receive multicast even when no local host membership exists.

FortiSwitch uses global IGMP-snooping settings by default. For a per-switch override, enable local-override under the managed switch's IGMP snooping configuration, then configure the VLAN. The VLAN can use the global proxy behavior, enable/disable proxy, and enable a querier with an address and IGMP version.

Configuration example (FortiGate-managed FortiSwitch)

config switch-controller igmp-snooping
    set aging-time 300
    set flood-unknown-multicast disable
    set query-interval 125
end

config switch-controller managed-switch
    edit "S524DF4K15000024"
        config igmp-snooping
            set local-override enable
            config vlans
                edit "vlan100"
                    set proxy disable
                    set querier enable
                    set querier-addr 192.0.2.1
                    set version 3
                next
            end
        end
    next
end

The documented ranges are 15–3600 seconds for aging-time and 10–1200 seconds for query-interval. The default aging time is 300 seconds and the default query interval is 125 seconds. Keep aging greater than query interval; otherwise a listener entry can expire before the next expected refresh.

Unknown multicast is a deliberate policy choice

With flood-unknown-multicast disabled (the default), unregistered multicast is forwarded only to mRouter ports. If enabled, it is flooded to all ports in the VLAN. Enabling flood can be a temporary diagnostic test, but it broadens the replication domain and can create a multicast storm. Do not leave it enabled merely because it makes an IPTV stream appear to work; identify why the listener or router state was not learned.

Verification

  • get switch igmp-snooping group shows learned multicast groups, VLANs, ports, querier state and aging. It proves the switch learned membership, not that the source is transmitting the expected group.
  • Confirm the receiver actually sends an IGMP report for the group. If the group table is empty, capture/inspect the report path before changing flooding.
  • Check the querier is active on the correct VLAN and that its IGMP version is compatible with the hosts. A v3 report ignored by a v2 querier is a protocol mismatch, not necessarily a VLAN or multicast-routing failure.
  • Check mRouter ports and inter-switch links. A correct access-switch table can still fail if membership or mRouter state is not propagated across the FortiLink/ISL topology.

Operational troubleshooting

For IPTV, place the source and receiver in the same test VLAN and compare group learning on the access and core switches. If the receiver's join is visible at the access switch but not upstream, trace the ISL and report-flooding behavior. If membership is correct everywhere but the stream is absent, check the sender's destination group and multicast source rather than turning on unknown-multicast flooding. If flooding is used as a temporary isolation test, restore the intended setting immediately after the comparison.

Primary source: FortiSwitch 8.0 Configuring IGMP-snooping settings. No matching Community article was published in the rolling 30-day window; older multicast troubleshooting material was not treated as recent evidence.

LESSON 05 · FortiAP/Wireless

Airtime fairness: per-SSID downlink scheduling weights

Editable draw.ioStandalone SVG

Wi-Fi airtime is the scarce resource. A low-rate or distant client can consume a disproportionate amount of transmit time for the same number of payload bytes, reducing the service available to other SSIDs. FortiAP airtime fairness (ATF) assigns a weight to each virtual AP (VAP/SSID) and schedules AP-to-client data transmission according to those weights. It is not a per-client byte-rate cap and it does not control the client-to-AP direction.

What the scheduler actually controls

ATF applies to downlink data only, on supported 2.4 GHz and 5 GHz radios. It is configured per SSID, and can be used with Bridge, Tunnel or Mesh VAPs and Open, PSK or Enterprise authentication. It does not allocate airtime for control or management frames. This boundary matters: a user may see no change in uplink throughput, association time or management-frame behavior even when the downlink ATF scheduler is working exactly as designed.

The weight is a relative share among the VAPs participating in that radio's ATF schedule. Fortinet's example assigns 80 to one SSID and 20 to another. Under simultaneous downlink load, the first VAP receives roughly four times the scheduled data airtime of the second. It does not promise four times the application throughput: RF rate, retries, aggregation, contention, client capability and application demand still affect bytes delivered per unit of airtime.

Configuration

Enable Advanced Wireless Features, set the SSID's airtime weight, then enable ATF on the radio in the FortiAP profile. The profile must include the intended VAPs; a configured VAP weight is not enough if the radio is not running ATF or the VAP is not attached to that radio.

config wireless-controller vap
    edit "staff"
        set atf-weight 80
        set ssid "staff"
        set security wpa2-only-enterprise
    next
    edit "guest"
        set atf-weight 20
        set ssid "guest"
        set security wpa2-only-personal
    next
end

config wireless-controller wtp-profile
    edit "FAP_ATF"
        config radio-2
            set airtime-fairness enable
            set vap-all disable
            set vaps "staff" "guest"
        end
    next
end

Use model-appropriate radio/profile settings; the example is a configuration pattern, not a universal radio number. The FortiAP guide shows the radio-level airtime-fairness enable command and per-VAP atf-weight.

Verification with feature-specific evidence

  • On the AP, cw_diag -c atf shows whether ATF is enabled and the configured/applied weights for each WLAN. A mismatch between configured and applied values points to profile/VAP application, not client RF quality.
  • wlanconfig wlan10 showatfinfo displays the ATF table and airtime percentages. This proves the scheduler is assigning airtime; it does not prove the application will achieve a matching throughput ratio.
  • cw_diag -d vap <vap-mac> exposes VAP transmit counters. Compare counters over the same controlled interval while both SSIDs have downlink demand. Raw byte totals from different client populations or unequal demand are not a fair ATF test.

Operational scenario

In a warehouse, a slow scanner on a distant AP consumes airtime and users on a nearby high-rate SSID report poor download performance. First compare RSSI, PHY rate and retry counters to establish the RF problem. If the design intentionally gives employee and guest SSIDs different service shares, configure ATF weights on both VAPs and the radio. Generate simultaneous downlink load and inspect the applied ATF table. If the issue is uplink-heavy scanner telemetry, ATF is not the control that will fix it; use RF design, client rate policy or application controls instead.

Dependencies and caveats

ATF is radio-specific and platform-dependent. Verify that the FortiAP model and radio support the feature and that the AP has received the intended WTP profile. Do not interpret a 80/20 weight as a guaranteed 80/20 Mbps split. If one SSID has no queued downlink data, its unused airtime may be available to other traffic; the feature is a scheduling weight under demand, not a hard reservation. Measure with comparable traffic and a stable RF environment.

Primary sources: FortiAP Airtime fairness; FortiAP 8.0 Advanced SSID options. No directly matching Community scenario was verified in the rolling 30-day window.

LESSON 06 · FortiNAC

Guest self-registration: sponsor approval, account templates and expiry

Editable draw.ioStandalone SVG

Guest self-registration lets a visitor request temporary access from their own device instead of waiting for an administrator to create an account. FortiNAC keeps the endpoint isolated while the request is pending, routes the request to a sponsor or request pool, creates a guest account from a template after approval, delivers credentials, and then moves the endpoint through the normal guest login and access process. The important distinction is that approval, account creation and network release are separate state transitions.

End-to-end transaction

  1. The endpoint connects and is placed in the isolation path. When the user opens a browser, FortiNAC redirects to the captive registration page.
  2. The visitor chooses Self Registration, completes the form and submits a request. The portal can require the sponsor's email address or route requests to configured sponsors/request pools.
  3. The request remains pending until an authorized sponsor or administrator approves or denies it. The default request timeout is 20 minutes; an unanswered request expires.
  4. On approval, FortiNAC creates the guest account using the selected visitor template. The template's account duration determines when the account expires.
  5. Credentials can be shown in the browser or delivered by email/SMS, depending on portal configuration. The guest must complete the login flow. FortiNAC then reconfigures access and the endpoint moves to the production/guest network.

A sponsor is not just an email address. The sponsor must exist in FortiNAC as an administrator and have the Guest Self Registration administrator profile or a Guest Manager profile that permits request processing. Directory groups can be used to assign these profiles at scale, but the resulting administrator and permission mapping must still be valid.

Required objects

Create a guest template with Visitor Type set to Self-Registered Guest and define Account Duration. The default GuestSelfRegistration template can be used or replaced with a purpose-built template. All self-registered guests use the template selected in the Portal Content Editor under Registration > Self Registration Login. Configure the portal's sponsor routing and the request approval behavior. If sponsor approval is not required, users can create accounts directly from the portal using the selected template; that is a materially different trust model from sponsor-mediated access.

Create an administrator profile specifically for sponsors. FortiNAC's guide notes that profile permissions are dependent on one another, so do not grant broad Manager access merely to allow approval. Give sponsors only the host/port and guest-request permissions required for their role. Ensure the sponsor administrator has a valid email address if email notifications and approval links are used.

Evidence and troubleshooting

  • Check the portal request record and its pending/expired/approved state. A visible request proves form submission, not sponsor delivery or approval.
  • Check the sponsor administrator record, profile permissions and email address. If the request is routed to a sponsor who is not a valid administrator with the correct profile, the notification or approval path can fail.
  • Inspect the created guest account: visitor type, template and expiration timestamp. Approval without an account record indicates a template/account creation problem.
  • After the guest logs in, inspect the host's network state and VLAN/port enforcement. A successful approval and credential delivery do not prove that the switch/AP moved the endpoint out of isolation.

In a high-availability deployment where redundant servers use different subnets or addresses, configure the settings that generate correct HTTPS links in sponsor emails. Otherwise the sponsor may receive a link to an unreachable administrative address even though the request was created correctly.

Operational scenario

A visitor submits a request, receives a waiting page, and then reports that the sponsor never received the email. Do not change the isolation VLAN first. Confirm the request exists and has not expired, then verify the sponsor is an administrator with the Guest Self Registration profile, has an email address, and is included in the portal's sponsor routing. If the sponsor approves but the guest remains isolated, move to the next boundary: template account creation, guest login, and switch/AP reconfiguration.

Primary sources: FortiNAC 9.4 Guest self registration; Add a guest self registration profile. No matching Community article was published in the rolling 30-day window; older sponsor-email tips were not presented as recent.

LESSON 07 · FortiNAC-F

Manual LDAP user import and explicit host association

Editable draw.ioStandalone SVG

FortiNAC-F separates directory identity from endpoint inventory. An LDAP user record can be read and created in FortiNAC without importing the entire LDAP group hierarchy, but the user is not automatically associated with the correct endpoint. That association is a separate relationship in the Hosts view. This distinction is useful when policy, host ownership or event correlation depends on knowing which directory user is tied to a particular MAC/IP host record.

Directory read versus local record versus host link

The prerequisite is an existing LDAP connection that can read the user's distinguished name (DN). The October 8, 2026 Community troubleshooting tip explicitly notes that there is no need to import the user group just to read the user; FortiNAC must be able to read the user DN. In Users & Hosts > User Accounts, select Add New and enter the directory username. After leaving the field, FortiNAC should display Loaded from Directory. That message is evidence that the directory lookup populated the user record. Assign the FortiNAC role and save.

Next, open Users & Hosts > Hosts, edit the endpoint host record, and associate the imported user. Do not assume that importing the user created a host association. The directory user and the endpoint host are separate inventory objects. The host may already exist from MAC learning, DHCP, switch polling or another discovery source; the user association ties the identity to that device record.

Operational sequence

  1. Verify the LDAP server connection and the account's ability to read the target user DN.
  2. Search for the exact directory username and use Add New in User Accounts.
  3. Wait for the Loaded from Directory indication; confirm the username and directory attributes populated correctly.
  4. Assign the appropriate FortiNAC role. A directory user record without a role may exist but lack the expected permissions or policy context.
  5. Find the correct host record by MAC/hostname/IP and explicitly associate the user with that host.
  6. Re-evaluate the endpoint policy and identity context. Confirm the intended user-to-host relationship is visible before troubleshooting downstream access.

What proves each step

  • LDAP connection test: proves FortiNAC can contact and bind to the directory. It does not prove a particular user's DN is readable.
  • Loaded from Directory: proves the user lookup returned directory data. It does not prove a host association or access decision.
  • User record and role: prove FortiNAC has a local identity object and role assignment. They do not prove the correct endpoint is linked.
  • Host association: proves the selected user is related to that host record. It does not prove the host is currently on the expected switch port or has passed endpoint compliance.

Common failure patterns

If the lookup does not show Loaded from Directory, confirm the exact user ID, base DN/search scope, LDAP bind account read permissions and directory server reachability. Do not import a large group as a workaround if the actual issue is that the user DN cannot be read. If the user record appears but the policy still sees an unknown user, inspect the host association and verify that the host MAC corresponds to the endpoint in question. A duplicate or stale host record can make the association look correct while the active endpoint is using a different record.

When a directory synchronization job is also configured, understand which fields are directory-owned and which are locally maintained. A later sync can refresh directory attributes; manual changes to a directory-owned field may be overwritten. Keep the role and host-association ownership clear in the operating procedure.

Recent scenario

The October 8 Community article demonstrates the exact boundary: the user can be imported by reading the LDAP DN without importing the group, but the engineer must then open the host record and assign the user. The lesson is not “LDAP is working” but “directory lookup, FortiNAC user creation and endpoint association are three independently verifiable operations.”

Primary source: FortiNAC-F 7.6 User Accounts. Scenario: October 8, 2026 Community tip: manually import LDAP user and assign host.

LESSON 08 · FortiAuthenticator

EAP-TTLS two-factor authentication: the 8.0.4 challenge-flow boundary

Editable draw.ioStandalone SVG

EAP-TTLS creates a TLS-protected tunnel between the supplicant and the RADIUS server, then carries an inner authentication method through that tunnel. FortiAuthenticator can terminate EAP-TTLS itself or proxy EAP to a remote RADIUS server; the distinction matters because the local EAP settings apply only to sessions terminated on FortiAuthenticator. A client-side error such as EAPPasswordError does not identify whether the password, token, realm, RADIUS policy or EAP tunnel failed.

The version boundary is the lesson

FortiAuthenticator 8.0.2 documentation states that challenge-based EAP-TTLS 2FA is not supported and describes password-plus-OTP concatenation for that release family. In that legacy flow, the client does not receive a separate OTP challenge prompt; the user enters the directory password immediately followed by the current OTP in the same password field. Email/SMS OTP cannot be used in this concatenation model when the token is only delivered after the first credential step.

That behavior changed. Fortinet's Community technical tip updated in October 2026 states that EAP-TTLS 2FA support is available from FortiAuthenticator 8.0.4 and that the legacy concatenation workaround should not be followed on 8.0.4. Treat this as a release-specific compatibility boundary: do not copy a workaround from an 8.0.2 guide into an 8.0.4 deployment without checking the installed build and current policy options. The exact client and FortiOS minimum versions also matter; the Community tip lists FortiOS 7.4.9/7.6.1 and FortiClient Windows 7.4.4 for its described LDAP EAP-TTLS MFA path.

Authentication path

  1. FortiClient starts IKEv2 and negotiates EAP. The FortiGate acts as the RADIUS client; FortiAuthenticator is the RADIUS server when configured that way.
  2. The EAP-TTLS outer method establishes TLS using the FortiAuthenticator EAP server certificate. The supplicant must trust the correct issuing CA and validate the server identity.
  3. The inner method carries user credentials. The FortiAuthenticator RADIUS policy selects the client, EAP type, realm and identity source; local EAP settings do not apply if the EAP session is proxied to another RADIUS server.
  4. FortiAuthenticator validates the directory password and the configured second factor according to the installed version's supported challenge behavior, then returns RADIUS Accept or Reject.

Configuration and evidence

On FortiAuthenticator, verify the RADIUS client entry for the FortiGate, the matching RADIUS policy, the selected realm/LDAP identity source, the accepted EAP method and the EAP server certificate. For EAP-TTLS, the certificate configuration is under Authentication > RADIUS Service > EAP. Confirm the session is terminated locally before troubleshooting those local EAP settings.

  • Correlate the FortiClient attempt timestamp with the FortiAuthenticator RADIUS log. A missing-token error points to the second-factor step, not necessarily the LDAP bind.
  • Run an authentication test against the same identity source, but remember that a direct LDAP test does not prove the EAP-TTLS supplicant sent the expected inner credential.
  • Check the RADIUS policy actually selected for the FortiGate client. A correct policy in the list may not match if the client source IP, authentication type or realm differs.
  • Confirm Access-Accept/Reject and the matching IKEv2 session result. A successful RADIUS result proves authentication; the VPN still needs the expected authorization/group mapping and tunnel policy.

Operational scenario

An IKEv2 user sees EAPPasswordError. LDAP credentials work in a direct test, FortiToken is assigned, and the RADIUS policy is present. On a pre-8.0.4 FortiAuthenticator build, the client may have submitted only the password because no second prompt was offered; the documented workaround is password+OTP concatenation. On 8.0.4, do not keep concatenating by habit: verify the new EAP-TTLS 2FA support and policy behavior. The Community thread from October 29–30, 2026 illustrates how an error can persist despite apparently correct LDAP, token and policy objects.

Dependencies and caveats

Do not confuse EAP-TTLS with EAP-MSCHAPv2. FortiAuthenticator has a separate setting for OTP with EAP-MSCHAPv2/FortiClient; that is not proof that EAP-TTLS is configured correctly. Confirm FortiOS, FortiClient and FortiAuthenticator versions as a set, then test with a token type supported by the chosen flow. A server certificate trust failure can prevent the inner credential exchange before LDAP is even reached.

Primary source: FortiAuthenticator 8.0.2 EAP documentation. Version update/scenario: October 29–30, 2026 EAPPasswordError discussion; Fortinet EAP-TTLS/PAP 2FA technical tip with 8.0.4 boundary.

LESSON 09 · FortiPAM

Certificate-based SSH authentication for SSH-key secrets

Editable draw.ioStandalone SVG

FortiPAM can store an SSH key as a secret using the FortiProduct (SSH Key) or Unix Account (SSH Key) template. The public-key field supports two modes: a standard public key, or a public key with a certificate. The latter lets the SSH authentication use a certificate-backed key and exposes certificate validity/expiry as an operational control rather than treating the credential as an unbounded raw key.

Secret object and authentication boundary

When creating the secret, select the SSH-key template and choose Public key with certificate in the Public-key dropdown. FortiPAM displays certificate details through the eye icon. The Secret Details page shows the certificate validity period and status. Fortinet documents this mode as improving SSH authentication security by controlling certificate expiry. It also supports email alerts for expiring certificates through the Certificate tab in Email Alert Settings.

Do not confuse this with the separate Certificate secret template. That template stores a certificate file and includes private-key and passphrase fields. The SSH-key template's certificate option is part of the SSH authentication credential; the Certificate template is a general secret object for storing a certificate artifact. They have different launch/use semantics.

Configuration and lifecycle

  1. Create a secret using the correct SSH-key template for the target type.
  2. Choose Public key with certificate rather than Standard public key, and populate the required key/certificate fields from the approved SSH CA process.
  3. Open the secret details and verify the certificate subject/validity/status. Confirm that the certificate is not expired or not-yet-valid.
  4. Configure the appropriate launcher for the target and associate the secret with the intended user/group/policy.
  5. Configure the Certificate email alert settings so the operations team is notified before expiry. Validate recipient routing with a test alert or controlled short-lived certificate in a lab.

The FortiPAM object proves that the credential is stored and its validity is visible. It does not prove that the target SSH daemon trusts the signing CA, accepts the certificate principal, or permits the requested account. The target-side SSH certificate-authority trust and principal policy must match the certificate that FortiPAM presents.

Verification

  • Inspect the secret template and Public-key selection. A standard public key will not provide the certificate validity lifecycle described here.
  • Open the certificate details and check the validity interval and status. This proves FortiPAM can parse the certificate metadata; it does not prove target acceptance.
  • Launch a session to a controlled target and correlate FortiPAM launcher output with the target's SSH authentication log. A launcher failure can be caused by target trust/principal policy even when the secret is valid.
  • Check the certificate alert configuration and delivery evidence. A certificate status shown in the secret is not proof that an alert recipient has been configured.

Operational failure analysis

A team rotates an SSH CA certificate and one managed target begins rejecting launches. First determine whether FortiPAM still shows the old certificate or a new certificate with a future validity date. Next compare the presented certificate's CA and principal with the target's trusted CA/principals configuration. Finally verify the launcher uses the intended secret revision. Do not regenerate unrelated passwords or disable SSH certificate checks: the problem may be trust-chain or principal mapping, not credential retrieval.

Dependencies and caveats

Certificate expiry is only useful if the target enforces certificate validity and the notification path is monitored. Set alert lead time before the earliest target-side expiration and ensure the secret's owning team can rotate both the FortiPAM object and the target trust configuration. If a certificate is revoked before its expiry, the target's revocation/trust behavior must be checked separately; the FortiPAM expiry display is not a revocation-status service.

Primary source: FortiPAM 1.9 Creating a secret. No matching Community scenario was verified in the rolling 30-day window.

LESSON 10 · FortiSIEM

External authentication profiles, user binding and organization scope

Editable draw.ioStandalone SVG

FortiSIEM external authentication moves credential validation to an identity provider while keeping FortiSIEM's own user, role and organization model in the authorization path. The supported integrations described in the 7.5.0 User Guide include LDAP/LDAPS/LDAPTLS, Azure AD, Okta, Duo and SAML providers; RADIUS is also used in the documented FortiAuthenticator integration examples. A successful provider connection is only one part of the login transaction.

Profile, user and tenant are separate objects

Create an External Authentication profile at Admin > Settings > General > External Authentication. The profile stores protocol-specific settings and an Organization scope. For LDAP/LDAPS/LDAPTLS, set the server host/IP and port, optionally enable certificate checking, and set a Base DN pattern if FortiSIEM cannot discover it or a manually created user needs an explicit DN pattern. The documentation notes that certificate checking validates the LDAP server certificate CN or subjectAltName against the host/IP entered in the profile; a self-signed certificate will fail that validation.

For Duo, the profile uses the API hostname and Integration Key. For SAML, FortiSIEM stores the IdP issuer and signing certificate, then maps the IdP's user, organization and role values to FortiSIEM values. User matching is exact and case-sensitive. If the SAML response does not include a role, create the FortiSIEM user in CMDB and assign the role there. A user who authenticates at the IdP but is absent from the FortiSIEM user model or mapped to the wrong organization can still fail to receive the expected access.

Authentication transaction

  1. FortiSIEM identifies the local user record and the external authentication profile bound to it.
  2. The selected profile contacts the configured LDAP/RADIUS/Okta/Duo/SAML provider and validates the credential or assertion.
  3. FortiSIEM maps the authenticated identity to the configured user and Organization. For SAML, the exact username, role and organization mapping must match the assertion attributes.
  4. FortiSIEM applies the user's role and tenant scope to determine which administrative functions and data are visible.

When multiple authentication profiles are associated with a user, FortiSIEM contacts servers one by one until a connection is successful. Once a server is contacted, an authentication failure ends the process; FortiSIEM does not necessarily continue to the next profile as a credential fallback. Profile order and provider reachability therefore matter.

Configuration and evidence

  • Use the profile's Test function with a known account. It proves that the provider settings can authenticate that credential; it does not prove the user record is bound to the profile or has the right role.
  • For LDAPS/LDAPTLS with Check Certificate enabled, validate the certificate chain and CN/SAN against the exact hostname or IP configured in the profile. If the certificate is issued to ldap01.example.com, using a raw IP in the profile can cause a name mismatch.
  • For a SAML profile, inspect the assertion's NameIdentifier/custom user attribute, organization and role. Confirm case-sensitive user match and explicit FortiSIEM role/organization mapping.
  • After login, verify the user sees the intended organization and role-specific pages. Authentication success without the correct tenant view is an authorization mapping problem.

Operational scenario

After a directory certificate renewal, one FortiSIEM user can no longer log in, while a second user with a different profile still works. Check the failed user's profile first: if certificate checking is enabled, compare the profile's LDAP host value to the certificate CN/SAN and trust chain. Then test the profile. If the test succeeds but the user still fails, inspect the user's Mode, Authentication Profile binding, Organization and Role in CMDB. Do not reset the directory password when the failure is a local profile binding or tenant mapping.

Security and scale considerations

Use a dedicated profile per provider/tenant where possible, and keep global/System scope distinct from a specific organization. SAML mappings should be explicit and case-sensitive. Protect signing certificates and rotate them with overlap so the IdP and FortiSIEM trust the same active certificate during cutover. In a multi-tenant deployment, a broad System profile may allow users from multiple organizations to authenticate, but the mapped role and organization still determine what each user can see.

Primary source: FortiSIEM 7.5.0 External Authentication Settings; FortiSIEM 7.5.1 Setting Up External Authentication. No matching Community scenario was verified in the rolling 30-day window.

LESSON 11 · FortiSASE

External threat feeds synchronized into Web Filter and DNS Filter

Editable draw.ioStandalone SVG

FortiSASE can consume external threat feeds that are defined in FortiManager and referenced by Web Filter or DNS Filter profiles. The critical rule is that a feed object is not automatically synchronized just because it exists in the FortiManager Threat Feeds list. The feed must be associated with a supported Web Filter or DNS Filter profile, and the profile/group must be part of the central-management synchronization. HTTP Basic Authentication credentials are a separate local configuration step in FortiSASE.

Feed types and policy binding

The documented workflow covers three use cases: an FQDN feed referenced by Web Filter, a domain-name feed referenced by DNS Filter, and an external-host feed used in the DNS Filter configuration context. For an FQDN feed, create a FortiGuard Category threat-feed object and reference its remote category in a Web Filter profile. For a domain feed, create a Domain Name feed and reference the corresponding remote category in a DNS Filter profile. The profile group binds the security profile to the policy context that is synchronized to FortiSASE.

The feed data is therefore consumed through a chain: external URL → FortiManager threat-feed object → Web/DNS profile remote category → profile group → FortiSASE central-management sync → FortiSASE feed cache and enforcement. If any link is missing, the feed card may exist without being used by a traffic policy.

Synchronization constraints

Fortinet documents two important limitations. First, only external feeds that are defined and then associated with Web Filter or DNS Filter profiles are synchronized. Second, if the feed requires HTTP Basic Authentication, the username/password configured in FortiManager are not synchronized; after the referenced feed arrives in FortiSASE, configure those credentials directly on the FortiSASE external-feed object. Do not diagnose a 401 response by repeatedly reinstalling the profile group if the missing credentials are local to FortiSASE.

The 26.1.107 guide states that a maximum of 21 DNS Filter Domain and Web Filter FQDN feeds are supported using category IDs 201–221 inclusive. External-host feeds are not included in that maximum. Plan category IDs centrally and avoid assuming that an external-host list consumes the same category namespace.

Verification sequence

  1. In FortiManager, confirm the feed URL/type and category, then open the Web Filter or DNS Filter profile and verify the matching remote category is referenced with the intended action (Monitor, Block or another supported action).
  2. Verify the profile group includes the correct Web/DNS profile and is in the central-management synchronization scope.
  3. In FortiSASE, open Configuration > External Feeds, inspect the feed card and use View entries to confirm that entries arrived.
  4. Open Analytics > Central Management Synchronizations, select the latest sync log and inspect its details. This proves the profile/objects were synchronized; it does not prove that the target traffic is matching the profile.
  5. Run a controlled URL or DNS query that is known to be in the feed and confirm the policy/profile action in the appropriate security log.

Failure isolation

If the feed object is visible in FortiManager but absent in FortiSASE, check profile association first. If the feed card exists but has no entries, check URL reachability, format, refresh and Basic Authentication credentials in FortiSASE. If entries are present but traffic is allowed, inspect the profile group, policy binding and remote-category action. A feed entry is intelligence data; enforcement requires the right profile and traffic path.

Operational design

Use separate feeds for domains/FQDNs and host IPs because they bind to different filter mechanisms. Keep the feed owner, update cadence, source format and expiry behavior documented. During a feed-source outage, determine whether the last successful cache remains usable in the current release and define the desired fail-open/fail-closed behavior rather than assuming that the external URL is queried on every user session.

Primary source: FortiSASE 26.1.107 Configuring external feeds with Web Filter and DNS Filter profiles. No matching Community scenario was verified in the rolling 30-day window.

LESSON 12 · Secure SD-WAN

Underlay-bandwidth-aware load balancing across overlay members

Editable draw.ioStandalone SVG

When several IPsec overlays share a smaller number of physical WAN links, measuring each overlay's available bandwidth independently can overstate the capacity available to all tunnels combined. FortiOS 8.0 adds a bandwidth-type selector to SD-WAN load-balance services so the hash algorithm can evaluate either each overlay's available bandwidth or the shared physical underlay bandwidth. This is a path-selection input; it is not traffic shaping and it does not split an individual packet across tunnels.

Members and shared capacity

Model the physical WAN interfaces as underlay members and the IPsec tunnels as overlay members. Several overlay members can point to the same physical underlay. A load-balance service selects among eligible priority members using a hash mode. inbandwidth chooses the member with the most available incoming bandwidth, outbandwidth uses outgoing bandwidth, and bibandwidth uses both directions. The new bandwidth-type value determines whether that available-bandwidth calculation uses the overlay member's own capacity or the underlying physical interface's shared capacity. The default is overlay.

If two tunnels ride the same 100-Mbps WAN, overlay-based accounting can make both appear to have capacity independently. Underlay mode makes those tunnels compete against the shared physical link estimate, so traffic is directed toward overlays associated with the underlay that has more remaining capacity. This is especially useful when multiple tunnels exist for different hubs or destinations but share the same ISP circuit.

Configuration pattern

config system sdwan
    config service
        edit 1
            set load-balance enable
            set mode sla
            set hash-mode bibandwidth
            set bandwidth-type underlay
            set dst "all"
            set src "CORP_LAN"
            set priority-members 3 4 5 6
        next
    end
end

The full Fortinet example also creates underlay and overlay zones, adds physical interfaces to the underlay zone, adds IPsec tunnels to the overlay zone, configures a health check and associates its SLA with the service. The member bandwidth estimates must be meaningful; a hash cannot make a correct capacity decision from missing or unrealistic bandwidth data.

Verification

Run diagnose sys sdwan service4 for the service and inspect the member list. Fortinet's example shows bibandwidth values for each overlay member. With the default overlay mode, two tunnels sharing a physical link can each show values based on their own overlay estimates. After setting bandwidth-type underlay, the available values reflect the shared underlay capacity and the overlay members associated with the better-capacity underlay are preferred. The tie-break is configuration order in the example; two equal values do not imply packet striping.

Use controlled traffic to confirm the service's member selection and compare the result with the underlay association. A tunnel marked alive proves it passed the health check; it does not prove the service used the intended bandwidth type. A service output showing a member as selected proves eligibility/selection for that service, not that every existing session immediately migrates.

Operational scenario

A branch has two ISP circuits and four hub tunnels. Two tunnels use WAN1 and two use WAN2. WAN1 is congested, but overlay-only bandwidth accounting makes the two WAN1 tunnels look individually healthy. Enable load balancing with hash-mode bibandwidth and bandwidth-type underlay, then inspect diagnose sys sdwan service4. If the values still look equal, verify the physical-member bandwidth estimates and that each overlay is associated with the intended underlay. Do not change SLA latency thresholds to solve a capacity-accounting problem.

Dependencies and caveats

This feature is available for load-balance services using inbandwidth, outbandwidth or bibandwidth. It is not a replacement for SLA eligibility: members must still meet the service's health/SLA requirements. Keep the service's source/destination scope and priority member list correct. If the deployment has dynamic overlays, verify that the underlay association remains correct after tunnel rekey or topology change. Use QoS/shaping when the requirement is to prioritize voice or cap a class; use underlay bandwidth mode when the requirement is to steer new sessions based on shared link capacity.

Primary sources: FortiOS 8.0 Use underlay bandwidth to make traffic steering decisions; FortiOS 8.0 SD-WAN underlay bandwidth feature. No matching Community scenario was verified in the rolling 30-day window.
