FortiGate · Lesson 1

Dynamic BGP learning of ISDB reputation IPs

Purpose and design boundary

FortiOS 8.0 can use FortiGuard Internet Service Database (ISDB) reputation categories as BGP network sources. The documented categories are Botnet-C&C.Server and Spam-Spamming.Server. The point is to distribute changing reputation IPs through the routing control plane so adjacent routers can steer them to a sinkhole, scrubbing path, or discard next hop. This is different from a firewall policy that locally denies a session: the feature originates reachability information; downstream routers decide what to do with it.

Mechanics and configuration

ISDB maintains category membership. A BGP network entry references the category by name instead of a manually maintained prefix. FortiGate translates the current members into BGP NLRI and sends ordinary BGP UPDATE messages to peers. The receiving peer installs the accepted routes subject to its normal import policy, best-path selection, next-hop resolution, and RIB/FIB programming. The official example shows the category attached directly under config router bgp:

config router bgp
    set as 65412
    set router-id 2.2.2.2
    config neighbor
        edit "3.3.3.3"
            set remote-as 65412
            set route-map-out "reputation-export"
        next
    end
    config network
        edit 10
            set internet-service-name "Botnet-C&C.Server"
        next
        edit 20
            set internet-service-name "Spam-Spamming.Server"
        next
    end
end

The Fortinet lab example also sets network-import-check disable. Treat that as an explicit design choice, not a harmless default: understand the route-origination check before copying it into production. A route-map on the neighbor is the right place to constrain where reputation routes are exported, tag them, or prepend the AS path.

Evidence and what it proves

On the FortiGate, diagnose internet-service id <id> exposes the category members and reputation metadata; the documented sample includes individual host IPs with botnet/reputation fields. On a peer, get router info routing-table bgp should show the received host routes, commonly /32 entries, with the FortiGate as next hop. The peer's advertised/received-routes view proves the BGP exchange; a route-map counter proves policy matching. None of these proves that traffic is blocked. To prove enforcement, inspect the downstream route action and test forwarding from a controlled source.

Operational failure analysis

If the peer sees no routes, split the problem into four boundaries: ISDB category availability, the BGP network statement, neighbor/session state, and outbound route policy. Verify the category name exactly, confirm the peer is established, then inspect whether the export map rejects the prefixes or the peer applies an inbound filter. If the route exists but traffic still reaches the destination, the route may point to an ordinary forwarding next hop rather than a discard/scrubbing path. If traffic is blackholed unexpectedly, check prefix scope and route preference before widening the export.

Dependencies and scale

ISDB updates are upstream data; BGP is the distribution mechanism. Route volume can grow with the reputation feed, so apply prefix limits, route filters, and a deliberate propagation domain. Do not redistribute the categories indiscriminately into every tenant or external peer. The operational invariant is that threat-intelligence membership, BGP advertisement, and data-plane enforcement are three separately verifiable stages.

FortiManager · Lesson 2

Importing PDE-protected password-type objects

Why this boundary matters

Private Data Encryption (PDE) protects passwords and keys on supported FortiGate hardware using a Trusted Platform Module (TPM). FortiOS 7.6.1 and later can generate the PDE key automatically; earlier releases may use a manually configured key. FortiManager 8.0 changes an important management boundary: it can import objects containing password-type attributes from a PDE-enabled FortiGate, but it does not silently infer the protected value. The Import Wizard makes the operator explicitly decide how each object secret is represented in the ADOM.

Import transaction

When a new password-type object is encountered, the Import Wizard prompts for the password used by that object. When the object already exists in the ADOM, the wizard presents the existing object and offers two materially different choices: enter a new password, or leave the field blank to keep the current FortiGate password. The blank action is not the same as clearing a password. It preserves the device's current value while allowing the rest of the object/configuration to be reconciled. This is especially important for firewall users, credentials, and other objects referenced by policy or service configuration.

A safe sequence is: enable PDE on the FortiGate; add the device to Device Manager; retrieve/import configuration; review each password-type prompt; reconcile the ADOM objects; preview and install only after references are complete. FortiManager does not enable or disable private-data-encryption on the managed FortiGate. That change is made on the FortiGate itself. If PDE is changed on an already managed device, retrieve the device configuration again so the manager's state is refreshed.

Important exceptions

FortiManager cannot create NAT or transparent VDOMs for PDE-enabled devices. Configure those VDOM settings directly on the FortiGate and then perform a retrieve operation. If NAT/transparent VDOMs are required on a fresh deployment, create the multi-VDOM mode and required VDOMs on the FortiGate before enabling PDE and onboarding it. The manager can then handle the supported configuration and installation work without pretending that the unsupported VDOM operation is centrally available.

Verification boundaries

Three separate outcomes must be checked. First, the import wizard must complete with an intentional decision for every password-type object. Second, the ADOM database must contain the expected object and references; an object omitted from import can cause a policy package to be incomplete. Third, the installed FortiGate must retain the expected functional behavior after installation. A successful retrieve does not prove that every secret was entered correctly; a successful install does not prove that an application using the credential can authenticate.

Upgrade and troubleshooting

FortiManager 8.0 supports PDE keys manually configured in FortiOS 7.6.0 and earlier and randomly generated in 7.6.1 and later. Existing managed devices continue to be managed subject to the object and VDOM exceptions. If an import appears to omit a password-bearing object, inspect the wizard prompts and ADOM object references before installing. If NAT/transparent VDOM state is missing, do not repeatedly retry an unsupported manager operation: configure it on the device and retrieve. The core operational lesson is to treat secret import as an explicit reconciliation step, not a normal text-field merge.

FortiAnalyzer · Lesson 3

Nested Fabric Groups for administrator RBAC

Purpose

FortiAnalyzer Fabric Groups provide a visibility scope over Fabric members and selected ADOMs. In 8.0, a Fabric Group can also contain other Fabric Groups. That nesting solves a practical RBAC problem: one administrator can be assigned a parent group that aggregates two or more otherwise separate operational scopes, without manually flattening every member and ADOM into a new list each time.

Object relationships

Think of the Fabric supervisor as the control point. Group_1 and Group_2 are leaf groups; each contains the intended Fabric members and/or ADOMs. Group_3 is created with Group_1 and Group_2 as members. An administrator is then assigned Group_3 under System Settings > Administrators. The administrator's Fabric scope is the transitive membership of the parent group. The documented workflow is explicit: create the parent in System Settings > Fabric Management > Fabric Groups, add the existing groups as members, then assign the parent group to the administrator.

RBAC is two-dimensional

Fabric Group membership controls which devices/ADOMs are in scope; the administrator profile controls which operations and product areas the account can use. Do not treat the parent group as a substitute for an admin profile. A user may correctly see two regions but still lack permission to edit a report, manage a device, or change a system setting. Conversely, a broad admin profile does not automatically grant visibility to every Fabric member if the Fabric Group scope is narrow. Keep the visibility boundary and action privilege boundary separately designed and tested.

Verification

Test with a least-privilege administrator assigned only to Group_3. Confirm the expected members and ADOMs appear in Device Manager, then test FortiView, Log View, and Reports using the same scope. A missing device usually points to group membership, ADOM selection, or the wrong admin assignment; an action denied on a visible device points more likely to the admin profile. Verify both positive and negative cases: the operator should see the intended two groups and should not see an unrelated third group.

Operational caveats

The multiple-group assignment is a Fabric-supervisor function. It is not a way to merge log databases or change ADOM ownership; it composes visibility groups. Plan parent/child naming and ownership so that membership changes are auditable. When a child group changes, re-test the parent-scoped administrator because the effective scope changes transitively. For large environments, keep the group graph shallow enough that administrators can explain why a device is visible. The value of nesting is reuse, but reused groups can unintentionally broaden access if membership is not reviewed.

FortiSwitch · Lesson 4

Dynamic MAC learning limits, violation actions and sticky persistence

Learning and the forwarding database

A FortiSwitch learns a dynamic forwarding-database entry from the source MAC address of an ingress frame. The entry associates a MAC with the receiving port/VLAN and is aged out when inactive. FortiSwitchOS can limit dynamic learning per interface or VLAN. A limit of 1–128 constrains learned addresses; zero means no limit. Static MAC entries are not counted. Changing whether learning is enabled flushes existing dynamic entries, so toggling learning is not a harmless way to “refresh” the table.

Limit, action, logging and timer are separate controls

For a physical port, learning-limit defines the threshold and learning-limit-action chooses none or shutdown. The shutdown action applies to physical switch ports, not trunks or VLANs. The global learning-limit violation log is disabled by default, and the global mac-violation-timer defaults to zero (disabled). The recent Community troubleshooting tip demonstrates the operational trap: setting the per-port action to shutdown does not by itself guarantee a port shutdown or an event record if the global timer/log prerequisites are not enabled.

config switch global
    set log-mac-limit-violations enable
    set mac-violation-timer 60
end
config switch interface
    edit "port3"
        set learning-limit 4
        set learning-limit-action shutdown
    next
end

For a FortiGate-managed FortiSwitch, the equivalent controls live under the managed-switch/port hierarchy and the switch-controller global settings. Use the syntax appropriate to the management mode and model.

Aging and sticky MAC

The default aging interval is 300 seconds; the supported range is 10 to 1,000,000 seconds, and zero disables aging. Sticky MAC is a different lifecycle control: a dynamically learned address can remain associated with a port when the link goes down and comes back up. Sticky entries are not automatically permanent across reboot. Save them to the switch configuration with the documented sticky-MAC save action if reboot persistence is intended. This is not the same as a manually configured static MAC.

Evidence and recovery

Use get switch mac-limit-violations all or the interface/VLAN-specific form to inspect the first MAC that exceeded a limit. Only one violation is recorded per interface or VLAN until reset, and only the most recent 128 are displayed. execute mac-limit-violation reset interface <port> clears the violation and the shutdown state for that port. Dynamic MAC event logging (log-mac-event) records learned, moved, and deleted entries; it is separate from the learning-limit violation log. A quiet log therefore does not prove that no learning occurred.

Troubleshooting scenario

If the port remains up after the fifth MAC appears on a port limited to four, check the global timer and violation logging before changing the per-port action. Then inspect whether the port is a physical interface (not a trunk), confirm the effective limit, inspect the violation table, and reset only after removing the unintended endpoint. If legitimate phones, hypervisors, or downstream switches need multiple MACs, size the limit for the actual topology rather than disabling the control. Sticky MAC should be enabled only where port identity is intentionally stable; otherwise a moved endpoint can appear to be a stale-security problem.

FortiAP/Wireless · Lesson 5

802.11r Fast BSS Transition

What 802.11r solves

802.11r Fast BSS Transition reduces the authentication work a client must repeat when roaming between APs in the same mobility domain. The FT key hierarchy establishes a mobility-domain root context (PMK-R0) and derives target-AP context (PMK-R1), allowing the client and target AP to complete reassociation without performing the full original authentication exchange on every roam. The practical benefit is lower interruption for voice, video, and latency-sensitive sessions. It does not preserve an IP address across Layer-3 boundaries; that is a different roaming problem.

FortiOS controls

FortiOS exposes FT as a VAP/SSID setting. The important parameters are fast-bss-transition, ft-mobility-domain, ft-r0-key-lifetime, and ft-over-ds. The mobility-domain identifier groups the APs that share FT context. The R0 key lifetime is configured in minutes (default 480 in the CLI reference). FT over the distribution system (DS) uses the wired/distribution path for the transition exchange; disabling it selects the over-the-air path. A representative configuration is:

config wireless-controller vap
    edit "corp-voice"
        set fast-bss-transition enable
        set ft-mobility-domain 1000
        set ft-r0-key-lifetime 480
        set ft-over-ds disable
    next
end

Confirm the exact syntax and supported combinations on the target FortiOS build. Do not confuse fast-bss-transition with fast-roaming (pre-authentication/OKC behavior) or with 802.11k/v assisted roaming. 802.11k supplies neighbor information; 802.11v can suggest a BSS transition; 802.11r changes the authentication/key-transition exchange.

Compatibility and design

All APs serving the SSID must agree on the mobility-domain and compatible security settings. Client support is decisive: older supplicants may not negotiate FT or may behave differently with FT over DS versus over-air. Mixed client fleets should be tested with representative hardware and OS versions before a broad rollout. A client can associate successfully with FT disabled and still roam poorly; conversely, enabling the VAP option does not prove that a given client actually used FT. PMF/WPA mode, 802.1X/RADIUS behavior, and client firmware can affect the result.

Verification and troubleshooting

Start with the VAP configuration and confirm that the intended SSID has FT enabled and a consistent mobility-domain value across APs. Capture or inspect the client's reassociation/authentication exchange and controller/AP event logs to determine whether FT was negotiated. Compare roam interruption time for a supported client with FT enabled and disabled. If only some clients fail, isolate client capability and FT transport compatibility before changing the whole SSID. If every client performs a full authentication, check that the APs are in the same mobility domain and that the client is using the expected security profile. The key evidence is a successful FT exchange, not simply an enabled checkbox.

FortiNAC · Lesson 6

Audit-only scans versus Forced Remediation Exceptions

Separate compliance measurement from enforcement

FortiNAC normally uses endpoint-compliance scan results to determine whether a host is at risk and should be placed into Remediation/Quarantine. There are times when an engineer needs to evaluate a new scan or measure executive/production endpoints without interrupting them. FortiNAC provides two independent controls for this: the scan-level Audit Only option and the host-group-level Forced Remediation Exceptions system group. They are not interchangeable.

Audit Only is scan-scoped

When Audit Only is enabled on a scan, FortiNAC runs the scan and stores pass/fail results. A host that fails that scan is not marked at risk and is not forced into Remediation or Quarantine by that scan. The setting affects only hosts evaluated by that particular scan. Another scan assigned to the same host with Audit Only disabled can still enforce remediation. This supports staged rollouts: for example, an executive scan can collect compliance data without interrupting users while a separate administrative scan continues to enforce policy.

Configure it under Policy & Objects > Endpoint Compliance > Scans, then edit the scan and enable Audit Only in the Remediation section. Do not disable global Quarantine VLAN switching just to protect one pilot group; that global property changes enforcement for all hosts.

Forced Remediation Exceptions is host-group-scoped

Hosts in the system group are still evaluated by their assigned scans. Failed results are stored and the host can be marked at risk, but the host is never forced into Remediation regardless of which scan it fails. This is useful for a specific host population that must remain connected while compliance is measured. The system group cannot be deleted, though its membership can be modified. Because the exception is based on group membership, it applies across scans; Audit Only is based on the scan that ran.

Evidence and troubleshooting

Use the scan result view and Host Properties/Health tab to confirm the evaluation occurred. Then separately inspect the host's at-risk state and remediation/VLAN state. A stored failed result with no at-risk marker is consistent with Audit Only. A failed result marked at risk but not moved to remediation is consistent with Forced Remediation Exceptions. If the host is moved to quarantine unexpectedly, verify which scan actually evaluated it, whether that scan had Audit Only enabled, whether the host is in the exception group, and whether another enforcing scan ran afterward.

Operational use

Use Audit Only for policy pilots and scan-specific observation; use the exception group for a defined set of hosts that must not be forced into remediation across scans. Keep a documented exit criterion for removing the exception. Preserve the Security Risk Host event if you need alarms on failed scans, because enforcement suppression does not mean the compliance failure should be invisible. The central diagnostic principle is that scan result storage, at-risk marking, and VLAN enforcement are three separate states.

FortiNAC-F · Lesson 7

Enhanced external Ethernet adapter and docking-station management

Identity problem created by shared adapters

USB-C docks and Ethernet dongles often present their own MAC address to the switch. Several laptops can therefore appear as the same network identity when they use the same dock. If NAC trusts only that shared adapter MAC, an unknown endpoint may inherit access that was intended for a registered device. FortiNAC-F's Docking Station Management feature maintains a preconfigured adapter identity and combines it with host/user authentication. FortiNAC-F 7.6.5 enhances external-adapter management by identifying adapters that may be shared, authenticating users before granting network access, and allowing provisioning criteria to include the adapter connection.

Registration and authentication flow

Docking Station Management is configured under System > Settings > Identification > Docking Station Management. Preconfigure the dock/dongle MAC and associate the expected host/user context. When an endpoint connects through the dock, the adapter MAC can mask the endpoint MAC. An authentication policy can match the docking-station-connected condition, deauthenticate the host, and move it to a dedicated authentication VLAN. The portal must expose Request New Credentials and use the GuestSelfRegistration template (or a custom template) for the self-registration flow.

The documented use case has two devices using the same dock: the registered device is recognized through the configured docking-station workflow; the second, unregistered device is sent through self-registration rather than inheriting the first device's access. This is the critical identity distinction: the adapter connection is a policy signal, not proof that the endpoint behind it is trusted.

Alternative: MAC Address Pass Through

Where supported by the laptop BIOS/firmware, MAC Address Pass Through makes the endpoint present its own unique MAC rather than the shared dock MAC. Fortinet documents this as an alternative to prevent the same dongle/dock from being reused by multiple hosts under one identity. It is not the same as adapter-aware authentication: pass-through changes what identity the network sees, while Docking Station Management explicitly controls the shared adapter and the endpoint/user onboarding flow. Verify model-specific BIOS support before relying on pass-through.

Verification and operational troubleshooting

Inspect the Docking Station Management entry and Adapter View to confirm the adapter is identified as connected. Check the authentication policy match, host deauthentication event, authentication VLAN assignment, portal page, and successful Request New Credentials transaction. A portal that displays but cannot complete registration often points to a missing guest template or authentication method; a host that bypasses the portal may not be matching the adapter-connected condition or may be presenting a pass-through MAC. Test both a registered endpoint and an unregistered endpoint through the same dock, then repeat with a second dock to ensure the policy is not relying on a single hard-coded MAC.

Scope and caveats

The 7.6.5 enhancement is specifically about external adapters shared among users; the detailed Docking Station Management workflow is documented in the 7.6.0 guide. Keep the adapter inventory current and do not treat a registered dock as a blanket trust grant. The desired result is an authenticated endpoint identity bound to the adapter context, with a predictable VLAN/portal transition for unknown users.

FortiAuthenticator · Lesson 8

OAuth Authorization Code with PKCE for public clients

Why PKCE is a distinct client mode

FortiAuthenticator 6.6 adds Authorization Code with Proof Key for Code Exchange (PKCE) for OAuth relying parties whose client type is Public. A public client cannot safely keep a client secret in a distributed mobile or desktop application. PKCE binds the authorization code to a verifier held by the client, so an intercepted code alone is insufficient to redeem a token.

Exact request flow

The client generates a high-entropy code_verifier and derives a SHA-256 challenge. The authorize request to /api/v1/oauth/authorize/ includes response_type=code, client_id, the registered redirect_uri, code_challenge_method=S256, and code_challenge. FortiAuthenticator redirects the user to the configured login portal. After authentication, the authorization code returns to the callback URI. The client then calls /api/v1/oauth/token/ with the code and original code_verifier. FortiAuthenticator hashes the verifier and rejects the exchange if its SHA-256 digest does not match the challenge associated with the issued code.

For this grant, the client_secret is ignored at the authorize endpoint. The option is available only when Client type is Public; the ordinary Authorization Code grant is the confidential-client path. FortiAuthenticator documents S256 as the only accepted challenge method.

Relying-party configuration

Under Authentication > OAuth Service > Relying Party, create the client as Public and select Authorization code with PKCE. Attach the intended OAuth policy, register exact callback/redirect URIs, and configure scopes and OIDC claims as required. HTTPS redirect URIs are strongly recommended. The documented default access-token lifetime is 36,000 seconds (10 hours); refresh tokens default to one day. Setting either expiry to zero means it does not expire, so avoid that unless there is a deliberate compensating control and token-revocation plan.

Evidence and failure isolation

A 302 redirect to the FortiAuthenticator portal proves the authorize endpoint accepted the request and initiated authentication; it does not prove a token was issued. At token exchange, verify the code, redirect URI/client context, and verifier. A missing verifier, a verifier generated by a different client instance, or a challenge created with a method other than S256 causes rejection. If authentication succeeds but token exchange fails, inspect PKCE parameters before changing the user policy. If the redirect fails, compare the callback URI byte-for-byte with the relying-party registration.

Security and lifecycle considerations

Keep the verifier local to the client transaction and do not log it. Treat authorization codes as short-lived credentials. Use scopes and claims to minimize what the token exposes, and keep access/refresh lifetimes finite. The security property is proof of possession of the verifier at token redemption; it is not a replacement for user authentication, redirect URI validation, consent/policy, or token lifecycle controls.

FortiPAM · Lesson 9

Kerberos authentication for native RDP Network Level Authentication

Purpose and supported path

FortiPAM 1.9 supports Kerberos authentication when launching native RDP sessions that use Network Level Authentication (NLA). Kerberos is preferred over NTLM in modern Active Directory environments because the client obtains a ticket from the domain Key Distribution Center (KDC) rather than relying on an NTLM challenge/response exchange. This option is not supported by the Web RDP launcher; selecting it does not change every RDP access path.

Realm and KDC selection

FortiPAM derives the Kerberos realm from the domain associated with the secret or target. In a conventional AD deployment, the realm aligns with the Windows domain's DNS name. When Kerberos for NLA is enabled, FortiPAM uses the domain and credential information associated with the secret to request a ticket from the appropriate KDC. The target configuration includes an optional KDC Address field under Advanced Domain Settings. It accepts an FQDN or IP address and optional port; the default is 88. If no explicit KDC is supplied, FortiPAM discovers the KDC through DNS SRV records for the realm.

Configuration sequence

In Secrets > Secrets, enable the RDP service, set RDP Security Level to NLA, then enable Use Kerberos for NLA. Associate the secret with the correct domain credentials. Fortinet's recommended pattern is a Target Only secret with the target computer FQDN as host information, associated with the corresponding Windows Domain Account secret. An alternative is a Windows Domain Account secret and entering the target FQDN in the launcher. Using the FQDN is important because Kerberos service identity is name-based; a raw IP target can lead to a different authentication path.

Transaction and verification

The launch request resolves the target/domain context, constructs the realm, locates the KDC by DNS SRV or explicit address, obtains a Kerberos ticket, and performs NLA through the native RDP launcher. Validate the secret's RDP/NLA settings, the target FQDN, the associated domain account, DNS resolution of the domain and KDC SRV records, and reachability to the KDC. If discovery is unreliable across sites, configure the KDC Address explicitly with the correct port. Confirm that the session is using the native launcher and that the target accepts NLA.

Troubleshooting boundaries

A working TCP/3389 path proves only that the RDP listener is reachable; it does not prove Kerberos ticket acquisition or NLA success. If the launch fails before a desktop appears, isolate the failure between realm construction, KDC discovery, ticket acquisition, and target NLA. Check DNS suffix/domain data, target FQDN, account association, time synchronization, and service principal identity in AD. If a Web RDP launcher is used, switch to the native RDP launcher for this feature rather than trying to force the Web path to consume Kerberos NLA. Keep NTLM fallback behavior and target policy deliberate; do not interpret an RDP session that succeeds through a different launcher as proof that Kerberos was negotiated.

FortiSIEM · Lesson 10

Two-way incident and CMDB ticketing integrations

Four integration directions

FortiSIEM's ticketing integrations provide a two-way link between incidents/CMDB and external workflow systems such as ServiceNow, ConnectWise, Salesforce, and Jira. The feature is not a single “send an alert” action. It has four distinct integration types: Incident Outbound creates an external ticket from a FortiSIEM incident; Incident Inbound updates the FortiSIEM incident from the external ticket state; CMDB Outbound sends FortiSIEM device changes to an external CMDB; CMDB Inbound populates FortiSIEM CMDB from an external source. Other systems can be integrated through the API.

Configuration and execution

The documented process has two main steps: create an integration policy, then attach it to an Incident Automation Policy or run it on a schedule. For ServiceNow, create an Incident/Outbound integration with the ServiceNow URL and credentials, map FortiSIEM fields to the external table, set organization mapping and Run For scope, and configure the maximum number of incidents. Link it to an automation policy using the Invoke an Integration Policy action. Inbound incident synchronization is configured separately and scheduled; matching inbound/outbound instance names help the two directions refer to the same integration instance.

The default outbound mapping writes incident name to short_description, comments to comments, organization to company, and severity to impact/urgency. For custom integration, External Ticket Id must be mapped in both directions; inbound processing needs an external ticket state value of Closed and an external cleared time mapping. When the external ticket is closed, FortiSIEM clears the linked incident and synchronizes the closed state.

CMDB synchronization

CMDB Outbound can create/update an external device record when a device is added or updated in FortiSIEM CMDB. It can be scheduled or configured to run after discovery, which is the mechanism for automatically pushing discovery changes. CMDB Inbound imports from an external CMDB and can work with any external CMDB using the supported integration/API approach. Do not confuse this with incident ticketing: a device inventory sync does not create an incident, and an incident close does not reconcile device inventory.

Verification and failure modes

Test the full lifecycle rather than only the connection test: trigger a controlled incident, verify an external ticket ID is stored, close the ticket externally, run the inbound schedule, and confirm the FortiSIEM incident clears with the external state recorded. For CMDB, add/update a test device and verify the mapped resource appears in the external inventory. If tickets duplicate, check automation policy trigger frequency, instance mapping, Max Incidents, and whether the same incident is being sent by more than one policy. If an external ticket closes but the incident remains active, inspect inbound schedule, time window, External Ticket Id, Closed value mapping, and cleared-time mapping.

Operational caveats

Credentials, organization mappings, Run For scope, ticket table permissions, and field types all affect the result. A successful outbound API call does not prove inbound state synchronization. Keep incident and CMDB integrations separate, use least-privilege external accounts, and test custom field mappings against the FortiSIEM incident schema before production rollout.

FortiSASE · Lesson 11

Endpoint-to-endpoint communication through SPA Hubs

Traffic model

FortiSASE can allow remote endpoints connected through the Cloud Security tunnel to communicate with one another. This is useful when remote users need to reach peer-hosted services or collaborate without sending traffic out to an external network. The critical architectural detail is that traffic is routed through a Secure Private Access (SPA) Hub; it is not a direct peer-to-peer bypass around FortiSASE inspection and policy. At least one SPA Hub must be configured before the endpoint-to-endpoint capability becomes available in the portal.

Control-plane prerequisites

Endpoints connect to FortiSASE Security PoPs using Secure Internet Access (SIA). To enable peer traffic, go to Network > BGP and enable Endpoint-to-endpoint Traffic. The SPA Hubs must then re-announce the BGP prefixes learned from FortiSASE Security PoPs. Without that route re-advertisement, the hub may not have the endpoint prefixes needed to route between PoPs even when both client tunnels are up.

Policy differs by PoP placement

Fortinet documents two policy cases. For endpoints connected to the same Security PoP, configure the usual To Hubs and From Hubs policies and also create an Endpoint-to-endpoint policy under Security > Policies > Secure Private Access. That policy can constrain security posture tag, user/group, service, schedule, action (Accept/Deny), status, and violation logging. For endpoints on different Security PoPs, configure the To Hubs and From Hubs policies; the hub-to-client/server policy path governs the routed exchange. Do not apply the same policy assumption to both cases.

Verification

First verify that both endpoints have active SIA connectivity and that the SPA Hub has the Security PoP prefixes in its BGP table. Confirm that the hub re-advertises those prefixes toward the other PoP. Then inspect the applicable Secure Private Access policy: same-PoP traffic must match Endpoint-to-endpoint; cross-PoP traffic must match To Hubs and From Hubs. Enable Log Violation Traffic during rollout so denied peer traffic is visible. A working SIA tunnel proves endpoint-to-PoP connectivity only; it does not prove peer routes or peer policy.

Security implications

Peer-to-peer reachability creates a lateral-movement path if policy is broad. Use user/group and posture tags to limit which endpoints can initiate which services. Prefer explicit service objects over “any” and keep deny logging during the pilot. Validate both directions where the policy model requires To and From Hub rules. When the same-PoP case works but cross-PoP fails, prioritize BGP re-advertisement and To/From Hub policy; when cross-PoP works but same-PoP fails, inspect the dedicated endpoint-to-endpoint policy.

Secure SD-WAN · Lesson 12

FortiCloud Overlay-as-a-Service transactional provisioning

Separate the OaaS control plane from the overlay data plane

Overlay-as-a-Service (OaaS) is a FortiCloud orchestration service for SD-WAN overlays. The control plane is the cloud portal/controller and the FortiGate OaaS agent; the data plane is the resulting IPsec/BGP/SD-WAN overlay between hubs and spokes. Each FortiGate participating through the OaaS portal needs the SD-WAN Overlay as a Service entitlement (SWOS). Do not treat a portal site object as proof that every spoke has the required license or that the tunnels are forwarding.

Transactional configuration mechanism

The FortiGate OaaS agent communicates with the OaaS controller over the FGFM management tunnel. When a change is orchestrated from the portal, the agent validates and compares the desired FortiOS configuration with the current device configuration, then applies the orchestrated configuration as a transaction. If any orchestrated change fails to apply, the agent rolls back the OaaS-orchestrated changes. This transaction boundary is the key operational safeguard: the feature is intended to avoid leaving a spoke in a partially applied overlay configuration. It is not a generic rollback of unrelated local administrator changes.

Verification command and interpretation

On a spoke, run:

get oaas status

The output includes Account ID, Account, Site, Configuration version, Configuration sync status, Target version, Task ID, and Error. A successful sync with matching configuration and target versions proves that the agent/controller configuration transaction completed. It does not prove that the IPsec tunnels are up, BGP has converged, the SD-WAN performance SLA is alive, or application traffic is taking the expected path.

Data-plane validation

After the control-plane transaction, inspect the generated SD-WAN zone and rules. The deployment guide documents an oaas_default rule associated with an oaas_overlay_hub performance SLA; additional rules should be placed below the default OaaS rule so that intended precedence is preserved. Verify both hub tunnels, BGP routes, SD-WAN member state, SLA measurements, and actual spoke-to-spoke traffic. Where ADVPN shortcuts are part of the design, confirm that the shortcut appears only after the expected traffic and hub/spoke discovery.

Failure analysis

If the portal task fails, compare the task ID/error with get oaas status on the affected spoke. Check the SWOS entitlement, FortiOS compatibility, FGFM management reachability, and local configuration conflicts with generated zone/service IDs. Because the agent rolls back its orchestrated changes after a failed transaction, inspect the post-failure configuration rather than assuming a partial set of changes remains. If sync status is SUCCESS but traffic fails, stop troubleshooting the OaaS transaction and move to tunnels, BGP, SLA, route selection, and firewall policy.

Design caveats

Keep manual configuration away from objects that OaaS owns unless the deployment guide explicitly permits it. Document the boundary between portal-managed objects and local policy. A successful OaaS task is a control-plane success signal; end-to-end service acceptance still requires independent data-plane tests from representative spokes.
