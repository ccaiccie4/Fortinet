FortiGate

1. Local-in policy boundaries and per-policy logging

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — Community page materially updated in September 2026; it documents GUI exposure for IPv4/IPv6 local-in policies.

Purpose and boundary

A local-in policy governs packets whose destination is the FortiGate itself: administration, VPN listeners, and other local daemons. It is not a substitute for a forward firewall policy. Transit packets can match forward policies and security profiles; packets addressed to a FortiGate interface enter local-in handling and are also constrained by interface administrative-access settings. Administrator trusted hosts are another control, not a universal replacement for local-in rules.

Matching mechanics

Rules combine ingress interface, source address, destination address, service, schedule, and action. IPv4 and IPv6 use separate tables, so a correct IPv4 rule does not imply equivalent IPv6 protection. Interface access toggles and built-in service allowances still matter. A broad rule can expose HTTPS, SSH, ping, or VPN control traffic on an unintended interface; a narrow rule can break monitoring or remote management while transit traffic remains healthy.

Configuration and ordering

Use address objects and explicit services rather than an unrestricted ALL rule. The example accepts HTTPS and PING on port1 only from an admin subnet; a subsequent deny can close those services to other sources. Inspect policy order and address family. Do not assume the familiar forward-policy implicit-deny behavior automatically protects every local-in service: where a deny boundary is required, use the explicit ordered local-in rules described in the guide. Preserve out-of-band recovery before changing management reachability.

Logging and evidence

FortiOS 7.6 supports per-rule local-in logging. The global local-in logging switch and each rule's logtraffic setting work together; enabling only one may leave the expected record absent. A debug-flow message from fw_local_in_handler naming a rule and drop is strong evidence that the packet reached the local-in handler and matched that rule. It does not prove the remote route, return path, or daemon is otherwise healthy. Built-in local-in policies can log policyid=0, which differs from forward-policy log semantics.

Failure isolation

Reproduce from one source and interface, capture the exact destination family and service, then inspect local-in rules and interface allowaccess. Enable local-in logging and use a narrow debug-flow filter. If no local-in hit appears, verify the packet targets a FortiGate interface address and reaches the expected VDOM. If a deny is logged, correct the source/interface/service or order. If traffic is allowed but the client still fails, move to daemon state, TLS, routing, and return traffic.

Operational caveats

Management changes can lock out operators, especially with HA management IPs, loopback interfaces, or separate VDOMs. Make IPv4 and IPv6 intent explicit, test permitted and denied sources, and document which service is reachable on each interface. The Administration Guide is primary; the Community article is scenario context for GUI visibility, not authority for the full security design.

Configuration reference

config log setting
    set local-in-policy-log enable
end
config firewall local-in-policy
    edit 10
        set intf "port1"
        set srcaddr "admin-subnet"
        set dstaddr "all"
        set action accept
        set service "HTTPS" "PING"
        set schedule "always"
        set logtraffic enable
    next
end

FortiManager

2. CLI template timing: model bootstrap versus install phases

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: No direct recent scenario verified. No directly matched recent Community case for this exact timing boundary was verified; the lesson is Administration-Guide-led.

Why timing matters

FortiManager has multiple configuration-automation lifecycles. A CLI template can bootstrap a model device or participate in a managed-device installation. Command text alone does not determine the outcome: template type, assignment target, and position decide when it is applied relative to the Device Database and policy package. A command that creates an interface needed by a later package belongs at a different phase from a command that adjusts a setting after package installation.

Pre-run model bootstrap

Pre-Run CLI Templates are intended for model devices and run once to seed the Device Database after the Add Device wizard completes. They are not recurring templates for every managed device. FortiManager unassigns the template after successful application. If applying it to the Device Database fails, review/update the template, manually reassign it, and perform an install to retry. A template that disappears from assignment may have completed its one-time lifecycle rather than been deleted.

Pre-VDOM and post-VDOM

Regular CLI templates can be CLI scripts or Jinja scripts. Pre-VDOM Copy runs during installation before the policy package; Post-VDOM Copy runs after the package and is the default. Pre-VDOM Copy is not restricted to model devices and remains part of managed configuration. These phases matter for dependencies: objects needed for policy compilation must exist before package application, while commands depending on package-created objects may need the later phase. Template groups organize scripts but do not remove ordering requirements.

Configuration and verification

Create a uniquely named template, choose type and position deliberately, assign the intended model/device/group, and inspect Jinja variables and rendered commands for each target. After installation, review per-device task results and compare the Device Database or device configuration with the expected state. A green task at one phase proves only that operation succeeded; it does not prove a later package or another template succeeded.

Failure isolation

If bootstrap state is absent, inspect the model assignment and Add Device task before debugging the policy package. If a command runs before its prerequisite object exists, move it to the right phase or split it into ordered templates. If a pre-run template failed, fix and explicitly reassign it; editing a template that has already been unassigned may not rerun it. For regular templates, inspect assignment and install preview, then examine device CLI errors rather than treating central database state as proof the FortiGate accepted the command.

Scale and guardrails

Use model bootstrap for one-time device construction and regular templates for managed configuration. Avoid non-idempotent commands in repeatable install phases unless a second run is safe. Test representative models and firmware because available CLI varies by platform. The primary Administration Guide defines phase semantics; no recent matching Community scenario was verified, so the example is an engineering case, not a claimed current incident.

Configuration reference

Device Manager > Provisioning Templates > CLI Templates
Type: CLI Script or Jinja Script
Pre-run: model devices only; one-time bootstrap
Pre-VDOM Copy: before policy package
Post-VDOM Copy: after policy package (default)

FortiAnalyzer

3. RFC 6587 syslog framing: byte-counted TCP messages versus delimiters

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — Fortinet Community technical tip dated September 9, 2026; it covers TCP syslog receiver framing mismatch.

Two independent protocol decisions

TCP is a byte stream, not a sequence of application messages. The receiver needs a framing rule to decide where one syslog record ends. RFC 6587 defines transparent framing, where a decimal byte count precedes the message, and non-transparent framing, where a delimiter such as LF or CR terminates a record. RFC 5424 instead describes fields inside a syslog message. A receiver can understand the payload but still reject the stream because framing does not match.

FortiAnalyzer controls

Log forwarding has independent settings for message format and framing. fwd-syslog-format selects FortiGate-native or RFC 5424 content; it does not switch TCP record boundaries. fwd-syslog-transparent controls framing: enable selects RFC 6587 octet-counting, disable uses delimiter framing, and faz-enrich is a non-transparent option with FortiAnalyzer enrichment. The entry must first be configured for a syslog destination. That prerequisite is easy to miss when editing an existing forwarding entry.

Configuration sequence

Inspect the entry, confirm the remote server type is syslog, then set message format and framing. The example uses RFC 5424 content and transparent framing because the receiver expects a length prefix. Do not copy both settings blindly: if the receiver expects delimiter framing, octet-counting can create a new parsing failure. Agree on framing with the SIEM administrator and test one known event before changing all forwarding entries.

Evidence and meaning

A receiver message such as Non-Transparent Framing (CR) points toward a boundary problem, not necessarily malformed hostname, timestamp, or PRI fields. A TCP capture can show whether records begin with a length prefix or end with a delimiter. The FortiAnalyzer setting proves what the sender is configured to emit; it does not prove the receiver parses it, TCP reaches the correct listener, or downstream field extraction is correct.

Troubleshooting workflow

Compare one emitted record with receiver expectations, check TCP connectivity, and inspect the log-forward ID and server type. If the connection is established but records are rejected or merged, verify framing before changing payload format. If records arrive but fields are empty, inspect RFC 5424 versus native format and parser mapping. Keep before/after samples and verify record counts and timestamps remain stable.

Operational implications

Forwarding mode is near-real-time; aggregation mode is a separate FortiAnalyzer-to-FortiAnalyzer workflow and does not substitute for correct syslog framing. The September 9, 2026 Community tip is the scenario source; the Administration Guide is primary for the forwarding object. Treat content format, transport, framing, and parser mapping as separate layers.

Configuration reference

config system log-forward
    edit <id>
        set fwd-server-type syslog
        set fwd-syslog-format rfc-5424
        set fwd-syslog-transparent enable
    next
end

FortiSwitch

4. Dynamic VLAN pruning: GVRP state and ISL trunk membership

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: No direct recent scenario verified. No direct recent Community incident for dynamic pruning was verified; feature and timers are documented in FortiSwitchOS 7.6.1+ guides.

Purpose and scope

Dynamic VLAN pruning reduces Layer 2 carriage on inter-switch links by allowing only VLANs active downstream. It is supported starting in FortiSwitchOS 7.6.1 and is disabled by default. It does not replace creating VLANs or configuring trunk ports; it narrows the VLAN set carried across an ISL based on learned membership state. A VLAN may still exist in the switch configuration while being pruned from a particular trunk.

Join and leave state

FortiSwitch uses GVRP messages to advertise VLAN state. Join indicates that a port belongs to an active VLAN; Leave indicates it is no longer active on that port. join-timer controls how often another Join is sent, with a documented default of 500 ms. leave-timer controls the delay after Leave before the port is considered inactive, default 1800 ms. These timers trade convergence speed against stability: short leave behavior can prune during transient state changes, while longer timers preserve carriage longer.

Configuration sequence

Enable pruning only after mapping which switches and ISLs participate and confirming release/model support. Supported ranges are 20–1000 ms for join-timer and 600–3000 ms for leave-timer. Start with defaults unless measured convergence requirements justify changes. Before rollout, capture current trunk behavior and test a VLAN known to exist downstream; then verify the dynamic list changes when a host or downstream service becomes active or inactive.

Diagnostic evidence

Use diagnose switch vlan-pruning dynamic-vlan list with the ISL interface to inspect the learned set. Use diagnose switch vlan-pruning protocol-packet stats to view received and transmitted GVRP counters, including JoinEmpty, JoinIn, LeaveEmpty, LeaveIn, LeaveAll, and Empty. Growing TX proves messages are emitted, not that the neighbor accepted them. RX counters and the peer's learned state help separate local generation from link or peer configuration.

Failure isolation

If a required VLAN disappears from the dynamic list, verify it is active downstream, then inspect Join/Leave counters on both ends of the ISL. Check that the port is an ISL and both devices run compatible software. If membership flaps, examine timers and downstream link state before increasing them; timer changes can mask instability. If the dynamic list is correct but traffic fails, inspect trunk forwarding, spanning tree, MAC learning, and the endpoint gateway separately.

Design caveats

Dynamic pruning changes operational VLAN carriage and can expose assumptions in static trunk audits. Record expected VLANs per ISL and compare with the live dynamic list. The official Administration Guide and 7.6.1 release documentation are primary sources; no matching recent Community case was verified, so the scenario is an operational example.

Configuration reference

config switch global
    set vlan-pruning enable
end
config switch vlan-pruning
    set join-timer 500
    set leave-timer 1800
end
diagnose switch vlan-pruning dynamic-vlan list port10
diagnose switch vlan-pruning protocol-packet stats port10

FortiAP/Wireless

5. Legacy WTP profile LLDP state and post-upgrade AP stability

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — Older upgrade scenario from November 2024: legacy profiles retained LLDP disabled; contextual rather than newly published failure.

What the profile controls

A FortiAP is a managed Wireless Termination Point (WTP); its profile contains platform and radio settings plus wired-side behavior. The FortiOS CLI reference exposes lldp under config wireless-controller wtp-profile, with enable/disable values and enable as the documented default for current profiles. New-profile defaults do not necessarily rewrite stored values in older profiles. A legacy profile can therefore preserve disabled LLDP after a controller upgrade.

Why LLDP matters

LLDP is Layer 2 neighbor discovery, not an RF roaming protocol. It lets the AP and adjacent switch exchange identity/capability information. Fortinet's older upgrade troubleshooting article describes APs that disconnect and reboot after a controller upgrade when LLDP remained disabled in profiles created on an earlier release. Logs included AP-leave and reasons such as AP FSM stuck or DTLS peer disconnected. Those messages are symptoms, not proof that the radio itself is defective.

Configuration and scope

Inspect the profile actually assigned to the AP, not only the current default. Use show wireless-controller wtp-profile to verify lldp, then change the intended profile and confirm the managed WTP uses it. The example enables LLDP in one profile. Before broad rollout, confirm switch edge and AP model support the expected behavior. Do not confuse LLDP enablement with changing CAPWAP data-channel encryption.

Evidence chain

Correlate AP-leave event timestamps with the WTP profile and the switch's LLDP neighbor state. If the profile has lldp disable and the switch does not learn the AP as expected, the configuration is a plausible cause. If LLDP is enabled and neighbor state is correct, continue with PoE negotiation, link errors, AP firmware, CAPWAP reachability, and certificate/control-channel diagnostics. A successful AP ping proves IP reachability only, not that controller state has completed.

Troubleshooting scenario

After a controller upgrade, APs begin leaving while client RSSI and channel utilization look normal. Compare an affected AP's assigned profile with a new profile. If only the legacy profile has LLDP disabled, change one AP group, monitor AP-leave events and switch neighbor learning, then expand. If the event persists, move to the next layer rather than repeatedly changing radio power or roaming thresholds.

Operational guardrails

The current WTP-profile CLI reference is primary; the Community article is older scenario context. Include effective LLDP state in upgrade checks. This topic is distinct from recent FortiAP discovery/DTLS certificate-chain coverage: its mechanism is persistent profile state and Layer 2 neighbor behavior.

Configuration reference

config wireless-controller wtp-profile
    edit "branch-ap-profile"
        set lldp enable
    next
end
show wireless-controller wtp-profile

FortiNAC

6. FortiLink CoA disconnect failures: accounting access and return path

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — January 20, 2026 scenario: VLAN change CoA works but host-deletion Disconnect-Request is not acknowledged.

RADIUS authorization lifecycle

FortiNAC can change network posture after an endpoint is reclassified, moved, deleted, or assigned a new role. A switch holds a session authorized by RADIUS Access-Accept. Change of Authorization can alter session attributes; Disconnect-Request flushes the current session so a new authentication can apply the new VLAN or policy. These are distinct RFC 5176 transactions. Successful VLAN reassignment in one workflow does not prove every disconnect message is accepted on the same path.

FortiLink dependencies

The FortiNAC integration guide requires FortiSwitch to process CoA/disconnect and be configured with the expected accounting server. FortiSwitchOS documents that the interface receiving CoA must allow radius-acct; CoA must also be enabled for the RADIUS server. FortiNAC uses the switch management IP and shared secret. In FortiLink deployments, check the managed-switch and FortiGate security-policy settings because the request may target the switch management endpoint, not the client VLAN gateway.

Packet and port checks

RADIUS authentication/accounting commonly use UDP 1812/1813; RFC 5176 CoA uses UDP 3799. Verify request and response in both directions and confirm NAT does not change the source identity expected by the switch. The secret must match across the relevant configurations. On FortiSwitch, allowaccess radius-acct permits the interface to receive accounting/CoA; it is not just a global RADIUS server toggle. Check model/release support before assuming every switch supports the transaction.

Failure isolation

A FortiNAC log saying Disconnect-Request sent proves an attempt, not acceptance. A capture with repeated requests and no response points to listener/allowaccess, routing, ACL, NAT, secret, or support. If the switch acknowledges but the client returns to the old VLAN, inspect the next Access-Request/Accept, policy role match, and applied VLAN attribute. If the response is a NAK, decode the error and distinguish unsupported attributes from reachability.

Operational remediation

Reproduce on one endpoint and capture UDP 3799 at FortiNAC and switch. Confirm switch IP, enable radius-acct on the receiving interface, enable CoA for the correct RADIUS server, and verify accounting and secrets. Test both attribute-change CoA and Disconnect-Request because they exercise different handling. Then delete or reclassify a test host and confirm reauthentication into the intended role/VLAN.

Caveats

The January 2026 Community report is scenario material; FortiNAC/FortiSwitch guides are primary. Avoid broad firewall openings: allow only required management peers and UDP services. HA, VDOMs, and multiple control-server addresses can change expected source IP. Document the boundary so address changes do not create silent disconnect failures.

Configuration reference

config system interface
    edit "internal"
        set allowaccess ping https ssh radius-acct
    next
end
config user radius
    edit "FortiNAC"
        set radius-coa enable
        set acct-interim-interval 86400
    next
end

FortiNAC-F

7. IoT profiling: combine fingerprints without blocking on missing data

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — Community tip from about five months earlier; it demonstrates multi-signal IoT/OT profiling and role enforcement.

Purpose and inputs

Device profiling assigns a device type and access role to endpoints that may not run an agent or authenticate as named users. FortiNAC-F can correlate MAC OUI, DHCP fingerprint, FortiGuard IoT category, open ports/services, protocol behavior, passive fingerprinting, and active probes. One signal is not perfect truth: OUI identifies a manufacturer but not necessarily device function; DHCP can hint at OS/class but may be absent; behavior can narrow a camera or industrial-controller classification.

Rule evaluation is ordered

FortiNAC evaluates ranked profiling rules until one passes, fails, or cannot be evaluated because required data is unavailable. The guide warns that missing data is not always skipped in favor of the next rule; combinations of criteria could otherwise become ambiguous and miscategorize a host. Rule order therefore controls correctness and performance. Put stable, inexpensive signals where they can classify common devices early, and avoid a rule that depends on an attribute an endpoint class will never provide.

DHCP and visibility

DHCP fingerprinting requires FortiNAC to receive endpoint DHCP packets. The guide recommends IP Helper on Layer 3 switches/routers for production VLANs using DHCP, pointing to management eth0 of the FortiNAC server or application server. That interface listens for fingerprint data; it does not answer DHCP requests. Static-IP endpoints may never send Discover/Request/Inform, so a DHCP rule can be unevaluable. This is a design constraint, not proof the device is offline.

Multi-signal classification

A camera rule might combine FortiGuard category, vendor OUI, RTSP port 554, and an HTTP response signature. A printer might combine DHCP identification, port 9100, and SNMP behavior. A PLC may need industrial-protocol evidence plus vendor/category data. A matched rule should produce device type, role, and registration choice; the role then drives access policy. Combine independent signals where possible, but avoid excessive active scans that add load or disturb fragile devices.

Verification

Inspect Endpoint Fingerprint for MAC, device type, OS, hostname, vendor/OUI, source method, and matched rule. If classification fails, verify host visibility, profiling enablement, required packets, and FortiGuard licensing/connectivity when used. If classification is wrong, inspect rule rank and matched criteria, then add a discriminating signal. Do not simply add a broad rule at the top; it may capture the host before the intended rule evaluates.

Policy implications

A classification error can become an access-control error because role assignment may immediately change network permissions. Use a restricted default role while refining rules. Confirm rule-on-connect or interval revalidation if endpoint identity can change. The Administration Guide is primary; the Community tip supplies IoT/OT examples. This is distinct from prior trap, NetFlow, and HA lessons because its core mechanism is ranked identity evidence and policy classification.

Configuration reference

FortiNAC-F: System > Settings > User/Host Management > Device Profiler
For DHCP fingerprinting, configure L3 IP Helper to the management eth0 address.

FortiAuthenticator

8. FSSO filters: ingestion boundary versus per-FortiGate forwarding

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — Older Community tip, useful for the distinction between global pre-filter and per-FortiGate filtering.

Two filter stages

FortiAuthenticator collects login information from remote LDAP/Windows sources, maintains an FSSO session database, and forwards user/IP/group mappings to FortiGate devices. The global pre-filter is ingress: it determines which login information enters the FAC database. A custom FortiGate Filter is egress: it selects which existing sessions are sent to a particular firewall. They are not interchangeable, even if the GUI labels look similar.

Object scope

A FortiGate filter identifies its target by name/IP and can use IP filtering, domain grouping, and FSSO object filters. Object types include group DN, group container/OU, user DN, user container, and combined user-and-group container. A group container includes users who are members of groups beneath that container or subcontainers; it is not identical to selecting one group DN. Importing LDAP objects reduces DN typos, but scope still needs review.

Build the forwarding policy

Create a named filter per FortiGate when firewalls need different subsets. Enable the specific FSSO filter, select LDAP groups/users/containers or existing SSO objects, and save. Avoid using the global pre-filter to solve a problem affecting only one firewall: that can remove sessions from the shared FAC database and affect every consumer. If a user should never be learned by FAC, a per-FortiGate filter is too late; correct the ingress scope.

Evidence and diagnosis

First check whether the user/IP session appears in the FAC SSO session monitor. If absent, inspect collector/poller connectivity, source event ingestion, global pre-filter, LDAP bind and group resolution. If present in FAC but missing on one FortiGate, inspect that firewall's named filter, group DN/container, IP filter, and connector status. A connected FSSO connector proves transport/session, not that the intended group was included.

Common failure pattern

A custom FortiGate filter includes the correct group but the user remains absent because the global pre-filter excluded the login before it entered the database. Another mistake is applying a one-firewall filter globally, hiding sessions from other firewalls. Trace a known user across both boundaries instead of repeatedly refreshing. Compare a known included user and an excluded user to verify positive and negative behavior.

Operational caveats

Group membership and directory structure change. Validate exact DN and whether the filter uses group, group container, or user container. Review filters after directory restructuring and when adding a FortiGate. The Administration Guide is primary; the Community tip is older but clarifies the ingestion/export distinction.

Configuration reference

FortiAuthenticator GUI:
Fortinet SSO Methods > SSO > FortiGate Filtering
Create a named filter per FortiGate and select intended groups, users, or containers.

FortiPAM

9. Windows Application Filter: secret-scoped deny rules and WinRM

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — Community case updated with a Fortinet response on February 10, 2026, pointing to prerequisites and troubleshooting guidance.

Purpose and policy model

FortiPAM Windows Application Filter limits application, installer, or script execution on a Windows target. It is not a network firewall. An administrator creates a profile with deny directories and optional exceptions, then applies it to a secret. FortiPAM generates and maintains deny rules for accounts associated with that secret. Different secrets usually have independent filters, so two secrets on one target can have different execution constraints.

Control-plane prerequisites

The target must be Windows, WinRM must be enabled, and the target must have a privileged account FortiPAM can use for WinRM operations. That is a control identity, not necessarily the restricted account whose application behavior is governed. The target's Windows Application Filter tab shows accounts and applied filters and provides deactivation/deletion controls. If WinRM authentication or permissions are wrong, a profile may appear configured while target-side rules are not managed correctly.

Configuration workflow

Create the filter profile, specify deny directories/applications, add only necessary exceptions, then attach the profile to the intended Windows secret. Confirm server information is Windows and target/privileged account are correct. Test with a harmless executable first. Review the target filter tab after application to confirm the account is listed and the expected filter is active. A profile saved in the library but not associated with the secret does not enforce anything.

Evidence and interpretation

The target view shows which accounts have filters and which profiles are applied. Verify WinRM listener, reachability, authentication, account privilege, and Windows-side rule effect. FortiPAM supports focused WAD diagnostics for secret and HTTP categories, with verbose output when needed. Logs can show the launch/control transaction, but a successful secret launch does not prove a denied executable was tested. A blocked launch may also involve a different target/account than the one inspected.

Troubleshooting sequence

Confirm the correct target and secret are being tested. Check WinRM and privileged account rights, then verify profile attachment and target filter record. Inspect deny paths and exceptions for path/scope mismatch. Reproduce one launch with focused diagnostics, then inspect the Windows target's generated rule effect. Do not immediately widen exceptions; identify whether the failure is control-plane deployment or rule logic.

Security and lifecycle

Because rules derive from secret policy, changing the account, target, or secret association can change enforcement. Review access after duplication, migration, or privileged-account rotation. Use least privilege and secure WinRM transport; do not copy legacy unencrypted WinRM examples into production. The Administration Guide is primary; the February 2026 Community exchange is the scenario aid.

Configuration reference

Prerequisites: Windows target, WinRM enabled, privileged account.

diagnose wad debug enable category http
diagnose wad debug enable level verbose
diagnose debug enable

FortiSIEM

10. Windows WMI/OMI monitoring: WinRM transport and event evidence

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: No direct recent scenario verified. No recent Community scenario matching WMI/OMI WinRM collection was verified; primary content comes from FortiSIEM configuration and agent guides.

Two Windows collection paths

FortiSIEM can collect through agentless WMI/OMI monitoring and through the Windows Agent. Agentless WMI/OMI uses remote management interfaces and WinRM to query Windows providers. The Windows Agent receives a monitor template from the Supervisor and can collect Event Logs, files, WMI classes, PowerShell results, and change-monitoring data. A host may answer ping while neither path is authorized or configured to produce the desired telemetry.

WinRM prerequisites and security

The Windows Server configuration guide identifies WinRM as necessary for WMI/OMI monitoring and some remediation actions. The service must be running, and credentials need permissions for the selected query. Remediation actions can require additional authentication/listener configuration beyond monitoring. Older examples include Basic and AllowUnencrypted settings for specific environments; treat these as legacy compatibility examples, not production defaults. Prefer HTTPS/TLS and supported authentication, scoped to the FortiSIEM Collector/Supervisor.

Windows Agent workflow

Install the correct agent and confirm it appears in the FortiSIEM CMDB under the configured hostname. Define a Windows Agent Monitor Template, select Event Log types and include/exclude IDs, then associate the agent with the template. The Supervisor distributes monitoring policies. A connected agent with no relevant events may lack a template or may exclude the desired IDs; it is not automatically a transport failure.

Evidence layers

For agentless monitoring, verify WinRM service/listener, authentication, Windows firewall, credentials, and the selected WMI/OMI query. Ping proves only reachability. For agent collection, inspect agent status, CMDB identity, template association, source configuration, and timestamps. If logs arrive but fields are missing, inspect parser/content updates. If metrics arrive but events do not, inspect the selected data source rather than assuming the Collector is entirely broken.

Failure isolation

Use one known Windows host and one method at a time. For WMI/OMI, test a harmless query with the same credentials and verify monitoring status. For agent logs, choose one known event ID, include it explicitly, and confirm Windows audit/source settings generate it. Do not troubleshoot agentless WinRM by changing an agent template, or agent subscriptions by broadening WMI permissions. Keep collection and remediation permissions separate.

Operational implications

Agent templates can include Security, System, Application, DNS, DHCP, Sysmon, PowerShell and other sources; event IDs are commonly entered as semicolon-separated lists. Availability still depends on Windows source configuration. FortiSIEM guides are primary; no recent matching Community case was verified, so this is a documentation-led operational case.

11. Certificate inspection versus deep inspection: endpoint trust boundary

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: No direct recent scenario verified. No recent FortiSASE-specific certificate-trust incident matching this exact feature was verified; this lesson is documentation-led.

Inspection modes

FortiSASE supports certificate inspection, deep inspection, and disabling inspection. Certificate inspection examines TLS handshake and server-certificate metadata so policy can use certificate identity, SNI, and URL/category information without decrypting payload. Deep inspection places FortiSASE in the TLS path, decrypts traffic for content-aware security profiles, then re-encrypts it to the server. The client sees the inspection certificate rather than the origin certificate, so endpoint trust is part of the design.

Payload-dependent controls

FortiSASE documentation identifies Split DNS, Antivirus, Web Filtering with Inline-CASB, File Filter, DLP, and Application Control with Inline-CASB as features that require deep inspection for encrypted content. Certificate inspection can support metadata-based category and URL decisions, but it cannot read an encrypted upload body or file payload. This explains partial failure: basic web filtering works while DLP or file-type controls do not trigger on HTTPS.

Certificate trust and exemptions

In agent-based mode, FortiClient can install the inspection CA on the endpoint. If the CA is not trusted, browsers and applications may report certificate warnings or reject intercepted connections. FortiSASE provides controls for uploading/installing the certificate, handling probe failures, invalid certificates, and exempting hosts or URL categories. Exemptions are deliberate policy boundaries: an exempt flow may bypass decryption required by content controls even if the rest of the profile is correct.

Configuration validation

Select the intended mode in the assigned security profile group, confirm the user/group policy references that profile, and verify the CA is deployed. Test a known HTTPS URL for certificate inspection and a controlled benign file/DLP test for deep inspection. Inspect the certificate chain seen by the endpoint and compare it with the configured CA. Review exceptions because a deep-inspection profile does not prove every destination is actually intercepted.

Evidence and failure isolation

If category blocking works but a DLP/File Filter test fails, check whether the flow is certificate-only or exempted before rewriting signatures. If deep inspection is enabled but the browser reports trust errors, inspect CA installation, endpoint store, profile assignment, and certificate-probe options. If one application fails, compare TLS behavior and exemption status with a known-good client. A policy log shows a decision; a controlled content test proves the payload was available to the profile.

Operational caveats

Deep inspection affects privacy, performance, certificate pinning, mutual TLS, and applications intolerant of interception. Scope exceptions narrowly and document the protection lost when traffic is exempted. Pilot CA deployment and test supported endpoint versions. The Administration Guide is primary; no matching recent Community scenario was verified, so the failure is a repeatable validation case, not a claimed current incident.

Configuration reference

FortiSASE Administration > SSL Inspection
Select Certificate or Deep inspection; install the inspection CA for deep mode.
Review host/category exemptions and certificate-probe behavior.

Secure SD-WAN

12. Local-out routing: steering FortiGate-originated service traffic

Primary feature source: Fortinet Administration/Configuration/CLI Guide · Related primary guide
Scenario source: Community scenario — Community tip dated October 21, 2025; older but relevant to local-out interface/source selection.

What local-out means

Local-out traffic is generated by FortiGate itself rather than forwarded between client and server. Examples include FortiGuard updates, DNS, NTP, syslog, FortiAnalyzer logging, RADIUS/LDAP, sFlow/NetFlow, and central management. By default, local-out connections use routing-table lookup to choose egress and source address. Transit traffic instead matches firewall policies and SD-WAN service rules based on the original packet's application or destination.

Per-service selection

Many local-out services support Auto, SD-WAN, or a specified interface. Auto uses route lookup; SD-WAN selects among configured members/rules; Specify pins traffic to an interface. Source IP may be automatic or manually configured for supported services. A manual interface must be the physical egress interface, and a manual source address may be needed when the intended source is not the interface's primary address. The exact knob varies by service.

Configuration and boundaries

Local Out Routing can be exposed through Feature Visibility. For system DNS, FortiOS documents interface-select-method with Auto, SD-WAN, or Specify. Similar controls exist for central management, FortiGuard, syslog, sFlow/NetFlow, RADIUS, LDAP and others, but not every service uses identical syntax. Configure the service-specific setting rather than assuming a transit SD-WAN rule will capture it. Keep active routes via intended links and confirm the remote service accepts the source IP.

Session lifecycle

Local-out selection occurs when the service creates a connection. Fortinet documents that a change in SD-WAN SLA or logic does not terminate an existing FortiManager-FortiGate tunnel; central-management SD-WAN logic is checked at session creation. A route or SLA change may affect new sessions before an existing control channel moves. Inspect local traffic logs, route table, interface method, source address, and connection timestamp before concluding a rule is ignored.

Troubleshooting

When FortiGuard or DNS exits the wrong ISP, identify the service and its local-out method. Confirm Auto/SD-WAN/Specify, inspect route and member eligibility, then verify source IP and return path. If only a pre-existing connection ignores new SLA state, test a controlled new session or wait for reconnect behavior instead of repeatedly changing policy order. FortiOS provides separate options for diagnostic ping/traceroute to use SD-WAN.

Design caveats

Local-out steering matters for asymmetric ISP policy, source-based upstream allowlists, logging continuity, and management reachability. A pinned source IP on the wrong egress can cause replies to follow another path or be filtered upstream. The Administration Guide is primary; the Community tip is older scenario context. This differs from transit application steering because the subject is traffic created by the FortiGate control plane.

Configuration reference

config system dns
    set interface-select-method sdwan
end
config system central-management
    set interface-select-method sdwan
end
