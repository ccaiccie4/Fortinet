FortiGate

BGP TCP Authentication Option (TCP-AO): authenticate the transport, not the route

622 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. BGP peers exchange routing information over a TCP connection, normally port 179. Protecting only the network path with ACLs or relying on source addresses does not cryptographically prove that a received TCP segment came from the configured peer. TCP Authentication Option (TCP-AO) adds per-segment authentication to the TCP transport used by BGP. It is not a route filter, does not encrypt UPDATE payloads, and does not replace BGP policy. Its job is to make forged or modified TCP traffic much harder to inject into the peer session.

Object model and transaction flow

FortiOS stores the cryptographic material in a config router key-chain object. Each key entry has an integer key ID, a secret string, an algorithm, a send lifetime and an accept lifetime. The send lifetime controls when this peer may use a key for outgoing traffic; the accept lifetime controls when it accepts traffic authenticated with that key. The BGP neighbor or neighbor-group selects the key-chain with set auth-options. The remote peer must have compatible key material and algorithm configured as well. Once the TCP-AO-protected TCP session is established, the normal BGP finite-state machine follows: OPEN, KEEPALIVE, UPDATE and route processing. A healthy TCP-AO transport is necessary, but it does not prove that BGP capabilities, address families, route policies or next-hop reachability are correct.

Configuration pattern

config router key-chain
    edit "BGP-EDGE-AO"
        config key
            edit 10
                set key-string "replace-with-managed-secret"
                set algorithm cmac-aes128
                set send-lifetime 00:00:00 1 Jan 2026 23:59:59 31 Dec 2027
                set accept-lifetime 00:00:00 1 Jan 2026 23:59:59 31 Dec 2027
            next
        end
    next
end

config router bgp
    config neighbor
        edit "192.0.2.2"
            set remote-as 65020
            set auth-options "BGP-EDGE-AO"
        next
    end
end

The example uses AES-128-CMAC because Fortinet documents it directly. The FortiOS key-chain reference also lists HMAC-SHA1, HMAC-SHA256, HMAC-SHA384 and HMAC-SHA512. Select only an algorithm supported by both peers and your security baseline. Treat the key string as a credential: do not copy it into tickets or the report repository. The example lifetime is illustrative; use a coordinated maintenance window and a planned overlap when rotating keys.

Evidence: what each command proves

  • diagnose sys tcp-auth-options reports the peer address, algorithm, send/receive key IDs and send/receive validity windows. It proves which TCP-AO key context FortiOS is using; it does not prove that the BGP route table contains the expected prefixes.
  • get router info bgp summary shows the BGP peer state and prefix counters. An Established peer proves the BGP session is up, not that the remote peer is advertising every intended route.
  • A packet capture showing TCP SYN retransmissions or resets can narrow the failure to transport establishment, but encrypted/authenticated option details may not be visible in a basic capture. Correlate with the TCP-AO diagnostic and peer-side logs.

Failure isolation and operational cautions

If ICMP succeeds but BGP remains Active, first compare the two key-chain entries: key ID, secret, algorithm, send/accept lifetimes and neighbor binding. A key can be present but outside its accept window. A neighbor-group may also be the effective object, so inspect inherited configuration rather than only the individual neighbor. Do not start by changing BGP timers, route maps or prefix lists: those operate after the transport has been authenticated. During rotation, ensure the sender's active key is accepted by the receiver before switching the sender. After transport is healthy, troubleshoot OPEN capability negotiation, address-family activation, policy and next-hop reachability as separate stages.

Operational scenario. A maintenance window replaces a shared BGP secret on one edge but not its redundant peer. The two peers have identical IP reachability and remote AS values, yet only one session establishes. TCP-AO diagnostics reveal a different receive key ID on the failed peer. Correct the key-chain entry on that peer and verify the TCP-AO context before inspecting BGP advertisements.

FortiManager

FortiManager 8.0 time-based retention: Task Monitor and Event Log age limits

534 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. FortiManager's Task Monitor and Event Log are often the first places an operator looks when an install, policy package operation or administrative change behaves unexpectedly. Disk-quota-only retention makes the age of the oldest record depend on log volume. A quiet manager may retain records for a long time; a busy manager may roll them out much sooner. FortiManager 8.0 adds a time-based retention ceiling for these local records so the administrator can define an age horizon instead of relying solely on disk consumption.

Mechanics and scope

The control is log-max-days under config system local log disk setting. Fortinet documents a range from 0 through 365. A positive value is the maximum age in days for Task Monitor and Event Log records. Setting it to 0 returns to the default disk-quota retention behavior. With a five-day value, records older than the configured window are truncated during the midnight cleanup cycle. This is a local FortiManager retention control; do not assume it changes FortiAnalyzer retention, ADOM revision history, device configuration backups, or external syslog/SIEM archives.

Configuration and change control

config system local log disk setting
    set log-max-days 30
end

show system local log disk setting

Choose a period based on the actual troubleshooting and audit requirement, not merely on current disk headroom. A short window can remove the evidence needed to investigate a failed install days later. A long window may be inappropriate where local disk is constrained. If the organization needs longer retention, export or forward the relevant events to an approved central repository before shortening the local window. The value 0 is not “keep forever”; it restores quota-driven behavior, which can still purge old records when the disk allocation fills.

Evidence and interpretation

  • Read back log-max-days to confirm the configured retention policy. A successful CLI write alone does not prove that older records have already been purged.
  • Compare the oldest Task Monitor and Event Log timestamps before and after the midnight cleanup cycle. Fortinet's example shows the cutoff taking effect at midnight after the setting is changed.
  • Inspect disk/log quota state separately. If the configured value is 0, age is an outcome of quota pressure rather than a fixed calendar limit.
  • Preserve a sample task record and event record before changing the policy so operators can validate which record classes are affected.

Troubleshooting and operational application

When an operator reports that an install history entry “disappeared,” distinguish three questions: was the entry created, was it retained locally, and was it exported elsewhere? Task Monitor history is not the same as a device's current configuration or revision database. A successful device install can be true even if the local task row later expires. Conversely, a task row that says completed is not proof that every target device reached the intended state; use device-side read-back and installation details.

Operational scenario. A change team reduces the setting from 30 days to five days during a disk cleanup. The next morning, an engineer cannot find last week's install task. The expected result is age-based truncation, not evidence that the install was rolled back. Restore an appropriate retention window, export task/event records before future reductions, and keep the runbook explicit about the midnight purge boundary.

FortiAnalyzer

Authenticated NTPv4 with SHA-256: matching Chrony keys to FortiAnalyzer

495 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. FortiAnalyzer timestamps are part of the evidence chain for event correlation, incident timelines, report windows and administrator activity. A time source that is merely reachable is not necessarily trusted. FortiAnalyzer 8.0 supports NTPv4 with SHA-256 keyed authentication, allowing the appliance and a compatible NTP server to verify that time messages were generated by a peer possessing the shared key. Despite the Fortinet feature title's use of the word “encryption,” this is message authentication/integrity; it does not encrypt the NTP time payload or provide confidentiality.

Server-side key model

Fortinet's example uses Chrony on Linux. The server configuration must permit the FortiAnalyzer address, bind to the intended server interface and load a key file. In /etc/chrony.keys, each line contains a key ID, the algorithm and key material. The ID configured on FortiAnalyzer must match the ID in the Chrony file, and the secret bytes must match exactly. The source documentation illustrates both hexadecimal and ASCII forms. A hex key must be represented as hex on both sides; an ASCII password must be treated as ASCII on both sides.

# /etc/chrony.conf (illustrative)
allow 10.2.2.10
bindaddress 10.2.2.2
keyfile /etc/chrony.keys

# /etc/chrony.keys
123 SHA256 HEX:f3c79b2288a249f8a218646af0492706014fc9f4beb58fd3b6aa6d45782dd6ca

FortiAnalyzer client configuration

config system ntp
    config ntpserver
        edit "chrony-primary"
            set server 10.2.2.2
            set authentication enable
            set key-type sha256
            set key-fmt hex
            set key f3c79b2288a249f8a218646af0492706014fc9f4beb58fd3b6aa6d45782dd6ca
            set key-id 123
        next
    end
end

The server address, authentication enablement, key type, key format, key value and key ID form one configuration unit. A mismatch in any of these can leave UDP reachability intact while authenticated time synchronization fails. Protect the shared key like any other infrastructure secret and coordinate rotation on both systems.

Verification boundaries

  • diagnose system ntp status is the Fortinet-documented verification command. It confirms the appliance's NTP state; run it after the client and server configuration are complete.
  • Chrony service status and logs help determine whether the daemon loaded the key file and accepted the FortiAnalyzer client.
  • A UDP/123 packet capture proves packets are exchanged, not that the keyed authentication check succeeded.
  • Correct wall-clock time at one instant does not prove long-term synchronization or correct key rollover. Check the selected server and synchronization state after a restart and during maintenance.

Operational troubleshooting

Start with the key ID. Then compare the key type and exact format. A 64-character hexadecimal string is not interchangeable with a visually similar ASCII password. Confirm that the Chrony key-file directive is active rather than commented out, that the configured server address is reachable from the FortiAnalyzer interface, and that the server ACL permits it. Do not troubleshoot log ingestion or event correlation until the time source itself is trusted; otherwise the same event can appear out of order across devices.

Operational scenario. After enabling SHA-256, FortiAnalyzer still receives NTP packets but reports no successful synchronization. Chrony has key ID 123 while the appliance references 222. Correct the identifier and exact key representation, then confirm status with the FortiAnalyzer diagnostic. This is an authentication mismatch, not a routing failure.

FortiSwitch

FortiSwitch signed configuration backups: same-device provenance and tamper verification

731 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. A switch configuration backup is not just a text file. It can contain management addresses, VLANs, routing, AAA, SNMP, port security and control-plane settings. If an attacker or an accidental process changes a backup before restore, the device may load a configuration that no longer represents the known-good state. FortiSwitchOS 8.0.0 signs configuration files created by the switch. During restore, the switch verifies that the file was generated by that same FortiSwitch unit and has not been modified since it was generated. This adds provenance and integrity checks to the backup/restore path.

What the signature proves—and what it does not

The signature binds a backup to the FortiSwitch that created it and detects changes to the file after creation. A file from Switch A is not automatically a trusted backup for Switch B, even if both units use the same model and firmware. The signature is device-specific provenance, not a universal vendor signature for every switch in the fleet. It also does not encrypt the configuration file. Treat the backup as sensitive data because it may contain credentials and network design details. Signature verification does not prove that the configuration was safe when it was originally saved; an administrator who had legitimate write access could have saved a harmful configuration and the switch would still sign that file.

Backup and revision workflow

FortiSwitch exposes several configuration-save behaviors under System > Config > Backup:

  • Automatically Save: saves configuration changes after each change.
  • Manually Save: requires an administrator to save changes from the Backup link on the System dashboard.
  • Manually Save and Revert Upon Timeout: requires a manual save and reverts to the saved configuration after the timeout and a restart; cfg-revert-timeout controls the timeout.
  • Revision Backup on Logout: creates a configuration file when a user logs out.
  • Revision Backup on Upgrade: creates a configuration file before a firmware upgrade begins.

These settings control when backup/revision files are created. The signature check is a separate control applied when a configuration file is restored. Do not assume that enabling automatic save means the backup is exported off-device, or that revision backup is the same as an external archive. Maintain a separate, access-controlled copy of critical backups and a tested recovery procedure.

Restore verification policy

config system global
    set verify-config reject
end

show system global

FortiSwitchOS provides two modes through set verify-config {log | reject}. In log mode, an unverified file is accepted and a warning is logged. In reject mode, an unverified file is rejected. Fortinet documents the default behavior as accepting unverified files and logging a warning. For security-sensitive environments, reject makes the trust boundary explicit: a file from another switch or a modified file cannot silently become the active configuration. Test the behavior on the target model and FortiSwitchOS release before enforcing it across a fleet.

Evidence and failure isolation

  • Read back verify-config to confirm whether the unit is in warning or reject mode. A CLI configuration write does not prove a restore has been tested.
  • Restore a known-good backup generated by the same unit in a lab or approved maintenance window. A clean restore confirms that the signature path accepts the original file.
  • In log mode, an unverified restore should be accompanied by a warning. Correlate the warning with the file, source switch and restore time.
  • In reject mode, a foreign or modified file is expected to fail verification. That is a security control, not necessarily a corrupt backup.

Operational troubleshooting

If a replacement switch rejects a backup exported from the failed unit, do not immediately disable verification globally. The file may be intact but signed by the original switch, so the replacement cannot establish same-device provenance. Use the organization's supported migration process to recreate or adapt the configuration for the replacement device, and treat any deliberate unverified restore as a controlled exception. If a file created by the same unit is rejected, verify that it has not been edited, truncated, transferred through a process that modifies line endings or otherwise changed. Preserve the original file and its hash while investigating.

Operational scenario. A technician copies a backup from a decommissioned access switch to a replacement unit. The replacement is configured with verify-config reject and refuses the file. This is expected: the backup is signed by the source switch, not the replacement. Use the documented migration path and record any exception rather than turning off verification fleet-wide.

FortiAP/Wireless

Dynamic captive-portal URLs from Cisco ISE: RADIUS Access-Accept attribute 27

510 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. A guest wireless deployment may need a different portal URL for different sessions, tenants or registration workflows. FortiOS WiFi controller can use a URL returned by Cisco Identity Services Engine (ISE) in the RADIUS Access-Accept instead of relying only on a static portal URL configured in the VAP. The URL is carried in the Fortinet vendor-specific RADIUS attribute Fortinet-Captive-Portal-URL, vendor attribute ID 27. The feature is disabled by default and is supported for a tunnel-mode captive-portal VAP whose portal type is auth-mac.

Packet and policy flow

The station associates to the SSID. MAC RADIUS authentication occurs first, and the station is placed in an unregistered user group. ISE evaluates its authorization policy and returns an Access-Accept containing the dynamic portal URL. FortiOS redirects the browser to that URL. After the guest completes the portal workflow, the station is assigned to the authorized group and its captive-portal state changes. The RADIUS exchange therefore carries two distinct kinds of information: the MAC-auth result/group and the portal URL. A successful MAC-auth result does not prove that the browser redirect URL was returned or accepted.

VAP and ISE configuration pattern

config wireless-controller vap
    edit "ISE-CWP"
        set ssid "ISE-CWP"
        set captive-portal enable
        set portal-type auth-mac
        set radius-mac-auth enable
        set radius-mac-auth-server "ISE-152"
        set radius-mac-auth-usergroups "AuthorizedGuest"
        set captive-portal-dynamic-redirect-url enable
        set schedule "always"
    next
end

In Cisco ISE, add the Fortinet RADIUS vendor attribute Fortinet-Captive-Portal-URL with ID 27, create an authorization profile that supplies the portal URL, and select that profile in the relevant authorization policy. On FortiGate, configure the ISE RADIUS server, user groups for unregistered and authorized clients, and the tunnel-mode VAP. Firewall policy must permit unauthenticated clients to reach the portal server (using the captive-portal exemption where required) and separately permit authorized-group traffic to the Internet. The static external-web URL remains a configured portal value, but the dynamic attribute is what provides the session-specific redirect.

Verification

  • Before login, diagnose wireless-controller wlac -d sta online should show the client in the unregistered group, with MAC RADIUS authentication allowed and cp_authed=no.
  • After login, the same command should show the authorized group and cp_authed=yes.
  • diagnose firewall auth list should show the RADIUS server and authorized group for the station.
  • Inspect the RADIUS Access-Accept to confirm attribute 27 contains the expected URL. A successful RADIUS Access-Accept without the attribute does not prove dynamic redirection is configured.

Failure isolation

If the client associates and MAC authentication succeeds but always reaches the default portal, check the ISE authorization profile and Access-Accept attribute before changing radio settings. Then verify tunnel mode, portal-type auth-mac and the dynamic redirect enablement. If the browser reaches the portal but the client cannot reach the Internet afterward, inspect the authorized-group assignment and firewall policy separately. The redirect URL is not itself an authorization grant.

Operational scenario. A guest is successfully placed in the unregistered group but lands on a generic portal instead of the tenant-specific page. The Access-Accept contains no attribute 27 because the wrong ISE authorization profile matched. Correct the authorization policy and verify the station's post-login group transition.

FortiNAC

FortiNAC authentication-policy timers: production grace, offline retention, and forced reauthentication

653 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. FortiNAC authentication is not simply “RADIUS accepted, therefore the host is on the production network.” An authentication policy combines a User/Host Profile, which decides which users/hosts and locations match, with an authentication configuration, which defines the treatment of those endpoints. The timers in that configuration control when an endpoint is moved between production and authentication VLANs, how long a disconnected host retains its authenticated state, and when a fresh authentication is forced.

Policy selection and state machine

When a host requires network access, FortiNAC compares its user/host attributes and connection location against the ordered authentication policies. The first matching policy is selected. Policy assignment is not permanent: the host may be reevaluated when a switch is polled or the Persistent Agent contacts the server. The authentication configuration supplies three important timers:

  • Time in Production before Authentication: while a user is waiting to authenticate, the host remains in the production VLAN until this timer expires. If authentication has not completed, FortiNAC moves the host to the authentication VLAN.
  • Time Offline before Deauthentication: after the host goes offline, the user remains authenticated for this interval. If the host returns before expiry, it does not need to authenticate again; if it returns later, authentication is required.
  • Reauthentication Frequency: forces reauthentication after the configured period since the last authentication, regardless of whether the host is online or offline. The host is moved to the authentication VLAN.

Hosts that do not match a User/Host Profile associated with an authentication policy are deauthenticated after the system default interval of ten minutes. Fortinet recommends creating a catch-all User/Host Profile and associating it with an authentication configuration so that hosts receive an explicit policy. A catch-all matches everything, so place it last; an earlier catch-all shadows more specific policies.

Authentication method precedence

If Authentication Method is enabled in the selected policy, that method overrides methods selected in the portal, guest/contractor template and Persistent Agent credential configuration. For example, a portal may default to LDAP while the matching authentication policy forces local authentication. If the method is not enabled in the policy, the default method is used. This is a policy-selection and method-precedence issue, not necessarily a RADIUS outage.

Configuration and evidence

In Policy & Objects > Authentication, create or edit the policy and set Enable Authentication, Authentication Method (if required), Time in Production before Authentication, Time Offline before Deauthentication and Reauthentication Frequency. Pair it with the intended User/Host Profile and order it above the catch-all. Use Policy Details to inspect the selected policy, profile and configuration. The Debug Log in Policy Details exposes the assessment process and is more useful than looking only at the final VLAN.

  • A successful RADIUS Access-Accept proves the identity provider accepted the credentials; it does not prove which NAC policy matched or which VLAN was applied.
  • A host that reconnects within the offline timer may retain authentication; a reconnect after expiry should require authentication again.
  • A host moved to the authentication VLAN at the reauthentication interval may be behaving exactly as configured, even if the RADIUS server is healthy.

Operational troubleshooting

When an endpoint is challenged unexpectedly, record the last authentication time, disconnect duration and current policy. Compare those values with the offline and periodic reauthentication timers. When a host remains in production while waiting, verify the production grace period and whether a matching policy is actually assigned. When a host receives the wrong method, inspect policy order and Authentication Method override before changing the portal's default. The related Community RADIUS-proxy article is useful context for separating external authentication from NAC treatment, but it is older than the 30-day window and is not used as the primary feature source.

Operational scenario. A laptop is disconnected for twelve minutes and reconnects. The offline retention timer is ten minutes, so the prior authenticated state has expired and the endpoint is required to authenticate again. Increasing the RADIUS timeout would not fix this policy timer behavior.

FortiNAC-F

FortiNAC-F 802.1X with Microsoft Entra ID using EAP-TTLS/PAP

610 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. FortiNAC-F 7.6.5 documents Microsoft Entra ID as an authentication source for 802.1X using EAP-TTLS with PAP as the inner method. This is not the same as a conventional PEAP deployment against on-premises AD, nor is it the same as EAP-TLS certificate authentication. The outer EAP-TTLS exchange establishes a protected TLS tunnel to the FortiNAC-F Local RADIUS service; PAP credentials are carried inside that tunnel and validated through the Entra ID service connector.

Components and transaction flow

The endpoint supplicant is the 802.1X peer. The access switch or wireless authenticator forwards EAP messages in RADIUS to FortiNAC-F. FortiNAC-F's Local RADIUS service terminates the EAP-TTLS tunnel and uses the configured Microsoft Entra ID mapping/service connector as the identity source. Entra application credentials and tenant information allow the connector to authenticate to Microsoft. When the credentials are accepted, the RADIUS result returns through the authenticator; FortiNAC-F's network access policy then determines whether the endpoint is registered, remediated or placed in a production VLAN. Identity authentication and NAC authorization remain separate decisions.

Configuration sequence

  1. Register the FortiNAC application in Microsoft Entra ID and record the tenant/application identifiers and required credential material.
  2. Configure the FortiNAC-F Local RADIUS TLS service. The cookbook lists this as a prerequisite for the TTLS-PAP use case; ensure the server-side TLS certificate and service are ready before testing endpoints.
  3. Create a Service Connector in Network > Service Connectors for the Entra ID application and configure the authentication source.
  4. In Network > RADIUS > Virtual Servers, create the Microsoft Entra ID mapping for the user's domain and select the service connector.
  5. Edit the RADIUS virtual server and enable TTLS in Supported EAP Types. Set the Authentication Source to the Entra-backed mapping.
  6. Configure the Windows supplicant to use EAP-TTLS with PAP as the inner method. Do not leave it on PEAP merely because that is the workstation's previous default.
  7. Enable 802.1X on the switch/AP path and verify the correct RADIUS server is selected. Ensure the FortiGate/FortiSwitch integration and production/registration VLAN configuration are consistent.

Critical limitation

Fortinet explicitly warns that EAP-TTLS PAP with Entra ID does not support MFA. The documented flow uses the resource-owner-password-credentials pattern, which is incompatible with MFA requirements. Do not deploy it for a policy that requires interactive or conditional-access MFA without selecting a supported alternative authentication design. This limitation is a design constraint, not a transient RADIUS fault.

Evidence and troubleshooting

  • Check the Windows supplicant's selected EAP method first. A PEAP attempt against a TTLS configuration can fail immediately even when the Entra connector works.
  • Inspect FortiNAC-F RADIUS logs for Access-Request/Access-Reject and the EAP method progression. A connector Test/Poll success does not prove a full 802.1X exchange.
  • Confirm Local RADIUS TLS service readiness and the certificate used by the server side of the EAP tunnel.
  • After Access-Accept, inspect the FortiNAC-F policy and resulting VLAN. A successful identity response does not prove the endpoint passed registration or compliance.

A FortiNAC-F Community case published on 2026-10-22 at 08:34 UTC (just outside this run's strict 30-day cutoff) shows Entra group import failing when a group description exceeds FortiNAC's 255-character field limit. The diagnostic is Data too long for column 'description' in output.master after enabling diagnose debug plugin enable AzureADApplicationInterface and polling the connector. Shorten the group description and disable debugging afterward. This is a group-sync failure, not an EAP-TTLS/PAP authentication failure; it illustrates why successful 802.1X authentication, Entra connector polling and remote-group population must be verified as separate stages.

Because the documented permission is broad, use a dedicated mailbox and a dedicated application rather than a general administrator mailbox. config secret setting

Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. Expired or unexpectedly removed certificates can break TLS services, VPNs, device authentication, code-signing and application trust. FortiSIEM's Windows Agent can monitor certificate stores and generate events when certificates are added, removed, expiring or expired. This provides an event source for alerting before a service failure, but it is a store-change/expiry monitor—not a complete PKI validation engine.

Collection architecture

The Windows Agent is installed and registered in the FortiSIEM CMDB. A Windows Agent Monitor Template defines what the agent should observe. Certificate Monitoring settings are selected per certificate store. A Host-to-Template Association binds the template to one or more Windows hosts, and the administrator applies the association so the Supervisor distributes the monitoring policy. The agent observes the selected stores and emits event records that are transported into FortiSIEM for event search, reports and correlation rules.

Configuration workflow

  1. Install the supported Windows Agent and verify that the host appears in the FortiSIEM CMDB with the expected hostname.
  2. Go to Admin > Setup > Windows Agent and create or edit a Windows Agent Monitor Template.
  3. Open Certificate Monitoring. For each required certificate store, enable the operations to monitor: Add, Delete, Expiring and Expired. Configure the days-before-expiry threshold for Expiring and the relevant expired threshold.
  4. Create or edit a Host-to-Template Association, select the host(s), attach the template and save.
  5. Use Apply on the association so the Supervisor distributes the monitoring policy to the agent.

Fortinet documents that no additional configuration is required on the Windows host beyond installing and registering the agent. The template and association are configured on the FortiSIEM side.

Event evidence

Search Resources > Event Types for AO-WUA-Certificate-. The documented event types include:

  • AO-WUA-Certificate-Added — a certificate was added to a monitored store.
  • AO-WUA-Certificate-Removed — a certificate was removed from a monitored store.
  • AO-WUA-Certificate-Expired — a certificate is expired.
  • AO-WUA-Certificate-Expiring — a certificate is approaching its configured expiry threshold.

Confirm the host, store, event type and timestamp in the raw event before building an alert. The certificate data model can also expose the certificate common name, fingerprint, store folder, issuer, issued-to value, valid-from/valid-to times, days-to-expiry, self-signed flag and CA flag. An event proves that the agent detected the configured store operation or expiry condition. It does not prove that a service is bound to that certificate, that the certificate chain is trusted, that revocation checking succeeds, or that the private key is usable by the application.

Troubleshooting and operational design

If no event appears, verify the host is online in CMDB, the template is attached, the association was applied, and the correct store and operations are enabled. Check agent status and raw event ingestion before changing correlation rules. If events arrive but alerts do not, troubleshoot the FortiSIEM rule, event grouping and time window separately. Set expiry thresholds to match certificate renewal lead time; a 30-day warning is not useful if the organization needs 60 days for change approval and deployment.

Use separate rules for impending expiry and actual removal/expiration. An unexpected removal from a machine certificate store may be more urgent than a normal renewal event. Avoid treating every certificate added event as malicious; correlate it with change windows, certificate issuer and host role.

Operational scenario. A Windows service fails after a certificate rollover. FortiSIEM shows a certificate removed event but no new certificate-added event for the expected store. That evidence narrows the investigation to the store update; it does not by itself prove which service binding is broken. Verify the service certificate binding and chain on the host.

Why this matters. A private application is not always a single server IP and port. A service may use a subnet of back-end nodes, a range of TCP ports or a set of fixed service ports. Objects and traffic path

The ZTNA application gateway is the secure entry point that mediates access to internal applications. FortiGate can serve as the gateway. A ZTNA private application represents the destination resource: IP, FQDN, wildcard FQDN, and—on supported FortiClient versions—IP range or CIDR plus port list/range. Configuration sequence

  1. In Security > Traffic > ZTNA > Agent-based, create a gateway with the name, FortiGate address/FQDN and ZTNA port.
  2. Create a private application. Choose IP range or CIDR for the destination and define the required ports, such as a list (80, 443, 8080) or a range (1000-2000).
  3. Associate the application with the gateway.
  4. Open Endpoint Management > Endpoint Profiles and create or edit a profile.
  5. Enable ZTNA, create a connection rule and select the new agent-based ZTNA application. Configure encryption and SAML browser behavior deliberately for the application/gateway.
  6. Apply the endpoint profile to the intended Windows endpoints and verify that the client has received it.

Version and scale constraints

Fortinet documents IP range/CIDR and port list/range support for FortiClient for Windows 7.2.8 or later. The FortiSASE instance must be on the Feature version for the Feature-only capability. Do not assume that an older FortiClient or a Mature instance can interpret the same object. FortiSASE documents a maximum of 32,000 ZTNA connection rules, so avoid creating unnecessarily granular duplicate rules.

Evidence and troubleshooting

  • Confirm the application object type, range/CIDR and ports in the portal. This proves the object is configured, not that an endpoint profile references it.
  • Confirm the endpoint profile contains the application in a ZTNA connection rule and that the endpoint is assigned the profile.
  • Check the FortiClient Windows version. If it is below 7.2.8, range/CIDR and port-list/range support is not met.
  • Verify the gateway address and port, and inspect the FortiGate ZTNA policy/logs. A matching client-side destination does not prove the gateway policy allows the session.

When encryption is enabled, traffic between FortiClient and the ZTNA application gateway is always encrypted even if the original application traffic is already encrypted. When disabled, that FortiClient-to-gateway leg is not additionally encrypted by this setting. This is a separate decision from whether the original application uses TLS.

A new internal application uses a /24 back-end pool and TCP ports 8443 and 9443. The administrator creates the CIDR and port list in FortiSASE, but users still connect directly. Secure SD-WAN

Mapping SD-WAN member SLA priorities into BGP MED across dual hubs

563 focused words
Mechanics diagram

Standalone SVG for quick reference.

Open SVG · Edit draw.io source

Why this matters. In a dual-hub SD-WAN design, a spoke may have overlays to more than one hub. Local SD-WAN steering decides which member is preferred for traffic leaving the spoke, but remote networks also need a way to prefer the hub that has the better path back to that spoke. FortiOS can map SD-WAN member priorities into the BGP Multiple Exit Discriminator (MED) attribute when the spoke advertises routes to hubs using iBGP. The hubs can then advertise those prefixes to external eBGP peers with relative MED values.

Mechanics and control flow

The spoke runs an SD-WAN health check over selected overlay members. The SLA state and configured priority-in-SLA/priority-out-SLA values describe the member's current suitability. Under config system sdwan config neighbor, the BGP neighbor is associated with the member set, a health check and a route-metric mode. In priority mode, the member's priority-in-sla/priority-out-sla values influence the MED used for the advertised route. In preferable mode, the health-check state is used to match BGP preferable/unpreferable route-map behavior. These modes are not interchangeable: one exports member priority values, the other follows the health-check preferable/unpreferable result.

Configuration pattern

config system sdwan
    config neighbor
        edit "10.255.0.1"
            set member 1 2
            set route-metric priority
            set health-check "Remote_HC"
        next
    end
end

config system sdwan
    config health-check
        edit "Remote_HC"
            set detect-mode remote
            set sla-id-redistribute 1
            set members 1 2
            config sla
                edit 1
                    set link-cost-factor remote
                    set priority-in-sla 100
                    set priority-out-sla 200
                next
            end
        next
    end
end

The exact neighbor IP, member IDs, health-check name and SLA values must match the topology. The spoke's BGP neighbors are commonly loopback addresses reachable through overlays. The hub advertises the spoke prefixes onward to external eBGP peers. The external router compares the MED values of eligible paths; by default, MED is compared among paths from the same neighboring AS, and vendor/router policy can alter path selection. Do not treat MED as a universal global preference that overrides every other BGP attribute.

Verification

  • diagnose sys sdwan health-check shows overlay state, loss, latency, jitter, bandwidth and SLA map. It proves the local health-check result, not what the hub advertised.
  • get router info bgp neighbors <peer> advertised-routes on the hub/external side shows the route and its Metric (MED). Compare both hubs for the same prefix.
  • Inspect the external router's best path. The route advertised by Hub-1 with MED 50 is preferred over Hub-2 with MED 60 in Fortinet's example, assuming the other BGP attributes and comparison rules allow MED to decide.

Failure isolation and caveats

If the external network uses the wrong hub, verify the spoke neighbor's member list, health-check binding, route-metric mode and priority-in-sla/out-sla values. Then verify that both hubs advertise the same prefix with the intended MED. Finally inspect the external router's BGP decision process; a lower MED may not win if a higher-precedence attribute or local policy decides first. The related Community BGP MED technical tip is useful for understanding how a failed health check can drive an extremely unattractive metric, but it is older than the current 30-day window and is not a primary source.

Operational scenario. Both hubs have healthy tunnels, but the external router prefers Hub-2. The spoke's Remote_HC reports different member priorities, yet the BGP neighbor uses preferable mode rather than priority. Confirm the intended mode, inspect the advertised MED from each hub and validate the external BGP best path before changing local SD-WAN service rules.
