1. FortiGate — Recursive DNS resolver

Primary feature source: https://docs.fortinet.com/document/fortigate/7.6.0/new-features/413462/7-6-0

Mechanism

FortiOS can operate as a recursive DNS resolver. This makes the DNS listener, cache decision, iterative recursion and returned response separate engineering boundaries. A client answer does not identify whether the response was cached or required external recursion.

Transaction and operational implication

Client query → FortiGate DNS service → cache lookup → recursive lookup when needed → response. Test a cached and deliberately uncached name because a cache hit can mask a broken authoritative/delegation path.

Evidence interpretation: A successful query proves that transaction was answered. A cache hit does not exercise recursion; an uncached successful answer proves the recursive path worked for that name.

Scenario

Do not treat object existence or configuration intent as proof of the downstream transaction. For this lesson the troubleshooting boundary is specifically the Recursive DNS resolver mechanism described above, not a generic policy/transport checklist.

2. FortiManager — Certificate-backed SD-WAN overlay templates

Primary feature source: https://docs.fortinet.com/document/fortimanager/7.6.0/new-features/512197/certificate-certificate-template-integrated-to-the-sd-wan-overlay-template

Mechanism

FortiManager SD-WAN Overlay Templates can use signature-based IPsec authentication instead of the default PSK. The wizard can select a Fortinet certificate, a custom local dynamic certificate, or a metadata variable resolving a certificate name per device.

Overlay Template → Signature authentication → certificate/template or metadata mapping → generated IPsec templates → install → IKE. Per-device mapping matters when certificate names differ across branches.

Evidence interpretation: Template configuration proves intent; metadata resolution proves FortiManager chose a certificate name; install success proves acceptance; only established IKE proves certificate authentication completed.

3. FortiAnalyzer — FortiSOC Connector incident handoff

Primary feature source: https://docs.fortinet.com/document/fortianalyzer/7.6.7/administration-guide

Mechanism

FortiAnalyzer SOC workflows can hand incident/event state to external response integrations. Detection inside FortiAnalyzer and successful external handoff are different transactions.

Transaction and operational implication

Analytics logs → event logic → incident → connector invocation → remote acknowledgement. If an event already exists, troubleshooting detection again skips the actual connector boundary.

Evidence interpretation: An event proves detection. Connector execution proves an outbound attempt. Remote acknowledgement proves the external endpoint accepted the transaction, not that remediation finished.

4. FortiSwitch — Unintended FortiLink adoption across L2 extensions

Primary feature source: https://docs.fortinet.com/document/fortiswitch/7.6.7/fortiswitchos-cli-reference/320376/config-switch-controller-global
Scenario source: Fortinet Community, Sep 9 2026

Mechanism

A standalone FortiSwitch on an L2-extended network can expose FortiGate Access Controller discovery beyond the local site. Fortinet's recent Community guidance shows why AC discovery must be considered separately from other automatic FortiLink/ISL controls.

Transaction and operational implication

Standalone switch → AC discovery → extended L2 domain → remote FortiGate discovery → possible adoption. The L2 domain is part of the management-plane blast radius.

Evidence interpretation: Discovery traffic proves AC discovery is active. A FortiGate listing the switch proves discovery crossed the L2 boundary. Adoption/configuration change is a later boundary.

5. FortiAP — FortiAP management through IPv6

Primary feature source: https://docs.fortinet.com/document/fortigate/7.6.0/new-features/4/change-log

Mechanism

Fortinet added FortiAP management through IPv6 in the 7.6.5 feature train. This is a control-plane reachability capability: IPv6 addressing/routing, controller discovery, CAPWAP establishment and AP authorization remain distinct stages.

6. FortiNAC — NetFlow-driven profiling

Primary feature source: https://docs.fortinet.com/document/fortinac-f/latest/administration-guide/164904/netflow-support

Mechanism

FortiNAC supports NetFlow v5, v9 and IPFIX as profiling input. Exporters send to FortiNAC on port 2055 and FortiNAC-OS must allow NetFlow. Records appear in Users & Hosts > Network Sessions and can feed the Network Traffic profiling method.

Transaction and operational implication

Exporter → UDP flow records → FortiNAC listener → Network Sessions → profiling rule. If sessions contain the records, changing exporter settings is no longer the first troubleshooting move.

Evidence interpretation: Exporter config proves intent, not delivery. Network Sessions proves ingestion/representation. A profiling match proves the traffic evidence satisfied that rule; access enforcement is downstream.

7. FortiNAC-F — Secure SSID device onboarding

Primary feature source: https://docs.fortinet.com/document/fortinac-f/7.4.0/administration-guide/659283/fortinac

Mechanism

FortiNAC-F documents secure/open SSIDs for guest management and device onboarding. The important mechanism is endpoint state transition from onboarding access through registration to production authorization.

8. FortiAuthenticator — SCEP enrollment and renewal

Primary feature source: https://docs.fortinet.com/document/fortiauthenticator/6.6.0/administration-guide/524036/general

Mechanism

FortiAuthenticator SCEP can automatically sign eligible requests or hold them for administrator approval. Configuration selects a default CA, enrollment password behavior, approval method, and whether an old certificate is revoked on renewal.

Transaction and operational implication

CSR → challenge/approval → CA signing → certificate issuance → optional old-certificate revocation → relying-party use. Renewal and revocation are separate lifecycle transitions.

Evidence interpretation: Pending proves CSR receipt. Issued proves CA signing. Renewal does not prove old-certificate revocation unless revocation state is verified. Successful authentication proves a relying party accepts the new identity.

9. FortiPAM — Secret custody versus privileged-session launch

Primary feature source: https://docs.fortinet.com/document/fortipam/latest/administration-guide

Mechanism

FortiPAM separates policy approval, secret checkout, target authentication and proxied privileged-session launch. These are not interchangeable success signals.

Transaction and operational implication

Request/policy → approval → checkout or launch → target authentication → optional proxy/recording → later rotation. Diagnose the first transition without positive evidence.

Evidence interpretation: Approval proves authorization. Checkout proves secret release. Target login proves credential acceptance. Recorded/proxied session proves traversal of the FortiPAM session path; rotation remains separate.

10. FortiSIEM — Windows Agent component trust and restart isolation

Primary feature source: https://docs.fortinet.com/document/fortisiem/latest/agent-user-guide

Mechanism

FortiSIEM Windows Agent health includes component loading before collection and forwarding. A recent support pattern involving a signed DLL shows why a restart loop can be a local component-load failure rather than a Supervisor ingestion failure.

Transaction and operational implication

Service start → component trust/load → collector initialization → event acquisition → forwarding → Supervisor ingestion. A crash before collector initialization makes server-side parsing downstream of the first failure.

Evidence interpretation: A momentary Running state proves only process state. Component/signature errors identify a local load boundary. Forwarded test events prove acquisition and transport progressed; Supervisor ingestion is next.

11. FortiSASE — DNS proxy session accounting

Primary feature source: https://docs.fortinet.com/document/fortisase/latest/administration-guide

Mechanism

FortiSASE Security PoPs can proxy DNS, so the client-facing transaction and an upstream DNS transaction are separate sessions. A client-side log with zero sent bytes can therefore be legitimate when the PoP answers from cache or performs upstream resolution separately.

Transaction and operational implication

Client → SASE PoP DNS proxy → cache decision → optional upstream DNS session → response. Do not expect upstream bytes to be represented on the client leg.

Evidence interpretation: Client DNS log proves client-to-PoP observation. Zero sent bytes does not prove failure. A returned answer proves satisfaction; a separate upstream session proves the proxy crossed outward for resolution.

12. Fortinet Secure SD-WAN — Hub BGP suppression when all spoke links fail

Primary feature source: https://docs.fortinet.com/document/fortigate/7.6.0/sd-wan-new-features/832953/whats-new-in-7-6-5

Mechanism

Secure SD-WAN can suppress BGP routes at a hub when all links to a spoke are down, preventing a control-plane advertisement from attracting traffic to an unreachable spoke.

Transaction and operational implication

Per-link health → aggregate spoke reachability → BGP advertisement state → upstream propagation. One failed link does not imply spoke withdrawal while another usable path remains.

Evidence interpretation: One member down proves only that member failed. Suppressed advertisement after all links fail proves the SD-WAN state affected BGP. Upstream withdrawal proves propagation; application traffic verifies forwarding after recovery.
