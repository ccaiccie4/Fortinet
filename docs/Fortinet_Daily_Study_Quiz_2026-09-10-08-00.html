1. FortiGate — BGP graceful restart: stale routes are a temporary forwarding contract

Primary source: FortiOS 7.6.6 Troubleshooting BGP

BGP graceful restart (GR) is useful when the routing process or HA control plane is temporarily unavailable but forwarding can continue. FortiGate can advertise GR capability and can act as the restarting router or as a helper for a restarting neighbor. Before a planned restart, peers learn that the speaker is restarting; rather than immediately withdrawing every learned route, they mark the affected routes stale and retain them for the configured stale-path interval. That distinction is critical: a route remaining in the table during GR does not prove the control plane is healthy. It proves the helper is intentionally preserving forwarding state while waiting for the speaker to return.

FortiOS exposes graceful-restart, graceful-restart-time, graceful-stalepath-time, graceful-update-delay, and per-neighbor capability-graceful-restart under config router bgp. Fortinet specifically notes the benefit to HA clusters: failover can avoid appearing as an ordinary route flap and the new main unit has time to return with usable routing state. The safety boundary is the timer. If the speaker does not return in time, retained stale paths must stop being treated as usable.

Evidence interpretation: an Established neighbor proves the BGP session is currently up; GR capability proves the restart behavior was negotiated/configured; a stale route during restart proves retention is working. None proves the next hop still forwards packets. Verify the forwarding path separately before treating stale-route retention as service continuity.

2. FortiManager — Workflow mode: configuration becomes an ordered approval transaction

Primary source: Enable workflow mode

Workflow mode changes FortiManager from direct editing into a controlled transaction model. It can be enabled globally or per ADOM. Once enabled, Device Manager and Policy & Objects are read-only until the administrator locks the ADOM and starts a workflow session. The lock is therefore not just an administrative courtesy: it is the prerequisite that creates an isolated change context. Approval groups can be configured per ADOM, with optional email notification through a selected mail server.

Inside the session, changes can be saved for later, discarded, or submitted. A saved session blocks creation of another session until it is submitted or discarded. Submitted sessions are reviewed by the configured approvers, and Fortinet documents that sessions must be approved in the order they were created. That ordering matters when two proposed changes depend on one another: approval is serialized rather than allowing a later session to leapfrog an earlier one. Changing workspace mode ends the current login session, which is a useful operational clue when enabling the feature.

Evidence interpretation: an ADOM lock proves an administrator owns the edit context; a workflow session proves a change transaction exists; approval proves governance accepted the transaction. None of those proves installation to a FortiGate succeeded. Installation/task results are the next boundary.

3. FortiAnalyzer — Event handlers: analytics logs become events through explicit rule semantics

Primary source: Event handlers

FortiAnalyzer distinguishes basic event handlers from correlation event handlers. A basic handler generates an event when any enabled rule matches; its rules have an OR relationship. A correlation handler instead evaluates a sequence and supports operators including AND, AND_NOT, OR, FOLLOWED_BY, and NOT_FOLLOWED_BY. This means correlation is not merely a longer filter: ordering and absence can be part of the detection condition.

Data selectors and notification profiles are separate reusable objects. The data selector scopes devices, subnets, and filters; the notification profile determines where an alert is sent after an event exists. Event handlers operate per ADOM, and Fortinet explicitly states that handlers generate events from Analytics logs, not Archive logs. In Analyzer–Collector deployments, the Analyzer evaluates the handlers. A common troubleshooting mistake is therefore to prove that a Collector archived a binary log and conclude that a handler should fire; the required evidence boundary is Analyzer analytics ingestion plus a matching enabled handler.

Evidence interpretation: handler Enabled proves it is eligible to evaluate logs; an Analytics log proves the input reached the searchable analytics store; a generated event proves rule evaluation matched. Notification delivery is a later boundary governed by the notification profile.

4. FortiSwitch — MCLAG: node redundancy without forcing STP to be the failover mechanism

Primary source: MCLAG

A normal LAG protects against individual link failure; MCLAG extends that idea across two FortiSwitch units so a downstream peer can treat links to two physical switches as one logical aggregation. The design therefore removes a switch chassis as a single failure point and can avoid the convergence delay that would occur if STP had to unblock an alternate path after a node failure. Fortinet requires the MCLAG trunk name to match on both switches, which is a concrete configuration invariant rather than a cosmetic naming preference.

MCLAG does not make every upstream dependency redundant. Fortinet recommends link monitoring or BFD for static-route gateway reachability in standalone, MCLAG, or layer-3 MCLAG topologies. This is an important boundary: an aggregation can remain logically healthy while an upstream gateway behind one path is unusable. Split-brain detection is likewise a separate concern because two peers acting independently can create forwarding inconsistency even though local ports remain up.

Evidence interpretation: member links up prove physical/LAG participation; peer state proves the two chassis are coordinating; downstream LAG up proves the attached peer sees an aggregate. None proves an upstream static-route gateway is reachable—use link monitor/BFD or equivalent route-path evidence for that boundary.

5. FortiAP — 802.11k and 802.11v: informing versus steering a roaming client

Primary source: Advanced SSID options

Fortinet exposes 802.11k and 802.11v independently on the SSID. With 802.11k, APs provide neighboring-AP and site information so the client can make a better roaming decision without blindly scanning every possibility. It is fundamentally assistance: the client still chooses whether and when to roam. With 802.11v, the infrastructure can take a more active role in transition behavior; Fortinet describes steering clients away from congested APs when another AP has better RSSI.

The distinction prevents a common diagnostic error. Seeing a valid 802.11k neighbor report does not prove the station will roam, because client roaming logic remains involved. Conversely, enabling 802.11v does not make RF conditions irrelevant: the decision still depends on alternative AP conditions and client support. FortiOS also exposes set 80211k and set 80211v under the VAP configuration, while 802.11r Fast BSS Transition is a separate advanced option.

Evidence interpretation: SSID configuration proves the AP is allowed to offer k/v assistance; neighbor-report exchange proves 802.11k information is available; a BSS transition interaction proves 802.11v steering was attempted. Only the client association moving to the target AP proves the roam completed.

6. FortiNAC — Device Profiler: ordered classification of rogues changes their management lifecycle

Primary source: Device profiling rules

FortiNAC Device Profiler evaluates rogue hosts against enabled profiling rules. As a rogue connects and obtains an IP address, available attributes are compared with methods in ranked rules until a match is found. Rule order therefore affects both performance and outcome. Fortinet recommends placing inexpensive/high-confidence methods such as OUI first, DHCP next, and active/TCP-UDP/IP-range/location methods later. Static-IP environments require special care because a device that never emits DHCP cannot provide a DHCP fingerprint; placing a required DHCP method too early can stop useful evaluation.

A match can move the endpoint into Inventory, register it into Host View, associate it with a user, or leave it as a rogue associated with the rule for later management. That transition matters because Device Profiler does not keep re-evaluating devices that are no longer rogues. The Catch All rule remains at the end, and already categorized devices are not changed simply by pressing Run after modifying rules. Incorrectly registered classification may require manual correction or deletion so the endpoint can return as a rogue and be evaluated again.

Evidence interpretation: Rogue Evaluation Queue proves work is waiting; Rule Name on a profiled device proves which rule matched; Device Profile Rule Missing Data proves evaluation lacked an attribute such as DHCP fingerprint. Registration proves lifecycle transition, not that later network-access policy enforcement succeeded.

7. FortiNAC-F — RADIUS local versus proxy mode: who actually authenticates the endpoint?

Primary source: Configure the appropriate server option

FortiNAC-F can process RADIUS using its built-in local server, external RADIUS servers, or a combination. In Proxy mode, FortiNAC processes RADIUS MAC authentication by default while proxying 802.1X EAP authentication to the customer-owned external RADIUS server; an option can also proxy MAB requests. Accounting is proxied to the external server. In Local mode, FortiNAC's Local RADIUS Server handles MAC and 802.1X EAP authentication itself, but the local server does not provide accounting; accounting can still be proxied externally.

The mode is configured per device, so two access devices can legitimately have different authentication paths. Integration guidance also warns against asymmetric routing between the network device and FortiNAC: RADIUS requests and responses must traverse the same FortiNAC interface. FortiNAC-F learns connection state from RADIUS, while disconnect awareness can depend on other mechanisms such as syslog or polling depending on the integration.

Evidence interpretation: an Access-Request arriving at FortiNAC-F proves NAS-to-NAC reachability; in Proxy mode it does not prove the external RADIUS server answered. An Access-Accept proves the authentication transaction succeeded, but VLAN/role enforcement and later CoA are separate boundaries.

8. FortiAuthenticator — HA modes: full failover and geographic load balancing solve different problems

Primary source: High availability

FortiAuthenticator documents two distinct HA modes. Cluster mode is active-passive failover and synchronizes all configuration between cluster devices. Load-balancing mode is active-active: one unit is a standalone primary and up to ten geographically separated load-balancers can serve authentication load. Distribution can use round-robin DNS, Auth/NAS client distribution, or external load balancers.

The important design boundary is synchronization scope. Load-balancing mode is intended for two-factor authentication deployments and synchronizes only a subset of configuration, so it must not be mentally modeled as a geographically stretched active-active copy of cluster mode. The modes can be combined: an HA cluster can act as the standalone primary for distributed load-balancers. Fortinet also documents an operational caveat that if HA is configured on an interface and then disabled, it cannot simply be re-enabled on that interface.

Evidence interpretation: cluster membership and synchronized configuration prove active-passive readiness; a load-balancer registered to the standalone primary proves distributed authentication topology. Neither alone proves a specific NAS is actually sending requests to the intended member—verify the client/load-distribution path.

9. FortiPAM — Password reconciliation: rotate the credential at its authoritative target, not the launcher

Primary source: Secret Password Rotation Using an Associated Secret and Password Reconciliation

FortiPAM's documented associated-secret pattern separates three responsibilities. Secret1 stores a higher-privileged reconciliation account on the domain controller. Secret2 stores the lower-privileged credential and also targets the domain controller; password reconciliation uses Secret1 to reset Secret2's account at the authoritative identity store. Secret3 is launcher-only, targets the jumpbox, and references Secret2 for the credential used to start the session. This separation prevents password management from being aimed at the system that merely consumes the credential.

Automatic Password Changing on Secret2 can run on a schedule, while Password Reconciliation selects the reconcile account and can reconcile directly. Fortinet warns not to put rotation/reconciliation on the launcher secret: doing so would make FortiPAM attempt the change against the jumpbox rather than the domain controller. The documented schedule is time-based; it does not mean the password rotates immediately when a session is checked in.

Evidence interpretation: FortiPAM's scheduled job proves rotation was requested; Windows Security Event ID 4724 on the DC, with the reconcile account as Subject and lower-privileged account as Target, proves the reset reached the authoritative store. A successful jumpbox launch afterward proves the associated credential remains usable end-to-end.

10. FortiSIEM — FortiDDoS integration: syslog parsing is the boundary before correlation

Primary source: FortiDDoS external-system integration

FortiSIEM monitors FortiDDoS security events through syslog. The integration documentation identifies more than 150 event types spanning protocol anomalies, traffic-volume anomalies, and DoS attacks, and maps the data into FortiSIEM security monitoring. Device support exposes FortiDDoS event types, while security exploit correlation rules and reports can consume the normalized events.

The operational sequence is therefore source event → syslog transport → FortiSIEM parser/event type → rule/report. A FortiDDoS attack counter increasing does not prove FortiSIEM received anything. Likewise, a packet arriving at the collector port does not prove parsing selected the intended event type. Correlation can only reason over the normalized event stream it actually sees, so parser evidence is the first useful boundary after transport.

Evidence interpretation: a FortiDDoS local event proves the source detected activity; received syslog proves transport; the normalized FortiSIEM event type proves parsing. Only then does a matching rule/incident prove correlation logic fired. Keep those boundaries separate when an expected incident is missing.

11. FortiSASE — Web Filter ordering: URL, category, then content

Primary source: Web Filter

FortiSASE applies Web Filter controls in a documented order: URL filter first, URL category second, and content filter third. The ordering matters when interpreting why a request was blocked; an earlier URL decision can make later content analysis irrelevant. By default there is one global Web Filter configuration applied through the default security profile group and default allow VPN or SWG policy. Administrators can create a custom profile group and apply it to a policy scoped to selected users or groups.

HTTPS introduces another boundary. Certificate inspection cannot inspect encrypted HTTP payload content, so content filtering of HTTPS requires SSL deep inspection. The same dependency applies to features such as enforced Safe Search. This is not merely a Web Filter toggle problem: if deep inspection is absent, the content stage cannot see the material it is supposed to evaluate.

Evidence interpretation: policy match proves the user/request selected the intended SWG or VPN policy; profile-group assignment proves which Web Filter configuration applies; a URL/category log can prove an earlier decision. For HTTPS content-filter behavior, verify deep inspection before blaming content-filter patterns.

12. Fortinet Secure SD-WAN — Performance SLA: measurement can withdraw and restore member routes

Primary source: SD-WAN performance SLA

FortiGate SD-WAN Performance SLA measures member-link health using active probes to a server or passive information captured from sessions matched by firewall policies. Link quality is expressed through latency, jitter, and packet loss. The result is not merely a dashboard score: when a link fails all health checks, FortiOS removes routes on that link from the SD-WAN load-balancing group so traffic can use other links; when the link passes again, the routes are reestablished.

This creates a direct chain from measurement to forwarding eligibility. A physical interface can remain up while SLA state makes it unsuitable for SD-WAN forwarding. Conversely, one probe target failing does not necessarily mean the member is unusable if the configured health-check logic still considers it healthy. The Performance SLAs GUI exposes configured servers, current quality values and thresholds, with green/red state indicating active/inactive at the last check.

Evidence interpretation: interface up proves carrier/link state; measured latency/jitter/loss proves probe or passive observations; SLA state proves FortiOS's health decision; route presence in the SD-WAN group proves forwarding eligibility. Application success remains a later end-to-end boundary.
