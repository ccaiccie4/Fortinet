6. FortiNAC — Portal Request Processing Rules: regex routing, duplicates and activation

Primary: Fortinet feature documentation · Scenario: Fortinet Community

Why request processing exists

The FortiNAC end-user portal is a web application used for authentication, registration and endpoint scanning. Browsers and operating-system captive-network assistants send HTTP requests with different URIs and user agents. FortiNAC Request Processing Rules (RPRs) classify those requests so the portal can allow them, block them, forward them to another destination, or return a specified file. They are not network access policies on a switch port; they are HTTP request routing decisions at the portal web-server boundary.

Rule evaluation and fields

The Administration Guide documents two matchable request fields: Request URI and HTTP User Agent. Each rule uses a regular-expression matcher and an action: Allow, Block, Forward or File. Forward and File require a target. A broad regex can match unintended requests; a literal dot must be escaped if the intent is to match an actual dot rather than any character. FortiNAC automatically orders rules when writing the web-server configuration. Changes in the GUI do not immediately change the live web server: the guide states that creating, editing or deleting rules requires restarting a process to take effect. This activation step is a separate control-plane boundary.

A concrete workflow

Suppose captive-network detection must be handled differently from full browser registration. A Request URI or User Agent matcher identifies the detection request and returns the intended file or response, while other requests continue through normal registration. Before adding a rule, inspect existing matchers for overlap. Create or edit it under Portal > Request Processing Rules, select the correct Field, Matcher, Action and Target, then apply the documented process restart during an approved maintenance window. Test both the special captive-network request and a normal browser registration request; one successful test cannot validate both paths.

Recent duplicate-rule failure

Fortinet's October 15, 2026 Community article documents a database with 102 RPR entries instead of 51, including exact and near duplicates. It identifies the `bsc.WebServiceDefinition` table and shows a read-only grouping query on service type, matcher, action and target to identify duplicates. Treat this as a diagnostic starting point, not authorization to delete arbitrary database rows. Near duplicates may differ in intended behavior or precedence. Before remediation, export the current configuration, establish which records are canonical, and follow supported Fortinet guidance for changes and service restart.

Evidence and recovery

Correlate the failing request's URI and User Agent with the RPR matchers and action. Compare the GUI rule list, effective web-server configuration after activation, browser developer-tools network trace, and portal application logs. An HTTP 302 to the wrong page suggests a forward decision; a missing or denied resource may reflect a block or file target; a request unaffected by a newly edited rule may mean the process has not been restarted. Avoid treating all captive-portal failures as RADIUS problems. This lesson isolates HTTP routing and activation from downstream user authentication, host registration, and VLAN enforcement.
