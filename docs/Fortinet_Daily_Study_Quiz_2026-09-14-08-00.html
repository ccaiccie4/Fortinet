1. FortiGate — FortiCloud SSO, HA identity, and post-failover serial validation

FortiCloud SSO allows administrative login through FortiCloud identity rather than a local password. In FortiOS 7.6.5 the feature is controlled globally with admin-forticloud-sso-login; IAM and non-IAM users are supported, and Fortinet recommends restricting administrative access to non-public interfaces and least privilege. Current 7.6.5 documentation also carries a security caution that server-side functionality was disabled because of FG-IR-26-060 until a patched version is used.

The important troubleshooting model is that successful identity-provider authentication is not the end of the transaction. The browser is redirected to FortiCloud, an SSO request is associated with appliance identity, FortiCloud returns an assertion/response, and FortiOS validates the returned identity before creating the administrator session. In an HA cluster, the appliance identity participating in request construction matters. A September 8, 2026 Fortinet Community technical tip documents issue 1286934: after failover, the BIOS certificate on the secondary can be used to generate the SSO request while the SSO daemon continues on the primary. The primary then sees a serial number in the IdP response that does not match its own and rejects the login.

This creates a useful evidence boundary. A user reaching FortiCloud and authenticating successfully proves browser-to-IdP reachability and credential acceptance, but it does not prove the FortiGate will accept the returned response. Correlate HA role with httpsd and samld debug during one fresh login:

diagnose debug reset
diagnose debug application httpsd -1
diagnose debug application samld -1
diagnose debug console timestamp enable
diagnose debug enable

The documented affected branches are 7.2, 7.4, 7.6, and 8.0; the Community article states fixes in 7.4.13, 7.6.7, and 8.0.1 and states that no workaround is available. Operationally, that means repeatedly changing IAM permissions, browser cookies, or local admin profiles is the wrong repair when the debug shows the serial mismatch after failover. The remediation boundary is software version, followed by a fresh post-failover SSO transaction.

Primary: FortiCloud SSO. Scenario: HA serial mismatch technical tip.

2. FortiManager — script targets, database scope, and Central DNAT attachment

FortiManager scripts are not merely remote command macros. Their semantics depend on the selected target: a script can run against FortiGate devices, policy packages, the ADOM database, global policy package, or device database. FortiManager 7.6.6 documentation also distinguishes direct-to-device execution from database-oriented execution. With workspace enabled, changes pushed through scripts may require saving in Policy & Objects, and direct device changes can require a later import to bring FortiManager's database back into alignment.

The September 9, 2026 Community scenario exposes a subtle object/reference distinction. A script that creates a VIP object in a policy-package/ADOM context can successfully create the object without attaching that VIP to a Central DNAT policy. The script itself may therefore report success while the intended policy behavior is absent. The missing transaction is not object creation; it is the reference relationship between the VIP and the Central DNAT construct.

Evidence should be collected in sequence: script execution history proves whether FortiManager accepted and ran the script; the object database proves whether the VIP exists; the Central DNAT table proves whether the object is referenced; install preview/device diff proves what FortiManager intends to render; and the FortiGate configuration/runtime proves what was installed. Stopping after “VIP exists” confuses object state with policy membership.

The Community example adds an explicit config central dnat stanza after creating the VIP so that the object becomes attached to Central DNAT. The broader design rule is to treat automation as a graph of objects and references, not a bag of CLI lines. A successful create operation is not proof that all dependent references were created.

Primary: FortiManager Scripts. Scenario: Central DNAT script technical tip.

3. FortiAnalyzer — dataset semantics and bandwidth interpretation

FortiAnalyzer reports are generated from datasets. A chart or macro does not “read bandwidth” generically; it references a dataset, and that dataset defines the log type, SQL query, filters, aggregation, and therefore the semantic meaning of the displayed number. FortiAnalyzer 7.6.6 allows predefined datasets to be copied and modified, which is convenient but also means two visually similar charts can calculate different quantities.

The September 1, 2026 Community guidance explains why interface bandwidth/utilization values can differ from traffic-log-derived bandwidth or a point-in-time interface observation. Different data sources, filters, sampling periods, and report time ranges produce different values. The correct troubleshooting question is therefore not “which number is wrong?” but “what population, interval, and aggregation does each number represent?”

Verification begins at the chart/macro and walks backward: identify its dataset, inspect the dataset SQL and log type, record filters and time range, then compare that definition with the other measurement. A live interface counter can be perfectly correct for the instant it was sampled while a report is also correct for an averaged or aggregated historical interval. Likewise, traffic logs describe logged traffic, not necessarily every physical-interface counter increment.

The operational implication is that report validation requires semantic equivalence before numeric comparison. If two charts disagree, first make their source, time window, filter, and aggregation equivalent. Only after that should you suspect ingestion or calculation defects. This avoids “fixing” a report whose dataset is answering a different question.

Primary: Creating datasets. Scenario: Bandwidth/utilization interpretation.

4. FortiAuthenticator — OAuth service and OIDC transaction boundaries

FortiAuthenticator 6.6.6 can act as an OAuth authorization server. A client authenticates and obtains an access token, then presents that token to a third-party service; the service may contact FortiAuthenticator to validate the token. OIDC extends the model with an authentication policy, authorization code, and OIDC claims for participating clients. The OAuth service must be exposed on the applicable FortiAuthenticator interface through HTTPS/TCP 443, covering endpoints including /api/v1/oauth.

That creates several independent failure boundaries: interface/service exposure, client registration/policy, user authentication, authorization-code issuance, token exchange, claims, and resource-side token validation. Seeing the browser return from authentication does not prove a token was issued. Seeing a token does not prove the resource server accepts its audience/scope/claims. Troubleshooting should therefore follow one transaction and identify the first missing artifact.

Fortinet documents an important OIDC dependency: remote users work only when their account has been imported into FortiAuthenticator configuration. This is exactly the kind of prerequisite that can make generic “authentication is working” observations misleading. Validate the user representation, client/policy, redirect/code stage, token endpoint result, and downstream validation separately.

Primary: OAuth Service. A sufficiently recent, semantically unique Community scenario was not verified during this run, so this lesson is marked source-partial rather than pairing an unrelated troubleshooting article.
