01 · FortiGate · FortiOS 8.0.0

TCP congestion control with BBR: when the bottleneck model beats CUBIC

504 focused words · mechanism, configuration, evidence and troubleshooting

Purpose and mechanics

FortiOS 8.0 adds a global choice between the traditional CUBIC congestion controller and BBR (Bottleneck Bandwidth and Round-trip propagation time). CUBIC is the documented default. BBR is model-based: it estimates the bottleneck delivery rate and the path's minimum propagation RTT, then uses those estimates to regulate the sender's pacing and in-flight data. The practical target is a path where loss-based backoff leaves capacity unused or where large queues inflate latency. BBR is not a new SD-WAN steering rule, a WAN bandwidth reservation, a TCP window-scaling replacement, or a way to repair a lossy physical link.

The configuration surface is deliberately small:

config system global
    set tcp-congestion-control bbr
end

# Restore the documented default:
config system global
    set tcp-congestion-control cubic
end

This is a system-global selection, not a per-policy knob. Treat it as a change to the FortiGate TCP stack's congestion-control behavior for the applicable TCP traffic handled by the unit. Do not assume that every accelerated, proxied, or offloaded flow follows an identical code path without checking the release/model notes for the deployed platform. A configuration read-back proves the selected global value; it does not prove that a particular test flow exercised BBR.

How to validate without confusing TCP mechanisms

Use a controlled A/B test: same endpoints, file, direction, path, policy, MTU, server load, and test duration. Record throughput, RTT, retransmissions, and packet loss for CUBIC, then repeat for BBR. Avoid changing shaping, proxy mode, MSS, and congestion control in the same test; otherwise the result is not attributable. Capture the SYN and SYN/ACK as well as data packets. Window-scale negotiation occurs in the handshake. If scaling is absent, the receive window can cap throughput even when the congestion controller is healthy. The recent Community proxy case is a useful contrast: the reported low rate was associated with disabled TCP options and a receive-window ceiling, not proof that CUBIC or BBR was at fault.

Useful evidence includes show full-configuration system global for the selected algorithm, a packet capture filtered to the test hosts for MSS/window-scale/ACK/retransmission behavior, and a repeatable application transfer. A session-table entry confirms that a session exists; it does not expose the internal BBR bandwidth/RTT model. A single speed test is not a valid comparison if the path was idle in one run and congested in the other.

Operational interpretation

  • If RTT is stable but throughput is low and the negotiated receive window is small, investigate TCP options and endpoint receive-window behavior before changing congestion control.
  • If retransmissions and loss dominate, repair the loss source or queueing policy; BBR cannot manufacture capacity or correct a bad physical path.
  • If BBR improves throughput but materially raises latency for interactive flows, revert to CUBIC and investigate queue management and traffic mix.
  • Because the setting is global, stage the change, baseline representative flows, monitor both bulk and latency-sensitive traffic, and keep the rollback command ready.

Engineering takeaway: BBR changes how the sender estimates and probes path capacity. It does not change the TCP handshake's window-scale negotiation. Diagnose those as separate control mechanisms.

02 · FortiManager · FortiManager 8.0.0

Managing multiple FortiSASE tenants from FortiManager 8.0

465 focused words · mechanism, configuration, evidence and troubleshooting

What multitenancy changes

FortiManager 8.0 can add multiple FortiSASE instances as separate managed-device objects in Device Manager. This is a management-plane expansion: FortiManager can inventory and administer several isolated SASE environments from a central platform. It does not merge the tenants' security PoPs, user populations, policies, or data planes. The old FortiSASE Connector entry in Fabric View is removed; the supported onboarding path is Device Manager > Devices & Groups > Add Device > Add FortiSASE Device.

The account relationship is the authorization boundary. FortiManager and FortiSASE must be registered under the same FortiCare account, or be within the same FortiCloud Organization Unit/sub-OU hierarchy. If they are under the same FortiCare account, the FortiManager Key can be left blank. If the SASE instance belongs to a different FortiCare account but remains inside the same OU/sub-OU hierarchy, generate the key from FortiSASE Central Management Settings and enter it when adding the managed device. A key is not a mechanism for crossing unrelated FortiCloud organizations.

Onboarding sequence

  1. Confirm that the FortiSASE instance is eligible for central management. Central Management is a select-availability capability; if it is not exposed, request enablement through Fortinet Support, then enable it in the SASE portal.
  2. Confirm the FortiManager and SASE FortiCare/OU relationship before generating credentials. Do not troubleshoot a connector key when the accounts are outside the supported hierarchy.
  3. For a different account in the same OU tree, generate the FortiManager Key in FortiSASE Central Management Settings and copy it securely into the FortiManager Add FortiSASE Device form.
  4. Add each SASE instance as its own device. Place the devices in the intended ADOM for administrative organization, while preserving the tenant boundary.
  5. Verify each device object independently: tenant identity, connection/management status, and the expected ADOM placement.

What the evidence proves

A FortiSASE device visible in Device Manager proves that FortiManager has an object for that instance. It does not prove that Central Management is enabled on every tenant, that a policy was installed, or that users from one tenant can access another. The FortiManager Key establishes the permitted management association; it is not a tenant-shared secret for user authentication. The FortiSASE architecture guide also notes that each customer receives an isolated FortiSASE environment and that a FortiCare account accommodates one FortiSASE instance. For an MSSP, this normally means a root organization for the service provider and dedicated child OUs/accounts for customers.

When onboarding fails, check the account and OU relationship first, then Central Management enablement, then the key. If three tenants are visible under one ADOM, do not infer that they are one tenant. ADOM is FortiManager's administrative grouping; tenant isolation remains in the FortiSASE service.

Engineering takeaway: Treat FortiCloud organization hierarchy as the trust boundary, FortiManager Key as the cross-account association credential within that hierarchy, and ADOM as an administrative container—not as the tenant boundary itself.

03 · FortiAnalyzer · FortiAnalyzer 8.0.0

FortiData incident ingestion: from SIEM Xlog to Event Monitor

485 focused words · mechanism, configuration, evidence and troubleshooting

The ingestion path is staged

FortiAnalyzer 8.0 recognizes FortiData devices (device IDs in the FDTxxxxxx form) as supported devices. The source sends SIEM Xlog files to FortiAnalyzer. The same record can be observed at several distinct processing stages, and those stages must not be conflated:

  1. Device registration: add the FortiData device in Device Manager so FortiAnalyzer knows the source identity.
  2. Raw receipt: incoming Xlog files appear in Log View > Logs > Log Browse. This is evidence that the file reached the raw-log layer.
  3. Analytics insertion: records are inserted into the FortiAnalyzer SIEM database (siemdb) and become searchable under Log View > Logs > All.
  4. Event handling: the predefined Ingested External Alerts event handler is enabled by default and generates Event Monitor alerts from FortiData Issue logs.

FortiAnalyzer 8.0 documents three supported incident log types: Issue, Risk Record, and Integration Event. The default handler's behavior is intentionally narrower than the ingestion support: it triggers on Issue logs. Risk Record and Integration Event data can be used to create custom event handlers, but they do not automatically become Event Monitor alerts merely because the raw log was received.

Configuration and verification

Start by registering the FortiData device in Device Manager and confirm that the expected FDT identity is present. Then inspect Log Browse for the raw Xlog file. Search Logs > All for the same time window and incident type to confirm SIEM database insertion. Finally, inspect Incidents & Events > Event Monitor and the enabled Ingested External Alerts handler. For Risk Record and Integration Event, create a custom handler with a filter that matches the intended record type and a clear action/severity mapping.

The distinction is important during incident response. If a Risk Record exists in Log Browse but not in Logs > All, the problem is before or during SIEM database insertion. If it exists in Logs > All but no alert appears, the problem is likely event-handler coverage or filtering—not necessarily log transport. If Issue records are in siemdb but do not trigger alerts, verify that the predefined handler remains enabled and that its conditions still match the incoming record fields.

Evidence boundaries and operational design

  • Log Browse proves raw-file receipt; it does not prove normalized SIEM insertion.
  • Logs > All proves records are queryable from siemdb; it does not prove an event handler fired.
  • Event Monitor proves an alert was created; it does not prove every FortiData incident type is covered.
  • Custom handlers should be tested against representative Risk Record and Integration Event examples before production activation.

Keep the source timestamp, raw Xlog, parsed record and alert ID together when escalating. That gives the SOC a traceable chain from the FortiData incident to the FortiAnalyzer alert. Avoid treating a missing alert as a missing incident until the raw and database layers have been checked.

Engineering takeaway: FortiData support is both a log-ingestion feature and an event-mapping feature. Verify raw receipt, SIEM database insertion, and event-handler output as three separate stages.

04 · FortiSwitch · FortiSwitchOS 8.0.0

Auto-topology and auto-ISL: who owns the inter-switch ports?

501 focused words · mechanism, configuration, evidence and troubleshooting

Auto-topology is an ownership mechanism

FortiSwitch auto-network can automatically form an inter-switch link (ISL) between two switches. The feature discovers the peer relationship and creates an ISL trunk containing the physical links connected between the same pair. If another cable is added between those same two switches, it is automatically added to the existing ISL trunk. The generated trunk uses LACP-active mode. This is not merely a topology picture: auto-network owns the participating ports and applies a defined set of link properties.

Fortinet documents auto-network as enabled by default starting in FortiSwitchOS 7.2.0. A standalone switch that receives execute factoryreset also returns with auto-network enabled. In zero-touch management, VLAN 1 is initially used for native VLANs and auto-topology is enabled. An operator who assumes that a factory-reset switch has no auto-ISL behavior can therefore encounter a manual trunk conflict immediately after cabling.

ISL attributes and configuration

config switch auto-network
    set mgmt-vlan 101
    set status enable
end

# Disable auto-topology when the design requires manual trunks:
config switch auto-network
    set status disable
end
config switch global
    set auto-fortilink-discovery disable
end

The ISL's native VLAN is determined by mgmt-vlan; the allowed VLAN list is 1–4094; DHCP snooping is trusted; and STP edge is disabled. The same management VLAN is also the native VLAN on the internal switch interface. Fortinet explicitly warns not to use the same VLAN for mgmt-vlan and an existing switch virtual interface (SVI). Treat that as a design constraint, not a cosmetic GUI setting.

In FortiSwitchOS 8.0, the Switch > Interfaces image icon indicates whether auto-network is enabled; a blue icon indicates an active ISL trunk. CLI inspection of the switch trunk should show the generated trunk and auto-isl 1 on the relevant object.

Real failure: manual trunk creation is rejected

A common symptom is that a port cannot be added to a manually configured trunk because it is already a member of an automatically generated ISL. Deleting or renaming a visible trunk does not necessarily remove the discovery condition; if the peer link remains connected, auto-topology can recreate the ISL. First inspect the actual trunk/member ownership and peer topology. Then decide whether the links should remain an automatic ISL or become a manual trunk. If the design is manual, disable auto-network and auto-FortiLink discovery as appropriate, verify that the generated ISL is no longer active, and only then build the manual trunk.

Operational checks

  • Before changing the native VLAN, confirm that the selected management VLAN is not already an SVI.
  • Check all physical links between the same switch pair; a second cable may be auto-enrolled into the existing ISL.
  • After factory reset, explicitly verify auto-network and auto-FortiLink discovery instead of assuming they are off.
  • Remember that the auto-ISL's trusted DHCP-snooping and non-edge STP attributes are part of the generated topology; do not copy them blindly to ordinary access ports.

Engineering takeaway: When a manual trunk operation fails, determine whether auto-topology already owns the ports. The fix is a topology/ownership transition, not repeated attempts to edit the same member interface.

05 · FortiAP/Wireless · FortiOS 8.0.0 / FortiAP 8.0.0

802.1X RADIUS authentication survivability: cached re-authentication, not a local RADIUS server

499 focused words · mechanism, configuration, evidence and troubleshooting

What survives when RADIUS disappears

RADIUS authentication survivability is designed for a specific failure: the RADIUS server becomes unreachable after a wireless client has already authenticated successfully. The wireless controller can locally re-authenticate that previously authenticated station using cached credential material for a bounded interval. It is not a replacement RADIUS server, not an offline user database, and not a way to authenticate a first-time client whose credentials have never been cached.

For EAP-PEAP, Fortinet requires the RADIUS server to return the credential-hash attribute used by the survivability feature. The guide identifies either the Fortinet vendor-specific Fortinet-AS-Credential-Hash or the Cisco-style Cisco-AVPair value containing AS-Credential-Hash=. If the attribute is missing, the cache cannot provide the expected local re-authentication behavior for that PEAP user. The RADIUS server's root CA and server certificate must also be imported and bound globally so that the controller trusts the server during normal authentication.

Configuration model

Configure the global wireless certificate references, then enable survivability on the target VAP/SSID. The survivability interval is configured per VAP and is bounded from 3600 to 864000 seconds; the documented default is 86400 seconds.

config wireless-controller vap
    edit "Corp-8021X"
        set radius-auth-survivability enable
        set radius-auth-surviv-intv 86400
    next
end

The cache is populated by successful authentication. During a RADIUS outage, a station with a valid cached entry can reconnect until that entry's expiry. A new station has no matching cache record and should fail closed rather than receive access simply because the SSID is configured for survivability. When RADIUS returns, normal remote authentication resumes. Once the configured interval expires, the cached station is no longer authorized by this fallback.

Evidence and troubleshooting

Use diagnose wpa wpad radius-auth-surviv-cache <ssid> to inspect cached station entries, their expiration, VLAN, EAP type, user and group. Use diagnose wireless-controller wlac -d sta online to verify the station's current online state. A direct RADIUS test such as diagnose test authserver radius peap chap test1 123456 can fail while an already authenticated client remains online through the local cache; those observations are not contradictory because they test different paths.

When an existing client fails to reconnect, check whether it authenticated before the outage, whether its cache entry exists, and whether the entry has expired. For PEAP, inspect the returned credential-hash attribute. Then verify the global CA/server certificate bindings and the VAP interval. Do not extend the interval to mask a missing hash attribute or certificate problem.

Design boundary

  • Existing cached clients may survive; first-time clients cannot be assumed to authenticate.
  • The interval is a security/availability tradeoff: longer values extend outage tolerance but also extend reliance on cached authorization material.
  • Cache visibility proves that a local entry exists; it does not prove that the RADIUS server is healthy.
  • A successful direct RADIUS test proves the remote server path is available at test time; it does not prove every client has a valid cache entry.

Engineering takeaway: This feature preserves access for known stations for a configured period. It does not turn the AP into an always-available local RADIUS authority.

06 · FortiNAC · FortiNAC 9.4.8 (feature introduced in 9.4.0)

Preserve Port Names: interface labels, resync semantics and model re-indexing

472 focused words · mechanism, configuration, evidence and troubleshooting

Port labels have an ownership decision

FortiNAC builds the port name shown in Inventory from the switch name, ifName, and ifDescription. The switch may expose an interface description such as “AP-3F-East”, while an operator may have deliberately renamed the corresponding FortiNAC port to a local operational label. The 9.4 Preserve Port Names setting controls which system is authoritative when a refresh occurs.

Preserve Port Names is enabled by default. When enabled, switch-side port-name/label changes are not automatically copied into the FortiNAC database. When disabled, changed switch descriptions are updated during the next Resync Interfaces operation or after FortiNAC services restart. The setting exists globally under Network > Settings > Network Device and can also be adjusted at the device-model level under Network > Inventory > device Properties. A per-device setting is useful when one switch family is maintained by switch-side descriptions while another has FortiNAC-owned labels.

Resync is not the same as every poll

Resync Interfaces reads interface information from the modeled device and updates FortiNAC's representation. Under normal conditions it updates interface status. With port-name preservation disabled, it also refreshes descriptions. Routine L2 polling is concerned with state such as link status, learned MAC addresses and current VLAN; it should not be treated as proof that a full interface-description/model refresh occurred. The Community inventory-sync case illustrates this boundary: repeated status refreshes did not update a port description until the preservation behavior and model-refresh path were considered.

There is a second, more consequential boundary for chassis and stacked switches. When boards or units are added, removed or repositioned, the interface sequence may change. FortiNAC can re-index the interfaces; if re-indexing is required, it deletes and recreates interface models to represent the new sequence. Manual port-group assignments attached to those models can therefore be affected. A successful resync is not proof that all manually maintained port group relationships survived a hardware-layout change.

Verification and safe operation

  1. Compare the switch's current interface name/description with the port label shown in FortiNAC Inventory.
  2. Check the global Network Device Preserve Port Names value and the device-level override. Confirm which setting is authoritative for the modeled device.
  3. If switch-side descriptions should win, disable preservation at the appropriate scope and run Resync Interfaces. Do not use repeated L2 polling as a substitute.
  4. After a chassis/stack change, verify the interface index, name, status, VLAN and port-group membership. Reapply manual groups if models were recreated.

Use the setting carefully. Turning preservation off globally can overwrite intentionally maintained labels on every affected device model. Leaving it on can make a changed switch description appear stale in FortiNAC. Neither state is universally correct; the design decision is whether the network device or FortiNAC owns the operational label.

Engineering takeaway: Preserve Port Names governs description synchronization, while Resync Interfaces governs model refresh. A status poll, a description refresh and a chassis re-index are three different operations.

07 · FortiNAC-F · FortiNAC-F 7.6.7+

RADIUS-only device support: selectors, reusable objects and irreversible migration boundaries

568 focused words · mechanism, configuration, evidence and troubleshooting

Why RADIUS-only support changes the configuration model

FortiNAC-F 7.6.7 adds support for infrastructure that communicates with FortiNAC exclusively through RADIUS and exposes no SNMP or CLI management interface. The guide names cloud-managed devices, modern APs and constrained IoT devices as examples. This does not remove SNMP/CLI integration for devices that support it. It adds a second management model: reusable configuration objects are selected dynamically rather than binding all behavior to one device model.

The reusable building blocks include Logical Networks, RADIUS Server Configurations, Response Attribute Configurations, VLAN Mapping Configurations and SSO/VPN Configurations. Configuration Selectors choose those objects based on device and request attributes. State Based Access Control Rules then determine what access action applies to the device/host state. The result is a chain: RADIUS request and device identity → selector match → selected RADIUS/response/VLAN/SSO objects → state-based access decision → RADIUS response/CoA enforcement.

Response attributes and VLAN mapping are separate objects

Response Attribute Configurations define the RADIUS attributes returned to the network device. They can reference an Authentication attribute group and choose RFC5176 behavior for Change of Authorization (system-defined or custom). Logical Network to Response Attribute mappings can add attributes for a selected logical network. VLAN Mapping Configurations map logical networks to access values; the guide supports VLAN ID or vendor-specific access value. These objects must be built before the selectors that reference them. The guide specifically warns to test mappings in a non-production environment and avoid overlapping assignments for the same logical network.

Selector rank matters. A specific selector must be able to win over a broad catch-all rule. When a device receives the wrong response, inspect the selector match log for the RADIUS Server Selector, Response Attribute Selector, VLAN Mapping Selector and State Based Access Control Selector. A successful Access-Request reaching FortiNAC proves transport, not that the correct selector or VLAN mapping was selected.

Legacy migration is the dangerous part

Fresh installations have Global Legacy Mode off; upgrades with existing devices have it on by default. Newly added devices default to selector mode. RADIUS-only devices show Legacy Mode as N/A and cannot be switched into legacy mode. The migration wizard can generate configuration objects and selectors from existing model configuration, but it does not automatically invent correct selectors for every existing device. Review generated conditions and ranks before changing each device's Legacy Mode to Off.

Turning off Global Legacy Mode is irreversible in the GUI: the migration wizard disappears, device-bound configuration is no longer available, and a pre-change backup is required to restore the earlier architecture. The safe sequence is to create/review selectors, migrate and test devices individually, confirm all required devices are off legacy mode, and only then disable Global Legacy Mode. Do not switch the global control off just to test one RADIUS-only device.

Operational troubleshooting

  • Confirm the device runs FortiNAC-F 7.6.7 or later and is treated as RADIUS-only.
  • Verify that the Access-Request reaches FortiNAC and that the intended selector conditions match.
  • Check selector rank and the selected logical network, response attribute group, VLAN mapping and SSO/VPN object.
  • Verify the Access-Accept attributes and, where applicable, RFC5176 CoA behavior at the network device.
  • Use the Community Friend-or-Foe example as a selector-based scenario, not as the primary definition of the RADIUS-only architecture.

Engineering takeaway: The new capability is not merely “RADIUS works without SNMP.” It is a selector-driven configuration architecture with an irreversible global migration boundary. Build and validate the object chain before moving production devices.

08 · FortiAuthenticator · FortiAuthenticator 8.0.1 (8.0.0+ required)

Subscription VM licensing: FDN validation is part of authentication availability

456 focused words · mechanism, configuration, evidence and troubleshooting

License validation is an operational dependency

FortiAuthenticator-VM supports perpetual and subscription licensing. The subscription VM license requires FortiAuthenticator 8.0.0 or later and periodic entitlement validation against update.fortiguard.net over TCP/443. Uploading the subscription license from System > Administration > Licensing triggers a reboot; the appliance then retrieves the subscription entitlements from FortiGuard. The license is therefore not just a static user-count file: outbound name resolution and HTTPS reachability are part of continued service operation.

If FortiAuthenticator cannot reach the validation FQDN for 30 days, the subscription license is disabled and services stop working. On expiry, the user limit falls to the unlicensed VM limits and authentication services are halted. The administrator GUI remains accessible. This creates a distinctive failure pattern: administrators can still sign in to the appliance to troubleshoot, but RADIUS, SAML and other authentication consumers may fail because the license gate has stopped authentication services.

HA behavior matters

A redundant HA pair requires a separate subscription VM license file for both active and passive nodes. Mixing perpetual and subscription VM licenses in the same HA pair is not supported. The active unit retrieves entitlements for itself and the passive unit; if their subscription entitlements differ, the lower entitlement is used. Therefore, a healthy-looking active license is not sufficient evidence that the pair is licensed consistently. Validate both license files and the resulting entitlement level.

Evidence and troubleshooting sequence

get system license-info
diagnose system updated status
diagnose system updated info
diagnose debug application updated <level>

get system license-info reports local license information. diagnose system updated status shows the license information fetched from FortiGuard/FDN. diagnose system updated info exposes runtime update information. The update daemon can be debugged with the documented application debug command. In Logging > Log Access > Logs, validation messages show the remaining grace period: for example, a failure to validate for several hours can report 30 days remaining, and subsequent messages decrement that window.

When authentication stops but the GUI remains available, do not begin by rebuilding RADIUS clients or SAML service providers. First confirm the license state, FDN reachability, DNS resolution and outbound TCP/443. Then compare active/passive entitlements and inspect the update logs. If the subscription was applied to an older 6.6.7 VM, the Community migration case is a warning: subscription licensing is an 8.0.0+ feature, and applying it before upgrading can change the VM model identity and block the upgrade path.

Operational safeguards

  • Allow outbound TCP/443 to update.fortiguard.net from the FortiAuthenticator management path.
  • Monitor validation countdown messages before the 30-day grace period is exhausted.
  • Keep both HA nodes on compatible subscription licensing and matching entitlements.
  • Do not confuse GUI availability with authentication-service availability.

Engineering takeaway: For subscription-licensed FortiAuthenticator, FDN validation is a service dependency. An appliance can remain administratively reachable after authentication has been halted.

09 · FortiPAM · FortiPAM 1.9.0

Access Authentication: a step-up gate between login and secret use

552 focused words · mechanism, configuration, evidence and troubleshooting

It is not the same as login MFA or approval

FortiPAM 1.9 adds Access Authentication as a second gate when a user accesses or launches a secret. The user's FortiPAM login establishes a session, but that session alone does not necessarily authorize viewing the secret's credential fields or launching its target. Access Authentication requires a fresh authentication transaction at the point of secret use. It is separate from Requires Approval to Launch Secret, checkout/check-in, session recording and SSH command filtering.

The control can be set on a secret policy in Secret Settings > Policies. When enabled, it applies to secrets in the folder where that policy is used, unless the setting is overridden at the individual secret. The policy can specify a remote authentication server, a duration and whether the secret owner may bypass the step-up gate. The documented duration defaults to 60 minutes and ranges from 0 to 180; a duration of 0 means short-lived authentication for immediate use. Owner bypass is disabled by default and should remain disabled unless the security design explicitly permits it.

Transaction flow

  1. The user signs in to FortiPAM and navigates to a secret.
  2. The folder policy and secret-level Session Security setting are evaluated.
  3. If Access Authentication is enabled and the current access window is absent or expired, FortiPAM presents the Access Authentication dialog.
  4. Successful authentication creates a bounded access window. Access Authentication Status displays the remaining duration.
  5. Editing the secret's protected settings and launching the secret are both gated by successful step-up authentication.

When the user is logged in as a remote RADIUS or LDAP user, the launch workflow offers Authenticate using PAM login credentials. This lets the user use FortiPAM login credentials for the Access Authentication step. It is not a reason to assume the remote RADIUS/LDAP identity itself has been silently revalidated by the target server.

Configuration and troubleshooting

Enable Access Authentication in the folder policy, select the intended remote server, choose a duration that matches the secret's sensitivity, and leave Bypass For Owner disabled by default. Then inspect the secret's Session Security pane for an override. An override can disable the folder-level requirement for one secret, so testing only the policy is insufficient. Check the Access Authentication Status timer and the warning shown when a user attempts to edit without authenticating. A user can have permission to see the secret in the list yet still be blocked from editing or launching it.

If the dialog does not appear, check policy inheritance and per-secret override first. If the dialog appears but authentication fails, check the selected server and the credentials used for the step-up transaction. If the user can edit but cannot launch, verify that the launch path is also gated and that the access window has not expired. Do not solve a step-up failure by disabling launch approval; approval and authentication enforce different controls.

Security interpretation

  • Login success proves entry to FortiPAM, not permission to read a protected secret.
  • Access Authentication Status proves the remaining step-up window, not that a target session is active.
  • Approval controls whether an approver permits use; Access Authentication proves the user re-authenticated.
  • A zero-minute duration is intended for immediate use, not a long-lived session.

Engineering takeaway: Use Access Authentication when policy requires fresh proof at secret-use time, independently of the user's existing FortiPAM session and approval state.

10 · FortiSIEM · FortiSIEM 7.5.1

Incident Investigation Workspace: build an evidence graph, then test causality

530 focused words · mechanism, configuration, evidence and troubleshooting

From a single incident to a linked investigation

The Incident Investigation Workspace is in Analytics > Investigation. An analyst can load a root Incident ID from the Incidents page or enter it directly. FortiSIEM builds an undirected graph containing the incident and involved entities such as host/IP, user, process and file. Related entities and related incidents can be added recursively. The investigator can choose Force or Bipartite layout, set a Time From/To range, and use the timeline to view incident occurrences in temporal order.

The graph is an evidence-navigation model, not a causal proof engine. An edge means FortiSIEM has identified a relationship according to its available incident/entity context. It does not prove that one node caused another. The timeline adds ordering: the analyst can hover or play through incident events to see which incident and entities are active at a given time. Entity context can include CMDB information, external lookups and event-database records. The workspace can also run reports, reputation checks, FortiSOAR playbooks/connectors, remediation actions, and case creation.

Investigation workflow

  1. Start from the incident that triggered the investigation; record its ID and initial time window.
  2. Load the incident in Analytics > Investigation. Confirm the root node, severity and triggering event details.
  3. Expand Related Entities and Related Incidents selectively. Avoid adding every possible node before understanding the root evidence.
  4. Inspect the node sidebar for incident details, triggering events, entity/CMDB context, and action history.
  5. Use the timeline to establish event order. Compare the time window against the raw triggering events and any external evidence.
  6. Run reports or reputation checks for selected entities; create a case or take remediation only after the evidence supports the action.

Evidence and backend checks

The graph and the underlying event database answer different questions. A graph edge provides a navigable relationship. The triggering-events view shows the events that caused the incident. The timeline shows the ordering used for investigation. The CMDB sidebar gives context about a host or user. The Community backend-query scenario is useful when an analyst needs to verify incident counts, status, or the existence of incident records in PostgreSQL. Such a query can validate a database discrepancy; it does not reconstruct the workspace's full relationship logic or prove causality.

If the graph appears incomplete, widen the investigation time range only after checking the incident's first/last occurrence and event retention. Confirm that related entity expansion is available for the selected node type. If the incident count in the GUI differs from a backend query, compare organization scope, time range, incident status and filters before assuming data loss. A graph with fewer nodes may reflect the selected time window or expansion choices rather than a parser failure.

Common reasoning errors

  • Do not infer causality from graph proximity or a shared IP address alone.
  • Do not use a timeline without checking the event timestamps and time-zone interpretation.
  • Do not clear an incident merely because its graph is visually connected to a known benign entity.
  • Do not confuse the bipartite login-anomaly model with the analyst-driven incident/entity graph; they solve different problems.

Engineering takeaway: Use the workspace to expand and organize evidence. Use triggering events, time ordering and entity context to justify the causal narrative before remediation or incident closure.

11 · FortiSASE · FortiSASE 26.1.107

Authenticated onboarding: SAML-gated endpoint registration and invitation-code rotation

504 focused words · mechanism, configuration, evidence and troubleshooting

Registration becomes an authenticated transaction

Authenticated onboarding makes the FortiSASE Management service act as a SAML Service Provider. Before a managed endpoint can register, the user is redirected to an external identity provider, authenticates there, and returns to FortiSASE with a SAML assertion. This is different from SCIM user/group provisioning: SCIM synchronizes directory objects, while authenticated onboarding gates endpoint registration with an interactive SAML transaction.

The feature is select availability and is not necessarily exposed by default. Request enablement through Fortinet Support before designing the rollout. Once enabled, configure the SAML SP/IdP relationship: Entity ID, Assertion Consumer Service (ACS) URL, IdP SSO URL, signing certificate, and the user/group claims needed to identify the enrolling user. For Microsoft Entra ID, the guide calls out the associated-domain and username claim behavior and a maximum of 150 groups in the SAML assertion. If a user belongs to more groups, scope the assignment/claim rather than assuming FortiSASE will receive an unlimited group list.

Invitation code and migration effects

Enabling authenticated onboarding generates a new invitation code. Previously distributed codes are no longer valid for new registration. Existing managed endpoints are migrated to the authenticated-onboarding flow and must complete the new authentication step; endpoint installers distributed through EMM also need to be updated with the current invitation code/configuration. This means the rollout is not only an IdP change. It is a registration-state and installer-distribution change.

Plan the sequence: enable the feature with Fortinet Support; configure and test SAML with a pilot group; verify that the IdP returns the expected username/domain/group claims; obtain the new invitation code; refresh installer packages and EMM assignments; then migrate existing endpoints and validate their re-authentication. Keep a rollback/communications plan for remote users who are offline during the transition. Do not assume a previously installed client will silently adopt a rotated invitation code.

Verification and failure isolation

When registration fails, separate the steps. If the client never reaches the SAML redirect, check that authenticated onboarding is enabled and that the current invitation code is used. If the redirect occurs but SAML fails, check Entity ID, ACS URL, SSO URL, signing certificate and the exact user/domain/group claims. If SAML succeeds but registration fails, check endpoint migration state and whether the installer/EMM package contains the new invitation code. For Entra ID, inspect the group claim count and ensure the associated domain/username claims are present.

A successful SAML login proves identity-provider authentication, not that the endpoint has completed FortiSASE registration or that a VPN tunnel is active. A successful endpoint registration proves the management onboarding transaction, not that traffic policy, security PoP selection or private-access routing is correct. Verify those later stages independently.

Operational caveats

  • Feature enablement may require a Fortinet Support request.
  • Invitation-code rotation invalidates older enrollment instructions.
  • Entra group assertions are bounded; reduce scope to the groups needed for onboarding.
  • Existing endpoints and EMM installers require an explicit migration/update plan.

Engineering takeaway: Authenticated onboarding inserts SAML identity proof into the endpoint registration path. Treat the invitation code, SAML claims, and endpoint migration as one coordinated change.

12 · Secure SD-WAN · FortiOS 8.0.0

IPv6 segmentation over one ADVPN overlay: VPN-ID/IPIP keeps VRFs separate

531 focused words · mechanism, configuration, evidence and troubleshooting

One physical overlay, multiple isolated routing contexts

FortiOS 8.0 supports IPv6 communication across L3 VPN segmentation carried by a shared SD-WAN/ADVPN overlay. A hub-and-spoke deployment can serve multiple companies or departments at each branch. Each tenant's subnet is placed in a different VRF. A branch in VRF-A can reach another branch's VRF-A subnet, while VRF-A must not reach VRF-B merely because both use the same IPsec tunnel infrastructure. Overlapping tenant address space is possible because the VRF identity is preserved through the overlay.

The key encapsulation setting is on the IPsec phase1-interface:

config vpn ipsec phase1-interface
    edit "ADVPN-OVERLAY"
        set encapsulation vpn-id-ipip
    next
end

vpn-id-ipip carries VPN ID/VRF information inside the IPsec tunnel. This setting is for forwarding traffic; Fortinet documents that it cannot be used for local-out traffic. That distinction matters when testing from the FortiGate itself: a locally generated ping is not equivalent to a forwarded host packet entering the VRF and overlay path.

IPv6 control-plane reachability

The IPv6 extension uses exchange-ip-addr6 to exchange loopback IPv6 addresses between spokes and the hub. The loopback addresses are used for spoke/hub communication instead of relying on the tunnel interface address. BGP then exchanges the VRF-specific routes. Each site must have consistent VRF identity and route policy; the shared tunnel does not remove the need for correct route import/export. A VRF-aware SD-WAN health check can tag its probes with the correct VRF so the hub forwards the probe to the health-check server in that same VRF. The health-check configuration uses set vrf and set source; the address mode can be IPv4 or IPv6.

Verification and failure patterns

Test from a host behind VRF-A at spoke 1 to a host behind VRF-A at spoke 2, then test the same source against VRF-B. The first should succeed when routes and policy are correct; the cross-VRF test should remain isolated. Inspect the route table in each VRF, BGP neighbor state and advertised/received routes, IPsec phase1 encapsulation, and the exchanged IPv6 loopback reachability. Verify the health-check source address belongs to the intended VRF and that the remote probe target is reachable in that VRF.

If IPv6 same-VRF traffic fails while IPv4 works, check the IPv6 loopback exchange and IPv6 route advertisements before changing the VPN-ID encapsulation. If a cross-VRF test succeeds unexpectedly, inspect VRF membership, route-target/import-export policy, and any explicit route leaking. If the overlay is up but the SLA is down, confirm that the health-check probe is tagged for the correct VRF and sourced from the correct address. A green IPsec tunnel alone proves only that the tunnel is established; it does not prove per-VRF route exchange or health-check reachability.

Scale and shortcut behavior

In a large ADVPN hub, shortcut offers can create load when many spokes repeatedly fail to establish shortcuts. FortiOS exposes auto-discovery-offer-interval on the phase1-interface; the documented default is five seconds and the configurable range is 1–300 seconds. Tune this only after measuring hub load and shortcut establishment behavior. It is not a substitute for fixing route or VRF mismatches.

Engineering takeaway: The overlay is shared, but the forwarding context is not. VPN-ID/IPIP, VRF-specific BGP exchange, IPv6 loopback reachability and VRF-aware health checks must all agree for same-tenant connectivity without cross-tenant leakage.
