FortiGate

1. Firmware Virtual Patching on the Local-In Management Plane

Primary feature lesson source: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/393161/virtual-patching-on-the-local-in-management-interface
Scenario support source: https://community.fortinet.com/fortigate-3/troubleshooting-tip-fmwp-signatures-not-available-for-virtual-patching-226341

The protected path is local-in, not transit inspection

FortiGate firmware virtual patching (FMWP) on the management plane protects traffic whose destination is the FortiGate itself. That puts the decision in the local-in path rather than in the normal IPv4/IPv6 transit-policy path. Fortinet exposes the feature under `config firewall local-in-policy` with `set virtual-patch enable`. The distinction matters because an administrator can have a perfectly valid IPS profile on a transit firewall policy and still have no FMWP protection for HTTPS or SSH sessions terminating on the appliance. Conversely, an FMWP-enabled local-in policy is not evidence that transit traffic is receiving the same treatment.

A local-in policy first determines whether the management-bound session is eligible for the feature. The session still has to target the interface/service and source conditions represented by that policy. This is why troubleshooting begins with the exact ingress interface and a new management session, not with a generic statement that “IPS is enabled.” The policy object is the control point that brings that FortiGate-destined traffic into the virtual-patch workflow.

How the vulnerability set becomes FortiOS-version specific

Fortinet documents a second control loop behind the local-in policy. WAD periodically queries the FortiGuard API for vulnerability items that apply to the running FortiOS version. The resulting version-specific information is supplied to IPS, which enables the applicable FMWP vulnerability rules. This is fundamentally different from treating the database as a static list that must always contain an enabled signature for every FortiGate.

The distinction explains an initially counterintuitive healthy state: `diagnose ips vpatch fmwp-status` can report zero enabled FMWP signatures even when the FMWP definitions are current. Fortinet’s troubleshooting article explicitly says that zero can be expected when the running FortiOS release has no known vulnerability represented by an FMWP signature. Therefore `Enabled FMWP signatures: 0` is an applicability result, not by itself an update failure. `diagnose autoupdate versions` should be used to establish whether the FMWP definitions/update state exists before drawing any conclusion about applicability.

Session tagging, bypass, and why retesting must use a new session

The inspection path also has an optimization boundary. Fortinet describes service tagging so sessions for which no applicable vulnerability signature exists can bypass unnecessary IPS scanning. The consequence is that the engineer must distinguish “the feature bypassed because nothing applies to this service/build” from “the feature never evaluated the session.” Those are different states and require different evidence.

Another documented behavior is that enabling virtual patching affects new sessions. An HTTPS administrative session that existed before the configuration change can therefore be a poor validation vehicle. Reset the management session and create a new one before judging whether the new local-in treatment is active. A successful login on an old session proves only that the old session remains usable; it does not prove a new exploit-bearing flow would bypass FMWP.

Evidence-driven failure isolation

Use `diagnose autoupdate versions` to verify the FMWP content/contract/update state. Then use `diagnose ips vpatch fmwp-status` to determine whether signatures are actually enabled for the current build. If definitions exist but the enabled count is zero, the first proven boundary is database availability and the next question is version applicability. Do not “fix” that state by forcing all signatures in production merely to make the count nonzero; Fortinet’s force-enable commands are appropriate for controlled testing, not proof that every build should normally have active rules.

If applicable signatures are enabled but a controlled exploit test is not blocked, move to the session boundary: verify the test creates a new connection, arrives on the interface referenced by the FMWP-enabled local-in policy, and targets the vulnerable service/signature. IPS/FMWP logging or a controlled block result is stronger evidence than the GUI simply remaining reachable. The chain to prove is: current FMWP content → build-specific applicable rule → new session matches local-in policy → IPS evaluates that eligible session → exploit signature matches and is dropped. Each arrow is independently testable.

Worked management-plane validation path

Consider a FortiGate whose administrators reach HTTPS on port2 from a management subnet. The local-in policy for that source/interface has virtual patching enabled. Begin by preserving the exact running FortiOS version and reading FMWP definition state; those two values determine whether FortiGuard has content and whether content should be applicable. If the FMWP database timestamp is current but `fmwp-status` has no enabled rules, compare that result with the running version before touching policy. The documented zero-signature condition exists specifically to prevent a false diagnosis that “virtual patching is down” whenever no vulnerable build condition is present.

If the build does have applicable signatures, create a fresh HTTPS session from an address that is in scope for the local-in policy. A packet capture can establish ingress and destination service, while local-in-policy hit behavior and IPS/FMWP logging establish later boundaries. A normal TLS handshake proves that HTTPS is reachable; it does not prove the exploit path is unprotected. The meaningful negative test is a controlled request that would exercise the applicable signature. If the request is blocked, the transaction has progressed through policy eligibility and IPS signature enforcement. If it reaches the GUI despite applicable signatures, investigate the exact service, session freshness, and local-in-policy match before changing the FMWP database. This sequence keeps three commonly confused states separate: content availability, signature applicability, and per-session enforcement.

Operational boundary to retain

The feature is best remembered as a version-aware exception-control mechanism around management services, not as a replacement for upgrading FortiOS. FMWP can mitigate a known vulnerable code path when FortiGuard supplies a rule for the running build, but the permanent corrective action for a fixed vulnerability remains moving to an appropriate fixed release according to Fortinet guidance. During a maintenance window, re-run the same applicability checks after upgrade: a signature that was appropriate before the upgrade may disappear because the new build is no longer vulnerable. That disappearance can be evidence of a changed applicability set rather than regression. Preserve the before/after `autoupdate` and `fmwp-status` output alongside the local-in policy so the operational record explains why the enabled-rule count changed.

2. Workspace Locking: ADOM, Device, Policy-Package, Commit, and Install Boundaries

Primary feature lesson source: https://docs.fortinet.com/document/fortimanager/7.6.4/administration-guide/233813/workspace
Scenario support source: https://community.fortinet.com/fortimanager-27/technical-tip-how-to-lock-unlock-an-adom-and-commit-changes-in-fortimanager-using-the-json-api-208549

Why lock scope changes what concurrent administrators can do

FortiManager Workspace mode changes the semantics of concurrent administration. With workspace disabled, administrators can modify the database without acquiring a workspace lock. With Workspace enabled, a lock establishes edit ownership over a scope. Fortinet supports an ADOM-wide lock as well as narrower device and policy-package locks. The narrower scopes are what allow two administrators to work in the same unlocked ADOM without editing the same object simultaneously.

A green padlock means the current administrator owns the lock; a red padlock identifies a lock held by another administrator. That state is not cosmetic. It is FortiManager's concurrency control. A policy-package lock does not imply ownership of every manager or object inside the ADOM, and an ADOM lock can supersede the narrower model by taking control of the enclosing scope.

Workspace and Workflow mode are different transaction models

Fortinet separates Workspace mode from Workflow mode. In Workflow mode the entire ADOM is the lockable unit and a workflow session is required before policy changes are made. In standard Workspace mode, devices and policy packages can be locked individually. This affects both GUI operations and automation because a script written to acquire only a policy-package lock is not equivalent to an ADOM-wide workflow session.

Fortinet also documents managers that require an ADOM lock even when narrower locks are otherwise available, including AP Manager, FortiClient Manager, VPN Manager, FortiSwitch Manager, and some System Settings. A successful device lock therefore proves only ownership of that device scope. It does not authorize a change in a manager whose transaction boundary is the whole ADOM.

Lock, commit, unlock, and install are four different pieces of evidence

The JSON API example makes the state transitions explicit: call `/dvmdb/adom/<ADOM>/workspace/lock`, make the change, call `/workspace/commit`, and then `/workspace/unlock`. Lock success proves exclusive ownership of the workspace scope. Commit success proves the modified workspace state was accepted into FortiManager's committed database. Unlock releases ownership. None of those operations, by itself, proves a managed FortiGate has received the configuration.

Installation is a later deployment transaction. An automation that logs “success” after the lock call can still leave uncommitted edits. An automation that logs “success” after commit can still have a later installation failure on one managed device. This separation is essential when determining whether a discrepancy lives in edit concurrency, FortiManager's database, or the device-install path.

Troubleshooting a stuck or surprising change

When an administrator cannot edit an object, first inspect the actual lock owner and scope instead of assuming someone “has the ADOM.” A red package lock can coexist with a different device lock. An attempted ADOM lock can collide with existing narrower locks because it encloses them. FortiManager also allows lock override in appropriate administrative circumstances, so audit who preempted whom when that capability is used.

When the complaint is “my FortiGate never got the change,” establish four checkpoints in order: who held the needed lock; whether the edited object is present in the committed ADOM database; whether the relevant install operation succeeded for that target; and whether the target FortiGate now shows the intended state. That sequence prevents a device-side investigation when the configuration never left the workspace.

Worked concurrency and deployment transaction

Imagine Administrator A locks policy package Branch-Internet while Administrator B locks Device-02 in the same ADOM. In Workspace mode that coexistence can be legitimate because the lock scopes do not overlap. If B later tries to acquire the entire ADOM, the enclosing request conflicts with A's package ownership. The useful evidence is not “someone is in the ADOM” but the exact object displaying the red or green padlock and the user recorded as its owner. That tells you which edit transaction is blocked and which other edits may continue.

Now follow Administrator A's change to completion. A modifies a firewall object while owning the package lock. Until the workspace is committed, the change is still an edit-state transaction. After `/workspace/commit` succeeds and the committed database contains the object, FortiManager has durable intent. Only a subsequent install maps that intent to managed-device state. If Device-01 installs successfully and Device-02 does not, the lock and commit stages are already common proven-good boundaries; the failure is device-specific installation, validation, or target acceptance. This model also prevents an automation bug in which the script reports success as soon as the lock API returns. The lock is merely permission to edit; it is not a substitute for commit and certainly not for install/read-back.

Lock scope during automation and change review

For API automation, record the ADOM, exact lock endpoint, session identity, commit result, and the install target list as separate fields. This is more useful than one overall “job succeeded” flag because FortiManager can reject one boundary while earlier calls succeeded. A 200-style transport response or successful login does not by itself establish that the requested workspace operation completed; examine the FortiManager API result for the lock/commit call and then read back the object. If an administrator must preempt a lock, treat that as a concurrency event: determine whether the displaced administrator has unsaved changes before proceeding. For policy-package work, keep package ownership and device-install ownership separate because one package can target multiple devices whose installation results differ. This gives change review a concrete transaction history: lock acquired → object modified → database committed → package generated/validated → target installation result → target read-back.

3. Correlation Event Handlers: Temporal Operators, Data Selectors, and Event Creation

Primary feature lesson source: https://docs.fortinet.com/document/fortianalyzer/7.6.6/administration-guide/444315/event-handlers
Scenario support source: https://community.fortinet.com/fortianalyzer-6/troubleshooting-tip-how-to-troubleshoot-for-event-handler-related-issues-141562

Basic handlers and correlation handlers answer different questions

A basic FortiAnalyzer event handler tests its rules as alternatives; Fortinet documents an OR relationship between rules in a basic handler. A correlation handler is different because it evaluates a sequence of rules with correlation operators such as `AND`, `AND_NOT`, `OR`, `FOLLOWED_BY`, and `NOT_FOLLOWED_BY`. The correlation engine can therefore express relationships in which ordering or the absence of a later condition is meaningful.

That means the same collection of raw log records can produce a basic event while failing a correlation event. Two records existing somewhere in the database is not enough for `FOLLOWED_BY`; the records must satisfy the configured sequence, grouping, fields, and timing semantics. Similarly `NOT_FOLLOWED_BY` is not simply an inverted filter: it represents an expected absence after an earlier qualifying condition.

The handler depends on objects outside the rule itself

Fortinet separates data selectors, event-handler rules, notification profiles, and optional downstream actions. A data selector defines the data set presented to the handler. The handler then evaluates its conditions. If an event is generated, notification profiles, automation stitches, or automatic incident creation can act afterward. Troubleshooting becomes much clearer when those stages are not collapsed into “the alert did not fire.”

A source record can be received and stored correctly while excluded by the data selector. A record can enter the selector and fail the handler filter. A handler can generate an event while an optional notification fails. Each state has different evidence, and the Event Monitor is the boundary between log ingestion and event generation.

Why Log View is the first proving point

Fortinet’s troubleshooting procedure starts by locating the expected input record in Log View. If the expected FortiGate event is absent there, editing correlation operators is premature because the handler has no qualifying input to evaluate. Once the record is visible, the investigation can move to handler enablement, data selector, filters, thresholds, grouping, and temporal sequence.

Fortinet also identifies `sqllogd` and, on supported releases, `fazalertd` as relevant processes. `diagnose test app sqllogd 1` and `diagnose test app fazalertd 1` can establish process state. A running daemon is only a prerequisite, however; it does not prove that one particular correlation rule matched one particular pair of records.

A precise correlation failure example

Assume rule A identifies an administrator login and rule B identifies a sensitive configuration change, connected by `FOLLOWED_BY`. Both records are visible in Log View but the event does not appear. The first proven boundary is ingestion. Next compare their timestamps and the fields used to correlate them. If the configuration-change record occurred before the login or belongs to a different grouping key, the two records do not satisfy the intended sequence even though both exist.

If the correlation event appears under Incidents & Events > Event Monitor > All Events but no incident is created, handler evaluation is already proven. The failure has moved to the optional incident/automation action. That is a materially different troubleshooting branch from missing input logs.

Worked temporal-correlation example

Suppose a correlation handler is intended to detect an administrator login followed by a configuration change, while excluding a known maintenance account. The data selector must first expose the relevant event-log dataset. Rule A identifies the login, Rule B identifies the configuration change, and an exclusion condition removes the maintenance identity. With `FOLLOWED_BY`, a configuration change that occurred before the login cannot satisfy the intended sequence even though both rows are visible. With `AND_NOT`, the maintenance-account condition changes whether the candidate is eligible at all. The operator is therefore part of the event meaning, not a cosmetic way to join filters.

Troubleshoot from the bottom of the pipeline. Confirm the exact source rows and timestamps in Log View. Confirm the fields used for grouping—such as device, administrator, source, or another handler field—align between records. Confirm the handler is enabled and the selected data selector includes those rows. Only then inspect process health with the documented daemon checks. If the event appears in All Events, the correlation engine has already done its job; a missing incident or notification is a new downstream problem. That boundary is especially valuable in busy FortiAnalyzer environments because otherwise an engineer can waste time changing a working sequence when the real failure is the automation stitch or notification profile attached after event creation.

Designing a correlation that can be explained from its records

Correlation handlers become easier to operate when every operator has an explicit event meaning. For a `FOLLOWED_BY` pair, document which record is the prerequisite and which record is the consequence. For `NOT_FOLLOWED_BY`, document what later record is expected not to appear and over what configured correlation context. Avoid using a broad selector merely because the raw logs are visible; the selector should expose the fields needed to distinguish the entities being correlated. When a handler is tuned, use known test records and preserve their timestamps/field values so a future engineer can reproduce why the sequence should match. If the handler creates incidents automatically, keep event generation and incident grouping separate in validation: the All Events record is the proof that correlation fired, while the incident is evidence that the next automation/grouping stage consumed it. That distinction makes false-negative and false-positive investigations much faster.

4. Storm Control: PPS Metering, Traffic Classes, Overrides, and Burst Behavior

Primary feature lesson source: https://docs.fortinet.com/document/fortiswitch/7.6.4/fortilink-guide/173291/configuring-storm-control
Scenario support source: https://community.fortinet.com/fortiswitch-36/troubleshooting-tip-how-to-verify-working-of-storm-control-115449

Storm control meters selected frame classes in packets per second

FortiSwitch storm control is a rate-policing mechanism for broadcast, unknown-unicast, and unknown-multicast traffic. Fortinet documents the threshold in packets per second rather than as a percentage of interface bandwidth. The managed-switch configuration supports a large PPS range and a default rate of 500 pps. The traffic classes are independently selectable, so “storm control is configured” is incomplete evidence unless the engineer also knows which class the test traffic belongs to.

When the enabled class exceeds the configured threshold, excess packets are dropped. The mechanism does not inherently shut down the port, elect a new spanning-tree root, or determine whether a loop exists. A loop can be the cause of a broadcast storm, but storm control's direct observable is rate policing of the selected class.

Inheritance and per-port override determine the effective threshold

Under FortiLink management, FortiOS exposes global storm-control settings and named storm-control policies. A policy can use `storm-control-mode override` and be assigned to a particular managed switch port. That means the value an engineer sees at the broad controller level may not be the value enforced on the problem port.

This hierarchy is especially important during troubleshooting after a template or port policy change. Before generating traffic, establish whether the port inherits the global setting or receives a policy-specific override. Otherwise a perfectly accurate packet-rate test may be compared against the wrong threshold.

Burst handling changes the shape of a useful test

FortiSwitch 7.6.4 adds configurable maximum burst behavior in the managed workflow. A short microburst and a sustained flood therefore need not produce identical observations. The engineer should generate traffic long enough and consistently enough to cross the actual meter behavior rather than infer failure from one short spike.

The Community verification approach uses a traffic generator and a mirror/capture destination in the same VLAN. That is strong evidence because the offered rate and forwarded rate can be compared. The configuration proves intent; measured clipping above the threshold proves enforcement.

Diagnosing “it does not drop” without guessing

First classify the frames. Known unicast is not unknown unicast. Multicast that is already learned/handled is not necessarily the same condition as unknown multicast. Next read the effective port policy and its enabled class. Then measure the offered packet rate. Sending 700 broadcast pps to a 1000-pps broadcast threshold should not cause drops, and that healthy outcome should not be labeled a failure.

If the generator sends well above the effective threshold for an enabled class and the mirror still sees the full offered rate, the enforcement boundary is unproven. At that point validate policy attachment and exact port/member rather than changing spanning-tree parameters. Storm-control evidence should remain about traffic class, PPS, burst, and effective per-port policy.

Worked rate-policing experiment

Take a managed FortiSwitch port with a named override policy: broadcast enabled at 1,000 pps, unknown unicast disabled, and a configured burst level. First read the effective port policy so the test is tied to the actual object applied to that port. Send 700 broadcast pps for a sustained interval and mirror the egress; full forwarding is expected because the threshold has not been crossed. Then raise the offered rate well above 1,000 pps while keeping frame size and class known. A reduced forwarded rate or storm-control drop evidence now validates the policer. Repeating the test with known unicast should not be expected to reproduce the broadcast result.

This experiment demonstrates why interface utilization percentage is a misleading substitute for PPS. A stream of small frames can hit a packet-rate threshold while consuming relatively little bit-rate, whereas larger frames can consume more bandwidth without reaching the same packet count. It also separates the feature from spanning tree: if a physical loop creates the storm, storm control can limit the broadcast damage while STP topology remains a different diagnostic domain. Once the test proves policing, the remaining engineering task is to locate the source of the excessive frames rather than raising the threshold until counters stop incrementing.

Choosing a threshold from observed frame behavior

A useful storm-control threshold should be derived from the normal packet-rate envelope of the protected VLAN/port rather than from interface speed alone. Broadcast ARP, unknown-unicast during MAC-learning transients, and unknown-multicast can have very different normal baselines. Capture a representative steady-state and legitimate-burst profile before setting a threshold close to production levels. Then validate with the same class of traffic because a broadcast test cannot prove the unknown-unicast setting. When a policy override is used for an uplink or device class, document why that port's PPS envelope differs from inherited ports. If storm-control drops appear during a real incident, correlate the drop timing with source MAC/VLAN observations and loop/misconfiguration evidence. The policer protects the forwarding domain from excess frames; it does not identify the origin by itself. Raising the PPS ceiling until the symptoms disappear can simply hide a loop while increasing the blast radius.

5. WIDS Rogue AP Detection and Suppression: Radio Binding and Deauthentication

Primary feature lesson source: https://docs.fortinet.com/document/fortiap/7.6.4/fortiwifi-and-fortiap-configuration-guide/961129
Scenario support source: https://community.fortinet.com/fortiap-5/troubleshooting-tip-wids-fortiap-rogue-suppression-does-not-work-146979

A WIDS profile must reach the radio that observes the air

Fortinet configures WIDS as a profile and then binds that profile to a radio under the FortiAP `wtp-profile`. The existence of the WIDS profile in the controller database does not make every AP radio a sensor. The radio binding is the point at which the configured detections become active on a particular FortiAP radio.

The profile includes intrusion detections and controls related to rogue AP behavior. This makes the first troubleshooting question concrete: which FortiAP radio is expected to see the rogue channel, and is the WIDS profile actually applied there? A controller-level object with no appropriate radio binding proves only configuration storage.

Detection and suppression are separate RF stages

A rogue AP appearing in the FortiGate's rogue view proves that WIDS observation/classification information reached the controller. Suppression is a later action. Fortinet’s troubleshooting article describes rogue suppression by transmitting deauthentication frames toward both sides of the rogue relationship: toward clients while spoofing the rogue AP, and toward the rogue AP while spoofing its clients.

That mechanism requires a radio capable of monitoring the relevant rogue channel and transmitting the mitigation frames. Many F- and G-series FortiAP models can dedicate a third radio to monitoring, but not every model has the same radio resources. Therefore “rogue detected but client stays connected” can be a healthy detection pipeline with an unavailable or misconfigured suppression path.

Rate limiting is part of the mitigation mechanism

Fortinet documents `deauth-unknown-src-thresh` as a limit on deauthentication transmissions per second, with 0 meaning no limit and a documented default of 10. The threshold exists because mitigation traffic is itself radio activity and can consume resources. Hitting the threshold does not mean the rogue detector failed; it means the suppression action is being rate-limited by configuration.

Setting the value to 0 for an isolated test can help characterize behavior, but it should not be turned into a universal production recommendation. The correct value depends on the deployment and the observed rogue/suppression conditions.

How to prove each boundary over the air

Start with the rogue record and classification on the controller. Then prove which radio is assigned to monitor and whether it is on/covering the rogue channel. Finally use over-the-air capture or the resulting client disassociation behavior to prove deauthentication frames are actually reaching the rogue relationship. The client disconnect is stronger suppression evidence than a red “rogue” icon.

If detection is present but there is no monitor-radio path to the rogue channel, changing the rogue classification rule will not create RF enforcement. If deauthentication is visible but the client immediately reconnects, the enforcement action is occurring and the remaining problem is persistence/effectiveness rather than missing WIDS execution.

Worked rogue-detection-to-suppression path

Assume the controller classifies an unauthorized SSID as rogue and displays it consistently, yet a test client remains connected to that AP. The rogue record establishes that at least one FortiAP sensor observed the BSSID and reported enough information for classification. Next identify the FortiAP radio expected to perform monitoring. Confirm that the WIDS profile is bound to that radio and that the radio can actually monitor the rogue channel. On a model without a dedicated third monitoring radio, serving-channel obligations can materially change how continuously the AP can observe and suppress another channel.

Once a monitoring path is proven, examine the deauthentication action. The documented mechanism sends frames toward the client while impersonating the rogue AP and toward the rogue while impersonating the client. An over-the-air capture is therefore ideal evidence: it can prove the frames are transmitted and show their source/destination relationship. If no frames appear, inspect suppression state and `deauth-unknown-src-thresh`; a rate limit can constrain mitigation even when detection remains healthy. If deauth frames appear and the client disconnects but rapidly rejoins, suppression is executing and the question becomes whether ongoing monitoring and deauth frequency are sufficient. That is fundamentally different from a WIDS profile that was never attached to the relevant radio.

Radio-resource and channel implications

A dedicated monitor radio makes the suppression topology much easier to reason about because it can scan independently of the radios serving production WLANs. Where no dedicated radio exists, the AP's channel-scanning behavior and serving obligations determine how quickly it can observe a rogue on another channel and how consistently it can transmit suppression frames. That is why model/radio capability belongs in the evidence chain rather than being treated as inventory trivia. Also separate a neighboring but authorized AP from a truly malicious/unauthorized AP before enabling aggressive suppression; classification accuracy is an operational prerequisite because deauthentication is an active RF action. During validation, record rogue BSSID/channel, the FortiAP/radio performing monitoring, and the deauth threshold. Those values let a packet capture be interpreted against the actual controller decision instead of just counting deauth frames with no context.

FortiNAC

6. Ranked Network Access Policies and the Decision-to-Enforcement Boundary

Primary feature lesson source: https://docs.fortinet.com/document/fortinac/9.4.0/administration-guide/926300/network-access
Scenario support source: https://community.fortinet.com/fortinac-28/technical-tip-troubleshooting-location-based-network-access-policies-97446

A Network Access Policy joins match criteria to treatment

FortiNAC separates the question “who/what/where/when is this host?” from “what network access should it receive?” A User/Host Profile contains the matching criteria. A Network Access Configuration contains the resulting treatment, such as a VLAN, CLI configuration, or VPN Group Policy. A Network Access Policy ties those two objects together.

That composition matters because a correct VLAN object cannot compensate for a User/Host Profile that never matches. Likewise a correct profile match does not prove the switch accepted the resulting access value. Treat selection and enforcement as separate state transitions.

Rank is deterministic first-match logic

For a registered host requiring network access, FortiNAC evaluates policies in rank order and uses the first matching User/Host Profile. It does not continue searching for a more specific rule after a higher-ranked policy has matched. A catch-all profile—Location Any, Group Any, no restrictive attribute, When Always—can therefore shadow every policy beneath it. FortiNAC visually indicates policies that are shadowed by such broad matches.

This explains why editing a perfectly reasonable lower policy may have no effect. The engine never reaches it. Move the troubleshooting focus to the actual winning policy shown by Policy Details and to rank/criteria, not to the VLAN number in the policy you hoped would match.

Location is resolved from explicit membership

Fortinet’s location-policy troubleshooting article identifies a concrete failure: the switch, port, SSID, or AP is absent from the location group referenced by the User/Host Profile. The host can be registered and online while still failing that location condition. The result may be another higher/later matching policy or, if no policy matches, the default VLAN configured on the switch.

Host View > Policy Details is the critical decision-engine evidence. Fortinet notes the host should be online for accurate policy details. If Policy Details shows the wrong rule, troubleshoot rank and match criteria. If it shows the intended rule, stop rewriting criteria and move to enforcement.

When the selected policy is correct but the endpoint lands in the wrong VLAN

Suppose Policy Details shows the intended medical-device policy and the expected Network Access Configuration, but the switch port remains on another VLAN. The selection boundary is already proven. The next stages are the logical-network/VLAN mapping, role-based access or model configuration, and the network device's enforcement mechanism.

This distinction prevents a common troubleshooting loop in which engineers repeatedly modify User/Host Profiles even though FortiNAC already selected the right one. The most useful evidence chain is: online endpoint facts → first matching User/Host Profile by rank → selected Network Access Configuration → command/API/VLAN enforcement on the switch/controller → endpoint receives the resulting network state.

Worked first-match and enforcement trace

Consider a registered medical device connected to Switch-A port 1/0/24. The intended User/Host Profile requires the Medical-Devices group and the Building-A location; its Network Access Configuration assigns VLAN 140. A broader employee/device policy sits above it and matches Group Any, Location Any, When Always. Policy Details shows the broad policy. That single observation proves why changing VLAN 140 in the lower policy has no effect: FortiNAC never reaches it. Correct the rank or the catch-all criteria, then re-evaluate while the host is online.

After the specific medical policy appears in Policy Details, the troubleshooting boundary changes. If the endpoint still receives the old subnet, confirm the selected Network Access Configuration really maps to VLAN 140 and then examine how that value is delivered to the modeled switch/port. Verify the switch's runtime port/session VLAN rather than assuming an assignment command succeeded. If FortiNAC shows VLAN 140 but the port remains VLAN 20, the selection engine is healthy and the enforcement handoff is not. If the port changes to VLAN 140 but the endpoint keeps its old address, enforcement is proven and DHCP/client renewal becomes the next boundary. This staged interpretation is why Policy Details is much more useful than repeatedly editing policy criteria based only on the endpoint's IP address.

Ranking changes should be verified against several host archetypes

Moving a catch-all policy lower can fix one endpoint while changing many others, because ranking affects every registered host whose profile evaluation reaches those rows. Before changing order, identify representative hosts for each policy that will be crossed by the move and use Policy Details to predict the winner for each. After the change, re-evaluate those hosts while online. This is a concrete consequence of first-match semantics, not generic change-management advice: the same profile predicates are evaluated in a new sequence. When VLAN is the Network Access Configuration, validate both the network-device VLAN state and the endpoint's subsequent DHCP/address state. A correct switch VLAN with an old client lease means FortiNAC enforcement succeeded even though the endpoint still appears on the old IP temporarily. Conversely, a correct Policy Details result with an unchanged switch VLAN means the failure is before DHCP and after the decision engine.

FortiNAC-F

7. Device Profiler Evaluation: Pass, Fail, and Cannot Evaluate

Primary feature lesson source: https://docs.fortinet.com/document/fortinac-f/7.6.0/administration-guide/855329/device-profiler
Scenario support source: https://community.fortinet.com/fortinac-f-57/technical-tip-track-rogues-that-do-not-match-profiling-rules-or-stop-being-processed-by-the-device-profiler-227830

DHCP observation can create the candidate before profiling knows what it is

FortiNAC-F can create Rogue host records from DHCP packets heard on the network. The Device Profiler setting `Create Rogues from DHCP packets` is documented as enabled by default. This accelerates host discovery, but Fortinet cautions that it can create many Rogue records if DHCP traffic from unmanaged areas is visible. On the FortiNAC-OS side, DHCP access must be allowed for this observation path.

A Rogue created from DHCP is a profiling candidate, not a successfully classified device. The DHCP packet establishes enough identity to create a host record. Device Profiler rules must still evaluate the host and decide whether a rule can register/classify it.

Pass, Fail, and Cannot Evaluate alter control flow differently

Fortinet’s 2026 guidance gives the profiler evaluation three operational outcomes. `Pass` means the rule succeeds and the device is registered according to the rule's settings. `Fail` means the rule criteria are not satisfied and evaluation can proceed to the next rule. `Cannot Evaluate` is fundamentally different: required evidence is unavailable, evaluation stops at that rule, and the host remains Rogue.

The documented example is stale or missing Layer-3 information—FortiNAC cannot obtain sufficiently current ARP/IP-to-MAC data required by the profiling method. The engineer must not interpret that state as “the criterion was false.” The criterion was not decidable with the available evidence.

Rule order interacts with evidence requirements

Because `Fail` continues but `Cannot Evaluate` stops, placing an evidence-dependent rule early in the sequence can prevent later rules from being reached whenever the required observation is unavailable. Reordering rules can change the behavior, but that should follow an understanding of which profiling methods require which L2/L3/device information.

A host that matches the wrong rule and a host that stalls at one rule are distinct cases. Wrong-match troubleshooting focuses on ranking, enabled rules, and criteria. Stalled evaluation focuses on the method at the stopping rule and the specific evidence it could not acquire.

Active NMAP profiling is a separate resource decision

FortiNAC-F can perform active NMAP profiling. Fortinet allows active profiling without first requiring an ICMP ping, but documents that option as disabled by default because scanning many unreachable hosts can cause a considerable performance drain. This is not the same pipeline as passive DHCP-based Rogue creation.

The operational design should therefore decide when passive observations are sufficient and when active probes are justified. If an endpoint is already stuck in `Cannot Evaluate` because IP-to-MAC information is stale, indiscriminately increasing active scanning may add load without fixing the underlying Layer-3 identity evidence. Prove the missing observation first.

Worked profiler-state investigation

A newly observed printer sends DHCP and appears as a Rogue. The first profiling rule uses evidence that depends on current IP-to-MAC/ARP information. If FortiNAC-F cannot obtain that Layer-3 mapping, the rule can land in `Cannot Evaluate`. The critical behavior is that evaluation stops; the later printer-specific rule never receives a chance to run. Seeing the Rogue associated with the first rule is therefore not evidence that the first rule rejected the printer. It is evidence that the profiler could not decide the rule with available data.

Contrast that with a genuine `Fail`. If the required evidence is present and does not satisfy the first rule, the profiler can proceed to the next rule. If the second rule then `Pass`es, registration follows that rule's settings. This state machine should drive remediation: for Cannot Evaluate, repair the missing/stale evidence source first; for repeated Fail results, inspect rule criteria and rank. Active NMAP profiling adds another dimension because it can acquire data but also consume resources when targets are unreachable. Turning on aggressive scans for every Rogue is therefore not a substitute for understanding which particular rule method lacks which observation.

Using the profiler outcome to choose the next diagnostic action

Build the troubleshooting decision around the displayed profiler result. For `Pass`, inspect the registration/profile result and do not continue tuning later rules that were never meant to run. For `Fail`, compare the evaluated evidence against that rule's criteria and then examine the next ranked rule. For `Cannot Evaluate`, stop and identify the required observation that is absent—commonly current Layer-3/IP-to-MAC information in the documented case. This prevents a damaging response in which administrators loosen rule criteria to compensate for missing telemetry. If DHCP-based Rogue creation is producing excessive candidates from unmanaged space, constrain the observation/design rather than assuming every Rogue should be actively scanned. And if enabling NMAP without ping, measure the cost because Fortinet specifically warns about scanning unreachable targets. The profiler is a state machine whose outputs tell you whether the problem is criterion mismatch, evidence absence, or successful classification.

FortiAuthenticator

8. RADIUS Accounting as an FSSO Identity Source

Primary feature lesson source: https://docs.fortinet.com/document/fortiauthenticator/8.0.2/administration-guide/714583/radius-accounting
Scenario support source: https://community.fortinet.com/fortiauthenticator-8/troubleshooting-tip-when-using-fsso-based-on-radius-accouting-fortigate-fails-to-apply-correct-policy-227427

Authentication success and accounting-based SSO are separate transactions

FortiAuthenticator can use RADIUS accounting records as an FSSO login source. A carrier RADIUS server or network access device such as a wireless controller sends accounting information to FortiAuthenticator. FortiAuthenticator extracts the session identity, can enrich it with group information, and inserts the result into the FSSO session state consumed by FortiGate.

The key troubleshooting consequence is that a successful RADIUS authentication is not proof of an accounting-derived FSSO login. The Access-Accept belongs to the authentication exchange. The accounting record is a later packet flow, and the FSSO session is a later state derived from that record.

The service endpoint identifies which transaction you are testing

FortiAuthenticator documents separate service ports: RADIUS authentication defaults to UDP 1812, RADIUS Accounting SSO to UDP 1813, and an accounting monitor service to 1646; RADSEC uses its own service. “RADIUS is reachable” therefore lacks enough precision for this feature.

If Access-Accept succeeds on 1812 but the Accounting-Start never reaches the configured Accounting SSO service on 1813, FortiAuthenticator has no accounting input from which to construct the FSSO identity. The accounting sender must also be configured as an accepted RADIUS Accounting SSO client.

Username normalization can break the join even when access authentication worked

A Fortinet Community troubleshooting case from May 2026 describes FortiGate failing to apply the expected FSSO policy because the RADIUS-accounting username was processed in a way that prevented the correct SSO session from being created. In that case, the relevant setting was `Strip off prefix or suffix from username if any`; disabling the transformation corrected the identity path.

This is a good example of why the original authentication result cannot be the final proof point. The user can be admitted to the wireless or wired network while the normalized identity sent into FSSO no longer matches what FortiGate policy expects.

Follow the identity from packet to policy

Start with the Accounting-Start/update reaching FortiAuthenticator from the intended NAS. Next inspect Monitor > SSO > SSO Sessions and verify the exact username and group membership. Fortinet’s broader FSSO troubleshooting guidance says that when the expected logins and groups are present there, the collection method is largely working and the investigation can move toward FortiAuthenticator-to-FortiGate communication.

Then verify FortiGate sees the FSSO login and that the expected user/group policy wins. This yields four distinct boundaries: RADIUS accounting transport → username/group processing → FortiAuthenticator SSO session → FortiGate identity/policy. A failure at one stage should not be “fixed” by random changes at another.

Worked accounting-to-policy identity trace

A wireless client successfully completes primary authentication through a controller, yet FortiGate treats subsequent traffic as unauthenticated. Begin after the Access-Accept, because that exchange is already proven. Confirm the controller sends an Accounting-Start to the FortiAuthenticator Accounting SSO service on UDP 1813 and that the controller is configured as an accepted accounting client. If no accounting packet arrives, FortiAuthenticator cannot manufacture an FSSO login from the earlier 1812 authentication result.

If the packet arrives, inspect the exact username after FortiAuthenticator processing and the group enrichment visible in Monitor > SSO > SSO Sessions. A prefix/suffix transformation can make the resulting identity different from the one FortiGate policy expects; the cited 2026 troubleshooting case demonstrates this failure. Once the correct username/groups appear in the SSO table, the accounting collection stage is strong evidence and the next handoff is FortiAuthenticator-to-FortiGate. Confirm FortiGate receives the login and associates it with the expected group before changing the firewall policy. A policy that never sees the expected identity cannot be repaired by rearranging unrelated network rules.

Session lifecycle after Accounting-Start

Accounting-derived identity is session state, so the lifecycle of accounting updates and stops matters as much as the initial start. The NAS is the authoritative source for the accounting session attributes FortiAuthenticator consumes. When troubleshooting stale identity, compare the NAS session with the FortiAuthenticator SSO session rather than assuming the initial login should remain forever. Username formatting must stay consistent across the lifecycle; otherwise an update or stop can fail to refer to the identity form that FortiAuthenticator inserted into FSSO. On FortiGate, verify both presence of the user and the expected group because identity-based policies can fail when the username exists but enrichment/group membership differs. This end-to-end view makes it clear why UDP 1812 reachability is insufficient: the feature being studied is built from accounting state on 1813 and the SSO propagation that follows.

FortiPAM

9. Tiered Secret Approval, Time-Bounded Access, and Revocation

Primary feature lesson source: https://docs.fortinet.com/document/fortipam/latest/administration-guide/922413/my-requests-list
Scenario support source: https://community.fortinet.com/fortipam-52/technical-tip-fortipam-identify-approver-for-secret-approval-215935

A visible secret and an approved request are not the same authorization state

When a FortiPAM secret is governed by approval, the requester creates a request rather than obtaining immediate launch rights. The request appears in My Requests and in the approvers' Approval List. FortiPAM tracks request type, tier approval progress, requested/effective start time, expiration time, duration, and creation time. Those fields form the authorization state for that one request.

Seeing the secret name or even seeing that one reviewer clicked Approve is not sufficient evidence when the approval policy has multiple tiers. The `Tier Approval Progress` field exists precisely because intermediate approval and final authorization are different states.

Approvers control the effective access window

Fortinet allows an approver to override the requested start and end time during review. Therefore the duration requested by the user is not the final enforcement interval. Troubleshooting a denied launch must read the approved request's effective start/end window, not rely on the requester's memory of what they asked for.

Fortinet also documents a strong time-bound enforcement behavior: when the approved access time expires, an active secret session is terminated even if the user still has the session window open. Expiration is thus a runtime authorization boundary, not merely a notification or audit field.

Tier transition, denial, and revocation are state-machine operations

Members of the configured approval groups can approve or deny. Before the request advances to the next tier or reaches final approval, a reviewer can revoke their approval action. A denied request and a pending-later-tier request can both produce “I cannot launch,” but their state transitions and remedies are different.

For a multi-tier request, inspect exactly which tier is complete and who/which group is expected to act next. If final approval is reached but current time is before the effective start time, the approval workflow is healthy and launch is correctly withheld. That is not a credential failure.

Audit evidence has a version-specific approver caveat

Fortinet Community documents Request Events > Request Event Log as the place to inspect operations such as Approved access and Denied access. It also documents a version-specific issue in which email-link approval could display the requester rather than the real approver in the User field on affected releases, with fixes listed in later FortiPAM releases.

That means the operation field can prove the approval action occurred while the displayed approver identity may require version/method context. After request state, tiers, and time window are proven, only then should a failed launch be moved downstream to the target credential/session proxy. Approval evidence does not prove the target accepted a login.

Worked approval-state and access-window trace

Suppose a contractor requests a database secret from 13:00 to 15:00. Tier 1 approves, Tier 2 changes the approved start to 14:00 and then gives final approval. At 13:30, a denied launch is expected even though the request page contains an approval action; the effective access window has not begun. At 14:10, final approval plus current-time-in-window proves the FortiPAM authorization stage is satisfied. If launch then fails, the investigation can move to target/session credentials rather than reopening the approval workflow.

At 15:00, FortiPAM's documented behavior is to terminate an active secret session when the approved time ends. That is runtime enforcement of the request object. The audit trail adds another diagnostic layer: Request Event Log can prove approve/deny operations, but the approver User field on affected releases and email-link workflows has a known display caveat. Therefore use tier progress and effective time fields to decide authorization, and use the event log for action history with version context. Do not infer password rotation, target login success, or perpetual entitlement from an Approved access event; those are different FortiPAM states.

Approval policy as a temporary capability

The safest mental model is that final approval creates a temporary capability bounded by the effective start and expiration timestamps. The capability can be unavailable before start, usable during the window, and forcibly invalidated at expiration. Tier approval progress explains how the request reaches that state; it does not itself extend the window. If an approver edits the requested times, the resulting approved values are what the requester must use. When troubleshooting a launch, capture current time and request window before testing the target because an out-of-window denial is correct behavior. Likewise, if a session is terminated exactly when expiration occurs, investigate neither target stability nor password health until the authorization boundary is accounted for. Request Event Log then supplies historical context for who approved/denied, subject to the documented release-specific email-link User-field caveat.

10. Infrastructure Discovery and the Automated CMDB

Primary feature lesson source: https://docs.fortinet.com/document/fortisiem/7.4.0/user-guide/103375/overview
Scenario support source: https://community.fortinet.com/fortisiem-34/troubleshooting-tip-troubleshooting-fortisiem-snmp-discovery-181050

Discovery produces modeled infrastructure, not just a list of IP addresses

FortiSIEM discovery identifies infrastructure across physical, virtual, on-premises, and cloud environments and places supported information into the CMDB. Fortinet describes hardware identifiers, serial/license information, software, applications/services, and configuration detail as discovery outputs. It also discovers relationships such as WLAN AP-to-controller and VMware guest-to-host. Scheduled rediscovery updates that model as the environment changes.

Another important result is capability discovery: FortiSIEM learns what a device can be monitored for and which logs can be pulled with the supplied credentials. A device existing in CMDB is therefore not the same thing as every desired monitor being active. The device model, credentials, and supported capabilities determine later monitoring behavior.

The source address of the discovery query can be a collector, not the supervisor

Fortinet’s SNMP discovery troubleshooting article stresses that the target device must permit the FortiSIEM node that actually sends discovery. In a distributed deployment, that can be a collector rather than the supervisor. A network team that whitelists only the supervisor can therefore produce a confusing state in which the supervisor is reachable while discovery still times out.

The article calls out UDP 161 for SNMP queries and UDP 162 for traps, and warns that NAT/firewalling can change the source address assumptions. “Ping works from the supervisor” is weak evidence for an SNMP discovery transaction sourced by a collector.

Process evidence and protocol evidence answer different questions

`phstatus` can be used to examine FortiSIEM process state; the discovery process is `phDiscover`. A running `phDiscover` proves the service is available on the FortiSIEM node. It does not prove the target accepts the SNMP credentials or that the routing/firewall path permits UDP 161 from the actual source.

Fortinet recommends using `snmpwalk` from the node performing discovery. If the same SNMP query fails there, GUI discovery cannot succeed with the same path/credentials. If `snmpwalk` succeeds but the device still does not populate correctly, the failure boundary has moved above transport into device support, credential association, discovery configuration, or FortiSIEM modeling/parsing.

Distinguish absent device, incomplete model, and missing events

“FortiSIEM does not see my device” can mean at least three different pipeline failures. The device may be absent from CMDB because discovery never completed. The device may exist in CMDB but lack an expected monitor because the discovery/credential combination did not learn that capability. Or the monitor/model may be healthy while expected logs are not being delivered.

Those cases require different evidence. CMDB presence proves accepted discovery data. It does not prove syslog/event ingestion. A successful `snmpwalk` proves SNMP path and credentials for the queried OIDs, not complete FortiSIEM support. Keeping those boundaries distinct avoids turning every monitoring symptom into “redo discovery.”

Worked distributed-discovery failure

A FortiSIEM supervisor can ping a router, but the router never appears correctly in CMDB. The organization uses a collector assigned to that network segment. The device's SNMP ACL permits only the supervisor IP. This topology explains why “supervisor connectivity is good” is irrelevant to the failing transaction: `phDiscover` is causing the actual SNMP query to originate from the collector. Run `snmpwalk` from that collector with the same version/credentials. If it fails, fix the device ACL, routing, NAT, or UDP 161 path before changing FortiSIEM discovery definitions.

If `snmpwalk` succeeds and `phDiscover` is running, transport and daemon state are proven. Now inspect whether FortiSIEM recognizes the device type and credentials sufficiently to populate the intended CMDB data and monitoring capabilities. A partial CMDB object can be a useful midpoint: identity/inventory discovery succeeded, while a specific relationship or monitor may still be absent. Syslog arrival is another separate path altogether. This layered model keeps SNMP discovery, CMDB modeling, monitoring activation, and event ingestion from collapsing into one vague “device not monitored” ticket.

Rediscovery and modeled relationships

Scheduled rediscovery is valuable because CMDB relationships can become stale independently of event ingestion. A VMware guest can move hosts, an AP can associate with a different controller, or device software can change while syslog continues uninterrupted. The discovery engine is responsible for refreshing supported inventory and relationship facts; the event pipeline is responsible for incoming logs. When a topology visualization is wrong but events are current, inspect rediscovery timing and credentials rather than assuming collectors have stopped receiving logs. Conversely, a fresh CMDB object with correct SNMP data does not prove the device is sending syslog. In distributed designs, record which collector owns the target segment and perform protocol tests there. This makes the source-IP dependency visible and prevents firewall teams from repeatedly adding the supervisor address when the collector is the actual SNMP initiator.

FortiSASE

11. Security Posture Tags in Dynamic Private Access Policies

Primary feature lesson source: https://docs.fortinet.com/document/fortisase/latest/feature-administration-guide/825799/configuring-dynamic-private-access-policies-using-security-posture-tags
Scenario support source: https://community.fortinet.com/fortisase-58/troubleshooting-tip-fortisase-posture-check-troubleshooting-prior-to-connection-to-vpn-227811

Posture evaluation creates a tag; the private-access policy consumes it

FortiSASE Security Posture Tagging Rules evaluate endpoint posture and assign tags. Dynamic private-access policy can then use a specific tag as part of the Source definition. Fortinet’s example differentiates compliant and non-compliant endpoints with tags such as `SASE-Compliant` and `SASE-Non-Compliant`, allowing one policy to permit and another to deny private access.

The architectural point is that the private-access rule does not recompute endpoint posture. It consumes the posture state already represented by the tag. Therefore a perfectly constructed private-access policy cannot match a tag that the endpoint never received, and an endpoint carrying the correct tag does not by itself prove the policy is the rule that decided the session.

Broad private-access defaults can mask a broken posture rollout

Fortinet documents an `Allow-All Private Traffic` behavior for agent-based secure private access in relevant hub deployments. When introducing posture-specific rules, a broad allow can make testing deceptively successful: the application remains reachable even though the `SASE-Compliant` policy never matched.

The validation objective must therefore be the effective decision, not merely application success. Confirm the tag-specific rule is above/otherwise selected as intended and that the source scope references the exact security posture tag. A user-visible success caused by a fallback policy is a policy-test failure even though the user can work.

There is explicit endpoint and portal evidence for assigned tags

Fortinet’s posture troubleshooting guidance identifies two concrete places to verify the control-plane outcome. FortiClient can display assigned Security Posture Tags on the endpoint. In FortiSASE, Operations > Endpoints > the endpoint > FortiClient > Tags assigned shows the tag state known to the service. Endpoint-profile connection settings also show the posture requirement associated with the connection.

If the expected tag is absent both on the client and in the portal, the failure is upstream of private-access policy matching. Investigate the posture-tag rule conditions and endpoint telemetry. If the tag is present, stop treating the posture engine as unproven and move to the rule/source/resource path.

Proving the private-access decision

For a compliant endpoint that is unexpectedly denied, establish the exact assigned tag, then inspect the dynamic private-access policy Source field and confirm it references that tag for the relevant Agent users. Next confirm the requested destination is the private resource/service the rule is meant to cover. Finally verify that the intended allow rule, rather than a deny or broad fallback, is the effective decision.

For a non-compliant endpoint that remains allowed, the same evidence chain is used in reverse: prove the non-compliant tag exists, prove a deny policy consumes it, and prove a broader allow is not winning first. This is feature-specific policy troubleshooting, not generic “check connectivity.”

Worked compliant-versus-fallback policy test

Create two controlled endpoints: one that should receive `SASE-Compliant` and one that should receive `SASE-Non-Compliant`. On each client, verify the tag in FortiClient, then confirm the same tag under Operations > Endpoints > FortiClient > Tags assigned. This proves the posture engine's result before any private application is tested. If the compliant tag is missing, do not tune private-access rules; examine the Security Posture Tagging Rule and endpoint telemetry that should produce it.

Next test a specific private application whose policy source references those tags. A compliant user should match the tag-specific allow rule and a non-compliant user the tag-specific deny rule. If both users can connect, inspect whether `Allow-All Private Traffic` or another broader rule is winning. That condition is especially deceptive because the application test “passes” from the user's perspective while the security design is not enforcing posture at all. Conversely, if the correct tag-specific rule is shown as the decision but the application still fails, the posture and policy stages are proven and the remaining boundary is the private-resource path/hub/application rather than the endpoint posture evaluator.

Testing policy precedence without relying on application reachability alone

During deployment, temporarily select a private resource whose expected behavior is unambiguous and inspect both compliant and non-compliant endpoints. Record the assigned tag on each endpoint and the matching Source definition in the private-access rule. Then test the same resource. If both endpoints receive the same outcome, compare rule precedence and broad fallback policies before modifying the posture checks. A posture rule can be correct while its tag is never consumed by the effective access rule. Likewise, a private-access rule can be correct while an endpoint never receives the referenced tag. The two-stage design is intentional: posture computation can be reused by multiple access policies, and policy can combine source scope with resource/service conditions. Troubleshooting should preserve that separation so endpoint telemetry problems do not lead to unnecessary changes in private-resource routing.

Fortinet Secure SD-WAN

12. ADVPN 2.0 Edge Discovery, Transport Groups, and Spoke Path Management

Primary feature lesson source: https://docs.fortinet.com/document/fortigate/7.6.4/administration-guide/637049/advpn-2-0
Scenario support source: https://community.fortinet.com/fortigate-3/technical-tip-how-to-configure-advpn-v2-0-on-existing-advpn-v1-0-tunnels-196173

ADVPN 2.0 moves shortcut path intelligence toward the spokes

ADVPN 2.0 adds edge discovery and path management at spokes. Instead of making shortcut behavior depend only on the hub's route-reflection/next-hop design, spokes learn information about underlays that can participate in spoke-to-spoke shortcuts and the health of those links. Fortinet positions this as a more flexible way to respond to underlay outage or degradation in an SD-WAN overlay.

The hub still participates in the initial overlay and edge-discovery exchange, but the desired data-plane outcome can become a direct spoke-to-spoke shortcut. A route learned through the hub proves basic overlay reachability. It does not prove that the two spokes discovered a compatible healthy direct transport.

Transport groups encode which underlays are compatible

Fortinet assigns each SD-WAN member a `transport-group` value from 1 through 255. Members in matching transport groups can participate as corresponding shortcut underlays. This lets the design distinguish Internet, MPLS, LTE, satellite, or other transport classes without relying on interface naming conventions.

Two spokes can each have two WAN links and still have only one compatible direct pairing. For example, Internet TG1 at Spoke A can pair with Internet TG1 at Spoke B, while Spoke B's LTE TG3 has no matching peer if Spoke A has no TG3 member. Counting interfaces is therefore not shortcut-eligibility evidence.

Health-check information participates in path management

Under `config system sdwan`, Fortinet exposes ADVPN selection on the SD-WAN zone with `set advpn-select enable` and references an ADVPN health check. Members carry their transport-group IDs, while SD-WAN service behavior can influence shortcut preference. Edge discovery shares the information needed for a spoke to evaluate whether a common underlay is acceptable.

This creates a distinct failure boundary when ordinary hub-and-spoke routing works but no direct shortcut forms. BGP/overlay reachability may be healthy while transport-group compatibility or SLA state makes the direct path ineligible.

Troubleshooting a missing shortcut without breaking the working hub path

First prove the remote prefix is reachable through the hub so base IPsec/overlay/routing is not conflated with shortcut selection. Then confirm ADVPN 2.0 selection is enabled on the relevant SD-WAN zone. Compare transport-group values on the participating members at both spokes. Check the referenced ADVPN health check and whether the candidate links are in an acceptable state. Finally inspect the service's shortcut preference and the resulting spoke-to-spoke path.

Fortinet’s cited documentation also states that ADVPN 2.0 currently supports IPv4. That is a documented capability boundary, not a reason to invent an IPv6 shortcut expectation. The proof chain is base overlay → edge-discovery participation → compatible transport group → healthy candidate → service/path choice → direct data-plane shortcut.

Worked spoke-to-spoke candidate selection

Consider Spoke A with Internet TG1 and MPLS TG2 and Spoke B with Internet TG1 and LTE TG3. Both spokes can already reach each other's LAN prefixes through the hub. That establishes the base overlay/routing path. During ADVPN 2.0 edge discovery, Internet TG1 is a common transport class, while A's TG2 and B's TG3 have no corresponding peer. The Internet pair is therefore the natural direct-shortcut candidate before SLA state is considered.

Now assume A's Internet health check is in SLA but B's Internet health is degraded. Matching transport groups alone no longer prove an acceptable path. Inspect the ADVPN health check referenced by the zone and the service's shortcut behavior. If both Internet members become healthy and a direct shortcut forms, observe the actual spoke-to-spoke data path rather than treating a route through the hub as shortcut evidence. If the route remains functional only through the hub, the overlay is healthy and the missing state is still edge-discovery/path eligibility. This separation is especially important during migration because engineers can preserve service through the hub while independently correcting transport-group, health, or shortcut-selection state.

Failure and recovery behavior across multiple underlays

ADVPN 2.0 is most useful when multiple spoke underlays have different health characteristics. Suppose the preferred TG1 Internet candidate is healthy and a direct shortcut exists. If one side's TG1 SLA degrades, the spoke must no longer treat that link as an equally healthy direct candidate; edge-discovery health information is what lets shortcut management react without depending solely on a hub route change. If another common group exists, that group can become a candidate according to the SD-WAN service behavior. If no other common group exists, traffic can continue via the working hub path while direct eligibility is unavailable. This distinction is why troubleshooting should preserve the hub route as a known-good baseline while inspecting transport-group and health information. It lets the engineer determine whether the failure is loss of overlay connectivity or simply loss of the preferred direct shortcut.
