IPv6 PIM-SM: BSR election and dynamic Rendezvous Point discovery

Additional official references

Why BSR matters in IPv6 PIM-SM

Protocol Independent Multicast sparse mode (PIM-SM) needs a Rendezvous Point (RP) for a multicast group while receivers and sources are not yet using a source-specific tree. The RP is the meeting point for the shared tree: a last-hop router with interested receivers sends a PIM Join toward the RP, while a source-side router registers the source with the RP. If the group-to-RP mapping is wrong or absent, the receiver can send an MLD report and still receive no multicast stream. IPv6 PIM-SM previously relied on statically configured RP addresses in many designs. FortiOS 8.0 adds Bootstrap Router (BSR) support for IPv6 multicast so candidate RPs can be discovered and advertised dynamically.

BSR and RP are different roles. A BSR distributes the candidate-RP set; it is not automatically the RP for every group. Candidate RPs advertise the multicast group ranges they serve, their priority and advertisement interval. The elected BSR collects those advertisements and floods the RP-set information in PIM bootstrap messages. Routers then derive the RP mapping for a group from the received set and the configured hash/priority behavior. This removes the need to manually duplicate every group-to-RP mapping on every router, but it does not remove the need to define group scope, candidate roles and PIM interfaces correctly.

Control-plane sequence and group scope

A typical receiver path begins with MLD: a host reports interest in an IPv6 multicast group, and the first-hop router learns that the group has local receivers. PIM-SM uses the BSR-distributed mapping to select the RP for that group and builds the shared-tree state toward it. Source registration and subsequent source-tree switching are separate operations. FortiOS exposes spt-threshold and spt-threshold-group controls so the operator can determine whether and for which groups traffic may move from the shared tree to a source-specific tree. Do not interpret a successful BSR election as proof that a receiver has joined, that a route exists to the source, or that packets are being forwarded.

Group scoping is a common failure point. Candidate RP configuration references IPv6 access-list objects through rp-candidate-group. A candidate that advertises the wrong list may be elected and visible while still not serving the group that the receiver joined. The candidate RP priority and interval are separate from the BSR priority and BSR interface. The BSR hash length influences RP selection among advertised candidates; it is not a multicast group filter. FortiOS also exposes compatibility controls such as cisco-crp-prefix and cisco-ignore-rp-set-priority for interoperability with older implementations. Use them only when the peer behavior requires them.

Configuration pattern

Enable multicast routing and PIM on the interfaces that participate in the IPv6 multicast domain. Define IPv6 group prefixes in an access list, then configure candidate RPs and a BSR candidate. A simplified pattern is:

config router access-list6
    edit "video-groups"
        config rule
            edit 1
                set prefix6 ff05::10/128
            next
        end
    next
end
config router multicast6
    set multicast-routing enable
    config interface
        edit "port1"
            set rp-candidate enable
            set rp-candidate-group "video-groups"
            set rp-candidate-priority 192
        next
    end
    config pim-sm-global
        set bsr-candidate enable
        set bsr-interface "port1"
        set bsr-priority 10
        set bsr-hash 10
    end
end

The exact interface names, group prefixes and priorities must match the topology. FortiOS also provides per-VRF PIM sparse-mode global settings under pim-sm-global-vrf; do not configure the global BSR and assume it automatically covers every VRF. Static RP entries under rp-address remain available where a fixed mapping is intentional. Static configuration and BSR are design choices that must be made consistently, not two independent sources that can be allowed to disagree.

Verification and failure isolation

Verify the control plane in layers. First confirm multicast routing and PIM are enabled on the expected interfaces. Then inspect the elected BSR and the RP mapping for the target group. FortiOS 8.0 adds IPv6 multicast commands including get router info6 multicast pim sparse-mode bsr-router, ... rp mapping, ... rp-hash, ... nexthop and ... mroute. Use get router info6 multicast mld groups to check receiver membership. The BSR/RP commands answer “who is advertising and which RP is selected?”; MLD answers “which groups have local receivers?”; the multicast route table answers “what forwarding state exists?” These are not interchangeable proofs.

If the BSR is absent, check the configured BSR interface, PIM adjacency and whether the BSR candidate is enabled in the correct VRF. If the BSR exists but the RP mapping is absent, check the candidate-RP advertisement, group ACL name, prefix match and advertisement interval. If the mapping is correct but no stream arrives, inspect the receiver’s MLD membership, upstream joins, source registration and multicast route state. A unicast ping to the source does not prove multicast forwarding. Likewise, a populated MLD group does not prove that the RP mapping or upstream tree is correct.

Operational caveats

BSR improves scale by distributing a common RP set, but it introduces control-plane dependencies: the BSR must be reachable through the PIM domain, candidate RPs must advertise the intended group ranges, and routers must agree on VRF and compatibility behavior. Use the documented defaults as a starting point rather than tuning priorities and hash lengths without a reason. Fortinet documents BSR priority from 0–255, hash length from 0–32, RP candidate priority from 0–255 and RP advertisement interval from 1–16383 seconds. The quick-refresh option controls acceptance of BSR quick-refresh packets; it is not a replacement for normal PIM reachability. For a controlled change, test one group and one receiver path before moving a large multicast domain.

Local certificate lifecycle: templates, renewal and expiry notifications

The certificate authority is scoped to the ADOM

FortiManager 8.0 adds lifecycle controls for certificates generated through certificate templates. The important architectural detail is that FortiManager includes a certificate authority (CA) server for each ADOM. When an ADOM is created, its private/public key pair is created and can be used when FortiManager defines IPsec VPN or agentless VPN topologies for managed devices. This is not a single global CA that should be assumed to issue every certificate in every ADOM. The template, device membership and ADOM context determine which local CA participates.

A certificate template can use an External CA or the FortiManager Local CA. An External template requires online SCEP enrollment details. A Local template uses the FortiManager CA server. Only Local-type certificates support FortiManager-configured validity periods and the documented GUI renewal workflow. If an operator expects the Local renewal controls to appear on an External template, the absence is not a GUI defect: the template type does not support that lifecycle path.

What happens during VPN installation

When a managed FortiGate is added to an IPsec VPN or agentless VPN topology that uses a template backed by the FortiManager CA, FortiManager orchestrates the certificate transaction. The FortiGate generates a certificate signing request (CSR). FortiManager signs that CSR with the Local CA and installs the resulting certificate on the FortiGate. The CA certificate containing the public key is also installed on the device. The documented workflow does not generate a pre-shared-key request for this certificate-based topology. This sequence matters when troubleshooting: a template existing in FortiManager is not proof that a leaf certificate has been generated, installed and trusted by the remote peer.

Certificate feature visibility must be enabled before the Certificate template area is available. In Device Manager, go to Provisioning Templates > Certificate, create a template, select Type = Local, and set the validity period. The documented choices are 3 years, 5 years, 10 years, or a custom period up to 3650 days. The remaining template information is configured and saved in the same dialog. The exact certificate subject/SAN and usage requirements still need to match the intended VPN or service; choosing Local does not make a certificate valid for every purpose.

Generate, renew and monitor

Generation and renewal are separate Certificate Operations. From Device Manager > Provisioning Templates > Certificate, right-click a configured template or use More > Certificate Operations. The operation dialog lets the administrator choose Generate or Renew. For renewal, the device table shows managed devices and certificate expiration dates; select the intended devices and confirm. FortiManager also raises a notification when managed-device certificates are within 30 days of expiry. The Notifications pane shows the number of affected devices, and Details opens the device-organized list. An administrator can view the default certificate or open Certificate Operations from the notification workflow.

Do not treat the notification as proof that a certificate has been renewed. It is an inventory/attention signal. Likewise, the certificate operation being accepted by FortiManager does not prove that the remote VPN peer trusts the installed chain. A complete validation checks the device’s actual certificate and issuer, the peer’s trust store, certificate validity dates, subject/SAN, EKU and the resulting IKE authentication.

Operational troubleshooting

Consider a site-to-site VPN that fails after a planned certificate rollover. First identify the ADOM and template used by the topology. If the template is External, the Local renewal procedure is not applicable. If it is Local, inspect the selected device list and expiration date in Certificate Operations, then verify the renewed certificate was installed on the affected FortiGate. If FortiManager shows a renewed certificate but IKE still fails, move beyond the management plane: confirm the peer has the correct CA certificate, that the new leaf certificate is presented, and that identity matching is correct. A stale peer trust anchor or mismatched subject can produce the same symptom as an unsuccessful renewal.

For change control, renew a small device set first, validate the resulting tunnel and then expand. The ADOM-local CA model is useful for centrally managed topologies, but it creates an explicit ownership boundary: the ADOM and template must remain available and correctly scoped. Fortinet’s guide notes that some settings may not be available in all ADOM versions, so verify ADOM compatibility before building the lifecycle around the feature. Do not silently convert an External CA process into a Local CA process just to obtain the renewal button; that changes the trust and issuance model.

Evidence that closes the loop

Use four pieces of evidence: the template type and validity period; the Certificate Operations device/expiry table; the Notifications pane’s affected-device list; and the certificate actually installed on the FortiGate plus the VPN result. Each proves a different stage. A notification proves that FortiManager identified an approaching expiry. A successful renewal operation proves that FortiManager processed the selected request. The installed leaf and issuer prove the device state. A successful IKE negotiation proves that the peer accepted the authentication exchange at that moment. Keep those stages separate in the troubleshooting record.

Machine-learning anomaly detection: training, artifact validation and inference

Primary Fortinet source

https://docs.fortinet.com/document/fortianalyzer/8.0.0/administration-guide/150557/machine-learning-for-anomaly-detection

Additional official references

  • Supporting Fortinet documentation
  • Supporting Fortinet documentation

Model, asset and artifact are different objects

FortiAnalyzer 8.0 introduces machine-learning anomaly detection that profiles historical behavior and generates alerts when new activity deviates from the learned pattern. The documented use cases are FortiAuthenticator login anomalies (geographic-location and time deviations) and FortiGate traffic anomalies (abnormal inbound/outbound, upload or download patterns). The feature is not a universal detector for every log source or every attack type. It complements signature and rule-based detection by looking for behavior that is unusual for a particular user or endpoint.

Three terms are central. A model is the algorithm for a specific task, such as login anomaly or traffic download anomaly. An asset is the entity being monitored, such as an end user or endpoint. An artifact is the trained model data produced from historical logs and used for live inference. A model can be configured but have no usable artifact; an artifact can be trained and tested but not deployed; a deployed artifact can be running inference without generating an alert if no behavior crosses its criteria. Treat these as separate lifecycle states.

Training and configuration

The feature is managed through the FortiAnalyzer CLI. Enabling the global machine-learning flow (config system mlflow) initializes required materialized views in the backend database. Each model is then configured under config models. The supported model types are login-anomaly, traffic-download-anomaly and traffic-upload-anomaly; Fortinet documents only one of each model type in the configuration. The training period is set by train-data-days (1–365, default 90), and the held-out test period by train-test-days (1–90 and no greater than the training period). Training repeat schedules can be daily, weekly, monthly or an interval such as 7d; the schedule uses the FortiAnalyzer system timezone.

Resource controls matter. asset-max-count limits tracked assets (100–100000; default 1000). Higher values require more memory and processing. artifact-max-count and artifact-retention control how many artifacts and how many days of artifact history are retained. auto-deploy determines whether a trained artifact is automatically deployed after its scheduled training. If it is disabled, a human must validate and deploy the artifact. inference-interval controls how often new data is evaluated. Login anomaly defaults to 20 minutes; traffic download/upload models use 60 minutes and require a multiple of 60. A faster interval is not automatically better because it increases processing demand.

config system mlflow
    set status enable
    config models
        edit 1
            set status enable
            set model-type login-anomaly
            set train-data-days 90
            set train-test-days 7
            set train-repeat-at '7d'
            set asset-max-count 10000
            set auto-deploy enable
            set inference-interval 20
            set artifact-retention 30
            set artifact-max-count 10
        next
    end
end

Validate before deployment

FortiAnalyzer exposes lifecycle commands so an operator can distinguish model configuration from artifact health. diagnose mlflow config shows per-model configuration and artifact statistics, including count, deployed state and last training. diagnose mlflow training-status shows current training progress. diagnose mlflow list-artifacts can filter by status, model type or artifact name. diagnose mlflow show-assets and show-details reveal the assets included/excluded and artifact details. diagnose mlflow test-result and infer-result provide test and latest inference results.

For manual lifecycle control, FortiAnalyzer provides execute mlflow train, test, deploy, undeploy, cancel and exclusion-list operations. A sensible change process is to train on a known historical interval, test on a separate interval, inspect sensitivity and excluded assets, then deploy the artifact. The test period is not merely a checkbox: assets that fail the selected sensitivity criteria can be placed on an exclusion list. If the data is unrepresentative—for example, a business holiday or a one-off bulk transfer dominates the training window—the artifact may learn an abnormal baseline.

Alerting and operational interpretation

Internal inference events are processed by the predefined alert handler Machine Learning Based Anomalous Activity Detection. Analysts find the resulting alerts under Incidents & Alerts > Alerts > All Alerts and can filter by that handler. An alert should include context about the deviation, such as upload volume exceeding the user’s learned 90-day pattern. That is evidence of statistical deviation, not proof of exfiltration. Correlate the alert with the user’s role, destination, application, change window, endpoint state and other logs before treating it as malicious.

Common failure patterns are: the global flow is disabled; the model is disabled; there is insufficient historical data; the model has trained but the artifact is not deployed; the asset cap excludes important users/endpoints; the test sensitivity excludes too many assets; or the traffic model uses an invalid inference interval. Check the stage rather than repeatedly changing alert thresholds. The machine-learning feature also creates materialized views and consumes storage/compute, so asset limits, artifact retention and training cadence are capacity settings, not cosmetic options.

A practical investigation

If an expected login anomaly is absent, confirm that the login-anomaly model is enabled, that FortiAuthenticator login logs are arriving, and that the historical training interval includes the user’s normal baseline. Then inspect the most recent artifact and whether it is deployed. Use show-assets to see whether the user was excluded, test-result to understand validation and infer-result to see the latest inference. Only after the model lifecycle is healthy should you conclude that no anomaly was detected. If the artifact is stale or the user was excluded, the absence of an alert is not evidence of normal behavior.

OpenSSL security levels per application and tunnel-mode overrides

Additional official references

  • Supporting Fortinet documentation

What changed in FortiSwitchOS 8.0

FortiSwitchOS 8.0 raises the default OpenSSL security level from 0 to 2. The setting can be configured from 0 through 5, with 0 the least restrictive and 5 the most restrictive. This is a runtime cryptographic policy applied to FortiSwitch applications that use OpenSSL; it is not the same thing as firmware-image signature verification or configuration-file integrity checking. A device can therefore boot and forward traffic normally while one management or infrastructure daemon fails to establish a TLS/SSH session with an older peer.

Fortinet exposes a long list of applications, including httpsd, sshd, snmpd, radius_das, dnsproxy, fortilinkd, miglogd, ntpd, sftp and other daemons. The list is important because a global security-level change can affect more than the management GUI. A TLS failure in one service does not prove the switch-wide policy is wrong; another daemon may use a different effective level.

Configuration and effective policy

The CLI hierarchy is config system security, then config app-security. Edit default to set the level for all applications, or edit a named application to set a narrower exception. A typical configuration is:

config system security
    config app-security
        edit default
            set security-level 2
        next
        edit httpsd
            set security-level 3
        next
    end
end

Fortinet documents an important override: when tunnel-mode is set to compatible under config switch-controller global, the OpenSSL security level is overridden and changes to 0 on the switch where the command is executed. When tunnel mode is strict, the security level is defined by the configured per-application value. This means the configured per-app number is not enough to infer the effective policy. Always inspect tunnel mode as well.

The security-level control is not a convenient way to force a specific cipher suite or protocol version. It selects an OpenSSL security policy level. The exact handshake result still depends on the peer’s certificate, key size, signature algorithm, protocol and cipher support. Fortinet’s guide tells operators that the level changed and how to configure it; it does not provide a per-level cipher matrix for every application. Do not invent one from the numeric value.

Troubleshooting a post-upgrade handshake failure

Consider a switch that upgrades to 8.0 and then stops sending logs to a collector or cannot complete an HTTPS session to a management endpoint. First isolate the failing application. Confirm whether the issue is in httpsd, miglogd, sftp, snmpd or another daemon. Check the configured default and per-application levels, then check tunnel-mode. If the mode is compatible, a per-application level may not be the effective value. If it is strict, the configured per-app level applies.

Next compare the peer’s certificate and TLS/SSH capabilities with the effective security level. A successful ping only proves IP reachability. A successful SSH login does not prove HTTPS, SFTP or RADIUS-over-TLS will negotiate the same way because they are different applications and may use different daemon policy. Use daemon-specific logs and a packet capture to identify the handshake stage that fails. Avoid lowering the global default to 0 as a first response; that may restore one old peer while weakening every application that inherits the default.

A safer remediation sequence

Make the narrowest change that addresses the peer incompatibility. If only one application must communicate with a legacy endpoint, use a per-application exception after confirming that the peer cannot be upgraded. Keep other applications at the stronger default. Test the affected transaction, then remove the exception when the peer is modernized. If tunnel-mode compatibility is enabled, decide whether the broader compatibility behavior is intentional; switching to strict changes the effective OpenSSL policy and should be planned with FortiLink dependencies in mind. The CLI tooltip requires configuration from console or SSH, so maintain out-of-band access before changing the policy.

A recent FortiSwitch Community technical tip dated November 9, 2026 describes transferring full configuration backups to SFTP, FTP or TFTP. That article is useful as an operational example of a service that may be involved in a backup workflow, but it does not document the OpenSSL level feature. Use the FortiSwitchOS administration guide as the primary source for the cryptographic policy and the Community article only as a scenario companion.

What the evidence proves

The configured app-security values prove intended policy, not necessarily the effective policy if tunnel mode overrides it. A daemon log or packet trace proves whether a specific handshake reached the peer and where it failed. A completed application transaction proves that the selected daemon negotiated with that peer at that time; it does not prove every other daemon is compatible. Record the switch version, tunnel mode, default level, per-application level and peer certificate/protocol details together so the next engineer does not mistake a service-specific interoperability issue for a general switching outage.

05 · FortiAP/Wireless · FortiAP/FortiOS 8.0.0

Encrypted CAPWAP data channels and FortiAP-side IPsec offload

733 focused words · feature-led lesson

Primary Fortinet source

https://docs.fortinet.com/document/fortiap/8.0.0/fortiwifi-and-fortiap-configuration-guide/746425/data-channel-security-clear-text-dtls-and-ipsec-vpn

Additional official references

  • Supporting Fortinet documentation

Control and data are separate CAPWAP channels

After a FortiAP joins a FortiGate, a CAPWAP tunnel is established. The tunnel carries two logically different channels. The control channel carries management traffic and is always encrypted with DTLS. The data channel carries wireless client packets and can be configured separately. Fortinet documents clear-text as the default data-channel policy, along with dtls-enabled, ipsec-vpn and ipsec-vpn-sn. This distinction is operationally important: a FortiAP can appear joined and manageable because the control channel is healthy while the data-channel encryption or forwarding path is not working as intended.

ipsec-vpn and ipsec-vpn-sn establish an IPsec tunnel between the FortiAP and FortiGate to carry CAPWAP data packets. The serial-number variant includes the FortiAP serial number within the tunnel. This is tunnel protection for the AP-to-controller data channel; it is not the same as the client’s WPA2/WPA3 radio encryption and does not replace the WLAN authentication policy. Think of the path as client-to-AP radio security followed by AP-to-FortiGate CAPWAP data-channel security.

Configure the data-channel policy

The setting lives in the wireless-controller WTP profile. A simplified configuration is:

config wireless-controller wtp-profile
    edit "branch-secure"
        set dtls-policy ipsec-vpn
        set ipsec-offload enable
    next
end

The dtls-policy selects the data-channel mode. The ipsec-offload option is available when the policy is ipsec-vpn or ipsec-vpn-sn; Fortinet documents it as enabled by default. The profile must then be applied to the FortiAP. Changing a profile that is not assigned to the affected AP will not change the running tunnel. Verify the actual WTP profile binding and the AP’s state after the change.

Fortinet explains that IPsec offloading allows the FortiAP to offload the IPsec traffic itself and improve client throughput. The documentation also notes that FortiGate models with NP6 can offload CAPWAP data traffic in IPsec, and that the FortiAP can become the performance bottleneck in this design because it does not have the same built-in hardware acceleration capability. Therefore, do not assume that enabling IPsec automatically increases end-to-end throughput on every AP model. The AP’s own processing capacity, client load and radio conditions still matter.

Security and performance trade-offs

Clear-text has the highest possible data throughput in the documented modes, and FortiGate hardware acceleration can improve throughput for clear-text CAPWAP data. It does not provide confidentiality for the AP-to-controller client-data tunnel. DTLS encrypts the data channel but may have a different performance profile from IPsec. IPsec provides an encrypted data channel and can benefit from FortiGate NP6 offload; the FortiAP remains a potential bottleneck. The correct selection depends on the security requirement and the hardware at both ends, not a universal ranking of the modes.

For secure branch deployments where the AP reaches a remote FortiGate across an untrusted transport, encrypted data-channel protection is generally the design requirement. If the security requirement is only management-channel protection, remember that control-channel DTLS is always enabled but the default data channel is clear-text. That is a common design misunderstanding: a protected CAPWAP control channel does not mean user data is encrypted inside CAPWAP.

Verification and troubleshooting

Verify in layers. Confirm the AP is authorized and joined, and that the control channel is healthy. Then inspect the WTP profile’s dtls-policy and ipsec-offload values, verify the IPsec SA between the AP and FortiGate, and check packet/byte counters while a wireless client sends traffic. If control traffic works but client data does not, focus on the data-channel policy, IPsec negotiation, serial-number binding (for ipsec-vpn-sn), routing and the AP-to-controller path. If the tunnel is established but throughput is low, compare AP CPU/load, FortiGate hardware acceleration and radio utilization before disabling encryption.

A packet capture taken only on the wireless side will show the client’s radio traffic; a capture on the wired transport between AP and controller should show the encapsulated CAPWAP/IPsec path. The exact visibility depends on capture point and decryption capability. A successful CAPWAP join proves management reachability, not data-channel encryption. A visible IPsec SA proves negotiation, not that the correct client VLAN/SSID traffic is using it. Confirm the data counters increase for the client flow.

Dependencies and rollout

Confirm the AP model, FortiOS release and WTP profile support the selected mode. Apply the profile to a pilot AP first, verify client association, DHCP, DNS and application traffic, then expand. Do not test by switching all APs to clear-text merely to recover throughput unless that is an explicitly approved security exception. When comparing throughput, hold radio channel, client mix and WAN path constant; otherwise the result may be attributed to IPsec offload when the bottleneck is actually RF or upstream transport.

06 · FortiNAC · FortiNAC 9.4.0+

Windows AV compliance using the Security-Center provider

759 focused words · feature-led lesson

Primary Fortinet source

https://docs.fortinet.com/document/fortinac/9.4.7/release-notes/636223/new-features-in-9-4-0

Additional official references

  • Supporting Fortinet documentation

Why the compliance source matters

FortiNAC 9.4 expanded its Windows antivirus compliance options. Earlier versions checked antivirus compliance within the Windows Defender AV product. Version 9.4 adds a choice named Security-Center in the Windows AV category so that FortiNAC can use the Windows Security Center view of antivirus protection and signature currency. This matters in environments where Windows endpoints use an antivirus product other than Defender but still register their protection state with Windows Security Center. A Defender-only check can report a false noncompliant state when Defender is not the active AV provider even though another registered provider is current.

The setting is a posture-source choice, not a replacement for endpoint security itself. FortiNAC is observing endpoint state and comparing it with the configured host profile or compliance requirement. It does not install an antivirus engine or make stale signatures current. The release note specifically describes up-to-date virus definitions as the compliance outcome. Do not silently broaden that to “the endpoint is fully protected,” “real-time protection is enabled,” or “EDR is healthy” unless those are separately measured by another control.

Where it fits in the NAC decision

FortiNAC’s out-of-band architecture combines endpoint information, network identity and access policy. The Windows AV category is one input into the host’s posture/compliance state. A policy can use that state when deciding whether the endpoint remains in its normal network, is assigned a restricted network or requires remediation. The exact enforcement action depends on the network access policy and the infrastructure integration; selecting Security-Center does not by itself define the quarantine action.

In the host profile, choose the Windows AV category and select the appropriate provider/check option. Use Defender when the intended policy explicitly requires Defender. Use Security-Center when the compliance design is to evaluate the AV provider reported by Windows Security Center. Validate that the endpoint’s actual AV product is registered with Windows Security Center and that the FortiNAC agent/host data reflects the expected status. The Fortinet release note does not specify the underlying Windows API or exact agent polling interval, so do not infer those implementation details from the UI label.

A realistic failure scenario

An organization standardizes on a third-party AV product for a group of Windows laptops and disables Defender’s active scanning. FortiNAC still uses a Defender-specific AV compliance check. The laptops are protected by the approved AV product, but the Defender-specific check sees Defender as inactive or not current and marks the hosts noncompliant. The wrong response is to enable Defender just to satisfy the NAC check; that can create a conflicting endpoint-security design. The better response is to confirm the provider’s Windows Security Center registration, change the Windows AV category to Security-Center for the appropriate host profile, and validate the resulting host state.

Do not apply the Security-Center source globally without understanding the endpoint mix. If the organization intentionally requires Microsoft Defender, a broad Security-Center setting may accept a different registered provider and weaken the policy’s meaning. The policy must express the actual requirement: “Defender is current” and “Windows reports an approved AV provider as current” are not equivalent statements.

Verification and troubleshooting

Collect evidence from both sides of the integration. On Windows, inspect the active AV provider and its definition status in the operating system’s Security Center view. In FortiNAC, inspect the endpoint/host record, the Windows AV category selected in the host profile, the agent-reported posture and the resulting compliance state. Compare the timestamp and provider identity. If Windows reports current definitions but FortiNAC still reports stale or absent data, investigate agent communication, host identity mapping, supported OS/agent version and the profile assigned to that host. Do not change the enforcement policy until the posture input is understood.

A compliant status proves that the selected compliance check passed according to the data FortiNAC received. It does not prove every endpoint protection feature is enabled. Conversely, a noncompliant status does not prove malware is present; it may indicate an unsupported provider, stale signatures, agent reporting delay or the wrong host profile. Keep the finding at the same level as the evidence.

Dependencies and change control

The feature is documented as part of FortiNAC 9.4.0 new features and is present in the 9.4 release line. Check the deployed release and endpoint agent compatibility before changing host profiles. Test with at least one Defender endpoint and one endpoint using the approved alternate AV provider. Confirm that the same policy does not accidentally accept a provider outside the organization’s approved list. The release note provides the product-level feature description but not a detailed agent protocol; if a low-level Windows API or polling behavior is required for an incident, obtain that detail from the matching FortiNAC agent documentation or Fortinet Support rather than guessing.

07 · FortiNAC-F · FortiNAC-F 7.6.0

KEA DHCP for isolated hosts and PXE boot option delivery

725 focused words · feature-led lesson

Primary Fortinet source

https://docs.fortinet.com/document/fortinac-f/7.6.0/dhcp-attributes

Additional official references

  • Supporting Fortinet documentation

The internal DHCP service changed

FortiNAC-F 7.6 uses KEA DHCP as the internal DHCP server for dynamically assigning addresses to isolated hosts. Earlier releases used ISC DHCP. The change is operationally significant because the configuration format and customization model differ. In earlier versions, administrators could edit dhcp.conf directly. FortiNAC-F 7.6 removes root login and explicitly directs administrators not to modify DHCP configuration files directly. Many common DHCP options can now be configured through the GUI. The DHCP Attributes Cookbook documents how to configure those options using supported GUI attributes.

The DHCP service is part of the isolation workflow. A host placed in an isolation scope still needs a valid address, gateway and DNS information so it can reach remediation or deployment services. For some use cases, the DHCP response must also contain boot-server and boot-file information. A successful lease is only the first part of the transaction; it does not prove that the host can reach the TFTP server or execute the boot program.

PXE boot transaction

Fortinet’s PXE example describes a five-step process. First, the host broadcasts an ordinary DHCP request. Second, the DHCP server responds with the host’s IP configuration and the file server’s address and boot-file path. Third, the client contacts the file server using TFTP and requests the boot file. Fourth, the server transfers the boot file, typically a network boot program (NBP). Fifth, the host executes the NBP, which can load an OS kernel, deployment tool or diagnostic utility. The DHCP exchange and the TFTP transfer are different protocols and different failure boundaries.

Before configuring the options, confirm that the file server supports TFTP, the boot file exists and is readable/executable by the TFTP service, and the host BIOS/firmware supports network boot. If a firewall is present, the isolation network must be allowed to reach the TFTP server. A DHCP ACK containing the correct address does not prove any of these conditions.

Configure both option representations when required

The cookbook calls out a compatibility issue: some PXE clients do not recognize the tftp-server-name and boot-file-name DHCP options in the same way. In those cases, configure both the Advanced settings and Standard DHCP attributes. Advanced settings include Next Server (the TFTP/file-server IP address) and Boot File Name (the absolute boot-file path). Standard attributes include tftp-server-name and boot-file-name. The two representations should agree. A mismatch can cause the client to request the wrong file or server even though the lease looks normal.

The cookbook shows a KEA DHCPv4 configuration with an isolation subnet, address pool, valid lifetime, next-server, boot-file-name, router, DNS and explicit DHCP options. It also shows the KEA lease database and log paths. The sample configuration is useful for understanding the resulting service state, but the supported configuration change should be made in the FortiNAC-F GUI rather than by hand-editing the file. The documented shell command execute enter-shell can be used to inspect the generated /etc/kea/kea-dhcp4.conf; inspection is not permission to make unsupported edits.

Troubleshooting a host that leases but will not boot

Start with the lease. Confirm the host received an address from the intended isolation scope, with the expected subnet, router and DNS. Then inspect the generated DHCP options: Next Server, Boot File Name, tftp-server-name and boot-file-name. Confirm both representations point to the same server and absolute path. Next test TFTP reachability from the isolation network and confirm the boot file is accessible with the required permissions. If the host never attempts TFTP, inspect the DHCP options and firmware PXE setting. If it attempts TFTP but the transfer fails, focus on routing, firewall policy, server service and file permissions rather than repeatedly changing the address pool.

When a host is isolated, the normal production path may be intentionally unavailable. The TFTP service must therefore be reachable through the isolation network’s approved remediation path. Do not solve the problem by broadly opening isolation-to-production access. Create the minimum path to the boot server and verify the source/destination/port requirements.

Upgrade and operational caveats

FortiNAC-F 7.6’s use of KEA and removal of root-level file editing are upgrade considerations. If an older deployment has custom ISC DHCP options, inventory them before migration and translate them into the supported GUI attribute model. Do not assume an old dhcp.conf fragment can be copied into KEA; the configuration syntax and service behavior differ. After migration, test a normal isolated-host lease and a PXE boot scenario. The two tests validate different parts of the service: lease assignment validates DHCP scope and options, while PXE validates the subsequent TFTP transaction.

08 · FortiAuthenticator · FortiAuthenticator 8.0.0+

OTP-only push notification modes and FortiClient-compatible fallback

721 focused words · feature-led lesson

Primary Fortinet source

https://docs.fortinet.com/document/fortiauthenticator/8.0.2/administration-guide/749421/general

Additional official references

  • Supporting Fortinet documentation

The policy controls what happens when an OTP-only user triggers push

FortiAuthenticator 8.0 adds an OTP-Only Push notification mode under Authentication > User Account Policies > General. It is not a global switch that makes every account use push. It defines how an OTP-only authentication request is handled when a push trigger is received and the user account may or may not support push notifications. This is important for environments where a user has a token-based account without a password and the client may use either a push workflow or a manually entered OTP.

The setting has three values. None is the default and does not support push notification for OTP-only users. Normal sends a push when the trigger is received and the account supports push; if the account does not support push, the authentication request is rejected. FortiClient-compatible also sends push when supported, but if the account does not support push, the request is ignored. That allows the end user to enter username and OTP manually in FortiClient and submit a new authentication request. The “ignore” behavior is deliberate compatibility behavior, not a successful authentication.

Authentication sequence

Think of the flow as a policy decision after the OTP-only account has been identified. The client sends an authentication request that includes the push trigger. FortiAuthenticator evaluates the user account policy and whether the account supports push. If push is available, the server triggers the notification. If push is unavailable, the configured mode determines whether the request is rejected or ignored. In FortiClient-compatible mode, the user can then send a new request with a manually entered OTP. That is a second authentication request, not a hidden server-side conversion of the original push request into an OTP.

This distinction matters during troubleshooting. An administrator may see no push notification and assume the token is invalid. But under None, push is not supported for OTP-only users; under Normal, an unsupported push-capable account is rejected; under FortiClient-compatible, the trigger can be ignored so the user can retry manually. The policy value changes the expected transaction and therefore the expected logs and client behavior.

Choosing the right mode

Use None when OTP-only accounts should not initiate push notifications. Use Normal when a push trigger must fail closed if the user is not configured for push. Use FortiClient-compatible when the supported FortiClient flow must allow a manual OTP retry for accounts that cannot receive push. Do not select compatibility mode merely to make a failed push disappear from the logs. It changes the expected user experience and can create a second authentication path that needs to be documented and tested.

Validate that the user’s account actually supports FortiToken Mobile push notifications and that the policy assigned to the user is the policy you changed. A correct global policy does not help if the user is matched to a different account policy or realm. Test at least one push-capable OTP-only account and one account without push support. Confirm that the former receives a push and that the latter follows the expected reject/ignore behavior.

Evidence and troubleshooting

Collect the policy value, user/account token state, client type, complete RADIUS or authentication request sequence and the resulting response. For a Normal-mode failure, check whether the account supports push before resetting the token. For FortiClient-compatible mode, verify that the client submits a second request containing the manually entered OTP. A missing notification alone does not prove the OTP is wrong. A rejected request does not prove the token seed is invalid; the rejection may be the configured policy response to unsupported push.

Fortinet documents the three mode behaviors but does not claim that every RADIUS client implements the same push-trigger exchange. Test the exact client and authentication path in use. Do not generalize FortiClient-compatible fallback to arbitrary third-party RADIUS clients. If the deployment uses mixed client types, separate policies or carefully scoped user groups may be safer than selecting one global behavior that surprises some users.

Security and operations

Normal mode is fail-closed for an OTP-only user who cannot receive push. FortiClient-compatible mode trades that strict rejection for a manual OTP retry path. Make the choice based on client capability and the intended authentication assurance. Keep token enrollment, account push capability and user policy aligned. During a change, monitor both successful push approvals and manual OTP retries so that a compatibility setting does not mask a broken push-delivery service. The policy controls the authentication workflow; it does not guarantee mobile network reachability, notification delivery or token validity.

09 · FortiPAM · FortiPAM 1.9.0

TCP Segmentation Offload and Generic Segmentation Offload on system interfaces

691 focused words · feature-led lesson

Primary Fortinet source

https://docs.fortinet.com/document/fortipam/1.9.0/administration-guide/327103/tcp-segmentation-offload-tso-and-generic-segmentation-offload-gso

Additional official references

  • Supporting Fortinet documentation

Why FortiPAM exposes segmentation offload

FortiPAM 1.9 adds TCP Segmentation Offload (TSO) and Generic Segmentation Offload (GSO) at the system-interface level. Both are enabled by default on all system interfaces and can be enabled or disabled per interface. The purpose is to reduce CPU work during packet transmission. Instead of requiring the CPU to segment every large TCP payload into smaller packets before transmission, the operating system can pass a larger buffer to the NIC or kernel, which performs the segmentation closer to the interface.

TSO and GSO are related but not identical. TSO generally delegates TCP segmentation to the network interface. GSO is a more general kernel mechanism that allows large packets to be carried through parts of the networking stack and segmented later by a capable lower layer. Fortinet’s FortiPAM documentation describes the combined behavior as the OS transmitting large data packets and delegating segmentation into network-compliant packets to the NIC or kernel. The operational effect is lower CPU overhead and potentially higher throughput, especially when the appliance handles sustained TCP data transfers.

Per-interface configuration

The settings are CLI-only and are configured under the system interface:

config system interface
    edit "port1"
        set tso enable
        set gso enable
    next
end

Because the settings are per interface, do not assume that changing port1 changes every path. A FortiPAM appliance with separate management, user-access and target-facing interfaces may show different behavior depending on which interface carries the traffic. The defaults in 1.9.0 are enabled, so a newly upgraded appliance may behave differently from an older deployment or a deployment where an administrator previously disabled offload for troubleshooting.

These settings affect packet construction and transmission efficiency; they do not change TCP application semantics or the maximum Ethernet MTU. The receiving endpoint still receives normal TCP segments within the path MTU. The large buffer is an internal representation before segmentation, not a jumbo frame sent unchanged across the network.

Packet capture interpretation

Offload can make packet captures confusing. A capture taken on the sending host before the NIC performs TSO/GSO may display a packet larger than the interface MTU. That does not necessarily mean the FortiPAM appliance transmitted an oversized Ethernet frame. The segmentation may occur after the capture hook. A capture on an external tap or on the receiving side should show the wire-sized segments. When investigating retransmissions, out-of-order traffic or apparent MTU violations, record the capture point before concluding that the network carried a giant packet.

Do not conflate TSO/GSO with path MTU discovery, TCP MSS clamping or fragmentation. Those mechanisms address different layers and different constraints. Segmentation offload changes where the work is performed; it does not make an underlay path support a larger MTU. If a peer or middlebox has an MTU issue, offload will not remove the path constraint.

Troubleshooting and safe testing

If FortiPAM shows high CPU during sustained transfers, first confirm the per-interface TSO/GSO state and compare CPU and throughput under a controlled workload. If a packet capture appears to contain oversized TCP packets, repeat the capture at an external tap or receiving endpoint before changing the configuration. If a suspected offload bug is being isolated, disable one feature at a time on a test interface, compare the result and restore the default unless the test demonstrates a repeatable problem. Disabling both globally can increase CPU overhead and reduce throughput.

Useful evidence includes interface configuration, CPU utilization, throughput, retransmission counters and captures from both pre-segmentation and post-segmentation points. A large packet in a host capture proves what the capture hook observed, not what was placed on the wire. A lower CPU reading after enabling offload supports the performance hypothesis but does not prove that every TCP session is healthy. Always verify the actual application transaction.

Operational implications

FortiPAM is a privileged-access platform, but its network interface still behaves like a TCP endpoint. When it proxies or records privileged sessions, the appliance may carry long-lived and high-throughput streams. Segmentation offload can reduce CPU cost for those streams, leaving more processing capacity for session control and recording. It is not a security policy and does not encrypt or decrypt traffic by itself. Keep the distinction clear when documenting the change: the feature optimizes packet segmentation; TLS, SSH, session recording and access controls remain separate functions.

10 · FortiSIEM · FortiSIEM 7.5.1

OAuth 2.0 Client Credentials grant for FortiSIEM public REST API tokens

734 focused words · feature-led lesson

Primary Fortinet source

https://docs.fortinet.com/document/fortisiem/7.5.1/user-guide/548346/api-token

Additional official references

  • Supporting Fortinet documentation

Why API tokens replace password-based automation

FortiSIEM 7.5.1 adds the OAuth 2.0 Client Credentials grant for API tokens used by public REST API calls. API tokens were introduced in 7.5.0 with a Refresh Token grant; in 7.5.1 the documented token acquisition flow uses a Client ID and Client Secret. This is a machine-to-machine credential model: an automation client obtains a short-lived Bearer access token and presents it to the REST API, rather than storing a human administrator’s password in a script. Password-based public REST calls remain available for backward compatibility in the documented release, but Fortinet notes that the method may be deprecated in a future release.

Token issuance and API authorization are separate. A token is associated with an owner, organization and Client ID. API calls made with the token inherit the privileges of the user who created it. A Network Admin token is therefore not equivalent to a Full Admin token. A token created by an organization’s Full Admin is scoped to that organization’s data; a Super-global Full Admin token can access data across organizations. The caller should not assume that successful token issuance means every API endpoint will be authorized.

Permissions and organization context

Only Full Admin users have built-in permission to create API tokens within each organization. A Full Admin can grant other users permission to create tokens by enabling OAuth Tokens in the user’s role profile. FortiSIEM also documents an organization-context restriction: Super/Global users cannot create an API token for an organization simply by switching organizations. The administrator must log in as a user belonging to the target organization to create that organization’s token. This is a common automation setup mistake because a global operator may be able to view multiple organizations but still cannot mint an organization-owned token by changing the UI context.

Before creating a token, decide which organization and role the integration requires. Use the narrowest role that can perform the required API operations. The token table displays token name, organization, owner, Client ID, Client Secret expiry and status. Those fields are the administrative inventory for the credential; the access token itself is not the long-term identity of the integration.

Token acquisition and use

The client posts to the FortiSIEM OAuth token endpoint with grant_type=client_credentials, client_id and client_secret. A successful response includes an access_token, token_type of Bearer and expires_in (the documented example returns 3600 seconds). The client then sends the access token in the Authorization header for public REST API calls. When the access token expires or is lost, the client can obtain another token as long as the Client Secret has not expired. When the Client Secret expires, a new Client ID/Client Secret pair is required.

POST /phoenix/rest/pub/security/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
client_id=<client-id>
client_secret=<client-secret>

# Response example
{
  "access_token": "abc123",
  "token_type": "Bearer",
  "expires_in": 3600
}

# Subsequent REST request
Authorization: Bearer <access_token>

Store the Client Secret in a protected secret store, not in source control or a command history shared by operators. The access token should be treated as a bearer credential until it expires or is revoked.

Rotation, revocation and evidence

FortiSIEM allows an administrator to reset a Client Secret or revoke a token from Admin > Settings > System > API Token. Resetting the secret issues a new secret that can be used to obtain an access token. Revoking the token invalidates the currently used access token immediately; the integration must obtain a new access token using the token endpoint. Deleting a token is a different administrative action and should be treated as removal of the credential record.

When troubleshooting a 401/403, separate authentication from authorization. A token endpoint failure suggests incorrect client credentials, expired secret, missing permission or wrong organization context. A token that is issued successfully but receives 403 from a resource endpoint may be authentic but lack the required role privilege or organization scope. Inspect the token table, response status, token expiry and user role. Do not rotate the secret repeatedly when the actual issue is that the token owner is a Network Admin trying to read a Full Admin-only resource.

Version and capacity caveats

Use the 7.5.1 User Guide and Release Notes for this flow. FortiSIEM 7.5.1 has an upgrade requirement of 32 GB memory on the Supervisor, which is relevant when planning the release upgrade that introduces the Client Credentials behavior. This is not a token-specific memory requirement; it is a platform prerequisite. After upgrade, validate the token endpoint, the role-scoped resource call and the secret rotation/revocation process in a non-production integration before switching production automation from password authentication.

Secure Browser: extension profiles, user assignment and browser-side controls

Additional official references

A browser-side enforcement plane

FortiSASE Secure Browser is an extension for supported browsers, including Google Chrome and Microsoft Edge. It is designed for unmanaged and contractor devices and can also be deployed on top of existing FortiClient-agent or agentless proxy deployments. The extension provides visibility into browser activity without relying solely on network deep-packet inspection, and can monitor/block web threats and reduce data exfiltration through browser actions. This is a different enforcement point from a Security PoP inspecting steered traffic: the browser extension can observe actions that are meaningful inside the browser, such as entering sensitive data or downloading a file.

Secure Browser is a select-availability feature and is not enabled by default on new FortiSASE instances. The administration guide directs customers to create a FortiCare support ticket to enable it. Do not spend time troubleshooting an extension profile on a tenant where the feature has not been enabled. Confirm tenant availability first, then deploy the extension to the supported browser and ensure the user is assigned a profile.

Profile and user assignment flow

A Secure Browser profile defines the extension’s behavior. Profiles are created or edited under Security > Browser > Secure Browser profiles. Assignment rules use identity-provider attributes to map users or groups to the right profile. Fortinet specifically calls out email as a required attribute for Secure Browser user assignment rules. A user can therefore authenticate successfully to an identity provider yet receive no intended Secure Browser policy if the required email attribute is absent or the mapping rule does not match.

Validate the identity claim, the user/group mapping rule, the selected profile and the extension’s current state. Do not assume that the policy package or firewall identity mapping is the same as Secure Browser profile assignment. This is its own assignment flow. If the browser extension is not installed or is disabled, the profile cannot enforce its browser-side controls even if the user exists in FortiSASE.

Inspection and policy layers

FortiSASE documents three distinct profile controls. Dynamic page inspection blocks malicious websites using the Secure Browser’s own detection engines and real-time inspection of active content for zero-hour phishing detection. It operates independently of FortiGuard category-based website rules. FortiGuard category-based website rules apply controls to groups of websites based on category lookups; Security Risk categories are blocked by default. URL domain group overrides apply site-specific behavior that overrides the category rule for selected domains. These layers should be tested independently because a site may be blocked by dynamic inspection even when its category is allowed, or a domain override may change a category-level action.

Profile actions include allowing or warning when sensitive data is entered into a website, and allowing, blocking all or blocking selected file extensions for downloads. A warning action should generate an event and inform the user; an allow action should not be mistaken for data-loss prevention. Domain group overrides can customize the behavior for individual websites. Define the narrowest override needed and document why it differs from the category policy.

Caveats that affect real users

Browser extension behavior depends on browser mode. Chrome Incognito and Edge InPrivate disable extensions by default, so the extension must be explicitly enabled in private browsing if that mode is permitted. Fortinet recommends disabling private browsing for most deployments. There are also documented limitations: the display watermark option is not applied when saving a local copy of a website, and the “pasting text copied from specified websites” override does not apply to websites including AI applications that provide code blocks with an inline copy button. These are specific product limitations, not evidence that the whole profile failed.

Verification and troubleshooting

When a browser action is not controlled, verify in this order: feature availability on the tenant; supported browser and extension installation; extension enabled state; user identity claims including email; assigned Secure Browser profile; dynamic inspection status; category rule; and URL domain group override. Then test a known malicious test URL or a controlled download/sensitive-input scenario that is safe for the environment. Do not use a production credential or real regulated data to test a warning/block action.

Network DPI logs alone do not prove browser-side inspection or action enforcement. Conversely, an extension event does not prove that every non-browser application is protected. Secure Browser complements agent and agentless traffic steering; it is not a replacement for those controls. Keep the evidence aligned to the enforcement point: extension state, profile assignment and browser event for browser-side controls; tunnel/PoP logs for network steering.

12 · Secure SD-WAN · FortiOS 8.0.0

Graceful BGP shutdown for planned SD-WAN edge maintenance

723 focused words · feature-led lesson

Primary Fortinet source

https://docs.fortinet.com/document/fortigate/8.0.0/administration-guide/86434/graceful-bgp-shutdown-new

Additional official references

  • Supporting Fortinet documentation
  • Supporting Fortinet documentation

Graceful shutdown is a route-drain signal, not graceful restart

FortiOS 8.0 adds BGP graceful shutdown support based on RFC 8326. It is designed for planned maintenance: an edge router tells its BGP peers that routes learned from it should be de-preferred so traffic can move to an alternate path before the session is closed. This is different from BGP graceful restart. Graceful restart asks peers to retain stale routes temporarily while a control-plane process restarts. Graceful shutdown deliberately makes the routes less attractive so traffic drains away from the node that will be maintained.

In a Secure SD-WAN design, BGP may distribute overlay or underlay reachability between edge FortiGates. A maintenance event on one edge should not abruptly withdraw every prefix if a peer can select an alternate overlay or underlay path. The GSHUT community is the signal that marks routes for de-preference. The receiving peer must recognize that community and apply the lower local preference. If a route policy strips the community or does not apply the receiver behavior, the peer may continue to select the path being drained.

Initiator and receiver roles

The initiator is the FortiGate that will be shut down. It sends the graceful-shutdown signal and applies the configured GSHUT community to its routes. The receiver is the peer that learns those routes and lowers local preference for routes associated with the graceful-shutdown community. FortiOS exposes neighbor settings for shutdown, graceful-shutdown-community, graceful-shutdown-local-preference and graceful-shutdown-delay. The setting is persistent across reboot according to the New Features documentation. Configure both sides intentionally; setting only the initiator’s community without a receiver policy does not guarantee traffic will move.

The graceful shutdown delay provides a time window for the peer to adjust and for traffic to drain before the session is closed. The delay must be sized against convergence time, application sensitivity and the number of routes. It is not a substitute for checking that an alternate route exists. If the peer has no alternate path, lowering local preference may leave it with only the de-preferred route and traffic may still fail when the session closes.

Configuration pattern

A simplified neighbor configuration includes:

config router bgp
    config neighbor
        edit "192.0.2.2"
            set shutdown graceful
            set graceful-shutdown-community "65535:0"
            set graceful-shutdown-local-preference 50
            set graceful-shutdown-delay 120
        next
    end
end

The community and local-preference values must be consistent with the design and the peer’s route policy. The example values are illustrative; use the values agreed by the BGP policy. Fortinet documents several shutdown modes, including graceful and graceful-soft. Review the exact release behavior before automating a maintenance workflow, and do not confuse the BGP neighbor shutdown command with an SD-WAN health-check action or an interface administrative shutdown.

Verify that traffic actually drained

Before completing maintenance, inspect the BGP neighbor state and the routes received from the initiator. Confirm the GSHUT community is present at the receiver and that the receiver has lowered local preference for those routes. Then inspect best-path selection and confirm the alternate overlay/underlay route is selected. Finally, observe traffic counters or application sessions to confirm that traffic has moved. A BGP session remaining Established does not prove traffic drained. A session going Idle does not prove the alternate path carried the workload successfully.

If the route remains preferred, inspect whether the community is being removed by an inbound route map, whether the peer policy matches the configured community, whether local preference is actually changed, and whether another path is eligible. If local preference changes but traffic does not move, inspect more-specific routes, policy routes, SD-WAN rules, session persistence and next-hop resolution. The BGP table and the data plane can disagree temporarily or because a different forwarding rule controls the flow.

Operational use in SD-WAN

Use graceful BGP shutdown as one step in a planned edge-maintenance runbook. First validate the alternate path and SD-WAN SLA state. Then trigger graceful shutdown on the intended BGP neighbor, verify community propagation and de-preference, wait for the configured delay and confirm traffic movement. Only then perform the maintenance action. After service is restored, remove the graceful-shutdown state and confirm normal route preference returns. Keep a rollback path available if the peer fails to select an alternate route.

The feature is useful only when the routing policy and SD-WAN design cooperate. If the alternate path is down, has a worse route policy or is not eligible for the destination, graceful shutdown cannot manufacture reachability. Treat it as a controlled signal to the BGP decision process, not a guarantee of hitless maintenance.
