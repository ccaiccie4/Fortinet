FortiGate

FGSP session synchronization and selective session pickup

Primary feature lesson source: FGSP · FortiOS 7.6.6
https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/668583/fgsp
Supports: FGSP architecture, session synchronization and pickup behavior.
Scenario support source: How to verify Sessions are SYNC in HA cluster through CLI
https://community.fortinet.com/fortigate-3/technical-tip-how-to-verify-sessions-are-sync-in-ha-cluster-through-cli-177197

Essence. FGSP synchronizes eligible session state between independently forwarding FortiGates. It is not FGCP ownership and it does not replace upstream load balancing or routing. Continuity requires upstream redirection plus compatible synchronized state on the surviving peer.

Mermaid teaching diagram — synthesized, not official Fortinet artwork
flowchart LR
LB[Load balancer] --> P1[FGSP peer 1]
LB --> P2[FGSP peer 2]
P1 <-->|eligible session state| P2
P1 --> A[Application]
P2 --> A
P1 -. failure .-> X[down]
LB -->|redirect| P2

What to notice: upstream steering and session synchronization are separate proof boundaries. Source: primary.

Architecture and dependencies. A flow is authorized, translated and inspected on the owning peer, creating local session state. FGSP exports eligible records across the synchronization link. TCP/SCTP pickup, connectionless pickup, helper/expectation state and NAT information are distinct state classes. Both peers still need compatible policy, routing, interfaces and NAT objects. Synchronizing every ephemeral flow can increase memory, CPU and sync-link load, so the design should match business continuity value.

Evidence. Verify the same representative flow on both peers and inspect the synchronization indicators described by Fortinet. What this proves: replication of that specific record. What it does not prove: upstream redirection or every protocol class. Next check: controlled failover while observing load-balancer redirection and survivor session lookup.

Scenario. Long-lived TCP database sessions survive a peer failure, but UDP telemetry and a helper-created child flow reset while upstream steering works correctly. Because steering is proven, compare enabled pickup classes and synchronized flags. If a translated flow reaches the survivor but the translated tuple changes, NAT-state synchronization and configuration symmetry become the narrower boundary.

Design/verification. Separate management intent from runtime state. After a change, prove owner state, peer copy, redirection, resulting forwarding and application continuity. Re-test after upgrades because session classes and diagnostics are release-sensitive.

FortiManager

Provisioning-template metadata variables, validation, and scope precedence

Primary feature lesson source: Validate metadata variables in provisioning templates
https://docs.fortinet.com/document/fortimanager/7.6.6/administration-guide/255972
Scenario support source: Install Preview Shows No Changes When Global and VDOM Provisioning Templates Are Both Assigned
https://community.fortinet.com/fortimanager-27/technical-tip-install-preview-shows-no-changes-when-global-and-vdom-provisioning-templates-are-both-assigned-vdom-enabled-fortigate-229494

Essence. Metadata variables turn one shared template into per-device intent. The important state chain is template syntax → target metadata resolution → scope/precedence → candidate CLI → preview/install → FortiGate runtime.

flowchart TD
T[Template] --> V[Resolve metadata]
V --> S{Scope precedence}
S --> C[Candidate CLI]
C --> P[Preview validation]
P --> I[Install]
I --> F[FortiGate runtime]

What to notice: FGFM transport is downstream of candidate generation. Primary source.

Architecture. FortiManager resolves metadata from device/group/default context, then renders candidate configuration. Global and VDOM provisioning scopes can both touch related settings; authoritative ownership determines which value survives compilation. A clean shared template does not prove every target has a usable value.

Evidence. If 99 targets validate and one reports an unresolved variable, the shared template parsed and the problem is target-specific. If a VDOM change produces no preview while a global template owns the same knob, scope precedence is the stronger hypothesis. Next check: inspect resolved metadata and rendered candidate before transport/install troubleshooting.

Scenario. One branch lacks loopback metadata and fails validation. Populate the missing target value instead of rewriting the shared template. Separately, a VDOM template edit produces an empty Install Preview because a global provisioning template already owns the setting. The lesson is compilation/ownership, not device connectivity.

Design. Make metadata naming deterministic, define defaults deliberately, document scope ownership and always use Install Preview as an explicit checkpoint. After installation, verify FortiGate runtime separately.

FortiAnalyzer

Report Guidance, Analytics dependencies, and No Data isolation

Primary feature lesson source: Report Guidance
https://docs.fortinet.com/document/fortianalyzer/7.6.7/administration-guide/385104/report-guidance
Scenario support source: FortiAnalyzer reports do not contain data of required time period
https://community.fortinet.com/fortianalyzer-6/troubleshooting-tip-fortianalyzer-reports-do-not-contain-data-of-required-time-period-190624

Essence. A report is a query/rendering pipeline over eligible Analytics data. Searchable logs alone do not prove a report has the required Analytics data, time range, device scope or fields.

flowchart LR
D[Device logs] --> I[Ingestion]
I --> A[Analytics]
A --> G[Report Guidance]
A --> Q[Dataset query]
Q --> F[Time device filters]
F --> R[Render]

Primary source.

Architecture. Ingestion, Analytics placement, dataset query, report filtering and rendering are distinct stages. Historical data retained only as Archive cannot necessarily satisfy a report that depends on Analytics. Rebuilding the report cannot manufacture historical Analytics data that was never retained.

Evidence. Report Guidance showing required data unavailable proves a report prerequisite is missing, not that the source device stopped logging. Compare Analytics versus Archive, ADOM/device scope, time range and dataset-required fields. If the dataset returns rows but output fails, move downstream to rendering.

Scenario. Last month's executive report is empty while current Log View searches work. The needed historical log family is Archive-only for that period. Changing report layout is premature. In a second case Analytics rows exist but a dataset filter excludes the target device; the failure is query scope.

Design. Align Analytics retention with reporting requirements, test dataset outputs before scheduled generation, and use Report Guidance to separate missing-data problems from rendering problems.

FortiSwitch

FortiLink split-interface topology and transition to MCLAG

Primary feature lesson source: FortiLink split interface
https://docs.fortinet.com/document/fortiswitch/7.6.1/fortilink-guide/801204
Scenario support source: Supported 802.3ad FortiLink topologies and split interface
https://community.fortinet.com/fortiswitch-36/technical-tip-supported-802-3ad-fortilink-topologies-and-split-interface-215416

Essence. A standby FortiLink member can be correct design state. Split-interface topology intentionally avoids forwarding on both legs when there is no supported multichassis relationship.

flowchart TD
FGT[FortiGate FortiLink] --> A[Active member]
FGT --> B[Standby member]
A --> S1[Switch 1]
B --> S2[Switch 2]
S1 -. ICL when MCLAG .- S2

Primary source.

Architecture. Carrier, LLDP adjacency, aggregate membership and forwarding role are separate proofs. In split mode, one path forwards and the redundant path waits to avoid loops. With a supported MCLAG/ICL pair, both switch chassis can present the multichassis aggregation semantics needed for active forwarding.

Evidence. Carrier and LLDP on both links prove physical adjacency, not that both should forward. Compare actual wiring, FortiLink role and MCLAG/ICL state to the documented topology before forcing a standby link active.

Scenario. A site repeatedly replaces optics because a FortiLink leg is standby even though it is a non-MCLAG split design and traffic is healthy. The state is expected. At a true MCLAG site, a standby member deserves ICL/peer consistency checks instead.

Design. Draw the intended topology, failure domains and loop-prevention behavior. Test member failure and peer failure separately.

FortiAP

DARRP channel scoring, measurements, weights, and change impact

Primary feature lesson source: Distributed Radio Resource Provisioning
https://docs.fortinet.com/document/fortiap/8.0.0/fortiwifi-and-fortiap-configuration-guide/299720
Scenario support source: DARRP channel assignment on FortiAP WiFi
https://community.fortinet.com/fortiap-5/troubleshooting-tip-darrp-channel-assignment-on-fortiap-wifi-181283

Essence. DARRP scores allowed channel candidates using RF evidence; it does not guarantee unique channels across neighboring APs. Channel reuse can be healthy when cells are sufficiently isolated.

flowchart LR
M[RF measurements] --> W[Weights]
W --> C[Allowed candidates]
C --> S[Score]
S --> B[Best channel]
B --> R[Radio change]

Primary source.

Architecture. Neighbor RSSI, noise, load and related RF observations feed scoring, but regulatory/radio-profile constraints define what can be chosen. Changing a channel can disrupt associated clients, so optimization timing is operationally significant.

Evidence. DARRP diagnostics prove the candidate/measurement context, not application quality. If a channel is never selected, first verify it is allowed. If two APs reuse a channel, inspect mutual RSSI, load, retries and noise before declaring co-channel interference.

Scenario. Two distant APs reuse a channel with weak mutual RSSI and low load; forcing uniqueness may add no value. Elsewhere, a clean channel is excluded by the radio profile; tuning weights cannot make an ineligible channel selectable.

Design. Validate allowed channels, RF measurements and client impact. Schedule disruptive channel changes deliberately.

FortiNAC

Proxy RADIUS: two AAA legs, EAP relay, and downstream enforcement

Primary feature lesson source: RADIUS
https://docs.fortinet.com/document/fortinac/9.4.0/administration-guide/214558/radius
Scenario support source: Technical Tip: RADIUS Proxy
https://community.fortinet.com/fortinac-28/technical-tip-radius-proxy-99601

Essence. Proxy mode creates NAS→FortiNAC and FortiNAC→upstream RADIUS relationships. Receipt of a request on one leg does not prove forwarding or authentication on the other.

sequenceDiagram
participant N as NAS
participant F as FortiNAC
participant R as Upstream RADIUS
N->>F: Access-Request
F->>R: Proxied request
R-->>F: Accept/Reject
F-->>N: Response

Primary source.

Architecture. FortiNAC identifies the NAS/client and applicable policy, relays configured EAP/accounting upstream, then can combine the AAA result with NAC registration and network-access treatment. Shared secrets and routing/firewall requirements are independent per leg.

Evidence. Capture both legs. NAS traffic arriving at FortiNAC proves the first transport only. Upstream Access-Accept proves authentication result generation, not VLAN enforcement. If upstream sees nothing, inspect proxy selection and the FortiNAC→RADIUS relationship.

Scenario. The switch sends requests and FortiNAC logs them, but NPS sees nothing. User credentials are premature; debug the second leg. In another case NPS returns Accept while the endpoint stays restricted, so move to NAC authorization/logical access and switch enforcement.

Design. Document both RADIUS client relationships and keep authentication proof separate from access-enforcement proof.

FortiNAC-F

Local RADIUS virtual server, EAP termination, and RadSec

Primary feature lesson source: Configure Local RADIUS Server settings
https://docs.fortinet.com/document/fortinac-f/7.6.0/administration-guide/366458/configure-local-radius-server-settings
Scenario support source: Device model configuration changes after disabling legacy mode
https://community.fortinet.com/fortinac-f-57/technical-tip-new-device-model-configuration-changes-introduced-after-disabling-legacy-mode-229564

Essence. Local RADIUS terminates supported EAP on FortiNAC-F. Local virtual-service state, EAP server certificate/trust, NAS client definition, identity source and authorization are direct prerequisites. RadSec adds an outer TLS layer around RADIUS and is distinct from EAP-TLS.

flowchart LR
N[NAS] --> L[Local RADIUS]
L --> E[EAP certificate trust]
E --> I[Identity]
I --> A[Authorization]
A --> M[Logical network/device model]
M --> N

Primary source.

Evidence. Packets reaching the listener prove transport, not service/certificate health. A successful RadSec handshake proves outer TLS only. Access-Accept proves the RADIUS decision, not switch enforcement.

Scenario. After migration from legacy device modeling, EAP-TLS succeeds and Access-Accept is returned, but the wrong VLAN is applied. Keep certificate analysis closed and troubleshoot logical-network/device-model enforcement. If the local RADIUS service is stopped, repair that earlier boundary first.

Design. Monitor service state, certificate lifetime and trust chain separately from network-access mapping.

FortiAuthenticator

EAP-TLS and RadSec certificate roles, trust chains, and fragmentation

Primary feature lesson source: RADIUS service — General
https://docs.fortinet.com/document/fortiauthenticator/8.0.1/administration-guide/656833/general
Scenario support source: EAP-TLS authentication fails with EAP method type 13
https://community.fortinet.com/fortiauthenticator-8/technical-tip-eap-tls-authentication-fails-with-error-authentication-failed-for-eap-method-type-13-229496

Essence. EAP-TLS authenticates an endpoint inside RADIUS; RadSec protects RADIUS transport. Treat them as different TLS layers.

sequenceDiagram
participant C as Client
participant N as NAS
participant F as FAC
C->>N: EAP-TLS
N->>F: RADIUS/EAP
F-->>C: server certificate via NAS
C->>F: client certificate via NAS
F->>F: validate chain
F-->>N: Accept/Reject

Primary source.

Architecture. FAC presents the configured EAP server certificate and validates the client chain. Large chains can require fragmentation. RadSec creates a separate outer TLS connection with independent certificates and trust.

Evidence. Method type 13 identifies EAP-TLS but not the cause. A successful RadSec TLS connection proves outer transport only. Use FAC debug and packet capture to distinguish missing intermediate CA, identity/EKU, clock, revocation, server certificate and fragmentation/MTU.

Scenario. After CA renewal, password methods work but EAP-TLS fails because an intermediate CA is missing. In another site only larger chains fail across a constrained path, making fragmentation/MTU a competing hypothesis.

Design. Track chain completeness, certificate lifetimes, EKUs and path MTU; test certificate rollover before mass deployment.

FortiPAM

Live session recording, streaming pipeline, and monitoring latency

Primary feature lesson source: Over-the-shoulder monitoring (live recording)
https://docs.fortinet.com/document/fortipam/1.9.0/administration-guide/170626/over-the-shoulder-monitoring-live-recording
Scenario support source: Active session video monitoring not showing in real time
https://community.fortinet.com/fortipam-52/technical-tip-active-session-video-monitoring-not-showing-in-real-time-228817

Essence. Live monitoring is a capture/stream/process/playback pipeline, not zero-latency screen mirroring. Final replay additionally requires recording finalization after session termination.

flowchart LR
S[Privileged session] --> C[Capture]
C --> U[Upload/stream]
U --> P[FortiPAM processing]
P --> V[Live monitor]
P --> F[Finalize]
F --> R[Replay]

Primary source.

Evidence. A smoothly updating live view with small documented delay can be healthy. Growing delay points to capture/upload/processing backlog. Live viewing proves streaming, not final recording completion.

Scenario. A nine-second delay is treated as failure even though playback remains continuous; compare expected latency first. In another incident live monitoring works but abrupt termination leaves no replay, localizing the issue to finalization rather than approval.

Design. Test both live view and post-session replay, and confirm per-secret/session recording prerequisites.

FortiSIEM

Device discovery, CMDB creation, credential association, and monitor scheduling

Primary feature lesson source: Discovering Devices
https://docs.fortinet.com/document/fortisiem/7.4.2/user-guide/157952/discovering-devices
Scenario support source: SNMP monitoring not scheduled despite successful discovery
https://community.fortinet.com/fortisiem-34/troubleshooting-tip-fortisiem-snmp-monitoring-not-scheduled-despite-successful-discovery-227511

Essence. Discovery proves identification in one context; continuous monitoring is a later scheduler/worker state machine.

flowchart LR
D[Discovery] --> C[Credential test]
C --> M[CMDB]
M --> S[Scheduler]
S --> W[Collector/worker]
W --> P[Polling]
P --> O[Metrics]

Primary source.

Architecture. Discovery creates/classifies a CMDB object. Monitoring then depends on monitor association, scheduler assignment, effective credentials and reachability from the actual execution node. Interactive Test Connectivity is not identical to scheduled job execution.

Evidence. Successful discovery proves the discovery path. Not Scheduled with credential evidence points to CMDB/credential/scheduler association. Once scheduled, test from the assigned Collector/worker.

Scenario. A router is discovered and SNMP test succeeds, but performance monitors remain Not Scheduled because the scheduler has no effective credential associated with the CMDB object. Repeated rediscovery is not the discriminating action.

Design. Track discovery ownership, effective credential, assigned worker and scheduled monitor as separate health indicators.

FortiSASE

Dynamic private-access policies driven by endpoint ZTNA posture tags

Primary feature lesson source: ZTNA posture tags in private access policies
https://docs.fortinet.com/document/fortisase/latest/mature-administration-guide/825799
Scenario support source: FortiSASE ZTNA agent based / agent-less issue
https://community.fortinet.com/support-forum-92/fortisase-ztna-agnet-based-agent-less-issue-222561

Essence. Endpoint telemetry creates dynamic posture tags that become policy match criteria. Authentication/tunnel connectivity does not prove a posture tag exists.

flowchart LR
E[Endpoint telemetry] --> Z[Posture evaluation]
Z --> T[Dynamic tag]
T --> P[Private-access policy]
P --> H[SPA hub]
H --> F[FortiGate]
F --> A[Private app]

Primary source.

Architecture. Managed endpoint telemetry is evaluated into tags; top-down private-access policy uses identity, destination and posture. After policy allow, SPA routing/FortiGate/application state is downstream. Agentless workflows may not supply the same telemetry as agent-based endpoints.

Evidence. Connected without expected tag proves on-ramp/authentication only. Correct tag plus correct policy ID moves troubleshooting downstream. Broad rules can shadow posture-specific policy.

Scenario. A managed laptop loses its compliant tag after a posture-definition change and falls to a broader rule. Repair posture evaluation first. In another case the tag is correct but an allow-all rule above a posture deny wins; policy order is the boundary.

Design. Separate agent-based and agentless evidence assumptions and keep posture-specific rules above broad fallbacks.

Fortinet Secure SD-WAN

BGP route tags as dynamic SD-WAN destinations and route-policy coupling

Primary feature lesson source: Using BGP tags with SD-WAN rules
https://docs.fortinet.com/document/fortigate/7.6.3/administration-guide/672387/using-bgp-tags-with-sd-wan-rules
Scenario support source: Using route-map-out preferable in BGP for route-tag use in an SD-WAN rule
https://community.fortinet.com/fortigate-3/troubleshooting-tip-using-route-map-out-preferable-in-bgp-for-route-tag-use-in-an-sd-wan-rule-178513

Essence. Route tags bridge routing policy and SD-WAN service policy. BGP Established does not prove the expected tagged best path exists in the RIB.

flowchart LR
B[BGP candidates] --> R[Route-map]
R --> T[Route tag]
T --> P[Best path in RIB]
P --> D[Dynamic destination]
D --> S[SD-WAN service]
S --> M[Member/SLA steering]

Primary source.

Architecture. BGP attributes/communities feed route policy. The selected/installed path carries the FortiOS tag, which populates a dynamic destination consumed by an SD-WAN service. Route-policy, RIB installation and service selection remain distinct stages.

Evidence. If tag 40's dynamic destination is empty, inspect the installed route and actual tag before touching SLA thresholds. A received route with the desired community proves advertisement, not best-path installation.

Scenario. BGP is Established and the desired route arrives with the right community, but an untagged route wins best path; the SD-WAN destination remains empty. Fix route-policy/best-path outcome rather than service-rule thresholds.

Design. Document community→route-map→tag→dynamic destination→service intent, and verify each step after routing changes or upgrades.
