FortiGate

1. Fortinet Support Tool capture lifecycle: scoped keys, daemon selection, and a time-bounded evidence bundle

Primary feature/admin documentation: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/775343/fortinet-support-tool-for-capturing-incidents
Additional primary documentation: https://community.fortinet.com/fortigate-3/technical-tip-fortinet-support-tool-google-chrome-extension-for-troubleshooting-gui-issues-102586

Scenario source: Materially updated 2026-10-29; the Community note says a fresh browser login may be required after installing the extension. This is scenario evidence, not the feature specification.
Scenario source; primary lesson mechanics remain grounded in Fortinet documentation.

Purpose and trust boundary

The Fortinet Support Tool is designed to capture troubleshooting evidence while an intermittent incident is happening, rather than relying on an engineer to enable several debug streams after the failure has already passed. FortiOS generates a REST API key on the appliance. The key is bound to a connection target and expiry; the operator can specify IP/FQDN, protocol, port, and optional trusted hosts. The desktop application uses that key to connect and request a selected capture scenario. Treat the key as temporary privileged access: share it only with the intended investigator and let it expire promptly after the capture window.

Capture transaction

Generate the key in the FortiGate GUI, copy it into the Support Tool, select the scenario, choose the daemon logs and filters, set a filename and capture duration, then start collection. The application can remain in the background for up to 48 hours, improving the chance of catching a low-frequency event. This is a bounded capture session, not an indefinite debug daemon. The resulting files can include configuration/device information, daemon logs, REST API responses, crash or profiling information, and resource charts depending on the capture type and selected scenario. Fortinet distinguishes .fgtcapture/.ftntguicap from .ftntcap review paths.

GUI capture is a separate evidence source

The FortiGate Support Tool feature and the Chrome extension are related but not identical. The administration guide says user-interface capture requires the browser extension. The extension can record the screen and correlate the visible symptom with browser network logs, JavaScript console output, FortiGate daemon logs, and resource usage. The Community note updated on October 29 adds a practical detail: after installing the extension, log out of FortiGate and log back in. A missing video pane therefore does not prove the appliance-side capture failed; it may mean the browser capture path was never initialized.

Permissions, filters, and evidence quality

The account used to generate the key must have the required System-category read/write access for the relevant capture operations. If the key is accepted but the expected daemon is absent, inspect the selected daemon list and the release-specific availability of that daemon before widening collection. Capturing every daemon indiscriminately increases volume and makes temporal correlation harder. Prefer a narrow reproduction window, timestamps enabled, and a scenario that maps to the observed failure: HTTPSD for GUI request handling, CMDB for configuration operations, or another daemon identified by the symptom. Avoid treating a successful key handshake as proof that the needed log stream was selected.

Verification and troubleshooting

First confirm that the target IP/FQDN, protocol, and port in the key match the management path actually reachable from the workstation. If connection setup fails, test routing and TLS trust before changing daemon filters. If the capture starts but contains no incident, compare the capture timestamps with the reproduced event and confirm the chosen duration covered it. If the GUI symptom is missing, confirm the extension is installed, the browser session was refreshed, and the capture was started from the relevant screen. Playback provides synchronized views, so line up the time of the visible freeze with daemon output and CPU/memory charts rather than reading each log in isolation.

Operational limits

The tool helps gather evidence; it does not diagnose every root cause automatically or guarantee that every subsystem exposes identical telemetry on every FortiOS release. Key expiry, trusted-host restrictions, account permissions, browser permissions, and capture length are independent gates. Keep the generated bundle access-controlled because configuration and diagnostic logs may contain sensitive operational information. Before sending it to support, confirm the file covers the failure, includes relevant timestamps, and does not contain unrelated user data. The useful result is a reproducible, time-correlated evidence package—not simply a capture file that exists.

Mechanism and troubleshooting fingerprints

Feature: support-tool-rest-api-key-expiry-trusted-hosts-daemon-selection-capture-window

Workflow: FortiGate issues expiring REST API key → desktop Support Tool connects to chosen endpoint → scenario and daemons selected → bounded capture runs → .fgtcapture/.ftntcap evidence reviewed

Failure class: Intermittent GUI or daemon fault occurs outside a manual debug window; expired key, insufficient admin scope, or missing browser extension yields incomplete evidence

Evidence: Key expiry/trusted hosts, selected daemon list, capture timestamps, resource charts, REST API responses, .fgtcapture/.ftntcap playback; GUI video requires the browser extension

Remediation path: Verify target and key validity; limit trusted hosts; ensure System read/write permission; select the relevant daemons and time window; reproduce once and correlate resource charts with logs

2. SD-WAN overlay templates: generated IPsec/BGP provisioning versus SD-WAN path intelligence

Primary feature/admin documentation: https://docs.fortinet.com/document/fortimanager/7.6.6/administration-guide/233668/sd-wan-templates
Additional primary documentation: https://docs.fortinet.com/document/fortimanager/7.4.8/administration-guide/224982/sd-wan-overlay-templates

Scenario source: No directly matched recent Community case was independently verified. No directly matched Community scenario in the rolling 30-day window was verified; the lesson is driven by FortiManager feature documentation.

Two different jobs in central management

FortiManager's SD-WAN overlay template wizard reduces repetitive construction of a hub-and-spoke or regional overlay. The wizard uses topology and underlay inputs to generate provisioning templates for IPsec tunnels, BGP, and supporting CLI. Those generated objects are a deployment mechanism: they establish the overlay and the routing relationships. They are not, by themselves, the SD-WAN intelligence layer that measures link quality and chooses traffic paths. The Administration Guide explicitly treats SD-WAN templates as a separate central-management feature.

Generated objects and dependency order

Start at Device Manager → Provisioning Templates → SD-WAN Overlay Templates, create the topology, select hub and branch roles, and supply the transport/region details required by the wizard. FortiManager generates the relevant provisioning templates and assigns them to the devices identified by the topology. Dependencies matter: interface configuration must exist before IPsec interfaces can use it, and IPsec connectivity must exist before BGP peering and the overlay routes can converge. FortiManager's SD-WAN template guidance documents the order as interface template, IPsec template, then SD-WAN template. An install task that skips or mis-targets a dependency can leave a partial deployment even though the wizard itself completed.

Underlay and routing assumptions

The overlay wizard assumes hub-to-branch underlay reachability already exists, using static routes, a dynamic routing protocol, or another supported mechanism. If the underlay cannot reach the peer, the generated IPsec objects cannot establish the tunnel. Once IPsec is up, BGP must form and advertise the expected prefixes; a green tunnel icon does not prove the route is present or preferred. Inspect the generated BGP neighbor parameters, AS numbers, update sources, and advertised prefixes against the intended topology rather than manually editing each branch after deployment.

Overlay does not mean steering

After tunnels and routes are installed, create or assign the SD-WAN template that defines members, Performance SLA health checks, and SD-WAN rules. The SD-WAN template becomes effective only after installation. If an administrator changes SD-WAN settings locally on a FortiGate, FortiManager can show the template as out of sync; repeating the install from the old template may overwrite the local change. The correct repair is to reconcile the intended state in FortiManager, update the template, and install again—not to keep editing the device locally.

Evidence boundaries

Use the installation preview and task result to prove what FortiManager attempted to deploy. Use IPsec SA state to prove tunnel negotiation, BGP summary and routing table to prove control-plane adjacency and route presence, and SD-WAN Monitor to prove measured health/member state. These are different layers. If the tunnel is up but the application uses an unexpected path, investigate the SD-WAN rule, its order, SLA mode, and session state rather than regenerating the overlay. If the tunnel is down, verify underlay reachability and the generated phase-1/phase-2 settings first.

Scale and change control

Central templates reduce configuration drift, but a topology-wide change can affect many devices at once. Review target groups, template order, and install preview before deployment. A template can be regenerated after topology changes, so compare the generated diff instead of assuming the wizard preserves every manual customization. For a staged rollout, install to a small branch group, verify tunnel/BGP/SD-WAN layers, then expand. The operational success criterion is not “templates generated”; it is the intended overlay and path policy installed and independently verified.

Mechanism and troubleshooting fingerprints

Feature: fmg-overlay-wizard-generated-ipsec-bgp-cli-template-dependency-order

Workflow: Choose hub/branch topology and underlays → wizard generates IPsec/BGP/CLI templates → assign roles/device groups → install interface then IPsec then SD-WAN settings → validate routing and path policy separately

Failure class: Tunnel or route is missing because template dependencies, underlay reachability, target assignment, or install order is wrong; generated overlay is mistaken for SD-WAN intelligence

Evidence: Generated template list/assignments, install preview and task, IPsec SA state, BGP neighbor/routes, SD-WAN Monitor health and rule match

Remediation path: Confirm underlay reachability; inspect generated templates and targets; install in dependency order; install a separate SD-WAN template and verify its rule/SLA behavior

FortiAnalyzer

3. OFTP log encryption negotiation: compatible algorithm levels, TLS, and server identity

Primary feature/admin documentation: https://docs.fortinet.com/document/fortianalyzer/7.6.6/administration-guide/381919/logs
Additional primary documentation: https://community.fortinet.com/fortigate-3/technical-tip-fortigate-and-fortianalyzer-not-connected-182351

Scenario source: No directly matched recent Community case was independently verified. Older contextual troubleshooting example from 2024 describes FortiGate/FortiAnalyzer connection failures around TLS and encryption settings; it is not a recent 30-day case.

What is being negotiated

FortiGate sends Fortinet-device logs to FortiAnalyzer using the Fortinet proprietary OFTP protocol. The transport is not merely a UDP syslog destination: the devices establish a protected session, validate the peer identity according to the configured trust/authorization settings, negotiate supported cryptographic parameters, and then transfer log records. Fortinet's Administration Guide states that FortiAnalyzer's encryption level must be equal to or lower than the sending device's level. This is a compatibility relationship between two endpoints, not a setting that can be diagnosed from the FortiGate alone.

Configuration objects and algorithm levels

On FortiAnalyzer, the global encryption algorithm is configured under config system global with the supported set enc-algorithm values for that release. On FortiGate, the remote logging object is under config log fortianalyzer setting and exposes its own algorithm choices, commonly high-medium, high, or low depending on version. Do not copy a command from an older KB without checking the current CLI reference: legacy options such as disabling encryption may no longer exist. Prefer a mutually supported strong setting, and confirm the exact syntax for both software versions before changing production logging.

Separate the failure boundaries

A ping to the FortiAnalyzer address proves only IP reachability. A TCP handshake proves a transport connection to the selected port, not a successful TLS handshake or accepted OFTP identity. A TLS alert or certificate/serial mismatch points to a different layer than a dropped route or MTU black hole. After TLS succeeds, the device still needs to be authorized and the logging configuration must point to the intended FortiAnalyzer. Repeated “connection up” events can also occur when two configured FortiAnalyzer destinations share an IP but present different serial identities; that is not solved by lowering the cipher level.

Useful evidence

Inspect show output for the FortiGate FortiAnalyzer setting and the FortiAnalyzer global encryption setting. Check the configured server, source IP/interface selection, minimum TLS protocol, certificate verification, and serial identity. Capture traffic on both ends for the relevant destination and port; seeing outbound packets at the sender but nothing at the receiver suggests routing or an intermediate filter, while a completed TCP handshake followed by TLS alerts points toward protocol or trust compatibility. FortiGate fgtlogd/miglogd diagnostics and FortiAnalyzer connection logs help distinguish negotiation failure from authorization or post-connect ingest problems.

Repair without weakening the channel unnecessarily

First verify software compatibility and the current supported TLS versions. Then align encryption levels so the receiver accepts the sender's configured strength. Check certificate verification and the expected FortiAnalyzer serial number. If traffic crosses a tunnel or constrained WAN, validate MTU and fragmentation as a separate test; do not assume every connection failure is cryptographic. Finally, verify that the FortiAnalyzer device is authorized and that new log timestamps arrive. A “connected” state does not prove Analytics indexing is complete, and a missing Analytics record may be a later ingestion/indexing issue.

Operational caveat

Encryption policy changes can affect every managed sender, so stage changes on one device and retain a secure rollback plan. Avoid downgrading to weak settings simply to make a handshake pass. Record the actual client and server algorithm/TLS settings and the packet/log evidence before escalating. The important diagnostic distinction is whether the fault occurs at network reachability, TCP/TLS negotiation, identity/authorization, or log ingestion; each boundary has a different corrective action.

Mechanism and troubleshooting fingerprints

Feature: faz-oftp-enc-algorithm-compatibility-tls-minimum-server-serial-identity

Workflow: FortiGate OFTP client connects → network/TLS negotiation → receiver/sender encryption capabilities and identity checked → OFTP authorized → log stream ingested

Failure class: FortiGate cannot establish secure logging because encryption level, TLS minimum, server identity, or network path differs

Evidence: FortiGate config log fortianalyzer setting; FAZ enc-algorithm/TLS settings; sniffers at both ends; fgtlogd/miglogd logs; authorized device serial/certificate

Remediation path: Compare both sides' algorithm and TLS settings; verify serial/certificate identity and MTU; align compatible settings without unnecessary security downgrade

FortiSwitch

4. BGP EVPN multihoming: ESI identity, designated-forwarder preference, and MAC holdtime

Primary feature/admin documentation: https://docs.fortinet.com/document/fortiswitch/8.0.0/fortiswitchos-administration-guide/44849/vxlan-interfaces

Scenario source: No directly matched recent Community case was independently verified. No directly matched recent FortiSwitch Community scenario was verified; the feature mechanics come from the FortiSwitchOS Administration Guide and release-specific documentation.

Purpose and scope

FortiSwitchOS 7.6.2 introduced BGP EVPN multihoming support for a customer-edge device connected to multiple provider-edge/leaf switches. The goal is link or switch redundancy without forcing the server to rely on a single physical attachment. The documented mode is active-active. EVPN advertises Ethernet-segment reachability so the fabric can learn that multiple leafs attach to the same logical segment. This is different from a traditional STP loop-prevention design: the EVPN control plane and Ethernet Segment Identifier (ESI) define the multihoming relationship.

ESI and trunk configuration

The Ethernet segment needs a unique ESI across the network. FortiSwitch combines the configured Ethernet-segment system MAC and segment ID into the 10-byte ESI value. Configure the ESI-related values on the switch trunk that represents the server-facing link; the segment identity must be consistent on participating switches. A conceptual configuration includes config switch trunk, then set evpn-mh-es-sys-mac, set evpn-mh-es-id, and the member interfaces. The exact supported trunk/LACP design and BGP feature licensing must be checked for the target model and release. EVPN/VXLAN operation also depends on the required BGP routing capability and the overlay being correctly established.

Designated forwarder and flooded traffic

Multihoming is active-active for supported traffic, but flooded traffic from the VXLAN overlay to the local Ethernet segment needs a designated-forwarder decision. FortiSwitch exposes a DF preference value from 1 to 65,535; the higher value wins. This preference is not a general “primary switch” setting for every unicast packet. It specifically influences which EVPN VTEP forwards flooded traffic toward the local segment. If DF preference is misunderstood, engineers may interpret asymmetric flooding as a failed active-active link even when unicast reachability is healthy.

MAC synchronization and holdtime

When an EVPN type-2 route is withdrawn, a switch may retain synchronized MAC entries for a configured holdtime to smooth convergence. FortiSwitchOS documents a default evpn-mh-mac-holdtime of 360 seconds and a configurable range of 0–86,400 seconds. A longer hold can reduce transient churn in some designs but can also preserve stale state longer; a shorter value is not automatically better. Tune it only after measuring how route withdrawal, link failure, and MAC relearning behave in the actual fabric.

Verification and failure isolation

Check the switch trunk and member links first, then verify BGP EVPN adjacency and routes, and inspect the Ethernet Segment/ESI representation on both leafs. The documented duplicate-address command family includes get router info evpn mac vni dup-addr to view duplicate MAC addresses and corresponding clear commands when remediation is justified. A duplicate MAC report is evidence of competing advertisements or movement; it does not by itself identify which physical link is wrong. Compare ESI, server NIC teaming/LACP behavior, VLAN/VNI mapping, and the timing of the route change before clearing state.

Operational design notes

Test one dual-homed server and one controlled failure before expanding. Validate both link failure and complete leaf failure, including flooded traffic, unicast sessions, ARP/ND behavior, and MAC relearning. The feature can preserve service when one PE or one CE link fails, but only if both switches agree on the Ethernet Segment identity and the EVPN/VXLAN control plane is healthy. Do not infer redundancy from two cables alone; the ESI, routing, DF behavior, and endpoint teaming model must agree.

Mechanism and troubleshooting fingerprints

Feature: fsw-bgp-evpn-multihoming-esi-df-preference-mac-holdtime-active-active

Workflow: CE server dual-homes to two FortiSwitch leafs → shared ESI identifies Ethernet Segment → EVPN advertises MAC/IP reachability → DF preference selects flooded-traffic forwarder → synchronized MAC entries age/hold on route withdrawal

Failure class: Dual-homed endpoint experiences blackholing, duplicate flooding, or inconsistent reachability due to ESI mismatch, wrong DF preference, or stale MAC synchronization

Evidence: Trunk ESI fields, BGP EVPN routes, duplicate MAC output, VTEP state, port/trunk status, configured MAC holdtime

Remediation path: Align the Ethernet Segment identity across participating leafs, validate trunk membership and EVPN routes, check duplicate MACs and DF preference, and tune holdtime only for a measured convergence issue

FortiAP/Wireless

5. RadSec for WPA2/WPA3-Enterprise: RADIUS-over-TLS transport and certificate trust

Primary feature/admin documentation: https://docs.fortinet.com/document/fortigate/7.6.0/new-features/300051/support-radsec-on-wpa2-wpa3-enterprise-ssid
Additional primary documentation: https://docs.fortinet.com/document/fortiap/8.0.0/fortiwifi-and-fortiap-configuration-guide/829255

Scenario source: No directly matched recent Community case was independently verified. No directly matched recent FortiAP RadSec troubleshooting case was verified; the lesson is based on the documented feature and current wireless configuration guide.

Why RadSec changes the transport

WPA2/WPA3-Enterprise still uses 802.1X/EAP for the wireless client authentication flow, but the RADIUS leg between the controller and RADIUS server can be carried over TCP with TLS using RadSec. FortiOS 7.6.0 added RadSec support for WPA2/WPA3-Enterprise SSIDs. The change protects the RADIUS transport with TLS and changes the transport behavior; it does not replace the EAP method or guarantee that the RADIUS server authorizes the user. Keep the wireless association, EAP exchange, TLS connection, RADIUS Access-Accept/Reject, and network authorization as separate stages in troubleshooting.

RADIUS client configuration

Fortinet's feature guide shows a RADIUS server object under config user radius with a server address, shared secret, NAS identity, and set transport-protocol tcp. The example also includes a custom NAS-ID and enables RADIUS CoA. Use the exact CLI options supported by the target FortiOS release. On the RADIUS server, the FortiGate/controller's source identity must match the configured client entry. If the server expects a different NAS-IP or NAS-ID, the TLS session may succeed while the request is still rejected by the server's client policy.

Certificate and TLS boundary

RadSec adds a certificate trust dependency. The client must establish a TLS session to the intended RADIUS server and validate the certificate according to the configured trust policy. A certificate-chain or name mismatch is not an RF issue and should not be repaired by changing channel, roaming, or SSID power settings. Verify the server certificate, its issuer, validity period, expected name, and the trust material configured on the FortiGate. Also verify the server listens on the expected TCP port and that intermediate firewalls permit the connection. A shared RADIUS secret is not a substitute for TLS certificate validation.

Observe each transaction separately

First confirm the station associates to the correct SSID and begins EAP. Next inspect the controller's RADIUS server object and the server-side TLS/RADIUS logs. A successful TCP handshake proves only reachability; a completed TLS handshake proves a protected channel was established, not that the user passed EAP. An Access-Accept proves the server accepted the authentication request, but the client may still fail to obtain the intended VLAN, DHCP address, or firewall access. Verify dynamic VLAN attributes and policy enforcement after authentication.

Failure scenario

A user reports that the Wi-Fi password is correct and the client associates, but the connection ends during authentication. If the RADIUS server shows no request, inspect routing, TCP listener, and TLS handshake. If the server logs a TLS certificate error, fix trust/name/expiry before investigating user credentials. If an Access-Reject appears, inspect the EAP method, identity format, RADIUS client definition, and directory policy. If Access-Accept appears but the endpoint lands in the wrong VLAN, inspect reply attributes and the SSID/controller mapping. Do not collapse all of these symptoms into “RADIUS is down.”

Deployment caveats

Test the exact FortiGate/FortiAP software combination and the RADIUS server's RadSec support before changing a production enterprise SSID. Maintain a rollback path to the previous RADIUS transport until certificate and policy behavior is proven. Monitor both authentication success and the assigned network outcome. The security benefit is encrypted, authenticated RADIUS transport; correct authorization still depends on EAP policy, NAS identity, reply attributes, and downstream VLAN/DHCP/firewall configuration.

Mechanism and troubleshooting fingerprints

Feature: fap-wpa-enterprise-radsec-tcp-tls-server-trust-nas-identity

Workflow: Client associates to enterprise SSID → EAP/RADIUS transaction reaches FortiGate controller → RADIUS client opens TCP/TLS to server → certificate trust and NAS identity validate → Access-Accept/Reject determines authorization

Failure class: RF association succeeds but 802.1X authentication fails because TLS transport, certificate trust/name, NAS identity, or server client definition is incorrect

Evidence: RADIUS transport-protocol setting, TLS handshake/certificate chain, server-side RADIUS client logs, Access-Accept/Reject, assigned VLAN and DHCP lease

Remediation path: Confirm compatible release/SSID mode; configure TCP/TLS transport and certificate trust; align NAS-IP/NAS-ID with server policy; test EAP, RADIUS authorization, and VLAN delivery separately

FortiNAC

6. IPv6 endpoint access versus IPv4-only infrastructure discovery: the FortiNAC capability boundary

Primary feature/admin documentation: https://docs.fortinet.com/document/fortinac/9.4.0/administration-guide/168784/ipv6-support

Scenario source: No directly matched recent Community case was independently verified. No directly matched recent IPv6-specific Community scenario was verified.

Two separate IPv6 capabilities

FortiNAC 9.4 documents IPv6 support for endstations and devices communicating with the portal and agents, as well as IPv6 access to the administrator UI. The important boundary is that network-device management and discovery in Inventory still requires the network equipment to have an IPv4 management address. A deployment can therefore have working IPv6 client-to-portal communication while switch discovery, polling, or topology maintenance fails because the switch is reachable only over IPv6. Do not treat “IPv6 supported” as a blanket statement that every discovery protocol and device-management operation is dual-stack.

Interfaces and records

The guide states that both eth0 and eth1 support IPv4 and IPv6. Eth0 is used for administrative access, while eth1 provides portal communication; agents can also communicate over IPv6. When a host or device uses IPv6, the address is displayed in Host View or Adapter View in addition to any IPv4 addresses associated with that record. This is useful for endpoint identity analysis, but it does not mean the appliance has discovered all infrastructure relationships or can poll every IPv6-only switch. Keep the address family and the object type visible when reviewing evidence.

L3 polling has a separate support matrix

FortiNAC's IPv6 guide describes L3 polling for IP-to-MAC data from a specific set of vendors/switches, including Cisco, Juniper EX, HP ProCurve, Brocade, and FortiGate. It explicitly directs administrators to Fortinet Support for additional device support. This is a supported integration boundary, not a generic promise that every SNMP device returns IPv6 neighbor information. If an IPv6 address appears on a host but no IP-to-MAC association appears, verify the switch vendor/model and the configured polling method before assuming the endpoint is invisible.

Diagnostic sequence

Start with the endpoint's ability to reach the portal or agent over IPv6. Confirm that the relevant FortiNAC interface has IPv6 configured and that routing, firewall rules, DNS, and the endpoint's IPv6 address are valid. Then inspect Host View/Adapter View to see which addresses FortiNAC associates with the endpoint. Separately inspect Inventory for the network device's management address and polling status. If the switch has only an IPv6 management address, the documented discovery limitation may explain the missing device data even while endstation communication succeeds.

Operational consequence for policy

Access policy decisions may depend on the host record, adapter identity, and network location data. If IPv6 address information is visible but infrastructure discovery is incomplete, the operator should not infer that all access-control inputs are current. Validate the actual registration, host/adapter mapping, switch/port association, and any required L3 polling data before changing policy rules. Where supported, retain IPv4 management reachability for network devices while enabling IPv6 for endpoint and portal traffic. This gives FortiNAC the documented management path and allows dual-stack endpoint communication.

Version and scope cautions

Use the guide for the deployed FortiNAC release and verify supported vendor integrations. IPv6 visibility, admin access, portal access, agent access, inventory discovery, and L3 polling are distinct functions. A successful IPv6 ping tests only reachability; it does not prove portal registration, agent communication, device discovery, or policy assignment. Report which function fails and collect evidence from that layer instead of applying a broad “IPv6 is broken” diagnosis.

Mechanism and troubleshooting fingerprints

Feature: fnac-ipv6-portal-agent-admin-ui-supported-versus-inventory-device-discovery-ipv4-required

Workflow: IPv6 host reaches portal/agent or admin UI → host/adapter record shows IPv6 address → separate network-device inventory discovery requires IPv4 management address → L3 IP-to-MAC visibility depends on supported vendor

Failure class: IPv6 endpoint can reach FortiNAC but infrastructure discovery or policy context is incomplete because endpoint IPv6 support is mistaken for IPv6 network-device management

Evidence: Host View/Adapter View addresses, portal/agent reachability, eth0 admin access, inventory device management address, supported L3 polling vendor list

Remediation path: Separate endpoint communication from infrastructure discovery; preserve IPv4 management on supported network devices; verify polling support and reconcile the host's IPv4/IPv6 identity

FortiNAC-F

7. Directory-sync machine-auth RBAC: host/user group projections and the AD primary-group trap

Primary feature/admin documentation: https://docs.fortinet.com/document/fortinac-f/7.6.0/administration-guide/359095/schedule-synchronization
Additional primary documentation: https://docs.fortinet.com/document/fortinac-f/7.6.0/administration-guide/81184/groups

Scenario source: https://community.fortinet.com/fortinac-f-57/troubleshooting-tip-identifying-when-a-host-does-not-match-a-user-host-profile-because-ad-group-membership-is-via-the-primary-group-229957
Community case dated 2026-09-16, outside the rolling 30-day window; retained as older contextual failure evidence, not represented as recent.

Directory synchronization creates NAC-side objects

FortiNAC-F 7.6.0 documents machine authentication with role-based access control based on Active Directory compute groups. During initial synchronization, FortiNAC-F creates two projections for each synchronized directory group: a host group named with the _host suffix and a user group named with the _user suffix. Registered computer objects can populate the host group; users already known through authentication or machine authentication populate the user group. The resulting groups are FortiNAC-F database objects used by User/Host Profiles and policy evaluation. They are not a live query of every possible AD group relationship at policy-evaluation time.

Scheduled sync and membership semantics

The directory configuration selects groups/organizational units and defines the synchronization schedule. A synchronization updates corresponding records and group membership, but users are added to the FortiNAC database when they connect and register; directory presence alone does not necessarily create an active host/user record. A successful task therefore proves the synchronization job ran, not that every machine is a member of the group the policy expects. Inspect the group selection, task completion, and resulting host/user group member counts after changing directory structure or membership.

The primaryGroupID edge case

A Community troubleshooting case describes a specific failure: 802.1X EAP-TLS machine authentication succeeds, the host registers, but the intended Network Access Policy is not selected. The synchronized _host group shows zero members even though Active Directory appears to show the computer in the group. The explanation is that the relationship is represented through the computer object's primaryGroupID, not the group's member attribute that synchronization uses to populate the FortiNAC host group. A computer's primary group can therefore be semantically meaningful in AD while not appearing in the expected synchronized membership projection.

Verify the decision path

Check the host's Policy Details and look for the Groups not matched line. Then inspect the FortiNAC-F host group member count and compare the AD computer's memberOf, the group's member attribute, and the computer's primaryGroupID. A successful EAP-TLS exchange proves the machine authenticated; it does not prove the User/Host Profile matched. Likewise, an empty _host group is evidence about the synchronized projection, not necessarily a failed directory bind. Keep authentication, synchronization, profile matching, and policy enforcement separate.

Remediation

First confirm the intended directory group is selected and synchronization completed without a timeout or LDAP error. If membership relies only on the primary-group relationship, use the supported AD membership approach for the policy design rather than repeatedly resyncing an unchanged directory. Where appropriate, make the computer a normal member so the relationship appears in the group's member attribute, then run the synchronization task again and inspect the host group count. Reopen Policy Details after the new membership is visible. Keep a local administrator session available while testing administrator-group changes to avoid lockout.

Change-control caveat

Directory changes affect more than NAC: changing a computer's primary group or group memberships may have broader AD implications. Confirm the intended RBAC model with the directory owner before altering membership. For a large environment, test one machine, run a targeted sync, confirm the host group projection and policy match, then expand. The key operational lesson is that identity authentication and identity-derived authorization are separate transactions with separate evidence.

Feature: fnacf-directory-sync-machine-auth-rbac-host-user-group-projection-primarygroupid

Workflow: LDAP/AD sync creates <group>_host and <group>_user projections → machine EAP-TLS registers host → User/Host Profile evaluates synchronized group membership → Network Access Policy match or default network

Failure class: Machine authentication succeeds but expected access policy does not match because AD membership exists only through primaryGroupID and not the group's member attribute

Remediation path: Verify group selection and sync completion; inspect AD membership attributes; use supported normal group membership or supported primary-group handling; resynchronize and re-check Policy Details

8. SAML IdP signing-certificate auto-rotation: staged trust and timed cutover

Primary feature/admin documentation: https://docs2.fortinet.com/document/fortiauthenticator/6.6.7/administration-guide/864572/general

Scenario source: No directly matched recent Community case was independently verified. No directly matched recent Community scenario for scheduled SAML IdP signing-certificate rotation was verified.

Why certificate rotation is a transaction

FortiAuthenticator can act as a SAML Identity Provider (IdP) and sign assertions consumed by configured Service Providers (SPs). The IdP's default certificate and signing algorithm determine how SAML assertions are signed. Replacing a certificate is not just a local file update: the SP must trust the certificate that will sign the assertion after cutover. FortiAuthenticator 6.6.7 exposes an option to automatically switch the default IdP certificate before the current certificate expires, allowing administrators to stage a replacement and schedule the moment when it becomes active.

Configure the staged certificate

In Authentication → SAML IdP → General, enable the SAML IdP portal if required, configure the Device FQDN and server address, select the default IdP certificate and signing algorithm, and enable automatic certificate switching before expiry. Choose the new default IdP certificate and set the switch date/time. The Device FQDN requirement matters for the portal's configured identity and URL behavior. Do not confuse this certificate with the HTTPS administration certificate: the HTTPS cert protects browser access to FortiAuthenticator, while the SAML IdP signing certificate validates the cryptographic signature on an assertion.

Coordinate the SP trust boundary

Before the cutover time, import the replacement certificate into the SP trust configuration or refresh metadata using the supported process for that SP. If the IdP begins signing with the new key while the SP trusts only the old key, the user may authenticate successfully at FortiAuthenticator but the SP will reject the response signature. Conversely, if the SP trusts the new certificate but the IdP still signs with the old one, signature validation can also fail depending on the SP's accepted keys. Plan the overlap so both sides are ready before the scheduled switch.

Evidence and validation

Record the current and replacement certificate fingerprints, validity dates, configured switch timestamp, and the SP's metadata/trust state. Test a pilot SP before the production cutover. After the switch, inspect a captured SAML response or the SP's SAML validation logs to verify which signing certificate was used and whether its signature validated. A successful FortiAuthenticator login proves the IdP accepted the user's authentication; it does not prove the SP accepted the assertion. Likewise, a valid certificate chain alone does not prove that the assertion audience, recipient, time conditions, or NameID attributes are correct.

Reverse-proxy and IdP-initiated caveats

The same General settings include reverse-proxy integration. When enabled, the response can be redirected to the configured reverse-proxy URL rather than the SP ACS URL when the request arrives on the reverse-proxy listening port. IdP-initiated portal listings also depend on the SP being configured to support IdP-initiated assertion response. If a login fails after certificate rotation, check the exact request flow, ACS/redirect URL, signature trust, and assertion fields rather than assuming the certificate alone is responsible.

Operational controls

Use a maintenance window appropriate to the SP fleet, stage the new certificate well before expiry, and keep the old certificate available during the supported overlap. Ensure the system clock is correct because certificate validity and SAML time conditions are time-sensitive. After cutover, monitor successful and failed SAML transactions across representative SPs. Automatic switching reduces the chance of an expired signing key, but it does not automatically update every SP's trust store or metadata.

Mechanism and troubleshooting fingerprints

Feature: fac-saml-idp-default-signing-certificate-preexpiry-scheduled-switch

Workflow: Import replacement certificate → configure default and new default IdP cert → set switch date/time → IdP signs assertions with replacement → SP validates signature using updated trust

Failure class: SAML authentication fails around certificate rollover because the SP does not trust the replacement signing certificate or the switch schedule is wrong

Evidence: IdP General settings, device FQDN, current/new default certificate, switch timestamp, SAML response signature, SP metadata/trust and error logs

Remediation path: Stage replacement cert, update SP trust/metadata before cutover, set and verify switch time, test pilot SP, and monitor assertion signature validation

FortiPAM

9. Secret checkout lock lifecycle: why an active launcher can block forced checkout

Primary feature/admin documentation: https://docs.fortinet.com/document/fortipam/1.8.2/administration-guide/165867/check-out-and-check-in-a-secret
Additional primary documentation: https://community.fortinet.com/fortipam-52/technical-tip-the-behavior-and-configuration-of-check-in-and-check-out-feature-in-fortipam-229607

Scenario source: Community article published 2026-08-26 and updated about eight days before this run; it documents that an active launch keeps the checkout lock alive until the session ends and the idle timer elapses.
Scenario source; primary lesson mechanics remain grounded in Fortinet documentation.

Checkout is an access lock, not just a reminder

FortiPAM's Requires Checkout option gives one approved user exclusive access to a secret for a limited period. Other users must wait until the secret is checked in or the checkout duration expires. When Requires Checkout is enabled, the secret password is visible only to a user with Edit or Owner permission for the secret being checked out. This protects accountability around shared privileged credentials, but it also means the lock's lifecycle must account for the launcher session that uses the secret, not just the clock value shown in the secret record.

How an active launch affects reclaim

The Community technical tip describes a case where User A checks out a secret, launches it, and leaves the launch alive while idle longer than the checkout duration. The administrator cannot force checkout while the launch remains active. Only after User A terminates the session or closes the browser tab, and the configured idle timer elapses, can the administrator force checkout. The distinction is intentional: reclaiming a secret while a privileged session is still using it can create ambiguous ownership and weaken session accountability.

Relevant secret fields

The secret database can expose fields such as checkout, checkout-duration, force-checkout-idle-time, inherit-permission, and the last launch timestamp. Interpret these fields together. Checkout duration limits the normal exclusive checkout; force-checkout idle time is an additional gate for administrator override after the launch has stopped being active. Permission inheritance controls who can manage the secret and is separate from the active-session state. A user may have view permission but not be able to see the clear password or override checkout.

Diagnostic evidence

When force checkout is unavailable, first verify that the secret is configured to require checkout and that the administrator has the necessary secret/folder permissions. Then inspect whether a launcher session is still alive. Compare the checkout duration with the last launch and session end time, and allow the configured force-checkout idle period to pass. If the launch is active, resolve the session through the approved operational process rather than deleting the secret or altering permissions. The absence of a visible password is not evidence that the secret record is corrupted; it may be the intended permission boundary.

Safe remediation

Coordinate with the current user or session owner to terminate the launcher cleanly. Wait for the idle threshold, then retry force checkout. If the secret remains locked after no active session exists and the timer has elapsed, capture the secret configuration and relevant logs and investigate a product/version-specific defect. Do not globally reduce checkout durations simply to make administrative override easier: the setting applies to privileged workflows and can affect simultaneous access, auditability, and operational safety.

Design implications

Choose checkout duration based on task length and define a reasonable force-checkout idle interval. Explain to operators that leaving a browser tab or native launcher open can keep the lock active. Test the workflow with a low-risk secret before broad rollout, including normal check-in, expiry, active launch, and administrator recovery. The meaningful evidence chain is checkout state → launcher lifecycle → idle timer → reclaim permission; looking at the checkout timer alone is incomplete.

Mechanism and troubleshooting fingerprints

Feature: fpam-secret-exclusive-checkout-active-launcher-force-checkout-idle-timer

Workflow: User checks out secret → exclusive lock begins → launcher starts proxy session → active launch prevents admin force checkout → session terminates → idle timer elapses → next approved user can check out

Failure class: Secret appears overdue but admin cannot reclaim it because a privileged launcher remains active or the force-checkout idle threshold has not elapsed

Evidence: Requires Checkout setting, checkout state/duration, last-launch-time, checkout-duration, force-checkout-idle-time, active session state, audit trail

Remediation path: Confirm permissions and checkout policy; inspect active launcher and timers; end the session safely, wait for idle threshold, then reclaim; do not weaken lock settings without risk review

FortiSIEM

10. CMDB business-service records: service inventory context versus live health evidence

Primary feature/admin documentation: https://docs.fortinet.com/document/fortisiem/7.3.4/user-guide/538340/viewing-business-services

Scenario source: No directly matched recent Community case was independently verified. No directly matched recent Community scenario for CMDB business-service mapping was verified.

What a business-service record contributes

FortiSIEM's CMDB includes Business Services and service categories such as IT service, business service, compliance, and ungrouped records. The documented view exposes attributes including Type, Name, Running on, Access IP, Details, and Maintenance. This inventory layer helps an analyst understand which service record is under review and the configuration context associated with it. It should not be confused with a synthetic transaction monitor or a raw event: a service object can exist even when the application behind it is unavailable.

Relationship to configuration items

The Running on and Access IP fields help connect the service record to the component or endpoint associated with it. During incident triage, use that relationship to locate the relevant CI, then verify whether the CI's current events and monitoring evidence align with the service record. If the service points to a retired host, old IP, or changed application endpoint, the analyst can misattribute impact or overlook the actual affected component. The CMDB relationship is useful context, but it needs maintenance when architecture changes.

Maintenance metadata is not proof of recovery

The Maintenance field provides service inventory context. Do not infer from the existence of a maintenance value that the service is healthy, that alerts were automatically suppressed, or that every dependent component is in maintenance. Confirm the exact behavior configured in the deployed FortiSIEM version and the operational process around maintenance. A service record's presence is a database fact; availability is a runtime property. When an incident occurs during a change window, correlate the recorded maintenance information with change records, event timestamps, and direct health checks.

Investigation workflow

Open CMDB → Business Services, select the service, and review Type, Name, Running on, Access IP, Details, and Maintenance. Then navigate to the linked CI or query the underlying events. Compare the time range of the incident with the service's recorded context. If the service has no valid running-on relationship or the access IP is stale, correct the inventory mapping before using it for impact analysis. If the mapping is correct but the service is failing, examine the raw logs and application/host health evidence instead of repeatedly editing the CMDB object.

Evidence hierarchy

A business-service record proves that the service is represented in CMDB with the shown attributes. A linked CI record proves that FortiSIEM has an inventory object for the component. A current event proves that a device or integration reported something at a particular time. A successful synthetic transaction or application probe—if separately configured—provides stronger evidence of end-to-end service behavior. These evidence types answer different questions. Use them together rather than treating a single CMDB screen as a health dashboard.

Operational hygiene

Assign clear ownership for service records and update Running on/access IP relationships when applications move, split, or change their front-end address. Use the CMDB to organize investigations and business context, but preserve raw event timestamps and direct health evidence in the incident record. For high-impact services, document the expected components and verify that the service object points to the right CI after changes. This reduces false attribution and makes the impact assessment explainable to operations and security teams.

Remediation path: Verify service-to-CI mapping and maintenance metadata; confirm underlying CI and raw events are current; update stale records and do not treat CMDB presence as synthetic availability

11. Steering bypass destinations: dynamic FQDN routes and on-net/off-net conditions

Primary feature/admin documentation: https://docs.fortinet.com/document/fortisase/7.4.0/administration-guide/662283/steering-bypass-destinations
Additional primary documentation: https://community.fortinet.com/fortisase-58/troubleshooting-tip-error-steering-bypass-destinations-not-working-in-fortisase-210167

Scenario source: Older Community case dated 2025-07-21 describes local printer traffic continuing through the tunnel until the correct bypass destination was configured and the endpoint reconnected.
Scenario source; primary lesson mechanics remain grounded in Fortinet documentation.

Purpose and traffic path

FortiSASE steering bypass destinations let administrators keep selected trusted traffic off the FortiSASE Cloud Security tunnel. This can reduce tunnel bandwidth and preserve local access to resources such as printers, local services, or high-bandwidth applications. The feature is configured in Endpoint Management → Configuration, inside the endpoint profile's Connection settings. The bypass rule is delivered to the endpoint, where it affects routing/steering; creating a destination in the portal does not immediately prove that an already connected endpoint has installed the new route.

Destination types

The documented destination types include Infrastructure, FQDN, Local Application, and Subnet. An FQDN destination adds the resolved IP address dynamically to the endpoint route table while the destination is in use and removes it after disconnection. A local application destination identifies a process by name, full path, or install directory, and host groups may need to be created before they can be selected. Subnet behavior varies with connectivity type: IPsec remote-agent connectivity supports unique subnet destinations in custom and default profiles, while SSL remote-agent connectivity has different inheritance constraints. Check the deployed FortiSASE release and endpoint platform before copying a profile design.

On-net/off-net conditions

When On-net Detection is enabled, a destination can apply only when the endpoint is classified as On-net, Off-net, or Both. A local printer bypass intended only inside the office may fail if the endpoint is classified Off-net or the detection rule does not match. Conversely, a broad Both condition may bypass traffic away from the corporate LAN when the intended policy was local-only. Confirm the endpoint's actual detected state and the selected condition, not just the rule's existence.

Important constraints

FortiSASE does not support wildcard FQDNs for FQDN split-tunnel destinations. Windows endpoints support application-based split tunneling or full tunneling; other platforms support full tunneling according to the cited guide. Do not assume a process-name bypass works on macOS or Linux simply because the portal accepts a profile. For subnet bypasses, review the profile inheritance rules so a custom profile does not unintentionally omit or inherit the wrong network ranges.

Operational scenario and verification

A user connected to FortiSASE cannot print to a printer on the local LAN, but printing works when the VPN is disconnected. The older Community case describes traffic to the printer still reaching FortiSASE because no matching bypass destination was installed. Confirm the assigned endpoint profile, add the correct printer subnet/IP or other supported destination, and reconnect the endpoint so it receives the updated route. Then inspect the endpoint route table and use traceroute or a packet capture to verify that printer traffic exits the physical interface rather than the cloud tunnel.

Do not stop at route presence

A route entry is necessary evidence but not sufficient proof that the application is working. Verify the destination address actually used by the application, DNS resolution, local LAN reachability, and any host firewall. Conversely, if the portal rule is correct but the route is missing, focus on profile assignment, endpoint reconnect/update, destination-type support, and on-net/off-net condition. Keep bypass lists narrow and documented because bypassed traffic does not receive the same cloud inspection path as tunneled traffic.

Mechanism and troubleshooting fingerprints

Feature: fsase-endpoint-profile-steering-bypass-fqdn-dynamic-route-onnet-offnet-condition

Workflow: Endpoint receives profile → destination type matches infrastructure/FQDN/local app/subnet → dynamic route or bypass condition applies → on-net/off-net state evaluated → traffic exits physical interface or cloud tunnel

Failure class: Local or high-bandwidth traffic stays tunneled because the destination is absent, condition does not match, FQDN pattern is unsupported, or endpoint has not received updated routes

Evidence: Assigned endpoint profile, bypass destination type, on-net detection result, endpoint route table, traceroute, tunnel/session logs before and after reconnect

Remediation path: Check assigned profile and exact destination object; avoid wildcard FQDNs; validate condition and platform support; reconnect endpoint and confirm route and actual egress

Secure SD-WAN

12. ADVPN 2.0 edge discovery and path management: shortcuts require compatible healthy underlays

Primary feature/admin documentation: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/637049/advpn-2-0
Additional primary documentation: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/985659/advpn-and-shortcut-paths

Scenario source: https://community.fortinet.com/fortigate-3/technical-tip-advpn-2-0-shortcut-tunnel-does-not-form-and-ike-debug-shows-error-vwl-found-no-viable-shortcut-drop-exchange-204721
Older Community example dated 2025-04-29; it illustrates the diagnostic boundary but is not a recent 30-day case.

What ADVPN 2.0 changes

ADVPN allows spokes in a hub-and-spoke IPsec topology to establish on-demand direct tunnels to each other, avoiding the hub for eligible spoke-to-spoke traffic. ADVPN 2.0 adds edge discovery and path management so a spoke can choose shortcuts based on the underlays available at both ends and their link-health criteria. The design is less dependent on specific legacy BGP route-reflector, recursive next-hop, per-overlay, or loopback mechanisms. Fortinet's 7.6.6 guide currently documents ADVPN 2.0 as IPv4-only, so do not assume the same path-management behavior applies to IPv6 overlays.

Shortcut eligibility is bilateral

A local spoke may have several healthy WAN members, but a shortcut is useful only when the remote spoke has a compatible underlay/path and the relevant health criteria are satisfied. Edge discovery supplies peer information; path management evaluates the candidates and triggers a shortcut query to the remote spoke. The remote endpoint must also be able to negotiate a viable tunnel over the proposed transport. In topologies where spokes use different transports than the hub, ADVPN 2.0 can use overlay placeholders to trigger shortcuts over transports to which the hub is not connected. This is a path-selection mechanism, not simply a route advertisement.

Control plane versus data plane

BGP routes can show that the destination subnet is reachable through the hub while the direct shortcut remains absent. That is not contradictory: route reachability and shortcut eligibility are different conditions. A shortcut may not form if no common healthy underlay is available, transport groups do not align, peer discovery is incomplete, or the IKE negotiation is rejected. If the shortcut does form, SD-WAN service rules and health state still determine whether application traffic uses it. Existing sessions and the hub fallback can make the symptom look intermittent as path state changes.

Diagnostic evidence

Check the software version and ADVPN 2.0 configuration on the relevant spokes first. Review the underlay interfaces, SD-WAN member health, and the SLA criteria on both sides. Use IKE debug around the time a flow should trigger the shortcut; the older Community scenario reports the message vwl found no viable shortcut, drop exchange when the path manager has no eligible candidate. The VPN Events log can distinguish shortcut tunnels from hub tunnels using the ADVPN Shortcut field on spokes; the hub's value remains zero because the shortcut is established between spokes. Confirm route and service diagnostics after negotiation rather than relying only on a tunnel name.

Failure isolation

If no shortcut query is triggered, inspect the initial traffic flow, edge discovery, and SD-WAN service matching. If the query is sent but rejected, compare transport compatibility, local/remote link-health criteria, and IKE proposals. If the tunnel forms but traffic still uses the hub, inspect the service rule, route selection, session state, and whether the shortcut remains in SLA. Do not repeatedly reset BGP as a first step when the actual log says no viable shortcut; that error points to path eligibility, not necessarily route absence.

Resilience and rollout

Maintain the hub path as a fallback while validating shortcut formation. Test at least one same-transport pair and one pair with different underlays, then simulate a degraded or failed member and confirm that path management withdraws or selects shortcuts as expected. Measure convergence and traffic loss instead of assuming that more shortcut tunnels always improve throughput. ADVPN 2.0 can build multiple paths for load-balancing services, but the path algorithm considers distinct underlays and SLA state. Document IPv4-only scope and version dependencies before using it as a universal overlay pattern.

Mechanism and troubleshooting fingerprints

Feature: sdwan-advpn2-edge-discovery-path-management-underlay-health-transport-compatibility

Workflow: Spokes learn peer edge/underlay information → both spokes' link-health and transport criteria evaluated → shortcut query sent → direct IPsec shortcut negotiated → SD-WAN selects healthy shortcut or falls back to hub

Failure class: Traffic remains hub-routed because no common eligible underlay/path satisfies both spokes' health and transport criteria

Evidence: ADVPN 2.0 release/configuration, IKE debug and shortcut-query result, VPN Events ADVPN Shortcut flag, underlay SLA/member state, routes and SD-WAN service diagnostics

Remediation path: Verify compatible versions and IPv4 scope; compare both spokes' underlay/member health and transport groups; inspect IKE shortcut-query logs; preserve hub fallback while correcting path eligibility
