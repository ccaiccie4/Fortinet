LESSON 01FortiGate

IPAM-managed firewall address objects and per-device unique subnet allocation

FortiOS 8.0 extends IPAM beyond interface addressing: an IPAM pool can allocate subnets to firewall-address objects, including objects consumed as VPN client ranges. Fabric objects can request a unique allocation on each FortiGate instead of inheriting the same subnet.

Purpose and object model

Traditional FortiGate IPAM manages interface subnets and associated DHCP scope from centrally defined pools. FortiOS 8.0 adds IPAM allocation for firewall address objects. This matters when a policy, VPN gateway, or Security Fabric design needs a managed address range that is not itself an interface subnet. The address object remains the policy-facing object; IPAM supplies its subnet value according to a pool and allocation rule.

The important objects are the IPAM subnet pool, an IPAM rule, and the firewall address object. A rule can apply to Addresses and match an address-object name pattern. For example, a rule matching VPN* can allocate from a dedicated VPN pool while other objects consume a different pool. The name match is operationally significant: a correctly typed object can still receive the wrong pool if it matches an unintended rule or no rule.

Allocation and Fabric behavior

Enable IPAM, define non-overlapping IPAM subnets, then create rules that select the intended pool. An IPAM firewall address uses set type ipam. When the object is also a Security Fabric object, set fabric-object enable permits its Fabric synchronization. The new ipam-allocate-unique control changes the allocation semantics: with it enabled, each FortiGate in the Security Fabric receives a unique subnet rather than every member inheriting the same subnet value through CSF synchronization.

This is not the same as creating a separate address object manually on every device. The object identity and policy reference can remain consistent while the allocated subnet differs by device. That is useful for branch VPN client ranges or per-site address pools where overlapping subnets would otherwise create routing ambiguity. An IPAM-type firewall address can also be selected as an address range on a VPN gateway so that remote clients consume centrally managed space.

config firewall address
    edit "VPN-CLIENT-POOL"
        set type ipam
        set fabric-object enable
        set subnet 192.168.0.0 255.255.255.0
        set ipam-allocate-unique enable
    next
end

The example shows the object-side controls; the IPAM pool and name-matching rule must exist separately. Do not copy the sample subnet into production without checking the actual pool design.

Verification and failure isolation

Verify the IPAM feature is enabled, the intended subnet pool exists, and the allocation rule applies to Addresses with the expected name pattern. Inspect the resulting address object on each Fabric member and compare the actual subnet values. A successful CSF sync proves that configuration was distributed; it does not prove that IPAM allocated a different subnet on each member or that the pool had sufficient free space.

If two FortiGates show the same subnet, check that the object is type ipam, is a Fabric object, and has ipam-allocate-unique enabled. Then check rule precedence/name matching and pool capacity. If VPN clients receive unexpected ranges, verify that the VPN gateway references the intended IPAM address object rather than a static range. Finally, inspect routes and policy references: allocation does not itself create a firewall policy or guarantee that the allocated subnet is reachable.

Operational caveats

Keep pools non-overlapping with branch LANs, tunnel interface ranges, and other VPN client pools. Treat renaming an object as a possible rule-match change. For a Fabric rollout, test one member first and verify the per-device allocations before installing dependent routes or VPN policies across all members. The feature is most useful when the address object is a reusable logical handle and the subnet must be unique at the consuming FortiGate.

Primary sources: FortiOS 8.0 IPAM firewall address; FortiOS 8.0 New Features.

LESSON 02FortiManager

Cisco pxGrid connected-user enrichment: Device Type and Session State

FortiManager 8.0 exposes Cisco ISE pxGrid endpoint Device Type and Session State in the connected-user view and CLI, allowing identity-policy operators to distinguish an authenticated endpoint from one that is merely started, postured, or disconnected.

Purpose and integration boundary

A pxGrid connector is not a generic syslog input. It is a certificate-based integration between FortiManager and Cisco ISE that imports identity and Security Group context so the imported groups can be used in FortiManager policy objects and installed to FortiGate. FortiManager 8.0 adds two useful connected-user attributes: Device Type and Session State. These make endpoint context more precise than username and IP alone.

In a distributed ISE deployment, FortiManager supports up to two Policy Administration/Monitoring (PAN/MnT) nodes and up to four pxGrid nodes. The connector depends on the ISE pxGrid service, certificates, node-name resolution, and ISE approval. A TCP/TLS connection is only the transport prerequisite; it does not prove that ISE has authorized the pxGrid client or that the expected endpoint events will be imported.

Transaction and policy flow

Create the Cisco ISE connector in FortiManager, establish certificate trust, and approve the pending FortiManager client in ISE > Administration > pxGrid Services > Clients. ISE must have the Security Group and identity-group/policy relationship needed to attach the endpoint to a group. FortiManager requires DNS capable of resolving the FQDNs of all ISE nodes because pxGrid payloads from Monitoring nodes can reference those names.

After connector import, FortiManager displays connected users with Name, IP Address, Device Type, and Session State. Imported pxGrid user groups can be selected in an FSSO/SSO Connector user group, referenced by a firewall policy, and installed to FortiGate. This is the control-plane chain: ISE identity/session context → pxGrid connector → FortiManager group → policy package → FortiGate enforcement. If the identity group is missing, the policy cannot match the intended user group even though the connector itself appears connected.

Feature-specific observables

diagnose system print connector <adom> pxgrid <connector_name> <optional_filter/tag>

The command displays imported users and filter attributes. FortiManager processes session states Started, Postured, and Disconnected; other ISE states such as Authenticated are ignored. Users with a null Security Group are also ignored. The GUI view is available under Fabric View > External Connectors or Policy & Objects > Security Fabric > Endpoint/Identity.

A user absent from the table does not automatically indicate a broken TLS connection. Check ISE client approval, certificate trust, DNS resolution for every ISE node, Security Group assignment, and whether the current ISE state is one FortiManager imports. A table row proves that context was imported; it does not prove that the FortiGate policy was installed or that traffic matched it. On FortiGate, verify the imported group and live FSSO user list separately.

Operational application

For BYOD or posture-based segmentation, use Device Type and Session State to explain why two users with the same username/IP range receive different access. A virtual machine or unmanaged device may have a different Device Type; a session that is only Started may not have the same posture as a Postured session. Build the policy around imported groups and the supported session semantics, not around an assumption that every ISE state is forwarded. During certificate renewal, validate both sides of the trust chain and repeat ISE approval if the connector identity changes.

Primary sources: FortiManager 8.0 pxGrid enrichment; Creating Cisco pxGrid connectors.

LESSON 03FortiAnalyzer

FortiAI Threat Posture Timeline: entity-scoped evidence correlation

The FortiAI Endpoint Analysis Agent gathers related logs and alerts for an Asset Identity Center endpoint, then summarizes traffic, sessions, threat score, highlights, and rationale over a selected time window.

Purpose and evidence model

The FortiAI Threat Posture Timeline is an endpoint- or asset-centered investigation view in FortiAnalyzer 8.0. It is different from alert triage: the analyst starts with an asset identity and asks how its posture evolved over a chosen interval. The feature uses FortiAI to summarize related traffic, sessions, threat score, alerts, and source logs. The underlying evidence can come from multiple Fabric sources, including FortiGate, FortiClient, FortiMail, and FortiAuthenticator where those products are sending relevant telemetry.

Open Fabric View > Asset Identity Center > Asset Identity List, right-click an asset, and choose Open FortiAI Threat Posture Timeline. Alternatively, open endpoint details and select Threat Posture Timeline. The FortiAI Endpoint Analysis Agent then fetches related log and alert data for the selected timeframe and performs analysis. The selected time window is part of the query, not just a chart zoom.

How the widgets behave

The Timeline widget plots Traffic, Sessions, or Threat Score over time. Alerts and source logs appear below the chart, with source device types (for example, FortiGate) shown for context. Hovering over a chart point, alert, or source device reveals related information. The FortiAI Endpoint Analysis Agent pane displays a summary and analysis details; Highlights appear when the agent identifies useful points and can emphasize the corresponding evidence in the timeline.

A subtle but operationally important distinction: toggling between Traffic, Sessions, and Threat Score changes the visualization and does not trigger a new agent analysis. Changing the selected timeframe does trigger a new retrieval and analysis. An analyst who changes the chart metric should not wait for a new model run; an analyst who changes the timeframe should expect the agent to fetch logs again.

Actions, prerequisites, and proof

The More menu can export a PDF, create a new incident, or add the posture analysis to an existing incident. The PDF includes the selected timeline view and highlights. The feature requires a valid FortiAI license and an administrator with the appropriate access. Without the license or permissions, the menu/view may be unavailable even though the underlying FortiAnalyzer logs exist.

The timeline is a correlation and explanation layer, not a substitute for raw-log validation. A summary proves that the agent analyzed the data it retrieved; it does not prove that every relevant device logged, that every event was normalized to the same asset, or that the timeline is complete. Inspect source logs, alert timestamps, source-device tooltips, and the selected timeframe before drawing conclusions. If the endpoint appears quiet, first confirm that the asset identity exists and that source devices are sending logs for the interval.

Troubleshooting application

When a SOC analyst reports that the timeline shows a threat-score spike but no obvious alert, expand Analysis Details, inspect the highlighted source logs, and compare the event timestamps with the selected window. If the analyst changed the timeframe after analysis, allow the agent to fetch and analyze again. If the chart metric changed but the narrative did not, that is expected behavior, not a failed refresh. If an incident is created, verify the incident record and attached evidence independently; exporting a PDF or clicking Create New Incident is an action, not proof that the resulting incident contains the expected source events.

Primary sources: FortiAnalyzer 8.0 FortiAI Threat Posture Timeline; New Features entry.

LESSON 04FortiSwitch

DHCP snooping bindings as the trust database for DAI and IPv4 source guard

DHCP snooping validates DHCP exchanges on untrusted ports and builds IP/MAC/VLAN/interface bindings. Dynamic ARP Inspection and IPv4 source guard can then use those bindings to reject forged ARP or source-IP traffic.

Purpose and shared state

DHCP snooping is an L2 security control, not merely a DHCP relay feature. It watches DHCP traffic on a VLAN, validates messages received from untrusted interfaces, filters invalid client messages, and maintains a binding database for leased hosts. FortiSwitch ports are untrusted by default; a port is trusted only when the administrator deliberately marks the server-facing interface as trusted. DHCP snooping is disabled by default per VLAN.

The binding database is valuable because it records the observed relationship among client MAC, leased IP, VLAN, and interface. Dynamic ARP Inspection (DAI) can consult that state to reject ARP packets that claim an IP/MAC association inconsistent with the learned binding. IPv4 source guard can use the same learned or static binding to restrict which source IPv4 address a host may use on a port. The controls are related but distinct: DHCP snooping builds the state; DAI validates ARP; source guard validates source IP traffic.

Configuration dependencies

Before enabling snooping, enable the trusted DHCP server list globally. Then enable snooping per VLAN, configure the approved DHCP server list, and set interface trust correctly. Enable source-MAC verification where appropriate, and configure Option 82 only when the DHCP design requires it. DAI and IPv4 source guard should be enabled only after the binding source is understood and populated. Static endpoints such as printers or servers need static snooping entries if they do not obtain leases from the observed DHCP process.

config system global
    set dhcp-server-access-list enable
end

config switch vlan
    edit <vlan-id>
        set dhcp-snooping enable
        set dhcp-snooping-verify-mac enable
        set dhcp-snooping-option82 disable
    next
end

Interface trust and DAI/source-guard configuration are separate steps; do not blindly trust every uplink. FortiSwitchOS documentation also describes static entries and DAI/source guard configuration in the FortiLink security-policy workflow.

State transitions and scale caveats

The binding database has lifecycle behavior that can surprise an engineer. Changing snooping from monitor to enable keeps the entries in the DHCP client/server databases? No: the client database is deleted on that transition. Changing from monitor to disable deletes both client and server databases. Plan the transition and repopulate bindings before enforcing DAI/source guard. The trusted DHCP server list has a global maximum of 2,048 entries across VLANs. ARP-derived static information can be retained for a configurable period from five minutes to seven days, or indefinitely.

Verification and troubleshooting

diagnose switch-controller switch-info dhcp-snooping status <switch-id>
diagnose switch-controller switch-info dhcp-snooping database <switch-id>
diagnose switch-controller switch-info ip-source-guard hardware

For a managed switch, the FortiGate CLI can display client/server database entries, trusted and untrusted ports, enabled VLANs, and database capacity. A DHCP lease visible on a client does not prove that the FortiSwitch has the correct binding or that DAI/source guard is enabled. If a client gets an address but cannot pass ARP or source-IP checks, inspect the binding database first, then the VLAN/port trust state and static entries. A rogue DHCP-server log proves that a server packet arrived on an untrusted interface; it does not prove the legitimate DHCP server is reachable. Treat high CPU or DHCP relay symptoms as model/firmware-specific and validate release notes before disabling the protection globally.

Primary sources: FortiSwitch DHCP snooping guide; FortiSwitch 8.0 FortiLink security policies; FortiGate managed-switch diagnostic commands. Scenario: recent DHCP snooping status collection tip.

LESSON 05FortiAP/Wireless

6 GHz Standard Power: AFC location eligibility and channel-grant lifecycle

AFC is the regulatory gate that lets supported 6 GHz APs request permitted Standard Power channels. The AP submits location information and receives an available-channel response; the country code, model, antenna design, and power mode determine what is possible.

Why AFC exists

Six-gigahertz operation is not one universal power mode. Low Power Indoor (LPI), Standard Power (SP), and Very Low Power (VLP) have different regulatory conditions, and VLP availability varies by country. Standard Power uses Automated Frequency Coordination (AFC) so an access point can use higher-power 6 GHz channels without interfering with incumbent licensed services such as fixed microwave links. The AP must provide its location so the AFC service can calculate which channels and power levels are available at that site.

The FortiAP workflow is therefore not simply “enable the 6 GHz radio.” The controller country/region and AP model/profile establish the regulatory context; the AP obtains a valid position; the AP sends location to the AFC service; AFC returns an available channel list; and the AP operates within that grant. If the country code is wrong, the geographic interpretation can be wrong. If the AP cannot provide acceptable location information, Standard Power channel selection can fail even though the radio hardware supports 6 GHz.

Model and location constraints

FortiAP G/K models use GPS positioning when AFC is required. The Community troubleshooting article updated November 10, 2026 notes that the FAP441K can use LPI indoors if GPS is unavailable, while the FAP443K is SP-only and requires AFC/GPS; the detachable Wi-Fi antenna design affects the regulatory mode. Confirm current country-specific rules and the exact model datasheet before deployment. Do not assume that every AP can fall back to LPI.

The FortiAP 8.0 Configuration Guide describes the location-source priority as Static LoWi (manual controller configuration), then built-in GNSS/GPS, then LoWi calculation using IEEE 802.11mc Wi-Fi RTT. LoWi calculation needs at least four responder APs with known positions and one initiator AP. This is a location-input mechanism; it is not the AFC authorization itself. A valid lowi-pos-type only proves the source of coordinates, not that AFC returned an allowed channel list.

diagnose wireless-controller wlac -c wtp <FAP-serial>
cw_diag -c afc status
cw_diag -c afc dump afc_request.txt
cw_diag -c afc dump afc_response.txt
cw_diag debug afc

Where GPS is unavailable and the model/regulatory rules allow it, the 8.0 guide documents per-AP static LoWi coordinates and error tolerances:

config wireless-controller wtp
    edit "<FAP-serial>"
        set static-lowi enable
        set static-lowi-lat "49"
        set static-lowi-lon "-123"
        set static-lowi-alt 33
        set static-lowi-lat-err 9
        set static-lowi-lon-err 10
        set static-lowi-alt-err 21
    next
end

Verification and troubleshooting

Check the FortiGate country/region and the AP profile's country/indoor-outdoor settings first. Then inspect the AP position type and coordinates. Use AFC status and request/response dumps to distinguish “no location,” “request not sent,” “no grant,” and “grant received but radio profile does not use an allowed channel.” A console log showing AFC connection is not proof that the returned channel list is usable by the AP model.

When a 6 GHz channel is missing from the GUI/CLI, do not immediately treat it as RF interference or a channel-planning issue. Compare the physical deployment country to the controller country code, check GPS/static location, verify AFC response, and check whether the model can operate in LPI. The Community article reports that AFC is required in the USA and Canada as of November 2026; regulatory requirements change, so verify the applicable country rules rather than hard-coding that statement into a global design.

Primary sources: FortiAP 8.0 profile configuration; automated FortiAP location positioning. Scenario: 6 GHz channel detection troubleshooting tip, updated 2026-11-10.

LESSON 06FortiNAC

Access Point Management: DHCP lease authorization for bridged AP clients

FortiNAC 9.4 can control hosts behind bridged access points using its DHCP lease file as the authorization signal, steering authorized and unauthorized clients to different DNS behavior and generating StaticIPAddress events for untracked addresses.

Deployment model

Access Point Management is intended for bridged APs where FortiNAC can associate downstream hosts with a switch interface. The AP must be discovered and support bridging, and the AP must appear connected to an interface on the upstream switch. This is not the same as managing an AP as a wireless controller object; FortiNAC is using the upstream wired topology and DHCP behavior to control hosts behind the bridge.

For a model initially placed in the Bridging Devices group, the AP-facing switch port must be moved into the Access Point Management group, the AP removed from Bridging Devices, and any user-defined uplink designation on the AP-facing interface undone. Resync the switch interfaces after changing the uplink designation. If the AP remains treated as a generic bridge, downstream clients may not be represented in the way Access Point Management expects.

DHCP and DNS transaction

The Configuration Wizard creates the DHCP configuration and address pools. FortiNAC maintains authorized and unauthorized pools and updates the DHCP server configuration with authorized IP addresses and their associated MAC addresses. Authorized hosts are directed to a valid DNS server so normal network access works. Unauthorized hosts are directed to FortiNAC's Access Point Management DNS, which resolves to the application server and redirects the user to the configured URL for the host state, such as registration, remediation, quarantine, or dead-end.

When a host connects, FortiNAC checks whether its MAC address appears in the DHCP lease file it maintains. If present, the host is allowed through the AP management path. If absent, FortiNAC generates a StaticIPAddress event. This is the core evidence boundary: AP discovery proves the bridge is known; DHCP lease membership proves that FortiNAC has a managed lease for the host; the StaticIPAddress event indicates the host is using an address not represented in that lease file. Map the event to an alarm and action through Alarm Mapping if the event should trigger enforcement or notification.

Configuration and verification

Before enabling the feature, configure the Access Point Management view, VLAN ID, and address ranges in the Configuration Wizard. Under System > Settings > Control > Access Point Management, enable the feature, set the DHCP configuration update interval, and add address ranges when static-IP detection is required. Add the AP-facing switch port to the Access-Point-Management group and verify membership with Show Members. Use a test client to confirm that authorized and unauthorized hosts receive the expected DNS behavior.

Important limitation and version boundary

If a host is manually rescanned or an existing scan is set to Failed while the host is already on the production network, FortiNAC does not automatically move that connected host to Isolation. The host can remain on production until its DHCP lease expires or it disconnects. This is not a generic NAC isolation mechanism. Plan the lease duration and disconnect/re-authentication behavior accordingly.

FortiNAC Access Point Management is documented for FortiNAC 9.4.0. A separate FortiNAC-F Community notice states that Access Point Management was removed in FortiNAC-F 7.6; do not assume this 9.4 feature exists on FortiNAC-F. Keep product family and version explicit in design documents.

Primary source: FortiNAC 9.4 Access Point Management. Version boundary: FortiNAC-F 7.6 removal notice.

LESSON 07FortiNAC-F

Administrator GUI MFA: per-admin versus global SMS/email enforcement

FortiNAC-F 7.6.5 adds a second factor to administrator GUI login. MFA can be configured per administrator or enabled globally, with country-code inheritance and token-timeout behavior that affect delivery and support.

Security boundary

FortiNAC-F administrator MFA protects access to the administrative GUI. It is separate from 802.1X, RADIUS, captive-portal, or endpoint authentication. The user first authenticates as an administrator; FortiNAC-F then requires a one-time token delivered by SMS or email before granting the GUI session. FortiNAC-F 7.6.5 release notes identify this as an introduced feature.

Individual and global policy

Individual MFA is configured from Users & Hosts > Administrators by modifying an administrator. Each administrator has a separate MFA setting. Global MFA is configured from System > Settings > Authentication > Multi-Factor Authentication. When global SMS or email MFA is enabled, it enables MFA for all administrators. The two controls are not interchangeable: an administrator may have an individual setting, while global policy provides a broad enforcement control.

Global SMS MFA can define a default country code. If an administrator has not configured a personal country code, FortiNAC-F uses the global default; if a personal country code is already set, that administrator's code and number are used. A mobile phone number with a country code but no configured mobile provider can still be sent through the REST SMS Gateway when the gateway is configured. Token Timeout controls how long the code remains valid.

Operational verification

Test an administrator with a personal country code and one without it. Verify the actual destination number and the selected delivery method, then test an expired token. If global MFA is enabled, verify the contact attributes for every administrator before enforcement. A successful password step does not prove the second factor completed. Likewise, a token-send request does not prove delivery or successful validation; inspect the configured SMS gateway/email path and the administrator's response.

The documented recovery command is:

execute admin-ui reset-mfa-settings

This is a recovery action for resetting MFA settings, not a routine workaround for a broken delivery path. Before using it, establish whether the failure is a wrong country code, missing contact value, SMS gateway issue, expired token, or a global/individual configuration mismatch.

Common failure patterns

If only one administrator fails, compare that administrator's individual settings and country code with the global defaults. If all administrators fail after a global enablement change, validate the global delivery configuration and contact data. If SMS arrives but the GUI rejects the code, compare the token age with Token Timeout and ensure the administrator is entering the latest token. If email works but SMS does not, test the SMS gateway independently rather than disabling MFA globally.

Do not infer that a FortiNAC-F cluster's HA health-check behavior is related to GUI MFA; they are separate control planes. Keep the release-specific feature introduction (7.6.5) and the detailed 7.6.0 configuration guide's individual/global controls aligned with the deployed version.

Primary sources: FortiNAC-F 7.6.5 What's New; Multi-factor Authentication guide.

LESSON 08FortiAuthenticator

REST API self-service provisioning of external SAML IdP resources

FortiAuthenticator 8.0.2 adds REST API resources for remote SAML servers and SAML IdP user sources, plus an embedded Swagger UI that exposes the exact API schema for automation.

What changed

FortiAuthenticator 8.0.2 adds two REST API resources for self-service external identity-provider setup: /remotesamlservers/ and /samlidpusersources/. It also adds built-in Swagger documentation at https://<FAC_IP>/api/v2/docs. The important operational distinction is that the remote SAML server and the SAML IdP user source are separate resource types. One represents the remote IdP relationship; the other represents the user-source side of the SAML identity workflow.

This is an API provisioning feature, not a new SAML assertion protocol. It enables automation to create the configuration objects through the REST interface rather than requiring every object to be entered manually in the GUI. The official release notes identify the resource paths, but the exact HTTP methods, required JSON fields, validation rules, and response schema must be taken from the Swagger page for the deployed build. Do not invent a POST body from a similarly named endpoint or assume that all 8.0.x builds expose identical fields.

Dependency and transaction model

A safe provisioning workflow begins by authenticating the automation client to the FortiAuthenticator REST API over the management interface. The client reads the built-in Swagger schema, confirms the supported operation and required fields, then creates the remote SAML server and the corresponding SAML IdP user-source object. The resources must be linked to the correct authentication flow and tested with the actual external IdP. Treat the remote server object as the trust/connection definition and the user-source object as the identity/group source; a successfully created object does not prove that SAML metadata, signing certificates, NameID, or group claims are correct.

Use least-privilege API credentials and protect them like administrator credentials. Validate the external IdP's entity ID, metadata/ACS information, signing certificate, and attribute/group mapping before enabling a production policy. If the IdP rotates its signing certificate, the resource may still exist while assertion validation fails. This is a trust-chain failure, not a REST transport failure.

Evidence and troubleshooting

Use the Swagger UI to confirm the deployed endpoint contract, then record the request identifier, resource path, response status, and returned object identifier from the actual API response. Confirm the new remote SAML server and user-source objects in the GUI/API inventory. Finally, perform an end-to-end SAML login and verify that the expected user and group attributes are consumed by the intended policy or service provider.

Interpret evidence in layers: a TCP connection proves reachability; an authenticated API response proves the API accepted the caller; a created resource proves the configuration object was stored; a successful SAML assertion proves the federation transaction; correct group membership proves the identity-source mapping. None of these individually proves all the others.

Failure isolation

If the API call succeeds but the user source is empty, inspect the separate /samlidpusersources/ resource and its mapping to the remote IdP. If the resource is present but assertions fail, inspect metadata, certificate issuer/subject/fingerprint, audience, and assertion attributes. If the endpoint rejects a field, return to Swagger for the exact version-specific schema rather than retrying guessed payloads. This approach makes API automation repeatable without confusing object creation with federation health.

Primary sources: FortiAuthenticator 8.0.2/8.0.3 REST API enhancements; 8.0.2 release notes.

LESSON 09FortiPAM

Non-TOTP target-side 2FA challenges in the WebSSH launcher

FortiPAM 1.9 WebSSH can relay an interactive second-factor challenge emitted by the SSH target and let the user enter a real-time code, including FortiToken, SMS, email, or third-party authenticator codes.

Two authentication systems, two boundaries

FortiPAM access authentication decides whether a user may view or launch a secret. The feature covered here is different: after the user has launched a WebSSH secret and FortiPAM connects to the target, the target SSH server can issue its own interactive 2FA challenge. FortiPAM 1.9 WebSSH can display that challenge in the console and accept a real-time token code. FortiPAM does not need to store the target's TOTP seed to perform this relay.

The target may use FortiAuthenticator-based FortiToken Mobile/FortiToken Cloud, SMS, or email delivery, or a third-party token application such as Google Authenticator. When the SSH server requests the second factor, WebSSH displays a prompt similar to Enter token code or no code to send a notification to your FortiToken Mobile. The user can enter the received code manually or request a push notification where supported.

Transaction flow and secret prerequisites

The flow is: user launches the secret → WebSSH opens an SSH connection → target authenticates the primary credential → target emits an interactive 2FA prompt → WebSSH renders the prompt → user enters the code → target validates the second factor → shell access continues. The target is authoritative for the second-factor decision. A successful FortiPAM launch does not mean the target has authenticated the user.

For FortiAuthenticator SMS/email delivery, FortiPAM documents secret-level prerequisites so the WebSSH workflow can accept and relay the challenge. At least one of these SSH-related settings must be enabled: SSH service with an SSH Filter selected (an empty filter profile is acceptable when no filtering is required), SSH Auto-Password, or a Target-Only Secret Template. These controls establish the WebSSH handling path; they do not replace the target's own 2FA configuration.

Failure and recovery behavior

If a user enters an incorrect token, the same SSH connection cannot retry the challenge. Close the WebSSH session and relaunch the secret with the correct code. Do not keep resubmitting in the same console or interpret the failed second factor as a FortiPAM password-check failure. FortiPAM also notes that automatic FortiToken Mobile push can behave inconsistently in some environments, so manual code entry is recommended for reliability.

When the challenge does not appear, verify that the target actually issues an interactive challenge for the account being used. Then inspect the secret's SSH service, filter, Auto-Password, or Target-Only template settings. If the prompt appears but the token is rejected, check time validity and the target's authentication logs. If SMS/email is not delivered, test the FortiAuthenticator delivery path separately. A push notification request is not proof that the target accepted a token.

Operational use

This feature is useful when privileged SSH targets enforce per-account MFA outside FortiPAM, especially where an organization uses a mix of FortiToken and third-party authenticator apps. It preserves the target's second-factor control while keeping the SSH session inside the PAM launcher. Document the relaunch requirement in operator procedures and ensure that session recording/auditing is reviewed separately from the authentication result.

LESSON 10FortiSIEM

Asynchronous incident triggering-events API: start, progress, result

FortiSIEM replaces a long synchronous triggering-event retrieval with a queryId-based job lifecycle. The caller starts a query, polls progress, and retrieves results only after progress reaches 100 percent.

Why the API is asynchronous

Incident triggering events can require a large query across a time window. The older endpoint returned the events synchronously, forcing the caller to wait for the complete response. FortiSIEM adds an asynchronous interface that returns a queryId immediately and separates job creation, progress monitoring, and result retrieval. This is a workflow change for integrations: a successful start response means the query was accepted, not that the evidence is ready.

Three-stage transaction

The start endpoint accepts the incident ID and time bounds:

/pub/incident/triggeringEvents/start?incidentId={id}&timeFrom={from}&timeTo={to}

It returns a queryId. The client then polls:

/pub/incident/triggeringEvents/progress/{queryId}

When progress reaches 100 percent, the client retrieves the triggering events:

/pub/incident/triggeringEvents/result/{queryId}

The legacy synchronous endpoint remains documented as /pub/incident/triggeringEvents?incidentId={id}&timeFrom={from}&timeTo={to}. New integrations should use the job lifecycle so a slow query does not hold one request open for the entire analysis.

Client design and evidence

Persist the queryId with the incident ID and requested time window. Poll progress with bounded backoff rather than issuing a tight loop. Request the result only after the API reports 100 percent. Keep the incident ID and time range with the returned result so that the evidence can be traced to the query that produced it. If the client process restarts, it should be able to resume monitoring the existing queryId rather than silently creating a new job.

Evidence has three distinct meanings: the start response/queryId proves job acceptance; the progress response proves the job's reported state; the result response proves that the triggering-event payload was retrieved. An HTTP success from the start endpoint does not prove that the result is populated. Likewise, progress at 100 percent does not prove that the requested incident/time window was the correct one.

Operational troubleshooting

If an integration receives a queryId but returns an empty event list immediately, inspect whether it called the result endpoint before the progress endpoint reached 100 percent. If the result is complete but contains unexpected events, compare incidentId, timeFrom, and timeTo to the incident's actual timeframe. If a client times out, do not assume the server job was cancelled; retain the queryId and check progress before starting another query. Use the Fortinet Developers Network API documentation for authentication and any version-specific request/response details not included in the user-guide feature note.

This asynchronous pattern is useful for SOAR integrations, scheduled incident enrichment, and evidence export. It should be modeled as a small state machine rather than a single REST call: STARTED → IN_PROGRESS → COMPLETE → RESULT_RETRIEVED. Treat failed or missing progress responses as a transport/monitoring problem until the query's server-side state is known.

Primary sources: FortiSIEM Enhanced Triggering Event API; FortiSIEM 7.4.0 API enhancements.

LESSON 11FortiSASE

Private Proxy over Branch On-ramp: encrypted steering for unmanaged endpoints

Private Proxy lets devices without FortiClient steer HTTP/HTTPS through a local proxy address, then carries the traffic over an encrypted Branch On-ramp tunnel to FortiSASE. Optional SPA extends access to private resources.

Use case and traffic path

Private Proxy is intended for devices where FortiClient cannot be installed and only web traffic needs steering, but the organization requires stronger transport protection than a proxy connection over the public Internet. The proxy client uses a manual proxy setting or PAC file and points to a private proxy primary/secondary IP configured on the Branch On-ramp nodes. The on-premises Branch On-ramp device then carries the proxy traffic through an encapsulated, encrypted IPsec tunnel to FortiSASE.

At the FortiSASE side, proxy policies inspect HTTP/HTTPS traffic. If Secure Private Access is also licensed and configured, the same proxy users can reach private resources behind an SPA hub. Do not confuse this with the agent-based Cloud Security Tunnel or with agentless proxy over the public Internet: Private Proxy adds the Branch On-ramp and encrypted tunnel segment between the client network and FortiSASE.

Prerequisites and dependency order

Private Proxy is a select-availability feature and is not enabled by default. Request enablement through FortiCare. Branch On-ramp must be licensed and configured, and a dedicated IP address must be implemented and licensed for the instance. BGP must be configured before enabling Private Proxy. A supported on-premises Branch On-ramp IPsec device must be connected successfully to a Branch On-ramp Security PoP. Configure primary and secondary proxy destination IPs on all On-ramp nodes, then set each proxy client to use the correct address in its manual proxy configuration or PAC file.

Secure Private Access is optional and is required only if Private Proxy users must reach private resources. For deep inspection, install the FortiSASE CA certificate on proxy-user endpoints; otherwise TLS certificate errors or inspection gaps can result. FortiSASE per-user licensing includes up to three devices per user, which can be a combination of FortiClient and Proxy devices.

Identity and NAT caveat

IP-based authentication for Private Proxy users is supported only when SSO authentication is configured and NAT is disabled on the On-ramp firewall policy. With NAT disabled, each client source IP remains unique, allowing users to be tracked in FortiSASE traffic and security event logs. If NAT is enabled, multiple clients can collapse to the same source address and IP-based identity loses the per-client distinction. Do not troubleshoot this as an SSO credential problem until the source-IP preservation path is checked.

Verification and failure isolation

Verify in dependency order: select-availability enablement and license; Branch On-ramp device registration and IPsec tunnel; BGP reachability; primary/secondary private proxy IPs on all nodes; client PAC/manual proxy settings; and the FortiSASE proxy log. If deep inspection is enabled, confirm the CA is installed on the endpoint. If the user is not identifiable, confirm SSO and no-NAT behavior. If private applications fail while Internet proxy works, check SPA licensing, hub routing, and private-resource policy separately.

For existing instances, Private Proxy with SSO is not compatible with certain configuration transitions, including secure-proxy migration and disabling then re-enabling Proxy from Network > Proxy configuration. Plan such changes with a maintenance window and validate the current instance state before toggling proxy settings.

LESSON 12Secure SD-WAN

Bandwidth-gated SD-WAN packet duplication across overlays and underlays

FortiOS 8.0 can stop sending duplicate packet copies when measured member bandwidth exceeds a directional threshold. The operator chooses whether the threshold measures the overlay or its underlay.

Purpose and behavior

Packet duplication sends additional copies over multiple SD-WAN members to improve delivery resilience for selected traffic. Duplication consumes bandwidth, and overlays can share the same physical underlay. FortiOS 8.0 adds a bandwidth gate that checks utilization before duplicating: when measured bandwidth is below the configured threshold, duplication starts; when it exceeds the threshold, duplication stops. The feature is intended to protect the link budget while preserving the original forwarding path.

Threshold controls

Thresholds are configured under each SD-WAN member:

config system sdwan
    config members
        edit <member-id>
            set duplication-threshold-upbandwidth <integer>
            set duplication-threshold-dwbandwidth <integer>
            set duplication-threshold-bibandwidth <integer>
            set duplication-threshold-bandwidth {overlay | underlay}
        next
    end
end

The upstream, downstream, and bidirectional threshold values are expressed in kilobytes per second, with the documented range 0–4294967295. The measurement source is either the overlay interface (default) or the underlay interface. This choice changes the meaning of the threshold. If several overlays share one underlay, measuring each overlay separately can hide congestion on the physical link; measuring the underlay makes those overlays respond to the shared physical utilization.

The Fortinet example uses four overlays across two underlay ports. The overlays associated with an underlay continue duplicating while the measured utilization on that underlay remains below the configured threshold; when it exceeds the threshold, duplication stops on the associated overlays. duplication-max-num remains a separate control on the maximum number of copies. Do not confuse a duplication threshold with a member-selection SLA or with monthly quota steering.

Verification and interpretation

Test the design below and above the threshold. Capture the original and duplicate packets on the overlay and underlay, and correlate packet counts with interface counters. Confirm which physical underlay each overlay uses and whether the threshold is upstream, downstream, or bidirectional. A healthy SLA score does not prove that the duplication threshold is below its limit. Conversely, seeing duplicate copies stop does not mean the original traffic was dropped; the gate controls the additional copies.

The documented default threshold is 0. Do not infer from the numeric default alone whether it disables the check or has another special meaning; confirm the deployed FortiOS command reference and test behavior before relying on a zero value. Also confirm whether counters are measured on the overlay or underlay chosen for each member, especially when tunnels are rebalanced or a second overlay is added to an existing physical link.

Operational application

For a spoke with two WAN circuits and multiple overlays per circuit, map every overlay to its physical member before setting thresholds. Choose underlay measurement when the business requirement is to protect the shared circuit capacity. Choose overlay measurement only when the intent is to cap each tunnel independently. Use directional thresholds when upload and download capacity are asymmetric. Validate the change with a controlled traffic test and packet capture; do not use an SLA probe result as a substitute for measuring the actual data-plane load.

Primary sources: FortiOS 8.0 packet-duplication bandwidth threshold; SD-WAN New Features overview.
