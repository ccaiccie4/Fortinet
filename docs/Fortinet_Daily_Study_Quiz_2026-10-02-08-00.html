1. FortiGate — BFD-enabled BGP graceful restart during FGCP failover

Editable draw.io

BGP graceful restart preserves forwarding state while BFD deliberately detects forwarding failure quickly. During FGCP failover those objectives can collide: a BFD expiry can cause the neighbor to withdraw routes before graceful restart retention completes. FortiOS 8.0 documents static BFD peers under config router bfd so the new primary can instantiate BFD state early rather than waiting for BGP registration. Verify HA role, BFD request/session state, BGP graceful-restart capability, route retention and actual forwarding in that order. A live BFD session proves liveness detection, not route retention; an established BGP session proves adjacency, not that forwarding survived the transition. If graceful continuity is the priority, validate whether BFD should be disabled on that peer or whether timers/static BFD behavior provide the required convergence semantics.

2. FortiManager — Workflow approval matrices and session conflict handling

Editable draw.io

Workflow mode separates editing, approval, ADOM adoption and device installation. FortiManager can require approval from multiple approval groups; one approver from every configured group must approve. Parallel sessions can conflict when they touch overlapping objects or policies, so reviewers must inspect the session diff and merge/conflict state rather than rely on timestamps. Approval does not itself prove installation to FortiGate. Troubleshoot the transaction as session creation, edits, submit, approval, conflict resolution, ADOM adoption, install preview and device task. This separation makes it possible to identify whether a failure belongs to governance state or deployment state.

3. FortiAnalyzer — Cloud storage connectors for log offload

Editable draw.io

Cloud storage connectors combine provider identity, endpoint or region, authentication, TLS trust and object-storage authorization. Local log ingestion can be healthy while offload fails. Fortinet requires the relevant cloud CA trust, so certificate validation is an explicit dependency. Verify local eligible logs, connector state, DNS/network reachability, TLS, cloud authentication/authorization and finally remote object creation. A successful TCP connection is weaker evidence than an object appearing with the expected timestamp. Treat offload as part of a retention/retrieval design and test recovery, not only upload.

4. FortiSwitch — BGP EVPN with VXLAN and ARP/ND suppression

Editable draw.io

VXLAN supplies the overlay data plane while BGP EVPN distributes reachability such as MAC/IP information. ARP/ND suppression lets VTEPs answer known neighbor requests from control-plane state instead of flooding them across the overlay. Troubleshoot underlay reachability, BGP EVPN session, EVPN routes, VNI mapping, VTEP state, bridge/MAC tables and encapsulated traffic separately. BGP up does not prove VXLAN forwarding; a reachable VTEP does not prove the required EVPN MAC/IP route exists. Duplicate-address detection and multihoming add further control-plane state that should be verified explicitly.

Evidence boundary

Collect configuration intent, live runtime state, the first downstream transaction, and the user-visible outcome separately. Do not use a lower-layer success as proof that the feature decision occurred.

5. FortiAP/Wireless — Dynamic captive-portal redirect URL from RADIUS authorization

Editable draw.io

A RADIUS Access-Accept can return Fortinet-Captive-Portal-URL so FortiGate redirects a wireless client to a session-specific portal. The VAP must use the compatible tunnel captive-portal/auth-MAC behavior and dynamic redirect must be enabled. Follow client association, RADIUS request, authorization profile/VSA, FortiGate redirect and portal reachability. Access-Accept proves authorization but not that the redirect attribute was present. An HTTP redirect to the intended URL proves the FortiGate portion even if DNS, TLS or the portal application then fails.

6. FortiNAC — Persistent Agent heartbeat, trust, and lost-contact state

Editable draw.io

Persistent Agent communication normally uses TCP/4568, with TCP/80 used for upgrades. FortiNAC can generate Lost Contact and Regained Contact events, but lost-contact timing also depends on L2 polling and is not an immediate liveness signal. Certificate trust is critical: the endpoint system account must trust the issuing CA; browser trust under a user context is not equivalent evidence. Troubleshoot endpoint online/L2 state, server discovery, transport, TLS trust, heartbeat, compliance scan and policy result in sequence. NATed VM topology can prevent full unsolicited-agent behavior, so bridged networking is a meaningful topology dependency.

7. FortiNAC-F — SSH remote backup path semantics after OpenSSH/SFTP behavior change

Editable draw.io

A recent Fortinet scenario shows backups failing after upgrade even when SSH authentication remains valid because modern OpenSSH scp defaults to SFTP. A chrooted SFTP namespace can expose a different destination path than an interactive shell or legacy SCP. The signature dest open ... No such file or directory points to path resolution, not key authentication. Test the underlying remoteBackup transfer, identify the SFTP-visible path, update configuration and verify actual remote files for database, system and archive jobs. In HA, authorize and test both nodes.

8. FortiAuthenticator — RADIUS accounting as FSSO session source

Editable draw.io

FortiAuthenticator can convert RADIUS Accounting-Start, Interim-Update and Stop records into identity sessions and publish them through FSSO. Authentication success alone does not prove an accounting/FSSO session exists. Listener port, RADIUS client definition, attributes, session correlation, group enrichment and downstream FortiGate mapping are separate boundaries. Follow one Acct-Session-Id from the wire into FAC and then into the FortiGate identity table. Missing Stop records can create stale identity, while aggressive timeout can remove active identity too early.

9. FortiPAM — Secret discovery and automatic import

Editable draw.io

Secret Discovery scans sources such as Active Directory, Unix and FortiOS for accounts/resources. Discovery results are not yet managed secrets: discovery, import, policy assignment, rotation and session use are separate states. Verify source reachability, discovery credential privilege, enumeration results, management/import state and then a policy-controlled use of the resulting secret. Automatic import should be scoped carefully because a broad scan can discover service and administrator accounts with different ownership and rotation requirements.

10. FortiSIEM — Credentialed device discovery and monitoring assignment

Editable draw.io

FortiSIEM discovery combines target scope, credential mapping, discovery type and the Collector or Supervisor performing the task. Range, Smart, L2 and cloud discovery have different semantics. A ping response is not enough for correct device identification; credentialed SNMP/SSH/WMI/API access can provide hostname, OS, hardware and services. After discovery, verify the CMDB object, assigned Collector/Worker and fresh metrics. Smart Scan and route discovery should be bounded carefully in large routing domains.

11. FortiSASE — DNS Filter precedence, translation, and fail-open behavior

Editable draw.io

FortiSASE evaluates local domain-filter rules before FortiGuard category filtering. Local Allow can bypass category filtering, while Monitor continues into rating. DNS translation can replace the returned address after resolution, so a correct upstream answer may intentionally differ from what the endpoint receives. Rating-error behavior is an explicit fail-open/fail-closed design choice. Private and public custom DNS paths also differ: a private resolver must be reachable through the private/SPA path. Verify the endpoint query, local match, FortiGuard decision, upstream resolver and final returned answer.

Evidence boundary

Collect configuration intent, live runtime state, the first downstream transaction, and the user-visible outcome separately. Do not use a lower-layer success as proof that the feature decision occurred.

12. Secure SD-WAN — Single IKE selector for ADVPN shortcut control-plane traffic

Editable draw.io

ADVPN shortcuts should be able to age out when user data becomes idle even though SD-WAN health checks and BGP control traffic continue. FortiOS can use a dedicated dynamic IKE selector for that control-plane traffic so periodic probes do not keep the data shortcut artificially active. Verify shortcut creation, IKE/IPsec selectors, BGP state, health checks, data-session counters and idle teardown. BGP Established proves control reachability but not selector classification. Generate data, stop it and observe which selector counters continue and whether the shortcut ages out then recreates on demand.
