1. FortiGate packet flow: policy routes, routing, firewall policy, NAT, session state, and debug flow

Beginner foundation — terms you need. A FortiGate does not forward a new packet merely because a route exists. The packet enters an interface and VDOM/VRF context, may be steered by policy routing or SD-WAN, needs a usable route and next hop, must be permitted by firewall policy, may be translated by NAT/VIP logic, creates or matches a session, may traverse inspection, and can later be accelerated in hardware.

The most reliable troubleshooting approach is to define one exact flow: source IP, destination IP, protocol, source port, destination port, ingress interface, VDOM/VRF, and expected egress. That turns “the application is broken” into a sequence of falsifiable state checks.

Policy routing is a separate decision layer from the ordinary routing table. diagnose firewall proute list displays policy-route entries. diagnose ip proute match <dst> <src> <iif> <proto> <sport> <dport> [vrf] tests a specific tuple. A match proves the policy-routing decision for the supplied fields; it does not prove that the selected gateway is reachable, that firewall policy permits the flow, that NAT is correct, or that the return path works.

After steering, verify routing with get router info routing-table all or an appropriately scoped route check. A route proves control-plane path selection, not authorization. Firewall policy then determines whether the traffic is allowed between the relevant interfaces/zones and whether NAT/inspection is applied. Once the session is established, existing session state can continue to influence traffic even after policy or route changes, so old-session versus new-session testing matters.

diagnose debug flow should be bounded and filtered. In multi-VDOM systems select the correct VDOM first. Apply a narrow address or tuple filter, start a small trace count, generate the test, then stop debugging. If the session is hardware-offloaded, CPU flow output can be incomplete; an empty trace is not automatically proof of absent traffic.

Healthy

  • Expected policy-route or ordinary route is selected.
  • Next hop is reachable.
  • Firewall policy and NAT match the intended design.
  • Session original/reply direction is consistent with the flow.

Abnormal

  • An unexpected policy route steals the flow.
  • The diagnostic is run in the wrong VRF.
  • Route is correct but firewall policy or NAT fails.
  • CPU debug looks silent because the established session is accelerated.

Evidence-first workflow

  1. Define the exact tuple and VDOM/VRF.
  2. Check policy-route/SD-WAN steering.
  3. Check route and next hop.
  4. Check firewall policy and NAT/VIP.
  5. Inspect session and acceleration state.
  6. Use bounded flow debug/sniffer evidence.
  7. Verify return path and re-test after the narrow correction.

2. NPU hardware acceleration: software sessions, NP6/NP7 offload, and diagnostic visibility

Beginner foundation. Hardware FortiGates can contain Network Processing Units. FortiOS establishes the session and policy state in software; eligible steady-state traffic can then use an NPU fast path. CPU tools and NPU tools therefore observe different execution paths.

The software session table is the starting point. diagnose sys session list exposes policy, NAT, original/reply direction and NPU fields. Fortinet Community examples show offload fields such as ofld-O, ofld-R, and directional offload values. An established session can exist and pass traffic even when a CPU packet trace shows little activity.

On supported NP7 systems, diagnose sys npu-session list answers a different question: whether accelerated hardware-session state exists. This is complementary to the software session table rather than a replacement for it. When troubleshooting a specific connection, first prove the FortiOS session, then determine whether the flow is accelerated.

IPsec adds offload-specific reason codes. Fortinet documents examples where reason code 1 corresponds to NPU offload being disabled, reason code 2 to an unavailable hardware offload path such as a VM without an NPU, and reason code 3 to an unsupported encryption/offload combination in the cited context. Those messages are about acceleration eligibility; they do not all mean the IPsec tunnel is unusable because software processing may continue.

Temporarily setting auto-asic-offload disable on the specific firewall policy can return the test flow to a CPU-visible path. That is a diagnostic modification, not a design fix. Fortinet warns that disabling acceleration shifts processing to CPU and can affect performance. Scope it narrowly, capture evidence, then restore acceleration.

Healthy

  • Software session has expected policy/NAT.
  • NPU fields show expected acceleration.
  • Hardware session is present when supported.
  • CPU usage remains appropriate for the traffic profile.

Abnormal

  • No CPU trace is misread as no packets.
  • A feature or platform legitimately prevents offload.
  • Offload is disabled and left disabled after troubleshooting.
  • An offload reason code is mistaken for a general VPN failure.

Commands

  • diagnose sys session list — software session/policy/NPU metadata.
  • diagnose sys npu-session list — NP7 hardware-session view on supported systems.
  • diagnose npu np7 port-list — NP7 port context where supported.
  • set auto-asic-offload disable — bounded policy-level troubleshooting change.
What to notice in Fortinet examples: the same connection can have software session metadata while packet forwarding is already occurring in hardware.

3. Secure SD-WAN: performance SLA, rule selection, zones, firewall policy, and real application health

Beginner foundation. A WAN link can be electrically and administratively Up but still be unsuitable for an application because of loss, latency or jitter. FortiGate SD-WAN measures path health, evaluates rules, selects an eligible member, then still requires firewall policy, NAT and session state.

diagnose sys sdwan health-check status answers whether the configured health checks are meeting their SLA criteria. It does not tell you which firewall policy allowed a user flow. diagnose sys sdwan member shows member state, and diagnose sys sdwan service4 helps expose SD-WAN service/rule decisions. diagnose firewall proute list lets you inspect the policy-route representation of steering in the data plane.

SD-WAN zones and members are different objects. Rules decide among members, while firewall policies can reference zones. Fortinet's enterprise SD-WAN guidance discusses using separate zones when different WAN types require different security policies. A steering decision does not bypass firewall inspection; it chooses the path on which the firewall session will be built.

Probe design is a common failure source. If the SLA target remains reachable while the real SaaS/application route is degraded, the link can be declared healthy according to the configured test while users still fail. The inverse also occurs: a poorly chosen target can mark a link unhealthy even though important destinations remain usable. Health checks must represent business reachability.

Troubleshooting chain

  1. Physical/member state.
  2. SLA target, loss, latency and jitter.
  3. Matching SD-WAN rule/strategy.
  4. Selected member and policy-route state.
  5. Firewall policy/NAT/session.
  6. Actual application transaction.

Healthy

  • Member usable.
  • SLA state within thresholds.
  • Rule selects intended member.
  • Firewall policy references intended zone.
  • Session egress agrees with rule.

Abnormal

  • Interface Up but SLA failed.
  • Probe target does not represent application path.
  • Rule priorities produce an unexpected path.
  • Steering is correct but firewall policy/NAT is wrong.

4. FortiSwitch MCLAG: ICL, LACP, STP awareness, split-brain, and multicast state

Beginner foundation. LAG combines links to one logical switch. MCLAG extends that logical bundle across two FortiSwitch peers, providing node redundancy. The peers need an inter-chassis link (ICL) and coordinated state.

Fortinet documents a maximum of two FortiSwitch units per MCLAG pair and recommends the same hardware model and software version. Mismatched pairs may appear to work but are unsupported. At least two links are recommended for ICL redundancy, which prevents the peer relationship itself from being a single-link failure domain.

The downstream system should attach to both peers using an 802.3ad aggregate. LACP state proves bundle negotiation; it does not prove the ICL, peer synchronization or STP behavior. Fortinet requires mclag-stp-aware at the global switch level and STP enabled on all ICL trunks; both are enabled by default in the cited requirements.

Split-brain protection is separate. Current FortiSwitch documentation calls for set mclag-split-brain-detect enable on both peers and warns that enabling split-brain detection can cause some traffic loss while LACP renegotiates. This is a resilience mechanism with a real convergence consequence.

Multicast introduces additional requirements. For IGMP snooping, mclag-igmpsnooping-aware must be enabled, IGMP proxy is required, and Fortinet defines different flood/report settings for ICL trunks versus ISL/FortiLink trunks. Therefore unicast can be perfectly healthy while multicast remains broken.

Verification

  • diagnose switch mclag icl — FortiSwitchOS ICL state.
  • diagnose switch mclag list — FortiSwitchOS MCLAG state.
  • diagnose switch-controller switch-info mclag icl — FortiGate controller view for managed FortiSwitch.
  • diagnose switch-controller switch-info mclag list — managed MCLAG list.
What to notice: treat LACP, ICL, STP, split-brain protection and multicast listener synchronization as separate state machines.

5. FortiAuthenticator EAP-TLS: RADIUS transport, mutual certificate trust, identity, and policy

Beginner foundation. 802.1X controls network admission. RADIUS transports EAP between the access device and FortiAuthenticator. EAP-TLS authenticates with certificates, so transport reachability and certificate trust are separate stages.

First prove the FortiGate/switch/AP is a recognized RADIUS client with the expected shared secret. Successful IP reachability only proves the network path; it does not prove the RADIUS client definition or EAP method.

FortiAuthenticator presents an EAP server certificate configured under Authentication > RADIUS Service > Certificates. The endpoint must trust the issuing CA and validate the expected server identity. If this direction of trust fails, the TLS exchange can stop before FortiAuthenticator ever evaluates the client certificate.

The client then presents its certificate. FortiAuthenticator must trust the issuing CA. Current FortiAuthenticator 8.0 examples show choosing the EAP Server Certificate and CA context and configuring the RADIUS service policy with Client Certificates (EAP-TLS). A valid client certificate can still fail when the wrong policy, realm or identity source matches.

Troubleshoot in order: RADIUS transport/client definition → server certificate → client certificate → RADIUS service policy/realm/identity → response/authorization. Do not jump to VLAN or firewall-policy troubleshooting until authentication is actually proven.

Healthy

  • NAD is a valid RADIUS client.
  • Endpoint trusts FortiAuthenticator server chain.
  • FortiAuthenticator trusts client issuer.
  • Correct EAP-TLS policy/realm matches.

Abnormal

  • Network path works but RADIUS secret/client definition is wrong.
  • Endpoint rejects server certificate.
  • FortiAuthenticator rejects client chain.
  • Wrong RADIUS policy matches first.

6. FortiManager policy-package installation: intent, validation, preview, diff, mappings, and target state

Beginner foundation. FortiManager stores centralized intent. A policy package in an ADOM is not automatically the running FortiGate configuration. Installation is a transaction with validation, generated changes and per-device results.

The first boundary is administrative: correct ADOM and correct policy package. The Install Wizard validates policy and objects, interfaces and installation preparation. Fortinet states that devices with validation errors are skipped, which means troubleshooting should stay in FortiManager until validation succeeds.

Install Preview shows the generated changes before the push. Policy Package Diff compares FortiManager policy/package state with the current device policy. These are not redundant: preview answers “what will FortiManager send?” while diff answers “how does managed intent differ from the target?”

Object mapping is an important failure mechanism. Fortinet documents that referenced objects need default or per-device mapping or installation fails. It also warns that some indirectly referenced objects can be installed and some unreferenced objects can be removed, especially during the first package install after adding/importing a device. That makes preview/diff essential change-control tools.

Create an ADOM revision for significant changes, run validation, review preview/diff, install, then examine per-device progress/errors and managed state. Do not troubleshoot a packet-flow issue on a policy that FortiManager never successfully installed.

Workflow

  1. Confirm ADOM and package.
  2. Select targets and validate.
  3. Review Install Preview.
  4. Review Policy Package Diff.
  5. Create revision when appropriate.
  6. Install and inspect progress/errors.
  7. Verify FortiGate managed/configuration state.

7. FortiAnalyzer: scope with FortiView, drill into session logs, then correlate with FortiGate runtime

Beginner foundation. FortiAnalyzer receives and indexes logs. FortiView is an analytical view over those logs; it is not a live packet capture. Historical investigation depends on selecting the right ADOM/device and time window.

Begin with scope: affected FortiGate or log source, incident time, source/user, destination, application, policy and action. A dashboard showing the current hour cannot answer what happened yesterday at 14:32.

FortiView is excellent for asking “what was dominant, unusual, denied, or consuming bandwidth?” because it aggregates indexed records by dimensions such as source, destination, application, policy and user. Once the relevant population is isolated, use the session-log drilldown to inspect the individual records behind the summary.

Fortinet notes that a dashboard can be unavailable when the required log type is not present or the relevant feature is disabled. Therefore an empty/gray widget may indicate missing telemetry rather than zero traffic.

FortiAnalyzer and FortiGate answer complementary questions. FortiAnalyzer is strong for historical context and trend/session reconstruction. FortiGate session/debug/sniffer tools are stronger for a live reproducible transaction. Correlate them rather than forcing one tool to answer every layer.

Workflow

  1. Select correct ADOM/device/time.
  2. Use FortiView to narrow source/user/app/policy.
  3. Open underlying session logs.
  4. Correlate policy/action/application/NAT fields.
  5. Reproduce on FortiGate and compare runtime evidence when needed.

8. FortiSwitch IGMP snooping in MCLAG: listener tables, querier versions, proxy, and ICL flood behavior

Beginner foundation. IGMP snooping lets a Layer-2 switch listen to host/router IGMP messages and build per-VLAN multicast listener state. Without it, multicast may be flooded more broadly. MCLAG adds a second switching node that must maintain compatible multicast state.

FortiSwitch creates a forwarding entry per VLAN and multicast group and adds/removes listener ports according to IGMP membership. FortiSwitchOS supports IGMPv1/v2/v3. The cited 7.6 guide allows a snooping querier using version 2 or 3 and documents version 2 as the default, which matters when a design expects IGMPv3 behavior.

For an MCLAG topology, Fortinet requires mclag-igmpsnooping-aware. It also requires IGMP proxy and defines different report/flood behavior between ICL trunks and ISL/FortiLink trunks. This is why “MCLAG is Up” is not sufficient multicast evidence.

A classic symptom is healthy unicast and LACP with missing, duplicated or over-flooded multicast. Start with the host membership, then the snooping table/querier, then MCLAG awareness and ICL/ISL behavior. Do not waste time changing LACP when the missing state is IGMP listener synchronization.

Fortinet also documents a hardware caveat: when IGMP or MLD snooping is enabled, unknown IPv4 and IPv6 multicast share the same flooding behavior because of hardware limitations. This can explain results that appear inconsistent with an IPv4-only assumption.

Workflow

  1. Verify receiver IGMP membership.
  2. Verify VLAN/group snooping state and querier.
  3. Verify MCLAG peer/ICL.
  4. Verify mclag-igmpsnooping-aware and IGMP proxy.
  5. Verify ICL versus ISL/FortiLink flood/report settings.
  6. Capture/test source-to-receiver multicast.
