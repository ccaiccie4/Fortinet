L01

FortiGate

FortiOS 8.0 ZTNA port abstraction: one listener, multiple protected applications

770 focused lesson words

Why the object split matters

In FortiOS 8.0, the ZTNA port is a separately managed external gateway listener rather than a listener that must be created inside each ZTNA server definition. It represents the interface, external address, TCP port and certificate that remote clients connect to. A ZTNA server then maps an application name and, when needed, a URL path to one or more internal real servers. This separation lets several protected applications share one HTTPS listener without collapsing their application identities into one backend.

Think of the configuration as three layers. The ZTNA port owns the client-facing socket and TLS identity. The ZTNA server/virtual-host mapping identifies the requested application and selects a real server. The ZTNA policy decides whether the endpoint and user are allowed to reach that application. The layers answer different questions; a healthy listener does not prove that a host/path maps correctly, and a valid mapping does not prove that posture policy will accept the endpoint.

Request and policy flow

  1. The remote client resolves an application FQDN to the FortiGate ZTNA port address and opens HTTPS to the configured external port.
  2. The listener presents its configured certificate. The IP/port must not collide with management access on the same interface. If the port is bound to a specific interface, FortiOS can use 0.0.0.0 so the gateway address follows the interface's primary/secondary address.
  3. The request's Host value selects a virtual host. In the 8.0 model, the Host field is important because several ZTNA server entries can reference the same port. A request to an unmatched host should not silently be treated as the intended application.
  4. For a web server in advanced mode, the path/API-gateway mapping selects a real server. Distinct paths can direct requests to different destinations; the real server can be an IP or an FQDN and can use a service port other than the default HTTPS port.
  5. The ZTNA policy applies the endpoint posture tag or tag group and optional user authentication. The full proxy policy can express more granular destination controls than the simplified firewall-policy form.
  6. Only after the request is mapped and authorized does the FortiGate proxy the session to the internal application.

Configuration shape

The GUI path is ZTNA > Ports for the listener and Policy & Objects > ZTNA > Servers & Portals for server mappings. A CLI listener is represented as an access-proxy VIP:

config firewall vip
    edit "ztna-shared"
        set type access-proxy
        set server-type https
        set extintf "wan1"
        set extip 203.0.113.10
        set extport 443
        set ssl-certificate "ztna-wildcard"
    next
end

A virtual-host object carries the host name and certificate, while a ZTNA web-proxy object references the VIP and host object. Its API-gateway entries then define path-to-real-server mappings. Keep host names unique and path matches unambiguous. The GUI's default path matching is substring-based; CLI configuration can use substring, wildcard or regular-expression matching. A broad substring can therefore capture more requests than intended.

What to verify—and what it proves

  • show firewall vip confirms the listener type, interface, address, port and certificate reference. It does not prove that a client can reach the socket through upstream routing or that the certificate is trusted.
  • show firewall access-proxy-virtual-host confirms the host and certificate mapping. Compare it with the actual Host header sent by the browser.
  • show ztna web-proxy confirms the VIP, virtual host, API-gateway paths and real-server objects. It does not prove the backend application is healthy.
  • diagnose firewall dynamic list helps verify synchronized dynamic ZTNA posture addresses/tags. It does not prove the policy references the intended tag or that the endpoint currently satisfies the EMS rule.
  • Test each FQDN and path separately. A successful TLS handshake proves only the listener/certificate stage; it is not evidence that the correct backend or policy was selected.

Dependencies and operational boundaries

FortiGate models with 2 GB RAM or less do not support this ZTNA application-gateway feature. The EMS connector must be healthy and posture tags synchronized before tag-based authorization can work. Starting in FortiOS 7.6.4, real-server certificate verification is enabled by default; explicitly verify the backend certificate chain and name instead of treating a successful client-side TLS session as end-to-end TLS proof. In HA, user information and TLS sessions are synchronized so the new primary can continue proxy sessions after failover.

Field scenario: two application FQDNs resolve to the same FortiGate address and port, but one reaches the wrong internal service. Do not create another VIP first. Confirm the Host header, virtual-host object, path rule and real-server address in that order. If the mapping is correct but access is denied, move to EMS tag synchronization and ZTNA policy evidence. This keeps listener faults, L7 mapping faults and authorization faults separate.

Primary Fortinet source: https://docs.fortinet.com/document/fortigate/8.0.0/administration-guide/194961/basic-ztna-configuration

L02

FortiManager

Multi-device install preview through the FortiManager JSON-RPC API

577 focused lesson words

Preview is a control-plane transaction, not an installation

FortiManager 7.6.0 adds an API enhancement that lets an automation client request an install preview for several managed devices in one JSON-RPC operation. The useful distinction is between submitting a preview job, retrieving its per-device output and installing the configuration. The preview endpoint does not push the candidate configuration to the FortiGate. It produces review evidence that can be consumed by a change-management pipeline before a separate install request is authorized.

The request is scoped to an ADOM and a list of target device/VDOM pairs. The example uses numeric oid and vdom_oid identifiers. These are FortiManager database identifiers, not device serial numbers or human-readable VDOM names. A stale or copied OID can direct the request at the wrong managed object even when the JSON syntax is valid.

Request, task and result flow

  1. Authenticate to the FortiManager JSON-RPC API and retain the session value for subsequent calls.
  2. Submit an exec request to /securityconsole/install/preview. The data includes the ADOM and a scope array. Each array item identifies one device OID and one VDOM OID.
  3. FortiManager returns a status object and a task identifier. A status.code of zero with a task number means the request was accepted; it is not the preview text and it is not proof of an install.
  4. Call /securityconsole/preview/result with the same ADOM and scope to retrieve the per-device preview result. The documented response identifies devices by name and OID and includes the result text for each.
  5. Review the preview, resolve validation warnings and compare it with the policy-package diff where appropriate. Only a separate install operation changes the managed FortiGate configuration.

Request shape

{
  "method": "exec",
  "params": [{
    "url": "/securityconsole/install/preview",
    "data": {
      "adom": 3,
      "scope": [
        {"oid": 185, "vdom_oid": 3},
        {"oid": 197, "vdom_oid": 3}
      ]
    }
  }],
  "session": "<authenticated-session>"
}

The submission response contains a task identifier. The result request uses the result URL:

{
  "method": "exec",
  "params": [{
    "url": "/securityconsole/preview/result",
    "data": {
      "adom": 3,
      "scope": [
        {"oid": 185, "vdom_oid": 3},
        {"oid": 197, "vdom_oid": 3}
      ]
    }
  }],
  "session": "<authenticated-session>"
}

Evidence interpretation

  • Submission response: status code zero and a task ID prove that FortiManager accepted the preview request. They do not prove every device produced a preview.
  • Result response: the per-device name/OID/result list shows which target produced content. The documented example includes No preview result; treat that as missing preview output to investigate, not as an implicit clean install.
  • GUI Install Preview: the wizard can display several devices and download preview details. It is a useful cross-check for API automation.
  • Policy Package Diff: this compares package policy state with device state. It is not interchangeable with the install preview, which describes the candidate installation operation.

Operational design and failure isolation

Build the automation around an explicit target manifest containing ADOM, device OID and VDOM OID. Resolve those identifiers from the current FortiManager database rather than hard-coding them across device replacement or ADOM migration. Preserve the API session for the result call and log the submission task, scope and per-device result. If the task is accepted but one target has no preview, verify that target's OID/VDOM association and the ADOM before changing the policy package.

Use preview as a gate in a pipeline: submit, retrieve, parse every device result, fail closed on missing or invalid output, attach the text to the change record, obtain approval, then issue the separate installation request. This prevents a successful API HTTP/JSON response from being mistaken for successful configuration deployment.

Primary Fortinet source: https://docs.fortinet.com/document/fortimanager/7.6.0/new-features/301818/api-enhancement-to-support-install-preview-in-the-response-for-multiple-devices

L03

FortiAnalyzer

FortiAI alert triage agent: evidence enrichment before analyst action

655 focused lesson words

What the triage agent adds

FortiAnalyzer 8.0's FortiAI Triage Agent is an investigation workflow attached to an alert record. It reduces the manual work of opening several panes and correlating logs, endpoint context and related alerts, but it does not make the alert's evidence self-validating. The agent exposes a sequence of reasoning steps and supporting evidence so an analyst can inspect how the assessment was formed before choosing a response.

Open Incidents & Alerts > Alerts, open an alert's details and select the Triage Agent tab. A valid FortiAI license and suitable administrator permissions are required. The result is presented as step panes while the agent runs; after completion, the panes can be revisited and the summary exported as a PDF.

The evidence sequence

  1. Get Alert Details: the agent reviews the alert type and details, performs a false-positive assessment, and forms an initial summary and hypotheses. This is an initial assessment, not a verdict.
  2. Get Triggering Logs: it examines the logs that triggered the alert. These logs provide the underlying event context. If the log source is incomplete, delayed or incorrectly parsed, the agent's reasoning inherits that limitation.
  3. Get Entity Details: it obtains endpoint risk information from the Asset Identity Center. Vulnerability severity, endpoint risk score and importance can change the triage assessment. This step depends on correct identity association; an IP address that has been reassigned can lead to misleading context.
  4. Get Alert Context: it looks for other alerts involving the same endpoints. This can expose a sequence of related activity, but a shared endpoint alone does not prove that two alerts have the same root cause.
  5. Triage Analysis: the agent reevaluates its hypotheses as evidence arrives, summarizes the findings and presents supporting evidence with a confidence level. The analyst should inspect the evidence, not use the confidence value as a substitute for it.
  6. Next Steps: it proposes actions such as creating an incident, adding the alert to an existing incident or suppressing further alerts. Configured connectors can expose actions such as endpoint quarantine, indicator enrichment or indicator blocking.

Analysis and execution are separate

The agent's recommendation and the connector's ability to execute it are different states. If a connector is missing or incomplete, the Next Steps pane displays a tooltip indicating that configuration is missing. A recommendation to quarantine an endpoint does not mean the endpoint has already been quarantined. The analyst must select the action and confirm that the relevant connector is configured and authorized.

Use the exported PDF as a portable investigation record, but retain the original alert, triggering logs and connector/action audit trail as the authoritative evidence. The PDF is a summary of the agent's output, not a replacement for the raw log records or the endpoint's current state.

Verification and troubleshooting

  • Confirm the FortiAI license and administrator role before troubleshooting an empty or unavailable Triage Agent tab.
  • Inspect the triggering-log pane. If the alert is not supported by the expected log events, investigate ingestion, parsing, time range and source-device health before trusting the assessment.
  • Inspect the Asset Identity Center entity details. Confirm that the endpoint identity, user, IP and risk data refer to the same current asset.
  • Review related alerts and their timestamps. A common endpoint is a correlation clue, not proof of causation.
  • Check the connector tooltip and connector configuration before treating a proposed response action as executable.

Operational scenario

An alert is raised for suspicious outbound traffic and the agent recommends isolating the endpoint. The triggering logs show the destination and session, Asset Identity Center shows a high-risk endpoint, and the related-alert pane shows two earlier suspicious events. That is a stronger basis for action than the alert title alone. If the quarantine connector is absent, the investigation can still be useful, but isolation has not occurred. Configure and test the connector, validate the endpoint identity, then have an authorized analyst select the response action. This preserves the human decision boundary between AI-assisted triage and enforcement.

Primary Fortinet source: https://docs.fortinet.com/document/fortianalyzer/8.0.0/administration-guide/186618/alert-triage-agent

L04

FortiSwitch

FortiSwitch packet mirroring: SPAN, RSPAN and ERSPAN are different transport paths

603 focused lesson words

Choose the mirror mode by collector location

FortiSwitch port mirroring copies selected ingress or egress packets for external analysis without changing the original forwarding decision. The important design choice is where the capture device sits. SPAN sends an unencapsulated copy to another port on the same switch. RSPAN transports copies through a remote Layer-2 path using VLAN 4092 toward the FortiGate. ERSPAN encapsulates the copy in Ethernet, IPv4 and GRE and sends it to a remote IPv4 collector. These modes are not interchangeable and have different reachability and capacity requirements.

Local SPAN

In a FortiLink-managed switch, a mirror session is configured under the managed-switch object. The session has a required destination port and one or more source ingress and/or egress ports. The original packet still follows the normal switching pipeline; the analyzer receives a copy. The destination must not also be a source, and a destination that is a trunk member has additional restrictions.

config switch-controller managed-switch
    edit <switch-serial>
        config mirror
            edit "capture"
                set status active
                set dst port1
                set src-ingress port2 port3
                set src-egress port4
            next
        end
    next
end

switching-packet controls whether the destination port also participates in normal switching. A dedicated analyzer port is easier to reason about; enabling switching on a shared destination can mix mirrored copies with ordinary traffic.

RSPAN and ERSPAN

RSPAN encapsulates mirrored traffic in VLAN 4092. In FortiLink mode, the controller automatically determines the uplink/destination ports, often an ISL toward the FortiGate. The FortiGate can capture on the RSPAN VLAN and save a PCAP. A capture on VLAN 4092 proves the copy reached the FortiGate; it does not prove that the copy was forwarded onward to a separate analyzer host.

ERSPAN adds Ethernet, IPv4 and GRE headers and sends the copy to a specified IPv4 collector. The collector must be reachable by IPv4 ICMP from the FortiSwitch; a FortiGate firewall policy may be required. If no collector IP is specified, traffic is not mirrored. The FortiLink guide also warns that ERSPAN cannot be used with SPAN or RSPAN. For the managed 7.6.5 workflow, plan for one RSPAN or one ERSPAN session and verify model support before designing multiple capture points.

RSPAN/ERSPAN use a controller-configured traffic policer to limit mirrored traffic. That protects the network from an unbounded copy stream, but a high-volume source can be rate-limited before it reaches the collector. Mirroring is therefore evidence collection, not a lossless packet archive guarantee.

Verification and failure boundaries

  • diagnose switch-controller switch-info mirror status on the FortiGate shows automatically selected FortiLink mirror destinations. Check whether an ISL has been selected before adding its ports to a source list.
  • For RSPAN, capture on the FortiGate's RSPAN VLAN. If packets are present there but absent at the analyzer, the fault is downstream of the switch mirror engine: VLAN handoff, destination port, switching state or collector attachment.
  • For ERSPAN, verify the collector IP is specified and reachable by IPv4 ping. Check the FortiGate policy and the collector's GRE/IP capture interface.
  • Inspect the configured mirror source/destination and policer. A missing packet at the analyzer does not prove the original packet was dropped; the mirror copy may have been filtered or rate-limited.

Operational scenario

A packet capture on the FortiGate's VLAN 4092 shows the expected RSPAN traffic, but the recording server sees nothing. Do not change the source-port list first: the copy has already reached the FortiGate. Trace the VLAN 4092 destination/forwarding path to the recording port, check whether the destination is configured as intended, and verify that normal switching is enabled where required. For a remote routed collector, use ERSPAN and test the IPv4/GRE path instead of assuming the RSPAN VLAN is routable.

Primary Fortinet source: https://docs.fortinet.com/document/fortiswitch/7.6.5/fortilink-guide/173278/configuring-fortiswitch-port-mirroring

FortiAP/Wireless

Bonjour profiles and micro-location: controlled mDNS service discovery across VLANs

527 focused lesson words

Bonjour is service discovery, not ordinary unicast routing

Bonjour uses multicast DNS (mDNS) and DNS-based service discovery so clients can find services such as printers, AirPlay receivers and casting devices without a conventional DNS server entry. In a segmented enterprise WLAN, the multicast discovery packets normally remain within their Layer-2/VLAN scope. A Bonjour profile lets the FortiAP WLAN system selectively advertise chosen services from one VLAN into another. It is not a general-purpose bridge between VLANs: the profile's source VLAN, destination VLAN and service list define what is exposed.

Profile objects and precedence

A Bonjour profile contains a policy list. Each policy entry identifies the source VLAN with from-vlan, the destination VLAN with to-vlan, and the service types to advertise. The profile can be applied to a FortiAP profile or directly to a device. If both levels contain a Bonjour profile, the device-level configuration takes precedence. That precedence is important during troubleshooting: editing the AP profile will not change behavior on an AP that has a device-level override.

config wireless-controller bonjour-profile
    edit "floor1-services"
        set micro-location enable
        config policy-list
            edit 1
                set from-vlan "100"
                set to-vlan "200"
                set services airplay printers chromecast
            next
        end
    next
end

config wireless-controller wtp-profile
    edit "FAP231G-default"
        set bonjour-profile "floor1-services"
    next
end

Micro-location and gateway election

Micro-location confines mDNS traffic to a location defined by the FortiAP group configured on the FortiGate. Two AP groups can represent two floors or buildings. Even if the SSID and VLAN identifiers are reused, the micro-location boundary prevents service advertisements originating in one AP group from being exposed in the other. This is useful when a printer or screen should be discoverable only in the room or floor where it is installed.

When multiple APs use the same Bonjour profile, they run an election. The AP with the highest base MAC address becomes the primary default gateway; other APs become backup gateways. In the FortiAP diagnostic output, oper indicates the active gateway, cap indicates a backup, and additional APs can be in hold. The election is a control-plane role selection for Bonjour handling, not the WLAN client association leader.

Verification

  • On the FortiGate, diagnose wireless-controller wlac -c bjprof helps confirm the controller's Bonjour profile and AP association.
  • On the AP, cw_diag -c bonjour shows configured VLAN mappings, service bitmaps and gateway election state. Check the actual oper AP rather than assuming the first AP in the group is primary.
  • bjallow provides service-allowance information. Use it with a client test that queries the intended service from the destination VLAN.
  • A correct VLAN mapping does not prove that a service is actually advertising or that a client can reach the service's unicast IP/port after discovery.

Operational scenario

Users on two floors can see each other's AirPlay receivers even though the service is intended to remain local. Check whether the APs are placed into distinct FortiAP groups and whether micro-location is enabled. Then inspect the device-level Bonjour profile for an override, confirm the source/destination VLAN pair and service list, and inspect the gateway election. Do not solve an mDNS scoping problem by changing client roaming or radio settings; those controls affect association and airtime, not the service-discovery boundary.

Primary Fortinet source: https://docs.fortinet.com/document/fortiap/8.0.0/fortiwifi-and-fortiap-configuration-guide/876617/connectivity-profiles-entry

FortiNAC

FortiNAC 9.4 RADIUS Activity: use failed-auth exports to isolate endpoint versus server faults

557 focused lesson words

Activity is an evidence surface over the RADIUS transaction

FortiNAC 9.4 adds a RADIUS Activity view that gives operators a concise view of 802.1X and MAC-authentication-bypass pass/fail outcomes and lets them export failed-authentication records. Find it under Network > RADIUS > Activity. It is particularly useful when a large access network produces many authentication attempts and an administrator needs to isolate a failure window without manually correlating every switch/AP log.

The view does not replace the RADIUS protocol or the endpoint supplicant. The transaction still begins when a switch or AP sends an Access-Request, FortiNAC processes the request and any configured directory/certificate lookup, and the authenticator receives an Access-Accept or Access-Reject. Activity is the operational record of those outcomes. It can show that a request failed, but the reason may still be on the endpoint, the directory, the EAP method, the NAS configuration or the FortiNAC policy.

Use the failure export as a correlation key

Enable Activity Monitoring in the RADIUS settings and use the Activity view to filter the affected period and authentication type. Export failed authentications before making changes. Compare the event time, endpoint identity, authentication method and reject outcome with the switch/AP RADIUS log, the Windows supplicant event log and the directory-side evidence. A burst of rejects affecting one endpoint OS build is a different pattern from rejects across every endpoint behind one NAS or one RADIUS client.

Recent scenario: Windows KB5127648 and cached PEAP credentials

Fortinet Community documented a Windows endpoint issue after update KB5127648, released on 13 October 2026. Windows hosts using 802.1X PEAP-MS-CHAPv2 with cached logon credentials can fail and report Event ID 12014, OneX Held State Timeout. The article states that the issue also affects other AD-integrated RADIUS servers, so it is not evidence of a FortiNAC defect. It affects cached username/password SSO; manually entering credentials succeeds, and client-certificate authentication is unaffected.

The documented cause is a Windows change to the default behavior when the BlockNTLMv1SSO registry value is not set. The article describes setting the value to Audit mode (0) to restore the previous behavior, or uninstalling the update as an alternative. Any endpoint registry change should follow the organization's Windows security/change-control process; the important network-engineering lesson is to establish that the failure follows the supplicant's cached-credential path before changing the NAC policy.

Registry:
HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Lsa\Msv1_0

Value: BlockNTLMv1SSO
Type: REG_DWORD
Audit mode: 0

Diagnostic boundaries

  • If only Windows clients with cached PEAP credentials fail after the update, test manual credential entry and inspect Event ID 12014. This points toward the supplicant/OS path.
  • If all clients behind one switch fail, compare NAS source IP, shared secret, RADIUS reachability and server response before changing endpoint policy.
  • If EAP-TLS clients succeed while PEAP-MS-CHAPv2 cached credentials fail, the evidence argues against a general RADIUS listener outage.
  • Activity pass/fail counts prove that FortiNAC observed authentication outcomes; they do not independently prove why a reject occurred.

Operational use

During an outage, export the failed events, select one affected endpoint and reproduce with cached versus manually entered credentials. Correlate the timestamp with Windows update inventory and Event ID 12014. Only after that comparison should you decide whether to change the endpoint setting, investigate Winbind/directory authentication or adjust FortiNAC RADIUS configuration. This avoids a common mistake: changing a shared secret or policy because a client-side authentication regression first became visible as a RADIUS reject.

Primary Fortinet source: https://docs.fortinet.com/document/fortinac/9.4.0/administration-guide/270902/activity

FortiNAC-F

FortiNAC-F Mist Service Connector: site polling, inventory creation and controlled migration

637 focused lesson words

What the Service Connector owns

FortiNAC-F's cloud Service Connector uses the controller's Device Management API to discover managed sites and build inventory objects. It is not the RADIUS authentication path itself. The connector creates a site-level virtual-controller model and associated AP inventory when it polls the cloud service. FortiNAC then uses RADIUS events and L2/L3 polling to learn where endpoints connect, while access control is enforced through RADIUS VLAN assignment and disconnect/CoA behavior.

Configure the connector under Network > Service Connectors. It needs the correct regional API domain, port 443, organization ID and a full-permission API token. The guide's default API domain is https://api.mist.com, but regional domains must match the organization. Use Test Connection before selecting sites; a successful test is required to read the managed-site list.

Discovery transaction

  1. Create the connector with its name, API domain, port, organization ID and token.
  2. Test the connection. This proves the API endpoint and credentials are accepted; it does not yet prove that inventory has been created.
  3. Select one or more managed sites. On the next Service Connector poll, FortiNAC creates a virtual controller for each site and adds its associated APs to the chosen inventory container.
  4. For switch discovery, enable the Discover Switches option where supported and provide both SNMP and CLI credentials. The guide states that both are required for switch discovery/management. Supplying only SNMP credentials can leave the switch absent even though AP discovery works.
  5. Use a manual Poll during validation, then tune automatic polling. The guide notes a cloud API limit of 5,000 calls per hour; its defaults are a 60-minute L2 poll and one Service Connector poll per day. Increasing poll frequency without considering the other discovery tasks can consume the API budget.

Visibility and enforcement are separate paths

For wired devices, endpoint notification arrives through RADIUS; MAC-table, IP-table and VLAN reads use SNMP/CLI. For wireless devices, RADIUS reports endpoint authentication while L2/L3/VLAN/SSID information is read through the cloud API. Dynamic VLAN assignment is performed through RADIUS. RADIUS authentication normally uses UDP 1812, accounting uses UDP 1813, and Disconnect/CoA uses UDP 3799. The RADIUS shared secret must match on the access device, RADIUS server and FortiNAC model/RADIUS settings.

In HA, use the primary and secondary FortiNAC server port addresses as RADIUS servers rather than a shared VIP, as specified in the integration guide. The guide also warns that a mandatory Event-Timestamp setting can cause CoA packets to be discarded because FortiNAC does not include that attribute in its CoA messages.

Migration and version caveats

Legacy Mist integrations built with CloudAPITool are not automatically migrated to the new Service Connector. Transition one site at a time: remove the existing APs for that site from FortiNAC, configure the new connector and select the site, then poll. The new connector creates APs as pingable devices and creates a virtual-controller model. The guide lists basic support from FortiNAC-F 7.4.1+/7.6.0+; managed switches require later versions (7.4.2+/7.6.3+) for the switch-discovery options.

Verification and safe rollout

  • Use Test Connection to isolate API credentials from site inventory creation.
  • Use manual Poll and verify the virtual controller and AP objects appear in the intended container.
  • For missing switches, verify version support and both SNMP and CLI credentials.
  • Confirm RADIUS source IP is the AP/switch address, not an unexpected NAT address; align the shared secret on all participants.
  • Validate isolation VLAN DHCP and portal access before enabling enforcement. Start with a small number of switch ports or a test SSID; a rogue MAC on an enforced port can be isolated.

Field scenario: the connector tests successfully but the AP list remains empty. Do not rotate the token immediately. Confirm that a managed site is selected and a poll has run; then verify the API domain/organization, connector logs and inventory container. If APs appear but switches do not, move to the separate SNMP-plus-CLI prerequisite.

FortiAuthenticator

EAP-TEAP: machine and user identity must both succeed in one RADIUS session

620 focused lesson words

What TEAP changes

FortiAuthenticator 8.0.2 adds RADIUS support for EAP-TEAP. TEAP chains machine authentication and user authentication into a single authentication session. The session succeeds only when both the machine and user authentications succeed. This is materially different from treating a successful machine certificate as sufficient to admit the endpoint, or from requiring only a user password. It lets the network make an admission decision that depends on both the device's managed identity and the person signing in.

FortiAuthenticator supports EAP-MSCHAPv2 or EAP-TLS for the machine and user authentications. The exact combination should match the endpoint supplicant, certificate infrastructure and directory design. EAP-TLS requires the appropriate client/server certificate trust; EAP-MSCHAPv2 depends on the configured identity source and credential validation path. Do not assume that a working user method proves the machine phase is configured correctly.

Configuration objects and relationships

FortiAuthenticator 8.0.2 reorganizes RADIUS authentication policy configuration around Auth Profiles. The previous Authentication type, Identity sources and Authentication factors tabs have been moved into profiles. A RADIUS policy now has an Authentication Profiles tab where the administrator specifies the authentication type and profile to use. RADIUS clients can also be grouped and selected as a unit, which helps keep policy scope manageable when there are many APs, switches or VPN gateways.

A practical configuration sequence is:

  1. Create an Auth Profile for the intended TEAP flow. Define the supported machine/user methods and the identity sources/factors needed for each stage.
  2. Configure the RADIUS client or client group. Confirm that the NAS shared secret and source address match the device configuration.
  3. Create or edit the RADIUS policy and select the intended Authentication Profile.
  4. Ensure the endpoint supplicant is configured for TEAP and trusts the RADIUS server certificate. If using EAP-TLS for either phase, validate the certificate chain, expiry and identity mapping.
  5. Test machine authentication and user authentication separately, then test the complete chained session.

Transaction and acceptance logic

The endpoint's supplicant negotiates the outer TEAP method with the authenticator, which forwards EAP/RADIUS to FortiAuthenticator. Inside the protected TEAP exchange, the machine authentication is performed and then the user authentication is performed. FortiAuthenticator evaluates both results as part of one session. A machine success followed by a user failure is still an unsuccessful TEAP transaction; the RADIUS Access-Accept should not be inferred from the first phase alone.

Use this AND condition when designing policy: machine success AND user success = session success. A failure in either stage should be investigated at that stage rather than weakening the whole policy to make the endpoint connect.

Evidence and troubleshooting

  • Inspect the RADIUS transaction and determine which phase failed. A generic Access-Reject does not identify whether the machine or user phase was responsible.
  • Verify the RADIUS policy's selected Auth Profile. A correctly configured profile that is not bound to the matching policy is inert.
  • Check client-group membership and policy selection. A request from an unexpected NAS source can match a different policy or fail client validation.
  • For EAP-TLS, verify certificate chain, EKU, identity binding and clock/expiry. A certificate presented by the machine does not automatically validate the user's certificate or identity.
  • For EAP-MSCHAPv2, validate the identity-source and directory path used by the selected profile. A successful LDAP bind or user login elsewhere is not proof that the TEAP machine/user phase is configured correctly.

Operational scenario

A laptop connects at the machine stage but is rejected after the user signs in. The correct response is not to disable machine authentication. Inspect the TEAP exchange and identify whether the user phase failed due to the selected inner method, identity source, profile binding or certificate/credential issue. The network should admit the endpoint only when both identities meet the intended policy. This is the key operational value of TEAP chaining.

FortiPAM

FortiPAM launcher privilege: choose the Windows token for the app and its init/clean commands

562 focused lesson words

Process identity is part of the secret-launch design

FortiPAM 1.9.0 adds a Privilege option to secret launchers. It controls whether FortiClient starts the target process under the signed-in Windows user or under the local SYSTEM account. It can also select a different identity for the launcher's initialization and cleanup commands. This matters because a privileged application and its setup script do not always need the same Windows token. For example, a database management tool may need SYSTEM privileges while a script that reads the user's profile must run as that user.

The option is configured under Secret Settings > Launchers. It is not a change to the target server credential stored in the secret. It controls the local endpoint process identity used by FortiClient to start the application and run the init/clean commands.

The four supported combinations

  • Launch secret and run init/clean under USER: the default. Both the application and its setup/cleanup commands use the signed-in user's context.
  • Launch secret under SYSTEM: the application is elevated to the SYSTEM context while init/clean commands remain under USER.
  • Run init/clean command under SYSTEM: setup/cleanup commands use SYSTEM while the target application runs as USER.
  • Launch secret and run init/clean command under SYSTEM: both run under SYSTEM.

These combinations are independent controls. Choosing SYSTEM for the application does not automatically mean the init command must also run as SYSTEM. Likewise, a SYSTEM init script does not require the target process to run as SYSTEM.

Version compatibility is decisive

The Privilege flag is supported only by FortiClient 8.0 and later. When FortiClient 7.x is used with FortiPAM 1.9.0 or later, the endpoint follows legacy hardcoded behavior: SSMS.exe is started by SYSTEM and other processes require a user. A launcher configured for a non-default privilege combination can therefore behave differently on endpoints that have not been upgraded. Treat the FortiClient version as a feature dependency, not a minor detail.

Verification

Fortinet's documented check is Windows Task Manager > Details. Add or inspect the User name column for the launched process. This shows whether the process is running as SYSTEM or as the interactive user. It does not prove that the application can reach the target server or that the secret credential is correct; it proves the local process token.

Test the three execution stages independently:

  1. Run the init command and verify its expected local effects under the selected identity.
  2. Launch the application and inspect its process owner in Task Manager.
  3. End the session and confirm the cleanup command runs with the expected privileges and removes only the intended temporary state.

For troubleshooting, compare the process identity with the resource the application needs. User context provides the user's profile, HKCU settings and per-user mappings; SYSTEM has local machine privileges but does not automatically inherit the user's desktop, mapped drives or user-specific environment. A process that starts successfully can still fail because it lacks the correct profile or remote resource access.

Operational scenario

A launcher starts SSMS correctly on one workstation but a different administrative client fails with an access-denied error during startup. The first comparison should be the FortiClient version and actual process owner, not the remote secret password. If the application requires SYSTEM but an initialization script needs the user's profile, select the split combination that runs the application as SYSTEM and init/clean as USER. Verify both identities rather than assuming the launcher setting was honored.

Primary Fortinet source: https://docs.fortinet.com/document/fortipam/1.9.0/administration-guide/649950/creating-a-launcher

FortiSIEM

FortiSIEM Linux Agent: separate event transport from systemd process supervision

517 focused lesson words

Agent data path

The FortiSIEM Linux Agent communicates outbound over HTTPS with the Supervisor and Collectors. It registers to the Supervisor and periodically receives monitoring-template updates. Event data is forwarded to the Collectors. The agent process, its systemd service and the network channels are separate parts of the design. A host can have working IP connectivity while the agent process is stopped; an agent process can be running while its Supervisor registration or Collector event path is unhealthy.

Before installation or reinstallation, the Linux Agent guide requires rsyslog to be running and lists OS-specific packages such as audit, logrotate and related utilities. The guide documents service operations including service fortisiem-linux-agent status, start and stop, and systemctl restart fortisiem-linux-agent after changing the agent's IP address.

Recent failure: SIGSEGV with no automatic restart

A Fortinet Community technical tip dated 20 October 2026 describes an agent that terminates with SIGSEGV (signal 11), producing messages such as phLinuxAgent: segfault and fortisiem-linux-agent.service: main process exited, status=11/SEGV. The article distinguishes the crash itself from the reason the service remains disconnected: a systemd unit with RemainAfterExit=yes can leave the service considered active after the main process exits, preventing the expected restart behavior.

The article's remediation is to change the unit's RemainAfterExit value to no, reload systemd and restart the service:

[Service]
RemainAfterExit=no

systemctl daemon-reload
systemctl restart fortisiem-linux-agent.service

This corrects the service-state behavior described in the article; it does not explain why the agent segfaulted. Treat the crash root cause as a separate investigation and preserve the crash logs for TAC if the process continues to fail.

Evidence that separates the layers

  • systemctl status fortisiem-linux-agent.service shows systemd's view of the unit. A unit reported active is not sufficient proof that the agent process is alive when RemainAfterExit semantics are involved.
  • journalctl -u fortisiem-linux-agent.service and kernel logs show process exit, signal and restart events. A SIGSEGV proves abnormal process termination, not a network failure.
  • Check the service unit for RemainAfterExit and the configured restart behavior. Do not assume that restarting the service once has fixed the crash cause.
  • Confirm the agent registers with the Supervisor and receives its monitoring template. Then confirm events arrive at the intended Collector. Registration and event forwarding are different success criteria.
  • Verify rsyslog and required packages before blaming the FortiSIEM backend for a local agent failure.

Recovery sequence

Preserve the crash timestamp and logs. Check the service unit, correct the RemainAfterExit setting as described, run systemctl daemon-reload, and restart the service. Confirm a live process, successful Supervisor registration and fresh Collector events. If the process crashes again, investigate the SIGSEGV separately rather than repeatedly restarting it. A service restart restores supervision; it does not repair memory corruption or a defective binary.

Operational scenario

A Linux server disappears from FortiSIEM while other hosts continue reporting. The agent log shows signal 11 and systemd says the unit is active. Start on the host: inspect the process and unit state, then the crash log. Do not begin by changing Collector routing or rebuilding the Supervisor. Once the process is stable, test the outbound HTTPS registration/template path and event delivery independently.

FortiSASE

FortiSASE pre-logon connectivity: get a new Windows device to Active Directory before first sign-in

557 focused lesson words

The first domain login is a different problem from the user's SASE session

A newly imaged, domain-joined Windows laptop may be off-network and have no cached domain credentials. Its first interactive login requires real-time connectivity to an Active Directory domain controller. FortiSASE Secure Private Access supports a pre-logon tunnel so the machine can reach AD before the user has signed in. This is a machine-identity connection, not the user's normal SAML or OAuth tunnel.

Pre-logon state sequence

  1. Windows boots and FortiClient starts using a preconfigured pre-logon profile.
  2. The machine authenticates to the gateway with its machine certificate and establishes the pre-logon tunnel.
  3. Through that tunnel, the endpoint can reach the AD server required for domain authentication.
  4. The user signs in to Windows with AD credentials. The pre-logon tunnel then disconnects.
  5. After login, the endpoint connects to FortiSASE automatically or manually according to its endpoint-management configuration.
  6. On later logins, the device can use locally cached Windows AD credentials rather than requiring the pre-logon path every time.

The Windows device must be staged before shipment with a supported FortiClient installer/profile and the machine certificates required for pre-logon authentication. If the certificate is absent, expired, untrusted or mapped to the wrong machine, the endpoint cannot establish the tunnel needed to reach AD. If the tunnel comes up but the domain controller is not reachable through the allowed routes, the user still cannot complete the first login.

Do not conflate machine pre-logon with user autoconnect

Pre-logon solves initial machine-to-AD reachability. Autoconnect tunnel connectivity solves the user's later connection to a Security PoP. FortiSASE can remember credentials and maintain an always-up tunnel, but the supported authentication combinations have limits. OAuth tunnel support is limited to Entra ID as the IdP, Windows endpoints and SSL-based tunnels. With SAML, the remember-password feature relies on persistent sessions supported by the IdP. If the IdP does not support persistent sessions, FortiClient cannot save the SAML password and the user must authenticate to the IdP for each tunnel attempt.

That means a machine certificate can make the first Windows domain login possible, while a separate IdP persistence limitation can still cause a user tunnel to prompt repeatedly. They are different authentication states and should be diagnosed independently.

Verification points

  • Before user sign-in, verify the pre-logon tunnel is established and the machine certificate is valid and trusted.
  • From the pre-logon state, test DNS and reachability to the domain controllers and services required for domain login. A tunnel-up indicator alone does not prove AD is reachable.
  • After the user signs in, confirm the pre-logon tunnel disconnects and the configured user tunnel starts. Do not expect both tunnels to remain as one continuous session.
  • For subsequent logins, test cached domain credentials. If the first login works but the user tunnel repeatedly prompts, inspect OAuth/SAML and IdP persistent-session support rather than the machine certificate.

Operational deployment

Stage the endpoint profile, supported FortiClient version and machine certificate before shipping the laptop. Test a device that has never logged on to the domain while it is genuinely off-network. Confirm the pre-logon tunnel can reach AD, perform the first login, observe tunnel teardown, then validate the user tunnel and later cached login. This sequence catches a common deployment gap: testing the user tunnel on a laptop that already has cached credentials does not prove that a brand-new device can complete its first domain sign-in.

Primary Fortinet source: https://docs.fortinet.com/document/fortisase/latest/secure-private-access-architecture-guide/269831/additional-configurations

Secure SD-WAN

Fabric Overlay Orchestrator with IPAM: allocate hub and spoke addresses before BGP forms

602 focused lesson words

Why overlay IPAM matters

FortiOS 8.0 extends the Fabric Overlay Orchestrator so it can use FortiGate IPAM to allocate the hub/spoke overlay network and spoke LAN addressing scheme, including loopback addresses. Instead of manually selecting tunnel and loopback addresses on every spoke, the Security Fabric root/hub owns the IPAM pools and the orchestrator references those pools when it creates the overlay. This reduces duplicate-address risk and makes the allocation source visible as a named IPAM firewall address.

The feature still builds a self-orchestrated overlay: the Fabric Overlay Orchestrator creates IPsec and BGP configuration for the root FortiGate as hub and downstream first-level FortiGates as spokes. It does not replace SD-WAN rules or prove that a selected path meets performance SLA. Address allocation is an earlier dependency in the tunnel/routing chain.

Objects and allocation flow

Enable IPAM on the root FortiGate and enable Require subnet size match. The orchestrator then references an IPAM-managed firewall address for the hub loopback pool and an IPAM address for each overlay tunnel subnet. FortiOS 8.0 adds the following references:

config system fabric-vpn
    set loopback-address-block-ipam "fabric_vpn_default_loopback"
    config overlays
        edit "port3"
            set overlay-tunnel-block-ipam "fabric_vpn_port3_1"
        next
    end
end

The assigned interface addresses are visible as ordinary FortiGate interface configuration, but their allocation source is the IPAM object. In the documented example, the root hub and two spokes receive unique loopback addresses from a shared loopback pool, while the hub and spokes receive tunnel addresses from the overlay pool. The root also has a tunnel-side address and remote-IP relationship. This is the allocation that the later IPsec and BGP configuration consumes.

The interface-level ipam-conflicts option controls whether an interface is ignored when IPAM conflict detection runs. enable means ignore this interface for conflict detection; disable means do not ignore it. Do not enable the ignore behavior merely to silence a genuine duplicate-address problem without understanding why the interface is excluded.

Prerequisites and scope

  • IPAM must be enabled on the root/hub and the correct address pools must exist before the orchestrator uses them.
  • The Security Fabric topology must be correct: the root FortiGate is the hub and the downstream first-level FortiGates are the spokes.
  • The Fabric Overlay Orchestrator described in the FortiGate guide does not work when VDOM mode is enabled. Check this before troubleshooting a missing menu or incomplete generated configuration.
  • Enable subnet-size matching so an IPAM pool with an incompatible prefix is not silently used for a different interface requirement.
  • The feature allocates addresses; it does not make an unreachable underlay, invalid IKE peer or broken BGP policy healthy.

Verification sequence

  1. On the root, inspect show system fabric-vpn and confirm the loopback and overlay pool references.
  2. Inspect each IPAM firewall address object with show firewall address <pool-name>. Confirm the subnet is the intended allocation range.
  3. Inspect each hub/spoke loopback and tunnel with show system interface <interface-name>. Confirm the assigned address, remote IP and parent interface.
  4. Open Network > IPAM and the Fabric Overlay Orchestrator topology. Confirm each spoke received a unique loopback and tunnel address from the intended pool.
  5. Only then investigate IKE/IPsec and BGP. If an interface has the wrong address, routing symptoms may be downstream consequences of the allocation problem.

Operational scenario

A new spoke forms IKE but does not establish the expected BGP adjacency. Before changing BGP neighbor settings, compare the spoke's loopback and tunnel IP with the root's IPAM pool and the orchestrator's overlay-tunnel-block-ipam reference. A wrong or conflicting allocation can produce a valid-looking tunnel with an unexpected routing identity. Correct the pool binding, inspect all generated interfaces and then re-evaluate IPsec/BGP. This keeps address-plan faults separate from path selection and routing-policy faults.

Primary Fortinet source: https://docs.fortinet.com/document/fortigate/8.0.0/new-features/405060
