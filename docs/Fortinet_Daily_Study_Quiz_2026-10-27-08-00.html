FortiGate — Multicast forwarding when packets arrive with TTL=1

Mechanism fingerprint: multicast-forward TTL decrement suppression

Mechanics

In FortiOS NAT mode, multicast-forward provides a simple forwarding path between eligible interfaces. Normally, packets with TTL 2 or greater are forwarded and the IP TTL is decremented by one. A packet arriving with TTL 1 expires at the FortiGate, so a downstream multicast router never receives it. This is a hop-limit issue, not necessarily an IGMP membership or receiver issue. Simple multicast forwarding is distinct from PIM routing, which builds protocol state for multicast distribution.

Configuration

The documented setting is `config system settings` / `set multicast-forward enable`. The separate `multicast-ttl-notchange` option prevents forwarded multicast TTL from being changed; Fortinet documents it for cases where packets expire before reaching a downstream multicast router. Use it only on the required path. In forwarding mode, disable multicast-routing if the design is a simple forwarder rather than a PIM router. NAT-mode forwarding still requires multicast policies that permit the intended traffic; preserving TTL does not bypass policy.

Verification

Capture the same group packet at ingress and egress. If TTL=1 is visible on ingress but no egress copy exists, inspect forwarding mode and TTL handling before changing IGMP timers. If egress exists, investigate policy matching, VLAN tagging, snooping state, and the downstream router. `diagnose sys mcast-session list` helps with routed multicast sessions, but an empty routed-session list alone does not prove a simple forwarding path is broken. A policy counter proves a policy matched, not that the next switch has a multicast-router port.

Scenario and guardrails

The Community tip updated October 6, 2026 describes forwarding multicast packets with TTL 1. Reproduce with a controlled stream, validate captures on both sides, and verify the multicast policy still limits the group and interfaces. TTL preservation changes normal hop-limit semantics; document why the stream requires it and avoid applying it globally as a first-line workaround. Transparent mode has different policy behavior, so use the guide for the installed mode and release.

Evidence to collect: paired captures, multicast session state, policy counters
Remediation: enable forwarding and scope TTL preservation to the required stream

Deeper field verification and failure isolation

Multicast path isolation and policy scope. Do not troubleshoot this as a receiver-only issue until the packet has been observed on both sides of the FortiGate. A capture on the source-side interface establishes the actual destination group, VLAN, source address, and TTL that entered the forwarding path. A capture on the egress side distinguishes TTL expiry from a policy drop or a downstream Layer 2 problem. If the packet exits, the next checks are the switch's multicast-router port, VLAN membership, and whether the receiver joined the expected group. If it does not exit, confirm NAT versus transparent mode and the intended forwarding/routing mode before changing unrelated multicast protocol settings.

TTL preservation is a targeted exception to normal hop-limit handling. It should not be used to mask a routing loop or to make every multicast stream traverse extra hops. Record the specific source/group/interface tuple that needs the behavior and retest other streams to ensure the change did not broaden forwarding. Also remember that multicast-forward and multicast-routing are different control paths: a PIM neighbor or group-state symptom should be investigated with the routing design, not treated as proof that simple forwarding is disabled.

FortiManager — Policy Blocks: reusable rule sets and installation-target boundaries

Mechanism fingerprint: independent Policy Block objects and Install On target selection

Object model

Policy Blocks hold multiple policies so they can be appended to a Policy Package together. FortiManager 7.6.6 documents firewall, proxy, and firewall virtual-wire-pair policies. The feature is hidden until enabled in Policy & Objects → Tools → Feature Visibility → Policy Block. A copied policy becomes an independent object: editing or deleting the original package policy does not update the copy in the block.

Targets and package attachment

A block's contents and its installation target set are separate. A block can be appended to a package, but its Install On targets can be selected from the block itself or the package view. The guide allows block targets that are not assigned to the enclosing package's target list. A correct package assignment therefore does not prove the block reaches only the package's normal device set. Inspect targets and install preview before committing.

Global/local scope

Blocks can exist in a local ADOM or Global Database ADOM. Global blocks can be used with global header/footer policies, but global constructs retain version dependencies between the Global Database ADOM and local ADOMs/devices. Local blocks can reduce upgrade coupling when ADOMs cannot move together. Confirm the active ADOM before editing; a similarly named block in another ADOM is a different object. Role-based access controls who can modify blocks.

Troubleshooting

If only some devices reflect a change, determine whether the block itself was edited or a source policy was copied into it. Compare block contents, package attachment, Install On targets, and the generated diff. Object visibility proves existence, not installation; a successful install task proves transaction completion, not correct policy order. The Community article gives global-package context, while the Administration Guide defines object and target semantics.

Evidence to collect: ADOM context, block membership, Install On list, install preview, device policy diff
Remediation: enable feature visibility and check block scope and targets independently

Scenario: Community technical tip, 2026

Deeper field verification and failure isolation

Install preview and policy provenance. Treat the Policy Block as a reusable bundle, not a reference that automatically follows its original source policy. When a shared rule changes, compare the block's own policy content and UUIDs with the source package, then inspect the install preview. A policy block can be installed directly to selected devices, including targets not in the enclosing package's target list, so review both target lists rather than assuming they are identical. Verify policy order after installation; a valid rule installed below a broad matching rule may never receive traffic.

Global reuse is useful for a common header/footer baseline, but it creates an ADOM/version boundary that should be considered during upgrades. Confirm the Global Database ADOM and local ADOM compatibility before moving shared policy constructs between versions. If a rule is intentionally different in one ADOM, use a local block or explicit local policy rather than silently editing a copied object and expecting the source to update. Preserve the install diff and device-side rule identifiers as evidence for change review.

FortiAnalyzer — Event handlers: OR rules, correlation sequences, and Analytics-only input

Mechanism fingerprint: event handler logic over Analytics logs with separate selectors and notification profiles

Separate the layers

FortiAnalyzer event handlers generate events from Analytics logs, not Archive logs. In Analyzer–Collector collaboration, the Analyzer evaluates handlers. Data selectors scope devices, subnets, and filters; notification profiles define destinations; handlers define detection logic. A notification profile cannot make Archive records eligible, and a valid handler cannot match a device excluded by its selector. Prove the raw log is eligible before changing the rule.

Basic versus correlation

Basic-handler rules have OR semantics: any qualifying rule may trigger when its conditions and threshold are met. Correlation handlers express relationships across rules using operators such as AND, AND_NOT, OR, FOLLOWED_BY, and NOT_FOLLOWED_BY. Correlation requires state across a window, so resetting state can reset threshold progress. Define whether the intent is any event, all conditions, or an ordered sequence before tuning thresholds.

Verification

Confirm the correct ADOM, raw Analytics record, selector, handler enabled state, aggregation field, threshold, time window, and notification profile. The Community troubleshooting guide references `diagnose test app sqllogd 1`, `diagnose test app fazalertd 1`, and a handler-specific query such as `diagnose test app sqllogd 200 conf adom=<name> handler=<name>`. Use commands appropriate to the installed release. Log View proves ingestion, not handler match; a handler hit does not prove notification delivery.

Recovery caution

Collect diagnostics before resetting correlation state. The documented `fazalertd` RocksDB reset can reset correlated handler data, including threshold-window state. Capture handler configuration and raw logs before clearing runtime state, then retest with controlled events. The Community source is diagnostic context; the Administration Guide is authoritative for handler semantics and the Analytics/Archive boundary.

Evidence to collect: Log View, ADOM, handler hit diagnostic, sqllogd/fazalertd state
Remediation: verify input eligibility, selector, handler logic, threshold, then daemon state

Scenario: older feature-specific troubleshooting guide

Deeper field verification and failure isolation

Aggregation, thresholds, and notification delivery. For a basic handler, check the aggregation key and threshold together. A count threshold grouped by source IP behaves differently from the same threshold grouped by device or user; a valid log can therefore exist without contributing to the bucket you are watching. Correlation handlers add sequence state and a time window, so test the intended order with controlled events and confirm whether the sequence requires both events, one event followed by another, or the absence of a later event. A rule that is logically wrong will not be fixed by restarting the handler daemon.

Use a layered acceptance test: find the raw Analytics log, confirm the selector includes its device/subnet, confirm the handler hit or correlation state changes, then verify the generated event and the notification destination. These stages are separate. If a handler hit exists but no email/webhook arrives, inspect notification configuration and transport rather than changing the detection predicate. Capture current state before any `fazalertd` state reset because resetting correlation storage can erase the threshold/window evidence needed to explain the issue.

FortiSwitch — IP source guard and DHCP snooping: bindings and spoofing enforcement

Mechanism fingerprint: per-port IPv4 allowlist from static MAC/IP bindings and DHCP snooping

Mechanism and limits

IP source guard permits IPv4 traffic on a protected port only when the source address matches a valid binding. Bindings can be static IP/MAC associations or dynamic entries learned through DHCP snooping. The feature is disabled by default and enabled per interface. Static entries take precedence when they conflict with dynamic entries. Fortinet documents a 2,048-entry maximum and notes that the feature does not work with VLAN translation.

Configuration order

Establish the DHCP snooping trust boundary so legitimate server replies reach clients while untrusted access ports cannot inject rogue offers. Confirm the switch learns the expected binding, then enable source guard or add a static binding for a device that does not use DHCP. In FortiLink mode, FortiGate can send VLAN/interface configuration but does not create the source-guard binding itself; configure and verify it on FortiSwitch. Example: `config switch interface; edit port6; set ip-source-guard enable; next; end`.

Evidence and blind spots

`diagnose switch ip-source-guard hardware entry list` directly checks programmed entries. The GUI monitor view helps correlate a binding to a port. Discarded addresses are not logged by default. Enable `log-source-guard-violations` and set the violation timer if evidence is needed. The log is bounded to 128 entries overall and five per port, so an empty log does not prove no drops occurred. A hardware entry proves a binding exists, not that trust is correct for every VLAN.

Failure pattern

If a client loses connectivity after a VLAN or DHCP relay change, verify its lease, VLAN, port, and programmed IP/MAC binding. Check that the uplink carrying server replies is trusted. Disabling source guard removes both static and dynamic entries for that interface; re-enabling without restoring entries can block legitimate clients. The Community tip highlights feature ownership in FortiLink deployments. Roll out on a small port set and test static hosts before campus-wide enforcement.

Evidence to collect: hardware binding table, trusted DHCP port, bounded violation log
Remediation: set trust boundary and verify binding on FortiSwitch before enforcement

Primary: Fortinet guide
Scenario: Community tip updated April 16, 2026
Diagram: Trusted DHCP uplink → Snooping table → Source-guard port → Matching source → Drop mismatch

Deeper field verification and failure isolation

Binding hygiene and rollout safety. A source-guard table entry is only correct if the DHCP snooping trust model is correct. Trust the ports that legitimately carry server replies, not every uplink by habit; an untrusted rogue DHCP server can poison endpoint configuration, while an untrusted legitimate server path can prevent a lease from being learned. Static bindings are appropriate for printers, cameras, and other endpoints that do not use DHCP, but document the address/MAC/port/VLAN relationship so moves do not leave a stale binding. The hardware table is the best place to confirm what the switch will enforce now.

The bounded violation log is diagnostic evidence, not a complete audit trail. Enable violation logging before a controlled test and collect the table/log output promptly because the per-port and global limits can overwrite older events. When a client is blocked, verify the exact source IP and ingress port against the programmed binding; do not assume an ARP entry alone is sufficient. Also verify that the design does not use VLAN translation on the protected path, and remember that disabling source guard removes static and dynamic entries for that interface.

FortiAP/Wireless — Rogue AP detection: RF observation, on-wire proof, and suppression

Mechanism fingerprint: RF scanning plus LAN/Wi-Fi MAC correlation and monitoring-radio deauthentication

RF visibility is not wired proof

FortiAP can hear nearby APs, but a detected AP is not automatically a rogue. A neighbor may cause interference without being attached to the organization's wired network. On-wire detection compares MAC addresses observed on the LAN with clients/APs observed on Wi-Fi. Exact MAC matching works when client MACs are visible on the LAN; MAC-adjacency can help when a rogue AP performs NAT because wireless and Ethernet MACs may be numerically close. The default adjacency value is 7; detection also requires an active client sending traffic.

Scanning behavior

Rogue scanning is configured in a WIDS profile applied to the FortiAP profile. Radios can scan by briefly switching from AP service to monitoring, or one radio can be dedicated to monitoring. The guide describes a default background scan period of 300 seconds and 20 ms per channel during each cycle. Busy radios can lose packets while switching; `ap-bgscan-idle` can delay scans until the AP has been idle for a configured period. Confirm model, regulatory domain, profile assignment, sensor mode, and client traffic.

Suppression is active response

Suppression is more than a dashboard label. The monitoring radio sends deauthentication frames while impersonating the rogue AP to its clients and clients to the rogue AP. The guide requires on-wire rogue detection and a Dedicated Monitor radio. Protected Management Frames can prevent the expected effect, so a Suppressed state does not prove clients were disconnected. Suppression is an active RF response; check applicable law and regional regulations before using it.

Evidence and diagnosis

Inspect BSSID, SSID, channel, signal/SNR, first/last seen, detecting AP, and the on-wire indicator. RF visibility alone is not proof of wired attachment. If a NATing AP is suspected, check MAC adjacency and active client traffic. If suppression does not work, verify monitor-radio mode and PMF before changing thresholds. The Community best-practices article supplies scenario context; the Configuration Guide defines requirements.

Evidence to collect: BSSID/SSID, on-wire indicator, MAC adjacency, monitor mode, PMF
Remediation: validate on-wire evidence and monitor-radio prerequisites before suppressing

Primary: Fortinet guide · Additional guide
Scenario: older best-practices article
Diagram: Radio scan → MAC correlation → Rogue classification → Monitor radio → Deauth response
Open standalone SVG · Open editable draw.io

Deeper field verification and failure isolation

Classification confidence and RF response. A nearby BSSID is first an observation. Classification as on-wire requires correlation between radio observations and wired-side MAC evidence; a NATing rogue may need adjacency logic and an active client generating traffic. That means detection can be delayed or incomplete if the rogue has no active client, if the wired-side observation is missing, or if the AP's MAC behavior defeats the heuristic. Record the detecting AP, channel, RSSI/SNR, BSSID, first/last seen, and on-wire state before changing the WIDS profile. Do not equate a strong signal with proof of organizational attachment.

Suppression uses deauthentication frames and can affect users, neighboring networks, or devices protected by PMF. The feature's state field is not a packet-level acknowledgement that clients disconnected. Validate the Dedicated Monitor radio and on-wire prerequisite, then observe a controlled test client and the radio's response. Consider scan overhead on serving radios: background scanning briefly interrupts service, so changing scan cadence is a tradeoff between detection latency and client impact. Use suppression only under the organization's RF policy and applicable regulations.

FortiNAC — Control Manager: host ownership handoff across distributed servers

Mechanism fingerprint: host inventory visibility versus active access-control ownership across appliances

Distributed visibility versus ownership

FortiNAC Control Manager supports deployments where different FortiNAC servers manage different parts of the access network. A host can be visible in more than one appliance database, while the appliance that manages the current access switch owns the active access-control relationship. If a laptop moves from switches managed by appliance A to switches managed by B, the transition depends on the old connection ending and a new connection being observed. Inventory presence and active enforcement ownership are not identical facts.

Connection lifecycle

The Control Manager guide ties connection-license consumption to connection state. A host consumes a connection license while connected; when it moves, the original license is released when the host disconnects and the host consumes a license again on the next connection. A host connected simultaneously through wired and wireless FortiNAC servers can consume two licenses because there are two active connections. During a move, duplicate rows alone do not prove duplicate live sessions or a licensing leak.

Verification

Check which appliance models the switch, whether the switch is online and assigned to the expected server, and whether the old connection actually ended. Compare host location, connection state, and disconnect timestamps with the move. Confirm the new appliance sees the expected switch port/VLAN and that the current connection is associated with it. A stale inventory row is not an active session; a current connection on the wrong appliance may indicate a switch ownership or topology-model problem.

Availability and source boundary

The guide states that individual FortiNAC servers continue using their license counts if Control Manager is down; do not generalize that to every centralized function. Validate Control Manager and managed servers separately. Avoid deleting host records before understanding the handoff. The official guide supplies the primary ownership model; a directly matching recent Community incident was not found, so no unrelated article is presented as an exact scenario.

Evidence to collect: switch ownership, host connection state, last-seen and disconnect timestamps
Remediation: verify modeled switch ownership and actual disconnect/reconnect before deleting records

Scenario: no directly matched recent Community incident verified
Diagram: Host on area A → NAC A owns switch → Disconnect / move → NAC B owns switch → New connection

Deeper field verification and failure isolation

Handoff timeline and ownership verification. Model the move as a timeline: old switch connection, old appliance disconnect, new switch connection, new appliance ownership. Compare timestamps and switch ownership at each point. If the host record remains in the old database but the old connection is closed, that may be retained inventory rather than an active enforcement conflict. If the old connection remains active, check whether the old switch is still modeled under appliance A or whether the network did not produce the disconnect event. If the new appliance never observes the host, validate switch polling and VLAN/port mapping before deleting records.

Control Manager health and each managed appliance's health are separate checks. A Control Manager outage does not automatically mean all individual appliance connection/license behavior stops, but it can limit centralized visibility or management. During a campus migration, avoid overlapping switch reassignment, host deregistration, and enforcement changes; those changes can make it difficult to identify which appliance owns the active session. Keep the host identifier, switch model/serial, port, connection state, and move timestamp in the incident record. This topic is about ownership handoff, not the separate device-profiling rule precedence mechanism.

FortiNAC-F — NetFlow sessions stop populating after FortiNAC-F 7.6.7

Mechanism fingerprint: NetFlow packet reception separated from session-record persistence

Feature contract

FortiNAC-F supports NetFlow v5, v9, and v10/IPFIX for device profiling. Configure the exporter destination as the FortiNAC-F address and listener port 2055; the receiving interface must allow the NetFlow service. Collected information appears under Users & Hosts → Network Sessions and can feed a Device Profiling rule using the Network Traffic method. Success has several stages: exporter sends, appliance receives, packets queue, session rows are created, and a rule consumes those rows.

Recent failure boundary

The recent Community tip describes FortiNAC-F 7.6.7 systems where NetFlow packets continue arriving and queueing, but no new Network Sessions records are created. Existing rows remain visible and no warning may appear in `output.master`. Network Traffic profiling rules then stop matching. This differs from an exporter that is not sending, blocked UDP, or missing `allowaccess netflow`. The symptom can occur whether NetFlow is the only session source or is used with firewall session polling.

Diagnosis

Check exporter destination/port and the receiving interface's NetFlow permission, then verify packet arrival. Compare the last Network Sessions timestamp with the upgrade time. If packets arrive and queue but rows do not advance, repeated exporter changes are unlikely to fix a downstream persistence regression. Capture build, session-source settings, packet evidence, and logs for support. Packet receipt proves ingress, not that the session store or profiling engine is healthy.

Temporary workaround

The Community article describes enabling FortiGate firewall session polling as an interim source when profiling cannot wait. Configure it from Network → Inventory on the modeled FortiGate and set a measured polling frequency. Polling returns a broader session set and queries the firewall each interval, adding load on busy units. Treat it as temporary; verify fresh session timestamps and a controlled profiling-rule match, then disable polling after upgrading to a build that resolves the issue.

Evidence to collect: current Network Sessions timestamps, packet receipt, interface allowaccess, output.master
Remediation: separate exporter faults from persistence; use polling only as a reviewed temporary workaround

Deeper field verification and failure isolation

Distinguishing transport, queueing, and persistence. NetFlow has a pipeline: the exporter selects records, the network delivers UDP datagrams, FortiNAC-F receives/queues them, the session processor creates Network Sessions records, and profiling rules consume the records. Each stage has its own observable. Verify the interface's NetFlow service permission and the configured destination/port first, then compare packet arrival and queue activity with the timestamp of the newest session row. If packet receipt continues but rows stop exactly after a software upgrade, preserve the build number, source configuration, queue evidence, and relevant logs for support instead of repeatedly changing the exporter.

The documented temporary workaround is firewall session polling from the modeled FortiGate. It can restore a session source for urgent profiling, but it queries the firewall at each interval and can return a broader set than a targeted NetFlow export. Disable polling after the fixed build is deployed and the NetFlow path passes that end-to-end test.

FortiAuthenticator — Realm matching and UPN parsing: preserve the real username

Mechanism fingerprint: username delimiter normalization before realm and identity-source selection

Realm is a routing key

FortiAuthenticator realms allow one appliance to authenticate users from local, LDAP, RADIUS, or SAML sources. The RADIUS policy and username format determine how the incoming User-Name is normalized and which backend is queried. Formats include `username@realm`, `realm\username`, and `realm/username`. Realm labels are locally significant; they need not be the same as a DNS domain. Realm and policy order matter when several identity sources are configured.

UPN delimiter collision

A user such as `alex@corp.example` may be a real User Principal Name, but if `@` is configured as the realm delimiter, FortiAuthenticator can treat `corp.example` as a realm and look up `alex`. Credentials may be correct while authentication fails because the username was normalized incorrectly. This is an identity parsing/source-selection problem, not necessarily a bad password or RADIUS shared-secret failure. The Community UPN troubleshooting article documents this class of mistake.

Configuration and verification

Create the realm under Authentication → User Management → Realms and select the intended source. Confirm the RADIUS client/policy accepts the realm and the username format matches the identity syntax. If the UPN must remain intact, use a format whose delimiter does not consume the @ within the UPN—for example, an explicit realm-prefixed form where the full UPN remains after the separator. Test one local and one remote identity before changing production policy.

Evidence boundary

RADIUS debug should show raw username, parsed realm, normalized username, selected backend, and final result. If logs show the local database being queried for a shortened username, fix parsing before changing directory permissions. Access-Reject proves rejection, not its cause. Compare parsed fields for failing and working formats. The Administration Guide defines realms; the Community tip provides the real UPN parsing failure pattern.

Evidence to collect: raw username, parsed realm, normalized username, selected backend, RADIUS debug
Remediation: choose a delimiter that preserves the UPN and test realm order

Primary: Fortinet guide · Additional guide
Scenario: older but directly relevant parsing issue
Diagram: Access-Request → Username parser → Realm match → Identity source → Accept / Reject
Open standalone SVG · Open editable draw.io

Deeper field verification and failure isolation

Username normalization and source-selection proof. Use one known-good account and one failing UPN to compare the full RADIUS debug transaction. Look for the raw User-Name, parsed realm, normalized username, selected source, and result. If the suffix is stripped before the lookup, do not reset the user's password or reimport the directory account first; those actions do not correct delimiter interpretation. Test the configured username formats explicitly and verify the realm order/default behavior so a request without a realm does not silently route to a different backend than expected.

Local and remote groups can interact with RADIUS policy options. If the debug shows the request being checked against LDAP when a local account was intended, review the realm and policy identity-source settings and the option that allows local users to override remote users where appropriate. A successful network ping proves only reachability; a configured realm proves only that an object exists. The decisive evidence is the source selected for the actual Access-Request and whether the normalized username matches the account's stored identifier.

FortiPAM — Password changer verification and Windows Server 2025 SAMR restrictions

Mechanism fingerprint: password changer plus verifier and retained credential history

Change and verify are separate

FortiPAM Password Changers define how a secret's target password is changed and verified. Types include Active Directory LDAP, Open LDAP, Samba, SSH with password/public key, and Web API. The changer can use the secret itself or an associated secret; the verifier has its own mode. A target may reject the change before verification, or accept a change while verification still fails. Generated password text alone is not proof of a completed rotation.

Credential history as recovery

FortiPAM retains the most recent five credentials used by a secret. If a change fails, the last attempted credential remains available so an operator can test whether the target and FortiPAM are out of sync. Password Changer Status records change time and status. Use Credential History to verify the last attempted or previous credential before restoring it. Blindly generating another password can make reconciliation harder if the target accepted a change but the response was lost.

October 15 Windows Server 2025 case

The Community tip describes local administrator rotation failing through the SMB/Samba changer with `NT_STATUS_ACCESS_DENIED` and a message that LANMAN password changes are disabled. The article identifies a Windows Server 2025 SAMR restriction involving `SamrUnicodeChangePasswordUser2`. On the target, inspect Computer Configuration → Administrative Templates → System → Security Account Manager → Configure SAM change password RPC methods. The described workaround allows supported change-password RPC methods; a domain GPO can override a local setting.

Acceptance criteria

Record target OS/build, changer type, template, verifier mode, and exact error. Verify effective server policy before repeating rotation. After the target accepts the change, run the verifier and test authentication with the new credential. If it fails, verify the last attempted credential before restoring it. Do not disable security policy broadly without change control; use the narrowest supported setting. The Administration Guide is primary for changer/verifier behavior, while the October 15 Community tip is the scenario source.

Evidence to collect: Password Changer Status, NT_STATUS_ACCESS_DENIED, Credential History, effective GPO
Remediation: verify target SAM change policy and effective GPO, then verify credential before restore

Deeper field verification and failure isolation

Target policy, credential history, and safe recovery. Do not treat the password changer and verifier as one atomic success flag. Capture the target-side response, FortiPAM changer status, verifier result, and the credential history entry used for the attempt. The five-entry history can help determine whether the target accepted a new value while the application failed to record success. Verify the last attempted credential against the target before restoring a previous one; restoring blindly can make the target and secret diverge further. Keep a change window and recovery plan for privileged local accounts.

For the Windows Server 2025 SAMR case, check the effective policy on the target and whether domain Group Policy overrides the local setting. Apply the narrowest supported change with security/change-control approval, then repeat one rotation and verify the new credential before scheduling broad rotation. FortiSIEM — Custom parser precedence, event recognizers, and attribute testing

Mechanism fingerprint: top-to-bottom parser selection by event recognizer then XML parsing instructions

Parser order is runtime behavior

FortiSIEM parser files are XML definitions with pattern definitions, an Event Format Recognizer, and Parsing Instructions. Enabled parsers are inspected top-to-bottom in Admin → Device Support → Parsers. The first recognizer match is used; if no parser matches, the event becomes `Unknown_Event_Type`. A broad recognizer above a specific parser can capture the event even when the lower parser's XML is valid.

Safe customization

Secure SD-WAN — Application steering: first-flow identification and top-down rule matching

Mechanism fingerprint: application-control recognition and custom/ISDB classification before top-down service rules

Classification precedes steering

SD-WAN service rules identify traffic and select an outgoing member based on strategy and link conditions. Application-based steering depends on application recognition; it is not only a static five-tuple match. The Administration Guide notes the first session may not match an application-based rule because the application signature has not yet been recognized. The IPS/application-control engine must inspect the first session to establish identity, so later flows can behave differently.

Prerequisites and order

Enable application control in the firewall policy handling the traffic. To expose individual applications/groups in the GUI, enable Application Detection Based SD-WAN in Feature Visibility; the documented CLI setting is `config system global` / `set gui-app-detection-sdwan enable`. Then review service-rule order: FortiGate evaluates rules top-down and uses the first applicable match. A broad earlier rule can capture traffic before a more specific application rule.

ISDB and application IDs

Internet Service Database classification and application-control IDs are separate signals. Community examples show that two addresses in the same ISDB category can be identified as different applications and therefore match different rules. Custom Internet Service definitions and application-control classifications can affect matching precedence. Do not infer the selected rule from destination IP alone; inspect classification output and rule order.

Verification

Useful diagnostics include `diagnose firewall internet-service-custom list`, `diagnose sys sdwan internet-service-app-ctrl-list`, and `diagnose internet-service info root 6 443 <destination-ip>`. Use syntax appropriate to the installed release. These commands establish classification/cache state; they do not prove a member is healthy or that an existing session was re-evaluated after a rule change. Test a fresh flow and a subsequent recognized flow separately.
