FortiGate · focused stand-alone chapter

FortiGate — FGSP session synchronization and selective session pickup

Primary feature source: FGSP
Release: FortiOS 7.6.6
https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/668583/fgsp
Scenario support source: Technical Tip: How to verify Sessions are SYNC in HA cluster through CLI
https://community.fortinet.com/fortigate-3/technical-tip-how-to-verify-sessions-are-sync-in-ha-cluster-through-cli-177197

Essence

FGSP is designed for horizontally scaled FortiGates that forward independently but need to preserve selected stateful sessions when traffic is redirected to another peer. The critical distinction is that FGSP synchronizes session state; it does not perform cluster election or upstream traffic steering.

How it actually works

A session is created on the FortiGate that receives the first packet. That peer performs route lookup, policy matching, NAT, and inspection, then exports eligible session state to the FGSP peer. If the original peer fails, an external load balancer or routing design must redirect the flow. The surviving FortiGate can continue the flow only if it has compatible synchronized state and matching policy/routing/NAT context.

What to notice: the diagram shows the exact product-specific handoffs discussed in this chapter.

Important implementation details

  • `session-pickup` controls the core state synchronization behavior.
  • Connectionless traffic, helper-created expectation sessions, NAT state, and delayed TCP pickup are separate controls because they have different continuity and scale implications.
  • Delayed pickup is useful when long-lived sessions matter more than short-lived connections; it reduces synchronization churn but intentionally leaves some early/short TCP flows unsynchronized.
  • FTP/SIP helper behavior can require expectation-session state in addition to the parent control session.
  • Peer configuration must remain compatible enough that a synchronized session can still map to valid policy, interfaces, routes, and translations on the survivor.

Configuration / diagnostics

config system ha
    set session-pickup enable
    set session-pickup-connectionless enable
    set session-pickup-expectation enable
    set session-pickup-nat enable
end

Production troubleshooting scenario

A payments application keeps long-lived TLS sessions through two FGSP peers. After a peer failure, TLS survives, but SIP media and UDP telemetry reset. Because steering and ordinary TCP state are already working, the investigation should focus on the unsynchronized state classes rather than the load balancer. If a NATed session reaches the survivor but its translated tuple changes, NAT-state synchronization and peer translation symmetry are the next areas to verify.

Design guidance

Use FGSP selectively. Synchronizing every short-lived connection increases CPU, memory, and sync-link load without necessarily improving user experience. Protect flows whose restart cost matters—long database sessions, selected voice/control flows, or stateful application sessions—and validate failover with real traffic classes. Keep peer configuration consistent with FortiManager or another controlled process.

Key takeaway: FGSP is designed for horizontally scaled FortiGates that forward independently but need to preserve selected stateful sessions when traffic is redirected to another peer. The critical distinction is that FGSP synchronizes session state; it does not perform cluster election or upstream traffic steering.

FortiManager — Provisioning-template metadata variables, validation, and scope precedence

Primary feature source: Validate metadata variables in provisioning templates
Release: FortiManager 7.6.6
https://docs.fortinet.com/document/fortimanager/7.6.6/administration-guide/255972
Scenario support source: Install Preview Shows No Changes When Global and VDOM Provisioning Templates Are Both Assigned
https://community.fortinet.com/fortimanager-27/technical-tip-install-preview-shows-no-changes-when-global-and-vdom-provisioning-templates-are-both-assigned-vdom-enabled-fortigate-229494

Essence

FortiManager metadata variables let one template produce different values for different devices. The important behavior is target-specific resolution: default values, group mappings, and device overrides are resolved before FortiManager renders candidate CLI and presents validation or Install Preview.

How it actually works

A provisioning template references metadata variables inside supported fields. FortiManager resolves those variables in the target ADOM, applies the most specific mapping, considers the scope that owns the setting, renders target-specific CLI, validates that result, and only then includes it in an installation transaction. Global and VDOM templates can compete for ownership of the same setting.

Important implementation details

  • Device-specific mappings are used for true exceptions; broader group/default mappings reduce per-device configuration sprawl.
  • Preview Script is the most useful checkpoint when a variable appears wrong because it shows the rendered candidate, not just the template source.
  • A template can be valid globally while one target fails because its metadata resolution differs.
  • Global-versus-VDOM scope can explain a missing Install Preview delta even when connectivity and the template are otherwise healthy.
  • FortiManager meta fields and metadata variables are different features; a field being called 'meta' does not mean it can be substituted in a provisioning template.

Production troubleshooting scenario

A branch template uses a loopback metadata variable. One device fails validation while 99 peers pass. The correct first check is that device's mapping and Preview Script, not the shared template. In another case, a VDOM template change never appears in Install Preview because a Global template defines the same setting; removing the scope conflict in a lab demonstrates why the lower-scope change was never candidate configuration.

Design guidance

Use metadata where values genuinely vary—site addresses, loopbacks, tunnel endpoints, branch IDs, or credentials—not for every possible field. Prefer defaults and group mappings; track device-level overrides as exceptions. Make validation and Preview Script review a pre-install gate, especially across mixed FortiOS versions.

Key takeaway: FortiManager metadata variables let one template produce different values for different devices. The important behavior is target-specific resolution: default values, group mappings, and device overrides are resolved before FortiManager renders candidate CLI and presents validation or Install Preview.

Essence

Report Guidance explains which log types and fields a report element expects and whether the required Analytics data is available. This is important because a report queries Analytics data, while older raw logs may still exist in Archive storage.

How it actually works

Logs are generated on source devices, ingested by FortiAnalyzer, and retained as Analytics and/or Archive data according to storage policy. FortiSwitch — FortiLink split-interface topology and transition to MCLAG

Primary feature source: FortiLink split interface
Release: FortiSwitchOS 7.6.1 / FortiOS 7.6.x
https://docs.fortinet.com/document/fortiswitch/7.6.1/fortilink-guide/801204
Scenario support source: Supported 802.3ad FortiLink topologies and split interface
https://community.fortinet.com/fortiswitch-36/technical-tip-supported-802-3ad-fortilink-topologies-and-split-interface-215416

Essence

FortiLink split-interface mode intentionally keeps one FortiLink member active and another standby in supported non-MCLAG topologies. The standby state is a loop-avoidance mechanism, not necessarily a failed LACP member. MCLAG changes the design by coordinating two switches as one multichassis aggregation endpoint.

How it actually works

FortiGate owns the FortiLink aggregate. In split-interface mode, one uplink forwards and the other remains standby while the switches are interconnected. In MCLAG mode, the two switches build an ICL and synchronize multichassis state so both FortiLink uplinks can forward after split-interface is disabled.

flowchart TD
F[FortiGate FortiLink] --> A[Active link]
F --> B[Standby in split mode]
A --> S1[Switch 1]
B --> S2[Switch 2]
S1 <-->|ISL or ICL| S2

What to notice: the diagram shows the exact product-specific handoffs discussed in this chapter.

Important implementation details

  • Physical carrier and LLDP adjacency do not determine whether an uplink should be forwarding.
  • `fortilink-split-interface enable` is correct for the classic redundant non-MCLAG topology.
  • MCLAG requires a healthy peer/ICL relationship before the design transitions to both FortiLink links active.
  • Disabling split-interface merely to make a suspended link active can create loops or split-brain risk in the wrong topology.
  • FortiGate-managed FortiSwitch deployments should avoid direct switch CLI drift that conflicts with controller intent.

Configuration / diagnostics

config system interface
    edit "fortilink"
        set fortilink enable
        set lacp-mode active
        set fortilink-split-interface enable
    next
end
# After verified MCLAG/ICL formation:
set fortilink-split-interface disable

One link remains standby after MCLAG is establishedThe MCLAG design may still be constrained by FortiLink split mode or LACP state.The optic is necessarily bad.

Production troubleshooting scenario

A branch uses two non-MCLAG switches with an inter-switch link. One FortiLink LACP member is suspended despite healthy optics. That is expected split-interface behavior. In a data-center MCLAG pair, the same suspended state is unexpected once the ICL and peer state are healthy; there the engineer should verify that split-interface was disabled after MCLAG formation.

Design guidance

Choose topology first, then configure split-interface behavior. Do not use `disable` as a generic performance switch. For MCLAG, validate peer compatibility, ICL resilience, STP behavior, and controller ownership before enabling both forwarding paths.

Key takeaway: FortiLink split-interface mode intentionally keeps one FortiLink member active and another standby in supported non-MCLAG topologies. The standby state is a loop-avoidance mechanism, not necessarily a failed LACP member. MCLAG changes the design by coordinating two switches as one multichassis aggregation endpoint.

FortiAP — DARRP channel scoring, RF measurements, thresholds, and optimization timing

Primary feature source: Configuring Distributed Radio Resource Provisioning
Release: FortiAP / FortiWiFi 8.0.0
https://docs.fortinet.com/document/fortiap/8.0.0/fortiwifi-and-fortiap-configuration-guide/299720
Scenario support source: DARRP channel assignment on FortiAP WiFi
https://community.fortinet.com/fortiap-5/troubleshooting-tip-darrp-channel-assignment-on-fortiap-wifi-181283

Essence

DARRP selects channels from an allowed candidate set using measured RF conditions and configured thresholds/weights. It is not trying to make every AP use a unique channel; reuse is normal when cells are sufficiently isolated.

How it actually works

FortiAPs collect channel load, noise, neighboring AP RSSI, spectral energy, and related measurements. DARRP first removes channels that are disallowed or exceed rejection thresholds, then scores the remaining candidates. A scheduled optimization applies the chosen channel, which can cause clients to reassociate.

flowchart TD

A -- no --> X[Reject channel]
A -- yes --> W[Apply weights]
W --> S[Score candidates]
S --> C[Choose channel]
C --> O[Scheduled change]

What to notice: the diagram shows the exact product-specific handoffs discussed in this chapter.

Important implementation details

  • Referenced defaults include a 3600-second selection period and 300-second monitor period.
  • Documented weights include managed AP 50, rogue AP 0, noise floor 40, channel load 20, and spectral RSSI 40.
  • Referenced thresholds include noise floor around -85 dBm, channel load 60%, and spectral RSSI around -65 dBm.
  • `darrp-optimize` defaults to 86400 seconds in the referenced guide, with a low-traffic recurring window around 01:00–01:30.
  • A channel not present in the radio profile candidate list cannot be selected regardless of its measured quality.

Configuration / diagnostics

config wireless-controller setting
    set darrp-optimize 86400
    set darrp-optimize-schedules "default-darrp-optimize"
end

diagnose wireless-controller wlac -c darrp
# FortiAP:
cw_diag -c darrp

Evidence interpretation

A quiet channel is absent from the candidate listThe selection problem is policy/candidate eligibility, not weighting.Changing weights will make the channel selectable.
Two same-channel APs hear each other weakly and retries are lowChannel reuse may be appropriate because mutual interference is limited.Co-channel interference is impossible under all client loads.
Channel load exceeds the configured thresholdThe candidate can be rejected before final weighted scoring.Every client necessarily has poor SNR.
Clients briefly reconnect immediately after optimizationThe radio channel changed as part of DARRP operation.The selected channel is inferior.

Production troubleshooting scenario

Two APs share a 5-GHz channel but are physically separated enough that mutual RSSI is weak and utilization is low. There is no reason to force a unique channel merely to make the plan look cleaner. At another site, a quiet DFS channel never appears because the radio profile excludes it; adjusting DARRP weights cannot solve an eligibility problem.

Design guidance

Tune DARRP only when measured client/RF outcomes justify it. Start with the candidate list, measurement quality, and thresholds before changing weights. Schedule optimization where a client reassociation event is operationally acceptable.

Key takeaway: DARRP selects channels from an allowed candidate set using measured RF conditions and configured thresholds/weights. It is not trying to make every AP use a unique channel; reuse is normal when cells are sufficiently isolated.

FortiNAC — RADIUS Proxy: two-leg AAA, EAP relay, MAC handling, and accounting

Primary feature source: RADIUS
Release: FortiNAC 9.4.x
https://docs.fortinet.com/document/fortinac/9.4.0/administration-guide/214558/radius
Scenario support source: Technical Tip: RADIUS Proxy
https://community.fortinet.com/fortinac-28/technical-tip-radius-proxy-99601

Essence

RADIUS Proxy makes FortiNAC the RADIUS server from the switch's perspective and a RADIUS client toward the upstream authenticator. That creates two independent AAA legs with separate secrets, reachability, and failure states.

How it actually works

The NAS sends Access-Request to FortiNAC. FortiNAC applies its proxy configuration and relays EAP/RADIUS to the upstream server. The upstream server returns Challenge/Accept/Reject. FortiNAC can then combine that result with NAC context before replying to the NAS. Accounting can also be proxied.

What to notice: the diagram shows the exact product-specific handoffs discussed in this chapter.

Important implementation details

  • NAS-to-FortiNAC and FortiNAC-to-upstream shared secrets are independent.
  • Proxy mode keeps EAP termination on the external RADIUS authority.
  • MAC authentication ownership can differ from 802.1X EAP depending on the chosen design.
  • An upstream Access-Accept does not prove the switch applied the intended VLAN/ACL or that FortiNAC selected the intended access treatment.
  • Capturing both sides of the proxy is the fastest way to determine whether a failure is before or after FortiNAC forwarding.

Production troubleshooting scenario

A switch sends Access-Request and FortiNAC logs it, but NPS sees no request. The client credential has not yet reached NPS, so it is not the first suspect. Check FortiNAC proxy selection, second-leg routing/firewall, and the upstream client secret. If NPS returns Access-Accept but the endpoint remains isolated, move to FortiNAC access policy and actual switch enforcement.

Design guidance

Document ownership for each AAA method: who terminates EAP, who handles MAB, where accounting goes, and who decides final network access. That prevents teams from troubleshooting the wrong RADIUS server.

Key takeaway: RADIUS Proxy makes FortiNAC the RADIUS server from the switch's perspective and a RADIUS client toward the upstream authenticator. That creates two independent AAA legs with separate secrets, reachability, and failure states.

Primary feature source: Configure Local RADIUS Server settings
Release: FortiNAC-F 7.6.0

Essence

In Local RADIUS mode, FortiNAC-F terminates supported EAP methods itself. That means the Local RADIUS service, EAP server certificate, trusted CAs, client/RadSec trust, identity lookup, authorization, and selector-based network access all become local dependencies.

How it actually works

The NAS sends RADIUS to the FortiNAC-F Local virtual server. If RadSec is used, the outer TLS transport is established first. FortiNAC-F then processes the inner EAP exchange, validates identity/certificates, returns RADIUS authorization, maps the host to a logical network, and applies the effective VLAN/access value through selector/device configuration.

FortiAuthenticator — EAP-TLS and RadSec certificate roles, trust chains, and fragmentation

Primary feature source: General — RADIUS service
Release: FortiAuthenticator 8.0.1
https://docs.fortinet.com/document/fortiauthenticator/8.0.1/administration-guide/656833/general
Scenario support source: EAP-TLS Authentication Fails with error 'Authentication failed for EAP method type 13'
https://community.fortinet.com/fortiauthenticator-8/technical-tip-eap-tls-authentication-fails-with-error-authentication-failed-for-eap-method-type-13-229496

Essence

EAP-TLS authenticates the endpoint inside RADIUS; RadSec protects the RADIUS transport itself. Those are separate TLS layers with separate certificate roles. A method type 13 error identifies EAP-TLS failure but not whether the root cause is certificate chain, EKU, revocation, time, or fragmentation.

How it actually works

The endpoint exchanges EAP with the NAS, which carries EAP inside RADIUS to FortiAuthenticator. FortiAuthenticator presents the configured EAP Server Certificate and validates the client certificate chain. If RadSec is enabled, the RADIUS messages also travel inside an outer TLS connection using a separate RadSec Server Certificate and client certificate trust.

Important implementation details

  • The referenced release documents Max Fragment Size for EAP-TLS with a default of 1024.
  • EAP Server Certificate and RadSec Server Certificate are different settings.
  • Wildcard certificates are not supported as the EAP server certificate in the referenced guide.
  • Default RadSec port is 2083.
  • RadSec clients must present a certificate signed by a configured Local or Trusted CA.
  • Large certificate chains can expose EAP/RADIUS fragmentation or path-MTU problems even when smaller RADIUS exchanges work.

Production troubleshooting scenario

After a CA rollover, EAP-TLS fails but password-based RADIUS methods still work. The leaf certificate is valid, yet the intermediate CA is missing from the trust chain. In another site, only clients with a larger certificate chain fail across a constrained path; the failure appears during certificate exchange, so EAP fragmentation and MTU become more credible than identity policy.

Design guidance

Operate EAP PKI and RadSec PKI as related but distinct services. Track server certificate expiration, intermediate/root CA changes, revocation dependencies, and client certificate requirements separately for outer and inner TLS.

Scenario support source: Active Session Video Monitoring Not Showing in Real Time
https://community.fortinet.com/fortipam-52/technical-tip-active-session-video-monitoring-not-showing-in-real-time-228817

Essence

FortiPAM live monitoring has expected pipeline delay because the session must be captured, transmitted, processed, and rendered. The useful distinction is fixed normal delay versus delay that grows over time. Finalized replay is a later stage and can fail even when live monitoring worked.

How it actually works

The privileged session is launched with recording enabled. Activity is captured by the supported agent/session path, sent to FortiPAM, processed for the Active Sessions monitor, and later finalized for replay. Global Live Recording and per-session recording eligibility are both required.

Important implementation details

  • The referenced guide lists Privileged Access Agent 7.2.3+ for the documented live-recording workflow.
  • Session Recording must be enabled for the session/secret and Live Recording must be enabled globally.
  • Fortinet recommends roughly 8 logical processors and 16 GB memory for smooth concurrent recording/transmission in the referenced guide.
  • The red video icon identifies a session ready for live monitoring.
  • Support guidance describes roughly 8–13 seconds delay in FortiClient mode and 6–10 seconds in agentless mode as expected, while sustained delay above about 30 seconds warrants further investigation.

FortiSIEM — Device discovery, CMDB creation, credential scope, and performance-monitor scheduling

Primary feature source: Discovering Devices
Release: FortiSIEM 7.4.2
https://docs.fortinet.com/document/fortisiem/7.4.2/user-guide/157952/discovering-devices
Scenario support source: SNMP monitoring not scheduled despite successful discovery
https://community.fortinet.com/fortisiem-34/troubleshooting-tip-fortisiem-snmp-monitoring-not-scheduled-despite-successful-discovery-227511

Essence

Discovery proves one FortiSIEM execution context can identify a device. Performance monitoring is a later scheduler/worker workflow that also depends on CMDB identity, credential scope, job assignment, and reachability from the actual Collector or Worker.

How it actually works

Discovery runs from the selected Supervisor or Collector using credentials. Successful discovery creates or updates the CMDB object. Performance-monitoring jobs are then scheduled to a Collector or Active Worker, which must have access to the correct credential and network path to the target.

Important implementation details

  • When a Collector performs discovery, FortiSIEM can assign that Collector ongoing monitoring responsibility for the discovered devices.
  • Without Collectors, the Supervisor performs discovery/Test Connectivity while Active Workers receive monitoring jobs.
  • Credential scope follows the organizational model; a credential visible in one organization may not be usable for a device in another.
  • Adding or removing Workers can redistribute monitoring jobs.
  • Test Connectivity and scheduled polling can therefore succeed/fail independently.

FortiSASE — Security posture tags and dynamic Secure Private Access policy enforcement

Primary feature source: Configuring dynamic private access policies using security posture tags
Release: FortiSASE 26.1.x

Scenario support source: FortiSASE ZTNA agent based / agent-less issue
https://community.fortinet.com/support-forum-92/fortisase-ztna-agnet-based-agent-less-issue-222561

Essence

Security posture tags convert endpoint telemetry into dynamic policy input. Authentication and tunnel connectivity do not imply compliance. The tag must be created, the intended private-access policy must match in the correct order, and traffic must still traverse the SPA hub/FortiGate/application path.

How it actually works

FortiClient evaluates endpoint posture and FortiSASE assigns tags such as compliant/non-compliant. Private-access policy uses those tags with user/source, destination, service, and policy order. If allowed, traffic continues through the SPA hub and FortiGate toward the private application. Agentless access uses a different proxy/bookmark workflow and does not automatically provide the same endpoint telemetry.

Important implementation details

  • Fortinet documents broad Allow-All private access in relevant baseline SPA use cases before posture restriction is added.
  • Posture-specific Allow and Deny policies can use dynamic tags as match criteria.
  • Policy order matters because a broad allow can match before a posture-specific rule.
  • Agent-based and agentless private access should be treated as distinct paths with different prerequisites.
  • A correct FortiSASE Allow decision is the handoff point to downstream routing, FortiGate policy, DNS, and application health.

Fortinet Secure SD-WAN — BGP route tags as dynamic SD-WAN destinations and routing-policy/service-policy coupling

Primary feature source: Using BGP tags with SD-WAN rules
Release: FortiOS 7.6.x
https://docs.fortinet.com/document/fortigate/7.6.3/administration-guide/672387/using-bgp-tags-with-sd-wan-rules
Scenario support source: Using route-map-out preferable in BGP for route-tag use in an SD-WAN rule
https://community.fortinet.com/fortigate-3/troubleshooting-tip-using-route-map-out-preferable-in-bgp-for-route-tag-use-in-an-sd-wan-rule-178513

Essence

BGP route tags create dynamic SD-WAN destination membership from routing state. The useful sequence is community/route-map policy, installed best path with a FortiOS route tag, dynamic route-tag address membership, and then SD-WAN service matching.

How it actually works

BGP receives candidate routes and attributes. Route-map logic can match a community and set a FortiOS route tag. Best-path selection decides which tagged route is installed. A firewall address object of type `route-tag` represents the installed prefixes with that tag, and an SD-WAN service references the object as its destination.

Mermaid teaching diagram — synthesized from the feature model
flowchart LR
B[BGP route] --> C[Community match]
C --> R[Set route tag]
R --> P[Best path installed]
P --> D[Route-tag address]
D --> S[SD-WAN service]

What to notice: the diagram shows the exact product-specific handoffs discussed in this chapter.

Important implementation details

  • Fortinet's example matches community `30:5` and sets route tag 15.
  • `set type route-tag` with `set route-tag 15` creates dynamic address membership from installed routing state.
  • BGP Established does not imply the desired prefix was received, selected, tagged, or installed.
  • A tagged non-best path may not populate the intended dynamic destination.
  • SLA-aware designs can deliberately change BGP community/tag behavior so service eligibility follows path quality.

Configuration / diagnostics

config router route-map
    edit "comm1"
        config rule
            edit 1
                set match-community "30:5"
                set set-route-tag 15
            next
        end
    next
end
config firewall address
    edit "DataCenter_route_tag_15"
        set type route-tag
        set route-tag 15
    next
end

Evidence interpretation

ObservationWhat it provesWhat it does not prove
BGP neighbor is EstablishedThe BGP session is up.The desired prefix is installed with the expected tag.
Received path has community 30:5The route arrived with that attribute.That path is best or has populated the route-tag object.
Installed best path has RouteTag 15Routing policy and best-path selection produced the expected tag.The SD-WAN service matched the current user flow.
Dynamic route-tag destination is emptyNo currently installed route satisfies that route-tag object.SLA thresholds are the cause.

Production troubleshooting scenario

A desired BGP path arrives with the correct community, but an untagged path wins best-path. The route-tag dynamic destination stays empty, so lowering SD-WAN SLA thresholds is irrelevant. Fix the route-policy/best-path outcome first. In an SLA-coupled design, a spoke may intentionally change community preference when an overlay fails, causing hub route-tag membership and SD-WAN service eligibility to change.

Design guidance

Document the semantic mapping from BGP community to FortiOS route tag to SD-WAN service. Operations should be able to explain why a prefix entered or left a service without reading the route-map line by line.

Key takeaway: BGP route tags create dynamic SD-WAN destination membership from routing state. The useful sequence is community/route-map policy, installed best path with a FortiOS route tag, dynamic route-tag address membership, and then SD-WAN service matching.
