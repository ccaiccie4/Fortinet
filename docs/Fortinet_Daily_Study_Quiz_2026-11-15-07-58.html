FortiGate · FortiOS 8.0.0

IPsec pre- versus post-encapsulation fragmentation: keep GTP-U whole without hiding reassembly cost

Open editable draw.io diagram · Open standalone SVG

Why the setting matters. IPsec adds ESP headers, padding, an integrity tag and sometimes UDP NAT-T overhead. A packet that fits the tunnel interface's inner MTU can therefore exceed the physical underlay MTU after encryption. FortiOS exposes the fragmentation point with ip-fragmentation under the phase1 interface. The two modes are not interchangeable performance toggles: they decide which packet the receiver must reassemble and which device bears that work.

Packet mechanics

Pre-encapsulation fragments the original inner packet before encryption. If a large GTP-U/UDP packet exceeds the tunnel MTU, the sending FortiGate splits the inner IPv4 packet, encrypts each fragment as its own ESP packet, and transmits several ESP packets. The receiving FortiGate decrypts each ESP packet and forwards the inner fragments unchanged. Reassembly is left to the downstream host. This can avoid outer IP fragmentation and can help in some NPU/PMTUD environments, but it is a poor fit when the receiving GTP-U node expects one complete UDP datagram and does not reassemble fragmented inner traffic.

Post-encapsulation encrypts the complete inner packet first. If the resulting outer ESP packet exceeds the underlay MTU, the outer IP packet is fragmented. The receiving FortiGate reassembles the outer ESP packet, decrypts it, and forwards the original complete GTP-U packet. This is the RFC-compliant default. The important distinction is that the downstream node sees a whole inner packet, while the receiving FortiGate must process outer fragments. The method is applied by the encrypting side, so configure both peers if both directions can carry oversized packets.

Do not assume that post-encapsulation eliminates fragmentation. It moves fragmentation outside the encrypted payload. Also check the tunnel interface MTU: packets larger than that interface MTU are fragmented before IPsec processing regardless of the selected post-encapsulation behavior. The cleanest design is to size the GTP-U endpoint MTU so the ESP packet fits the underlay. Fortinet's deployment example calculates an SA MTU of 1422 bytes for a 1492-byte underlay with AES-CBC/SHA-256 and no NAT-T; AES-GCM has lower ESP overhead.

Configuration and verification

On each sending peer, inspect the phase1 object and explicitly set the intended mode. For the common GTP-U case where the downstream node must receive a complete datagram, use:

config vpn ipsec phase1-interface
    edit "mobile-core"
        set ip-fragmentation post-encapsulation
    next
end

Check the tunnel interface MTU separately; changing the fragmentation mode does not raise it. A representative interface override is:

config system interface
    edit "mobile-core"
        set mtu-override enable
        set mtu 1422
    next
end

Use a downstream capture to distinguish inner from outer fragmentation. A filter for UDP/2152 plus non-zero IPv4 fragment offsets shows whether the downstream node receives fragmented GTP-U. In a pre-encapsulation case, fragments appear after decryption on the clear side. In a successful post-encapsulation case, the underlay may carry outer fragments, but the clear-side capture should show a complete UDP/2152 datagram.

Throughput and failure interpretation

Post-encapsulation can reduce throughput because the receiving FortiGate must reassemble outer fragments. On NP7/NP7Lite platforms, when the Host Protection Engine shaper is enabled, ESP packets and IP fragments sent to the CPU can be rate-limited. Inspect HPE_IPSEC_ESP and HPE_IP_FRAG counters with the platform-supported NPU diagnostic. If they increase during the test, calculate expected packets per second and raise esp-max and ip-frag-max with headroom; extreme values effectively remove CPU protection and are not a safe default.

Fragment reassembly memory is another independent limit. Fortinet documents a default 32 MB reassembly buffer. When exhausted, ReasmFails increases; orphan fragments can remain until timeout and amplify pressure on a lossy link. Check diagnose snmp ip frags and socket-memory counters while reproducing. The configurable fragment-memory threshold has a documented range of 32–2047. Increase it only after measuring peak fragment memory, not as a first response to packet loss.

Operational sequence: capture the clear-side packet, confirm the phase1 mode on the sender, check the tunnel MTU, then measure HPE drops and reassembly failures on the receiver. A successful IKE/ESP SA proves control-plane establishment, not successful inner-packet delivery. A complete downstream GTP-U datagram proves reassembly worked for that sample, not that the receiver has enough CPU for the sustained peak rate.

The case also documents receiver-side HPE and reassembly-memory bottlenecks after changing the fragmentation mode. FortiManager · FortiManager 8.0.0

Recurring policy-package installation: schedule the deployment, then prove each device result

Open editable draw.io diagram · Open standalone SVG

Purpose. FortiManager 8.0 adds recurring scheduling for policy-package installation. This is useful when a standard change must reach a defined group of managed FortiGates at a repeatable maintenance time. The schedule is a deployment trigger attached to a policy package; it does not turn the install into a transaction that guarantees every target succeeds.

Objects and execution path

The important objects are the ADOM, policy package, managed-device selection, schedule definition and install task. The policy package remains the source of the intended policy and device settings. The schedule adds recurrence metadata: start date/time, recurrence pattern (daily, weekly or monthly), and an end date. The Install Wizard still determines what package and device settings are being installed and which managed devices are in scope.

The documented workflow starts in Policy & Objects. Select the policy package, open the Install Wizard, choose Install Policy Package & Device Settings, and use Schedule Install rather than starting an immediate install. Define the recurrence and window, select the target devices, and save. A clock indicator appears beside the package when a schedule is attached; opening that indicator exposes the schedule details. The schedule can be reviewed or removed without confusing it with the current package revision.

At the scheduled time, FortiManager creates the install work and communicates with each selected device over its management channel. Each device has its own validation and install result. A package can therefore be scheduled correctly while one device is unreachable, another fails syntax verification, and a third installs successfully. The scheduler is responsible for when the task is initiated; it does not make the fleet update atomic.

Change control and configuration example

Before creating the schedule, make sure the package has been reviewed and the target list is explicit. The feature is GUI-driven; the documented path is the Install Wizard rather than a new CLI scheduler object. Treat the schedule as a change-control record: record the package name, ADOM, selected devices, recurrence, start time and end condition. Avoid overlapping recurring schedules for the same devices, especially when another automation may install policy or device settings at the same time.

For a weekly branch rollout, select the branch package, choose Install Policy Package & Device Settings, set a weekly recurrence during the maintenance window, select only the branch devices, and save. If the package is changed after the schedule is created, do not assume the old preview still describes the next run. Re-open the package and verify exactly what will be installed before the next scheduled execution.

Verification and failure boundaries

Use the package's clock indicator to verify the schedule definition. Then use Task Monitor and the installation history to verify that the task actually ran and inspect the per-device result. A scheduled entry is evidence of intent, not evidence of deployment. A successful task summary is also not enough if a subset of devices failed; inspect each device result and compare the device's installed configuration with the intended package.

The recent Community install-failure case is a useful reminder of per-device schema boundaries: a FortiManager release attempted to install an attribute unsupported by a particular FortiGate model/firmware combination, and verification failed before changes were applied. The correct response is not to keep retrying the same schedule. Inspect the verification report, identify the unsupported command and affected model, then correct the package or use a supported model-specific override before the next run.

Other common failure classes are an FGFM tunnel that is down, a device moved to another ADOM, a package that has not been installed or synchronized as expected, or a target list that changed after the schedule was created. Check device authorization and connectivity before the maintenance window. If a scheduled install fails, preserve the task output, fix the specific validation or reachability issue, and use a controlled retry rather than creating duplicate schedules.

Operational implication: recurring installation reduces repetitive operator initiation, but it increases the importance of package hygiene, target selection and post-run verification. Build a pre-window checklist and a post-window report that records success/failure per device. Never infer fleet-wide success from the presence of a schedule or one green device.

FortiAnalyzer · FortiAnalyzer 8.0.0

AI Access Visibility: understand the log lineage behind each dashboard number

Open editable draw.io diagram · Open standalone SVG

What the dashboard measures. AI Access Visibility is not a packet mirror and it is not a universal inventory of every generative-AI session. It is an analytics view built from supported FortiGate security logs. The FortiGate must be authorized to send logs to the correct FortiAnalyzer ADOM, and the relevant inspection profiles and logging must produce the events that the dashboard consumes. A blank widget can therefore mean no observed activity, but it can also mean missing source logs, incomplete feature coverage, a time filter mismatch or a broken log path.

Data sources and aggregation

FortiAnalyzer's AI Access Visibility view uses several FortiGate log families. DLP logs provide sensitive-data detections and policy outcomes. DNS Filter logs can carry FortiGuard AI Technology category classification. Web Filter logs can also provide AI category information. Application Control logs identify Generative AI applications. These sources are complementary: one may indicate an application category, another a sensitive-data event, and another a blocked or allowed action. They should not be treated as interchangeable evidence.

The dashboard groups that data into three useful views. Gen AI Access Threats summarizes DLP violations, threats detected/alerted/blocked and sensitive-data detections. Overview summarizes observed applications and users, including blocked and allowed applications. Categories groups observed AI applications by category and displays sanctioned/unsanctioned status. That sanctioned label is supplied through FortiGate configuration/metadata; it is not a verdict that FortiAnalyzer independently derives from user behavior.

ADOM and time-range filters matter. A FortiGate may be authorized but still not produce the required event type if the relevant profile is absent or logging is disabled. A device can send traffic logs while missing DNS, Web Filter, Application Control or DLP evidence. The dashboard only aggregates what arrives and matches its data model. It cannot infer an unlogged SaaS transaction.

Configuration and evidence checks

Start by confirming the FortiGate is authorized in the intended ADOM and that its logging destination is correct. On the FortiGate, verify the FortiAnalyzer connection and test connectivity. On the Analyzer, inspect the receive path and log rate before changing dashboard filters. Then verify the specific security profiles and logging settings that generate DLP, DNS Filter, Web Filter and Application Control events. Ensure the relevant AI Technology and Generative AI classifications are available for the FortiGuard service version in use.

For example, if the dashboard shows application activity but no sensitive-data events, do not assume the DLP widget is broken. Check whether the relevant DLP sensor is applied to the policy and whether the action is configured to log. Conversely, if all widgets are empty after an upgrade, first verify the log pipeline and source authorization rather than changing the dashboard. The recent Collector-to-Analyzer forwarding case illustrates this boundary: a certificate common-name mismatch left the collector's server-authentication state at Query and the forwarding connection disconnected. That is a source transport/authentication failure, not an AI classification problem.

Interpretation and troubleshooting

Use the widgets to ask different questions. A rise in blocked applications indicates enforcement events were logged; it does not prove all AI access was blocked. A large sanctioned category may simply reflect the configured sanctioned attribute. A threat count is a count of events that matched the source log model, not a full incident count. A user count depends on identity visibility and log normalization.

When a number looks wrong, compare the same time window in raw FortiGate logs and FortiAnalyzer Log View. Check ADOM selection, time zone, device authorization, receive rate, and whether the expected log family exists. If the source logs are present but a widget is empty, inspect category mapping and dashboard filters. If logs are absent, repair the FortiGate-to-FortiAnalyzer path first.

What evidence proves: a populated widget proves FortiAnalyzer received and aggregated matching source events. It does not prove complete AI traffic coverage, successful DLP enforcement for unlogged sessions, or that the user identity is always accurate. Treat the dashboard as a visibility layer whose quality is bounded by source inspection, logging and transport.

Recent scenario: A November 13 Community case reported FortiAnalyzer Collector-to-Analyzer log forwarding disconnected after an upgrade, with a certificate common-name mismatch. It is useful as a source-pipeline failure example; it is not the AI Access Visibility feature definition. Open Community scenario

FortiSwitch · FortiSwitchOS 8.0.0

Automatic clock-source selection: PTP first, NTP second, local time last

Open editable draw.io diagram · Open standalone SVG

Why automatic source selection exists. Time is a dependency for log correlation, certificate validation, scheduled jobs and authenticated management protocols. FortiSwitchOS 8.0 introduces an automatic system-time mode that selects the best available source in a defined priority order: Precision Time Protocol (PTP), then Network Time Protocol (NTP), then manually configured local time. The setting is a source-arbitration policy; it does not mean every source is healthy or that a configured NTP server is currently selected.

Source hierarchy

PTP is preferred because it can provide tighter synchronization in supported Layer 2/Layer 3 timing designs. NTP is the next choice and is appropriate for enterprise network infrastructure when a common, reliable time hierarchy is available. Manual local time is the fallback when neither PTP nor NTP can discipline the clock. The switch can therefore remain operational with a clock even when an upstream timing source disappears, but the quality of that clock may be lower. Do not treat the presence of a local time value as proof of synchronization.

The configuration separates the overall selection mode from the individual source settings. In automatic mode, the switch evaluates the available candidates and uses the highest-priority valid source. PTP configuration still needs a compatible PTP domain/profile and a path that delivers timing messages. NTP still needs server reachability, DNS resolution if names are used, correct source-interface behavior and a consistent time hierarchy. Manual time is a fallback value, not a replacement for a reliable reference.

Configuration and verification

Enable automatic selection in the global system-time configuration:

config system global
    set system-time-mode auto
end

Then configure the PTP and NTP candidates that are appropriate for the deployment. Do not remove the NTP server merely because PTP is preferred; NTP is the fallback when PTP is unavailable. If the switch is a managed device, coordinate the time-source policy with the rest of the network so FortiGate, FortiSwitch, controllers and monitoring servers do not drift onto unrelated time trees.

Verify actual selection, not just saved configuration. Use diagnose sys ntp status to inspect NTP synchronization, selected server, reachability, stratum and clock offset. Check PTP status separately using the PTP diagnostic/status view for the release. Record the current UTC offset and compare it with the management server. A server listed as reachable does not prove that it is selected or that the clock offset is acceptable.

Operational failure pattern

SNMPv3 User-based Security Model uses engine time and boots counters to resist replay. A monitoring server and a switch that use different NTP references or stratum tiers can drift far enough that an otherwise valid SNMPv3 request is rejected as outside the time window. The important diagnostic is not simply “NTP enabled”; compare the selected server, stratum, clock offset and jitter on both ends. The protocol's time-window protection can reject requests even when credentials and authentication keys are correct.

When troubleshooting, first verify that the switch selected the intended source. If PTP is selected but its timing path is unstable, inspect the PTP domain and network path. If NTP is selected, compare the server and stratum against the monitoring host. If local time is selected, restore a valid PTP/NTP source rather than repeatedly setting the clock by hand. A common reference for all infrastructure devices and monitoring systems is more important than a high stratum number on one device.

Caveats

Automatic selection is a priority policy, not a promise of zero time step or zero drift. A source can become valid or invalid during operation, and logs around a source transition should be correlated with the selected-source state. Scheduled maintenance, certificate validation and SNMPv3 polling can all be affected by time jumps. Validate time synchronization before investigating authentication failures that could actually be replay-window or certificate-validity problems.

Operational implication: source configuration answers what the switch may use; source status answers what it is using. Always capture both before concluding that a time-dependent protocol is misconfigured.

FortiAP/Wireless · FortiOS/FortiAP 8.0.0

Disable radio VAP broadcast without deleting SSID configuration

Open editable draw.io diagram · Open standalone SVG

Operational use. Administrators sometimes need to stop a radio from advertising its configured WLANs during a maintenance window, a coverage test or a temporary service change, while preserving the SSID/VAP objects for later restoration. FortiOS 8.0 adds a radio-level VAP status control for FortiAP and FortiWiFi local radios. The key benefit is that the radio's configured VAP assignments can remain in place while broadcasting is disabled.

Profile and device scope

The WTP profile is the reusable configuration object applied to managed FortiAPs. Within the profile, each radio has its own VAP broadcast state. Setting vap-status disable under the radio suppresses broadcasting of all configured SSIDs on that radio. It does not delete the SSID object, remove the VAP from the profile, or change the SSID security settings. When the status is re-enabled, the configured VAPs can be advertised again without rebuilding the WLAN configuration.

Some maintenance actions are intended for one AP rather than every AP that uses a profile. For that case, the per-device WTP configuration provides an override. The override must be enabled before the device-level value takes precedence. This is a common source of confusion: an administrator changes the shared profile, but a local override on one AP continues to control that AP's radio. Conversely, a profile change can affect every AP that inherits the profile if no local override is active.

Configuration example

To suppress the VAPs on the second radio in a profile, use the radio-specific setting:

config wireless-controller wtp-profile
    edit "branch-ap-profile"
        config radio-2
            set vap-status disable
        end
    next
end

For a single AP, enable the override in that WTP entry and set the radio status there. Keep a record of whether the change is profile-wide or device-specific so the next profile edit does not unexpectedly restore or re-suppress the WLAN.

Verification boundaries

Read back the WTP profile and the managed WTP configuration. Confirm the radio index is correct and that the VAP status is disabled at the intended scope. A wireless beacon capture should show that the affected SSIDs are no longer advertised. The SSID/VAP objects should still be visible in the configuration. After re-enabling, verify beacon transmission and then test client association and authentication.

Do not equate “no beacon” with “the AP is offline.” CAPWAP control connectivity can remain healthy while a radio stops advertising VAPs. Likewise, a CAPWAP DTLS peer disconnect is not the same failure. In a recent Community scenario, AP leave/join behavior was associated with missed CAPWAP keepalive responses on the uplink network; the investigation required AP and FortiGate CAPWAP debug plus switch-port mirror captures. That symptom points to the management/control path, not a deliberate VAP broadcast state.

Common mistakes and troubleshooting

If an SSID remains visible after a profile change, check whether the AP has a per-device override. If all SSIDs disappear but the AP remains online, inspect the radio's VAP status before rebuilding the WLAN. If the AP itself disappears from the controller, inspect CAPWAP keepalives, DTLS and the uplink network; do not assume the radio status caused the controller disconnect.

When a radio is re-enabled, the existence of the SSID object is not enough. Confirm that the VAP is still assigned to the radio, that the AP received the updated profile and that the SSID's security and VLAN dependencies remain valid. A successful profile install proves that the configuration was delivered; a beacon capture proves that the SSID is actually being advertised.

Mechanism-to-implication: the feature changes the broadcast state of VAPs, not the identity or configuration of the SSIDs. That distinction makes maintenance reversible and reduces accidental WLAN recreation.

Recent scenario: A November 3 Community case describes AP leave/join events caused by missed CAPWAP keepalives. It is a separate control-plane failure: a VAP broadcast disable should not be diagnosed as a DTLS peer disconnect. Open Community scenario

FortiNAC · FortiNAC 9.4.0

FortiNAC 9.4 dashboard widgets: discovery, activity, logical access and RADIUS outcomes

Open editable draw.io diagram · Open standalone SVG

What changed in 9.4. FortiNAC 9.4 adds four dashboard widgets that expose different parts of the host-access lifecycle: Recent Hosts, Top Host Activity, Logical Network Access and RADIUS. These widgets are useful because they answer different operational questions. They should not be treated as four views of the same metric or as a replacement for host-level investigation.

Read each widget as a different evidence source

Recent Hosts displays newly discovered hosts by type. It is a discovery view: it helps an operator notice new endpoint populations, unexpected device types or a sudden increase in unknown devices. It does not prove that a host has authenticated, been registered, or received the intended network access.

Top Host Activity displays hosts with the most connection activity over a configurable period. It is useful for spotting endpoints with unusual connection volume, repeated reconnects, a possible loop or a host that is repeatedly moving between access points. It is not a traffic-volume chart and should not be interpreted as proof of malicious behavior without examining the underlying connection records.

Logical Network Access displays hosts that had access to each Logical Network over a configurable period. It is a useful way to answer “which hosts were seen with access to this logical network?” It does not necessarily tell you why access was granted or whether a current session is still active. The selected time window matters; a host may appear because it had access earlier in the interval.

RADIUS displays authentication success/failure information over specified time frames. It is the fastest place to identify an authentication failure spike, but a success counter is not the same as a completed authorization workflow. A RADIUS Access-Accept can be followed by VLAN assignment, posture evaluation, host registration or network-device actions that still fail.

Practical triage sequence

Start with Recent Hosts to see whether the endpoint was discovered at all. If it is absent, investigate discovery, VLAN reachability, device polling and host visibility before changing authentication policy. If it is present, use RADIUS to determine whether the authentication transaction succeeded. A failure spike points toward credentials, server selection, policy or a network-device request. A success result means the RADIUS exchange completed; it does not prove the endpoint landed in the correct logical network.

Next use Logical Network Access to see whether the host appears in the intended network. If RADIUS succeeds but the host is absent from the expected logical network, investigate authorization attributes, role mapping, VLAN assignment and the network device's application of the returned result. Finally, use Top Host Activity to identify whether the endpoint is repeatedly reconnecting or generating an unusually high number of connection events.

Configuration and interpretation

The widgets are added and arranged on the FortiNAC dashboard. Configure the time window deliberately and keep the same interval when comparing widgets. A one-hour RADIUS view compared with a 24-hour activity view can create a false narrative. When an incident begins, note the dashboard time zone and time range, then drill into the host and underlying event records for the same interval.

For a site with a new access switch, a burst of Recent Hosts may be expected. If RADIUS success is high but Logical Network Access is low, verify whether the switch is returning the expected role/VLAN attributes and whether FortiNAC recognizes the logical network. If Top Host Activity is dominated by one endpoint, inspect its connection timeline before disabling the account; repeated activity can also be caused by roaming, link flaps or repeated authentication attempts.

What the widgets prove—and what they do not

A widget is an aggregation layer over FortiNAC's observed host and access data. It is useful for prioritizing where to investigate, not for proving the complete packet path. Recent Hosts proves that discovery data exists for the displayed host type. Top Host Activity proves that connection events were counted in the selected window. Logical Network Access proves that the host was associated with that logical network during the window. RADIUS proves that authentication success/failure events were recorded.

None of these alone proves the current switch port state, the exact VLAN on the wire, or that a firewall policy allowed the application. For a disputed access decision, correlate the widget with the host record, RADIUS request/response attributes, network-device logs and a packet capture where needed. The benefit of the new dashboard is faster navigation between evidence classes—not replacement of those underlying records.

FortiNAC-F · FortiNAC-F 7.6.0

Maximum concurrent sessions: accounting-backed limits for registered and logged-in hosts

Open editable draw.io diagram · Open standalone SVG

Purpose. Maximum concurrent sessions prevents a user from accumulating more endpoint sessions than the organization allows. FortiNAC-F exposes the limit globally and at the individual-user level, with two distinct counters: Registered Host and Logged in Host. These are different definitions of “session,” and choosing the wrong one changes what the policy actually limits.

Registered Host versus Logged in Host

A Registered Host limit counts endpoints registered to a user. It is useful when the objective is to limit how many devices a user may own or register, regardless of whether they are actively connected at this moment. A Logged in Host limit is about active authenticated connections. It is more appropriate when the objective is to restrict simultaneous access sessions. The two counters are not interchangeable: a user can have several registered endpoints but only one currently logged in, or can have stale registration records that remain after a device is no longer used.

Fortinet explicitly notes that accounting must be enabled to obtain the correct number of sessions. For RADIUS-backed access, accounting start/stop messages let FortiNAC correlate the beginning and end of a session. If the access device does not send accounting, or if an accounting stop is lost, the displayed active-session state can lag reality. The feature supports Captive Portal without host logout, VPN, 802.1X/MAB, and Agent without logout/delete host. These supported types reflect the need for FortiNAC to observe session lifecycle events.

Scope and precedence

A global limit is configured under Settings > User/Host Management > Allowed Hosts. It can be applied to Registered Host or Logged in Host and affects all users. An individual limit is configured under Users & Hosts > User Accounts and applies to the selected user. If the global and user-level values conflict, the individual user's setting overrides the global setting for that user. The feature is not available at user-group scope; Fortinet excludes group-level settings to avoid a conflict between group and individual overrides.

Before enabling a limit, decide whether the policy is about registered devices or concurrent logins. Document the expected number, test a user with a known number of registered hosts, then test active sessions using an authentication method that produces reliable accounting. Do not apply a very low global limit before validating accounting behavior; otherwise an accounting gap can look like a user exceeded the limit.

Evidence and troubleshooting

Check that accounting is enabled on the relevant access device and that start/stop records arrive. For RADIUS, inspect the Access-Request/Accept and Accounting-Start/Stop transaction separately. A successful authentication proves that credentials were accepted; it does not prove that the session was later closed or removed from the active count. When a user disconnects, confirm the NAS sends a stop or responds successfully to a Disconnect-Request.

A recent FortiNAC-F Community case illustrates this boundary. After a role change, FortiNAC sent a Disconnect-Request, but the access device returned Disconnect-NAK because required session-identifying attributes were missing. The client stayed in the old VLAN until reconnect. The lesson for session limits is that a disconnect request is only an attempted action. Capture the RADIUS exchange and confirm Disconnect-ACK or a subsequent accounting stop before assuming the active session disappeared.

If the limit is reached unexpectedly, compare Registered Host and Logged in Host counts. Verify whether the user has a per-user override. Then inspect stale sessions, accounting records and disconnect outcomes. If the count is wrong only for one authentication method, confirm that method is supported by the limit feature and that the device sends the expected accounting messages.

Operational caveats

Do not assume a user-group limit exists. Do not assume every authentication method provides a reliable logout signal. Do not assume deleting a host record is equivalent to receiving an accounting stop. The enforcement decision is only as accurate as the lifecycle evidence FortiNAC receives. A good rollout starts with monitoring-only validation, followed by a small user pilot, then a global policy after accounting quality is proven.

FortiAuthenticator · FortiAuthenticator 6.6.7

SHA-1 removal: migrate certificate signing before upgrading

Open editable draw.io diagram · Open standalone SVG

Release boundary. FortiAuthenticator 6.6.7 removes support for SHA-1 cryptographic operations. Fortinet's special notice specifically tells administrators to update SHA-1 certificate signing to SHA-2 or above. If that cannot be done, the release note documents a downgrade to 6.5.3 as the fallback for SHA-1 support. For a production deployment, the preferred plan is to migrate the affected certificate and signing workflows rather than remain on an older release.

What SHA-1 means in a certificate

Do not confuse a certificate's public-key algorithm with its signature digest. An X.509 certificate contains a public key (for example, RSA or ECDSA) and a signature created by the issuer. The signature algorithm combines a public-key signature scheme with a digest such as SHA-1 or SHA-256. An RSA key can therefore be used in a certificate whose signature digest is SHA-1. Replacing a 2048-bit RSA key with another 2048-bit RSA key does not fix a SHA-1 signature.

FortiAuthenticator can participate in certificate management and authentication workflows. The relevant migration inventory is not just the certificate currently bound to the GUI. Review certificates issued by a local CA, certificates used for EAP-TLS or other client authentication, signing profiles, and any external relying party that validates a certificate chain issued by FortiAuthenticator. The release note is explicit about certificate signing; do not broaden it into an unsupported claim that every SHA-1 occurrence in every remote system is automatically rejected.

Inventory and remediation

Before upgrade, export the certificate inventory and inspect the signature algorithm of each certificate and CA certificate. A certificate inspection tool can show the signature algorithm separately from the public-key algorithm. Identify whether the SHA-1 use is in a leaf certificate, an intermediate CA, a root certificate, or a signing profile that will issue new certificates. A new SHA-256 leaf signed by a SHA-1 intermediate does not solve a weak chain.

Reissue affected certificates with SHA-256 or a stronger digest supported by the target FortiAuthenticator release and the relying systems. Update the CA chain and distribute new trust anchors where needed. Test the full authentication path: certificate presentation, chain validation, revocation checking, user mapping and final authorization. Do not stop at “certificate imported successfully”; the relying party must trust the new chain and the intended identity must still map to the correct user.

For a certificate used in EAP-TLS, test both supplicant and RADIUS server behavior. For an administrative or SAML signing certificate, test the service provider's trust and metadata refresh. Keep the old chain available during a controlled overlap where the protocol allows it, but do not leave SHA-1 signing active after the upgrade. Record certificate serial numbers, expiry, subject/SAN, issuer and signature algorithm in the change plan.

Evidence and diagnostic boundaries

The most useful evidence is the actual certificate signature algorithm, the issuer chain, the FortiAuthenticator version and the operation that failed. If a certificate is rejected after upgrade, confirm whether FAC is being asked to verify or create a SHA-1-signed object. A larger key, a different CA subject name or a successful TLS handshake to an unrelated server does not prove that the affected signing operation is SHA-2 compatible.

A recent Community case reported FSSO Mobility Agent NTLM failures after a Windows security update, with NT_STATUS_MORE_PROCESSING_REQUIRED. That is a separate authentication mechanism. NTLM signing behavior is not the same as the SHA-1 digest used in an X.509 certificate signature. When troubleshooting, identify the layer from the error and logs before changing certificates or weakening authentication settings.

Upgrade decision

Use a staged upgrade: inventory, reissue, deploy, validate relying parties, then upgrade FortiAuthenticator. If an indispensable integration cannot move off SHA-1, document the dependency and the vendor-documented compatibility fallback; do not treat a downgrade as equivalent to a security fix. The release note's point is algorithm removal, not a cosmetic warning.

Operational implication: cryptographic deprecation is a dependency-discovery exercise. The hard part is finding every certificate or signing workflow that depends on the removed digest and proving the new chain works end to end.

Recent scenario: A November 13 Community report describes an NTLM signing compatibility issue after a Windows security update. It is deliberately used as a contrast: NTLM signing and X.509 certificate signature digests are different cryptographic layers. Open Community scenario

FortiPAM · FortiPAM 1.9.0

Auto-provisioned user lifecycle: inactivity disable first, purge only after disabled retention

Open editable draw.io diagram · Open standalone SVG

What 1.9 adds. FortiPAM 1.8 introduced automatic disabling of auto-provisioned users after prolonged inactivity. FortiPAM 1.9 adds the second stage: automatically purging disabled auto-provisioned users after a configurable disabled-retention period. This is a lifecycle policy, not a general cleanup of every user account in the system.

Two independent timers

The first timer is User Max Inactivity Days. When an auto-provisioned user has been inactive for the configured number of days, FortiPAM disables the account. The documented default is 180 days and the range is 0–3650. A value of 0 disables this stage, so inactive auto-provisioned users remain in the system indefinitely. Fortinet notes that disabling inactive accounts frees user license seats and generates a system log entry visible under the User Events area of System Event logs.

The second timer is User Max Disabled Days. It starts after the account is disabled. When the disabled duration reaches the configured threshold, FortiPAM deletes the disabled auto-provisioned user. The documented default is also 180 days, with a range of 0–3650. A value of 0 disables automatic deletion, so disabled users remain indefinitely. These two values are not a single “inactive for X days then delete” setting; they define two separate lifecycle stages.

The feature is located in the Provisioned User Auto-purging pane under System > Settings > Advanced. The user must be auto-provisioned for this cleanup workflow to apply. Do not assume a manually created local user will be disabled or deleted by the same policy. The source of the account matters.

Configuration and rollout

Before enabling the feature, identify which provisioning rules create users and confirm that the external identity source is authoritative. Set the inactivity threshold to the period that reflects actual privileged-access usage, then set disabled retention to a longer interval that gives administrators time to detect an accidental disable and recover the account through the normal provisioning process. If the organization needs indefinite retention for disabled identities, set User Max Disabled Days to 0.

Example policy: retain an auto-provisioned user for 180 inactive days, disable it, then retain the disabled record for another 90 days before deletion. The two stages mean a user can exist for up to 270 days without activity before purge, assuming the timers are not reset by renewed activity or re-provisioning. Test this with a non-production identity before applying the values globally.

Evidence and safety boundaries

When a user is disabled, check the User Events system log. The log entry proves that the lifecycle engine disabled the account; it does not prove that the account was deleted. When the disabled-retention period expires, verify the user record is gone and confirm that the external provisioning source will not immediately recreate it. If the source still asserts that the user is entitled, the account may be provisioned again. This is why the external identity source and the FortiPAM cleanup policy must agree.

Do not assume that deleting a user also deletes or transfers every secret, folder, launch configuration or audit record associated with that user unless the product documentation explicitly describes that behavior. Review ownership and access dependencies before enabling automatic purge. Preserve the audit trail and ensure another authorized administrator can still reach critical secrets.

Troubleshooting

If an inactive user remains enabled, verify that the account is auto-provisioned, that User Max Inactivity Days is not 0, and that the actual inactivity timestamp is older than the threshold. If a disabled user is not purged, check User Max Disabled Days and confirm it is not 0. If a user disappears unexpectedly, inspect the two thresholds and the provisioning source before restoring the account.

A recent Community report about HTTP 400 errors during secret launch after passkey registration and an AD password change is a useful contrast. That issue involved the internal WAD launch parser; it was not a user lifecycle event. A launch error should not be “fixed” by changing auto-purge thresholds.

Operational implication: the two timers control license reclamation and identity retention separately. Use the disable stage to reduce inactive account exposure and the purge stage to enforce a defined retention policy, with audit and ownership review before deletion.

Recent scenario: A November 6 Community report describes an HTTP 400 secret-launch failure after passkey registration and an Active Directory password change. This is a separate WAD launch-path issue, not evidence of user auto-purge. Open Community scenario

FortiSIEM · FortiSIEM 7.5.0

ClickHouse Event Log Integrity: validate archived event partitions and interpret every status

Open editable draw.io diagram · Open standalone SVG

Purpose. FortiSIEM's Event Log Integrity function lets an auditor validate that archived event data stored in ClickHouse has not been altered. The feature compares the stored checksum with a newly calculated checksum for the selected event-log partition. It is an integrity check, not a backup, retention policy or availability test. Fortinet explicitly notes that this ClickHouse function is not available for Elasticsearch.

Data model and status table

Navigate to Admin > Settings > Database > Event Integrity. The view can be filtered by From/To time and by status: All, Not Validated, Success, Failure or Not Found. Each row represents an event-log file/partition associated with a shard. The table exposes the earliest and latest event time, shard ID, partition ID, partition name/path, validation status and checksum.

The status values have distinct meanings. Success means the checksum matched and the log file was not altered according to the validation. Failure means the checksum comparison failed and the log data was altered. Not Found means the log event/partition has been removed or detached. System Error indicates a shell-command or parsing error during validation. Not Validated is not a failure; it means the integrity check has not yet been run.

A blank Partition Name or Validation Status can also be meaningful. Fortinet notes that if ClickHouse cannot consolidate event data—for example, because there is insufficient storage—the partition name and validation status can appear blank. Do not classify a blank row as tampering. First check consolidation and storage health.

Manual and automatic validation

For a single event log, select the row and click Validate. For several, use Ctrl/Command selection and click Validate. Validate All triggers validation for every displayed event log. After the operation, review the Validation Status and checksum, and retain the result with the audit evidence. Use the time range to isolate the period relevant to the investigation rather than validating all partitions during peak production load without planning.

Automatic validation is controlled by the Event Integrity drop-down. When set to On, ClickHouse integrity checking runs when it consolidates data. Fortinet documents this as resource-intensive and therefore Off by default. Enabling it changes the cost profile of the consolidation process. In a large deployment, plan the resource impact and monitor storage/CPU before enabling it across the full event database.

How to interpret a result

A Success status proves that the checksum calculated during validation matches the recorded checksum for that partition. It does not prove that the original event source was truthful, that every event was collected, or that the event was not deleted before the archive was created. A Failure is a strong integrity signal; preserve the partition identity, checksum and validation history before taking action. A Not Found status is a partition lifecycle/availability issue, not automatically a checksum mismatch. A System Error requires investigation of the validator path itself.

When an operator reports “integrity failed,” first record the shard, partition ID/name, event-time range and exact status. If the partition is missing, inspect ClickHouse partition consolidation and storage. If the result is System Error, collect the relevant FortiSIEM logs and validation history. If it is Failure, preserve the evidence and follow the organization's incident and forensic process; do not immediately delete or rebuild the partition, because that can destroy evidence.

Operational dependencies

ClickHouse must be able to consolidate the event data. Low disk space can prevent consolidation and leave the partition name/status blank. Event Integrity is a validation mechanism layered on top of the event storage lifecycle; it does not create a second independent archive. Ensure the underlying storage and shard health are monitored. For long retention, include validation in the audit schedule and export status records for the required period.

Mechanism-to-implication: checksum comparison is meaningful only when the expected checksum and the event partition still exist. The most useful operator skill is distinguishing “not yet checked,” “checksum mismatch,” “partition absent” and “validator failed.” Those states demand different responses.

FortiSASE · FortiSASE 26.1.107

FortiExtender/LAN Extension control-plane subnet: address it separately from user IPAM

Open editable draw.io diagram · Open standalone SVG

What the subnet is for. FortiSASE's IP Management page has a separate control-plane subnet for FortiExtender and LAN Extension devices. After the 26.1.1 feature release, FortiExtender devices receive a management address from this subnet. The purpose is to avoid collisions between FortiSASE-managed edge/control addresses and customer on-premises addressing. It is not the same pool used for remote-agent and edge-endpoint IPAM.

Default and reservation behavior

The default control-plane subnet is displayed as 10.252.0.1/16. Before customization, FortiSASE also reserves 10.253.0.0/16 as a management subnet. Once a custom control-plane subnet is configured, the previously reserved 10.253.0.0/16 range is also removed. That matters for IP planning: a range that appeared unavailable before customization may become available for other use, but only after the control-plane subnet change is applied.

Fortinet documents a current caveat: saving BGP configuration overwrites the custom FortiExtender/LAN Extension control-plane subnet back to the default 10.252.0.0/16. The administrator must save the custom subnet again from Network > IP management > Advanced. This is a configuration dependency, not an IPAM allocation algorithm. It is easy to miss if a routing change is made after the subnet was customized.

Do not confuse it with remote-agent IPAM

The IPAM tab manages address pools for remote agents and edge endpoints. By default, FortiSASE uses the 100.65.0.0/16 range within the larger 100.65.0.0/16 allocation, and it can use other private pools such as 10.0.0.0/8, 100.64.0.0/10, 172.16.0.0/12 or 192.168.0.0/16. Excluded subnets prevent remote agents and edge endpoints from being allocated addresses that overlap customer networks. The control-plane subnet for FortiExtender/LAN Extension is a different setting under Advanced.

Changing the remote-agent IPAM pool has a much larger impact: Fortinet warns that remote users and edge-device users may need to disconnect and reconnect, and IPAM changes can cause traffic disruption. Do not change the remote-agent pool to solve a FortiExtender management-address collision. Select the control-plane subnet for that problem.

Configuration workflow

Before customizing, inventory the customer's LAN, WAN transit, tunnel pools, BGP router IDs, remote-agent pools and FortiExtender management addresses. Choose a subnet that does not overlap any of those ranges. In the portal, open Network > IP management > Advanced, set the FortiExtender and LAN Extension control-plane subnet, and save. Verify the assigned management addresses after the change.

If BGP is also being configured, save the BGP changes first, then return to IP management > Advanced and reapply the custom control-plane subnet. Read the value back after both operations. Do not rely on the value you remember entering before the BGP save.

Verification and failure patterns

When a FortiExtender cannot be managed or a control-plane address overlaps an on-premises subnet, inspect the control-plane subnet and the actual management address assigned to the device. Separately inspect BGP neighbor state and router IDs. A BGP session can be down because of an overlapping router ID or tunnel address even when the management subnet is correct; conversely, a management address collision can break device reachability without proving a BGP issue.

Record the configured control-plane subnet, the address assigned to each FortiExtender/LAN Extension device, and the BGP configuration save time. If the subnet reverts to 10.252.0.0/16 after a BGP change, reapply the custom value and verify again. Keep the control-plane range in IPAM documentation so future network changes do not reclaim it accidentally.

Operational implication: the control-plane subnet is an address-plan dependency for edge management. Keep it distinct from remote-user IPAM, and include a post-BGP-save check because the documented configuration interaction can silently restore the default.

Secure SD-WAN · FortiOS 8.0.0

Scheduled interface speed tests: backend coordination, measured bandwidth and shaping source

Open editable draw.io diagram · Open standalone SVG

What changed in FortiOS 8.0. Scheduled speed tests are now coordinated between the FortiGate and Fortinet's backend server. Administrators no longer configure the old retry/retry-pause parameters; the coordination logic handles the retry behavior. The second change is where measured bandwidth is consumed: the interface configuration now selects whether shaping uses manually configured or measured bandwidth. This separates running a test from deciding whether its result affects traffic shaping.

Test scheduling and traffic handling

A scheduled test is configured per interface under config system speed-test-schedule. The FortiGate coordinates with the backend to obtain the test token and execute the throughput test. The test traffic does not use the ordinary interface traffic shaper, but it is still constrained by the speed-test-specific maximum settings. The existing update-inbandwidth-maximum and update-outbandwidth-maximum values act as limits on the test; minimum values can clamp low measurements upward. If the values are exceeded or not met, the configured minimum/maximum is used instead of the raw measured result.

FortiOS 8.0 removes the old retries and retry-pause commands because retry behavior is now managed by the FortiGate/server coordination mechanism. The old update-inbandwidth and update-outbandwidth toggles are no longer used to shape the speed-test traffic. The old update-shaper field is removed. Do not copy a 7.6 configuration and assume those fields still control the test.

The new update-bandwidth-limit-unit option determines whether the min/max values are interpreted as kilobits per second or as a percentage of the interface's configured bandwidth. The default is kbps. A value intended as 50,000 kbps has a completely different meaning if the unit is percentage. Document the unit with the values and verify it after migration.

Measured result versus shaping source

The test populates measured-upstream-bandwidth and measured-downstream-bandwidth on the interface. Those fields are measurements; they do not automatically become the effective shaping values unless the interface selects them. Under config system interface, inbandwidth-source and outbandwidth-source choose either the default/manual value or the measured value. The new setting replaces the previous scheduled-test update-interface-shaping behavior.

Example configuration:

config system speed-test-schedule
    edit "wan1"
        set update-inbandwidth-minimum 10000
        set update-inbandwidth-maximum 500000
        set update-outbandwidth-minimum 5000
        set update-outbandwidth-maximum 100000
        set update-bandwidth-limit-unit kbps
    next
end
config system interface
    edit "wan1"
        set inbandwidth-source measured
        set outbandwidth-source measured
    next
end

Verification path

Before the scheduled time, run the speed-test daemon debug and observe the schedule arm, token request and test start. The debug output should show the test completing and report upstream/downstream throughput. A completed test proves that the test path ran; it does not prove the interface selected the measured values for shaping.

To prove application, inspect the interface's inbandwidth/outbandwidth source and the measured fields. For a VPN overlay, diagnose vpn tunnel list exposes egress traffic-control bandwidth. Fortinet's example shows the tunnel egress bandwidth reflecting the measured upload result. If the test completes but the shaping value does not change, check the interface source selection and the min/max clamp settings before troubleshooting the test server.

Failure and performance considerations

If the scheduled test does not run, verify the speed-test license/service entitlement, interface schedule, backend coordination and reachability of the test server. If the test runs but the measured value is unexpectedly low, consider the test path, tunnel encapsulation, available capacity and the configured maximum/minimum. The test traffic bypasses the ordinary interface shaper but can still be limited by the test-specific caps. Do not confuse those two control points.

After an upgrade, remove obsolete retry and update-shaper commands from configuration templates. Confirm that the schedule is still present and that the interface source is set to measured only where intended. A manual speed test can also update the measured fields; the interface source controls whether those values become the effective shaping inputs.

Operational implication: speed-test scheduling, test traffic limits, measured values and interface shaping are four separate mechanisms. Verify each stage. A green test result is not proof that production traffic is being shaped from the new measurement.
