1. FortiGate — Hybrid post-quantum IKEv2 key exchanges: IKE_INTERMEDIATE and CHILD_SA rekey boundaries

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortigate/8.0.0/administration-guide/229631/post-quantum-cryptography-for-ipsec-key-exchange

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and cryptographic boundary

Traditional IKEv2 exchanges an ephemeral Diffie–Hellman contribution to establish key material, but long-lived confidentiality requirements motivate a second key-exchange family. FortiOS 8.0 documents hybrid post-quantum key exchange, which supplements classical DH with one or more KEM contributions. The design is hybrid rather than a wholesale replacement: the IKEv2 control exchange must negotiate compatible additional KE groups on both peers. Encryption of ESP packets is still determined by the negotiated IPsec SA proposal; enabling a post-quantum KEM does not by itself replace the ESP cipher or prove that the peer completed the additional exchange.

Transaction sequence and objects

The IKE_SA_INIT exchange establishes the initial negotiation context. RFC 9242 IKE_INTERMEDIATE carries extra key exchanges before authentication, while RFC 9370 defines multiple key exchanges. FortiOS also documents IKE_FOLLOWUP_KE for additional exchanges during IKE SA rekey or when creating additional CHILD_SAs. Phase-1 and phase-2 interface objects have separate addke1 through addke7 settings; they are not interchangeable. Up to three key-exchange groups can be proposed per additional round. A tunnel may show an established classical IKE SA while a new CHILD_SA fails because phase-2 additional KE proposals differ.

Source-supported configuration

On both compatible FortiGate peers, open VPN > VPN Tunnels, edit the tunnel, and configure Post Quantum Cryptography Additional Key Exchanges. In the phase-1 interface CLI, Fortinet documents config vpn ipsec phase1-interface, edit <name>, set addke1 <group1> <group2> <group3>, and set childless-ike enable; phase-2 interface entries also expose set addke1 through set addke7. Group IDs and combinations must be checked against the exact release and peer capability; the example values 35 36 37 are not a blanket interoperability recommendation. Keep a rollback plan and verify both peers before introducing PQC on a production critical tunnel.

Evidence and its limits

Check the negotiated IKEv2 exchange sequence, not only the green tunnel icon. Capture UDP/500 or UDP/4500 on the correct WAN and inspect whether IKE_INTERMEDIATE appears and whether the peer rejects an additional KE proposal. diagnose vpn ike gateway list and diagnose vpn tunnel list help distinguish IKE SA establishment from CHILD_SA traffic selectors and counters; exact debug fields vary by FortiOS build. A live ESP counter proves packets use a negotiated SA, but it does not independently attest to which post-quantum group contributed to the SA key material.

Operational failure and correction

Suppose a newly upgraded hub enables addke1 while a spoke still advertises only classical IKEv2. The initial proposal exchange may proceed but authentication or subsequent CHILD_SA setup cannot complete the configured extra exchange. Compare phase-1 and phase-2 addke groups, firmware compatibility, and IKE logs on both sides; restore mutually supported transforms or stage upgrades before enforcing additional rounds. Avoid treating a generic DPD timeout as evidence of a KEM failure: a timeout may simply indicate routing, NAT, or reachability loss.

Design, HA and upgrade caveats

Each additional exchange increases control-plane messages and handshake work; measure establishment and rekey time across high-latency overlays. During FGCP failover, validate that peer state and rekey behavior converge rather than assuming a tunnel name guarantees identical security negotiation. For hybrid designs, inventory algorithm support by FortiOS release and by non-Fortinet peer where applicable, but keep this lesson's commands Fortinet-specific. The security claim is strengthened key-establishment material, not automatic protection against weak authentication, leaked preshared keys, or permissive phase-2 selectors.

Feature fingerprint: fgt-ikev2-hybrid-addke-ike-intermediate-followup-ke · Workflow: IKE_SA_INIT classical DH → IKE_INTERMEDIATE additional KEM → IKE_AUTH authenticated SA → CHILD_SA traffic keys → IKE_FOLLOWUP_KE rekey → Peer proposal/debug

2. FortiManager — Scheduled FortiSwitch packet capture: management delegation and capture evidence lifecycle

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortimanager/7.6.6/administration-guide/749365/configuring-fortiswitch-packet-captures

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and ownership

FortiManager can orchestrate a FortiSwitch packet capture without requiring the investigator to sign in independently to every managed switch. This is an operational diagnostic feature, not a forwarding policy or a passive traffic mirror. FortiSwitch devices in FortiSwitch Manager are associated with a FortiGate that manages them; choosing the wrong FortiGate or switch in the tree can produce a technically valid capture on the wrong device. Central management access and authorization therefore determine where the capture is requested, while the switch datapath determines which packets are observable.

Control and data flow

The engineer selects FortiSwitch Manager > Managed FortiSwitches, chooses the managed FortiGate scope, then a FortiSwitch. Packet Capture opens a list of filters. Create New defines the capture filter; Schedule Run optionally sets start and end times. Start Capture requests execution; a scheduled capture begins at the configured time. The result appears in Captures and can be viewed in FortiManager or downloaded as PCAP. The capture filter limits which frames are recorded, not which frames are forwarded. Captures are point-in-time observations, not continuous flow telemetry.

Configuration and validation

Create a narrow filter matching a test client's IP/MAC, VLAN, and expected protocol when the UI supports those fields. For an 802.1X failure, target EAPOL on the access port or the RADIUS exchange on the appropriate uplink; the two packets are not necessarily visible at the same interface. Use the documented Start Capture control for immediate work or Schedule Run for a reproducible maintenance window. After the run, download the PCAP and inspect timestamps, source/destination, VLAN tags and sequence. Preserve the unmodified original PCAP when escalating a case.

What the evidence proves

A capture showing a DHCP Discover arriving on the client-facing switch port proves the endpoint transmitted at that observation point. It does not prove the FortiGate received the packet, nor that the DHCP server replied. A RADIUS Access-Accept captured upstream does not prove the switch installed the returned VLAN on the client port. Conversely, an empty PCAP can mean an incorrect filter, capture window, port, switch selection, or actual absence of packets. Correlate capture timestamps with FortiSwitch port counters and FortiGate policy/session evidence.

Failure scenario

A roaming phone intermittently fails to obtain a DHCP address, but FortiManager captures show no DHCP traffic. Before blaming the DHCP server, verify the capture's FortiGate scope, FortiSwitch serial, port mapping, VLAN filter and schedule window. Repeat with a short approved test and a broad-enough filter, then narrow the scope once ingress is confirmed. If Discover is visible and Offer absent, move the capture boundary toward the uplink and FortiGate rather than repeatedly restarting the endpoint.

Scale and safety

Scheduled captures consume local capture resources and can contain sensitive application data. Keep packet counts and durations bounded; avoid full-packet capture on high-rate uplinks unless necessary. Device and FortiManager versions may differ in supported capture controls, so check the exact guide. During failover or switch replacement, revalidate the managed FortiGate/switch mapping. The key distinction is management-plane orchestration versus switch-local observation: a successful capture job proves execution, not end-to-end service delivery.

Feature fingerprint: fmg-managed-fsw-packet-capture-filter-schedule-pcap · Workflow: FortiManager operator → Managed FortiGate selector → Managed FortiSwitch → Capture filter + schedule → PCAP result → Traffic-path interpretation

3. FortiAnalyzer — Log-file rolling versus retention: why archive age can exceed configured days

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortianalyzer/7.6.6/administration-guide/871759/log-storage

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and data model

FortiAnalyzer receives a stream of logs and writes them into files. It also maintains analytics/SQL representations for searchable use. Log storage policies govern space and retention, but deletion is not a per-record operation for archived files. The log-file roll boundary determines which records are grouped into a unit eligible for deletion. This mechanism differs from simply choosing Analytics versus Archive storage: it explains why retention displays can look inconsistent even when the configured policy is applied.

Rolling mechanics

Fortinet documents a default log-file size roll threshold of 200 MB and optional scheduled daily or weekly rolling. When either configured trigger is met, FortiAnalyzer compresses the current file and creates a new one for incoming records of that type. Rolling daily is recommended to keep a file from spanning multiple days. An archive file may contain logs with timestamps from several dates; the retention process cannot surgically delete the oldest day inside that compressed file. This matters in low-volume ADOMs where size-based rolling may occur infrequently.

Deletion and quota interactions

Under days-based retention, a file becomes eligible only when all of its logs fall outside the retained-day window. Under storage-size pressure, FortiAnalyzer deletes the file with the oldest last-received log. The oldest timestamp displayed in an archive may therefore exceed the configured number of days, and gaps may exist between the oldest surviving file and recent logs. These are different observations from the actual volume of retained evidence. Global automatic-delete settings and per-ADOM storage policies are both active and must be inspected together.

Configuration and observables

In System Settings > ADOMs, select the ADOM and View Storage Info to compare Analytics and Archive quotas, historical graphs and device breakdowns. Review log rolling and upload configuration for size and scheduled time. diagnose fortilogd lograte-adom <name> and diagnose fortilogd logvol-adom <name> provide per-ADOM ingestion rates/volumes. A log-rate counter proves data arrival at the logging subsystem, not that a particular historical file remains searchable. Export an evidence sample before altering retention during an investigation.

Operational scenario

An auditor sees '100/90 days' in an archive display and assumes the 90-day policy failed. A low-volume log file contains entries from days 100 through 88, so deleting it would also remove data still inside the retention window. Confirm file roll timestamps and last-received dates before changing the policy. If the objective is a predictable day boundary, configure scheduled daily rolling and ensure disk capacity supports the resulting file count. Do not equate archive age with continuous completeness of logs for every intervening day.

HA, capacity and verification

In a high-volume deployment, smaller roll intervals can increase file-management overhead; in a low-volume deployment, large files can delay day-based deletion. Test retention with a noncritical ADOM and document actual oldest/newest timestamps, file boundaries and deletion triggers. During upgrades, preserve the archive and validate rolling settings and quota graphs afterward. The root-cause chain is incoming log -> file roll -> file-level retention decision; changing report SQL or an event handler does not correct this storage-boundary behavior.

Feature fingerprint: faz-archive-roll-file-delete-eligibility-last-log-time · Workflow: FortiGate log stream → Active log file → Roll size/time trigger → Compressed archive file → Retention eligibility → Oldest-file deletion

4. FortiSwitch — Ingress/prelookup/egress ACL pipeline and hardware density-mode tradeoffs

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortiswitch/7.6.4/fortiswitchos-administration-guide/738913/acl

Secondary Community scenario: https://community.fortinet.com/fortimanager-27/technical-tip-how-to-configure-fortiswitch-port-level-access-control-lists-in-fortimanager-230466

Purpose and pipeline

FortiSwitchOS ACLs can act at ingress, prelookup, and egress stages of the switching pipeline. The stage matters: an ingress drop occurs before the forwarding lookup, while an egress action acts after a forwarding decision. The ACL is a hardware classifier/action mechanism, not a FortiGate firewall policy. A port ACL applied through FortiLink may be centrally configured but must still fit the switch model's hardware resources and classifier capabilities. Mirroring can be configured at ingress or egress for selected traffic.

Objects and hardware limits

An ACL policy defines match fields and actions; an ingress ACL group can aggregate policies before assignment to a managed switch port. Some models have limited Layer-4 ranges or action combinations, and the FS-6xxF family supports specific additional DSCP/CoS classifiers and remark actions from 7.6.2. In 7.6.1 the CLI gained source/destination MAC mask and L3 interface match enhancements. An ACL entry visible in configuration does not prove that every action was programmed into hardware; model-specific feature matrices and resource limits matter.

Counters and policing

FortiSwitchOS supports green/yellow/red color counters for ingress policers and green/yellow for egress, with interpretation tied to committed/excess burst thresholds. The GUI Switch > Monitor > ACL Counters and get switch acl counters all show relevant matches; get switch acl usage helps establish available resources. A rising ingress drop counter is stronger evidence of a specific policy decision than a generic interface discard counter. A nonzero match counter alone does not show that the intended traffic was blocked; inspect the programmed action.

Density-mode operational tradeoff

The guide documents config switch acl settings followed by set density-mode enable to optimize hardware resource use when ACLs are relatively static. In density mode, allocated hardware resources are not automatically removed when configuration changes. Reclamation can require a switch restart or execute acl key-compaction, which affects ACL service. That makes density mode a capacity-versus-change-frequency decision, not a free scale improvement. Schedule compaction with change control and verify production traffic after the operation.

Scenario and diagnosis

A managed access port should deny a particular subnet, but traffic still passes after a FortiManager install. First verify that the ingress policy is in the correct ACL group and that the group is attached to the intended port. Check switch ACL usage, counters and hardware compatibility. A FortiManager job marked successful proves configuration delivery, not switch dataplane enforcement. If a feature-generated internal ACL conflicts with the user ACL, Fortinet warns that precedence and resulting behavior can be model dependent.

Design and upgrade caveats

Separate policies by stage and avoid assuming a match field supported on one model is available on all deployed switches. When migrating from pre-6.0 syntax, account for the stage-aware ACL CLI structure. For 7.6.2+ FS-6xxF, test DSCP remark and queue actions explicitly. During firmware upgrade, recheck the feature matrix and hardware utilization. In the lab, send a known test flow, record before/after ACL counters, then verify both the observed forwarding result and any mirrored copies.

Feature fingerprint: fsw-acl-pipeline-stage-density-key-compaction-hardware · Workflow: Ingress packet → Ingress ACL classifier → Prelookup stage → L2/L3 forwarding lookup → Egress ACL action → ACL counters/TCAM

5. FortiAP/Wireless — MPSK profile key-to-VLAN binding and WPA2/WPA3 transition compatibility

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortiap/8.0.0/fortiwifi-and-fortiap-configuration-guide/356880/mpsk-profiles

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and security model

A single shared WLAN password creates a large revocation blast radius: rotating it affects every device. FortiAP MPSK profiles allow many preshared keys under one SSID, organized into groups, with key-based dynamic VLAN selection and optional schedules. This is still a personal-key authentication design, not EAP-TLS identity assurance. It is useful for segmented device populations where full 802.1X supplicants are impractical. Fortinet supports WPA2-Personal, WPA3-SAE and WPA3-SAE Transition modes for MPSK profiles.

Object relationship

Enable Advanced Wireless Features, then create an MPSK profile under WiFi & Switch Controller > Connectivity Profiles > MPSK Profiles. Add a group and create or import keys. Bind one MPSK profile to a VAP/SSID; Fortinet documents that only one MPSK profile can be assigned to a VAP at a time. Enabling MPSK removes the previous single passphrase and automatically enables dynamic VLAN. Therefore, a change that appears to concern only passwords can alter the client-to-VLAN authorization path.

Authentication and VLAN transaction

A client associates to the SSID and proves knowledge of a configured PSK or SAE password. The WLAN controller matches the key entry, applies the associated MPSK group settings and selects the VLAN when configured. The client must then complete DHCP and reach a permitted FortiGate firewall policy; successful Wi-Fi association is not proof of Layer-3 reachability. In WPA3-SAE Transition mode, keys may individually use WPA2-Personal or WPA3-SAE. A legacy-only device may fail if the assigned key type does not match its security capabilities.

Source-supported setup

From System > Feature Visibility enable Advanced Wireless Features. Create an MPSK profile, select the security type, add a group, and create a key with name, passphrase/SAE password and optional MAC association. Configure VLAN and schedule values supported by the GUI, then assign the profile to the SSID. The corresponding CLI object is config wireless-controller mpsk-profile; the VAP references the profile. Do not paste an unverified full CLI stanza across firmware branches: the GUI and profile fields differ by release and radio platform.

Evidence and failure isolation

Inspect the client's negotiated security mode, SSID, MPSK group/key match, assigned VLAN, and DHCP lease. A correct WPA handshake with no DHCP address points toward VLAN tagging, DHCP relay or firewall configuration rather than the password itself. A key listed in the MPSK profile does not prove that it is enabled by schedule or assigned to the intended VAP. Compare two test clients using different keys on the same SSID and validate that their VLANs and policies differ as designed.

Operational implications

Key exports contain sensitive secrets and should be handled like credentials. Keep group ownership and expiry processes documented; revoke individual keys rather than rotating the entire SSID where possible. If migrating from a single PSK, test representative WPA2 and WPA3 clients, DHCP and segmentation before cutover because dynamic VLAN is enabled as part of MPSK. At scale, balance per-device key management against the operational benefits of certificate-based 802.1X. The mechanism-to-outcome chain is key match -> VLAN selection -> routed access, not merely successful association.

Feature fingerprint: fap-mpsk-per-key-dynamic-vlan-wpa3-transition · Workflow: Client association → SSID VAP → MPSK profile → Group + per-client key → Dynamic VLAN mapping → DHCP + firewall policy

6. FortiNAC — Portal Request Processing Rules: HTTP regex matching, publishing and duplicate-rule failure

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortinac/9.4.0/administration-guide/778577/request-processing-rules

Secondary Community scenario: https://community.fortinet.com/fortinac-f-57/technical-tip-how-to-identify-and-remove-duplicate-request-processing-rules-in-fortinac-230584

Purpose and traffic boundary

FortiNAC's captive portal receives browser and captive-network-assistant HTTP requests with different purposes. Request Processing Rules control how those requests are handled: allow, block, forward to another URL, or return a file. The decision is based on a request field, such as Request URI or HTTP User Agent, evaluated against a regular expression. This is a web-server request-routing layer; it does not itself assign an endpoint VLAN or replace the network access policy that placed the endpoint in registration.

Rule objects and publishing

Navigate to Portal > Request Processing Rules. Create or edit a rule, select the field, regex matcher, action and target when Forward or File is used. For File, ! means load a file at the same path as the request URI. FortiNAC automatically orders rules when it writes the web-server configuration. Crucially, editing a rule in the GUI does not immediately change the active web-server behavior. Publish writes the generated conditional chain and restarts the portal HTTP process; startup and upgrades also publish automatically.

Generated configuration and diagnostics

Fortinet identifies the generated portal web-server configuration as /etc/httpd/conf.d/000_web_servces.conf on the application server. Use the supported GUI Publish action rather than hand-editing the generated file, because later publish or restart can overwrite manual changes. Validate regex special characters: . matches any character, * repeats the previous expression, and \ escapes special syntax. A broad matcher can intercept login assets or CNA probes unexpectedly. Inspect the browser's request URI, response code, redirect target and HTTP User Agent.

Recent failure scenario

Fortinet Community's October 15 case describes duplicate Request Processing Rules: 102 records existed where 51 were expected, with some exact duplicates and others differing slightly. The article locates records in bsc.WebServiceDefinition and demonstrates grouping by serviceType, serviceMatcher, serviceAction and serviceTarget to identify duplicates. This is a specialized support diagnostic, not a recommended routine database edit. Prefer supported GUI cleanup and TAC-reviewed procedures before touching database records, and back up the appliance first.

What proves the fix

A GUI list that looks correct is insufficient because the active web server may still be running the previously published rule chain. Record the initial HTTP response and publish timestamp, publish the corrected rule set, then repeat the same request with the same URI and User Agent. Verify that the expected redirect/file/block action now occurs and that unrelated portal assets still load. If HTTP 500 persists, check portal service logs and generated rule syntax rather than assuming the network VLAN or RADIUS server is at fault.

HA, upgrade and safety

Publish restarts the portal HTTP process briefly, so schedule it when captive-portal traffic is not at a peak. In HA deployments, validate the active service owner and post-failover portal behavior. Export/backup rule configuration before bulk changes. A user reaching the portal but failing to register may involve the next workflow stage; a user who never reaches the portal requires earlier DHCP, DNS, VLAN and redirection checks. The critical boundary is configuration stored -> rules published -> HTTP service applies match -> browser outcome.

Feature fingerprint: fnac-portal-rpr-uri-useragent-regex-publish-httpd · Workflow: Captive portal HTTP request → URI/User-Agent matcher → Allow/Block/Forward/File action → Publish generated rules → Portal HTTP service restart → Browser/CNA outcome

7. FortiNAC-F — Winbind MSCHAPv2 AD domain join versus non-AD LDAP/Kerberos directories

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortinac-f/7.6.0/administration-guide/670285/winbind

Secondary Community scenario: https://community.fortinet.com/fortinac-f-57/troubleshooting-tip-fortinac-winbind-domain-join-fails-against-a-freeipa-server-230354

Purpose and authentication boundary

FortiNAC-F uses Winbind when local RADIUS must validate MSCHAPv2 credentials against a Microsoft Active Directory domain. Winbind is not a general-purpose LDAP connector. The Fortinet guide explicitly says Winbind is needed for MSCHAPv2, while EAP-TTLS/PAP and EAP-TLS use different mechanisms and do not require this configuration. This distinction is critical when a team attempts to authenticate against a non-AD LDAP/Kerberos directory: the presence of LDAP records and a valid user password does not make a Samba domain join possible.

Transaction sequence

An 802.1X supplicant negotiates an EAP method with the RADIUS server. With PEAP/MSCHAPv2 or TTLS/MSCHAPv2, FortiNAC's authentication path delegates MSCHAPv2 validation to Winbind/ntlm_auth. The Winbind instance must already be joined to the AD domain and have usable domain-controller discovery. The FortiNAC DNS configuration must resolve the controller's A record and LDAP/Kerberos SRV records for additional domains. If the machine account or domain join is invalid, correct client credentials alone cannot make the MSCHAPv2 validation succeed.

Source-supported configuration

Go to Network > RADIUS > Winbind. Define the instance with an FQDN, domain controller names or * for discovery, NetBIOS and Kerberos realm settings as applicable. Join the AD domain using an authorized account or uploaded keytab. Fortinet says join before enabling the service; inspect Enabled/Running state separately from Joined/Not Joined domain state. Multiple instances are supported, but each additional domain requires working DNS records. The guide notes Winbind cannot encrypt its connections using LDAPS or STARTTLS; review the authentication transport and segmentation design.

Evidence hierarchy

First confirm the endpoint selected MSCHAPv2 rather than EAP-TLS or PAP. Then check Winbind service state, domain-join status, controller DNS/SRV resolution, machine account freshness and Winbind/systemd logs. FortiNAC can display stale Domain Information even after a join is lost; the current Winbind Domain status is more reliable. A date around 1969/1970 for last machine-account password change is an indicator documented for lost join state. A RADIUS Access-Reject alone does not distinguish a bad password from a failed Winbind trust.

October scenario and correction

An October 2 Fortinet Community troubleshooting article documents attempts to Join Domain against FreeIPA. The join fails because the operation performs a Samba Active Directory domain join that FreeIPA does not accept in this deployment. Do not retry with random bind credentials or enable insecure settings. Choose an authentication scheme that fits the directory's supported protocol, such as a separately configured LDAP/PAP or certificate-based path, or use an actual AD-compatible domain for MSCHAPv2. Validate the full RADIUS-to-network authorization result after changing the design.

Operational implications

Domain-controller failover depends on DNS, routing and available controllers; test each after planned maintenance. Protect the join credential or keytab and document machine-account lifecycle. During upgrade, recheck Winbind service status, domain trust and the exact EAP methods enabled. A successful AD join is a prerequisite, not proof that the client certificate trust, inner EAP negotiation, or RADIUS VLAN attributes are correct. Diagnose from client method to RADIUS to Winbind to directory before changing endpoint access policy.

Feature fingerprint: fnacf-winbind-samba-ad-join-mschapv2-ntlm-auth · Workflow: 802.1X PEAP MSCHAPv2 → FortiNAC RADIUS → Winbind ntlm_auth → AD domain join/DNS SRV → Domain controller → Access-Accept or Reject

8. FortiAuthenticator — OAuth public-client authorization-code PKCE: challenge/verifier binding and redirect controls

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortiauthenticator/6.6.0/administration-guide/796040/relying-party

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and client threat model

A browser or mobile OAuth client cannot reliably keep a static client secret confidential. FortiAuthenticator 6.6 supports Authorization code with PKCE for Public relying parties, so possession of an intercepted authorization code is insufficient to redeem it without the verifier. The authorization server binds a code_challenge supplied at authorization time to a code_verifier presented at token exchange. This mitigates authorization-code interception; it does not replace TLS, redirect-URI validation, user authentication, or correct token audience/scope policy.

Objects and authorization sequence

In Authentication > OAuth Service > Relying Party, define a Public client and select Authorization code with PKCE. The client generates a high-entropy code_verifier and sends a derived code_challenge plus code_challenge_method to the authorization endpoint. The user authenticates on FortiAuthenticator's portal; the authorization code returns only to an allowed redirect URI. The client then presents the original verifier to the token endpoint. A different verifier must fail even if the code and client ID are valid. A Confidential client follows a different secret-based grant policy.

Source-supported configuration

Create the relying party, select Public, and choose Authorization code with PKCE. Register exact redirect URIs, preferably HTTPS, then configure scopes, claims and access/refresh token expiry. Fortinet documents that the client_secret is ignored for PKCE authorization requests and that code_challenge_method and code_challenge are required at /oauth/authorize/. Do not attempt to repair a missing PKCE parameter by supplying a client secret: the server is deliberately using proof-of-possession of the verifier instead. Scope access tokens narrowly to the relying application's needs.

Evidence and troubleshooting

Inspect the browser's authorization redirect, the registered redirect URI, the challenge method and whether a fresh code_verifier is retained by the client across the redirect. At token exchange, a rejected verifier indicates a client transaction-state problem, not necessarily invalid user credentials. Conversely, a successful login page does not prove a token was issued. Check FortiAuthenticator authentication/OAuth logs and the application's token response separately. Avoid logging raw codes, verifiers, refresh tokens or client secrets; record only sanitized correlation identifiers.

Operational scenario

A single-page application authenticates users successfully but returns to its callback with an authorization code that cannot be exchanged. A developer changed the verifier in local storage between the initial redirect and callback, so the token request no longer matches the original challenge. Reproduce with a new authorization request and verify challenge/verifier derivation, exact redirect URI and code lifetime. Do not disable PKCE or switch to password-based grants to conceal the bug; the failure is an intended security boundary.

Upgrade and scale implications

Refresh-token expiry and access-token expiry are independent; the guide notes refresh tokens can be configured never to expire with zero, which increases operational risk. For HA, keep relying-party settings and authentication service reachability consistent across nodes, then test the complete redirect flow during failover. Audit allowed scopes and claims whenever an application is onboarded. PKCE proves that the token redeemer knows the original verifier, not that a browser is malware-free or that the resource server enforces the issued token correctly.

9. FortiPAM — Target TOTP secret auto-delivery: template overrides and SSH keyboard-interactive limits

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortipam/1.8.2/administration-guide/549807

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and separation of factors

FortiPAM can store a target credential and the TOTP material needed when the target server requires a second factor. This is target authentication, distinct from a human administrator's MFA to log in to FortiPAM itself. The target's expected TOTP algorithm, code length and time interval must match FortiPAM's generation settings. Storing the TOTP seed alongside a privileged secret creates a strong reason to restrict secret access, audit launches and avoid displaying the shared key to operators.

Configuration objects

The secret template can define default TOTP settings, while an individual secret may inherit them or override them. In Secrets > Secrets, select the template and secret, enable TOTP and choose a third-party shared key or FortiToken activation. Fortinet's secret CLI example uses config secret database, edit 1, config totp-setting, set status enable, set use-template-setting disable, set totp-length 6, set totp-duration 30, set hash-type hmac-sha1, and set shared-key <secret>. Do not copy real seed material into tickets or reports.

Transaction and launcher boundary

At launch, FortiPAM opens the configured proxy/launcher session and supplies the target username/password as permitted. When the target requests an OTP, FortiPAM can generate a code from the stored seed and deliver it through supported authentication paths. Fortinet's 1.8.x documentation distinguishes SSH automatic delivery from limitations on other launchers; WebSSH with TOTP requires keyboard-interactive authentication. Non-proxy and web-launch flows may require manually copying the code. Do not assume that enabling TOTP means every RDP, browser and SSH launcher supports identical automation.

Evidence and feature limits

If password authentication succeeds but the target rejects the OTP, inspect the target's authentication method, TOTP time synchronization, hash/length/duration settings and whether the secret inherited template values or overrides them. An SSH session reaching a keyboard-interactive prompt is evidence that the target requested that method; it is not proof FortiPAM delivered the correct code. Fortinet also warns that password changer does not support public key plus TOTP authentication and that certain LDAP-backed password/FortiToken combinations should not use the changer.

Operational scenario

A WebSSH secret worked before a target SSH hardening change, but now fails after the target switches from keyboard-interactive to a different authentication method. FortiPAM still holds the correct password and TOTP seed. Check the target SSH server's enabled methods and FortiPAM launcher support rather than rotating the seed first. In a separate case, a 30-second clock skew can cause otherwise correct codes to fail; compare NTP and code-window settings before declaring a credential compromise.

Upgrade and security implications

FortiPAM versions differ in RDP TOTP support and prerequisites, so consult the exact firmware's example and limitations. Some RDP auto-delivery designs require a FortiAuthenticator agent and TLS security level; do not generalize across releases. Use a test secret and a disposable target account to validate each launcher. Keep TOTP seeds out of exports, enforce role-based access and capture launch audit evidence. The security boundary is operator authorization -> secret policy -> launcher method -> target's second-factor challenge.

Feature fingerprint: fpam-target-totp-secret-template-override-keyboard-interactive · Workflow: Secret template TOTP policy → Secret shared key/FortiToken → Launcher proxy session → Target SSH keyboard-interactive → Time-based code delivery → Target auth/session audit

10. FortiSIEM — ClickHouse storage regions: event-worker routing and non-overlapping shard placement

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortisiem/7.5.0/release-notes/399872/whats-new-in-7-5-0

Secondary Community scenario: https://community.fortinet.com/fortisiem-34/technical-tip-clickhouse-duplicate-data-part-error-230431

Purpose and architectural change

FortiSIEM 7.5 introduces ClickHouse Storage Regions, allowing event data from selected collectors or external devices to be placed in designated ClickHouse data nodes instead of distributing every worker's events to every data node. This is a data-placement and scale-isolation mechanism, not an incident rule, parser or monitoring policy. Regions contain one or more Event Upload Workers and one or more ClickHouse shards. The documented requirement is that worker and shard memberships do not overlap between regions.

Ingestion and placement flow

Before 7.5, an Event Upload Worker could distribute received events across the ClickHouse data-node set. With storage regions, a collector is configured to forward events to an Event Upload Worker belonging to the intended region; that worker sends the events to the region's designated shards. A load balancer must also direct collector uploads only to workers in the correct region. Misrouted collectors can produce the wrong placement even when every worker and ClickHouse process is healthy.

Source-supported deployment

First inventory collectors, expected event volume and region-to-shard ownership. Create storage regions with disjoint workers and shards, then configure each collector or external sender with the correct worker addresses. Fortinet's 7.5 release notes explicitly mention configuring worker IPs on the collector when no load balancer is present, and region-aware load-balancer forwarding when one is used. Use the version-specific storage-region configuration procedure for the actual GUI fields; do not reuse pre-7.5 worker distribution assumptions.

Evidence hierarchy

Check sender connection success, collector upload destinations, worker region membership, ClickHouse shard health and query visibility for representative event IDs. An event received by a worker does not prove it was committed to the expected shard. A query that returns zero records might indicate wrong region, ingestion delay, parser issues or a time-range mismatch. Trace one unique event from source timestamp through collector upload and worker routing to stored record. Confirm storage health independently of rule incident generation.

Recent contextual failure

An October 7 Community article describes ClickHouse DUPLICATE_DATA_PART errors that can stop database service. This is a storage-engine operational failure, not direct evidence of region misrouting. Its diagnostic value is to separate data-node health from worker-region placement. Check ClickHouse service and logs if data parts are unhealthy; avoid executing destructive detach or removal commands without a backup and Fortinet-supported recovery guidance. Region routing changes will not repair corrupted ClickHouse parts.

HA and upgrade caveats

Non-overlapping shards create explicit placement boundaries, so a region failure can affect only its assigned sources but may also remove redundancy if poorly sized. Test worker failover within the same region, verify load-balancer membership, and plan storage growth. The 7.5 release notes include significant upgrade prerequisites; validate hardware memory, ClickHouse indexing and feature compatibility before adopting regions. The mechanism is collector destination -> region worker -> region shard; dashboards and rules are downstream consumers, not proof of placement.

Feature fingerprint: fsiem-clickhouse-storage-region-event-worker-shard-isolation · Workflow: Collector/device event source → Region-specific Event Upload Worker → Region A ClickHouse shard(s) → Region B Event Upload Worker → Region B ClickHouse shard(s) → Query scope/region verification

11. FortiSASE — Mandatory administrator change comments: audit transaction and 30-day summary retention

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortisase/26.1.107/feature-administration-guide/519208/administration

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and governance boundary

FortiSASE can require an administrator to enter a change summary before submitting configuration modifications. The control applies broadly to changes to objects, endpoint profiles, analytics and reporting settings, and security traffic policies. It is an audit and accountability gate, not an approval workflow with separate reviewers. A successfully recorded comment describes an operator's stated intent; it does not prove the change was correct, tested, or authorized by a change board.

Transaction mechanics

Under System > Administration, enable Require comments for configuration audit log. When an administrator creates or edits a traffic policy, FortiSASE presents a configuration audit log change-summary pane before the operation completes. The submitted summary is associated with the modified object and administrator identity. The audit record can then be viewed under Operations > Logs > Events > Administrator Events. New log entries can appear after a delay, so an immediate empty search is not definitive evidence of missing audit capture.

Source-supported workflow

Enable the setting, create a harmless test object or policy in a controlled tenant, and submit a concise summary with a change ticket reference and expected effect. Then open Administrator Events, locate the administrator event and inspect Details. Record object identity, administrator, time and summary. Fortinet documents that existing change summaries are retained for 30 days; do not treat this feature alone as a long-term immutable compliance archive. Export logs to the organization's approved retention system where supported and required.

Evidence and its limits

A visible comment pane proves the gate was invoked, but not that the change committed. Confirm the object appears in the effective policy and that the corresponding Administrator Event is recorded. A saved policy without an immediately visible log may reflect ingestion latency; repeat after an appropriate delay and confirm time-zone filters. An Administrator Event does not by itself prove that a remote endpoint received an updated policy, that a security PoP enforced it, or that the change preserved service availability.

Operational scenario

An administrator reports that a FortiSASE policy edit is stuck after clicking OK. The tenant recently enabled mandatory audit comments. The pending change-summary dialog is hidden behind another window or blocked by a browser extension. Verify whether the summary was submitted before investigating propagation or endpoint posture. In a different case, a compliance reviewer requests a 60-day-old summary; the documented 30-day retention means the record may no longer exist in the portal, even if the policy remains.

HA, scale and review

Standardize concise, meaningful comments and avoid embedding passwords, tokens or customer personal data in audit summaries. During organizational handovers, review the 30-day retention and external evidence export before relying on the portal as the sole audit store. Validate role permissions and identity federation separately from this feature. The mechanism-to-implication chain is admin edit -> required comment -> configuration commit -> delayed event log -> finite summary retention, not a generic claim that every administrative action has been approved.

Feature fingerprint: fsase-admin-change-comment-submit-audit-30day-retention · Workflow: Administrator edits policy → Configuration audit comment gate → Object change commit → Administrator Events log → Change summary 30-day retention → Auditor review

12. Secure SD-WAN — FortiGuard SLA database targets: licensed probe presets versus measured path quality

Primary Fortinet feature/admin guide: https://docs.fortinet.com/document/fortigate/latest/administration-guide/875001/fortiguard-sla-database-for-sd-wan-performance-sla

Secondary Community scenario: Not independently verified for this exact mechanism; lesson operational scenario is an engineering application of the primary guide.

Purpose and control-plane boundary

FortiGuard's SLA database supplies preconfigured probe destinations and recommended performance thresholds for popular SaaS and internet services. It reduces manual server/threshold selection but does not replace actual health measurements. The FortiGate still sends health-check probes from eligible SD-WAN members, evaluates latency, jitter and loss, and applies the relevant SLA requirements to rule decisions. A database preset is a configuration input, not evidence that a SaaS application is reachable or performing acceptably.

Objects and licensing

In Network > SD-WAN > Performance SLA, Create New exposes the FortiGuard database when the service is available. The CLI health-check object supports set fortiguard enable and set fortiguard-name <predefined-target>. Fortinet documents that downloading or updating the database requires a valid SD-WAN Underlay and Application Monitoring license. If the database is missing, check entitlement and update reachability before editing unrelated routing policies. A manually configured health check and a FortiGuard preset should be compared by actual probe server and thresholds, not just their names.

Measurement and forwarding sequence

The health-check selects a target and probes each configured member, producing performance measurements. An SD-WAN rule then considers member eligibility and the required SLA targets when steering new sessions. A probe can succeed while an application still fails due to DNS, TLS, authentication or a different CDN path. Likewise, an application can work while a specific probe destination is unreachable. Separate underlay route reachability, probe target accessibility, measured thresholds and session-path selection in troubleshooting.

Source-supported setup

Create or edit a health check, select the FortiGuard SLA preset for the desired application class, and verify the populated target and thresholds. In CLI, Fortinet documents config system sdwan, config health-check, edit <health-check-name>, set fortiguard enable, set fortiguard-name <name>, then close the contexts. Bind the intended SLA to a service rule and explicitly select the member participants. Do not assume a preset's recommended thresholds are universal: baseline real branch latency and business tolerance first.

Evidence and troubleshooting

Compare the installed FortiGuard database availability, health-check configuration, member probe statistics, SLA pass/fail state and session distribution. A healthy preset probe is not proof the business application selected the expected WAN: inspect the matching SD-WAN rule and session route. A failed preset probe does not automatically mean the WAN is physically down. If a site sees different results from another site, compare DNS resolution, member source addresses, upstream filtering and which CDN/service endpoint is actually probed.

Operational implications

Preset targets can evolve as FortiGuard content is updated; validate behavior after license renewals, database updates and FortiOS upgrades. For HA pairs, ensure both units have appropriate entitlement and synchronized configuration and retest probes after failover. In high-scale branches, limit unnecessary overlapping probes and monitor resource use. The failure-isolation sequence is license/catalog -> health-check target -> probe metric -> rule threshold -> session forwarding -> real application outcome. Changing the FortiGuard preset alone cannot fix a broken DNS or application authentication flow.

Feature fingerprint: sdwan-fortiguard-sla-preset-server-threshold-license · Workflow: FortiGuard SLA preset catalog → License/download entitlement → SD-WAN health-check object → Member probe to SaaS target → Measured latency/jitter/loss → SD-WAN rule path decision
