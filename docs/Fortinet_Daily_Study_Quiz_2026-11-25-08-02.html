Lesson 01 · FortiGate

Explicit web proxy isolation: PAC delivery, policy matching and FortiIsolator handoff

Purpose. Explicit proxy is a browser-directed HTTP/HTTPS forwarding service. A client either has a static proxy address or downloads a Proxy Auto-Configuration (PAC) script that returns PROXY host:port or DIRECT for a URL/host. This is different from transparent proxy interception. PAC distribution, listener reachability, proxy-policy matching and isolator health are separate failure domains.

Transaction mechanics

First the browser retrieves the PAC file. FortiGate can serve it itself, including over HTTPS through its captive-portal service. The PAC script is JavaScript evaluated by the browser; FortiGate does not interpret the decision function. A PAC result of DIRECT intentionally bypasses the proxy. A PROXY 10.1.100.1:8080 result makes the browser open a new connection to the explicit proxy listener. That session is evaluated against ordered proxy policies.

A proxy policy can use an isolator server. The isolator is configured like a forward proxy endpoint, but it sends potentially unsafe browsing into a remote isolated environment. The isolate action is logged distinctly from accept. That log proves policy selection, not that the isolator's remote browser container or its upstream Internet path is healthy.

Configuration

config web-proxy explicit
    set status enable
    set http-incoming-port 8080
end
config web-proxy isolator-server
    edit "isolator"
        set addr-type ip
        set ip 172.16.200.7
        set port 8080
    next
end
config firewall proxy-policy
    edit 20
        set proxy explicit-web
        set dstintf "wan1"
        set srcaddr "all"
        set dstaddr "Finance"
        set service "webproxy"
        set action isolate
        set isolator-server "isolator"
        set schedule "always"
        set logtraffic all
    next
end

For HTTPS PAC delivery, configure pac-file-server-status, pac-file-name, pac-file-data and pac-file-through-https; set the captive portal address/port and a custom global web-proxy SSL certificate. Fortinet notes that the factory certificate is not accepted by Windows in this use case; the issuing CA chain must be trusted on clients.

Evidence and failure isolation

  • PAC GET: proves endpoint and certificate reachability, not the script's decision for every host.
  • FindProxyForURL: proves whether the browser chooses PROXY or DIRECT.
  • Proxy-policy log: proves listener reachability and the matched action, not isolator health.
  • Isolator session: proves the isolated browsing path and its upstream connectivity.
Historical Community case: deleting a VDOM with a name similar to root could empty the root VDOM PAC data on affected FortiOS builds, causing PAC HTTP 404. The article identifies fixes in 8.0.1 and 7.4.13; treat this as version-specific, not universal.

When a browser goes direct, inspect the PAC result first. If PAC is correct, test the listener and policy. Only after an isolate log should the isolator server be investigated. Do not change firewall rules to fix a PAC certificate problem.

Lesson 02 · FortiManager

Security boot chain: TPM, UEFI Secure Boot, self-encrypting drives and runtime integrity

Purpose. FortiManager stores configuration databases, credentials, scripts and device-management trust. Platform protections are layered: trusted-host restrictions reduce GUI exposure; TPM provides a hardware trust anchor where supported; UEFI Secure Boot validates the boot chain; self-encrypting drives protect data at rest; real-time file-system integrity checking (RT-FSIC) protects important binaries after startup. These controls are not interchangeable.

Boot and runtime sequence

Fortinet's RT-FSIC description specifies a BIOS-level integrity check of signed internal files before the root filesystem and executables are loaded. Once loaded, important binaries are protected from writes, kernel module loading is restricted, and executable/library hashes are held in memory. When a binary is initialized, its hash is checked. A mismatch or missing hash blocks execution and can reboot the appliance. A sudden restart may therefore be a security response rather than an ordinary process crash.

TPM and Secure Boot support platform trust; self-encrypting drives address confidentiality if media is removed; RT-FSIC detects unauthorized modification/injection of executable code. Encryption does not prove firmware integrity, and a trusted boot chain does not restrict who can reach the GUI. Trusted-host policy is a separate management-plane control.

Operational configuration

The FortiManager 8.0 Administration Guide groups trusted hosts, TPM support, self-encrypting drives, UEFI Secure Boot and RT-FSIC under Setting up FortiManager → Security considerations. These are platform/hardware capabilities, not generic firewall policy objects. Confirm model/VM support and release-specific availability before assuming every control is configurable on every appliance. Document model, firmware, hardware capability, encryption state, trusted-host list, administrator roles and recovery procedure.

Restrict GUI/SSH management to known management subnets and maintain an out-of-band recovery path. Because RT-FSIC can block binaries and reboot after a mismatch, preserve system event logs/support bundles before repeated restarts or firmware changes.

Evidence and failure isolation

  • Boot integrity result: proves signed boot components passed/failed; not later user-space correctness.
  • Write/module violation: indicates a protected file/module operation was blocked; correlate path and process.
  • Hash mismatch/missing hash: indicates an untrusted runtime binary; preserve evidence and validate the signed image.
  • Drive encryption: proves data-at-rest protection, not firmware integrity.
  • Trusted hosts: proves source-address restriction, not account integrity.
Do not copy binaries from another appliance or repeatedly reboot to clear an integrity event. Preserve evidence and use the vendor-supported signed-image recovery/reflash path.

When FortiManager reboots during a maintenance window, correlate boot/security logs before assuming hardware failure. If the event is a runtime hash mismatch, investigate binary integrity; if only GUI access fails, investigate trusted hosts and routing.

Sources: FortiManager 8.0 setup/security · RT-FSIC mechanics
Lesson 03 · FortiAnalyzer

Playbook execution: connector tasks, dry-run replay, node debugging and partial reruns

Purpose. FortiAnalyzer playbooks automate response workflows around incidents and alerts. A playbook is a graph: one trigger starts the workflow and linked tasks invoke connector actions on FortiAnalyzer or external systems. The 8.0 editor adds testing/debugging controls because automation failures are often data-contract failures—one task emits JSON the next task does not expect—not trigger failures.

Execution model

Triggers include incident/alert events, scheduled execution and on-demand execution. Each task is bound to a connector/action, receives defaults or variables from the trigger/previous task, and produces output variables for downstream tasks. A task begins when its connected predecessors complete. FortiAnalyzer 8.0 adds Branch (if), Wait Operator, Compare and Switch controls plus Jinja conditions/loops. A connector can appear in the editor while inactive; it is grayed out and must be configured/activated before production action execution.

Dry-run workflows use mock data for testing. The editor can run, pause and inspect individual nodes, replay with alternate input, and restart from a selected node (partial run). Mock data is cleared when saving or leaving the editor, so it is not persistent production state. A task's input pane shows variables from the trigger/prior tasks; output previews the current task's result. Do not build downstream steps against guessed JSON field names.

Debugging workflow

  1. Record the Job ID, trigger, start/end time and status from Playbook Tasks.
  2. Run the prior task with representative mock input and inspect its output JSON.
  3. Compare the actual output keys/types with the next task's input contract.
  4. Validate connector activation, credentials and action permissions.
  5. Run the failing node alone; after correcting the mapping, use partial rerun from that node.

Evidence boundaries

  • Trigger configuration: proves when a playbook should start, not connector health.
  • Job ID/task status: proves an execution occurred and localizes failed nodes, not that every external action completed.
  • Node input/output: proves data mapping at the task boundary; dry-run does not prove live credentials/API reachability.
  • Grayed connector: indicates inactive/unconfigured state; production requires activation and successful action testing.
  • Partial rerun: tests the selected node with current upstream data; it does not repair stale upstream output.

When a response workflow fails at task 3, compare task 2 output to task 3 input, inspect the connector and run task 3 alone. For destructive actions, use on-demand triggers and representative dry-runs before enabling incident-driven automation. Recent Community material about stale “Last Log” status after reboot is a separate device-status refresh boundary; it is not proof of playbook failure.

Lesson 04 · FortiSwitch

Storm control: traffic-class thresholds, burst handling, port overrides and telemetry

Purpose. Storm control limits the effect of broadcast, unknown-unicast and unknown-multicast storms. It measures packet rate (pps) and acts when a configured threshold is exceeded. A storm can be caused by a Layer 2 loop, faulty NIC, virtual-switch misconfiguration, unknown-destination flooding or attack. It is containment, not root-cause repair; aggressive thresholds can suppress legitimate ARP, IPv6 ND and service discovery.

Mechanics and scope

Each traffic class is enabled independently. The FortiSwitchOS guide documents global and per-port settings. Above threshold, the switch drops excess packets or rate-limits them. Burst-size levels control short bursts; maximum packet/byte allowance varies by model. A rate of zero means drop all packets for enabled classes, not disable storm control. The feature is disabled by default. A per-port override changes the effective threshold on that port, so inspect it when only one access port is affected.

Configuration

config switch storm-control
    set rate 500
    set burst-size-level 2
    set broadcast enable
    set unknown-mcast enable
    set unknown-unicast disable
end
config switch physical-port
    edit "port12"
        set storm-control-mode override
        config storm-control
            set rate 1000
            set burst-size-level 4
            set broadcast enable
            set unknown-multicast enable
            set unknown-unicast enable
        end
    next
end

From FortiSwitchOS 7.4.3, monitoring can log when dropped-packet rate exceeds a high-rate threshold:

config switch global
    set storm-control-monitor enable
    set storm-control-high-rate 100
    set storm-control-rate-filter 50
end

Evidence and diagnosis

  • get switch storm-control: global configuration only; inspect port override separately.
  • diagnose switch storm-control: shows drop-rate/port telemetry; not the storm's source.
  • Storm-control log: proves monitor threshold crossed; correlate with STP state and port counters.
  • Ingress/egress capture: frame seen at ingress but absent at egress with a matching drop counter localizes the switch drop.

Do not deploy low thresholds across all classes without measuring normal traffic. Storm control is not a replacement for MSTP/root guard/loop guard. Use it to limit impact while the loop or faulty endpoint is found, then correct the topology or device.

Lesson 05 · FortiAP/Wireless

RADIUS VLAN name tags and round-robin VLAN pools on one enterprise SSID

Purpose. Dynamic VLAN assignment lets users with different access requirements share one enterprise SSID while being placed into distinct Layer 2 segments after authentication. The RADIUS server returns tunnel attributes in Access-Accept. FortiGate's wireless controller interprets them and maps the returned value to a VLAN. The 7.6 configuration guide extends the usual VLAN-ID/interface-name match with a vlan-name table: a logical tag such as data can map to several VLAN IDs, selected round-robin.

Authentication and forwarding flow

The client associates to a WPA2/WPA3-Enterprise SSID, performs EAP, and the FortiGate controller sends RADIUS authentication to the configured server. The server returns Tunnel-Type=VLAN (IETF 64 value 13), Tunnel-Medium-Type=IEEE-802 (IETF 65 value 6), and Tunnel-Private-Group-ID (IETF 81). The final attribute can be a numeric VLAN ID, a VLAN interface name, or a text key in the VAP's vlan-name table.

When the value is a name tag, FortiGate resolves it against the table under the VAP. A name can map to one VLAN or multiple VLAN IDs, up to eight. When multiple IDs are configured for a name, the controller selects one round-robin. The RADIUS server chooses the logical tag; the controller owns the mapping and allocation. Identity/group policy determines the tag, while wireless configuration determines the eligible VLAN pool.

Configuration example

config wireless-controller vap
    edit "wifi.fap.02"
        set ssid "Enterprise"
        set security wpa2-only-enterprise
        set auth radius
        set radius-server "peap"
        set dynamic-vlan enable
        config vlan-name
            edit "data"
                set vlan-id 100 200 300
            next
            edit "voice"
                set vlan-id 400
            next
        end
    next
end

The RADIUS record for a data user returns Tunnel-Type=VLAN, Tunnel-Medium-Type=IEEE-802 and Tunnel-Private-Group-Id=data. The AP profile and SSID must be attached to the correct FortiAP, and the upstream bridge path must carry the selected VLANs. Each VLAN also needs its L3 interface, DHCP service and security policy. A valid Access-Accept is not enough if VLAN 200 is absent from the switch trunk or has no DHCP scope.

Evidence and failure isolation

  • RADIUS packet: proves the server returned the intended Tunnel-Private-Group-ID; not that the VAP has a matching name tag.
  • VAP configuration: proves dynamic-vlan and the name-to-VLAN pool; not that the AP is using that VAP.
  • Wireless client table: proves the controller's assigned VLAN; not upstream trunk or DHCP reachability.
  • DHCP lease and packet capture: prove the selected VLAN can reach its gateway and scope.

Common mistakes are returning a VLAN label that differs from the configured key, leaving dynamic VLAN disabled, or configuring the pool without allowing all VLANs on the AP uplink. Keep this distinct from RADIUS-driven captive-portal redirect URLs: that feature changes where the client is redirected; this feature changes the client's Layer 2 forwarding domain.

Lesson 06 · FortiNAC

High availability: primary/secondary control, MySQL replication and shared-IP failover

Purpose. FortiNAC HA keeps network-access control available when an appliance fails. It is not simply two servers with identical configuration. The HA management process exchanges state between primary and secondary appliances, determines which node is in control, mirrors critical information and coordinates services. Database synchronization uses MySQL replication. Optional shared-IP configuration gives administrators and agents one management endpoint that moves to whichever appliance is active.

Control and synchronization

The primary is the appliance currently in control; the secondary is standby and can take control when the primary fails. The management process sends messages between nodes, monitors state and controls service transitions. Supporting scripts check whether database replication is working and can restore database/files from the secondary to the primary during recovery. The 9.4 Administration Guide notes that when HA settings are saved, the primary attempts to contact the secondary to verify database replication; if it cannot communicate, it continues retrying.

Topology determines whether a shared IP is appropriate. The 9.4 guide says not to use a shared IP if primary and secondary servers are in different subnets. In a same-subnet design, the shared IP/host name can move so administrators and Persistent Agents continue to reach the active node. In a multi-subnet design, omit the shared IP and plan management/agent communication paths to each appliance. If a Control Server and Application Server are deployed as pairs, failover behavior must be understood at both layers; a Control Server failure may require its paired Application Server to fail over too.

Configuration sequence

Before configuring HA, confirm each appliance is licensed/keyed for HA, verify primary/secondary addresses and gateways, and confirm inter-node routing/firewall access. In the GUI open System > Settings > System Management > High Availability, enter peer details, configure a shared IP only if the subnet requirement is met, save and wait for the success message, then restart FortiNAC services on both appliances as directed by the guide. A successful form submission is not proof replication has completed.

Capture primary role, secondary role, replication health, service state and shared-IP ownership before a failover test. Test both node failure and recovery/rejoin. The standby must not become active merely because its management UI is reachable; HA state and the management process decide control.

Evidence and failure isolation

  • HA role/state: proves which node is in control and whether the secondary is eligible; Idle can mean the process is functional but takeover is not enabled.
  • Replication status: proves database synchronization; not that the shared IP moved or agents can reach the new primary.
  • Gateway monitoring: proves the configured gateway probe path; not every application path or peer replication.
  • Shared-IP ownership: proves management endpoint movement; verify agent registration, service state and Control/Application Server pairing separately.
Do not configure a shared IP across different subnets. If the secondary GUI is unavailable for a configuration task, FortiNAC documents a separate secondary-administration service procedure; stop that service after the task so it does not interfere with failover UI behavior.

When the primary fails but the secondary remains Idle, inspect HA state and database replication before changing DNS or routing. When the shared address fails to move, inspect same-subnet design and the service/management process rather than assuming MySQL replication alone controls the virtual address.

Sources: FortiNAC 9.4 High Availability · HA reference manual · Secondary configuration UI case
Lesson 07 · FortiNAC-F

TEAP chained machine-and-user authentication: outer tunnel, inner-method ordering and policy result

Purpose. TEAP (Tunnel Extensible Authentication Protocol) allows more than one authentication method to run inside a protected EAP tunnel. This supports a stronger wired/wireless admission model than authenticating only the user or only the machine. A Windows endpoint can first prove it is a managed/domain computer and then prove the interactive user's identity. FortiNAC-F 7.6.3 adds TEAP support for multiple inner methods and flexible user/machine combinations.

Protocol flow

The supplicant begins 802.1X and negotiates EAP-TEAP with the RADIUS server. The outer TEAP TLS tunnel protects the inner exchange. FortiNAC-F's RADIUS virtual server defines which EAP types are supported and the order of inner authentication. For a computer-first design, Fortinet's example enables TLS, TTLS, TEAP and MSCHAPv2 as supported types, then sets Primary Auth Type = Computer and Secondary Auth Type = User. The Windows adapter must use Microsoft: EAP-TEAP and have authentication mode configured to allow the intended user/computer sequence.

The stages answer different questions. Computer authentication identifies the endpoint before a user signs in; user authentication identifies the person. NAC policy can then use both identities to select a role/network/authorization result. A successful outer TLS handshake only proves the tunnel was established. It does not prove either inner method succeeded. A successful machine stage does not prove the interactive user's identity was checked.

Configuration sequence

  1. On FortiNAC-F open Network > RADIUS > Virtual Servers and edit the server used by the switch/AP.
  2. Enable the required EAP types, including TLS and TEAP.
  3. Set Primary Auth Type to Computer and Secondary Auth Type to User for the intended order.
  4. On Windows, open the adapter's Authentication tab and select Microsoft: EAP-TEAP.
  5. In Additional Settings, set authentication mode to User or Computer as required. Ensure the trusted root certificate used by the server is installed on the endpoint.
  6. Trigger a fresh 802.1X exchange and inspect both inner stages.

Evidence and troubleshooting

  • Virtual-server EAP list: proves TEAP is enabled; not that the client selected TEAP.
  • Outer TLS handshake: proves server certificate trust/tunnel establishment; not inner credentials or policy mapping.
  • TEAP/RADIUS debug: shows primary and secondary method order and where the exchange stops.
  • Windows EAP event log: shows client-side method selection and trust errors; correlate with RADIUS trace.
  • Access-Accept: proves final authorization; verify both inner stages if both identities are required.

A common mismatch is FortiNAC-F configured for Computer then User while Windows is configured for user-only authentication. Another is a trusted-root mismatch that prevents the outer tunnel from reaching the inner stage. Do not change VLAN policy until the RADIUS exchange reaches the expected final authorization.

Uniqueness boundary: the earlier Entra ID lesson covered single-stage EAP-TTLS/PAP through Local RADIUS. This lesson covers TEAP's protected outer tunnel and sequential machine-plus-user inner authentication, not the Entra TTLS/PAP connector workflow.

Lesson 08 · FortiAuthenticator

RADIUS proxy transparency and Message-Authenticator enforcement

Purpose. FortiAuthenticator can proxy authentication to an existing RADIUS server while preserving the client's original authentication method. This is useful during migration or when FAC is inserted as an identity/security control point without changing the NAS/supplicant method. The Proxy preferred authentication method differs from selecting MSCHAPv2, MSCHAP, CHAP or PAP: it forwards the credentials sent by the RADIUS client to the remote server unchanged.

Request/response flow

The NAS sends Access-Request to FAC. FAC selects a remote RADIUS server profile, applies realm behavior and forwards the request upstream. With Proxy selected, FAC does not convert the method into another password exchange; the upstream server remains responsible for understanding and validating the original method. FAC receives Access-Accept/Reject and returns the result to the NAS. A secondary remote server can provide redundancy, but timeout matters: the guide allows 1–60 seconds and defaults to 3 seconds; a high timeout can reduce request throughput when the remote server is unresponsive.

Realm handling matters in federated designs such as eduroam. When Include realm in username is enabled, the username sent upstream remains the same qualified string received from the RADIUS client. Preserving the realm allows a hierarchy of RADIUS proxies to route the request to the appropriate home realm. If the realm is stripped, a downstream proxy may no longer know where to send it.

Message-Authenticator is an integrity attribute. Fortinet documents that when FAC is the RADIUS client it always includes Message-Authenticator in outgoing authentication requests. The optional Require Message-Authenticator Attribute in Response setting makes FAC accept only upstream responses that include the attribute. This is a compatibility decision: confirm every upstream server in the primary/secondary set emits it before enforcing it.

Configuration points

Go to Authentication > Remote Auth. Servers > RADIUS and create a remote server. Set Preferred auth. method to Proxy when the original method must pass through unchanged. Set timeout, decide whether to preserve realm, configure primary and optional secondary server address/port/secret, and enable response Message-Authenticator enforcement only after upstream validation. This is a remote-server profile, not a global RADIUS server switch.

Evidence and failure isolation

  • Profile: proves Proxy/realm/timeout settings, not packet delivery.
  • Packet capture on both RADIUS legs: proves method/attributes and Message-Authenticator presence.
  • FAC debug: distinguishes upstream timeout, reject, invalid shared secret and response-attribute failure.
  • Access-Accept: proves that request succeeded, not that accounting was forwarded or every failover target is compatible.

When only one NAS fails, compare original RADIUS method and realm before changing user credentials. If all clients fail after response enforcement is enabled, inspect upstream Message-Authenticator behavior. A long timeout can make an outage look like slow authentication; use realistic timeout and a tested secondary server.

Source: Remote RADIUS server configuration
Lesson 09 · FortiPAM

Web RDP connection-broker load-balancing cookie propagation

Purpose. In a Remote Desktop Services farm, the connection broker uses a load-balancing token/cookie to select the correct collection or farm target. FortiPAM 1.9 adds a target-level Loading Balancing Information field for targets using templates with the Web RDP default launcher. This is not a credential or a generic launcher parameter: it is routing metadata passed to the Microsoft Terminal Services connection broker.

Transaction mechanics

The user authenticates to FortiPAM and launches a Web RDP secret. FortiPAM resolves the secret's target and template, then the Web RDP launcher builds the broker connection. The target-level load-balancing information is included so the broker can choose the intended farm/collection endpoint. If the value is missing or malformed, FortiPAM may authenticate the user successfully but the broker can still select the wrong host or fail to resolve the intended farm. PAM authorization can succeed while the RDS broker path fails.

The feature is constrained by template and launcher type. The field is available only for targets using templates with the Web RDP default launcher. Fortinet's CLI example is:

set rdp-load-balancing-info "tsv://MS Terminal Services Plugin.1.loadbalance1"

The prefix tsv://MS Terminal Services is mandatory; the farm/load-balance token follows it. Do not copy a value from a native RDP template and assume the Web RDP launcher will interpret it, or set the field on a target that uses a different launcher.

Configuration and validation

Open Secrets > Targets, create or edit the target, choose a default secret template that uses the Web RDP default launcher, and populate the Loading Balancing Information field with the broker's expected cookie. The target's general settings also identify its address/domain and optional gateway. The template must contain the fields required for that target. If the target is behind a gateway, verify gateway selection independently; the broker cookie does not replace network reachability.

  • Target field/template: proves FortiPAM has a broker token and compatible launcher; not that the broker accepts it.
  • FortiPAM launch log: proves PAM authorization and launch attempt; not correct RDS host selection.
  • Connection-broker logs: prove the cookie was received and how the farm/collection was resolved.
  • Session on target host: proves final host selection and RDP connectivity; compare with broker selection to isolate routing from credential failure.

When a user can log in to FortiPAM but receives an RDS farm error, inspect the target's template type and exact cookie prefix before changing user permissions or the target password. Confirm broker DNS, certificate and port reachability from the FortiPAM path. This attribute controls selection; it does not create or repair the RDS farm.

Lesson 10 · FortiSIEM

Windows Agent File Integrity Monitoring: SHA-256 evidence and threat-intelligence correlation

Purpose. File Integrity Monitoring (FIM) provides endpoint evidence when a watched file or folder changes. FortiSIEM's Windows Agent monitor template separates log collection from change monitoring. The template contains Log Settings, Change Settings (including FIM, registry changes, installed-software changes and removable media) and Script Settings. The agent observes configured paths/operations, generates events and forwards them for normalization and investigation.

Hash and event mechanics

FortiSIEM Windows Agent release 3.1.0 changed file/folder FIM hashes from MD5 to SHA-256. This matters because SHA-256 hashes can be compared directly with modern threat-intelligence feeds that publish SHA-256 indicators. A hash is a content identifier: if file bytes change, the hash changes. It does not by itself prove the file is malicious. A legitimate software update and a malicious replacement both produce a new hash; path, signer, process, user, timestamp and parent activity provide context.

The flow is: administrator defines the monitor template; template is assigned to endpoint/agent; agent observes file operations in scope; agent computes the file hash and emits an event; Collector receives it; FortiSIEM parses the event and associates it with the reporting host; analyst correlates the hash with threat intelligence and surrounding telemetry. This differs from Windows Event Forwarding (WEF), which forwards Windows Security/Application/System logs from source computers to a central Windows server. A WEF collector does not automatically provide the same FIM, custom-log or Sysmon coverage as the native agent.

Configuration and scope

In the Windows Agent administration area, define a Windows Agent Monitor Template. Under Change Settings, configure File Integrity Monitoring and the file/folder scope appropriate to the server role. Keep scope narrow enough to make the signal actionable: critical executable directories, configuration directories, startup locations and sensitive application files are stronger starting points than every temporary directory. Validate agent version compatibility and permissions on protected paths. The release notes identify SHA-256 as the FIM hash algorithm from agent 3.1.0 onward.

Evidence boundaries

  • Monitor template: proves which paths/changes should be observed; not that the agent is running or has access.
  • Agent event/log: proves endpoint observation; not that the event reached the Collector.
  • Parsed FortiSIEM event: proves host/path/hash data arrived and was normalized; not that the hash is malicious.
  • SHA-256 match: proves byte-level equality with the indicator; validate feed source, path, signer and process before containment.

When an expected FIM event is missing, check template assignment, path scope, agent health and permissions before changing parser rules. When an event is present but a feed match fails, verify algorithm and normalized hash length/value. A 32-character MD5 value will not match a 64-character SHA-256 indicator. Correlate a changed file with installed-software events to avoid treating a patch cycle as intrusion.

Sources: Windows Agent monitor templates · Windows Agent release notes and SHA-256 change
Lesson 11 · FortiSASE

IPsec remote-agent application-based split tunneling: route scope and platform boundaries

Purpose. FortiSASE supports remote-user connectivity over IPsec for FortiClient endpoints. Split tunneling determines which traffic is carried through the IPsec tunnel to the Security PoP and which traffic uses the endpoint's local network path. On Windows, FortiClient supports application-based split tunnel or full tunnel. FortiClient endpoints on other platforms support full tunnel only according to the current Feature Administration Guide. A profile that expects application-based split tunneling on macOS or Linux will not behave like a Windows endpoint.

Control-plane and data-plane behavior

The endpoint establishes an IPsec agent tunnel and receives endpoint-profile/global settings. For Windows application-based split tunnel, FortiClient classifies application traffic according to the profile's split-tunnel rules. Selected application flows enter IPsec and are processed by FortiSASE policy/security services. Excluded application flows use the local interface/route. The tunnel can be fully established while an individual application is intentionally excluded; successful IKE/IPsec status does not prove every application traverses the PoP.

Split tunneling must be kept separate from split DNS. Split DNS controls which resolver/path is used for a domain; split tunneling controls the forwarding path for packets/application flows. A DNS query can resolve to a private address while the corresponding application flow is excluded from the tunnel, or a flow can be tunneled while its DNS query is handled separately. Diagnose name resolution and packet forwarding as separate transactions.

Version and migration dependencies

FortiSASE Feature 25.4.b changed the SSL-to-IPsec transition process for existing instances: it no longer requires resetting the instance to defaults or redeploying clients, but a scheduled maintenance window is still required because temporary network disruption and user-session interruption can occur. New instances have IPsec remote-agent support enabled by default starting in 24.4.b.1. Recommended FortiClient version depends on instance creation timing: the guide lists 7.4.7 for new instances and 7.2.14 for existing instances created before 25.4.c. Confirm exact instance/version compatibility before changing tunnel mode.

LDAP authentication is unavailable for IPsec remote agents in the current feature guide; administrators should use supported SSO, RADIUS or local authentication. Global connection settings apply across endpoint profiles, so a global change can affect endpoints beyond the intended pilot group. Use a test profile and controlled endpoint cohort before broad rollout.

Verification and troubleshooting

  • IPsec status: proves tunnel establishment and peer negotiation; not application selection.
  • Endpoint profile: proves tunnel mode and split-tunnel intent; not client-version support.
  • FortiClient route/application diagnostics: prove whether a specific flow is classified as tunnel or local.
  • PoP logs: prove tunneled traffic reached FortiSASE; absence may mean local bypass rather than a block.
  • DNS trace: proves resolution path only; not the subsequent packet path.

When one application bypasses inspection, compare its process identity, destination and split-tunnel rule with an inspected application. Do not start by changing DNS or firewall policy. If the entire endpoint loses connectivity during SSL-to-IPsec migration, verify the transition best-practice workflow and maintenance window before assuming a routing defect.

Source: IPsec remote agent support
Lesson 12 · Secure SD-WAN

SD-WAN zones as route interfaces: multi-zone IPv4/IPv6 static routes and service-rule preference

Purpose. SD-WAN zones abstract groups of member interfaces. A zone is the logical interface used by firewall policies, static routes and service rules; members are the physical or tunnel links that the SD-WAN engine can select. This separation lets routing intent remain stable when an underlay member changes. FortiOS 8.0 allows IPv4/IPv6 static routes to reference one or more SD-WAN zones and lets service rules express zone preference.

Mechanics and object relationships

Create SD-WAN members and assign them to zones. Members cannot be used directly as firewall policy interfaces once managed as SD-WAN members; policies use the zone. A static route can point at a zone so routing resolves the destination through eligible members of that zone. The route does not choose a specific WAN by itself. The SD-WAN service rule then selects an eligible member within the zone based on strategy and health. This creates two decisions: route lookup determines the logical egress zone; SD-WAN selection determines the actual egress interface.

FortiOS 8.0 uses sdwan-zone in IPv4 config router static and IPv6 config router static6. The service-rule field priority-zone expresses zone preference. A route can include multiple zones; a service rule can also include one or more preferred zones. This is not BGP route-tag matching or a per-member SLA tie-break; it is a route-interface abstraction.

Configuration example

config router static
    edit 10
        set dst 10.40.0.0 255.255.0.0
        set sdwan-zone "overlay" "internet"
    next
end
config router static6
    edit 10
        set dst 2001:db8:40::/48
        set sdwan-zone "overlay"
    next
end
config system sdwan
    config service
        edit 10
            set name "private-apps"
            set priority-zone "overlay"
        next
    end
end

Verify zones exist and members are assigned. Confirm firewall policies use the zone as source/destination interface and static routes reference the intended zone. The CLI hierarchy uses config system sdwan rather than the older config system virtual-wan-link; diagnostics use diagnose sys sdwan rather than diagnose sys virtual-wan-link.

Evidence and failure isolation

  • Routing table: proves route installation and logical zone/interface; not member health.
  • diagnose sys sdwan: proves member/zone state and service selection; not firewall permission.
  • Firewall policy: proves the zone is referenced for traffic direction; not that the route points to it.
  • Session/debug flow: proves selected service rule and actual member for a session; existing sessions may retain prior path until re-evaluated.

If a route is present but traffic does not leave, check member health and service-rule selection. If a route disappears after moving a member, check whether the referenced zone still has eligible members. If traffic is dropped before SD-WAN selection, inspect policy interface references. Do not troubleshoot this as a BGP community problem unless the route is learned dynamically and carries that metadata.
