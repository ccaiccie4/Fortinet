Lesson 01 · FortiGate

BGP neighbor transport establishment: Active state and debug error 107

555 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiOS 8.0 CLI Reference — config router bgp primary

Community / KB scenario research

  • Troubleshooting Tip — BGP debug output 107, October 30, 2026 scenario only

Purpose and state-machine boundary

BGP does not begin by exchanging prefixes. A configured neighbor first has to become a reachable TCP endpoint. FortiOS then moves through the BGP finite-state machine: Idle, Connect, Active, OpenSent, OpenConfirm, and Established. The first three states are still about getting transport started. Route maps, prefix lists, and inbound policy cannot repair a TCP connection that has not reached the BGP OPEN exchange.

The October 30 Fortinet troubleshooting note explains that a neighbor remaining in Active with debug message 107-Transport endpoint is not connected has not completed the TCP three-way handshake. This is a transport boundary, not evidence that the peer rejected an NLRI. A related 104-Connection reset by peer indicates that the remote side reset the attempt rather than simply leaving the handshake unanswered.

Objects and packet flow

The local FortiGate needs a route to the configured neighbor address in the correct VDOM/VRF. It selects a source address and egress path, sends TCP SYN to destination port 179, receives SYN-ACK, and completes the handshake with ACK. Only then can peers exchange BGP OPEN messages, compare AS numbers and capabilities, negotiate timers, and proceed through KEEPALIVE to Established. A route to the peer is necessary but not sufficient: return routing, source address, security policy, and any intervening VPN must also permit the same flow.

For multihop eBGP, the peer may be several routed hops away. FortiOS exposes ebgp-enforce-multihop and ebgp-multihop-ttl under the neighbor object. update-source binds the local source to the selected interface address. It changes the local identity used for the TCP attempt; it is not a policy route.

config router bgp
  config neighbor
    edit "192.0.2.2"
      set remote-as 65002
      set update-source "loopback0"
      set ebgp-enforce-multihop enable
      set ebgp-multihop-ttl 5
    next
  end
end

This is an illustrative neighbor fragment. Use the actual peer, AS, interface, and hop count; do not enable multihop merely to mask a missing route.

Evidence and what it proves

Start with get router info routing-table all in the VDOM that owns the neighbor. Confirm the route's next hop and interface, then inspect get router info bgp neighbors <neighbor-ip> for the configured remote AS, local source, timers, and current state. A packet capture filtered to the peer and TCP/179 separates unanswered SYNs from a completed handshake. SYN with no SYN-ACK points toward routing, ACL, remote listener, or return-path failure; a reset points to an active rejection or mismatch. Debug 107 is consistent with an incomplete handshake; it does not identify which hop dropped the packet.

Check password configuration on both peers, QoS treatment of TCP/179, and IPsec Phase 2 selectors when BGP runs over a tunnel. A successful ping proves only that ICMP has a working path; it does not prove TCP/179 is allowed or that the correct source address is used. Once the state reaches Established, move to OPEN errors, capability negotiation, route advertisement, and policy diagnostics.

Operational troubleshooting sequence

  1. Confirm VDOM/VRF, peer IP, remote AS, and route to that peer.
  2. Check the selected local source and egress interface; compare with the remote neighbor configuration.
  3. Capture TCP/179 in both directions and determine whether SYN, SYN-ACK, and ACK complete.
  4. Inspect filters, asymmetric routing, multihop TTL, password, QoS, and VPN selectors according to the observed packet boundary.
  5. After Established, inspect received/advertised routes and route policy separately.

Diagnose the earliest uncompleted state transition. Changing prefix policy while TCP is still Active adds noise and leaves the actual failure untouched.

Lesson 02 · FortiManager

Install-time capability mismatch: udp-not-quic in SSL/SSH profiles

520 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiManager 8.0 Administration Guide — Installing policy packages and device settings primary
  • FortiOS 7.6 CLI Reference — config firewall ssl-ssh-profile primary
  • FortiManager 7.6.8 Release Notes — Known Issues primary

Community / KB scenario research

  • FortiManager 7.6.8 install failure on 2 GB / unsupported models; October 23–29, 2026 scenario only

Why a valid manager object can fail

FortiManager's policy package is a desired configuration model; installation is a compilation and deployment transaction against target devices. A setting can be representable in the FortiManager database and still be unsupported by a particular FortiGate model or FortiOS build. The install wizard validates selected devices, prepares the installation, and can show a CLI preview. The target then parses and applies that payload. These are distinct gates: a clean object editor does not prove every target understands every generated command.

The recent FortiManager 7.6.8 Community case documents bug 1352524. FortiManager adds udp-not-quic to the HTTPS and DNS-over-TLS portions of an SSL/SSH profile. Certain FortiGate devices running FortiOS 7.6 do not expose that attribute, so the device rejects the generated configuration. The issue was initially described for 2 GB devices, but later comments report other models too; model/build capability, not RAM alone, must drive the decision.

Understand the two protocol controls

Under config firewall ssl-ssh-profile, the https and dot subtrees contain separate protocol controls. quic selects how QUIC traffic is inspected, bypassed, or blocked. udp-not-quic specifies the action when matched UDP traffic is not QUIC. They are not synonyms. A model that lacks the CLI node cannot accept a value merely because the manager's schema contains it.

config firewall ssl-ssh-profile
  edit "custom-deep-inspection"
    config https
      set quic bypass
      unset udp-not-quic
    end
    config dot
      set quic bypass
      unset udp-not-quic
    end
  next
end

This illustrates a device-specific removal strategy reported in the Community discussion, not a universal template. Other targets may support the field and require an explicit action. The FortiOS CLI reference documents the option and its meaning for supported targets.

Use validation and preview as evidence

Record the FortiManager build, ADOM version, target model, memory class, and FortiOS build. In the install wizard, run validation for each device and inspect the detailed progress report. The preview is useful: if the unsupported line appears under both https and dot, compare it with the target's CLI parser. A manual command that returns a parse error or return code -61 is strong evidence that the target build does not recognize the node; it is not a routing or reachability failure.

Do not treat a successful install to a higher-capability model as proof that every device in the group supports the setting. A successful retrieve does not necessarily remove a manager-generated default from the desired configuration. Keep the target-specific override scoped to the affected model and inspect the next install preview to prove the line is gone only where intended.

Safe remediation and rollout

  1. Inventory exact target model and FortiOS build; test the CLI node on a representative device.
  2. Inspect install preview and task log to identify the unsupported command and subtree.
  3. For unsupported targets, use a model-scoped device override or unset the field only there; do not globally downgrade the ADOM object.
  4. Re-run validation and preview for affected and unaffected models.
  5. Check current release notes before adopting a fix. The Community article said fixes were expected in 7.6.9 and 8.0.3; verify the actual released build and resolved-issue entry.

A broad workaround can remove inspection behavior from capable devices, while a narrow workaround can leave the unsupported line in later generated payloads if the source of truth is not corrected.

Lesson 03 · FortiAnalyzer

Fluentd Azure Monitor Log Ingestion: output profile, secret variables, and remote-server attachment

547 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiAnalyzer 8.0 New Features — Fluentd supports Azure Monitor Log Ingestion API primary
  • FortiAnalyzer 8.0 Administration Guide — Output profile example primary

Community / KB scenario research

  • Masking Fields in FortiAnalyzer output profiles, October 30, 2026 scenario only

Feature purpose and object model

FortiAnalyzer 8.0 adds a Fluentd output-profile type for the Azure Monitor Logs Ingestion API. This is two linked configuration objects, not one forwarding switch. The Output Profile stores the plugin type and parameters. A Log Forwarding Remote Server object selects the output plugin and references that profile. Creating the profile alone does not send logs; the forwarding destination must be attached to the log-forwarding settings.

On Azure, the pipeline uses an App Registration, Log Analytics Workspace, Data Collection Endpoint (DCE), Data Collection Rule (DCR), and custom table. The application identity needs the documented Monitoring Metrics Publisher role assignment associated with the DCR. The DCR controls the stream and transformation that maps the incoming record into the table schema.

Schema and timestamp requirements

Fortinet's example creates a custom table with the _CL suffix and uses a transformation to derive TimeGenerated from the incoming logtime field. The Logs Ingestion API requires TimeGenerated; a payload with another timestamp name is insufficient unless the DCR transform creates the required column. The sample transformation is:

source
| extend TimeGenerated = todatetime(logtime)
| project-away logtime

The first expression converts the source timestamp to datetime. The second removes the source field after conversion. If the table name, DCR stream, input columns, or transform disagree, authentication can succeed while ingestion fails at schema processing.

Build the profile without exposing secrets

In FortiAnalyzer, go to System Settings → Advanced → Log Forwarding → Output Profile, create a profile, and select Azure Logs Ingestion. Use the default Fluentd configuration as the starting point. Fortinet's example requires six parameters: tenant_id, client_id, client_secret, dce_url, dcr_id, and table_name. The October 30 Community tip shows variable references rather than literal secret values:

<match>
  tenant_id ${TENANT_ID}
  client_id ${CLIENT_ID}
  client_secret ${CLIENT_SECRET}
  dce_url ${DCE_URL}
  dcr_id ${DCR_ID}
  table_name ${TABLE_NAME}
</match>

Define variables under Configuration and Fields, then use Validate and Save. Variable indirection reduces accidental disclosure in profile text, but does not remove the need to protect the variable store and restrict administrative access.

Activate and prove the end-to-end path

After the profile validates, create a Log Forwarding setting with server type Remote Server, select Forward via Output Plugin, and choose the saved profile. Send a small, known test log and correlate it across the chain. Validate and Save proves FortiAnalyzer accepted local profile configuration; it does not prove the DCE is reachable, the client secret is valid, the DCR authorizes the identity, or the table received a row.

Separate failures by layer: token acquisition points to tenant/client/secret or role assignment; endpoint connection points to DCE URL and network path; ingestion rejection points to DCR ID, stream/table name, transform, or schema; no forwarding points first to the Remote Server attachment and selected profile. Inspect Azure-side ingestion diagnostics and table arrival rather than treating local validation as an end-to-end receipt.

Operational controls

  1. Create the Azure identity and grant only the required publisher role for the target DCR.
  2. Create the DCE, DCR, transform, and _CL table before configuring FortiAnalyzer.
  3. Populate the six required variables and validate the output profile.
  4. Attach the profile to a Remote Server forwarding setting and enable intended log types.
  5. Send a controlled event and verify it in the expected table with a valid TimeGenerated value.

Keep credentials out of exported configuration and screenshots. Rotate the client secret through Azure identity management and update the FortiAnalyzer variable without changing the DCR/table contract.

Lesson 04 · FortiSwitch

VRRP destination-route tracking: fail over when the gateway is alive but upstream reachability is lost

485 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiSwitch 8.0 Administration Guide — VRRP primary

Community / KB scenario research

  • Technical Tip — VRRP failover based on destination route monitor, October 14, 2026 scenario only

VRRP role and virtual identity

FortiSwitch VRRP provides a shared virtual IP address for a gateway on an interface. One switch is Master and sends advertisements; backups monitor them and can take over when the Master fails. The group uses a VRID and virtual router IP. FortiSwitch also supports a virtual MAC address, disabled by default and required to be enabled on every member of a VMAC-based group. VRRP requires the advanced-features license.

Ordinary VRRP detects loss of the Master as a VRRP participant. It does not necessarily detect a subtler failure: the switch is powered, its VLAN interface is up, and advertisements continue, but the route to a critical upstream destination has disappeared. Clients still send frames to the virtual gateway, and the active Master can black-hole traffic. Destination tracking extends the election decision beyond local interface state.

How vrdst changes the election

The vrdst setting identifies an IPv4 destination whose route reachability the VRRP instance monitors; IPv6 uses vrdst6. The FortiSwitch 8.0 guide documents one or two tracked addresses. If the Master cannot reach the tracked address, its priority changes to zero. A backup that still has reachability can become Master and own the shared gateway. When the route returns, preemption determines whether the recovered switch takes Master again.

config system interface
  edit "CORE"
    set vrrp-virtual-mac enable
    config vrrp
      edit 110
        set priority 200
        set vrgrp 10
        set vrip 10.10.1.1
        set vrdst 1.1.1.1
      next
    end
  next
end

This is a shortened example; use the correct interface/VLAN, VRID, group, address, and tracked target. The peer must share the VRID and virtual IP, with priority/preemption chosen for the intended takeover.

Evidence and design caveats

get router info vrrp should show VRID, virtual IP, VMAC state, Master/Backup role, priority, and configured vrdst. The Community example shows the original Master moving to BACKUP with priority zero after the monitored destination becomes unreachable, while the peer becomes MASTER. Also inspect the route table and test the tracked destination from both switches; a ping from a management workstation does not prove the switch's own route lookup succeeds.

Choose a destination representing the upstream path whose loss should trigger failover. Do not track an Internet host blocked from both switches or a single endpoint whose ICMP policy changes independently of routing. If both devices lose the same target, both can reduce priority and the desired active/standby result may not occur. Test recovery and preemption deliberately.

Platform and rollout constraints

The FortiSwitch 8.0 guide notes a model-specific conflict: on FS-6xxF models, set vrrp-virtual-mac enable cannot be used with set allow-mac-move enable. Validate the feature matrix and license before building the design. A VMAC takeover is a Layer 2 identity change; verify that upstream switching learns the shared MAC on the new path and that ARP/forwarding converges.

  1. Confirm advanced-features entitlement and model support.
  2. Configure identical VRID/VIP and VMAC behavior on all peers.
  3. Set the tracked destination and verify route reachability from each peer.
  4. Simulate loss, observe priority zero and role transition, then restore reachability and test preemption.

Lesson 05 · FortiAP/Wireless

IPv6 CAPWAP management: multicast or DHCPv6 discovery, controller access, and NPU boundary

507 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiOS 8.0 New Features — FortiAP management through IPv6 primary
  • FortiAP 8.0 Configuration Guide — AP network interface primary

Community / KB scenario research

  • FortiAP 231K repeated cwWtpd/lldpd restarts and CAPWAP failure; active October 22–30, 2026 scenario only

What IPv6 management changes

FortiOS 8.0 allows FortiGate to manage FortiAP over IPv6 for major wireless management functions. IPv6 can be used for Access Controller discovery, CAPWAP control and data channels, managed AP upgrades, and tunnel- or bridge-mode SSID connections. This is a management/control-plane capability; it is not the same as enabling IPv6 addressing for wireless clients. A client can use IPv6 on an SSID while the AP discovers its controller over IPv4, or the AP can use IPv6 for CAPWAP while client addressing remains IPv4.

The AP must learn the controller's IPv6 address and reach the FortiGate interface that accepts wireless-fabric management. The interface's IPv6 access list must include fabric. An IPv6 address alone does not enable AP management. Routing, neighbor discovery, multicast scope, DHCPv6 service, and control/data ports must align.

Two discovery methods

Fortinet documents two controller discovery paths. Multicast discovery uses the controller multicast address configured under config wireless-controller global. DHCPv6 discovery uses Option 52 to advertise the Access Controller IPv6 address to the AP. Select the method supported by the reachable management network and ensure the advertised address is routable from the AP.

config system interface
  edit "port3.66"
    config ipv6
      set ip6-address 2001:db8:66::1/64
      set ip6-allowaccess ping fabric
      set ip6-send-adv enable
      set ip6-manage-flag enable
      set ip6-other-flag enable
    end
  next
end
config wireless-controller global
  set discovery-mc-addr6 FF02::18C
end

For DHCPv6, the server's Option 52 carries the controller IPv6 address. Do not advertise a link-local address if the AP/controller relationship requires routed reachability.

CAPWAP data path and hardware caveat

After discovery, the AP establishes CAPWAP control and data communication with the controller. A capture should distinguish UDP 5246 control traffic from UDP 5247 data traffic and show actual IPv6 source/destination addresses. Fortinet documents CAPWAP offload for IPv4 and IPv6 data traffic on NP7 and NP7lite platforms. It explicitly does not support CAPWAP offload on NP6/NP6lite FortiGates. Lack of offload is a performance/platform boundary, not proof IPv6 CAPWAP cannot function.

Verify controller address, interface fabric access, route, and packet flow before investigating SSID or client authentication. If the AP is authorized but no data channel forms, inspect data separately from discovery/control.

Use the recent CAPWAP failure as a diagnostic lesson

The October 22 Community discussion describes a FortiAP 231K repeatedly restarting lldpd and cwWtpd, with “Send debug config info to capwap failed.” Fortinet staff noted that these logs alone do not identify root cause and requested the exact AP firmware build, FSM state, crash log, power information, and certificate status. The same symptoms on replacement hardware make it important to test software/compatibility and network reachability before another RMA.

Useful AP-side evidence includes fap-tech, wcfg | grep fsm-state, diag_debug_crashlog read, cw_diag power, and cw_diag -c cert Fortinet_CA1.cer. Correlate these with an on-wire capture from the AP management VLAN. A daemon restart is a symptom; it is not proof of a missing CA certificate, broken CAPWAP route, or defective radio.

Verification sequence

  1. Confirm FortiOS/AP compatibility and AP firmware build.
  2. Check the FortiGate IPv6 address and ip6-allowaccess fabric.
  3. Verify multicast discovery or DHCPv6 Option 52.
  4. Capture IPv6 CAPWAP control/data packets and check the return path.
  5. Inspect AP FSM/crash/certificate/power evidence before changing authorization or replacing hardware.

Lesson 06 · FortiNAC

802.1X EAP session correlation: interpreting “No EAP session matching state”

525 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiNAC 9.4 Administration Guide — Local RADIUS Server primary
  • FortiNAC 9.4 Administration Guide — Wired devices and 802.1X primary
  • FortiNAC 9.4 Administration Guide — RADIUS activity primary

Community / KB scenario research

  • Support Forum — No EAP session matching state, October 16–20, 2026 scenario only

EAP is a stateful exchange

In 802.1X, the endpoint supplicant and network authenticator do not send a username/password in one self-contained packet and receive a final answer. They exchange EAP messages through the switch or wireless controller, which relays them to RADIUS. FortiNAC must maintain context for the EAP conversation while it processes Access-Request, Access-Challenge, and subsequent responses. The outer RADIUS transaction carries EAP-Message attributes and an identifier; the server must associate each continuation with the active authentication state.

The recent FortiNAC support discussion reports intermittent wired and wireless failures with “No EAP session matching state” and an outer-method failure between the switch IP and FortiNAC. A Fortinet staff response explains that the server is receiving EAP packets but cannot match them to an active EAP session. Possible causes include delays, load balancing, or the NAS/supplicant interrupting or restarting authentication. That symptom does not by itself prove that the user's password is wrong.

Local and proxy RADIUS are different paths

FortiNAC supports proxy RADIUS and local RADIUS modes. Proxy mode is enabled by default: FortiNAC processes MAC authentication but proxies 802.1X EAP authentication to an external RADIUS server, and can proxy accounting to that server. Local mode, introduced in FortiNAC 8.8 and disabled by default, processes MAC and EAP authentication itself. Local mode supports TTLS/PAP, TTLS/MSCHAPv2, PEAP/MSCHAPv2, TLS, and FAST, subject to prerequisites. The local RADIUS service does not provide accounting; accounting can still be proxied externally.

For local EAP, FortiNAC needs a server certificate. PEAP/MSCHAPv2 and TTLS/MSCHAPv2 authenticate AD users and require FortiNAC to join the domain; the documented limitation is one domain. EAP-TLS validates the client certificate and requires the Endpoint Trust Certificate. If both local and proxy modes are configured, their authentication ports must differ. A correct EAP state machine can still fail later at certificate, domain, or credential validation.

Correlate the transaction, not just the final message

Use Network → RADIUS → Activity and authentication logs to identify the device, NAS IP, user or MAC identity, time, EAP method, and outer-method result. Correlate the switch/AP's RADIUS request and response sequence with FortiNAC logs. If a request is retransmitted, the authenticator restarts EAP, or different RADIUS destinations receive different portions of the exchange, the server may see a packet for which it has no active session context. The Community response specifically suggests checking delays, load balancing, NAS/supplicant interruptions, peak load, and service restarts.

Do not assume “RADIUS server reachable” proves the EAP exchange is coherent. A successful Access-Request or open UDP/1812 path proves only transport to the service. It does not prove a later EAP-Message is associated with the same live exchange or that the outer method completed.

Troubleshooting and configuration discipline

  1. Confirm whether the device/SSID uses local or proxy RADIUS and identify the selected profile.
  2. Compare NAS-IP, Calling-Station-Id, EAP method, and timestamps for a success and failure from the same endpoint.
  3. Check whether the NAS retransmits, changes source, or restarts the supplicant exchange; avoid uncontrolled load balancing across stateful RADIUS servers.
  4. Inspect FortiNAC load, RADIUS service restarts, and exact EAP certificate/domain prerequisites.
  5. After changing the RADIUS path or EAP method, test one endpoint and verify a complete Access-Challenge/Accept sequence.

Escalate with correlated RADIUS Activity and output.master evidence if the issue persists. Ask which EAP continuation lost its server-side context rather than assuming a password failure.

Lesson 07 · FortiNAC-F

FortiNAC Manager global-object synchronization: GUID identity versus local database IDs

555 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiNAC-F 7.6 Manager Guide — Server Synchronization (vF 7.6.3+) primary
  • FortiNAC-F 7.6 Manager Guide — CA Management primary
  • FortiNAC-F 7.6 Manager Guide — Requirements primary

Community / KB scenario research

  • Troubleshooting Tip — Manager synchronization GUID conflict for Group-GROUP_NAME, October 9, 2026 scenario only

Two synchronization mechanisms

FortiNAC Manager controls more than one kind of replication. Host and user propagation moves endpoint identity/state between managed Control Servers as devices roam. Global Object Synchronization distributes centrally managed configuration objects such as Admin Profiles, Groups, Roles, User/Host Profiles, Endpoint Compliance Policies, configurations, scans, and Security Actions used by Endpoint Compliance. These are different data flows with different identities and timing. The FortiNAC-F 7.6.3+ guide describes host propagation separately from global-object synchronization; the latter runs automatically on a ten-minute interval when enabled.

For global objects, the Manager is authoritative. Information on the managed FortiNAC server is read-only, and information older than the Manager's copy is overwritten. A manual Synchronize Now also overwrites the managed server's copy of globally shared objects. Investigate an object-identity and authority problem before editing the local CA object.

GUID is not the local row ID

The October 9 Community troubleshooting tip describes a GUID conflict for a globally synchronized Group. Its example shows the Manager's row ID and GUID as a large value, while the managed CA has a different local row ID. That difference is normal: database primary keys are local to each appliance. The cross-appliance GUID is the identity used to associate the same global object. The failure occurs when the managed server's GUID is stale or incorrectly set, not merely because its local numeric ID differs.

The log signature is a GlobalObjectGRPCClient sync Failed GUID conflict message for a group table. The article compares ID, name, guid, landscape, globalModifiedDate, and modification metadata on both Manager and managed CA. The object name and GUID relationship matter more than equality of local row IDs.

Synchronization mechanics and prerequisites

When global synchronization is enabled, managed CAs synchronize with the Manager every ten minutes. The CA Management view exposes managed server status and last configuration sync, and the Manager can manually push global objects to a selected CA. The FortiNAC-F requirements guide says the Manager and managed CA servers must run the same code version for functions such as server synchronization to be supported. Inter-server ports must be open; if a proxy is configured, Manager and CA port1 addresses must be in the proxy exclusion list.

A healthy CA-management connection does not prove every global object synchronized. A CA can be reachable while an individual row fails GUID validation. Conversely, a stale global object may be overwritten by the next sync, so manual local edits are not a durable correction.

Safe repair and verification

The Community article demonstrates setting the stale managed-CA GUID to the unassigned value -1 for the specific affected global object, then synchronizing again. It explicitly instructs administrators to back up the database first, compare object names and GUIDs with the Manager, and avoid changing objects that exist only on the managed server. Direct database writes are high-risk maintenance; perform them only with a current backup and preferably under Fortinet Support guidance in a maintenance window.

-- Example only: verify the exact row and GUID before any change
SELECT ID,name,guid,globalModifiedDate
FROM Group
WHERE name='ALL_MANAGEMENT';

-- Only after backup and Support review:
UPDATE Group SET guid=-1
WHERE ID=1 AND name='ALL_MANAGEMENT' AND guid=1;

Afterward, query the same row, confirm the intended GUID state, trigger Synchronize Now, and inspect Manager/CA logs plus Last Configuration Sync. Verify that the group is present as a global read-only object. Do not run a broad update across all groups; local-only objects must retain their local identity.

Lesson 08 · FortiAuthenticator

TACACS+ client-policy binding and the authentication-before-authorization boundary

446 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

Client registration and service binding

FortiAuthenticator does not accept an arbitrary TACACS+ packet merely because the daemon is reachable. The network device must be registered as a TACACS+ client and assigned to a policy. The TACACS+ service is enabled or disabled per FortiAuthenticator network interface, so the interface receiving the request must have the service enabled. The policy determines how the request is authenticated; authorization rules then apply to users and groups to decide which services or commands are permitted.

This produces a layered decision: network-device identity and shared secret, service listener, policy selection, authentication, then authorization. A failed login should be traced through those stages rather than immediately editing command rules. A client that never matches a policy has not reached the user authorization decision.

The authentication/authorization ordering issue

The October 30 Community post describes a Cumulus switch whose Linux PAM TACACS+ client sends an authorization request before it sends authentication. The same FortiAuthenticator server works with another network-device family that performs authentication first. The FortiAuthenticator TACACS+ guide documents authentication and authorization as distinct operations and does not offer an “authorize before authenticate” compatibility mode. Changing a command authorization rule cannot fix a client that invokes the phases in an unsupported order.

Establish which TACACS+ packet arrives first and whether FortiAuthenticator has an authenticated user/session to which the authorization request can be attached. If the NAS implementation requires authorization-first behavior, align the NAS/client workflow with the supported sequence or use a supported authentication method—not broader authorization rules.

Authorization rules and supported limitations

Create authorization rules and assign them to users or groups. They can distinguish shell and non-shell service requests and define which command/service attributes are accepted. Confirm the rule assignment and group membership after authentication. FortiAuthenticator exposes TACACS+ debug logs at https://<FAC-IP>/debug/; select TACACS+ from the Service dropdown. This is useful to confirm client matching, policy selection, authentication, and authorization events.

Two protocol limitations matter. TACACS+ authentication on FortiAuthenticator does not currently support challenge/response. For two-factor authentication, the user appends the token to the password—for example, password followed by the OTP value. End users cannot change their password during login. A client expecting an interactive challenge or password-change exchange will not become compatible by changing an authorization profile.

Operational verification

  1. Verify TACACS+ is enabled on the ingress interface and the NAS IP/secret is registered.
  2. Confirm the device is assigned to the intended policy and that the request matches it.
  3. Inspect TACACS+ debug to determine whether authentication or authorization arrived first.
  4. Confirm successful authentication and then inspect user/group authorization-rule matches.
  5. Test one allowed and one denied command; preserve logs for both.

A Cisco success does not prove another NAS sends the same TACACS+ sequence. Validate each NAS implementation independently and do not treat server reachability as protocol interoperability.

Community / KB scenario research

Two enforcement levels

FortiPAM ZTNA control can be applied at appliance access level and protected-secret level. Access-level control determines whether an endpoint may log in through a particular interface. Secret-level control determines whether that endpoint may access or launch a secret protected by ZTNA. A trusted endpoint must present a valid client certificate and meet required posture-tag conditions. FortiPAM must be connected to the same FortiClient EMS server that the endpoint uses; a tag from another EMS control plane is not equivalent evidence.

The access proxy validates the client certificate. A firewall access-proxy policy can require ztna-status enable and one or more ztna-ems-tag values. The proxy's API gateway maps URL prefixes to services; Fortinet's example maps /pam to pam-service, separately from TCP forwarding and GUI routes.

Certificate and bearer token are different identities

The October 12 Community tip demonstrates REST API access using both a client certificate and an API user's bearer token. The certificate establishes endpoint/device trust at the TLS/access-proxy layer. The bearer token identifies the FortiPAM API user and is evaluated by the API service. Passing one does not substitute for the other. A request can complete TLS and still fail API authentication, or carry a valid bearer token from an endpoint not allowed by ZTNA policy.

curl.exe --location "https://pam.example.net/pam/<resource>" ^
  -H "Authorization: Bearer <API_TOKEN>" ^
  --cert "CurrentUser\MY\<CERT_THUMBPRINT>"

The Community example uses -k; that disables server-certificate verification and should not be the production default. Install and trust the correct server CA and validate the TLS chain. Protect the API token and certificate private key separately.

Access-proxy design and unmanaged endpoints

FortiPAM's guide explains that trusted and untrusted endpoints can be separated by using different NICs or multiple access proxies/VIPs. One interface can enforce ZTNA while another remains unrestricted, but the network must then restrict who can reach the open interface. The guide also documents empty-cert-action accept for a design in which endpoints without a certificate may log in to access non-ZTNA-protected secrets. This does not make protected secrets available to unmanaged endpoints; secret-level policy still governs what they can launch.

Use separate VIPs and policies when managed and unmanaged clients must coexist. Keep the no-ZTNA path source-restricted and avoid a broad any-to-any policy that bypasses the device-trust boundary.

Verification sequence

  1. Confirm FortiPAM's EMS connector is connected to the same EMS server as the client.
  2. Verify endpoint tag and certificate chain/thumbprint.
  3. Inspect access-proxy client-cert setting, VIP, API gateway URL map, and firewall policy tag.
  4. Test TLS first, then API bearer authentication, then secret-level authorization.
  5. Use a controlled API resource and confirm the user has only intended secret permissions.

Identify whether the failed gate is TLS/device trust, EMS posture, API identity, URL routing, or secret authorization. Do not label every failure simply “ZTNA denied.”

Offline OS repository synchronization and ordered Supervisor, Worker, and Collector upgrades

533 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiSIEM 7.5.1 Offline Installation and Upgrade Guide primary

Community / KB scenario research

  • Technical Tip — retrieve fsm-sync-os-repo.sh from target upgrade package, October 16, 2026 scenario only

Why offline upgrades need a separate OS repository

FortiSIEM's offline installation and upgrade guide distinguishes fresh installation from upgrading an existing environment. In a disconnected deployment, the OS repository must be mirrored to a staging host and mounted where the upgrade process can read it. Copying only the main FortiSIEM upgrade ZIP is not enough; the OS package repository is a separate dependency.

For FortiSIEM 7.5.1, the guide requires at least 2 TB on a mounted filesystem for the repository. Earlier 7.5.0 documentation described a smaller 375 GB requirement, so do not carry an old capacity estimate into a 7.5.1 run. The synchronization script launches multiple wget processes in the background. The command returning does not prove all downloads completed or disk space was sufficient.

Get the script from the correct release

The October 16 Community technical tip explains how to extract fsm-sync-os-repo.sh from the targeted upgrade ZIP. It creates /opt/upgrade, transfers and unpacks the ZIP, then extracts the script from the versioned FortiSIEM RPM using rpm2cpio and cpio. This avoids blindly reusing a script from a different running version. Verify the package/build in the path and keep the script paired with the upgrade package that will consume the repository.

mkdir -p /opt/upgrade
cd /opt/upgrade
7za x FSM_Upgrade_All_<BUILD>.zip
rpm2cpio <VERSIONED_RPM> | cpio -i --to-stdout './opt/phoenix/deployment/jumpbox/fsm-sync-os-repo.sh' > fsm-sync-os-repo.sh

Run the script with documented permissions. Monitor all background wget processes and confirm the full repository is present before moving it to the isolated environment.

Mount and upgrade the core nodes

Copy the repository to USB or export it through NFS. Mount it on the Supervisor at a stable path such as /offline-repo, and add the mount to /etc/fstab so it survives reboot. Check the mount and run mount -a before upgrading. Unzip the target package under /opt/upgrade and invoke:

./upgrade.sh --offline-osrepo-path /offline-repo

The Supervisor or Manager uses the mounted repository instead of reaching the Internet. If the mount is missing or the parameter points to the wrong path, an offline site can still attempt to access the remote repository. The core node must return healthy before proceeding to Workers.

Worker and Collector dependencies

After the Supervisor is upgraded and online, the Worker can reuse the same offline repository. The guide instructs the operator to verify the mount, copy the upgrade package to the Worker, and obtain the offline-repository OS update password from the upgraded Supervisor's /etc/dnf/dnf.conf. The Worker script consumes it with --offline-osrepo-super-passwd. Protect that password; it is not a general-purpose user credential.

Collectors follow a different path through the GUI and Image Server. The guide says to select Disabled for Hash Check in Image Server settings before the documented offline Collector upgrade so the Collector can obtain the image from Supervisor without Internet access. Treat this as a version-specific procedure and protect the repository through controlled staging, checksums, and access control; do not interpret it as permission to disable integrity checks broadly.

Verification and failure isolation

  1. Confirm target release/build and use its matching sync script.
  2. Verify at least the documented 2 TB for 7.5.1 and monitor wget completion.
  3. Validate mounted path and persistent fstab entry on Supervisor and each Worker.
  4. Upgrade Supervisor/Manager first, then Workers with the required password, then Collectors through Image Server.
  5. If a component reaches out to the Internet, inspect its own parameter/mount/role path rather than assuming all nodes inherit the Supervisor's offline setting.

Lesson 11 · FortiSASE

FortiClient Multi-Connect: concurrent IKEv2 tunnels and Windows DNS priority

458 focused words · mechanics, evidence, dependencies and operations

Primary feature / administration documentation

  • FortiEndpoint Administration Guide — Remote Access / Multi-Connect primary
  • FortiSASE Feature Administration Guide — Tunnel settings primary

Community / KB scenario research

  • Support Forum — FortiSASE IPsec Multi-Connect, October 16–17, 2026 scenario only

What Multi-Connect enables

FortiClient's Multi-Connect option allows more than one eligible IPsec VPN tunnel to be connected concurrently. The FortiEndpoint administration guide labels the feature beta and limits it to IPsec IKEv2 tunnels. The endpoint profile can contain up to 50 eligible IKEv2 tunnels. This is an endpoint tunnel capability, not a statement that every FortiSASE tunnel object exposes editable Phase 1 and Phase 2 settings.

In FortiSASE, the SASE service tunnel is managed by the service. The October 16 Community thread asked why Phase 1 and Phase 2 could not be entered for the SASE tunnel; Fortinet staff clarified that those settings cannot be changed there and asked whether the SASE tunnel or on-premises tunnel was failing. The SASE-managed tunnel and an endpoint-profile custom tunnel have different ownership.

Tunnel settings and control/data planes

FortiSASE uses IKEv2 settings for its security PoPs and configures corresponding settings on FortiClient. The tunnel-settings guide lists different proposals and parameters for PoPs and endpoint clients; custom/alternative IPsec gateways must match the settings FortiSASE configures on the endpoint for that tunnel type. Do not copy a PoP-side table into an unrelated custom gateway without checking which side the table describes.

The endpoint management/telemetry channel distributes the profile and tunnel definitions. IKEv2 establishes each data tunnel independently. A healthy telemetry connection proves the endpoint received policy; it does not prove each IKE_SA and CHILD_SA negotiated successfully. One working tunnel does not prove the second has a matching peer ID, proposal, route, or firewall path.

DNS Priority is a Windows interface preference

When Multi-Connect is enabled, the DNS Priority list contains eligible IPsec IKEv2 tunnels in the profile. The administrator orders the list by drag-and-drop. The guide states Windows uses this order to determine which tunnel interface has higher priority for DNS queries; the priority corresponds to the VPN tunnel interface metric. Windows queries the DNS server from the highest-priority tunnel first and, if that query fails, tries the next tunnel. This is not a general traffic-steering rule for every application packet.

Changing the list can alter which DNS view a user receives even when both tunnels remain up. Split-horizon names may resolve differently through SASE and on-premises DNS, so validate name resolution from the endpoint rather than inferring it from tunnel status.

Verification workflow

  1. Confirm FortiClient version, platform, beta feature status, and that each tunnel is IKEv2.
  2. Identify the SASE-managed tunnel separately from each custom/on-prem tunnel.
  3. Check IKE and CHILD_SA state for each tunnel independently and compare proposals, IDs, NAT-T, DPD, and routing.
  4. Inspect Windows interface metrics and DNS Priority; test a name with different answers on each resolver.
  5. Do not modify SASE-owned Phase 1/2 settings; correct the custom gateway or endpoint profile through supported controls.

Isolate tunnel establishment from DNS preference. Two tunnels can be up while names resolve through the wrong DNS path, or one tunnel can fail independently.

Monthly traffic-volume quota steering: billing counters, overage values, and SLA member selection

Primary feature / administration documentation

  • FortiOS 8.0 SD-WAN New Features — Overview primary

Community / KB scenario research

  • No directly matched recent Community scenario was verified; the lesson is documentation-led.

Why volume quota is a steering input

Some WAN underlays have a monthly data allowance and charge overage once the allowance is exceeded. FortiOS 8.0 adds per-member volume quota settings so SD-WAN can alter member preference when accumulated traffic reaches a billing threshold. The member remains physically up; this is a cost/weight/volume-ratio adjustment used by SD-WAN selection, not a link-down detector. The feature supports HA.

Under config system sdwan, each member can have quota-limit in gigabytes, billing-start-day, overage, overage-cost, overage-weight, and overage-volume-ratio. The billing start day controls when usage begins to count for the monthly period. Overage settings are available when a quota is configured. When the threshold is crossed and overage is enabled, preference values are applied to influence member selection.

Configure quota and the consuming service

The quota configuration does not independently define which applications move. SD-WAN service rules still determine which traffic matches and which members are eligible. Fortinet's example uses SLA-mode services for IPv4 and IPv6 and gives two members: one with a small monthly allowance and another as the alternative. The first member is preferred before the threshold; after it is over quota, its in-memory cost is increased so the service can select the other eligible member.

config system sdwan
  config members
    edit 1
      set interface "agg1"
      set quota-limit 2
      set billing-start-day 1
      set overage enable
      set overage-cost 10
      set overage-weight 1
      set overage-volume-ratio 1
    next
  end
end

This is an illustrative member fragment. The matching service must reference intended members and SLA, and the alternate must be alive and allowed by the service rule. If the service excludes the alternate, changing quota preference cannot force traffic to an unavailable path.

Read billing and service state together

Fortinet adds diagnose sys sdwan bill member <id> to inspect quota state. Output includes member interface, overage enablement, quota limit, whether it is overaged, billing start day, reset information, current bytes, and bytes used since the billing day. This is evidence for the accounting mechanism. It does not prove which member a particular flow uses.

Use diagnose sys sdwan service4 and service6 to inspect the service's selected members, SLA state, and ordering. Then capture a known flow on ingress and egress to prove the data plane moved. The guide's example shows usage crossing 2 GB, the member becoming overaged, the cost changing in memory, and the flow moving to the second member while both links remain up.

Failure isolation and billing-cycle behavior

If traffic stays on the quota-exceeded member, check whether it is actually overaged, whether overage enable is set, and whether the billing start day matches the ISP contract. Then inspect the matching service: the alternate may fail its SLA, be excluded by the member list, or lose to another service rule. Do not diagnose this as a health-check failure unless SLA state actually changes. A link can remain alive and become less preferred because of quota.

On the next billing day, accumulated usage and overage preference reset according to the configured period. Validate reset and HA behavior before relying on quota as a cost-control mechanism. The feature controls selection; it does not enforce a hard bandwidth cap or stop packets if the service still chooses the member.

Operational checklist

  1. Translate the ISP billing cycle into billing-start-day and quota values.
  2. Enable overage and define the intended cost/weight/volume-ratio adjustment.
  3. Confirm matching IPv4/IPv6 services use an appropriate selection mode and include the alternate member.
  4. Monitor billing counters and member SLA state together.
  5. Test pre-quota, over-quota, and reset-day behavior with a controlled flow.
