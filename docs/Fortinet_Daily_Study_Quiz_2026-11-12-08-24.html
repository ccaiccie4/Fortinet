01 / 12 · FortiGate · 771 focused words

Exact Data Matching for DLP: record-aware protection with EDM templates

Why this exists. Ordinary DLP dictionaries and regular expressions are useful when the protected value can be described as a pattern. They are less precise when an organization needs to recognize a record from its own data set, such as a customer SSN paired with a name or email address. FortiOS Exact Data Matching (EDM) lets the administrator index a controlled CSV or TXT source and map each source column to a FortiGate data type. A match is evaluated against the mapped record, reducing false positives compared with a broad keyword rule.

Data model and matching logic

The source is a CSV or TXT file containing up to 32 columns. Each indexed column represents values or patterns for a built-in data type such as an SSN, credit-card number, keyword, or other supported EDM type. The source can be uploaded to the FortiGate or hosted as an external data feed. A local upload is a snapshot: it is not periodically synchronized, so changes require an explicit file update. An external feed is represented as a data-type external resource and can be refreshed at a configured interval. FortiOS documents model-dependent size limits for external data feeds, so do not assume a data set that works on a high-end platform will fit an entry-level appliance.

The EDM template maps column numbers to data types and defines the logical match. All of these fields are conjunctive: every configured field must match. Any of these fields is disjunctive: the configured number of fields from that group must match. For example, column 1 may be a US SSN and columns 3 and 9 may be first name and email. Requiring the SSN plus either the first name or email makes the rule more discriminating than matching an SSN alone. This is record logic, not a claim that every string in a message must be present in one order.

Inspection path

The template is not itself an enforcement point. The operational chain is data source → EDM template → DLP sensor → DLP profile rule → firewall policy. The DLP rule chooses the sensor, protocol, match type and action (for example, block or log). The policy must actually carry the DLP profile. Fortinet's example uses proxy-based inspection and a deep-inspection SSL profile for HTTPS uploads. For HTTPS, SMTPS, POP3S, IMAPS and FTPS, encrypted content must be decrypted by the inspection engine, and the client must trust the FortiGate deep-inspection CA. Without that trust and inspection path, the presence of an EDM template does not prove that encrypted payloads were inspected.

config system external-resource
    edit "customer-data"
        set type data
        set resource "https://192.0.2.20/customer_data.csv"
        set refresh-rate 60
    next
end

config dlp exact-data-match
    edit "Customer-SSN-EDM"
        set data "customer-data"
        config columns
            edit 1
                set type "ssn-us"
            next
            edit 3
                set type "edm-keyword"
            next
            edit 9
                set type "edm-keyword"
            next
        end
    next
end

This is the source-defined object relationship; complete the sensor, profile rule and firewall-policy binding in the GUI or the matching CLI hierarchy for the target FortiOS build. Do not copy sample data or real personal information into a lab report.

What to verify

  • Confirm the external resource is reachable and refreshes at the intended interval. A successful fetch proves source access, not that every row is semantically valid.
  • Open the EDM template's entries and inspect the column-to-type mapping. Fortinet notes that the GUI can display entries as “Valid” without validating every value against its column type; a malformed value may therefore be displayed but not used for matching.
  • Generate a controlled test message that contains a known test record and verify the DLP log, matched data types, policy ID and action. A log proves that the inspected transaction matched; absence of a log does not by itself prove that the data feed is broken.
  • Verify the policy's inspection mode, DLP profile and SSL inspection profile. A policy hit alone does not prove the DLP engine saw decrypted content.

Operational boundaries

Use a local upload when the data set is small and changes infrequently; use an external feed when the source of truth changes and refresh must be automated. External feeds have platform-specific size limits. Local uploads require a platform with a hard disk and are not automatically refreshed. Treat the data feed as sensitive: it contains the exact values the firewall is being asked to protect. Limit feed access, avoid logging raw sensitive values unnecessarily, and plan a controlled refresh test after schema changes. When matching stops after a firmware or hardware change, check platform support and inspection mode before rebuilding the template. EDM is only effective when the data source, field mapping, inspection path and policy action all line up.

02 / 12 · FortiManager · 596 focused words

Remote GUI access to managed FortiGate: the 8082 proxy path and FGFM boundary

Purpose. Remote Access lets an operator open the managed FortiGate GUI from FortiManager's Device Manager without first creating a separate direct management route from the workstation to every branch firewall. It is not simply a bookmark to the FortiGate address. FortiManager acts as an HTTP proxy for the browser session, while the existing FGFM relationship remains the management/control relationship between FortiManager and FortiGate.

Two paths, two failure domains

The workstation first reaches the FortiManager proxy listener, TCP/8082 by default. FortiManager then uses the managed-device relationship to reach the FortiGate GUI. The FortiGate still performs its own administrator authentication and authorization. The feature therefore has at least four independent gates: the FortiManager administrator must have the Remote GUI Access capability in the assigned admin profile; the browser must reach the FortiManager proxy port; the FGFM tunnel must be established; and the FortiGate HTTPS service/certificate/trusted-host policy must accept the proxied request.

Enabling the proxy globally does not automatically grant every FortiManager administrator permission to use it. Fortinet documents both a system setting and an admin-profile setting. A representative configuration is:

config system admin setting
    set fgt-gui-proxy enable
    set fgt-gui-proxy-port 8082
end

config system admin profile
    edit "Network-Operations"
        set fgt-gui-proxy enable
    next
end

The port can be changed, so firewall rules and packet captures must use the configured value rather than assuming 8082. The FGFM control tunnel normally uses TCP/541; that tunnel being up is necessary but does not prove the browser-to-proxy leg is open.

Authentication and trust

The browser is redirected to the FortiManager address and proxy port. After the proxy connection is established, the FortiGate login page is served through that path and the operator authenticates to the FortiGate. If the FortiGate uses trusted hosts for administrators, the FGFM tunnel-side address must be considered in that trust policy. The FortiGate HTTPS server certificate must be valid. Deep inspection or another implicit SSL proxy in the path can interfere with the proxied GUI transaction and should not be casually inserted into this management path.

Diagnosing a 502 or “Error reading from remote server”

  • Check the FortiManager admin profile first. If the feature is not authorized, network captures will not repair the missing permission.
  • Confirm FGFM is established and up. This tests the management relationship, not the browser proxy listener.
  • Capture TCP/8082 on FortiManager and FortiGate. A SYN that never reaches FortiManager points to workstation-to-proxy routing or filtering; a request that reaches FortiManager but fails upstream shifts attention to the FortiGate leg.
  • Check the FortiGate HTTPS server certificate, custom admin-sport and trusted-host entries. A stale certificate can cause the upstream proxy to fail even when FGFM is healthy.
  • Check the exact FortiManager/FortiOS release pair. Community troubleshooting notes version-specific 502 behavior with non-standard admin-sport values; do not apply a workaround from a different release without checking the applicable known-issues list.

Useful packet capture syntax from the Community troubleshooting material is diagnose sniffer packet any "port 8082" 3 on both ends, adjusting the port if customized. A capture proves whether packets traverse that interface; it does not prove that the proxy can complete TLS or that the FortiGate accepts the administrator.

Deployment caveats

FortiManager Cloud does not support GUI Remote Access to managed FortiGates; SSH remote access is a separate supported workflow. Treat this as a management-plane convenience with explicit RBAC and network controls. Keep the proxy port reachable only from trusted operator networks, retain FortiGate-side authentication, and audit the operator identity at both management layers. Do not confuse a browser redirect failure, a FortiManager permission failure and an FGFM outage: they occur at different transaction boundaries and require different evidence.

03 / 12 · FortiAnalyzer · 577 focused words

Device Manager status: OFTP state, Last Log Time and mode-specific no-log thresholds

Why the status can mislead. FortiAnalyzer Device Manager shows an Up/Down state, but that state is a derived health indicator rather than a direct statement that the firewall's logging configuration is correct. Fortinet documents that the state is based on the OFTP connection when the device supports OFTP and/or the age of the last received log. The GUI also exposes Last Log Time, logging mode, average log rate and other device metadata. An engineer should interpret these signals together.

How the evaluator works

For near-real-time logging, the default no-log threshold is 15 minutes. For scheduled uploading, the default threshold is six hours. FortiAnalyzer lets the administrator change these separately:

config system log settings
    set log-interval-dev-no-logging 15
    set log-upload-interval-dev-no-logging 360
end

The first value is the number of minutes without received logs before a near-real-time device is considered Down. The second is the number of minutes without uploaded logs before a scheduled-upload device is considered Down. Do not copy the example values blindly into production; first confirm the device's logging mode and expected delivery cadence. A scheduled-upload firewall that sends a batch every few hours should not be judged by the near-real-time threshold.

OFTP connectivity and log freshness answer different questions. An OFTP session can be established while the latest log timestamp is old, for example because the device has stopped generating or forwarding the expected records. Conversely, after a FortiAnalyzer restart, the firewall can reconnect and resume log delivery before Device Manager's displayed state and Last Log Time have fully reconciled.

Post-reboot convergence scenario

A recent Fortinet Community Technical Tip describes a 10–15 minute interval after FortiAnalyzer reboot in which Device Manager can show Down and a blank or stale Last Log Time even though FortiGate reports its FortiAnalyzer connection as registered/up. The article's key lesson is to test the data path rather than treating the GUI state as definitive. On the FortiGate, run execute log fortianalyzer test-connectivity and get log fortianalyzer setting status. On FortiAnalyzer, diagnose test application oftpd 3 lists devices currently sending logs, and diagnose fortilogd lograte shows the receive rate. Increasing packet/receive counts are stronger evidence of live ingestion than a stale status label.

Evidence and escalation

  • Registered/up on FortiGate: proves the FortiGate's connection state, not that the correct ADOM, policy or event types are being indexed.
  • OFTP device appears in the oftpd listing: proves that the receiver sees the device session, not that all expected log classes are present.
  • Increasing fortilogd rate: proves that log traffic is arriving, not that reports or analytics are current.
  • Last Log Time advances: proves recent receipt of at least one log, not completeness of the stream.

If the UI has not recovered after roughly 30 minutes, or the device cannot reach FortiAnalyzer, move from convergence testing to fault isolation: check routing and port 514 reachability, device authorization in Device Manager, the logging mode, FortiAnalyzer's fortilogd service and release-specific known issues. Capture firmware versions, reboot time and command output before opening a TAC case. Avoid changing the no-log threshold merely to hide a real receive outage.

Operational design

Schedule FortiAnalyzer reboots with an expected status-refresh window in the change plan. During the first 10–15 minutes, use source-side connection state and receiver-side counters to establish whether the pipeline is recovering. Only escalate when the receive evidence fails to recover or the delay exceeds the documented/observed convergence window. This prevents unnecessary policy changes during a normal post-reboot reconciliation period while preserving a clear boundary for a genuine outage.

04 / 12 · FortiSwitch · 612 focused words

MACsec dynamic CAK: RADIUS authentication, MKA and secure association keys

Purpose. MACsec protects Ethernet frames on a point-to-point link by providing link-layer confidentiality and integrity. On a FortiSwitch it can secure switch-to-switch links, including links that carry VLANs and control protocols. FortiSwitch supports pre-shared-key (PSK) mode and dynamic connectivity-association-key (CAK) mode. The difference is how the peers obtain the key material used to establish the secure channel.

PSK versus dynamic CAK

In PSK mode, the administrator configures the connectivity association key and connectivity association name in a MACsec profile and applies that profile to a port. This is operationally simple but requires secure distribution and rotation of the shared key. In dynamic-CAK mode, a Port Access Entity (PAE) participates in authentication. A port configured as a supplicant requests authentication from the RADIUS server; a port configured as an authenticator enforces the authentication result before the interface is allowed to access the link. The RADIUS server generates the master session key (MSK), and the CAK is derived from that MSK. The same MACsec profile can be used for both PAE roles when the peers are configured consistently.

After the CAK/CKN relationship is established, MACsec Key Agreement (MKA) determines the key-server role and distributes a Secure Association Key (SAK). The SAK is the traffic key used to encrypt and authenticate frames. It is distinct from the CAK: the CAK supports the association/key-agreement process; the SAK protects the data plane. FortiSwitchOS 7.6.0 adds a configurable MKA SAK rekey timer from 60 to 1,000,000 seconds; setting it to zero disables timer-based rekey. Rekey behavior should be coordinated with the peer and change window.

Port and profile relationship

Create a MACsec profile, select Dynamic CAK or PSK, choose the cipher suite and traffic confidentiality settings, then bind that profile to a physical switch port. The port must use security mode macsec. For PSK mode the PAE mode is none; for dynamic CAK choose supp or auth according to the role. The FortiSwitchOS 8.0.0 release notes identify MACsec support on specific 108F/112F/216F and 624F/648F model families; the FSR 108F/112F/216F models listed for the new feature support only GCM-AES-128. Check the platform matrix rather than assuming every FortiSwitch supports the same cipher or key mode.

Traffic policy and overhead

By default, all traffic is encrypted. FortiSwitchOS allows selected protocols to be excluded from the MACsec traffic policy, including ARP, 802.1Q VLAN, FortiLink, IPv4/IPv6, LACP, LLDP, QinQ and STP. Excluding a control protocol changes the protection boundary; do so only when the design requires it and document the consequence. Confidentiality offset can leave the first 0, 30 or 50 bytes unencrypted while still protecting the remainder according to the selected mode. XPN cipher suites require a zero-byte offset. MACsec adds frame overhead, so validate effective MTU and throughput on the actual path.

Verification and troubleshooting

  • Confirm the model and FortiSwitchOS build support the chosen MACsec mode and cipher.
  • Check that both ports agree on PSK/dynamic mode, PAE role, cipher, confidentiality offset and traffic policy.
  • For dynamic CAK, verify the RADIUS exchange and authentication result before investigating SAK rekey. A failed RADIUS authentication prevents the PAE from establishing the secure association.
  • Verify MKA peer/secure-channel state and MACsec protected/unprotected frame counters. A successful RADIUS Access-Accept proves authentication, not that MKA has installed a usable SAK.
  • Change active profiles only after taking the port out of service; the Fortinet guide warns that the port should be shut before applying profile changes.

Use a controlled two-switch lab first. Confirm ordinary L2 reachability, then enable MACsec and compare counters at both ends. If the link comes up but applications fail, inspect excluded control protocols, MTU, VLAN tagging and whether both peers are encrypting the same traffic. This separates key establishment from post-encryption forwarding.

05 / 12 · FortiAP/Wireless · 515 focused words

LoRaWAN gateway profiles on FortiAP: separate CUPS provisioning from TC/LNS traffic

Purpose. Supported FortiAP models can act as both Wi-Fi access points and LoRaWAN gateways. This lets an AP receive low-power sensor traffic and forward it to a LoRaWAN network service without requiring a separate dedicated gateway at every location. The feature is not a generic “turn on LoRaWAN” switch: the gateway protocol, configuration/update server and traffic-controller endpoint are separate settings, and the resulting profile must be attached to the managed FortiAP profile.

Two LoRaWAN protocol modes

FortiAP supports Basics Station and UDP Packet Forwarder modes. Basics Station uses a Configuration and Update Server (CUPS) for gateway configuration, certificates and firmware updates, and a Traffic Controller (TC) endpoint for LoRaWAN data communication. Packet Forwarder mode uses the UDP packet-forwarder protocol toward the configured network server. The selected lw-protocol determines which gateway behavior the AP uses. Do not troubleshoot a Basics Station CUPS registration as if it were a UDP packet-forwarder path.

The LoRaWAN profile is a FortiGate-managed object under config wireless-controller lw-profile. The profile can include a CUPS server, port and API key, plus a TC/LNS server, port and API key. Fortinet documents IPv4, IPv6 and FQDN formats for the server addresses. The CUPS endpoint is a control/provisioning relationship; the TC/LNS endpoint is the data exchange relationship. A successful CUPS registration does not prove that sensor payloads are reaching the LNS.

Configuration sequence

config wireless-controller lw-profile
    edit "campus-lorawan"
        set lw-protocol basics-station
        set cups-server "cups.example.net"
        set cups-server-port 443
        set cups-api-key <protected-key>
        set tc-server "lns.example.net"
        set tc-server-port 443
        set tc-api-key <protected-key>
    next
end

config wireless-controller wtp-profile
    edit "FAP-gateway-profile"
        set lw-profile "campus-lorawan"
    next
end

The sample values are placeholders; use the actual provider's endpoint, port and API credentials. After creating the LoRaWAN profile, bind it to the correct WTP profile. The FortiGate then pushes the profile to the AP. If the WTP profile is not assigned to the intended AP, the global object can look correct while the physical gateway never receives it.

Verify on the AP

Fortinet documents the AP-side command cw_diag -c lw-config. The output includes gateway EUI values, CUPS server/port and TC server/port. This is useful because it proves the AP has received a specific configuration. It does not prove that the CUPS handshake succeeded, that the API key is valid, or that LoRaWAN packets are being forwarded. Continue with server-side registration state and LNS traffic counters.

Fault isolation

  • No LoRaWAN configuration on AP: check model support, FortiAP firmware and the lw-profile reference in the WTP profile.
  • CUPS fields present but no registration: validate DNS resolution, TCP reachability, port and CUPS API key. CUPS is responsible for configuration/certificate/update exchange.
  • CUPS works but no sensor traffic: validate TC/LNS address, port, API key and selected protocol. The traffic-controller side is a separate transaction.
  • Wrong protocol: confirm Basics Station versus UDP Packet Forwarder with the network server provider. The server expects a specific gateway protocol.

Protect API keys as credentials and restrict their administrative visibility. Treat the AP as a dual-purpose device: Wi-Fi client service and LoRaWAN gateway operations have separate service dependencies. Monitor both independently so a healthy WLAN does not mask a failed sensor-data path.

06 / 12 · FortiNAC · 652 focused words

Role assignment precedence: resolving conflicting user, host, group and profiler roles

Why role precedence matters. FortiNAC roles are not just labels attached to users. Roles can be assigned to users, hosts, network devices and ports, and the effective role can influence which network access policy, VLAN or device configuration is applied. In a live environment, more than one source may try to assign a role to the same entity: directory attributes, directory groups, a captive portal, manual registration, device profiling or inherited user identity. FortiNAC resolves conflicts using a defined precedence order.

Ranked matching

The Roles view contains the role names and their rank. When multiple methods match, FortiNAC uses the first matching role in the ordered list. Low-numbered ranks have higher precedence. A host that already has a role from group membership can change when it is added to a second group associated with a higher-ranked role. This is not a random overwrite; it is the result of role ranking. Roles created on an individual FortiNAC server rank above global roles created on FortiNAC Manager. Local roles can be moved relative to other local roles, but cannot be ranked below a global role from the manager.

FortiNAC documents a hierarchy for host role assignment: directory attributes have the highest precedence; group membership is the middle tier; portal-page role assignment has the lowest precedence. Directory attribute data is retrieved directly from the directory when the user registers, whereas group membership is retrieved from data cached on the FortiNAC server. Fortinet therefore recommends directory attributes where possible when freshness matters. A stale cached group can produce a role that appears inconsistent with the current directory membership.

User-to-host inheritance is conditional

If the user's role field is populated from a directory attribute and the host's role field is blank, the host can inherit the user's role. A host may also have its own role. In the documented use case, a student user has two registered hosts: one host inherits Student, while another is explicitly Gaming. When the directory changes the user to Faculty, the inherited host follows the user to Faculty, but the Gaming host remains Gaming because it did not match the original inherited role. This distinction prevents a user role change from indiscriminately overwriting a host-specific classification.

Captive portal registration adds another decision point. If the portal's Role field is populated, the host receives that role. If it is blank, the host inherits the user's role. Hosts assigned by a device profiler are matched using device characteristics and can receive a device type and role; FortiNAC documents that profiler-assigned roles take precedence over vendor OUI-derived roles.

Removal is not always reversal

A critical operational caveat is that removing a host from a group does not necessarily reset the host role. The role can remain until an administrator changes it manually. Similarly, a directory group change may not immediately appear if the local group cache has not synchronized. Do not assume that removing the source of a role automatically restores a default role.

Verification workflow

  • Inspect the effective role on both the user and host records.
  • Review the Roles view order and determine which role is the first match.
  • Check directory attributes and group membership separately; do not assume the two sources are equally fresh.
  • Check whether the portal role field was explicitly populated or left blank.
  • For a device-profiled host, inspect the matching profiling rule and device type; for Inventory-managed network devices, confirm the corresponding Network Device Role mapping exists.
  • After removing a host from a group, explicitly verify the role and manually correct it if the documented behavior leaves the old role in place.

Roles for users and hosts in Host View are generally consumed by network access policies. Roles for devices or hosts in Inventory require a corresponding Network Device Role to apply VLAN or CLI configuration. A correct role name alone is not proof that a switch port has been reconfigured; verify the role mapping and the actual network-device action.

07 / 12 · FortiNAC-F · 623 focused words

Secure Boot and file integrity verification in FortiNAC-F 7.6.3

Security objective. FortiNAC-F 7.6.3 adds a trust chain for platform software and boot-critical files. The feature is intended to detect unauthorized modification and ensure that installed software is authentic. It combines signed General Availability (GA) firmware with file-integrity verification at boot and runtime. This is a platform integrity control, not an endpoint compliance scan and not the same thing as validating a user's credentials.

Image trust and file trust are separate checks

GA firmware images are cryptographically signed with both Fortinet and an external-authority signature. During an upgrade, the system verifies the image signature before installing it. A system already running a signed build blocks unsigned upgrades by default, which prevents an unsigned image from silently replacing a trusted build. Separately, a defined set of boot-critical files is hashed and verified during boot and at runtime. Image signature verification establishes the provenance of the firmware package; file-integrity verification checks that the protected files on the installed system still match their expected values.

These checks have different failure signatures. An unsigned or untrusted upgrade image can be rejected before installation with an image-signature validation error. A runtime file-integrity mismatch is a problem with the installed system's protected files, not necessarily the firmware package being uploaded. Do not treat a failed image signature as evidence that a runtime file has been modified, or vice versa.

Upgrade and downgrade behavior

Once a system is running a signed build, unsigned upgrade images are blocked by default. Fortinet documents that downgrade to a pre-7.6.3 unsigned build remains possible with user confirmation. This is a controlled transition rather than a permanent lock-in. It is important during maintenance planning: a downgrade can move the system back to a software trust model that does not provide the same signed-image enforcement. Record the reason, source image and approval before using that path.

Fortinet also states that the integrity checks and signature verification are self-contained and function in air-gapped environments. The appliance does not need Internet access at every boot to validate the already-installed trust material. This matters for isolated OT networks: lack of Internet reachability is not, by itself, a reason for the local signature check to fail.

Interim builds and the bypass risk

A Fortinet Community upgrade tip describes the expected rejection of unsigned interim builds on FortiNAC-F 7.6 and later. It shows an “Image verification failed” message followed by installation abort. The same older tip documents a --prechecked path for controlled interim testing. That option bypasses the normal signature validation guard and must not become a routine production upgrade method. Use an interim image only when Fortinet Support has explicitly supplied it for a controlled test and the risk has been accepted. The official 7.6.3 release notes remain the primary source for the signed-firmware behavior.

Operational verification

  • Record the current FortiNAC-F version and whether it is a signed GA build before planning an upgrade.
  • Obtain the image from the supported Fortinet distribution path and validate its provenance/checksum before staging it.
  • Capture the full installer output. A signature rejection is an image-trust failure and should be resolved by using a valid signed image, not by disabling integrity controls.
  • After boot, confirm that the system starts normally and review integrity-related messages for the boot/runtime file checks.
  • For an air-gapped deployment, retain the signed image, release notes and provenance records locally; external connectivity is not a prerequisite for the on-device verification.

Do not invent a recovery command from the boot-selection CLI. The release notes describe the feature behavior; any recovery or interim-install procedure must match the exact release and be approved by Fortinet Support. In an HA deployment, plan each node's upgrade sequence and failover state separately, and verify that both nodes return to a trusted signed build before declaring the maintenance complete.

08 / 12 · FortiAuthenticator · 658 focused words

One-time private-key delivery: deleting a user certificate key after PKCS#12 download

Purpose. FortiAuthenticator can generate user certificates and private keys, then export a PKCS#12 package for delivery to an endpoint. The private-key lifecycle policy controls whether the server retains the generated user private key after that package has been downloaded. The option is named Delete user certificate's private key once downloaded, is located under Certificate Management → Policies → General, and is enabled by default.

What the control actually deletes

When enabled, the private keys generated by FortiAuthenticator for user certificates are deleted after they are downloaded for distribution to the endpoint. The setting affects the Users tab's Export Key Cert action under Certificate Management → End Entities. It is intended for deployment models where the endpoint receives its key once and the server does not need to offer the same private key for later re-download. This reduces the period during which a server-side copy of the user's private key remains available.

The sequence is: create or enroll a user certificate; FortiAuthenticator generates or associates the private key; an administrator exports the PKCS#12 package; the endpoint receives the package; and the server-side private key is deleted if the policy is enabled. The certificate object and its status are separate from the private key material. Deleting the private key from FortiAuthenticator does not revoke the certificate and does not erase copies that have already been downloaded to endpoints, backups or secure enrollment systems.

Choose the setting based on the key-delivery model

For a one-time delivery model, keeping the default enabled is a sound security posture. It avoids retaining a second copy of a key after the endpoint has received it. For an operational model that requires re-export—for example, a controlled staged deployment where the same key must be delivered to a replacement device—the administrator must deliberately plan for retention or use a new enrollment/reissue process. Do not disable deletion merely to make re-download convenient; retaining private keys increases the impact of a compromised administrator account or server backup.

Before rollout, define who is allowed to export the PKCS#12 package, where it is staged, how it is transported, and how the endpoint confirms successful import. Protect the package as a credential: it contains private-key material and may also be password-protected. The policy only controls the server's generated private-key copy; it cannot protect a package left in a shared file system or copied to an unmanaged workstation.

Verification and failure analysis

  • Check the global policy under Certificate Management → Policies → General and confirm the deletion setting.
  • Open the relevant user certificate under End Entities → Users and verify that the certificate is active, pending, expired or revoked as expected.
  • Use Export Key Cert in a controlled test. With deletion enabled, the generated user private key is removed after the download; a second export should not be treated as a supported recovery mechanism.
  • Verify the endpoint import independently. A successful browser download proves transfer, not that the endpoint imported the certificate and private key into the correct store.
  • When a user loses the endpoint key, assess whether the certificate should be revoked and reissued. Reissuing creates a new key pair; it does not restore the deleted private key.

Certificate status versus key custody

Keep three operations distinct: private-key deletion is a server-side key-custody action; certificate revocation changes whether relying parties should trust the certificate; certificate deletion removes or archives the certificate object. These are not interchangeable. A certificate can remain active after its private key has been deleted from FortiAuthenticator because the endpoint already holds the key. Conversely, revoking a certificate does not delete copies of its private key. Build lifecycle procedures around both the server-side policy and the endpoint's certificate state.

This control is especially important for EAP-TLS and other certificate-based authentication deployments. The authentication service needs the public certificate chain and a valid endpoint private key, but the CA does not need to retain every endpoint's private key indefinitely. Validate the actual enrollment workflow before changing the default policy.

09 / 12 · FortiPAM · 636 focused words

One secret, multiple approved hosts: Multiple Target Address templates and destination allowlists

Use case. Operations teams sometimes need the same privileged account to reach a controlled set of servers—for example, a service account used across a small cluster—without creating a separate secret for every host. FortiPAM 1.9.0 adds a Multiple Target Address field type to secret templates. It allows one secret to be associated with multiple approved destinations while preserving a destination allowlist at the target object.

Template, target and secret are separate objects

The template defines which fields a secret or target can contain. The target represents the destination resource and its connection properties. The secret contains the credential and is linked to a target. The new Multiple Target Address field type replaces the standard Service Address field type; it is not intended to coexist with the ordinary Target Address or URL field. The allowlist supports individual IP addresses, IP ranges, CIDR networks, FQDNs and wildcard FQDNs. When the user launches a session, FortiPAM presents the approved destinations and the user selects the intended host.

This changes the relationship from one secret → one fixed service address to one secret → one target object → a constrained set of destinations. The credential remains the same, but the destination is selected at launch time. This is useful for controlled groups of equivalent servers, but it also increases the importance of a narrow allowlist: a wildcard that spans an entire domain may expose more destinations than the operational use case requires.

Configuration sequence

  1. Use FortiPAM 1.9.0 or later. The feature is not available as a general multi-address capability on earlier releases; older versions supported multiple addresses only for OT launchers.
  2. Under Secret Settings → Templates, create or edit a template and choose the Multiple Target Address field type instead of the standard Service Address field.
  3. Create a target using that template and populate only the IP addresses, ranges, CIDRs, FQDNs or wildcard FQDNs that are approved for the credential.
  4. Create or edit the secret and associate it with the target. Apply the normal user/group permissions, approval requirements and launcher permissions.
  5. Launch a supported session and verify that the user can choose an approved destination. Test a destination outside the allowlist and confirm that it is not offered or accepted.

Security and operational implications

The feature reduces secret duplication, but it does not remove the need for least privilege. If a credential is valid on five servers, the allowlist should contain those five destinations or the narrowest equivalent network/FQDN patterns. Avoid broad wildcards such as *.example.com unless every matching host is genuinely in scope. Review DNS changes because an FQDN allowlist can resolve to a different address over time. For IP ranges and CIDRs, confirm that the network boundary does not include management interfaces or unrelated systems.

The Multiple Target Address field is a destination selector, not a new authentication method. The target still needs a compatible launcher/protocol and network reachability from the FortiPAM session path. The selected destination must match the service's protocol and port; a valid credential does not prove the target is reachable or that the launcher supports the selected address format.

Verification

  • Inspect the secret template and confirm that Multiple Target Address is used instead of Target Address/URL.
  • Review the target's allowlist entries and resolve FQDN/wildcard entries from the relevant FortiPAM network context.
  • Check the launcher's destination picker and session audit record to confirm which host was selected.
  • Test both a permitted and an unlisted destination. The negative test is important: it proves the allowlist is actually constraining the launch, not merely populating a UI list.
  • When a launch fails, separate template-field mismatch, destination resolution, route/firewall reachability, service/port mismatch and credential failure.

Use this feature to consolidate secrets only when the same credential is intentionally authorized across the listed hosts. Do not use it to make a broad shared password convenient for an entire server estate.

10 / 12 · FortiSIEM · 549 focused words

Headless Windows Agent 7.5: direct Collector ingestion for restricted OT endpoints

Why a headless agent exists. The standard FortiSIEM Windows Agent registers with the Supervisor and is centrally managed. That model can be awkward in an OT or restricted network where endpoints cannot communicate with the Supervisor or where local agent administration is preferred. Windows Agent 7.5.0 introduced a Headless Agent that is configured locally and does not register to the Supervisor. It sends supported event data to a Collector instead.

Architecture and licensing

The headless deployment points the agent at the Collector IP/hostname and Collector port, not the Supervisor. The minimum FortiSIEM architecture still includes a Supervisor and at least one Collector. The Collector receives the agent data and forwards it into the FortiSIEM event-processing path. The headless agent does not require an Agent license, but it consumes a device license, and the generated events count toward the GB/day or EPS license. This is a licensing distinction, not a free collection path.

The supported source set is deliberately limited: Windows Security logs and user-defined log files. Do not assume that a headless agent can run every monitor template feature available to a fully registered agent. The Windows Agent guide states that only EventLog and user-defined log-file settings are permitted in the exported configuration. Beginning with Agent 3.0, agents upload event data to a Collector; the Collector must be IPv4-only, and TLS 1.2 must be enabled for agent communication with FortiSIEM nodes. A dual-stack or IPv6-only Collector is not supported for this agent path.

Provisioning and configuration

First create a Collector-side HTTP authentication account using the documented htpasswd mechanism. The username has a restricted character set; the password must be 8–64 characters and include a letter, number and special character. Install the Windows Agent with the Headless deployment type and the Collector address/port. For command-line installation, the documented parameter is DEPLOYMENT_TYPE="Headless"; the SUPERNAME/SUPERPORT values must identify the Collector, not the Supervisor.

FSMLogAgent.exe SUPERNAME=<Collector-IP>   SUPERPORT=443 ORGNAME=<Org-Name> ORGID=<Org-ID>   AGENTUSER=<Collector-User> AGENTPASSWORD=<Password>   UNPROTECT=1 DEPLOYMENT_TYPE="Headless"

After installation, export a Windows Agent monitor template from Admin → Setup → Windows Agent. Include only EventLog and user-defined file sources. Copy the exported JSON file to C:\Program Files\Fortinet\FortiSIEM\config and name it fsm_agent_config.json. The agent begins collecting according to that local configuration. This avoids Supervisor registration, but it also means template changes are not centrally pushed through the ordinary registered-agent workflow.

Verification and troubleshooting

  • Confirm the installed agent is configured with the Collector address and port. A headless agent pointed at the Supervisor is a common architecture mistake.
  • Verify TLS 1.2 on the Windows host and Collector reachability over the configured port.
  • Check Collector-side HTTP authentication and the configured htpasswd identity. A wrong username/password prevents upload even if the TCP connection is open.
  • Inspect the local agent logs and Collector receive logs, then verify events appear in FortiSIEM. A running Windows service proves process health, not successful ingestion.
  • Check the exported JSON template for unsupported sources. If a source is not EventLog or user-defined file collection, it is outside the documented headless feature set.

Use headless mode where the Supervisor-registration path is intentionally unavailable, not as a generic replacement for registered agents. Document local template ownership, credential rotation, Collector placement, IPv4-only constraints and the device/EPS licensing impact. This makes the endpoint's data path auditable even when the agent is not visible as a Supervisor-managed object.

11 / 12 · FortiSASE · 642 focused words

Agentless ZTNA: proxy SSO bookmark portal and SPA access to private HTTPS applications

Use case. Agentless ZTNA provides browser-based access to a private web application without requiring the remote endpoint to run a FortiClient agent or be configured as a proxy user. The user authenticates to a bookmark portal through proxy single sign-on (SSO), then opens a private-application bookmark. FortiSASE proxies the request through its Security PoP and secure private access (SPA) hub to the HTTPS application behind a FortiGate.

Prerequisites and transaction flow

Fortinet documents several prerequisites: an Advanced or Comprehensive remote-user subscription; proxy and proxy-user SSO configured in FortiSASE; an SPA hub on a licensed FortiGate using BGP per overlay or BGP on loopback; and a private web application that supports HTTPS and resides behind the FortiGate. The administrator configures user groups, a Private Access security profile group, the SPA hub, the private application, geofencing and the bookmark portal. Users reach the portal only after authenticating with the configured proxy SSO provider.

Proxy and proxy SSO are configuration dependencies, but the remote endpoint does not need a proxy PAC file or the deep-inspection CA certificate simply to use the agentless bookmark. The agentless ZTNA request uses the proxy SSO identity configuration for authentication and then accesses the private application through SPA. Fortinet explicitly notes that agentless ZTNA traffic is proxied directly to the private application, bypassing the normal Secure Internet Access tunnel or proxy flow. This is a key distinction: it is not just a different URL for an ordinary SIA session.

Access control and routing details

The private application is defined in Security → Traffic → ZTNA → Agentless → Private applications. The bookmark portal provides the user-facing entry point. The SPA hub must have routes to the application and its DNS server, and the FortiGate policy must permit traffic from the FortiSASE Security PoP. If the application is configured by FQDN, the corresponding DNS rule must use Access Type Private when the server is reached behind an SPA hub. If the FortiGate hub restricts source addresses, include the shared public IP address used by the originating Security PoP; do not assume the user's home address is the source seen by the private application.

Proxy users and agent users cannot access the agentless ZTNA private-application bookmarks. This prevents a normal agent/proxy session from being treated as an agentless bookmark session. Use the correct access model for each endpoint. A user who has a valid agent connection should normally use Secure Private Access through the agent rather than attempting to reach the agentless bookmark in the same session.

Authentication caveats

Proxy SSO has its own inspection requirements. FortiSASE release notes state that at least one proxy policy using SSO authentication must use deep inspection in its security profile group; SSO authentication does not work in a policy using certificate inspection only. Other authentication methods may not be available after SAML SSO is enabled. These are proxy-SSO prerequisites, not a requirement to install a proxy CA on the agentless endpoint.

Verification

  • Authenticate to the bookmark portal and verify that the expected user identity/group is recognized.
  • Check that the private application is HTTPS and the bookmark points to the correct host/path.
  • Verify SPA BGP routes and FortiGate policy logs from the Security PoP toward the application.
  • For FQDN applications, verify private DNS resolution and Access Type. A correct bookmark does not prove that the DNS server is reachable through SPA.
  • Test a user who is not an agent/proxy user and compare with an endpoint that has an active agent/proxy session; the documented session separation should be visible.

A Community support discussion from January 2026 describes an agentless bookmark portal that worked only when the ZTNA agent was connected. It is an older scenario, but it reinforces the need to separate agentless and agent-based session paths. When troubleshooting, isolate proxy SSO, bookmark authorization, PoP-to-hub routing, DNS and application reachability instead of changing all layers at once.

12 / 12 · Secure SD-WAN · 594 focused words

Per-packet distribution across aggregate static IPsec tunnels

Design objective. FortiOS can aggregate multiple static IPsec tunnel interfaces and distribute packets across the aggregate. A typical design has two Internet providers at each site, with one static IPsec tunnel over each underlay. The two tunnel interfaces are configured as aggregate members, an ipsec-aggregate interface represents the combined tunnel set, and that logical interface is added as an SD-WAN member. This is different from creating two independent SD-WAN members and letting an SLA rule choose a path for each session.

Building the tunnel members

On each FortiGate, create a Phase 1 interface for each underlay. The Fortinet example uses static remote gateways, disables the per-tunnel net-device, and enables aggregate membership. The crypto proposal, DH group, peer address and authentication must match the remote side. The two peers need a compatible aggregate definition and matching member relationships. Validate each underlying ISP path and each IPsec SA before adding the aggregate to SD-WAN; otherwise a failure in one layer can be mistaken for an aggregate failure.

config vpn ipsec phase1-interface
    edit "branch-wan1"
        set interface "wan1"
        set peertype any
        set net-device disable
        set aggregate-member enable
        set proposal aes256-sha256
        set dhgrp 14
        set remote-gw 198.51.100.10
        set psksecret <protected-secret>
    next
    edit "branch-wan2"
        set interface "wan2"
        set peertype any
        set net-device disable
        set aggregate-member enable
        set proposal aes256-sha256
        set dhgrp 14
        set remote-gw 203.0.113.10
        set psksecret <protected-secret>
    next
end

Create the aggregate interface using the member tunnels, then add the aggregate interface—not each individual tunnel—to the SD-WAN member list. The Fortinet example shows the aggregate as a single SD-WAN member with its gateway configured. Routing and policy must direct the desired traffic through that logical member.

What per-packet distribution means

The feature distributes packets across the aggregate's static IPsec members. It is not the same as ordinary session-based SD-WAN selection, where a flow is generally associated with a selected member. Per-packet distribution can use both underlays for a single traffic stream, but packets may experience different delay and arrive out of order. Applications and TCP stacks normally tolerate some reordering, but large path-delay differences can cause duplicate acknowledgements, retransmissions or throughput collapse. Measure path latency and loss before assuming that adding a second circuit doubles application throughput.

Verification

Fortinet documents diagnose sys ipsec-aggregate list to display aggregate members and the aggregate algorithm. The example output includes the aggregate name, algorithm, member count and run tally. Use diagnose vpn tunnel list to inspect each Phase 1/SA state and its packet counters. Then check the aggregate interface and SD-WAN member status, and compare per-member traffic counters during a controlled test. An aggregate showing two configured members does not prove that both SAs are established or carrying traffic.

Failure isolation

  • If one tunnel is down, test the underlying WAN interface, route to the peer, remote gateway, proposal, authentication and DPD independently.
  • If both SAs are up but only one member carries traffic, verify aggregate membership and that the logical aggregate—not a single tunnel—is used by the SD-WAN service and routing policy.
  • If throughput is poor despite balanced counters, measure per-underlay delay, loss, MTU and packet reordering. A fast path and a slow path can make per-packet distribution worse for latency-sensitive traffic.
  • If packets disappear after encryption, verify remote aggregate symmetry, route return path, firewall policy and MTU/fragmentation behavior.

Use this design when the objective is packet-level utilization across parallel static IPsec paths and the application can tolerate the resulting path variance. Use ordinary SD-WAN SLA-based session steering when the desired behavior is to keep each session on a selected healthy path. The two models solve different problems and should not be conflated.
