FortiGate

DNS over QUIC and DNS over HTTP/3: transparent proxy versus local-in DNS service

DoQ/DoH3 inspection, local-in DNS and transparent proxy modes

Primary feature / administration documentation

  • FortiOS 8.0 — DNS over QUIC and DNS over HTTP/3
  • FortiOS 8.0 — FortiGate DNS server
  • FortiOS 8.0 CLI — config system dns-server

Community / scenario material

  • Historical Community Tip — DNS over HTTPS/443 (not a recent DoQ/DoH3 scenario)

Purpose and two operating modes

DNS over QUIC (DoQ) and DNS over HTTP/3 (DoH3) carry DNS queries over QUIC rather than classic UDP/TCP DNS. FortiOS 8.0 documents them in two placements. In transparent mode, FortiGate acts as a proxy that forwards a client's DNS query to an upstream resolver. In local-in DNS mode, FortiGate itself is the DNS server on an interface, applies the DNS filter profile configured on that service, and resolves or forwards according to its DNS mode. The distinction is operational: a transparent proxy does not become the authoritative source of the answer, while a local-in DNS service can answer from its local DNS database or forward the miss.

DoQ uses QUIC on UDP/853. DoH3 carries DNS over HTTP/3 using QUIC on UDP/443. Do not conflate DoH on HTTP/2/TCP with DoH3. Fortinet states that DoQ and DoH3 are supported in proxy-mode inspection for transparent and local-in modes, and that FortiGate can handle the QUIC/TLS handshake and deep-inspect HTTP/3 and QUIC traffic. A successful QUIC session is only transport establishment; it does not prove the DNS filter, resolver mode or policy is correct.

Packet and policy path

For transparent DNS proxying, the client sends DoQ or DoH3 through a firewall policy. The policy must be in proxy mode. The SSL/SSH inspection profile must inspect QUIC and HTTP/3 protocol mappings, and the DNS filter profile must be applied so the decoded DNS request can be rated. An allowed query is forwarded upstream; a blocked category receives the configured block behavior. This is a content decision on the queried domain, not merely a decision to allow UDP/443 or UDP/853.

For local-in DNS, the packet terminates on a FortiGate interface with DNS service enabled. The service mode controls resolution: recursive checks the shadow DNS database then forwards misses to system DNS; non-recursive answers only from the public DNS database; forward-only bypasses the local database; resolver mode iterates root, TLD and authoritative servers. The DNS filter profile is attached to the system DNS server object. A QUIC handshake therefore proves neither that the right listener received the query nor that the DNS database/filter returned the expected answer.

Configuration pattern

Enable DNS Database under System > Feature Visibility if the DNS server GUI is absent. For transparent inspection, use a proxy-mode firewall policy and an SSL/SSH profile that inspects HTTP/3 and DNS over QUIC. For local-in mode, enable DNS service on the interface, select the DNS mode and bind a DNS filter profile. In FortiOS 8.0 the DNS service certificate is selected with set ssl-cert under config system dns-server; if not set there, FortiGate falls back to the certificate under config web-proxy global. This certificate selection is a release-specific detail worth checking after upgrades.

config firewall ssl-ssh-profile
  edit "dns-quic-inspection"
    config dot
      set status deep-inspection
      set quic inspect
    end
  next
end

config system dns-server
  edit "port2"
    set dnsfilter-profile "dnsfilter_fgd"
    set doq enable
    set doh3 enable
    set ssl-cert "dns-service-cert"
  next
end

The snippet illustrates the documented objects. Confirm listener mode, ports, profile names and certificate chain on the target build. The CLI exposes separate doh, doh3, doq, mode, dnsfilter-profile and ssl-cert controls.

Evidence and interpretation

Test DoQ and DoH3 separately. Fortinet documents use of the q client for DoQ and DoH3, and curl for DoH3. Use a known FortiGuard category-30 domain when validating a block action: the expected default redirect block IP demonstrates that the DNS filter decision was applied, not just that a socket connected. Compare an allowed domain with a blocked domain and repeat against the transparent proxy and local-in listener if both are deployed.

Verify the DNS service interface, mode, DNS filter profile, doq/doh3 state and certificate selection. In the SSL/SSH profile, verify HTTP/3 and DNS over QUIC are set to Inspect. A packet capture can prove QUIC endpoint and UDP port; it cannot prove the category action or local DNS view. If the returned address is unexpected, determine whether it came from a shadow record, public record, upstream recursion, forward-only mode or a filter replacement response.

Failure isolation and limits

If UDP/53 works but DoQ fails, check UDP/853 reachability and the DoQ listener/inspection setting. If DoQ works but DoH3 fails, check UDP/443, HTTP/3 protocol mapping and whether the client fell back to HTTP/2 DoH. If encrypted DNS succeeds but filtering does not, check proxy inspection mode and DNS filter binding before changing category lists. A certificate warning points toward the DNS service certificate, SAN/chain or client trust, not necessarily the upstream resolver.

Keep transparent and local-in modes separate in the change plan: one is a transit proxy requiring the correct policy; the other exposes a DNS service on the FortiGate interface. Confirm the FortiOS 8.0 certificate fallback behavior and listener-port design. Troubleshoot in order: transport, QUIC/HTTP3 decode, DNS filter decision, then local/upstream resolution. This prevents an engineer from treating a successful QUIC handshake as proof that DNS security policy is working.

FortiManager

FortiManager 8.0 Workflow Mode: concurrent sessions, selective approvals and install boundary

Concurrent workflow sessions, approval quorum and separate device installation

Primary feature / administration documentation

  • FortiManager 8.0 — Workflow mode
  • FortiManager 8.0 New Features — selective approvals
  • FortiManager 8.0 — Workspace settings

Community / scenario material

  • Community Technical Tip — package install verification mismatch after target default change (Oct 23, 2026)

Purpose and concurrency models

FortiManager exposes Disable, Workspace and Workflow concurrency modes. Disable is permissive: administrators can change configuration without locking an ADOM or creating a session. Workspace is lock-based; an administrator locks an ADOM, device or policy package so another administrator cannot change the same element. Workflow is a review-and-approval model in which administrators stage changes in sessions and submit them to an approval matrix. FortiManager 8.0 redesigned workflow mode around individual admin sessions and selective approvals. Multiple administrators can create sessions concurrently without locking the entire ADOM first.

Workflow is appropriate when policy/object changes require peer review before entering the shared ADOM database. It is not a deployment engine. An approved session updates the ADOM configuration state; installing that state to FortiGate devices is a separate workflow with its own preview, target validation and result. “Approved” is not synonymous with “installed successfully.”

Session lifecycle and approval semantics

When an administrator enters an ADOM configured for Workflow, the Workflow Session selector initially shows None. The administrator creates a new session or opens an in-progress session. Changes are staged inside that session. It can be saved for later, submitted for approval or discarded. The administrator cannot create another new session while the current one remains active; it must first be saved and closed, submitted or discarded.

On submission, FortiManager evaluates the configured approval groups. The 8.0 new-features guide states that sessions can be approved in any order and are not restricted to submission order. Once one approver from each required group approves, the session changes are implemented in the ADOM. If rejected, the change set can be repaired and resubmitted as a new session or discarded. Concurrent sessions can conflict; FortiManager identifies conflicts so they can be merged or discarded rather than silently overwriting one another.

Review the diff; install separately

View Diff is the key review tool. Inspect policy rules, address/service objects, shared objects, package references and device settings that actually change. A session name or submitter does not explain impact. When two sessions touch related objects, inspect both diffs and conflict information. Approval validates governance of the ADOM change; it does not validate target-device syntax, firmware support or reachability.

The Oct 23 Community scenario is a useful boundary case, not a Workflow defect: a package install failed verification because FortiProxy's default antiphish:max-body-len differed from FortiManager's modeled default. The session may be approved while the install still fails against the target. After approval, check package status, run Install Preview, select the intended devices and inspect install history/results separately.

Configuration pattern

Workspace settings can be enabled globally or per ADOM. Per-ADOM mode allows one ADOM to use Workspace, another Workflow and another Disable. Configure approval groups and notification settings before users start sessions. Confirm user profiles grant the intended modifier and approver permissions; edit permission does not automatically imply approval authority. FortiManager 8.0's redesigned workflow no longer requires the old ADOM-wide lock as the gate for each workflow session.

config system global
  set workspace-mode workflow
end

# GUI: System Settings > ADOMs > Edit ADOM
# Set Workspace Mode to Workflow and define approval groups.

The global mode selector is shown for orientation; the approval matrix is configured in the GUI. Changing workspace mode ends the current FortiManager session and requires a new login, so perform the change in a planned window.

Evidence and failure isolation

Use the session list to confirm creator, state and approval progress. View Diff proves what the session proposes; it does not prove that a device received it. After approval, inspect the ADOM/package status, then Install Preview and install history. If installation fails, read the target verification output and distinguish missing objects, unsupported commands, default-value mismatches and device reachability from approval problems. If sessions conflict, compare object references and package scope before merging.

For a stuck workflow, verify the ADOM is in Workflow mode, the administrator has an open session and every required approval group has an eligible approver. For a rejected session, repair or discard it before expecting downstream changes to proceed. For an approved package that will not install, inspect the target's actual firmware/defaults rather than reopening the approval. The operational sequence is session isolation, diff review, approval quorum, ADOM commit, install preview and device deployment.

FortiAnalyzer

Custom report assembly: datasets, charts, macros, Report Guidance and hcache

Dataset/chart/macro dependencies, Report Guidance and hcache

Primary feature / administration documentation

  • FortiAnalyzer 8.0 — How reports are populated
  • FortiAnalyzer 8.0 — Report Guidance
  • FortiAnalyzer 8.0 — How auto-cache works
  • FortiAnalyzer 8.0 — Creating datasets

Community / scenario material

  • No directly matched recent Community scenario was verified for this selected mechanism. Community searches were retained in the sweep record; unrelated posts were not promoted as lesson evidence.

Report object graph

A FortiAnalyzer report is a composition of reusable objects, not a static query attached directly to a PDF. A dataset defines the SQL query and log database tables from which information is selected. A chart references a dataset and renders rows as a table, bar, pie, line or other visualization. A macro also references a dataset but returns a value such as text, bandwidth, counter, duration or percentage. A report definition combines charts and macros with cover pages, images and explanatory text. At run time, each object contributes output based on the Analytics data available for its device type, log type and time range.

This dependency graph matters when only some sections show No Data. A chart can be valid while its dataset points to the wrong log type; a macro can reference a dataset whose fields are not present in the selected ADOM; a report can render while individual items have no rows. Debugging the PDF alone hides the failed dependency. Trace each item back to its dataset and then to the underlying Analytics log table and fields.

Datasets, charts, macros and ADOM scope

Datasets define data source and query logic. Validate checks SQL syntax; Test executes it for a chosen time period and device scope; Analyze Query displays original SQL, transformed SQL and the hcache query used when auto-cache is enabled. Variables can define expressions that become report filter fields. Charts consume dataset rows and fields; macros extract scalar or formatted values. Changing a dataset can affect multiple charts/macros and every report that references it.

ADOM boundaries are not cosmetic. Each ADOM has its own reports, datasets, charts and macros. A dataset imported into an ADOM must use device types supported by that ADOM. Fabric ADOMs can support reports across device types and datasets that use the SIEM database (siemdb). Before troubleshooting missing output, confirm the current ADOM and its device/log schema. A query that works in a Fabric ADOM may not be valid when imported into a device-specific ADOM.

Report Guidance diagnoses No Data

Report Guidance answers whether Analytics logs required by a chart or macro are available. In Reports > Report Definitions > All Reports, the Config Recommendation icon opens a pane organized by item title, device type and log type. It lists relevant log fields and indicates whether Analytics logs are available. An application-visibility chart may require FortiGate app-control logs and fields such as app and appcat; a threat chart may require attack logs and fields such as attack and severity.

No Data can result from logging not enabled correctly, a report element expecting another device/log type, or no matching records in the selected time window. A license-controlled element may also lack usable data without the required subscription. Report Guidance reports availability of the analytics fields needed by the report item; it does not prove that the device is currently sending every event. Correlate the pane with device logging and recent log receipt.

Auto-cache and hcache

For expensive reports, auto-cache instructs FortiAnalyzer to build hcache. Hcache is persistent, on-disk database-table cache, not a short-lived memory cache. It applies to matured database tables: once a table has rolled and will no longer grow, hcache can run the required SQL query in advance and save intermediate results. At report time, FortiAnalyzer merges cached results rather than recomputing every historical query from raw tables. This can significantly reduce generation time for reports with large datasets.

Auto-cache consumes CPU, disk I/O and storage because cached results must be assembled and retained. Enable it selectively for reports whose datasets are expensive, not for every report. The Cache Status column shows cache build state. Analyze Query can expose the transformed/hcache query, useful when a custom dataset behaves differently after caching. Hcache is a performance optimization; it does not create missing source logs or correct a wrong SQL filter.

Build and troubleshoot a custom report

Start in the correct ADOM, select a known log type and bounded time range, create or clone a dataset, validate SQL and test against representative devices. Then build the chart or macro and verify consumed fields. Add it to a report and use Report Guidance before scheduling. For a slow report, compare uncached generation time, enable auto-cache only for the relevant report and monitor Cache Status/resource use. If the report says No Data, check the item title and required fields before changing the template.

Do not confuse archive presence with analytics availability. A raw log may be visible in Log Browse while the Analytics table required by a chart is not indexed or is outside the selected range. A successful SQL test on one device does not prove every device type supplies the same fields. The engineer should be able to explain which dataset feeds each chart, what fields it needs, which ADOM owns the objects and whether hcache is accelerating a query or masking a design problem.

FortiSwitch

Private VLANs: isolated and community sub-VLAN forwarding within one IP subnet

Primary, isolated and community VLAN forwarding matrix

Primary feature / administration documentation

  • FortiSwitchOS 8.0 — Private VLANs

Community / scenario material

  • No directly matched recent Community scenario was verified for this selected mechanism. Community searches were retained in the sweep record; unrelated posts were not promoted as lesson evidence.

Purpose and primary/secondary structure

A Private VLAN divides one primary VLAN into secondary sub-VLANs while retaining the original IP subnet and Layer-3 gateway. It is useful when a shared subnet must remain operational as one IP network but endpoints must not all communicate at Layer 2. Examples include hotel or campus access ports, tenant-facing networks and shared server segments where hosts need gateway access but not peer access.

The primary VLAN is the common forwarding domain. Secondary VLANs are isolated or community. The primary VLAN forwards frames downstream to secondary VLANs, but the secondary type controls which host ports may exchange frames. PVLAN is not the same as creating multiple independent VLANs with separate subnets, and it is not simply a firewall ACL. The forwarding decision is made inside the switch's Layer-2 PVLAN relationship.

Forwarding matrix

A promiscuous port (P-port) normally connects to the router, firewall or shared gateway. It can communicate with any port in the primary or secondary VLANs. An isolated port (I-port) connects to a host in the isolated secondary VLAN. It can communicate with P-ports but not with other secondary VLANs; hosts on the same isolated VLAN cannot reach one another. A community port (C-port) connects to a host in a community secondary VLAN. It can communicate with P-ports and other ports in the same community VLAN, but not with another community or isolated VLAN.

Only one isolated VLAN is allowed in a PVLAN domain, while multiple community VLANs can exist. Think of P-port as the shared gateway/service path, I-ports as mutually isolated subscribers, and each C-port group as a small peer group. IP address and gateway can remain unchanged across these port classes because the switch applies restrictions beneath Layer 3. An endpoint can reach its gateway yet fail to reach another endpoint in the same IP prefix.

Configuration pattern

Create the primary PVLAN and define isolated/community secondary VLAN identifiers. Then configure each switch interface with its role and VLAN relationship. The FortiSwitchOS guide shows primary VLAN 1000, isolated VLAN 101 and community VLANs 200 through 210. The gateway-facing port is promiscuous; host-facing ports are sub-VLAN ports with primary and secondary IDs.

config switch vlan
  edit 1000
    set private-vlan enable
    set isolated-vlan 101
    set community-vlans 200-210
  next
end

config switch interface
  edit "port2"
    set private-vlan promiscuous
    set primary-vlan 1000
  next
  edit "port3"
    set private-vlan sub-vlan
    set primary-vlan 1000
    set sub-vlan 101
  next
  edit "port7"
    set private-vlan sub-vlan
    set primary-vlan 1000
    set sub-vlan 200
  next
end

Use the target model/release syntax and ensure each host port's primary and secondary IDs correspond to the configured PVLAN. The upstream gateway must be connected through a promiscuous port.

Verify the matrix, not just VLAN presence

Test from an isolated host to the gateway, a second isolated host and a community host. Expected: gateway reachability, peer isolation and cross-community isolation. From a community host, test the gateway, a peer in the same community and a host in another community. Expected: gateway and same-community reachability, with cross-community isolation. From the P-port, confirm communication with every secondary segment. Capture ARP and unicast traffic if needed; an IP ping can be misleading because host firewalls or missing ARP can resemble PVLAN filtering.

Inspect PVLAN state and port roles before changing ACLs or routing. A DHCP lease proves the host obtained Layer-3 parameters, not that the correct secondary VLAN was assigned. A gateway ping proves the P-port path works, not the intended peer-isolation matrix. If same-community hosts cannot communicate, check whether they were assigned different community VLAN IDs or one port was configured as isolated.

Dependencies and cautions

PVLAN support is model- and release-dependent, so confirm the FortiSwitch feature matrix. Maintain a VLAN-to-role inventory and avoid reusing secondary IDs outside the intended domain. When moving a port between host classes, re-test the matrix because the endpoint may keep its IP address while its Layer-2 peer reachability changes. Keep gateway/shared-service ports promiscuous only when they genuinely need access to all secondary segments.

PVLAN provides intra-subnet Layer-2 segmentation. If the requirement is to restrict a routed application, use FortiGate policy or routed ACLs as well; PVLAN does not replace Layer-3 authorization. Conversely, a firewall policy may never see traffic switched locally between ports, so a routed policy cannot enforce peer isolation if the switch forwards those frames within the VLAN. Document both the PVLAN matrix and the routed-policy boundary.

FortiAP/Wireless

FortiAP mesh ZTP: default-mesh bootstrap, Ethernet-first backhaul and leaf authorization

Default-mesh bootstrap, Ethernet-first leaf discovery and authorization

Primary feature / administration documentation

  • FortiAP 8.0 — Configuring a meshed WiFi network with ZTP
  • FortiAP 8.0 — Manually configuring a mesh network
  • FortiAP 8.0 — Creating a FortiAP profile

Community / scenario material

  • Historical Community Tip — mesh link across radios under FortiEdge Cloud (July 27, 2025)

Bootstrap architecture

FortiAP mesh extends controller-managed service to a leaf AP that cannot use wired Ethernet at its final location. A root AP provides a wireless backhaul SSID; the leaf associates and then establishes its management relationship with the FortiGate controller. FortiAP 7.6.3 and later documents zero-touch provisioning (ZTP) for mesh leaves: a default-configured leaf can discover the FortiGate through a default mesh link using predefined settings. This removes the need to log into each leaf and manually enter initial mesh credentials before it can be managed.

The default mesh SSID is a bootstrap mechanism, not the final design. The root can broadcast default-mesh with default settings. The documented security includes WPA3-SAE, protected management frames and SAE H2E-only. Once the leaf connects and FortiGate detects it, an administrator authorizes the AP and can customize the mesh SSID and passphrase at runtime. Treat bootstrap as controlled onboarding, then replace it with deployment-specific credentials and radio settings.

Ethernet-first and leaf discovery

On the documented FortiAP 7.6.3-or-later behavior, MESH_AP_TYPE defaults to 2, meaning Ethernet with mesh backup support is used for controller communication. If Ethernet is unavailable, the AP scans for available mesh-backhaul SSIDs and tries to connect as a leaf. A leaf may therefore prefer Ethernet even when a root is broadcasting. A technician who expects immediate radio association can misdiagnose a correctly operating Ethernet-first AP.

The default MESH_AP_SSID and MESH_AP_PASSWD on the leaf match the FortiGate default mesh settings. The root can be configured through its FortiAP profile or overridden on an individual managed AP. Profile-based configuration scales consistently; a per-device override is useful for a specific root but creates configuration divergence that must be documented.

Configuration pattern

On FortiGate, open WiFi & Switch Controller > FortiAP Profiles, edit the root AP profile and enable Broadcast mesh provisioning SSID under Mesh Setup. The CLI equivalent in the WTP profile is:

config wireless-controller wtp-profile
  edit "FAP432G-default"
    set default-mesh-root enable
  next
end

Power on the leaf. It should discover the default mesh SSID, establish the backhaul, appear as a managed FortiAP candidate and then be authorized. The documentation also supports enabling the setting on an individual AP with override-default-mesh-root enable and default-mesh-root enable under the WTP object. After connection, create a custom mesh SSID, apply it to the root radio and configure the leaf profile to use it. Confirm migration before removing the bootstrap SSID.

Evidence and fault isolation

Separate root broadcast, leaf radio association, controller discovery and administrator authorization. A root profile showing default-mesh-root enable proves intended advertisement; it does not prove the leaf can hear the SSID on a supported radio. A leaf visible in Managed FortiAPs proves controller discovery; it does not prove authorization or that the custom runtime profile was applied. Check model/firmware, root profile assignment, radio band and physical placement before changing credentials.

For cross-radio or weak-link cases, verify the root BSSID and the leaf's selected radio. The older Community mesh tip is historical context for radio selection under FortiEdge Cloud, not the authoritative FortiGate-managed ZTP procedure. Use it as a reminder that radio/BSSID choice matters, not as a substitute for the FortiGate profile workflow.

Operational limits and secure rollout

Mesh throughput is shared with the wireless backhaul, so adding leaf APs can reduce airtime for client traffic. Plan root placement, channel selection, line of sight and hop count before rollout. The ZTP guide documents discovery and authorization, not unlimited multi-hop capacity. Confirm model support, regulatory domain and radio capabilities, and keep the root's wired controller path healthy. A leaf that repeatedly scans but never associates may have a radio/BSSID mismatch, unsupported band, weak signal or bootstrap credential mismatch.

After onboarding, use a unique strong mesh passphrase and deliberate root/leaf profiles. Check that the leaf is operating on the custom SSID rather than remaining on bootstrap. Preserve a wired recovery path where practical. The operational sequence is root broadcast, leaf discovery, backhaul association, controller visibility, authorization, custom-profile push and client-path test. A single green controller icon does not validate every stage.

FortiNAC

Security event parsers: syslog extraction, host correlation, triggers and alarm actions

Syslog parser, IP-to-MAC correlation, trigger and alarm action

Primary feature / administration documentation

  • FortiNAC 9.4 — Security event parsers
  • FortiNAC 9.4 — Security events
  • FortiNAC 9.4 — Security incident implementation

Community / scenario material

  • No directly matched recent Community scenario was verified for this selected mechanism. Community searches were retained in the sweep record; unrelated posts were not promoted as lesson evidence.

Normalize raw syslog

FortiNAC can receive security syslog messages from appliances and convert them into structured security events. A Security Event Parser defines how the raw message is interpreted. Supported formats include CSV, TAG/VALUE and CEF. CSV uses a delimiter such as comma, pipe or space; TAG/VALUE extracts a value associated with a tag; CEF parses standard-position and tagged fields. The parser maps source IP, destination IP, type, subtype, threat ID, description and severity into FortiNAC event fields.

The parser is selected when configuring a pingable device in Topology to accept security events. It can be enabled, disabled, copied, exported and tested, and its In Use view identifies devices using it. Populate from Received Syslog can seed the parser from a real message. That is safer than relying only on a vendor example because firmware versions can change field order, tag names or optional fields. A parser can extract a plausible source address while mapping severity incorrectly, creating an event but driving the wrong response.

Host correlation is a separate stage

After parsing, FortiNAC attempts to identify the host associated with the event. The documented path resolves the source IP in the message to a MAC address in the FortiNAC database through Layer-3 polling. If the IP cannot be resolved yet, the event is held in memory until an associated host can be found. The parser can therefore succeed while host identity remains unknown. An event may arrive before inventory or L3 polling state is complete.

Once associated, the event appears under Logs > Security Incidents > Events with source IP/MAC, destination IP, type, subtype, severity, threat ID, description and location. The event view is evidence storage, not enforcement. FortiNAC reviews security rules for each event. When an event satisfies a trigger and the associated host/user/location profile matches, an alarm is created. The alarm can then execute a configured response such as notification, host disablement or isolation.

Triggers, profiles and rule precedence

The event, trigger and security rule/alarm are separate objects. The event is the normalized fact extracted from syslog. The trigger is the condition over fields such as source IP, threat type, subtype, severity or description. The rule associates that trigger with a host, user or location profile and defines the response. A matching event alone does not prove the full rule matched; host correlation may fail, the profile may not match or a required field may be absent from the parser.

FortiNAC's implementation guide states that a rule with a satisfied trigger and matching User/Host profile creates an alarm. When multiple rules match, the higher-ranked rule's action takes precedence. A lower-ranked action is not automatically implemented, although it may be invoked manually; a higher-ranked rule can override a lower-ranked action previously applied. Rule order is therefore significant. A broad lower-severity rule must not unintentionally outrank a narrow high-severity isolation rule.

Build and test the parser first

Open System > Settings > System Communication > Security Event Parsers. Create or copy a parser, choose the message format and use Populate from Received Syslog when a real sample exists. Map source/destination IP, type, subtype, threat ID, description and severity. If only part of a field is needed, use Partial Column/Tag with a regular expression; otherwise use the entire value. Define severity mappings so vendor-specific levels become FortiNAC Low, Medium or High. Test a representative raw message before selecting the parser on the pingable device.

Illustrative TAG/VALUE input:
src=192.0.2.44 dst=198.51.100.20 type=ips subtype=signature threat=4711 severity=critical

Expected normalized fields:
Source IP 192.0.2.44; Destination IP 198.51.100.20
Type ips; Subtype signature; Threat ID 4711; Severity High

The example is illustrative; use the actual vendor message and delimiter. Verify the event appears in Security Events before enabling automated isolation.

Troubleshooting and safeguards

If no event appears, verify syslog reachability, that the correct pingable device accepts events, and that the parser is enabled and selected. If fields are blank, inspect the raw sample and delimiter/tag mapping. If an event appears without a host, verify L3 polling, IP-to-MAC resolution and database presence. If no alarm is generated, inspect trigger fields, severity mapping, target profile and rule rank. Do not immediately change isolation VLANs; the fault may be in parsing or correlation.

Start with notification-only or manual response while validating a new parser. A bad source-IP mapping can associate an event with the wrong endpoint, and a broad trigger can isolate the wrong host. Keep a sample for each vendor firmware version and retest after parser changes. The operational chain is raw message, normalized event, host correlation, trigger/profile match, alarm creation and action. Evidence at one stage does not prove the next stage succeeded.

Fingerprint records are observations

FortiNAC-F continuously collects identity records as hosts connect. Each new fingerprint heard for a MAC can create a separate record. The same physical endpoint can present different evidence over time: when an adapter moves from a registration VLAN to production and obtains a new IP address, another fingerprint may appear. If the same MAC and port show different operating systems, the endpoint may be dual-booting and FortiNAC can raise a Device Fingerprint Changed event. Multiple rows for one MAC do not automatically mean multiple physical devices.

The Endpoint Fingerprints view exposes MAC, device type, operating system, IP, hostname, vendor/OUI, source method, matched profiling rule, registered/rogue state, last-heard time and creation time. Charts can be filtered by device type, OS, vendor, OUI or source. These fields answer two different questions: what evidence was observed, and which source was used to populate the host record?

Evidence sources and source rank

Sources include passive DHCP attributes, vendor OUI, active NMAP, SNMP, SSH, TCP/UDP port observations, Telnet, endpoint agent and WinRM. DHCP attributes include parameter/option lists, vendor class and message type. NMAP can report output and open ports; SNMP fingerprints include queried OID and response; SSH/Telnet can record command output; WinRM can return UUID, hardware type, serial and asset tag. FortiNAC-F can also use FortiGuard IoT classification, with DHCP fingerprint collection enabled to improve query results.

Set Source Rank determines the order in which methods populate the host record. Fortinet gives Agent, DHCPv4 and Vendor OUI as an example ordering. A high-priority source can override a weaker lower-priority observation. OUI identifies the NIC manufacturer, not necessarily the complete model or OS. DHCP vendor-class can be useful but may be spoofed. An authenticated agent or managed-device query may provide stronger evidence, depending on the environment.

Profiling rules and rogue-to-registered transition

A fingerprint is evidence for classification; it does not automatically register the endpoint. FortiNAC creates a rogue host record from collected evidence. Automatic registration occurs only when the endpoint matches a Device Profiling rule configured for automatic registration. If the OUI is not recognized, FortiNAC may be unable to register it automatically. Administrators can test a rule against selected hosts, confirm that a host still matches, or create a rule from the fingerprint view. A device can be well-profiled yet remain rogue because registration is a separate decision.

Device Profiler settings control whether rogue hosts are created from DHCP, whether NMAP runs without ICMP ping, and whether FortiGuard IoT collection/proactive profiling is enabled. The no-ping NMAP option helps where ICMP is blocked, but is disabled by default because scanning many uncontactable endpoints can consume significant resources. Enable only methods that solve a defined inventory problem.

Passive visibility and configuration

For DHCP fingerprinting on FortiNAC-OS, the applicable interface must permit DHCP access. If endpoints' DHCP broadcasts do not reach FortiNAC, a switch SPAN/mirror can copy DHCP packets to eth0. The historical Community article shows this topology and recommends filtering to UDP/67 and UDP/68 to avoid wasting compute. FortiNAC's eth1 is primarily for isolation and should not be used as the passive profiling interface.

Verification and troubleshooting

When a device is misclassified, inspect all fingerprint records for its MAC, not only the newest row. Compare source, last-heard time, rule name and attributes. If DHCP evidence is absent, check that the correct VLAN's DHCP traffic reaches eth0 and the protocol is allowed. If NMAP data is blank, check reachability, filtering and scan cost; a blocked ping can prevent the default scan unless the no-ping option is deliberately enabled. If a rule does not register the endpoint, test the rule against the fingerprint and verify automatic/manual registration and OUI recognition.

Use Last Heard to distinguish stale evidence from a current observation. A new DHCP hostname may update identity fields without changing the physical device. A source-rank change can alter the populated host record even though raw fingerprints remain. Document source precedence and keep active profiling bounded. The goal is defensible endpoint classification with known evidence provenance, not the maximum possible fingerprint count.

FortiAuthenticator

RADIUS accounting proxy: attribute transformation and fan-out for RSSO

Accounting packet matching, attribute transformation and RSSO fan-out

Primary feature / administration documentation

  • FortiAuthenticator 6.6 — Accounting proxy

Community / scenario material

Purpose and object model

FortiAuthenticator's RADIUS accounting proxy receives accounting packets from a carrier RADIUS server, transforms selected attributes and forwards records to multiple FortiGate or FortiMail devices for RSSO. It is not a RADIUS authentication proxy. The input is accounting information from an upstream RADIUS server; the output is shaped for downstream devices that use accounting records to identify user sessions and group membership.

The proxy uses three object types. Sources identify the upstream RADIUS server and its shared secret. Rule sets define which incoming attributes qualify and how output attributes are changed. Destinations identify the FortiGate/FortiMail receiver, its shared secret, selected source and rule set. The destination is an explicit mapping from producer through transformation to consumer, not simply a broadcast of every packet to every receiver.

Matching and transformation

A rule set can contain multiple rules. Add can insert a fixed value or an attribute retrieved from a user's LDAP record. Modify renames an attribute so the destination accepts the expected name. Matching RADIUS attributes determine which accounting requests are proxied; matches can use standard or vendor-specific attributes and can optionally use substring matching for supported IDs. Thus a rule set both filters the input population and shapes the output record.

Fortinet's example begins with User-Name, NAS-IP-Address and Fortinet-Client-IP-Address. The outgoing record adds Session-Timeout with fixed value 3600 and Fortinet-Group-Name derived from the user's LDAP group. The key design point is provenance: a field may be copied from the packet, added as a constant, derived from LDAP or renamed. If a FortiGate does not learn the expected group, determine which path was intended and whether the attribute existed at each stage.

Sources, destinations and cache/retry controls

FortiAuthenticator supports up to 25 rule sets, 500 proxy sources and 500 proxy destinations. General settings include group cache lifetime 1–10080 minutes (default 480), retries 0–3 (default 3), retry timeout 1–10 seconds (default 5), and statistics update period 1–3600 seconds. A long group cache reduces LDAP lookups but delays recognition of group changes; a short cache increases directory queries. Retries can help a transient timeout but should not hide a persistent secret or routing mismatch.

For each source, define upstream FQDN/IP and shared secret. For each destination, define receiver FQDN/IP and destination secret, select the source and attach the rule set. One source can feed multiple destinations with different rule sets when consumers expect different attribute naming or group mapping.

Configuration and evidence

Configure Accounting Proxy under Authentication > RADIUS Service > Accounting Proxy. Set General values, create a rule set, define sources and destinations, and specify matching attributes plus Add/Modify actions. Validate LDAP lookup and resulting attribute values before production fan-out. A controlled test should use a known user, known LDAP group and known accounting record so the output can be compared field by field.

Example transformation:
Incoming: User-Name, NAS-IP-Address, Fortinet-Client-IP-Address
Rule set: Add Session-Timeout=3600
          Add Fortinet-Group-Name from LDAP group
Destination: FortiGate RSSO receiver + destination secret

Use FAC accounting-proxy logs/statistics to confirm receipt, match and forwarding. On the FortiGate, verify RSSO user/group/session state. A packet leaving FAC proves forwarding, but the receiver may still reject it if the destination secret or expected attributes are wrong.

Troubleshooting and security

If nothing is forwarded, check source IP/FQDN, shared secret and match filters. If forwarded but group membership is wrong, inspect LDAP-derived value and exact attribute name/vendor ID. Check group-cache lifetime when membership changed recently. If the destination times out, inspect retry/timeout only after validating routing and receiver health. The Oct 27 CSV-import Community issue concerns stored user RADIUS attributes being cleared by bulk import; it is not an accounting-proxy fault, but it highlights the need to distinguish user-record attributes from transformed accounting attributes.

Protect source and destination secrets and restrict sources to trusted peers. Avoid broad substring filters unless tested; a loose match can forward unrelated sessions. Keep transformations explicit and version them with downstream RSSO policy. Trace one accounting record from source packet through match/transformation to each destination and the FortiGate's learned session.

Additional Access Authentication for secrets: policy inheritance, time window and launch gate

Primary feature / administration documentation

Purpose and policy inheritance

FortiPAM 1.9 adds Access Authentication as a separate gate for opening or launching a secret. A user may already have permission to see a folder or secret, yet the secret can still require fresh authentication before sensitive content is editable or a launcher can connect to the target. This reduces the risk that a long-lived portal session alone is enough to reveal or use a privileged credential. It is distinct from checkout, approval-to-launch, JIT privilege elevation and session recording; those controls can coexist but solve different problems.

Access Authentication is configurable at two levels. A secret policy in Secret Settings > Policies can set Enable, Disable or Not Set. Enable requires authentication for secrets in the folder unless the secret-level setting is disabled. Not Set allows the secret to customize the behavior. The secret exposes Access Authentication in Session Security and an Access Authentication Status that shows the remaining time for which access is valid.

Authentication lifecycle

When a user opens a protected secret for editing, FortiPAM displays an Access Authentication dialog. Until authentication succeeds, editing is disabled and the UI warns the user to authenticate. When launching a protected secret, authentication is mandatory for a successful launch. This gates both reading/editing the secret configuration and using the credential through a launcher. A successful portal login is not enough if the access-authentication timer has expired.

The policy can specify an authentication server and duration. The documented default is 60 minutes, with a range of 0–180; zero is a short-lived authorization for immediate use. Owner bypass is disabled by default. Settings explicitly set to Enable or Disable at policy level cannot be changed on the secret; Not Set permits secret-level customization. If per-secret exceptions are required, do not hard-code Enable in the folder policy and then expect a secret override.

Configuration pattern

Create/edit the secret policy and set Access Authentication deliberately. Choose the authentication server, duration and owner-bypass behavior. If different secrets in the folder need different requirements, leave the policy Not Set and configure the secret-level Session Security option. If all secrets must require reauthentication, set Enable at policy level and treat it as enforced. Review Access Authentication Status on the secret before testing launch.

Secret Settings > Policies
  Access Authentication: Enable | Disable | Not Set
  Server: approved authentication server
  Duration: 0-180 minutes (default 60)
  Bypass For Owner: disabled unless approved

Secrets > Secrets > <secret> > Session Security
  Access Authentication: inherit or override when policy is Not Set
  Access Authentication Status: remaining valid duration

For remote RADIUS/LDAP users, FortiPAM documents an option to select “Authenticate using PAM login credentials” when accessing or launching a secret. A remote directory login identity is not necessarily the credential FortiPAM expects for this additional step.

Evidence and troubleshooting

Verify the policy's Access Authentication value and the secret's Session Security value. If a user can see the secret but cannot edit it, check whether the authentication dialog is pending or the policy enforces the requirement. If editing works but launch fails, confirm the authentication window is still valid at launch time. Access Authentication Status is the feature-specific observable for remaining time. The dialog confirms the gate is active; it does not prove that the target host is reachable.

Test both a local FortiPAM account and a remote RADIUS/LDAP account. For the remote account, verify the PAM-login-credentials option where required. If the secret-level control is not editable, inspect the folder policy for explicit Enable/Disable instead of Not Set. If launch fails after access authentication, move to launcher, target resolution, checkout/approval and network path diagnostics rather than repeatedly changing the authentication setting.

Operational safeguards

Choose a duration that matches secret sensitivity and workflow. A long duration improves convenience but increases the period in which an authenticated browser session can use the credential. Zero is intended for immediate use and should be tested with the exact launcher. Owner bypass should be exceptional because it creates a different assurance path for the secret owner. Document whether the control applies to viewing, editing, launching or all three.

Access Authentication is additive. A secret may also require approval, checkout, password rotation or session recording. Authentication proves the user at access time; approval authorizes a request; checkout reserves exclusive use; recording captures activity. When troubleshooting, identify which gate stopped the workflow. The sequence is folder/secret permission, additional authentication, approval/checkout if configured, launcher creation and target connection.

Agentic plans, sequential SQL evidence and analyst persistence

Purpose and agentic versus non-agentic modes

FortiSIEM 7.5 provides FortiAI Incident Analysis to help analysts decide whether an incident is a false positive or true positive. The guide describes a basic non-agentic approach and an Agentic approach. Agentic mode creates a plan, executes the steps and reaches a conclusion from gathered evidence. This is more than a paraphrase of the incident title: the plan can identify indicators of compromise, retrieve related incidents and query historical behavior for the same user or source context.

The documented example is an Office 365 mailbox login from outside the user's country. A prompt can ask FortiAI to identify IOCs, inspect related incidents by incident ID, find successful logins for the same user from the source country in the preceding seven days, and aggregate other users who successfully logged in from that country. Those steps provide context for deciding whether the location is anomalous for one account or common across the organization. The value is evidence chaining, not an unverified model opinion.

Plan execution and data handoff

Open Incidents > List by Time, set Auto Refresh to Manual Refresh and open the incident slide-in. Select the FortiAI tab and choose Agentic. FortiAI presents a prompt that can be reviewed or edited. The engine creates sequential steps, generates SQL queries to retrieve results and can feed one step's output into later steps. It then analyzes the evidence holistically and produces a summary, including a false-positive assessment and likely root cause based on related incidents.

The output handoff is the key mechanic. An initial IOC extraction can determine which user, source country, IP or time interval the next query should use. A related-incident lookup can narrow the historical comparison. Analysts should inspect the plan and evidence at each step. No related incident may mean no data was collected, the time range was wrong or criteria were too restrictive; it does not automatically prove the event is malicious.

Analyst workflow and persistence

During execution, FortiSIEM displays the steps. The analyst can stop the analysis, edit the prompt and rerun, export a PDF, or add the analysis to Incident Comments. The prompt can be saved as a rule attribute for reuse with future incidents triggered by the same rule. Saving a prompt is not the same as saving a completed investigation: the prompt preserves instructions, while the result must be attached to comments or exported.

Fortinet documents a UI-state limitation: stay in the FortiAI tab while analysis runs. Switching tabs, closing the slide-in or changing focus to another incident stops execution. Unless the result is added to Incident Comments, it is lost if the analyst navigates away or closes the slide-in. This is an interaction/lifecycle boundary, not a query-engine failure. Keep the incident in focus until completion and then persist the result.

Evidence quality and safe use

For a geographic-login incident, specify the incident ID, IOC fields, first-seen time, source country and seven-day lookback. Ask for both the same user's history and other users' behavior from that country. The result should show which time window and fields were queried, not just a confidence label. Compare SQL outputs with the original incident, raw authentication logs and known travel/VPN context. If no history is returned, confirm the source and retention window before concluding that no historical event exists.

FortiAI is decision support, not an automatic containment action. A plan can be limited by missing telemetry, incomplete identity normalization or a misleading prompt. Treat its conclusion as a hypothesis backed by displayed query results. If useful, attach it to Incident Comments so the next analyst can see the reasoning and evidence behind the disposition.

Troubleshooting and application

If analysis stops, confirm the FortiAI tab, slide-in and selected incident remained in focus. If a completed analysis disappears, check whether it was added to comments before navigating. If the plan returns weak evidence, edit the prompt to specify IOC, entity, time range and aggregation fields. If a query returns no data, verify the relevant log source and retention rather than asking FortiAI to infer missing history.

Use Agentic when the question requires dependent queries and contextual aggregation; use the basic approach for a short bounded explanation. For repeatable investigations, save the reviewed prompt as a rule attribute and ensure the rule exposes the needed incident fields. The analyst record should include the original incident, plan, SQL evidence, conclusion and whether the result was persisted to comments or PDF.

Community / scenario material

Inline-CASB is a network transaction

FortiSASE Application Control with Inline-CASB recognizes SaaS and other application traffic as it passes through the security PoP. It uses IPS protocol decoders to analyze application traffic, including traffic on non-standard ports or protocols. The documented detection support covers HTTP/1.0, HTTP/1.1 and HTTP/2. The feature combines Application Control with SSL deep inspection to identify individual cloud applications and apply granular access control. This differs from API-based CASB, which connects to a SaaS tenant/API and evaluates stored content or tenant activity. Inline-CASB operates in the user traffic path.

Steering matters. FortiSASE must receive the user's traffic through the configured agent, IPsec or agentless path before the decoder can inspect it. If traffic bypasses the PoP, Inline-CASB cannot enforce the category or per-app decision. A policy that permits the network connection does not prove the application signature was decoded; encrypted content must be visible through the inspection design.

TLS deep inspection and QUIC fallback

For HTTPS SaaS traffic, FortiSASE performs SSL deep inspection to decrypt application data and expose HTTP fields to the decoder. FortiSASE acts as an intermediary, connects to the real server, inspects content and presents a certificate signed by its inspection CA. FortiSASE Endpoint Management Service pushes the CA to managed endpoints' Trusted Root CA store so FortiClient trusts it. Unmanaged endpoints need an equivalent trust deployment if silent inspection is expected.

HTTP/3 uses QUIC over UDP/443. Fortinet's Inline-CASB deployment guidance says QUIC must be blocked when SSL deep inspection and related security features need to inspect HTTP/3 traffic, forcing fallback to TLS 1.3 over TCP. If QUIC remains available, browser sessions may use a transport not inspected by the documented path. Scope the block to the relevant egress policy and validate the resulting HTTP version; it is not a generic instruction to block all UDP.

Category actions and per-app overrides

Application Control With Inline-CASB presents categories and allows an action for each. Allow passes traffic to subsequent web-filter, antivirus and DLP engines. Monitor processes similarly to Allow but generates a log for matching traffic patterns. Block denies attempts to access applications in that category. Application Overrides assign an action to an individual app that overrides its category action. For example, a category can allow Video/Audio while a particular video application is blocked. The per-app override is the more specific decision.

Cloud signatures are marked in the interface, and a lock icon can indicate that SSL deep inspection is required. Fortinet notes Inline-CASB features are not guaranteed when all other security features are disabled; enabling at least one of AV, file filter, DLP, web filter or DNS filter is recommended. This dependency should be tested in the deployed profile group, not assumed from a saved toggle.

Configuration pattern

Enable Application Control With Inline-CASB in the relevant FortiSASE security profile group. Customize category actions, then add per-app overrides. Enable SSL deep inspection and deploy the inspection CA to endpoints. If HTTP/3 inspection is required, block QUIC UDP/443 on the relevant path so browsers fall back to TLS over TCP. Use separate profiles for different policy contexts if proxy-category restrictions make a profile unsuitable for an SWG policy.

Deployment sequence:
1. Steer endpoint traffic to FortiSASE PoP.
2. Deploy/trust FortiSASE inspection CA.
3. Enable SSL deep inspection for SaaS HTTPS.
4. Block QUIC UDP/443 where HTTP/3 inspection is required.
5. Enable Inline-CASB Application Control.
6. Set category actions, then per-app overrides.
7. Validate app logs and downstream AV/DLP/Web Filter behavior.

The older Community article about unavailable SWG profile groups is historical context, not a recent scenario. It recommends a separate SWG profile where the Proxy category constrains available actions; confirm current UI behavior on the deployed release.

Verification and failure isolation

Test a known SaaS application with category Allow, category Monitor and explicit application Block. Confirm traffic is steered to the PoP, the certificate chain is trusted and the app is identified in logs. If the browser shows a certificate warning, fix CA distribution before changing signatures. If a cloud signature is not detected, check the deep-inspection requirement and whether the client used QUIC. If category action works but one app behaves differently, inspect Application Override.

Allow does not mean no further inspection: permitted traffic continues to web filter, AV and DLP. Monitor is not a block. If an app is blocked, distinguish category block from per-app override. If a profile group is unavailable in an SWG policy, use a separate SWG profile where required rather than weakening Inline-CASB. Prove steering, TLS visibility, app identification and final action as four separate stages.

Secure SD-WAN

ADVPN 2.0: edge discovery, path management and transport-group shortcut selection

Shortcut query/reply, transport groups, path health and overlay placeholders

Primary feature / administration documentation

Architecture change

ADVPN 2.0 changes how spokes discover one another and choose direct shortcut paths. The FortiOS 8.0 guide describes edge discovery and path management on the spokes. Spokes use available underlays and link-health information to decide whether a shortcut can form and which transport should carry it. This improves resiliency when an underlay fails or degrades and reduces dependence on a specific hub-and-spoke BGP design. A shortcut is not simply a static route or a tunnel that always uses one WAN interface; it is the result of discovery and path eligibility.

The guide contrasts ADVPN 2.0 with earlier designs that relied on BGP route reflection, next-hop recursive resolution, per-overlay BGP or BGP on loopback. The spokes now use more intelligence to select a shortcut from matching available underlays and health criteria. The documented release supports IPv4 only. A design that assumes identical behavior for IPv6 is outside this documented scope.

Edge discovery and path selection

When spoke-to-spoke traffic needs a direct path, edge discovery carries a shortcut query through an available path, commonly via the hub. The reply can include remote-spoke participating links, health checks and transport-group information. The spokes use this to determine eligible underlay combinations. Members in the same transport group can create shortcuts with one another. The group is a compatibility constraint: it prevents a spoke from selecting a path that does not match the intended transport design.

In some deployments, spokes use different transports than the hub. ADVPN 2.0 can use overlay placeholders to trigger a shortcut between spokes over transports to which the hub is not connected. The hub can relay discovery without being a member of every transport used for direct data traffic. Path management tracks eligible paths and can react when link health changes. Shortcut existence therefore depends on discovery, transport compatibility and health, not only IKE reachability.

Configuration pattern

Enable ADVPN 2.0 selection in the SD-WAN zone with advpn-select and define transport groups on the relevant SD-WAN members. Configure consistently across the hub/spoke topology using the full FortiOS 8.0 deployment guide. Do not enable the feature on one spoke and assume a legacy peer understands the new discovery attributes. Confirm each member is attached to the correct zone and that health checks represent the destinations/applications being protected.

config system sdwan
  config zone
    edit "overlay"
      set advpn-select enable
    next
  end
  config members
    edit 1
      set interface "wan1"
      set transport-group 1
    next
    edit 2
      set interface "wan2"
      set transport-group 2
    next
  end
end

The snippet illustrates the feature controls; use the complete 8.0 configuration guide for Phase 1, zone, member and health-check details. Make transport-group membership and health-check intent consistent at both spokes rather than copying a generic two-WAN example blindly.

Discovery versus IKE evidence

When a shortcut does not form, separate discovery from IKE/IPsec establishment. Confirm ADVPN 2.0 selection is enabled and participating members have expected transport groups. Check SLA/health state; an administratively up link may be ineligible because required health criteria fail. Verify the shortcut query/reply can traverse an available path and both spokes advertise compatible links. Then inspect IKE debug and resulting IPsec SA.

The historical Community symptom vwl found no viable shortcut, drop exchange is a clue that a shortcut exchange arrived but no eligible path candidate was found. It does not by itself prove an IKE proposal mismatch. Compare transport groups, link health, member availability and discovery attributes before changing cryptographic proposals. If no shortcut is eligible, traffic may continue through the hub as fallback rather than indicating total overlay failure.

Operational limits and troubleshooting

ADVPN 2.0 improves shortcut selection under underlay change, but does not remove the need for correct underlay routing, IKE reachability, policies and health checks. Validate each WAN path independently, then test spoke-to-spoke shortcut while observing selected member. Degrade one underlay in a controlled test and confirm the path manager selects another eligible transport or falls back to the hub. Keep a clear mapping of transport groups to provider/service types so paths are not accidentally treated as interchangeable.

Use IPv4-only support as a design gate. Distinguish ADVPN 2.0 from BGP route-tag steering or graceful BGP shutdown: those influence route/policy behavior, while ADVPN 2.0 handles spoke discovery and shortcut eligibility. Troubleshoot in order: discovery, transport-group compatibility, link health, IKE negotiation, route installation and application traffic.
