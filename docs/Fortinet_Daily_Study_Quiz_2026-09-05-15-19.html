FortiGate — IoT detection service and asset intelligence

Primary lesson source: https://docs.fortinet.com/document/fortigate/8.0.0/administration-guide/981276/iot-detection-service
Scenario support source(s): https://community.fortinet.com/fortigate-3/technical-tip-how-to-configure-device-detection-in-fortigate-118947

Why this capability exists

FortiGate combines passive device observations with FortiGuard IoT intelligence so administrators can identify connected assets, enrich them with type/vendor/OS information, and expose vulnerabilities associated with the detected device.

Architecture and processing model

Traffic and link-layer observations enter the device-identification pipeline from monitored interfaces. FortiOS correlates MAC/OUI, protocol behavior, DHCP and other fingerprints with the IoT Detection Service database. The resulting device record is an operational object that can be viewed in device inventory/topology and can carry security context such as detected vulnerabilities. Identification is therefore downstream of visibility: no traffic or no device detection on the interface means the cloud intelligence has nothing useful to classify.

The practical way to learn this feature is to treat each transition in the diagram as a contract. The upstream component must create a specific state or observation before the downstream component can act. This is more useful than memorizing the GUI because the same reasoning survives version changes: determine what information enters the feature, which Fortinet component owns the next decision, what state is created, and which evidence proves that transition occurred.

Implementation and configuration workflow

Enable device detection on the relevant interface and ensure the FortiGate can use the required FortiGuard services. In the GUI, verify the device inventory/asset views rather than assuming that a MAC seen in a forwarding table equals a fully identified IoT asset. For CLI verification, use interface configuration to confirm device-identification settings and inspect the device inventory/diagnostic views supported by the FortiOS release. Do not invent a static device fingerprint: the observed fields are environment dependent.

Before changing configuration, record the expected object, target, scope, and release. Fortinet features often expose both configuration intent and runtime state; a correct configuration object is necessary but not sufficient. Use install preview, runtime monitors, diagnostic commands, event logs, session tables, or product-specific status views as appropriate to prove the actual state. Where a value is dynamic—MAC addresses, user names, counters, IDs, timestamps, learned fingerprints, model scores, or SLA measurements—this report intentionally does not invent a canonical output value.

Healthy state and what it proves

A healthy state is a device record whose MAC/IP relationship is current, whose vendor/device family is classified with useful confidence, and whose traffic is still being observed on the expected interface. Vulnerability enrichment can then be evaluated separately. A generic or unknown classification proves only that the endpoint was observed; it does not prove the FortiGuard classifier had enough evidence to identify it.
