1. FortiGate: Multus CNI: discover every pod interface, not just the default network

Primary source: FortiOS 8.0 Administration Guide — Multus CNI for Kubernetes connectors

Why this matters. A Kubernetes pod normally has a primary network interface, but Multus CNI lets the pod attach to additional networks at runtime. A firewall policy that relies on a Kubernetes SDN connector can therefore be incomplete if the connector only learns the pod's default interface. FortiOS 8.0 adds Multus-aware discovery so the connector can populate dynamic firewall address objects with all relevant pod addresses, including secondary IPv4 and IPv6 addresses. This is particularly useful for virtual network functions, telecom workloads, VM-backed pods, and workloads that separate management, storage, and service traffic across multiple network attachments.

Objects and data path

The control-plane objects are the Kubernetes SDN connector, the pod annotations written by the CNI chain, and a FortiGate dynamic firewall address. The connector talks to the Kubernetes API server using its configured address, port and secret token. Multus exposes the default interface in k8s.v1.cni.cncf.io/network-status and additional attachment details in k8s.v1.cni.cncf.io/network-extra-info. FortiGate consumes these annotations, evaluates the connector filter (for example K8S_PodName=virt-launcher-testvm3-7q5gl), and builds the resolved address list for the matching dynamic object. The firewall policy references the object, not a static IP copied from a deployment manifest.

That distinction matters when a pod is rescheduled or an attachment receives a different address. The Kubernetes API remains the source of truth; the dynamic address object is a derived policy object. It can contain the primary pod address plus addresses from multiple Multus networks. IPv6 dynamic address objects are configured in the CLI even though IPv4 dynamic objects can be created in the GUI.

Configuration pattern

config system sdn-connector
    edit "kuber_multus_cni"
        set type kubernetes
        set server "172.19.137.22"
        set server-port 6443
        set secret-token <KUBERNETES_API_TOKEN>
    next
end

config firewall address
    edit "kuber_multus_cni_address"
        set type dynamic
        set sdn "kuber_multus_cni"
        set filter "K8S_PodName=virt-launcher-testvm3-7q5gl"
    next
end

config firewall address6
    edit "kuber_multus_cni_address6"
        set type dynamic
        set sdn "kuber_multus_cni"
        set filter "K8S_PodName=virt-launcher-testvm3-7q5gl"
    next
end

The Fortinet example includes a connector certificate-verification setting; do not copy a disabled-verification example into production without evaluating the cluster API certificate and the trust chain. Use the supported certificate-validation configuration for the deployed release. Keep the connector token scoped to the minimum Kubernetes read permissions needed for the connector.

Verification: what each signal proves

diagnose sys sdn status "kuber_multus_cni" should show the connector as Up. This proves the connector's control-plane session is healthy; it does not prove that a particular pod matched the filter or that secondary addresses were returned. In the GUI, use View Matched Addresses on the dynamic address. In the CLI, show firewall address and show firewall address6 should show the resolved list. The list is the evidence that the object contains the expected primary and secondary IPs. It still does not prove that the intended firewall policy is the first matching policy for a packet.

Failure isolation

If the connector is Up but a secondary address is missing, inspect the pod itself before changing the FortiGate policy. Confirm that Multus attached the secondary network and that network-extra-info contains the attachment name and address. Then check the exact filter string, the connector's collection scope (Private versus Public), and whether the missing address is IPv6. A filter that matches the pod name but an annotation that contains only the default network will produce a healthy connector and an incomplete address object. If the pod is recreated, verify that the connector has refreshed the new runtime address rather than assuming the previous IP remains valid.

Operational application and caveats

Consider a virtual router pod with eth0 on the cluster overlay, a second interface on a service VLAN, and a third interface on a storage network. A policy that protects the service VLAN must reference the dynamic object that includes the second attachment; using only the default pod IP silently protects the wrong interface. Treat each attachment as a distinct policy identity where segmentation requires it. Validate both address families and the object-to-policy reference after a deployment rollout. The feature improves discovery; it does not decide which pod networks should be trusted, nor does it replace Kubernetes network policy or the need to design FortiGate policy boundaries.

2. FortiManager: Global ADOM local-in policy blocks: centralize management-plane protection

Primary source: FortiManager 8.0 New Features — Local In policies in Global ADOM and policy blocks

Why this matters. A local-in policy controls traffic destined to the FortiGate itself—administrative HTTPS/SSH, routing/control-plane services, and other traffic terminating on an interface. It is not an ordinary forward firewall policy for traffic crossing the FortiGate. In a large estate, repeating the same management-plane allow/deny boundary in every local ADOM creates drift: one site may allow a jump-host subnet while another leaves a broad management service exposed. FortiManager 8.0 extends local-in policy packaging so common IPv4 and IPv6 controls can be authored in the Global Database ADOM and reused across multiple policy packages and ADOMs.

Objects and relationships

The feature uses four distinct layers. First, Feature Visibility must expose Local In Policies in Policy & Objects. Second, the Global Database ADOM contains global policy packages and global policy blocks. Third, a local-in policy can be created as a header or footer policy in the global package, or inside a global policy block that can be appended to packages. Fourth, the global package is assigned to target ADOMs and installed to managed FortiGates. Local ADOMs can still own their local policy content; the global portion provides common controls without requiring each ADOM administrator to recreate the same objects.

Header and footer placement is important. It lets a central team place shared policy boundaries around the local package's own local-in rules. A global policy block is reusable content, while package assignment is the step that scopes that content to an ADOM. Creating a block does not automatically make it effective on every device. The package must include it, be assigned to the ADOM, and be installed to the intended FortiGate targets.

Build and deploy workflow

Enable the Local In Policies feature in Policy & Objects > Tools > Feature Visibility. Enter the Global Database ADOM, select a global policy package, and create the required IPv4 or IPv6 Local In Header/Footer Policy. Alternatively, create a global policy block, add the local-in header/footer policies to that block, then append the block to each required global package. Use Action > Assign on the global package to assign it to the target ADOMs. In each local ADOM, the global flag indicates that global policy content is assigned. Review the package and install preview before pushing the result to FortiGate.

FortiManager's local-in policy editor exposes interface, source address, destination address, service, schedule, action, and—in IPv4 policies—an HA Management Interface Only option. A change note is required. IPv4 and IPv6 local-in policies are separate policy types; do not assume that an IPv4 header policy automatically protects IPv6 management traffic.

Verification and diagnostic boundaries

At the FortiManager layer, confirm that the policy is visible in the Global Database ADOM, that the policy block is appended to the intended package, and that the package is assigned to the correct ADOM. The global flag in a local package is evidence of assignment, not proof of installation. The install preview and task result prove what FortiManager attempted to send. Read the resulting local-in policy table on the FortiGate to prove the device received the expected rules. A saved object in the Global ADOM is not runtime enforcement evidence.

Common failure modes

If the local-in policy selector is missing, first check Feature Visibility rather than assuming the ADOM is corrupt. If one ADOM is protected and another is not, compare global package assignment and installation history before editing the local policy itself. If a block exists but has no effect, verify it was appended to the package and that the package was installed to the device. For IPv6 management exposure, inspect the IPv6 local-in policy list independently. The feature centralizes distribution; it does not remove the need to validate interface scope, source ranges, service ports, schedules, and rule ordering for each device.

Operational application and caveats

A central operations team can publish a shared jump-host allowlist and deny all other inbound management services, while regional teams retain local exceptions where approved. The same block can be appended to several global packages and assigned to separate ADOMs. Keep a documented exception process and test management access from the out-of-band path before installing a restrictive change. A local-in policy can lock out the administrator if the source address or interface is wrong. The design is therefore a policy-distribution improvement, not a substitute for staged deployment, install preview, and recovery access.

3. FortiAnalyzer: SOC Automation content packs: entitlement, FDS delivery and object provenance

Primary source: FortiAnalyzer 8.0 Administration Guide — SOC Automation

Why this matters. FortiAnalyzer's Security Automation Service is not simply a downloadable parser bundle. It is a licensed FortiGuard content-delivery service that distributes curated content packs, including premium reports, advanced correlation rules, alert handlers, third-party SIEM parsers, and connectors. The content is designed to extend detection and response as vendors and threat patterns change. Administrators need to distinguish four separate states: entitlement, delivery, object installation, and operational configuration. Confusing these states is a common reason teams assume a parser or connector is active when only the package inventory is visible.

Delivery and object lifecycle

A valid Security Automation Service license allows FortiAnalyzer to receive content packs from the FortiGuard Distribution Server (FDS). When a pack is available, FortiAnalyzer applies it automatically. The inventory is visible at Incidents & Alerts > FortiGuard Services > SOC Automation. The table organizes objects by content pack and exposes Content Pack Version, object Name, Config Type, Description, Status (New or Modified), Release Date, Vendor, and Min Version. The Config Type determines where the object is used: reports appear under Report Definitions, alert handlers under Alert Handlers, SIEM parsers under Log Parsers, and connectors under Active Connectors.

Fortinet's SOC Automation Objects guide explains the provenance boundary. RHSP package reports are stored at the global level and display Origin = FortiGuard; FortiGuard-delivered alert handlers and parsers also expose their origin. The inventory pane is primarily a review surface. To inspect or customize the object's configuration, navigate to the corresponding feature pane. A connector object may be delivered by the pack but still require the administrator to configure endpoint URL, credentials, tenant identifiers, scopes, or other environment-specific values before it can exchange data.

Entitlement and version dependencies

Start with the License Information widget to confirm the Security Automation Service license. The device must also be able to reach FDS. Fortinet's SOC Automation Objects introduction notes that beginning in FortiAnalyzer 7.4.9 and 7.6.5, FortiAnalyzer requires a valid FortiCare Elite or FortiCare Premium support contract registered in FortiCloud to receive object updates. Check the deployed release and contract status rather than assuming a license from another Fortinet service covers this content. Each object also has a minimum supported FortiAnalyzer version; a pack may be present while an individual object is not usable on an older build.

Verification: separate the states

The License Information widget proves the appliance sees entitlement. The SOC Automation table proves the content pack and its objects are inventoried, including version, release date, and new/modified status. Origin = FortiGuard proves provenance. Finding a parser under Log Parsers proves the parser object is available, but it does not prove the source device is forwarding logs or that the parser matches the raw message. Finding a connector under Active Connectors does not prove it is configured or authenticated. For a parser, validate source log arrival, parser selection, parsed fields, and event normalization. For a connector, validate the connection and successful data pull separately.

Troubleshooting sequence

If an expected pack is absent, check the Security Automation Service license, FDS reachability, the FortiCare contract requirement for the installed branch, and the content pack's minimum version. If the pack is present but an object is missing, filter by content pack and Config Type. If a parser is present but logs remain raw, inspect the incoming vendor/product identity and the parser's expected message format. If a connector is present but idle, complete its environment-specific configuration and test authentication. Do not repeatedly reinstall a pack when the failure is actually a source-device or credential problem.

Operational application and caveats

For example, a new Armis log parser may appear in a monthly pack. That update reduces the need to build a parser from scratch, but it does not create an Armis API connection or guarantee the device sends the expected syslog format. Record the pack version and release date during change review, then validate the downstream object in its own pane. Treat FortiGuard-origin objects as vendor-delivered content with explicit minimum-version and licensing dependencies. The service accelerates content maintenance; it does not remove the need to verify ingestion, field extraction, rule execution, and response workflow end to end.

4. FortiSwitch: Layer-3 routing within MCLAG: VRRP, BGP and local forwarding

Primary source: FortiSwitchOS 8.0 Administration Guide — Using layer-3 routing within an MCLAG

Purpose and design. A multichassis LAG gives downstream devices one logical Layer-2 attachment to two FortiSwitch peers. FortiSwitchOS also supports Layer-3 routing across that MCLAG pair so the pair can behave like a single router while forwarding traffic on both cores. VRRP provides a shared next-hop identity on each routed VLAN interface (SVI); BGP or OSPF distributes the routes that each peer needs. This is different from merely keeping the inter-chassis link (ICL) alive: the goal is to make a packet received by either peer routable locally, avoiding unnecessary ICL transit while retaining active-active forwarding.

Control-plane and data-plane mechanics

In the one-tier example, Core1 and Core2 form the MCLAG. Both peers have northbound and southbound SVIs. VRRP is configured on each SVI, and the virtual IP is used as the next hop or BGP neighbor address by the adjacent routers. Always enable vrrp-virtual-mac. The VRRP backup automatically performs Layer-3 lookup for the VRRP virtual MAC. MCLAG trunk hashing can deliver an ingress frame to either peer; if that peer has the route in its own routing table and hardware, it can route without sending the packet across the ICL.

With BGP, the northbound and southbound routers establish eBGP sessions to the relevant VRRP VIP. Because the neighbor address is the VRRP VIP, the router peers with the current VRRP master. Fortinet specifies enabling ebgp-enforce-multihop and setting ebgp-multihop-ttl to 3. The two MCLAG cores then use iBGP across the ICL. Routes learned through eBGP are advertised to iBGP so the VRRP backup receives and installs the same forwarding information. OSPF can be used instead, or in a mixed design with BGP northbound and OSPF southbound.

Configuration sequence

Build the MCLAG trunks and ICL first, then create the northbound and southbound SVIs on both peers. Configure the same VRRP virtual IP on the corresponding SVI on each peer, but set priorities so there is a VRRP master on each MCLAG core for the appropriate north/south role. Enable the virtual MAC. Next, configure eBGP to the adjacent routers and iBGP between the cores. For eBGP peers using the VRRP VIP, enable multihop and TTL 3. Ensure the same prefixes are learned and installed on both peers before relying on local forwarding.

config system interface
    edit "nb"
        set ip 20.1.1.11 255.255.255.0
        set vrrp-virtual-mac enable
        config vrrp
            edit 5
                set priority 200
                set vrip 20.1.1.1
            next
        end
    next
end

config router bgp
    set as <CORE_AS>
    set router-id <CORE_ROUTER_ID>
    config neighbor
        edit <NORTHBOUND_PEER>
            set remote-as <NORTH_AS>
            set ebgp-enforce-multihop enable
            set ebgp-multihop-ttl 3
        next
    end
end

Verification and evidence

Check VRRP state on both peers, eBGP state to northbound and southbound routers, and iBGP state across the ICL. Then inspect the routing table on both cores. A healthy eBGP session on Core1 alone does not prove Core2 has the routes needed to forward locally. Validate the same destination prefix and next hop on both peers. During a controlled traffic test, observe which peer receives the frame, which peer forwards it, and whether the ICL carries data-plane traffic that should have been routed locally. The objective is not zero ICL traffic—east-west traffic between separate MCLAG domains may cross it—but no unnecessary north/south transit caused by missing local routes.

Limits and failure patterns

Both peer switches must be configured. FortiSwitchOS 8.0.0 supports IPv4 and IPv6 in this topology; earlier versions supported IPv4 only. Up to 250 SVIs are supported. PIM multicast routing, policy-based routing, IS-IS, and RIP are not supported in this MCLAG Layer-3 design. If the backup receives traffic but lacks the route, it may need ICL transit or fail to forward as expected. If the eBGP neighbor is configured against a physical peer IP rather than the shared VIP, the routing behavior no longer matches the documented single-router design. If VRRP virtual MAC is disabled, the backup's local Layer-3 lookup assumption is broken.

Operational application

In a collapsed core, two FortiSwitches can serve northbound routers and southbound access blocks. Use VRRP VIPs for stable adjacency, eBGP at the boundaries, and iBGP across the peer link so both cores have the same route knowledge. Test one peer failure and one ICL failure separately; they exercise different failure domains. After the test, verify both routing tables and the VRRP role distribution. Do not infer active-active Layer-3 behavior solely from an MCLAG trunk being up.

5. FortiAP/Wireless: FortiAP Configuration mode: isolated local setup without controller SSIDs

Primary source: FortiWiFi and FortiAP Configuration Guide 8.0 — FortiAP Configuration mode

Purpose. FortiAP Configuration mode is a temporary local setup and recovery environment. It is useful when an AP must be given a management address, corrected before controller discovery, or configured without relying on the normal controller-managed SSIDs. It is not a production WLAN and should not be confused with factory reset. The reset button has three distinct timing bands: less than five seconds reboots, five to ten seconds enters Configuration mode, and more than ten seconds factory-resets the unit. The difference is operationally significant: an overlong press can erase the intended configuration instead of opening the local setup path.

Mode transition and isolation

The AP must be booted before the reset button is held for five to ten seconds. After the transition and reboot, it broadcasts FAP-config-<serial-number>. The AP suppresses all SSIDs configured by its controller while this mode is active. Only one Wi-Fi client can associate to the temporary SSID. The SSID is open and operates in NAT mode to provide internet connectivity for local setup. Transmit power is reduced to 1 dBm on each radio, so the setup client must be physically nearby. The AP automatically exits Configuration mode after 30 minutes or when it is rebooted.

The recommended GUI path is to connect a single laptop or service device to the temporary SSID, browse to https://192.168.100.1, authenticate as admin using the AP admin password, and confirm the red CONFIG MODE banner. Under Settings, open Local Configuration and make the required changes. Click OK to save, then use the admin menu to reboot. Configuration changes take effect after the AP restarts. The CLI path uses SSH or a console connection; after editing the local configuration, run cfg -c to save and reboot to leave the mode.

What this mode does—and does not do

The temporary SSID is a bootstrap path, not a replacement for the normal FortiGate or FortiCloud controller relationship. It provides local reachability even when the AP cannot yet discover its controller. Because the controller-configured SSIDs are not broadcast, a client that expects to join the normal corporate WLAN will not see it during this mode. The single-client limit and 1 dBm transmit power are deliberate containment controls: they make the temporary access path short-range and avoid exposing a broadly usable service SSID. NAT mode gives the connected device a way to reach the internet for initial setup, but it does not prove that the AP has a valid CAPWAP path to its controller.

Verification and troubleshooting

The appearance of FAP-config-<serial> and the CONFIG MODE banner prove the AP entered the temporary state. A successful HTTPS login proves local management access. A successful save and reboot prove that the configuration was committed; the AP's new management address and controller discovery after reboot prove the intended settings took effect. Wi-Fi association alone is not evidence of configuration persistence. If the SSID is missing, check that the AP was fully booted before the timed press and that the press lasted five to ten seconds. If the client cannot associate, verify that no other Wi-Fi client is connected and move closer because the radio is limited to 1 dBm. If the AP reappears in normal mode after 30 minutes, the timeout is expected.

Operational application and caveats

Imagine a new AP installed on a switch port in the wrong management VLAN. It cannot reach the controller, so the normal managed SSID is never provisioned. A technician can enter Configuration mode, connect locally, correct the network settings, save, reboot, and then validate controller discovery. Use the mode for controlled local repair, not for long-term administration. Protect the admin password, keep the temporary client physically close, and avoid the greater-than-ten-second reset window unless a factory reset is intended. Model support can vary; confirm the exact AP model's guide before using the button sequence.

6. FortiNAC: MultiKnownHostEntries: preserve SSH trust across VIP owner changes

Primary source: FortiNAC 9.4 Administration Guide — Model configuration

Problem being solved. FortiNAC often models a network device through a virtual IP address rather than through the physical address of each controller or firewall in a high-availability pair. When the VIP moves, the device answering SSH may change. If the two possible owners have different SSH host keys, FortiNAC's cached key for the VIP no longer matches the active owner. SSH correctly rejects the connection, so CLI polling or configuration actions fail even though the VIP responds to ping. FortiNAC 9.4.3 adds the per-device-model MultiKnownHostEntries attribute to handle multiple legitimate keys for the same VIP.

Trust model and object scope

The setting is disabled by default and is applied to the modeled device, not globally to every SSH target. When enabled, FortiNAC checks all potential matches in its known_hosts cache for the VIP and selects the matching entry. This is not a recommendation to disable host-key checking. It is a way to pre-authorize the keys of the devices that are legitimately allowed to own the VIP. Each possible VIP owner must be represented before failover testing; otherwise the new owner can still present an unknown key.

Prepare every candidate key

For the legacy FortiNAC procedure, log in to the FortiNAC CLI as root. Open an SSH connection to each physical IP address that can own the VIP and accept its host key. The key is written to /root/.ssh/known_hosts. Copy the key into /bsc/.ssh/known_hosts, replace the physical address with the shared VIP, and keep a separate line for each possible owner. Repeat for every device that may become active. Fortinet's guide says the VIP should then have two entries with different keys: one for the full device model and one for the pingable model. The key list is therefore a controlled set of trust candidates, not a wildcard trust rule.

ssh root@<PHYSICAL_IP>
cat /root/.ssh/known_hosts | grep <PHYSICAL_IP>
# Copy the key into /bsc/.ssh/known_hosts and change its host to <VIP>

cat /bsc/.ssh/known_hosts | grep <VIP>

device -ip <VIP> -setAttr -name MultiKnownHostEntries -value true

Enable the attribute only after the candidate keys are present. The setting applies to FortiNAC versions 9.4.3 and later. If the network device does not use a VIP, the procedure is unnecessary.

Evidence and diagnostic boundaries

cat /bsc/.ssh/known_hosts | grep <VIP> should show multiple distinct key entries. That proves the cache contains candidate identities. The device model attribute proves multi-entry matching is enabled. A successful SSH poll after a controlled VIP failover proves the active owner presented a key that FortiNAC already trusts. None of these checks proves the SSH username has the correct privilege level, that the password or key authentication is correct, or that the device CLI output is parseable by the selected model.

Failure isolation

If polling still fails after failover, compare the active device's presented host key with the keys copied into the VIP entries. Check for a missed standby owner, a key copied under the wrong VIP, an incomplete write to /bsc/.ssh/known_hosts, or an attribute enabled on the wrong modeled device. If the key is accepted but polling fails later, move to credentials, privilege, prompt format, and model-specific command parsing; do not keep modifying the known-hosts cache. A host-key mismatch is a trust failure, not a RADIUS or SNMP failure.

Operational application and caveats

A pair of wireless controllers may share a management VIP. FortiNAC polls the VIP every cycle. After a failover, the new active controller presents its own host key and the poll fails until that key is trusted. Preloading both keys prevents the maintenance event from looking like a device outage. Perform this setup before the change window, test failover, and preserve the strict host-key checks. The feature is deliberately scoped to VIP models; it should not be used to normalize arbitrary host-key changes across unrelated devices.

7. FortiNAC-F: FortiNAC-F appliance LAG: active LACP aggregation versus redundant links

Primary source: FortiNAC-F CLI Reference — Aggregation and Redundancy

Purpose. FortiNAC-F 7.6.3 adds link aggregation support on the appliance. A LAG combines multiple physical ports into one logical interface so the appliance can use multiple links and tolerate an individual member failure. This is not the same as a redundant interface group. An aggregate interface can use all negotiated members for bandwidth and resilience; a redundant group forwards over one member at a time and primarily provides failover. Choosing the wrong type can leave an appliance with less throughput than expected even though the IP address remains reachable.

Interface model and negotiation

The FortiNAC-F CLI reference describes IEEE 802.3ad/802.1ax aggregation and LACP active/passive modes. The logical interface owns the IP and management access configuration; physical member ports are bound to that interface and should not be configured separately for competing Layer-3 purposes. LACP exchanges control frames with the peer switch to negotiate which physical links belong to the same aggregator. If one member fails, traffic can continue on the remaining active member(s), reducing available bandwidth but preserving connectivity. Both ends must agree on the channel and member configuration.

Fortinet's example creates lag0 from unused port2 and port3 with lag-mode lacp-active. The redundant example creates redundant0 from port3 and port4; only one link is used at a time. Do not place a physical port into an aggregate while it is still assigned to another interface or switch construct.

config system interface
    edit "lag0"
        set type aggregate
        set lag-mode lacp-active
        set allowaccess ping ssh http https
        set member port2 port3
    next
    edit "redundant0"
        set type redundant
        set allowaccess ping ssh http https
        set member port4 port5
    next
end

Operational transaction

Plan the switch-side port-channel first. Confirm the selected appliance ports are unused, configure the FortiNAC-F aggregate interface, add the physical members, and apply the intended addressing and allowed management services to the logical interface. Configure the peer switch with matching LACP settings and the same physical member set. LACP active mode initiates negotiation; passive mode responds. If both ends are passive, the bundle may not form. If one side is a static channel and the other expects LACP, the link may appear physically up without forming the intended aggregate.

Verification: do not stop at ping

Confirm that the logical interface exists with the intended member list, then inspect the LACP actor/partner state and per-member counters on both the appliance and switch. A ping to the management address proves that at least one path is forwarding; it does not prove both members are active or that traffic is distributed. Disconnect one member in a controlled test: the logical interface should remain up and traffic should continue on the surviving member, with reduced capacity. For a redundant group, expect one active path rather than simultaneous use of all links.

Failure isolation and caveats

If the LAG does not form, check that the member ports are unused, the switch ports belong to the correct port-channel, the LACP mode is compatible, and speed/duplex and VLAN treatment match. If the interface is reachable but one member carries no traffic, inspect aggregator state and member counters before assuming a cabling fault; LACP may have selected only one compatible aggregator. If the requirement is simply to keep management reachable over one alternate link, a redundant group may be the more appropriate design. The 7.6.3 release note introduces the capability; use the CLI reference for exact syntax and confirm model-specific port availability before change.

Operational application

For a FortiNAC-F appliance connected to a redundant core pair, use a supported switch-side multi-chassis LAG design and verify that the switch presents one consistent LACP partner identity. The FortiNAC-F logical interface then survives one cable or switch-port failure without changing its management address. Avoid assuming that two cables automatically double throughput: member negotiation, hashing, and traffic distribution determine actual utilization.

8. FortiAuthenticator: FIDO for IdP-initiated SAML: authenticate first, then release the SP assertion

Primary source: FortiAuthenticator 8.0.3 Administration Guide — General SAML IdP settings

Security objective. IdP-initiated SAML starts at the identity provider's portal rather than at the service provider. FortiAuthenticator 8.0.0 adds a control to require FIDO authentication for this login path. The administrator can require FIDO alone or password plus FIDO, and can optionally allow password plus OTP only when every FIDO key registered for a user has been revoked. This makes the IdP portal's authentication strength explicit before it issues an assertion to a participating service provider.

Components and trust boundaries

FortiAuthenticator acts as the SAML Identity Provider (IdP). Each service provider (SP) is configured with its entity ID, ACS URL, certificate, and the setting that allows IdP-initiated assertion responses. Users authenticate to the FortiAuthenticator portal, and group filters determine which SP entries they are allowed to see. A registered FIDO key is a user authentication factor; the signed SAML assertion is a separate trust artifact consumed by the SP. FIDO validates the user to the IdP; SAML conveys the resulting identity and attributes to the SP.

IdP-initiated transaction

The user opens the FortiAuthenticator IdP portal. If the browser is not already authenticated, the IdP presents a username-only page and follows the configured FIDO/password flow. With FIDO-only, the user authenticates using the registered FIDO authenticator without a password. With Password and FIDO, both factors are required. If the optional recovery setting is enabled, password plus OTP can be allowed when all FIDO keys for the account have been revoked. After successful authentication, the portal presents only SPs for which the user passes the configured group authorization. The user selects an SP, FortiAuthenticator generates the SAML assertion, and the browser posts it to the SP. The SP validates the assertion and decides whether to grant the application resource.

Configuration sequence

In Authentication > SAML IdP > General, enable the SAML Identity Provider portal, set the device FQDN and server address, and configure the IdP Initiated Login authentication method. Choose FIDO-only or Password and FIDO according to the assurance requirement. If using the recovery path, enable the documented fallback only when all FIDO keys have been revoked. In each SP configuration, enable support for IdP-initiated assertion responses so the SP appears in the portal. Configure group filters and ensure users have FIDO enabled with at least one registered key. The default IdP certificate and signing algorithm remain responsible for the assertion signature; FIDO does not replace SAML signing.

Evidence and failure boundaries

FortiAuthenticator authentication logs should show the selected factor outcome. The SP list in the portal is evidence of group-filter authorization, not proof that the SP will accept the assertion. A successful SAML response at the SP ACS proves assertion delivery and signature/trust processing; application authorization is still controlled by the SP. If the SP is absent, inspect its IdP-initiated support setting and group filters before changing FIDO. If FIDO is unavailable, check whether FIDO is enabled, a key is registered, and at least one key remains active. If all keys were revoked, the configured fallback determines whether password plus OTP can be used.

Operational caveats

IdP-initiated and SP-initiated SAML are different browser flows. In SP-initiated mode, the SP sends the authentication request first; in IdP-initiated mode, the user selects an SP after authenticating at the IdP. Do not assume a working SP-initiated integration proves the IdP portal is configured correctly. Also keep certificate rotation, ACS URL, entity ID, and group mapping in the change plan. FIDO protects the IdP login step; it does not fix a stale SP certificate, incorrect NameID, or an SP that rejects the assertion audience.

9. FortiPAM: Terraform provider: declarative folders and secrets with a sensitive state file

Primary source: FortiPAM Administration Guide — Terraform as a provider

What the provider manages. FortiPAM's Terraform provider automates resource management for folders and secrets on a physical appliance or VM. It gives infrastructure teams a repeatable way to create, update, import, and delete privileged credentials as code rather than repeatedly entering them in the GUI. It is not a full Terraform representation of every FortiPAM feature: the documented provider focuses on folder and secret resources. A secret resource includes a template, a folder path, and named fields such as Host, Username, and Password.

Authentication and object model

The provider authenticates to FortiPAM through a REST API user and API token. The documented workflow creates a Standard User with User Type API User. A Super Administrator can create it in the GUI or with the CLI. The example CLI uses config system api-user and execute api-user generate-key <API_USER_NAME>. The token is displayed once and cannot be retrieved later; if it is lost, generate a new key and update the automation secret store. Use the least privilege required for the folder and secret operations, and protect the token as a credential.

The provider configuration identifies the FortiPAM base URL, access token, and TLS verification behavior. The guide's sample uses verify_ssl = false for demonstration; production automation should validate the appliance certificate and use a trusted CA chain rather than disabling verification. Pin the provider version and Terraform version used in the tested pipeline. Fortinet's example requirements are FortiPAM 1.5.0 or later, provider 1.0.0, and Terraform 1.9.6.

Declarative resource workflow

A folder resource establishes the organizational path. A secret resource references the folder, selects a FortiPAM secret template, and populates its fields. Dynamic blocks can iterate over a local list of field names and values. terraform init downloads and initializes the provider; terraform plan compares the declared state with the remote object and shows additions or in-place updates; terraform apply performs the change. The guide shows a Host field changing from one address to another as an in-place update. Import uses the secret ID from the target appliance so an existing secret can be brought under Terraform management.

provider "fortipam" {
  base_url     = var.fortipam_url
  access_token = var.fortipam_api_token
  verify_ssl   = true
}

resource "fortipam_resource_folder" "network" {
  parent = "Production"
  name   = "Network Devices"
}

resource "fortipam_resource_secret" "edge_router" {
  name     = "edge-router-01"
  path     = "Production/Network Devices"
  template = "Unix Account (SSH Password)"
  dynamic "fields" {
    for_each = local.secret_fields
    content {
      name  = fields.value.name
      value = fields.value.value
    }
  }
}

Critical state-file security

The Fortinet example explicitly warns that importing a secret can output secret field values into terraform.tfstate as plain text. This is the most important operational caveat. A protected FortiPAM vault does not automatically protect a Terraform state file. Use an encrypted remote backend, strict backend ACLs, state locking, audit logging, and limited state readers. Do not commit state or plan files to Git. Mark sensitive variables and outputs, but remember that Terraform's sensitive display controls do not remove values from state. If a state file is exposed, rotate the affected credential and the provider API token.

Verification and failure isolation

The plan is the first evidence of intended change: verify resource address, secret name, folder path, template, and field diff before applying. The apply result proves the provider completed its API operation; read the secret back in FortiPAM to verify the actual object. A plan that proposes replacement rather than in-place update deserves investigation before apply. Authentication failures point to the API user/token or URL; TLS failures point to certificate trust; schema errors point to the secret template or field names. Import conflicts require checking whether the remote secret ID is already bound to another Terraform resource address.

Operational application

Use Terraform for controlled creation and rotation of non-human service credentials, while keeping the actual secret values in a secure variable source and the state backend in a protected store. Separate workspaces or state files by environment, review plans before production apply, and keep the provider/API token out of source control. This makes secret provisioning reproducible without confusing infrastructure-as-code state with the vault's own access controls.

10. FortiSIEM: Native Case API: create investigations, attach incidents and preserve evidence

Primary source: FortiSIEM 7.5.1 User Guide — What's New in 7.4.0, REST API enhancements

Purpose and boundary. FortiSIEM's Case API provides a native case-management object that can be created and updated through REST calls. It is distinct from a two-way integration with an external ticketing system. The API allows a SOC workflow to discover analysts, create a case, associate incident IDs, update case state, add notes, and upload attachments. It does not by itself create a ServiceNow or Jira ticket, nor does creating a case automatically close or suppress the underlying incident.

Endpoints and lifecycle

The documented API includes GET /pub/case/analysts, POST /pub/case, PUT /pub/case/{caseId}, and POST /pub/case/{caseId}/attachment. A caller first retrieves the analyst list and selects a valid assignee. In Service Provider deployments, the organization parameter is mandatory; in Enterprise mode it is optional. The analyst lookup supports a time window of up to 90 days, defaults to 30 days when no range is supplied, and supports offset/limit pagination. The returned analyst record includes user ID, username, overdue count, and assigned count.

Case creation accepts organization, assignee, summary, severity, and optional status, stage, incident IDs, note, policy name, and due date. The API returns a case ID. The case stage can represent Analysis, Containment, Detection, Eradication, Lessons Learned, or Recovery. An incident ID can be assigned to only one case at a time. When updating a case, incident IDs are appended rather than replacing existing IDs, and notes are also append operations. An attachment can be uploaded from an IRI or from a file path under /tmp. These append semantics matter when automation retries a request: a retry should not assume it is replacing an existing list or overwriting a note.

Example request sequence

# 1. Discover eligible analysts
GET /phoenix/rest/pub/case/analysts?organization=Acme&offset=0&limit=100

# 2. Create a native case
POST /phoenix/rest/pub/case
{
  "organization": "Acme",
  "assignee": "soc.analyst",
  "summary": "Credential abuse across VPN gateways",
  "severity": "High",
  "stage": "Analysis",
  "incidentIds": "INC-12345,INC-12346",
  "note": "Correlated incidents opened for investigation"
}

# 3. Update the case
PUT /phoenix/rest/pub/case/{caseId}

# 4. Upload evidence
POST /phoenix/rest/pub/case/{caseId}/attachment

Use the exact payload field schema for the installed release and organization mode. The FortiSIEM release notes define the endpoints; the FortiSOAR integration reference provides additional field behavior and is useful as an integration example, not as a replacement for the FortiSIEM API contract.

Evidence and troubleshooting

The create response's caseId proves a case object was created. Read the case back through the case list/API and verify its assignee, severity, stage, and incident associations. The attachment endpoint's status/message proves the upload operation completed; verify the attachment appears in the case before treating evidence collection as complete. If the analyst list is empty, define at least one FortiSIEM user as an analyst in the UI. If the call fails in Service Provider mode, check the organization context. If an incident cannot be attached, verify it is not already assigned to another case. If an attachment fails, confirm the IRI is valid or the file is present under the supported /tmp path.

Operational caveats

Case creation, incident association, and external ticket synchronization are different transactions. A successful POST to the Case API proves only the native FortiSIEM case exists. It does not prove that a downstream ITSM ticket was created, that a notification was sent, or that the incident was closed. Design automation to read back the case ID, record it in the orchestration context, and make update calls idempotent where possible. Preserve notes and attachment status so that a retry does not create duplicate evidence or misleading case history.

Operational application

When several correlated alerts are promoted to one investigation, automation can look up the on-call analyst, create a case, associate the incident IDs, and attach a packet capture or forensic timeline. The case becomes the native investigation record; external ticketing can be layered on separately. This separation prevents a SOC from mistaking an internal case record for a fully synchronized service-management workflow.

11. FortiSASE: Require comments for configuration audit: commit gate and 30-day evidence

Primary source: FortiSASE 26.1.107 Feature Administration Guide — Administration

Purpose. FortiSASE can require an administrator to enter a change summary before a configuration change is committed. The control is intended to improve traceability across a cloud-managed security service where many administrators can change traffic objects, endpoint profiles, analytics, and reporting settings. It turns the change description into part of the configuration transaction rather than relying on an operator to remember to add a comment later.

Commit workflow

Enable System > Administration > Require comments for configuration audit log. When an administrator submits a configuration change, FortiSASE displays a Configuration audit log pane and requires a change summary before completing the action. The summary records the object being changed, the administrator who made the change, and a short description. Fortinet's example uses creation of a traffic policy: the administrator configures the policy, clicks OK, enters the summary in the audit pane, and then confirms the change. The audit gate applies broadly to configuration changes, including objects, endpoint profiles, and analytics/reporting configurations.

Review records under Operations > Logs > Events > Administrator Events. New logs may appear after a delay, so a missing row immediately after a commit is not proof that the change failed or that the summary was discarded. Existing change summaries are retained for 30 days. If the Require comments option is disabled later, the prompt no longer appears for new changes, but existing summaries remain available within their retention period.

Evidence and limitations

The Administrator Events record and its Details view provide evidence of the actor, object, and submitted change summary. That proves the platform recorded the administrative change context. It does not prove the change was approved by a separate change board, linked to an external ticket, tested successfully, or reviewed by a second administrator. A required summary is not an approval workflow. Organizations that require segregation of duties should pair it with role-based access and their external change-management process.

Failure isolation

If the summary pane does not appear, check whether the requirement is enabled in System > Administration and whether the administrator is performing a configuration change rather than a read-only action. If the configuration is saved but the event is not immediately visible, allow for log propagation delay and refresh Administrator Events. If the summary is absent after the retention window, the 30-day retention boundary may explain it. Disabling the feature stops future prompts; it does not retroactively erase existing summaries before their retention expires.

Operational application

During an emergency traffic-policy change, the operator must state the operational reason before the commit completes. A useful summary names the affected object, the service or user population, the intended effect, and the change reference. Keep summaries factual and concise because they become searchable operational evidence. Export or retain records within the 30-day window if longer-term audit requirements apply. Do not treat the prompt as a substitute for pre-change review, post-change validation, or external approval controls.

12. Secure SD-WAN: Dynamic application steering: classification cache, SLA cost and best-quality selection

Primary source: FortiOS 8.0 Administration Guide — Dynamic application steering

Purpose. Application-based SD-WAN rules let the FortiGate choose a WAN path according to the application actually carried by a session, rather than only destination subnet or port. FortiOS uses Application Control signatures to identify the application. The selected strategy can then optimize for cost subject to an SLA, or choose the best measured link quality. This allows business-critical collaboration traffic to use preferred low-cost DIA circuits while less critical traffic chooses the best-performing available path.

Application recognition precedes rule matching

Enable Application Detection Based SD-WAN in Feature Visibility (or set gui-app-detection-sdwan enable in the CLI). Application Control must also be enabled in the firewall policy. On the first session, the IPS engine inspects application-layer traffic to match a signature. The first session does not match an application-based SD-WAN rule because the application has not yet been recognized. After identification, FortiGate records the destination IP, protocol, and port (the 3-tuple) in the application-control Internet Service ID list. Future sessions to that recognized 3-tuple can match the application-based SD-WAN rule. Entries with no hits for eight hours are removed.

This learning behavior explains a common troubleshooting symptom: the first connection to an application may use a different rule, while later sessions match the expected application rule. Applications with multiple destination IPs can also miss the expected rule if a new IP has not yet been recognized. The application ID alone is not a universal mapping to every IP used by a cloud service.

Lowest Cost (SLA) strategy

Lowest Cost (SLA) evaluates the required SLA first, then uses member cost and interface preference to select among qualifying links. In Fortinet's example, two DIA links have cost 0 and an MPLS backup has cost 20. Business applications such as Office 365, Google Docs, Dropbox, and SIP use a Required SLA target; if a DIA link passes, it is preferred because its cost is lower. When costs tie, Interface Preference breaks the tie. MPLS is selected only when the lower-cost members are not available according to the rule's SLA logic. If no member meets the SLA target but health checks remain alive, the selection proceeds to the next cost-selection step rather than assuming all paths are physically down.

Best Quality strategy

Best Quality selects based on configured quality criteria such as latency or available bandwidth, using the Measured SLA. It does not require an SLA target to be met in the same way as Lowest Cost (SLA). Fortinet documents a default 10% preference advantage for a more-preferred interface; for latency, the preferred link's calculated latency is adjusted by that factor. The advantage can be customized with link-cost-threshold for priority/auto modes. This means interface preference can intentionally influence the quality ranking, so it is not merely a cosmetic ordering.

Configuration and observability

config system global
    set gui-app-detection-sdwan enable
end

config system sdwan
    config health-check
        edit "BusinessCriticalApps_HC"
            set server "office.com" "google.com"
            set members 1 2 3
            config sla
                edit 1
                    set link-cost-factor packet-loss
                    set packetloss-threshold 1
                next
            end
        next
    end
    config service
        edit 1
            set name "BusinessCriticalApps"
            set mode sla
            set internet-service enable
            set internet-service-app-ctrl 17459 16541
            set health-check "BusinessCriticalApps_HC"
            set priority-members 1 2 3
        next
    end
end

Use diagnose sys sdwan internet-service-app-ctrl-list [app ID] to inspect recognized application and 3-tuple entries. Use diagnose sys sdwan health-check <name> to inspect loss, latency, jitter, and SLA state. Use diagnose sys sdwan service <id> to see the rule's selected members. The application list proves recognition/cache state; the health-check output proves probe measurement; the service output proves member selection. None alone proves that every destination IP used by the application is recognized or that the firewall policy permits the session.

Failure isolation and caveats

If the rule never matches, verify Application Control is attached to the policy and inspect the application-control list before changing costs. If the application is recognized but traffic still uses the wrong link, inspect the destination IP, rule order, SLA participants, thresholds, member costs, and tie preference. A cloud service that changes destination IPs may require new classification entries. Do not interpret an SLA target failure as a physical link-down state; a link can be alive while failing a quality threshold. Use Lowest Cost (SLA) when cost is primary but quality must be acceptable; use Best Quality when the goal is to choose the best measured path without a hard pass/fail target.

Operational application

For a branch with two DIA links and an MPLS backup, create a business-critical application rule with Lowest Cost (SLA), packet-loss threshold, and preference order DIA1, DIA2, MPLS. Create a separate Best Quality rule for noncritical video/social traffic using only the DIA links. Test first-session behavior and repeat-session behavior separately, then verify the cache, SLA measurements, and selected members. This gives the operator a clear explanation for why an application uses a path, rather than relying on destination IP assumptions alone.
