Today's 12 mechanism-level lessons

1. FortiGate — Domain external feeds inside DNS Filter

A domain-name external feed is not merely an address list. FortiGate periodically retrieves a text list, materializes it as a Remote Category, and lets a DNS-filter profile assign Monitor or Block semantics to matching queries. A remote-category match can override the domain's original FortiGuard category. The operational chain is therefore external server → external-resource retrieval → remote-category population → DNS query classification → DNS-filter action → DNS event log. Retrieval success does not prove matching semantics, and matching does not prove that the profile is attached to the traffic path.

Wildcard semantics matter. A wildcard subdomain entry such as *.example.com is intended for subdomains and should not be assumed to cover the parent example.com; include the parent explicitly when required. Fortinet also recommends server-certificate validation for the feed connection. For verification, first prove that the external resource is populated, then inspect the DNS-filter Remote Categories action, then prove the firewall policy applies that profile, and finally inspect DNS Query logs for the category/action.

Primary: FortiOS 7.6.6 Domain name external feed. Scenario: External-feed matching behavior.

2. FortiManager — Per-device dynamic mapping and install preview

FortiManager objects can carry a default definition plus device/platform-specific mappings. At install time, the target device receives the matching dynamic mapping; a nonmatching device receives the default. This means an object name being present in the ADOM is not sufficient evidence that a particular target receives the expected value. The resolution boundary is ADOM object → target scope → dynamic mapping → generated device configuration → install preview.

A recent operational case makes this concrete: adding an address to an address group could show “no change made on package” when the target used per-device mapping and the new member was not represented in that mapping. The correct troubleshooting boundary is therefore the resolved target representation, not merely the global object editor. Install Preview is strong evidence of what FortiManager intends to push; it does not prove the device has accepted the configuration until the install task completes and state is read back.

Primary: Per-device/per-platform dynamic mapping. Scenario: Address-group install mapping failure.

3. FortiAnalyzer — IOC, TIDB, rescanning, and licensing

IOC is a licensed post-breach analytics pipeline, not a synonym for raw IPS logging. FortiAnalyzer downloads FortiGuard's threat-intelligence database (TIDB), compares supported log evidence such as IPs, domains, and URLs, and aggregates threat evidence per endpoint. New TIDB packages make previous packages obsolete; rescanning lets historical logs be reevaluated against newer intelligence. Consequently, “the raw log exists” and “IOC can enrich it” are separate facts.

Useful boundaries are log ingestion → supported IOC field → TIDB availability → license → matching/scoring → endpoint verdict. A “no data found” attack-information symptom can therefore be a license/enrichment problem even though the underlying IPS log is visible. diagnose test application sqllogd 204 stats can expose post-breach-detection license/TIDB state. It proves the analytics substrate; it does not by itself prove that a specific endpoint's logs contain matchable fields.

Primary: FortiAnalyzer IOC. Scenario: IOC license/attack detail symptom.

4. FortiSwitch — DHCP snooping as a transaction gate

DHCP snooping validates DHCP messages arriving from untrusted sources and builds a binding database tying leased IP information to untrusted hosts. Ports are untrusted by default; trust must be assigned deliberately toward legitimate DHCP-server paths. The binding database becomes evidence for other controls such as DAI, so a broken DHCP-snooping transaction can have consequences beyond address assignment.

Troubleshooting must follow DORA rather than stopping at DHCPDISCOVER. On affected 110G switches running 7.6.8, Fortinet documented a case where debug showed DISCOVER accepted from an untrusted client port and forwarded toward the trusted group, but subsequent DHCP messages never completed; fixes are in 7.6.9 and 8.0.1. Seeing DISCOVER therefore proves ingress and initial snooping classification, not a healthy four-message DHCP exchange.

Primary: DHCP snooping. Scenario: 110G 7.6.8 DHCP transaction failure.

5. FortiAP — Airtime fairness is downlink scheduling, not client policing

Airtime fairness addresses the fact that low-rate or distant clients can consume disproportionate RF airtime. FortiAP applies configured airtime weighting from the AP transmit side. It is per SSID/VAP, can be applied on 2.4 and 5 GHz, works across bridge/tunnel/mesh VAPs and authentication types, and applies to data rather than management/control traffic.

The crucial implication is directional: an 80/20 VAP weight constrains AP-controlled downlink opportunity; it does not directly force uplink client transmissions into the same ratio. If a complaint is uplink-dominated, a correct airtime-fairness configuration may coexist with the symptom. Verification therefore requires radio/client counters and traffic direction, not just checking that weights exist.

Primary: FortiAP airtime fairness.

6. FortiNAC — Unknown-host isolation and Forced Registration

FortiNAC distinguishes host registration state from ordinary role-based access. Unknown devices can be placed into a Registration/isolation VLAN, but the access ports must participate in the Forced Registration group for that state-based control to be enforced. The Service Network Interface can provide DHCP, DNS, and captive portal services to isolation networks.

In Layer-3 designs, isolation VLANs generally exist per separated location/state, and NAT can hide the MAC identity FortiNAC needs. A device reaching production does not automatically mean VLAN-change signaling failed: first determine whether the port was actually subject to Forced Registration and whether the host was classified unknown. A community case where only Role-Based Access was selected reinforces this exact boundary.

Primary: Isolate unknown devices. Scenario: Registration VLAN assignment discussion.

7. FortiNAC-F — RFC5176 disconnect attributes are a contract with the NAS

RADIUS authorization and subsequent session termination are separate transactions. A network device can authenticate successfully yet ignore or never receive a useful Disconnect Message if the RFC5176 request lacks the attributes that identify the live session in the way that NAS expects. For an Aruba CX 6100 integration, Fortinet documents a custom RFC5176 mode including User-Name (1), NAS-IP-Address (4), NAS-Port (5), and Calling-Station-Id (31).

The troubleshooting sequence is Access-Accept → session establishment → policy-triggered enforcement → FortiNAC-F emits Disconnect/CoA → NAS correlates attributes to session → port/session changes. An Access-Accept proves authentication, not dynamic enforcement. A packet capture of the Disconnect request proves transmission, not that the NAS could correlate it.

Primary mechanism documentation: FortiNAC-F RADIUS/model configuration corpus. Scenario: RFC5176 Disconnect attributes.

8. FortiAuthenticator — SAML SP contracts: request, signature, ACS, assertion

When FortiAuthenticator acts as a SAML IdP, each service provider definition is a protocol contract: IdP entity/SSO/SLO identifiers, SP entity ID, ACS/SLS endpoints, optional request-signature validation, signing certificate/algorithm, NameID construction, and assertion attributes. A successful user authentication at the IdP does not prove that the SP will accept the assertion.

If “SAML request must be signed by SP” is enabled, FortiAuthenticator validates the request using the configured SP certificate or CA model. After authentication, the assertion still must target an acceptable ACS and contain the identity/attributes expected by the SP. Diagnose by stage: AuthnRequest arrival/signature → user authentication → assertion generation/signing → ACS delivery → SP validation. Certificate mismatch errors belong to the signature boundary, not the password boundary.

Primary: FortiAuthenticator SAML service providers. Scenario: SAML IdP common errors.

9. FortiPAM — Proxy mode is the observation point for session recording

A FortiPAM secret policy can require Proxy Mode and Session Recording. Proxy Mode puts FortiPAM in the user-to-target connection path; session recording then captures actions for access launched through that controlled path. This architecture explains why reachability to the target and successful privileged access are not equivalent to “FortiPAM can record the session.”

When troubleshooting, prove policy assignment, proxy mode, launcher path, PAM-to-target reachability, and recording generation separately. Native-launcher failures can occur on the endpoint-side TLS path even when WebSSH/WebRDP works. A documented native-launcher case showed an x509 unknown-authority failure in FortiTCS because the endpoint did not trust the CA signing the PAM server certificate. That evidence isolates endpoint launcher trust rather than target credentials.

Primary: Secret policy / proxy / recording. Scenario: Native launcher TLS failure.

10. FortiSIEM — Rules are event-to-incident state machines

A FortiSIEM rule begins with event filters and subpatterns, applies aggregation/grouping and relationship constraints, and then maps qualifying state into an incident. Exceptions and clear conditions alter the lifecycle after matching. Incident attributes are normally derived from Group By/filter/aggregate context, so a rule can receive the right raw events yet create misleading incidents if the grouping/incident mapping is wrong.

Starting with 7.4.0, Fortinet reserves numerous incident attributes because the system may set/overwrite them; existing custom rules using those attributes should be rewritten. For scheduled rules, subpattern capabilities also depend on storage environment. Test a rule before activation. Verification should prove raw event parsing, subpattern membership, threshold/aggregation, relationship timing, incident generation, and clear behavior separately.

Primary: FortiSIEM 7.4.2 Creating Rules.

11. FortiSASE — FortiExtender ZTP has registration, entitlement, provisioning, authorization boundaries

FortiExtender onboarding to FortiSASE is a multi-system transaction. The device and ThinEdge entitlement must be registered in FortiCloud; FortiZTP must have FortiSASE enabled as a provisioning target; the asset is provisioned to FortiSASE; and the FortiExtender is then authorized in FortiSASE. Firmware compatibility and clean prior configuration matter.

Alternative static discovery can point the FortiExtender at the FortiSASE domain; get extender status can then prove a nonzero controller address and management-state CWWS_RUN. A current support note adds another operational boundary: if integration still fails despite documented procedures, source-IP whitelisting may be required, especially when the edge has no static public IP. Thus entitlement success does not prove network admission, and controller discovery does not prove final authorization.

Primary: FortiExtender via FortiZTP. Scenario: FortiSASE/FortiExtender integration.

12. Secure SD-WAN — Passive health measurement uses real TCP sessions

Active SLAs send synthetic probes; passive WAN health measurement derives latency, jitter, and packet-loss information from live TCP sessions crossing policies with passive-wan-health-measurement enabled. When applications or Internet Services are defined in the SD-WAN rule, metrics can be differentiated by service/application even on the same WAN member. This matters because two applications sharing a link can experience different performance.

The evidence chain is firewall policy enables passive measurement → real TCP sessions produce samples → kernel/log telemetry records metrics → SD-WAN application/service SLA state is calculated → steering logic consumes it. No traffic means no meaningful passive sample; a healthy synthetic probe does not contradict poor application-specific passive metrics. Enhanced telemetry can expose RTT samples, directional jitter/loss, retransmissions, SYN/SYN-ACK retransmissions, and resets.

Primary: Passive health measurement by application.
